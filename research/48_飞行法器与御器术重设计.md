# 48 飞行法器与御器之术重设计（载体数据 / 许可技能两分）

> **用途**：按用户要求把"飞行法器"整套重做一遍——**法器里那条技能只描述"这辆车"**（速度、最大人数、坐还是站、
> 长什么样），**功法里另一条技能才是"能不能御器"**；有那条技能的人，才能拿**主手 / 副手**上的飞行法器起飞。
> **基准**：工作树现状（`data/ability/type/FlightAbilityType.java`、`FlightDisplay.java`、`runtime/artifact/FlightService.java`、
> `FlyingSwordEntity.java`、`FlightEventBridge.java`、`attachment/FlightAttachment.java`、`registry/MxtEntityTypes.java:21`、
> `registry/MxtAbilityTypes.java:24`、`runtime/ability/AbilityActivationService.java`、`AbilityService.java:224-248`、
> `runtime/wheel/{WheelSource,WheelSources,WheelService}.java`、`data/ability/{Ability,Togglable,ToggleContext}.java`、
> `data/cultivation/Technique.java`、`runtime/cultivation/CultivationGrantService.java`、`attachment/AbilityAttachment.java`）。
> 原版 / 平台事实取自本机源码包：MC **26.1.2**（`mergeWithSources_c6e4e114…_output.jar` 里的 `Entity.java` /
> `EntityAttachments.java`）与 NeoForge **26.1.2.109**（`IEntityExtension`）。`gradle.properties:7-11` 钉的是
> MC `26.1.2` + NeoForge `26.1.2.99`（同一个 MC；差的是 NeoForge 补丁号，本文引用的方法签名两版一致）。
> **状态**：**已于 2026-09-25 落地**（用户拍板："`mxt:flight` 删掉、按键留在术上——因为法器变成实体后是要从背包里拿走的，这时候法器自身的 ability 会自动失效"，即本文的方案 B 加上**真托管**）。落地记录见 §14；§11 里当时列的待拍板逐条给出去向。
> **关系**：本文**推翻** `35_御剑飞行系统设计.md` §2 表格里第 1、3、7 行与 §6.1 的字段形状（理由见 §12），
> 并**关闭**本轮盘点提出的四条遗留（生物御剑、起剑多付一次、几何死常数、Curios/背包口径）。

## 1. 结论：一件事拆成两条技能

| | 谁写 | 类型 | 按键吗 | 它回答什么 |
|---|---|---|---|---|
| **载具** | 法器的 `abilities` | `mxt:mount` | **不**（纯数据） | 这辆车：`speed`、`seats`、`sit`、`display`、几何、每 tick 燃料 |
| **御器之术** | 功法 / 灵根 / 体质 / 技能书 / 命令 / 脚本的 `granted_abilities` | `mxt:flight_control` | **是**（`Toggable`） | 你能不能御器：起剑一次的价格、冷却、条件、取哪只手、速度倍率 |

一句话流程：**按下轮盘上"御器之术"那一格 → 服务端从主手、其次副手找一件声明了 `mxt:mount` 的法器 → 造载具、
把驾驶者放上去 → 每 tick 由驾驶者付载具自己的燃料**。手上没有飞行法器就拒飞（`NO_VEHICLE`），有法器但没学
御器之术就根本按不下这一格（技能没被授予，轮盘上没有它，命令与脚本也过不了共用闸门）。

这样分的好处，正好是**上一条盘点里那些绕不开的问题一次全消**：

- "哪条技能在飞"不再靠法器的 id：飞的是**术**，车是术的实参；同一把剑换给谁、副手再拿一把，都不会读错状态。
- 术来自修行（功法/灵根/体质），法器只是**装备**——"能不能飞"与"飞什么"彻底分开，符合用户要的语义。
- 起剑一次的费用落在术上、每 tick 的燃料落在车上：上一条盘点发现的"起飞多付一次"从**缺陷**变成**设计**（§4.3）。
- 取用范围收成**主手 + 副手**：不再扫 Curios 与背包，也顺手消掉"飞行中物品被挪走算什么"的怪状态。

### 1.1 记下被否掉的另一种按法（方案 A）

也可以让**法器那格**当按键（载具类型实现 `Togglable`）、术只当被动许可（不实现 `Togglable`）。它有一处确实更好：
拿在手上就自动多一格，不用先去配置界面把术钉到主盘。但它有两个硬伤：

1. 用户的话是"**有这个技能的**可以使用飞行法器飞行"——被授予的许可才是玩家学到的、要按的东西；把按键留在法器上，
   术就退化成一条看不见的门槛，玩家按不动时只看到一句拒绝，不知道差什么。
2. 轮盘格的身份会继续是"某件法器的某条技能"，于是"两把剑都带了飞行"仍然是两个格子、两种状态，而它俩其实做同一件事。

真要选 A，改动是局部的：载具类型实现 `Togglable`（`activate` 里先查术），术类型退化成空类型——轮盘、附件、服务端
流程都不用动。**这是 §11 的第 1 条待拍板。**

## 2. 与现状的逐项差异

| 维度 | 现在 | 改成 |
|---|---|---|
| 谁描述车 | `mxt:flight`（法器侧，同时是按键格） | `mxt:mount`（法器侧，纯数据） |
| 谁能飞 | 只要法器在手就能按（`AbilityService.gate` 只查授予） | 必须另有 `mxt:flight_control` 被授予 |
| 状态记在哪 | `FlightAttachment.archetype` = 法器那条技能 | `archetype` = **术**；另加 `vehicle` = 载具能力 id |
| 取用范围 | 双手 + Curios + 玩家背包（`ArtifactService.carried`） | **只主手 / 副手**（`hand` 可指定 `main` / `off` / `either`） |
| 载具几何 | 死常数（`MxtEntityTypes.java:21`：`0.35 × 0.12`、`passengerAttachments(0.65F)`） | 定义给（尺寸 / 座位落点 / 步高），运行期按定义覆写 |
| 座位 | 1 个（其余乘客被 `startRiding(force)` 无视） | `seats`（1..4），多座位 + 右键上座 |
| 坐姿 | `shouldRiderSit()` 恒 `false`（站） | 定义 `sit`（默认 `false` 维持今天的样子） |
| 每 tick 燃料 | `mxt:flight` 自己的 `costs` | **载具**的 `costs`；起剑一次是**术**的 `costs` |
| 载具实体 | 会被存档，重启后自清 | 建议 `noSave()`（瞬发召唤物） |
| 失败原因 | 9 个 `FlightService.Failure` + 复用 `Togglable.Failure` | 多一个 `NO_VEHICLE`；`Failure.COLLISION` 按 `35` §7-F 处理（本次一并定） |

## 3. 数据形状

两条技能都还是**普通的 `mxt:ability` 注册表条目**（`docs/数据包格式.md:862` 那条"技能只定义一处"不变），
法器与功法只写 id 或 `#标签`。载具**不是**按键技能，所以它不需要承载物、不进轮盘、也不进配置界面的池子。

### 3.1 载具 `mxt:mount`（法器侧）

进入 `data/ability/type/MountAbilityType.java`，注册名 `mount`。**不实现 `Togglable`**。

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `speed` | `NumberProvider` | **必填** | 每 tick 的基础位移（格）。运行期求值后与术的 `speed_multiplier` 相乘，写进载具实体并夹在 `0.01..1.0`（沿用今天 `FlyingSwordEntity.setFlightSpeed` 的夹取） |
| `seats` | int | `1` | 总座位数（含驾驶者）。加载期夹在 `1..MAX_SEATS`（建议 `4`），越界报错而不是静默截断 |
| `sit` | bool | `false` | 乘坐姿势：`false`＝站（今天的 `shouldRiderSit() == false`）、`true`＝摆坐姿。**全车一个姿势**（原因见 §5.3） |
| `display` | `FlightDisplay` | `FlightDisplay.DEFAULT` | 载具怎么画，语义照原版物品模型的 `display`（`translation` 以 **1/16 格**记）。这个类型与编解码器**原样保留**，只是从 `mxt:flight` 搬到 `mxt:mount` |
| `width` / `height` | double | `0.35` / `0.12`（今天的常数） | 载具碰撞箱。XZ 是**正方**（原版 `EntityDimensions` 只有宽高），长条造型靠视觉，见 §6.4 |
| `seat_offsets` | `Vec3[]` | 按 `seats` 摊开（座位 0 在 `passengerAttachments` 的原点，其余沿模型方向后退 `0.8` 格） | 每个座位相对载具原点的落点（格：X 右 / Y 上 / Z 前）。只读前 `seats` 个，多写的忽略 |
| `step_height` | double | `0` | 载具的 `maxUpStep()`——今天恒 0，"一点台阶都上不去"（`35` §4） |
| （顶层 `costs`） | `Cost[]` | `[]` | **每 tick 的燃料**，驾驶者付（origin 仍是 `CostOrigin.ARTIFACT_FLIGHT`）。付不出即落地 |
| （顶层 `condition`） | `EntityCondition` | 恒真 | **每 tick 复查**：不满足即落地。写法与 `mxt:modifier` / `mxt:aura`"每轮重算 condition"的口径一致 |
| （顶层 `name` / `description`） | 文本 | 按四段式生成 | 提示框上那一行"载具 · …"用的就是它自己的名字 |

其余顶层字段（`entity_action`、`target_selector`、`modifiers`、`components`、`cooldown`、`cast_time`…）对载具**没有意义**：
它从不被"施放"，所以这些字段在落地时改成**加载期报错**（§14.4 第 3 条），`docs/数据包格式.md` 里写清哪几个键不能声明。

```json
// data/example/mxt/ability/azure_sword_mount.json —— 青霜飞剑那辆车
{
  "type": "mxt:mount",
  "speed": 0.12,
  "seats": 2,
  "sit": false,
  "width": 0.6, "height": 0.15,
  "seat_offsets": [[0, 0, 0], [0, 0, -0.8]],
  "display": {"translation": [0, 0, 0], "rotation": [90, 0, -45], "scale": [2, 2, 2]},
  "costs": [{"id": "mxt:qi", "amount": 2}]
}
```

法器侧（不变的那个形状）：

```json
// data/example/mxt/artifact/sword/azure_flight_sword.json
{
  "items": "minecraft:iron_sword",
  "abilities": ["example:azure_sword_mount"],
  "require_owner": false
}
```

### 3.2 御器之术 `mxt:flight_control`（功法侧）

进入 `data/ability/type/FlightControlAbilityType.java`，注册名 `flight_control`。**实现 `Toggable`**。

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `hand` | `main` / `off` / `either` | `either` | 从哪只手找载具。`either` = **主手优先，主手不是载具再看副手**；`off` 可以专门写"副手御剑" |
| `speed_multiplier` | `NumberProvider` | `1.0` | 乘在载具 `speed` 上。加载期要求有限且 `> 0`；运行期非有限 → 拒飞 / 落地（`INVALID_FORMULA`） |
| （顶层 `costs`） | `Cost[]` | `[]` | **起剑一次**的价格，走共用闸门（`AbilityService.gate`，origin `ABILITY`），与今天的口径一致 |
| （顶层 `cooldown`） | `NumberProvider` | `0` | 起剑冷却。由共用闸门写入；**落地不写**（落地永远是免费的） |
| （顶层 `condition`） | `EntityCondition` | 恒真 | 起剑条件（共用闸门校）。**飞行中不复查**——途中条件变假不该把人扔下去（要复查就写载具的 `condition`，它每 tick 看） |
| （顶层 `name` / `description`） | 文本 | 按四段式生成 | 轮盘那一格与提示框上的名字 |
| `state()` | — | — | 读 `FlightAttachment`：有在飞的、且 `archetype` 就是自己 → `true`（沿用今天 `FlightAbilityType.state` 的写法） |
| `gated()` | — | — | 没在飞 → `true`（起剑过闸门）；在飞 → `false`（落剑免费、不查条件与冷却） |

```json
// data/example/mxt/ability/sword_control.json —— 御器之术
{
  "type": "mxt:flight_control",
  "hand": "either",
  "speed_multiplier": 1.0,
  "costs": [{"id": "mxt:qi", "amount": 5}],
  "cooldown": 20
}
```

功法只写引用（`Technique.grantedAbilities`，`Technique.java:41/56`）：

```json
// data/example/mxt/technique/qingfeng_sword_art.json
{ "granted_abilities": ["example:sword_control"] }
```

`granted_abilities` 按境界分层也照旧（`Technique.StageConfiguration.abilities`）：入门只给术、化境再给
`speed_multiplier` 更高的另一条术，是内容层的事，本体不需要新字段。

**来源不限于功法**：术就是一条普通技能，灵根 / 体质 / 技能书 / 战利品函数 / `/mxt ability` / KubeJS 都能授予它
（`CultivationGrantService.recalculate` 已经把功法、灵根、体质三种来源都走通，`AbilityEventBridge` 管装备来源）。
功法只是最自然的那条路。

## 4. 起飞与飞行

### 4.1 起剑（一次按下）

1. 轮盘（或命令 / 脚本）→ `WheelService.trigger` → `WheelSources.offers` 先复核"这个来源此刻还认不认这一项"
   （主盘看存档布局、从盘看授予账）→ `AbilityActivationService.activate`。
2. `FlightControlAbilityType.activate`：`state()` 为真 → `FlightService.dismount(holder, STOPPED)`，**到此结束**（免费）。
3. 否则 `gated()` 为 `true` → `AbilityService.gate`：**已授予**（`abilities.has`）、冷却、`condition`、术的 `costs` 一次付清。
   这一步同时把起剑冷却写进 `mxt:cooldown`。
4. **找车**：按 `hand` 读主手 / 副手 → `ArtifactService.definition(access, stack)` 解出法器定义 → 该堆的 `abilities`
   里第一条 `mxt:mount`（`ArtifactService.abilities` + 类型过滤，与今天 `ArtifactService.flight` 同一条读法）。
   都没有 → `Togglable.Failure.NO_VEHICLE`（**新增枚举值**）。
5. **判权**：`ArtifactService.mayUse(stack, definition, holder.getUUID())`（沿用 `require_owner` 的既有语义）→ 不过就 `NOT_OWNED`。
6. **算数**：`speed = mount.speed(ctx) × skill.speed_multiplier(ctx)`，有限且 `> 0`（否则 `INVALID_FORMULA`）；
   读出 `seats` / `sit` / `display` / 几何。
7. **造车**：按定义的几何建 `FlyingSwordEntity`（§6），`setVisual(stack.copy())`（**传副本**，理由同今天：
   载具持有的是交进来的那个堆，而主手那个堆别处会改），`addFreshEntity`，驾驶者 `startRiding(vehicle, true, true)`；
   `startRiding` 失败 → `discard` + `CANNOT_MOUNT`。
8. **记档**：`FlightAttachment.start(...)` 写 `archetype`（术）、`vehicle`（载具能力 id）、`started_at`、
   玩家飞行前权限快照（`CREATIVE_FLIGHT` 属性、`flying`、`flyingSpeed`，与今天一致）、`vehicle_uuid`。

### 4.2 每 tick（驾驶者的 `EntityTickEvent.Post`，服务端）

`FlightEventBridge` 的分工不变（每只生物都过一遍、`getExistingData` 判有没有记录、客户端早退）：

| 检查 | 不过时 |
|---|---|
| 术的 id 仍解析得出来（`Abilities.resolve`，自带 `mxt:disabled` 过滤） | 落地 `NOT_FLYABLE` |
| 载具能力 id 仍解析得出来且类型仍是 `mount`、未被 `mxt:disabled` | 落地 `NOT_FLYABLE` |
| 载具实体还在、`vehicle_uuid` 对得上、驾驶者仍是控制者 | 落地 `MOUNT_LOST` |
| 载具的 `condition` 成立 | 落地 `CONDITION_FAILED`（新出口） |
| 速度重算后写入实体 | 非有限 / `≤ 0` → 落地 `INVALID_FORMULA` |
| 载具的 `costs` 由驾驶者付（`CostTransaction.pay`，origin `ARTIFACT_FLIGHT`） | 落地 `INSUFFICIENT_RESOURCE` |
| 碰撞（`35` §7-F 已拍板"让 `COLLISION` 生效"） | 落地，见下表末行 |

**飞行中不再要求手里还握着那件法器**（§11 第 4 条待拍板）：载具实体自己带着那份视觉副本，物品挪到哪儿都不影响
飞行；燃料与速度都从**记录的载具能力 id** 读，不回头翻物品（`35` §6.4 的"托管"因此**不需要做**——东西从没被拿走）。

### 4.3 两笔费用（口径写死）

| 时机 | 谁的价格 | 谁付 | origin |
|---|---|---|---|
| 起剑（一次） | **术**的 `costs` | 驾驶者 | `ABILITY`（共用闸门） |
| 每 tick（含起剑那一 tick 之后的每 tick） | **载具**的 `costs` | **先扣载具里那件法器存的同门灵气**，扣得动的部分不碰驾驶者，余额由驾驶者付 | `ARTIFACT_FLIGHT` |
| 落剑 | 无 | — | — |

这正好把上一条盘点里的发现（今天同一个 `mxt:flight` 的 `costs` 在起剑时被闸门收一次、之后每 tick 再收一次）
变成**两个字段各自的一笔账**：想让起剑便宜、维持贵，写两个数即可；不想收起剑费就把术的 `costs` 留空。

### 4.4 失败原因

`Togglable.Failure` 现在 15 个值（`Togglable.java:47-65`）。这次只**新增 `NO_VEHICLE`**（手上没有飞行法器），
其余全部复用：`NOT_OWNED`（未认主 / 不是主人）、`INVALID_FORMULA`、`CANNOT_MOUNT`、`ALREADY_SET`、`COOLDOWN`、
`CONDITION_FAILED`、`INSUFFICIENT_RESOURCE`、`INSUFFICIENT_COST`、`NOT_GRANTED`（术没被授予）。文案表
`actionbar.mxt.ability.failure.*` 加一条即可（两份 lang 都要加）。

## 5. 多人：座位、上座、驾驶者

### 5.1 原版事实（逐条核过 26.1.2 源码）

| 事实 | 出处 | 对设计的影响 |
|---|---|---|
| 座位落点按**乘客序号**取：`getPassengers().indexOf(passenger)` → `attachments.getClamped(PASSENGER, index, yRot)` | `Entity.java:2346-2349` | 多座位**原版就支持**，只要挂点多、序号对得上 |
| `canAddPassenger` 默认"只能一个乘客" | `Entity.java:2456-2458` | 载具必须覆写它，否则第二个人上不来 |
| `startRiding(vehicle, **force=true**)` 会**跳过** `canAddPassenger` | `Entity.java:2374` | **座位上限必须由载具自己守**；今天的 `mount` 用的就是 `force=true` |
| `getControllingPassenger()` 默认返回 `null`（不是第一个乘客） | `Entity.java:3427-3429` | 驾驶者要自己点名，否则"谁在开"没有答案 |
| `shouldRiderSit()` **没有参数**（NeoForge `IEntityExtension` 的 default 方法） | `IEntityExtension`（javap） | 座位姿势只能**全车一个**，做不到"驾驶坐、乘客站" |
| `isPickable()` 默认 `false` | `Entity.java:1918-1920` | 想让别人右键上座，必须覆写成 `true` |
| `canRide` 要求"没在潜行、且 `boardingCooldown <= 0`" | `Entity.java:2396-2398` | 潜行按右键不会上座（原版口径，照用） |

### 5.2 座位与上座

- `seats` 是**总人数含驾驶者**，`MAX_SEATS = 4`（常量，加载期校验）。
- 驾驶者＝**按下术的那个人**，坐 0 号位；1..n-1 号位是乘客。
- 乘客入口（**默认方案**）：**对载具按右键**（`Entity#interact` 覆写 + `isPickable() == true`）→ 有空位就
  `startRiding(vehicle, false)`（**force=false**，让 `canAddPassenger` 与 `canRide` 生效），满员则回一条
  actionbar 文案。飞行中同样允许上座（悬停接人比"只能落地接人"更好玩，也更省一套状态）。
  - 0.35 格高、贴脚的箱子不好点中，所以多座位载具应当同时把 `width`/`height` 写大一点（§6.4）。
  - 备选入口：**右键驾驶者**＝请求上座（更好点中，但语义绕一层）；**只允许契约兽自动上座**（接 `47` 的
    `ContractOperations`/跟随行为）。两条都进 §11 待拍板。
- 驾驶者落剑 / 死亡 / 掉线 → 载具 `discard()`，**全体乘客一起下**（原版 `ejectPassengers`）。不做"无人载具继续飞"，
  免得留下幽灵车；将来真要"换人接着开"，那是单独的玩法。

### 5.3 姿势

`sit` 是**车**的属性，不是座的属性（`shouldRiderSit()` 无参，见 §5.1）。所以"驾驶者站着、乘客坐着"这种写法
本轮不支持——要支持得改渲染侧读取方式（不在本设计范围内）。默认 `false` ＝保持今天实机确认过的"站在剑上"。

### 5.4 移动

- 驾驶者必须是**玩家**（`ServerPlayer`）：位移来自 `getLastClientInput()` / `getLastClientMoveIntent()`，
  生物没有这两样。**上一条盘点里"生物御剑在实机活不过一 tick"由此变成明确口径而不是缺陷**：生物可以**当乘客**，
  不能当驾驶者；"NPC 御剑"若要做，得另给一套脚本驱动的速度来源（§11 第 12 条，建议推迟）。
- 乘客不产生输入，只是被载具带着走；每 tick 燃料仍**只由驾驶者付**。

## 6. 载具实体与几何（覆写点已逐条核对）

`runtime/artifact/FlyingSwordEntity.java` 继续是**一个**实体类型（`registry/MxtEntityTypes.java:21` 的
`flying_sword`），只是把写死的几何换成"读定义"。**建议顺手加 `noSave()`**：它是按键召唤出来的瞬发载具，
不该在世界里留一份孤儿；掉线/重启后靠附件的 `MOUNT_LOST` 自愈（今天已经这么写，见 `35` §5.4）。

| 定义字段 | 覆写的原版方法 | 依据 |
|---|---|---|
| `width` / `height`、`seat_offsets` | `getDimensions(Pose)` → `EntityDimensions.fixed(w, h).withAttachments(EntityAttachments.builder().attach(PASSENGER, v0).attach(PASSENGER, v1)…)`，改完调 `refreshDimensions()` | `Entity.java:3626-3628`（默认读实体类型）、`EntityDimensions.withAttachments`、`Entity.java:3308-3314`（`refreshDimensions` 重算并修正位置） |
| `step_height` | `maxUpStep()` | `Entity.java:3849` |
| `seats` | `canAddPassenger(Entity)`：`getPassengers().size() < seats` | `Entity.java:2456`（默认只容一个） |
| 驾驶者 | `getControllingPassenger()` → 0 号位乘客（是玩家才给输入） | `Entity.java:3427`（默认 `null`） |
| `sit` | `shouldRiderSit()` → `!sit`（站姿） | NeoForge `IEntityExtension`（默认 `true`＝坐） |
| 右键上座 | `interact(Player, InteractionHand)` + `isPickable() == true` | `Entity.java:1918`（默认不可拾取） |
| `display` / 外观 | 已有：`DATA_VISUAL`（同步的载体物品堆）+ `FlyingSwordRenderer` | 现状不动 |

### 6.1 客户端怎么知道几何（不新增同步字段）

载具已经同步了"它画的那件物品"（`DATA_VISUAL`），而渲染器**今天就是**用
`ArtifactService.flight(registryAccess, visual)` 逐帧解析定义的。沿用同一条路：客户端与服务端都从
`visual` 那份堆解出 `mxt:mount`，再算尺寸、座位落点与坐姿；解不出来（空堆、旧存档、定义被删）就退回
实体类型注册时的兜底几何。这样：

- **不需要**给几何加新的同步项，客户端与服务端永远同一份解析结果（数据包本来就是双端同步的）；
- `/reload` 改 `width` 立刻双端生效（与 `display` 同口径）；
- 代价是每次 `getDimensions` 都可能走一遍法器解析 → **按实体实例缓存一份，`DATA_VISUAL` 变化时失效**
  （实现细节；渲染器那条逐帧查询照旧，别在这里顺手改口径）。

### 6.2 载具实体类型注册时的兜底

`EntityType` 在数据包之前就注册完了，所以 `MxtEntityTypes:21` 仍要写一对兜底值（建议就留今天的
`0.35 × 0.12` + 一组 `passengerAttachments`），定义给出的值在运行期覆写。`noLootTable()`、`MobCategory.MISC`、
`clientTrackingRange(10)`、`updateInterval(1)` 都不动。

### 6.3 没有血条

载具是普通 `Entity`，`showVehicleHealth()` 默认 `this instanceof LivingEntity` 为假（`Entity.java:2355-2357`），
原版 GUI 也只对 `LivingEntity` 画坐骑血条——`35` §2 第 9 行的结论不受本次改动影响。

### 6.4 已知取舍：正方碰撞箱 vs 长条造型

`EntityDimensions` 只有宽高，原版 AABB 在 XZ 上是**正方**。所以一把 3 座位、视觉 3 格长的剑，要么把 `width`
开到 3（飞起来更容易卡在方块之间），要么让箱只盖住中间一段（座位 2、3 悬在箱外）。**建议：箱只盖住车体**，
把它交给定义（`width`/`height`），并在文档里写明"箱管碰撞、视觉管观感"——这正是 `35` §7-H 那道待拍板，
本次把旋钮交出去，不再由本体写死。

改成每 tick 都真的 `move()`（§14.4 第 1 条），撞到方块/地面即落剑。

### 14.5 燃料改成"先烧法器、数字可以是小数"（2026-09-25，用户追加两条）

1. **燃料的数值口径**：`mxt:mount` 的 `costs` 仍然是**每 tick** 一笔（口径不变，`AGENTS.md` §7 的"倍率语义"因此没有动），但测试夹具把数字改小了——原来 `2` / `3` 每 tick 是 40/60 点每秒，太快；现在青霜飞剑 `0.1`、沧海舟 `0.15`（= 2/3 点每秒）。

### 14.6 驾驶输入与"客户端权威"（2026-09-25，用户实机报"激活后没法移动"）

**症状与根因**：起飞成功、人坐在剑上，但按 WASD 一点都不动。根因是**两条原版规则撞在一起**（都不是本模组自己的 bug）：

1. `FlyingSwordEntity` 的驾驶者是玩家，而 `Player#isClientAuthoritative()` 是写死 `true` 的，于是**客户端把载具当成"自己的"**：`ClientPacketListener#handleMoveEntity` 在 `entity.isLocalInstanceAuthoritative()` 为真时**只更新位置差分解码基准、根本不移动实体**（`handleEntityPositionSync` 同样在真时整段跳过）。也就是说服务端每 tick 发出去的位置，客户端一格都不采纳。
2. 客户端自己不模拟（`tick` 在 `isClientSide` 处早退），于是它报回去的永远是**出生时那个坐标**；服务端 `handleMoveVehicle` 收到就把载具 `absSnapTo` 回那个点。两边一夹，剑被钉在原地。

**定案（用户拍板）**：位移仍然**只在服务端算**（服务端权威的口径不动），客户端不再宣称权威。三处改动：

- `FlyingSwordEntity#isLocalClientAuthoritative()` 覆写为 `false`——客户端于是走 `moveOrInterpolateTo` 那条路，正常采纳服务端位置，也不再每 tick 发 `ServerboundMoveVehiclePacket`；
- `FlyingSwordEntity#tick` 里的 `interpolation.interpolate()` **提到客户端早退之前**（`InterpolationHandler` 只在 `interpolate()` 里改坐标，早退就等于永不动）；
- 位移仍是"读 `ServerPlayer` 的 `getLastClientInput()` / `getLastClientMoveIntent()` 再 `move(MoverType.SELF, …)`"，碰撞标志与 `Failure.COLLISION` 的判据因此不变。

**同时按用户要求补的两件事**（都在同一轮）：

1. **下降改用独立按键**：原版"潜行 = 下坐骑"（`Player#rideTick` → `wantsToStopRiding()`）与"潜行 = 下降"不能共存，用户选择**加一个可重绑的下降键**（`key.mxt.flight_descend`，默认 `X`）——潜行于是保留原版含义（按下去就是落剑、法器还回来）。它是按住状态而不是一次性触发，所以自走一条 `FlightDescendC2SPayload`（按下/松开各发一次，上座那一刻补发一次），服务端把它写在驾驶者那份**飞行记录**上（`FlightAttachment#descend`，**不落盘**），飞行 tick 每刻读一次。
2. **新增服务端配置「飞行 → 朝视线方向飞行」（`flight.follow_look`，默认 `true`）**：开启时前进/后退沿视线方向（抬头爬升、低头俯冲），左右仍是水平平移（把意图在 yaw 坐标系里拆成前后/左右，再用视线向量与 yaw 右向量拼回去，所以斜着看天不会加速）；关闭时四个方向都只在水平面上——也就是 14.5 及之前的旧手感。跳跃上升与下降键两种方式两种情况都可用（它们**替换**而不是叠加移动里的垂直分量）。

**没跑的**：本轮仍**未开实机**，以上都是对着 26.1.2 反编译源逐行核出来的（`ClientPacketListener#handleMoveEntity` / `#handleEntityPositionSync` / `#handleMoveVehicle`、`ServerGamePacketListenerImpl#handleMoveVehicle` / `#tick` 的"载具漂浮超时"只在收到过载具移动包时才计数、`LocalPlayer#tick` 的 `isLocalInstanceAuthoritative` 分支、`Entity#isLocalInstanceAuthoritative` / `isLocalClientAuthoritative` / `moveOrInterpolateTo`、`InterpolationHandler#interpolate`）。实机要看的正是"按 W 剑往前飞、按 X 下沉、按 Shift 落剑"这三条。

### 14.7 座位调试指令与"驾驶者一走就结束"（2026-09-25，用户追加两条）

1. **`/mxt flight fill`（= 顶层 `/flight fill`，第 18 个别名，`requires(mayChange)`）**：把**当前玩家所骑载具**的空座位全塞上僵尸，用来对着实机调 `seat_offsets`。实现是 `FlightService.fillSeats(sword)`——`freeSeats()` 读的就是定义里的 `seats`，每个空位 `EntityType.ZOMBIE.create(level, COMMAND)` 后 `setNoAi(true)`（不思考、不攻击）、`setPersistenceRequired()`（不消失）、头上塞一顶**加了 `UNBREAKABLE` 的铁头盔**、记一个 `mxt:seat_dummy` 标签，再 `startRiding(sword, true, true)`；位置**不用自己算**——乘客位置每 tick 由载具的 `positionRider` 按定义摆，所以 `/reload` 改完立刻换位。头盔那一条不是装饰：`Mob#aiStep` 对 `BURN_IN_DAYLIGHT` 标签的生物调 `burnUndead()`，而它只在**头盔格子为空**时才 `igniteForSeconds(8)`（有东西就只磨损它、且坏掉才清空），所以"非空且不可损坏"的头部物品等于完全免疫日晒——否则白天调座位时参照物会在 20 秒内烧死。这些标记是载具自己的垃圾：`FlyingSwordEntity#remove(shouldDestroy)` 里连同 `giveBack()` 一起把带标签的乘客 `discard()`（遍历乘客表的副本，避免边删边遍历）。没在飞、座位已满分别有自己的文案。**这条只编译，未实跑。**
2. **驾驶者下线即结束**：原来 `tick` 只要求"0 号位是个活着玩家"，于是**驾驶者掉线后，后面那位乘客会被顶到 0 号位、接管这趟飞行**——而 `FlightEventBridge` 只对**持有飞行记录的人**跑，燃料因此不再扣、也没人付，等于白飞。现在多一条判据：`this.owner`（起剑时写下的 UUID，已在存档里）必须等于 0 号位乘客，否则 `discard()`。它一次覆盖下线、死亡、被挤出 0 号位三种情况；`discard()` 走 `setRemoved` → 乘客统一 `stopRiding` 放下，法器照 14.4 的规则归还（主人在线进背包、不在线落在原地）。

### 14.8 载具自己的行为与尾迹粒子（2026-09-25，用户追加）

`mxt:mount` 新增两个字段，都是这一轮从"数据"扩到"会做事"：

1. **`mount_action`**：`on_mount` / `on_dismount` / `tick` 三个可选 `EntityAction`（`MountActions` 记录，整组 `.optionalFieldOf("mount_action", MountActions.NONE)`，三个字段各自 `EntityAction.optionalCodec` 默认 `mxt:no_op`）。**都跑在驾驶者身上**——载具是普通 `Entity`，`mxt:apply_effect`、资源、经验这些行为对它没话说；要动载具本身（粒子、位置）另有 `trail` 与 `mxt:teleport` 一类。挂点：`on_mount` 在 `FlightService.mount` 里 `startRiding` 成功、飞行记录写好之后（此时法器已收进载具）；`tick` 在 `FlightService.tick` 里**燃料付清之后**（所以能跑到的 tick 都是付过钱的）；`on_dismount` 在 `FlightService.dismount` 里、`stopRiding` **之前**（钩子还能看见"人骑着车"这个状态）。驾驶者已经不在的那条路（掉线 → 载具自己 `discard`）没有可执行对象，因此不跑——已在文档里写明。
2. **`trail`**：`MountTrail` 记录（`particle` 必填，`interval` / `count` / `speed` / `spread` / `offset_x` / `offset_y` / `offset_z` / `moving_only` 有默认），由**载具实体自己**在自己的 `tick` 里发（`ServerLevel#sendParticles` 那条不带 player 的重载，一次给整张世界的玩家，看不看得到由客户端自己的距离规则决定）。两个刻意的取舍：**`spread` / `offset` 按格算**（`mxt:spawn_particles` 会把 `spread` 乘上实体尺寸，而载具是一块 `0.35 × 0.12` 的薄板，尺寸对尾迹没有意义）；**`moving_only`**（默认 `false`）让作者能选"悬停也发"和"只留真尾迹"两种。有限性照 §4 的口径在加载期校验（`RAW_CODEC.validate(...)`，与 `FlightDisplay` 同一写法：`MAP_CODEC` 供内部、`CODEC = MAP_CODEC.codec()` 供字段引用——嵌套定义给字段用的必须是 `Codec`，`MapCodec` 上并没有 `optionalFieldOf`）。**`particle` 是原版 `ParticleTypes.CODEC`，只认对象形式** `{"type": "minecraft:end_rod"}`；夹具最初写成裸 id 字符串，2026-09-25 实机启动直接以 `Failed to parse mxt_test:azure_sword_mount` / `Not a JSON object: "minecraft:end_rod"` 报错并让整张 `mxt:ability` 注册表加载失败（世界都进不去），这正是"数据包包体字段写错必须报错"的预期行为——`mxt:spawn_particles` 的 `particle` 同理。文档已写清对象形式。
3. **探针与夹具**：`azure_sword_mount` 加了两个 `mxt:play_sound`（起剑 / 落剑）与一条 `end_rod` 的 `moving_only` 尾迹；`cloud_skiff_mount` 加了 `tick` 粒子与一条 `cloud` 尾迹。`/mxt_test artifacts` 的载具腿把新字段并进原有断言，另加一条"只读被写出来的那一个钩子、其余默认"的腿（标签 `artifact roster mount reads mount_action=on_mount sound and trail interval=4 moving_only`）。**仍然只编译、未实跑。**
