# 法器开关与轮盘接线设计（`ToggableArtifactAbility`）

> **已于 2026-09-23 被 [`40_能力与法器能力合并设计.md`](40_能力与法器能力合并设计.md) 取代**（代码层面）。本文描述的
`ToggableArtifactAbility`、`ArtifactToggleService`、`ArtifactCapability`、`WheelEntryKind.ARTIFACT` 与
`mxt:artifact_ability_type` 全部删除：接口升格为与宿主无关的 `data/ability/Toggable`（`mxt:active` / `mxt:flight` /
`mxt:storage` 三个技能类型实现它），一键入口是 `runtime/ability/AbilityActivationService`，轮盘 kind 收成 `EMPTY` /
`ABILITY` / `AURA`，条目身份就是它自己的注册表 holder（`Holder<Ability>`）。**本文仍值得读的**是它的推理过程（为什么"要按键"
> 该有一个统一判据、"状态归实现自己管"、储物复用原版箱子界面、空槽位编解码那个坑）；§7.2/§7.3/§7.4/§7.6 的具体结论已写进 `41` 与
`docs/数据包格式.md`。

> 基准：2026-09-22 的代码与文档——[`31_多轮盘与轮盘来源设计.md`](31_多轮盘与轮盘来源设计.md)（多轮盘、从盘来源、主盘/从盘编号）、
`data/artifact/ability/`（`ArtifactAbility` 的六个内置类型）、`runtime/wheel/`（`WheelSource` / `WheelSources` /
`WheelService`）、`screen/wheel/`（`WheelContent` / `WheelEntryKind` / `WheelMenuEntry`）。
>
> 触发这次设计的原话：「我发现 ArtifactAbility 你只把主动触发的写入了轮盘，考虑在 ArtifactAbility 基础上写一个
> ToggableArtifactAbility 接口，只要实现这个接口说明需要塞入轮盘」，以及「武器的对应我记错了，武器的技能也是走 artifact 的，只要做
> artifact 的就行」。

## 1. 问题

轮盘的从盘（主手 / 副手 / 法器）读的是**技能账本**（`AbilityAttachment.sources()`），而且只列 `type` 为 `mxt:active` 的技能（
`WheelSources.abilities` 那行 `instanceof ActiveAbilityType`）。这是对的：轮盘只负责"施放"，被动 / 触发 / 光环 /
蓄力都不是按一下能放的东西。

但**法器自身的能力条目**（`Artifact.abilities` 里的 `ArtifactAbility`）根本不在这本账上——`mxt:flight`、`mxt:storage`、
`mxt:upkeep` 是"这件法器能干什么"，由别的入口驱动。于是出现两个后果：

1. 一件法器的飞行开关进不了轮盘。它今天甚至**没有任何玩家入口**：`FlightToggleC2SPayload` /
   `ServerNetworkHandler.onFlightToggle` / `NetworkManager` 的注册三件套都在，客户端**没有任何发送点**（
   `FlightService.mount` 只被服务端处理器与 `/mxt_test` 调用）。也就是说"御剑"目前只能靠命令或脚本触发。
2. 将来任何"常驻开关"型法器能力（护体、剑域、引灵入刃……）都没有统一的"该不该进轮盘"的表达方式。

## 2. 结论

### 2.1 新接口：实现即进盘

`data/artifact/ability/ToggableArtifactAbility extends ArtifactAbility`，语义只有一句：**这个法器能力是一个常驻开关，必须出现在轮盘上
**。接口把三件事交给实现自己回答：

| 方法                                              | 含义                                     |
|-------------------------------------------------|----------------------------------------|
| `boolean enabled(ArtifactToggleContext)`        | 现在开着没有。两侧都问：客户端画状态，服务端决定往哪边翻。          |
| `Result toggle(ArtifactToggleContext, boolean)` | 开到 / 关到指定的那一侧，返回"变了没有 + 为什么没变"。只有服务端调。 |
| `Component displayName()`                       | 轮盘这一格叫什么（如"飞行"）。                       |

`Result(boolean changed, @Nullable Failure failure)` 与 `Failure{NOT_CARRIED, NOT_OWNED, ALREADY_SET, UNAVAILABLE}`
是轮盘唯一需要的词汇：失败原因进日志 + 一条 actionbar 文案，因为"按了没反应"在轮盘上没有任何别的线索（与 31
号设计里技能/灵气失败的口径一致）。

**开关状态归实现自己管**：飞行用现成的 `FlightAttachment`（每玩家一份 + 记着是哪个 `archetype`），本轮**不**
新增通用开关存储。理由是通用存储要回答"按件还是按格、跨槽位算不算同一个开关"这些还没有消费者的问题；等第二个开关型能力出现时再定，落在
`mxt:artifact_state` 或独立附件都只是局部改动（见 §6）。

### 2.2 条目身份 = 法器自己的 id

`WheelEntryKind` 新增 `ARTIFACT`，id 用**法器定义的注册表 id**（不是能力类型 id）。也就是说轮盘上这一格回答的是"哪件法器"
，而"是哪个开关"由那件法器给出的 `displayName()` 回答。这个选择的直接后果：

- `Artifact` 只允许**一个**实现 `ToggableArtifactAbility` 的条目，构造期拒绝第二个（异常文案与 `mxt:flight` /
  `mxt:storage` / `mxt:upkeep` 的"每样一次"同一口径）。一件法器要两个开关就得拆成两条定义——目前不需要，真需要时给条目加一个
  `key` 字段即可（见 §6）。
- `WheelEntryKind.ARTIFACT.exists(access, id)` = 这个 id 在 `mxt:artifact` 里能解析**且**
  它声明了开关。于是布局校验不会收下"随便一个法器 id"。

### 2.3 出现在哪里

| 位置              | 为什么                                                                                 |
|-----------------|-------------------------------------------------------------------------------------|
| 从盘：主手 / 副手 / 法器 | 这三张盘本来就按"来源"读玩家身上的东西；开关属于那件法器，所以出现在声明它的那张盘上，物品拿走就跟着消失（与技能同一口径，不存任何东西）。              |
| 主盘（配置界面右侧那个池子）  | "塞入轮盘"就是能钉在主盘上：池子 = 玩家持有的 active 技能 + 玩家携带的法器开关，可点进 12 格、可清空。主盘的格子是编号存储，id 与从盘完全同源。**2026-09-26 收紧**：只有**Curios 槽位**上的法器开关还在池子里，**主手 / 副手**物品声明的开关不再进池（手里的东西说换就换，那两张从盘页才是它的位置）——见本表下方的修订。 |

从盘上的顺序：**先技能（按 id 排序），再开关（按法器 id 排序）**。两段各自确定，合起来也确定。

> **2026-09-26 修订（用户点名）**：主盘池子里的**法器开关只保留 Curios 槽位上那件**——主手 / 副手物品声明的技能不再进池。
> 起因是实机看到"储物"出现在配置界面右池（`mxt_test:spirit_gathering_jade` / `cloud_beast_bell` / `bound_sword` 都声明 `mxt:storage`），
> 用户口径是"这个应该绑物品上"。落地形状：`WheelSources.handOnly(entity, ability)`（持有它的来源**全是** `mxt:equipment/...` 就算手部物品）
> ＋ `WheelContent#options`（编辑器用，`#pool` 仍是那 12 格的解析名单，所以**已经钉好的格子照旧解析、服务端照旧受理**）；
> tooltip 最后一行改写成来源（`学习的技能` / `X的技能` / `其它来源`，原来是第 3 行的「法器：X」；X = 承载物品名，按品质上色、无品质则金色）。
> §5 那条验收项（"把「飞行」或「储物」钉到主盘某一格"）现在只在**法器放在 Curios 槽**时成立。

### 2.4 触发链路一个字都不改

仍然是 `WheelActionC2SPayload(source, kind, id)`：客户端说"从哪张盘、哪种条目、哪个 id"，服务端按**页来源**重读一遍（
`WheelSources.offers`），再执行。

- 请求的语义是**翻转**，不是"设成开/关"：客户端不传目标状态，服务端读自己的 `enabled(...)`
  再取反。客户端本来就不可信，这样连"客户端猜错状态"这类不一致都不存在，也不需要新包。
- 与 `FlightToggleC2SPayload`（带 `enabled` 字段）的区别就在这里：那个包是"请求某个状态"，轮盘这条是"翻一下"。**本轮不动那个包
  **（删注册包属于要先问的事，见 §6）。

### 2.5 第一个实现者：`mxt:flight`

`FlightArtifactAbility implements ToggableArtifactAbility`：

- `enabled` = `FlightAttachment.active()` 且记着的 `archetype` 就是本定义（客户端读得到：这个附件是 `.sync(...)` 的）。
- `toggle(true)` → `FlightService.mount(player, stack, artifact, context)`；`toggle(false)` →
  `FlightService.dismount(...)`。失败原因映射：`NOT_OWNED` → `NOT_OWNED`，`ALREADY_ACTIVE` → `ALREADY_SET`，其余 →
  `UNAVAILABLE`。
- `displayName` = `wheel.mxt.artifact_toggle.flight`（"飞行" / "Flight"）。
- 状态在 HUD 格子上的表达：`accentColor()` 开 = 绿、关 = 灰（HUD 格与配置界面都画这条 2px 底线），tooltip 再写一行"
  状态：已开启 / 已关闭"，并带上法器自己的名字。

顺带：`mxt:storage` **不**实现这个接口。它是"打开一个界面"，不是"开/关一件事"，硬塞进来会让这两件事在轮盘上长得一样。

## 3. 与现状的差异（本轮改动清单）

| 位置                       | 之前                                     | 之后                                                                                |
|--------------------------|----------------------------------------|-----------------------------------------------------------------------------------|
| `data/artifact/ability/` | 只有 `ArtifactAbility` 与六个类型             | 多 `ToggableArtifactAbility` + `ArtifactToggleContext`；`FlightArtifactAbility` 实现它 |
| `Artifact`               | flight / storage / upkeep 各限一次         | 再限"开关条目一次"，并给出 `toggable()`                                                       |
| `runtime/artifact/`      | `ArtifactService`（定义、归属、灵气）            | 多 `ArtifactToggleService`（把"玩家身上的法器开关"读出来 / 找一个 / 翻一下）                            |
| `WheelEntryKind`         | `EMPTY` / `ABILITY` / `AURA`           | 多 `ARTIFACT`（`exists` 要求"是法器且声明了开关"）                                              |
| `WheelSources`           | `abilities` / `offers`                 | 多 `equipment(entity, source)` 与 `toggles(entity, source)`；`offers` 处理 `ARTIFACT`  |
| `WheelContent`           | 从盘 = active 技能；池子 = 持有的 active 技能      | 从盘 = 技能 + 开关；池子 = 技能 + 携带的开关（`pool(...)`）                                         |
| `screen/wheel/content/`  | `AbilityWheelEntry` / `AuraWheelEntry` | 多 `ArtifactWheelEntry`                                                            |

| 数据包                      | `mxt:flight` 只让法器能飞                    | 同一个字段、同一个类型，`mxt:flight` 现在还作为一格进轮盘                                               |
| 探针                       | `/mxt_test wheel` 五条腿                  | 多两条：从盘列出开关 / 真翻一次（挂上飞剑再落地）                                                        |

## 4. 不做的部分

- **武器的对应**：用户澄清"武器的技能也是走 artifact 的"，所以 `weapon_binding` 不动，也不新增 `WeaponAbility` 体系。
- **通用开关存储**：见 §2.1。`mxt:artifact_state` 不加字段，老存档不受影响。
- **失败原因细分**：飞行的 `INVALID_FORMULA` / `CANNOT_MOUNT` 合并成 `UNAVAILABLE` 一档文案；要细究看日志（服务端那行记的是接口的失败枚举）。真需要细分时给
  `Failure` 加值即可。
- **主盘编号语义**：与 31 号设计一致——编号只是位置，开关进池子不改变"编号仅用于存储、真正释放传 source + id"。
- **`FlightToggleC2SPayload` 的处置**：本轮不删不改。它现在是零发送点的注册包，删它属于"注册 vs 删除"那类要先拍板的事。**2026-09-25 拍板并落地**：并入 `WheelActionC2SPayload` 的可选 `enabled`（留空＝按了这一格、填了＝点名一个状态），旧包、`ServerNetworkHandler.onFlightToggle` 与它在 `NetworkManager` 的注册都删除——见 `research/48` §14.4。

## 5. 验证方式

- 编译：`./gradlew.bat compileJava compileTestModJava --console=plain`。
- `/mxt_test wheel`（需实机，先问）：原有五条腿 + 新增四条（见 §7.6）。要看的输出：
    - `wheel probe: capabilities=2 ... OK`——主手盘列出两格、副手盘与法器盘不列、`ARTIFACT.exists` 认"法器 + key"这一对而不认裸
      id。
    - `wheel probe: flight flipped=true pilot=true OK`——经 `ArtifactToggleService`（也就是轮盘那条路径）挂上
      `FlyingSwordEntity`，再关掉落地。
    - `wheel probe: storage opened=true pilot=true OK`——同一条路径开出一行九格的箱子，再关掉。
    - `wheel probe: storage sync contents=9 stored=3 OK`——带一个空槽位的储物组件走一遍**注册的网络编解码**（
      `container_set_slot` 用的就是它），空槽位与物品都要原样回来。这条腿是 2026-09-22 实机报错的回归断言，由来见 §7.6。
- 主盘方向只能在客户端看：把「飞行」或「储物」钉到主盘某一格，按使用键应当起剑/落剑、或打开箱子；从盘则在把剑拿到手上时自动出现这两格。（**2026-09-26 起**：要钉上去，那件法器得在 **Curios 槽**里——拿在手上的法器其技能不进池子，见 §2.3 的修订。）

## 6. 开放项

1. **`FlightToggleC2SPayload` 零发送点**：要么删（连同 `ServerNetworkHandler.onFlightToggle` 与 `NetworkManager`
   的注册），要么让它成为"脚本/别处请求指定状态"的入口。轮盘不走它。
2. **`WheelEntryKind.ARTIFACT` 在主盘上的过期格子**：主盘存的是 `法器/key`，玩家把法器放下后那一格在配置界面显示 `?`
   （与技能过期同一表现），按下去由服务端拒绝并提示"这件法器不在身上"。
3. **每客户端刻的成本**：主盘的池子（`WheelContent#pool`）现在每刻重算一次，其中 `CuriosIntegration.equipped` 会拷贝栈、
   `ArtifactService.definition` 会扫一遍法器注册表。以今天的量（双手 + 几个 Curios 槽 +
   几十条定义）可以忽略，但它落在客户端每刻路径上；法器定义很多的内容包值得再量一次，真要省就在
   `WheelSelectionState#refresh` 那层加一次每刻缓存（语义不变，池子本来就只在每刻解析一次）。
4. **储物窗口每刻也重解析一次**（`ArtifactStorageContainer#stillValid` → `ArtifactService#carried` 扫背包 +
   Curios）。只在窗口开着时有成本，且同样可以先量再优化（比如缓存一次解析结果、只在槽位变动时失效）。
5. **储物超过 54 格**：见 §7.4，夹到 54。要真正支持更大的储物就得做分页界面（多页槽位重映射 + 整窗重发），那是另一个设计。

## 7. 修订：储物也算技能，界面复用原版箱子（2026-09-22 同日）

> 依据：用户「储物的你好像没做技能开关，参考一下 E:/Java/Origins-NeoForge
> 那个」「备注一下：所有需要按键激活的都可以算作技能，进入轮盘」，以及「起源主要是参考一下怎么做的储物」。

**判据从"开关"放宽成一句话**：凡是要按键才发动的都算技能、都进轮盘。于是 `ToggableArtifactAbility` 不再只表示"能开能关"
，它表示"需要按键"，`mxt:storage` 也实现它，`mxt:flight` 仍是第一个实现者。

### 7.1 接口从"翻转"改成"按下"

| §2 里的形状                       | 现在                                                               |
|-------------------------------|------------------------------------------------------------------|
| `boolean enabled(ctx)`        | `Optional<Boolean> state(ctx)`：**空 = 一次性**（没有开/关这回事，如储物），有值 = 开关 |
| `Result toggle(ctx, boolean)` | `Result activate(ctx)`：按下了；做什么由实现决定（飞行读自己的 `state` 决定往哪边，储物直接开箱） |
| —                             | `String key()`：同一件法器内唯一的能力名，进入轮盘条目身份                             |

参考实现给的就是这个形状：Origins-NeoForge 的 `data/power/Toggleable`（`KeySettings getKey()` + `toggle(holder, key)`）是"
按键激活"的统称，连 `InventoryPower`（打开容器）都实现它；"现在是不是开着"另放在 `Power#isActive`，只有真有状态的类型（
`TogglePower`）才覆盖。我们照这个把**"要按键"和"有状态"分成两件事**，于是储物天然没有状态那一行。

### 7.2 条目身份 = 法器 id + key

`mxt_test:bound_sword` 同时声明飞行与储物 ⇒ §2.2 的"一件法器一个开关"必须撤。改成 `ArtifactCapability(artifact, key)`
，把身份拼成 `命名空间:路径/key`（`ArtifactCapability#id` / `#parse`；key 由代码给出、不含斜杠，所以取路径里最后一个 `/`
就是切分点，法器自己的路径里有 `/` 也不影响）。`Artifact` 构造期的检查从"最多一条开关"改成**同一个 key 只能一条**，
`WheelEntryKind.ARTIFACT.exists` 也从"是法器且声明了开关"改成"这一对真的存在"（裸法器 id 一律为假）。

### 7.3 储物界面：原版箱子，零自绘

照 `InventoryPower` 的做法：激活时 `player.openMenu(...)`，界面**直接复用原版容器菜单**——所以注册的是 `ChestMenu`（新
`MxtMenus.ARTIFACT_STORAGE`，行数走 `IMenuTypeExtension` 的附加数据），客户端注册 `ContainerScreen`（原版 `generic_54.png`
本来就画 1..6 行）。**没有新菜单类，也没有新界面类。**

内容那一侧是 `ArtifactStorageContainer extends SimpleContainer`：开窗时从 `mxt:artifact_storage` 组件读出来（**已于 2026-09-26 修正**：内容改存物品组件 `mxt:storage` 里的 `mxt:container`，按技能自己的 id 寻址，见 `54`），之后每次
`setChanged()` 整份写回（`ArtifactStorageService#replace` → `ArtifactStorageComponent#of`，一次组件更新而不是每格一次）。*
*它故意不持有那个物品堆**：Origins 的容器活在能力组件里，天然没有"物品跑了"的问题；我们的内容挂在物品上，所以每次读写都按
`ArtifactService#carried` 重新解析"这件法器还在不在玩家身上"（双手 + 背包 + Curios），`stillValid`
一旦为假，原版每刻的菜单检查就把窗口关掉。这是本轮唯一一处比参考实现多出来的东西，原因就是"内容在物品上"。

### 7.4 格数：按 9 取整、最多 54

原本 `MAX_STORAGE_SLOTS = 256`，但界面是箱子，而**容量与窗口必须是同一个数**——否则最后一行会出现"点得进去却存不下"的格子。改成
`storageSlots = min(ceil(声明 / 9), 6) * 9`（`ArtifactService#storageSlots`；常量 `STORAGE_COLUMNS` / `MAX_STORAGE_ROWS` /
`MAX_STORAGE_SLOTS`）。代价写进文档：**声明超过 54 格的定义被夹到 54**，旧存档里若真有第 55 格起的内容将读不到（测试包最大 27
格，不受影响）。参考实现的 `InventoryComponent` 自己也标着 "Max 54 Items"。

### 7.5 格子画什么

法器技能格**不画法器的物品图标，改画能力名**：一件法器的两个技能若都画同一把剑就分不出谁是谁，哪件法器由 tooltip 说。颜色由状态决定：
**开=绿、关=灰、一次性=紫**。行动栏文案从「切换失败」改成中性的「使用失败：<原因>」（`actionbar.mxt.wheel.use_failed` +
`actionbar.mxt.artifact_skill.*`），语言键随之从 `artifact_toggle` 改名成 `artifact_skill`，轮盘条目种类名也从「法器开关」改成「法器技能」。

### 7.6 验证

`/mxt_test wheel` 第 6~8 条腿：主手页列出**两格**（`bound_sword/flight`、`bound_sword/storage`，前者 `state = 关`、后者没有状态）、
`ARTIFACT.exists` 认这一对而不认裸法器 id、飞行真起剑落剑、储物真开出一行九格的箱子并关闭。

**第 9 条腿（同日实机报错之后补的）**：带一个空槽位的储物组件走一遍注册的网络编解码。实机那次报的是
`Failed to encode packet 'clientbound/minecraft:container_set_slot'`，根因在**空堆**——储物用 `ItemStack.EMPTY` 表示"
这一格是空的"，而 `ItemStack.CODEC`（以及 `STREAM_CODEC`）明确拒绝空堆（`count` 必须 1..99、物品不能是 `minecraft:air`），于是*
*装着带洞的储物组件的那件法器自身**一被同步就炸整个包：窗口看着正常，东西却过不去。修法是把组件编解码换成
`ItemStack.OPTIONAL_CODEC.listOf()`（`data/artifact/ArtifactStorageComponent`，网络侧的
`ByteBufCodecs.fromCodecWithRegistries` 跟着一起好）；同一条 codec 也用于落盘，所以那次报错同时意味着带洞的储物**存不进存档
**。腿 9 就是这条路径的回归断言——探针只有跑 codec 才看得见它，开窗口本身不会出错。房规已记进 `AGENTS.md` §4。
