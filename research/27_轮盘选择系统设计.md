### 1.1 抄了什么

- **判扇区只看方向，不看距离。** MineMenu 用鼠标相对窗口中心的角度决定选中项，指针还在内圈里也算数。这条必须保留：它让"文字画在中间"成立——中心那块空地永远显示"当前指着的扇区叫什么"，玩家不用把鼠标甩出去才能看到名字。
- **一个扇区一个平四边形。** MineMenu 的扇环不是三角形扇，而是一扇一个四边形的近似。本仓在它之上把每扇再切成 `ARC_SEGMENTS = 6` 段：12 扇每扇 30°，若只画一条弦，外缘会比圆周凹进 `r(1−cos15°) ≈ 3.3px`，12 边形一眼看得出来。
- **选中扇区向外扩。** MineMenu 把选中扇内外各推 2（在它的 130 缩放制下），本仓是内外各推 `SELECTED_GROW = 3` GUI 像素。
- **开场动画。** MineMenu 用 `animationTimer` 从 20 起每刻减 5，扇环半径按它整体缩放。本仓改成**时间驱动**（见 §1.5），但缩放语义相同：整个扇环从 72% 长到 100%。
- **交互组合。** 按住显示 / 按键切换（`mode`）与"松开即选中 / 按住再左键点"（`release_to_select`）两两组合，MineMenu 就是这么给的。
- **界面不暂停、不画背景。** MineMenu 覆写 `isPauseScreen() → false` 与空 `extractBackground`。本仓照做，理由见 §1.6。

### 1.3 一个事实只留一份：指针角度 → 扇区号只有一处

MineMenu 里这段换算是**抄了三遍**的：`mouseClicked`、`renderText`、`RadialMenuBackgroundElement#buildVertices` 各算一次，而且约定还不完全一致——前两处先 `mouseAngle -= ANGLE_PER_ITEM / 2` 再 `360 - mouseAngle`，绘制那一处只减了半格、**没有取反**，只因为绘制用的是 `currAngle + 90 + 半格`（另一套圆心偏移）才碰巧对上。这正是 `research/26` §1.4.1 ③ 记的那类 bug 的温床：同一件事写两处，两处各自演化。

本仓只有一个映射：`WheelGeometry.sectorAt(angle)`，`sectorStart` / `sectorCentre` / `sectorAt` 三者由同一组常量推出，且互相自洽（`sectorAt(sectorCentre(k)) == k`，绘制用 `sectorStart(k)..sectorStart(k+1)` 正好是 `sectorAt` 那一格）。命中、绘制、图标摆位全部从它派生。角度约定写在类注释里：**0° 指向屏幕右方，角度增大朝屏幕下方（即视觉上顺时针），第 0 扇的中心在屏幕正上方**（屏幕坐标 y 向下，正好就是 `atan2(dy, dx)` 与 `cos/sin` 的原生约定，不需要翻来翻去）。

### 1.4 按键不能用 `KeyMapping.isDown()`（踩出来的坑）

本仓其它按键都走 `MxtKeyMappings.KeyMappingHolder` 的 `isDown()` 变化。轮盘**不能**这么做，原因在 `Minecraft#setScreen`：

```java
if (screen != null) { this.mouseHandler.releaseMouse(); KeyMapping.releaseAll(); ... }
```

任何界面一打开，原版就把**所有** `KeyMapping` 置为松开（`KeyMapping#release()`：`clickCount = 0; setDown(false)`）。轮盘一开，我们自己的按键立刻变成"松开了"，下一帧控制器就会认为玩家松手——在"松开即选中"模式下，轮盘会在出现的那一帧自己选中并关掉。

所以控制器按 MineMenu 的办法**直接读原始输入状态**（`InputConstants.isKeyDown(window, key)`；绑定成鼠标键时用 `GLFW.glfwGetMouseButton`），`KeyMapping` 仍然保留，只为让这个键出现在原版按键设置里、能被改键。副作用与 MineMenu 相同：轮盘的开合判定精度是**客户端刻**（20 Hz），一次短于 50ms 的点按可能被漏掉；连续两次开合必须在两次客户端刻之间松开再按下。这是可接受的代价，写在类注释里。

另外两条来自同一处：`Screen.removed()` / "当前屏幕不再是我们"时控制器必须**放弃引用而不去关屏**（否则会把玩家刚打开的那个界面关掉）；关屏统一用 `Minecraft#setScreen(null)`（与原版 `Screen#onClose` 的效果一致，并且会 `grabMouse()` 把准心收回来）。

### 1.5 参数与观感

| 常量 | 值 | 说明 |
| --- | --- | --- |
| `WheelGeometry.SECTORS` | `12` | 登记表按它开数组，扇区角 = `360/12 = 30°` |
| `INNER_RADIUS` / `OUTER_RADIUS` | `56` / `96` | 满尺寸下的内外半径（GUI 像素）。内圈留出来给中间文字，环宽 40 够放 16px 图标 |
| `MARGIN` | `8` | 窗口太小时整体缩小：`scale = min(1, (min(宽,高)/2 − 8) / 96)`，所以 240 高的窗口里半径是 104→自动缩到放得下 |
| `OPEN_SCALE` | `0.72` | 开场动画的起始缩放，`160ms` 内 ease-out 长到 1 |
| `SELECTED_GROW` | `3` | 选中扇内外各推多少（按 `Ring#scale` 同倍缩放） |
| `ARC_SEGMENTS` | `6` | 每扇切成几段四边形 |
| 颜色 | 底色 `0xB010131D`、选中 `0xE0FFD24A`、空扇区 `0x6010131D`、中间文字底板 `0xB010131D`、文字 `0xFFFFFFFF` | 选中色沿用 HUD 编辑器那一支金色；**暂不做成配置项**，见 §3 |

动画时钟用 `System.nanoTime()` 起算（单调、不受系统时间调整影响），而不用 MineMenu 的"每刻减 5"：那种写法在 20 Hz 下肉眼可见地跳，而轮盘只活几百毫秒。

### 1.6 界面语义（为什么是 `Screen` 而不是 GUI 层）

轮盘是**模态选择**：只在按键按下时存在，需要玩家用指针指方向。做成 `Screen` 有两个直接好处：`Minecraft#setScreen` 会 `releaseMouse()`，指针自然可用（`MouseHandler#xpos/ypos` 给的是窗口像素，角度与 GUI 缩放无关）；松手后 `setScreen(null)` 又会 `grabMouse()` 把准心收回，与原版操作手感一致。做成常驻 GUI 层反而要自己处理指针捕获。

两个覆写：

- `isPauseScreen() → false`：单人游戏里开着轮盘不应该暂停世界。
- `extractBackground(...)` **留空**：`Screen` 默认在"非游戏内界面"时会走 `extractBlurredBackground`（`blurBeforeThisStratum`，糊掉此前提取的整层 HUD）再叠一层菜单底色。轮盘是浮在世界上的一层选择器，既不需要虚化世界，也不该把底下的 HUD 一起糊掉——这与 `HudEditScreen` 当初为同一个模糊问题覆写 `isInGameUi()` 是同一件事，只是这里直接不画背景。

### 1.7 交互状态机

```
每客户端刻：
  若 记录的轮盘屏 ≠ 当前屏 → 丢弃记录（被 ESC / 别的界面关掉了）
  若 记录还在 且 没有世界 → 关屏
  down = 原始按键状态
  若 down == 上一次 → 返回
  down 为真：
    没开着 → 打开（要求：当前没有任何界面 且 登记表非空）
    开着 且 模式=切换 → 选中（方式=松开）并关闭
  down 为假：
    开着 且 模式=按住 → 松开即选中 则 选中（方式=松开）并关闭；否则只关闭
```

"选中并关闭"的顺序是**先关屏、再执行回调**：这样回调里开自己的界面（比如以后接"打开功法面板"）不会被紧接着的关屏顶掉。指着的扇区是空的时，回调不执行，但轮盘照样关——轮盘只有一条规则：**手势结束就关闭，选中与否取决于那一扇里有没有东西**。

## 2. 与现状的差异

- **不动任何现有模块**：`screen/wheel` 是新包，只新增文件，加上 3 个既有文件的小改（`MxtClientConfig` 加分类、`MxtKeyMappings` 加一个按键、两份 lang 各加 6 键）。快捷栏、资源条、法器、技能都没接进来。
- **按键 R**：用户先选了 `V`，但 `V` 已是 `HotbarModeRegistry.SPIRIT_KEY`（`key.mxt.spirit_burst`，发射灵力）的默认键——两个绑定会同时生效（按住 V 会一边开轮盘一边发灵力）。确认后改用 MineMenu 自己的 `R`，本仓当前无人占用。
- **登记表初始为空**，因此**默认按 R 什么也不会发生**（`WheelMenuRegistry.isEmpty()` 时不开轮盘）。这是"只做框架"的直接后果，不是故障；验证方式见 §4。

## 3. 不做 / 推迟的部分

1. **没有编辑界面**：扇区内容只能由代码登记（`WheelMenuRegistry.register(slot, entry)`），没有游戏内改图标 / 改标题 / 拖位置 / 存配置的入口。
2. **颜色与半径不是配置项**，是常量。MineMenu 有 8 个颜色配置（`Config.VISUAL`），本仓先按"框架先跑起来"的口径留常量；要不要给玩家调，等有内容接进来再定（数据包 vs 玩家设置）。
3. **没有二级分类 / 翻页**：只有 12 个槽位，第 13 条内容没有地方放，登记时直接抛异常而不是静默丢弃。
4. **没有"不可用 / 冷却中"状态**：MineMenu 也没有；技能那类条目接进来时会需要（灰掉并拒绝选中），届时再加一个 `enabled()`。
5. **没有音效**：HUD 编辑器拾取元素有 `UI_BUTTON_CLICK`，轮盘开合与选中目前是静音的。
6. **没有手柄 / 键盘选扇区**：只有指针方向。键盘可访问性（方向键转扇区）与 HUD 编辑器的方向键微调是一个性质的事，但轮盘更依赖指针，先不做。
7. **每帧重算、不缓存**：12 个扇区的顶点每帧重建（48 个四边形），量与一个 HUD 元素同级别，不值得缓存。
8. **按住轮盘时角色会停下**：原版 `Minecraft#setScreen` 对任何界面都调 `KeyMapping.releaseAll()`，移动键随之松开（`KeyMapping.setAll()` 只在 `MouseHandler#grabMouse()` 里、也就是"没有界面"时才重新按物理键状态同步）。松开轮盘键时 `setScreen(null)` → `grabMouse()` → 按键状态自动恢复，不需要重新按。MineMenu 同样是 `Screen`，同样如此。**要"边跑边开轮盘"就得改成 GUI 层并自己接管指针**（不释放鼠标、自己算角度），代价是全部指针捕获与事件穿透都要自己写——本轮按参考实现的口径不做。

## 6. 2026-09-22 改版：R 只负责选择，V 负责使用

> 本节由原 `research/29_轮盘选中与使用设计.md` 并入（2026-09-22 合并，29 不再单独存在）。**取代** §1.1 的「交互组合」、§1.7 的状态机、§2 与 §4 里关于 `release_to_select` 的写法；几何（§1.3）、渲染（§1.5）、`Screen` 语义（§1.6）、按键读原始输入（§1.4）全部继续成立。

**起因**：原设计是"按住 R、**松开即选中并触发**"，一个键同时承担"选"和"用"。用户要求拆成两个键：`R` 只**选择**，`V` 负责**使用**。

用户拍板的四点：

| 问题 | 选择 |
| --- | --- |
| V 什么时候能用 | **轮盘关着也能用**——记住上一次选中的那一扇 |
| 按 V 之后轮盘关不关 | **保持打开**，可以连按 V 用不同扇区；松开 R 才关闭 |
| 「松开即选中」配置 | **删掉**（松开已经不再触发） |
| 轮盘开着时左键 | **等同于 V**（也能使用） |

### 6.1 手势

```
按住 R ──► 轮盘打开，指针指哪一扇就选中哪一扇（金色高亮 + 中间写名字）
   │
   ├── 按 V（或左键）──► 用掉当前指的那一扇；轮盘不关，可以继续按
   │
   └── 松开 R（HOLD）/ 再按一次 R（TOGGLE）──► 关闭；**不触发**
                                              关闭时那一扇成为"当前选中"

轮盘关着时按 V ──► 用掉"当前选中"那一扇
```

- `R` = `key.mxt.wheel`（默认 `R`，不变）；`V` = `key.mxt.wheel_use`（**新增**，默认 `V`）。原来的 `key.mxt.spirit_burst`（`V`）已随灵力快捷栏删除，所以 `V` 是空的。
- `mode`（HOLD / TOGGLE）保留；`release_to_select` 删除。
- 选择与使用**都只发一次既有的 `WheelActionC2SPayload(kind, id)`**：服务端看到的仍是"某一格被触发"，它不需要知道玩家按的是 R 还是 V。

### 6.2 "当前选中"存在哪

新增客户端状态 `screen/wheel/WheelSelectionState`：一个 `int sector`（`-1` = 还没选过），**内存里，客户端不写档**（跨会话那半存在服务端附件里、由它填回来，见 §7）。

- 轮盘打开期间每帧把指针所在扇区写进去，所以 HUD 会跟着指针动。
- 关闭轮盘时保留，于是关着也能按 V。
- **`ClientPlayerNetworkEvent.LoggingIn` 时清空**：选中属于"这一次会话"。否则上一个世界的第 7 扇会被带到下一个服务器上，而那里第 7 扇可能是别的东西——按一下 V 就放了个没想放的技能。
- 条目在**用时**才解析（`WheelMenuContent.entry(player, sector)`），与轮盘画面同一套规则：授予被撤销 / 定义被删 / 灵气不再付得起，那一扇当场变成"没有目标"，V 什么都不做。解析结果**每个客户端刻刷新一次并缓存**（`WheelSelectionState#refresh`，由控制器在刻里调用）：HUD 那一格每帧都要读它，而解析要走一遍灵气注册表并逐条求值"能不能发射"的公式，不能 60 次/秒地做。
- **跨会话记住需要服务端存**（`wheel_layout` 附件加字段 + 一条上送通道）：2026-09-22 已做，见 §7。

### 6.3 为什么两个键都读原始输入（在 §1.4 之上又一条理由）

§1.4 记的是"打开界面时 `KeyMapping.releaseAll()`，所以 R 不能用 `isDown()`"。V 还多一条：

- 若关着的时候用 `KeyMappingHolder` 的边沿检测，那么"按着 V 松开 R"这一下会在关界面那一帧被 `MouseHandler#grabMouse()` → `KeyMapping.setAll()` 补成一次 `false→true`（`setAll` 按真实物理状态重置 `isDown`），于是**多触发一次**。
- 一个键只在一处判边沿就没有这个问题：`WheelMenuController` 同时轮询 R 与 V，V 的按下边沿只处理一次，再按"轮盘开着 → 用指针那一扇 / 关着 → 用记住的那一扇"分派。

代价与 R 相同（§1.4）：边沿每客户端刻采一次，短于一 tick 的点按会漏。`WHEEL_USE` 与 `WHEEL` 一样**只注册进按键表**（能在原版按键设置里改键），**不带 `onStateChange` 回调**。

另外，关着的时候还要求 `Minecraft#screen == null` 才使用：否则在聊天栏里打一个 `v` 就会放技能。轮盘开着时按键本来就归屏幕，不存在这个风险。

### 6.4 界面与 HUD

- **轮盘中间**：名字下面那一行，可用时写「按 `V` 使用」（键名取实际绑定，改键后跟着变），不可用时写「冷却中 4.3s」——两者共用原来那一行，不新增高度。**冷却改成秒**（2026-09-22 用户要求）：原来按"剩余比例 × 100%"报百分比，玩家从中学不到任何能行动的信息；附件里本来就存着"冷却结束在哪一 tick"，所以直接算剩余 tick、由 `WheelDuration.seconds` 统一写成**永远一位小数**的秒数（tooltip 的「冷却 / 施法」也用这同一个格式），`WheelMenuEntry` 的钩子随之从 `float cooldown(Player)`（0..1 比例）改成 `long cooldownTicks(Player)`（剩余 tick，0 = 就绪），`usable()` 语义不变。
- **左键**：`WheelSelection.Method.CLICK`，与 V 同一条路径（不关闭轮盘）。`Method` 由 `RELEASE`/`CLICK` 改成 `KEY`/`CLICK`，条目仍可区分是键盘还是鼠标。
- **新增可拖动 HUD 元素「轮盘选中」**（`screen/overlay/wheel/WheelSelectionEntry`，布局键 `wheel.selection`）：画选中那一扇的图标，没有图标就画名字开头几个字（与扇区、配置格子同一套规则），底下一条类型色带（灵气蓝 / 技能金），不可用时压一层暗色；没有选中时只画一个空槽框，这样它在布局编辑器里永远看得见、拖得动，也顺带告诉玩家"现在 V 没有目标"。默认位置与资源条两列站在同一条线上（屏幕底部居中，两列之间那道空隙里）。
- 有了这个元素，"关着也能按 V"才成立：否则玩家按下去之前不知道会放什么。

## 7. 2026-09-22 续：选中的条目跨会话持久化

**起因**：用户点名「当前激活的技能也做一下持久化，但是得 Optional，如果 Holder 解析失败了就转 `Optional.empty()`，给个 warning 不报错」。§6.6 第 1 条原本把这件事列为开放项（"要服务端存"）。用户同时拍板了存法：**存 `kind + id`（复用已有的 `WheelSlot`），解析不到就清空 + warning**，而不是"技能一个 `Holder` 字段、灵气再来一个"。

### 7.1 存什么，为什么不是扇区号

- 存 `WheelSlot`（`WheelEntryKind` + `Identifier`）而不是 `int sector`。扇区号离开它当时的那份布局就没有意义：玩家在两次会话之间把技能挪到别的扇区，记忆应当跟着**条目**走，而不是跟着"第 7 扇"走。
- 位置是**同一个** `wheel_layout` 附件的 `selection` 字段（`Optional<WheelSlot>`）。放同一个附件是因为它同步给本人、脏标记与整包同步的路径都已经在跑；用 `Optional` 是因为"什么都没选"是个真实状态，而它同时就是解析失败的落点——用户要的 `Optional.empty()`。
- **不新增 S2C**：附件本来就会同步给玩家自己，客户端恢复时读到的就是服务端认下的那一份。
- 上送走新的 `WheelSelectionC2SPayload`（`wheel_selection_c2s`，`Optional<WheelSlot>`）。没有把选中项塞进 `WheelLayoutC2SPayload`：那条通道的语义是"配置界面保存了一整份布局"，而选中项在轮盘每次换扇区时都可能变。
- 用户原话里的 `Holder` 在这个存法下不存在（id 是 `Identifier`，不会解码失败）；等价的失败点是"这个 id 解析不到定义"与"这一条已经不在 12 格里"，两者都按 `Optional.empty()` + warning 处理。

### 7.2 谁在什么时候做什么

| 时机 | 动作 |
| --- | --- |
| 玩家加入后第一次拿到附件 | `WheelSelectionSync#consult`：把 `selection` 找回它所在的扇区写进 `WheelSelectionState`；找不到或解析不到 → `LOGGER.warn` + 把空值写回服务端（所以只警告一次） |
| 指针换到另一个扇区 | `WheelSelectionSync#tick` 发现 `WheelSelectionState.sector()` 变了 → 发 `WheelSelectionC2SPayload`（空扇区就发空） |
| 配置界面保存布局 | `WheelContent.save` 顺手 `republish()`：存下来的值含义是"那个扇区装的东西"，布局一换就可能过期 |
| 服务端收到选中项 | `WheelService.sanitizeSelection` 重新解析 id → 写回附件；解析不了就存空 + warning |
| 掉线 / 换世界 | `LoggingIn` 清空客户端状态与两个标志，下一次登录重新走第一行 |

### 7.3 三个刻意的取舍

1. **恢复要"重试到附件出现"**。附件是在玩家加入之后才发的（`PlayerList#placeNewPlayer` 里 `syncInitialPlayerAttachments` 排在登录包之后），所以头几刻 `getExistingData` 是空的，而"还没收到"与"这个玩家从没选过"在那几刻完全一样。做法是每客户端刻查一次，直到它出现；一旦本次会话自己选了东西就再也不查（`consulted` + `sector() >= 0`），所以**永远不会把玩家刚选的扇区冲掉**。恢复必须排在上送之前也是同一个理由：先发一条"什么都没选"会把服务端记住的值擦掉，那正是这个功能要恢复的东西。
2. **上送只在"变了"时发生**。轮盘关着时一个包都不发，指针停在同一扇里也不发（每客户端刻最多一个包）。代价是"扇区内容因别的原因变了"（授予被撤销之类）不会重新上送——但那种情况下界面本来就把那一扇当"没有目标"，见 §6.2 最后一条。
3. **不能改成"每刻把解析结果同步过去"**。客户端换维度时**所有附件都会丢**（`ServerPlayer#changeDimension` 里那句 `syncInitialPlayerAttachments` 的注释就是为此），随后的空窗里 `WheelContent.layoutFor` 返回的是**派生填充**——每刻同步会把派生内容写进存档。只在"玩家换了扇区"与"保存了布局"这两个明确动作上发，就绕开了这件事。

### 7.6 实机该看什么（先问再跑）
