## 1. 授予与被动属性：来源注册化，主 tick 阶段化（A01–A04）

### 1.1 问题

- `AbilityGrantService.recalculate` 自己知道四种来源（灵根 / 体质 / 功法 / 子境界 / 生物档案 / 契约）的附件形状、命名与累积规则，新来源必须进这个中心类加分支；
- `PassiveAttributeService.entries` 同理，自己枚举境界 / 功法 / 体质的属性表，且用 `getData` 给没有身份的实体创建附件；
- `AbilityEventBridge.onEntityTick` 同时是"全实体总调度"：资源初始化、自然回复、触发器、被动属性、Curios、成长推进、技能生命周期全在一个方法里，顺序只由语句顺序保证；
- `ResourceService` 认识 Aura / RealmStage / `ServerCache`，并自己走境界链算排名。

### 1.2 来源注册化

照仓库已有的三个先例（`QualityService.carry` / `HoldLookup.register` / `TriggerRehydrators.register`）：

```java
// runtime/ability/AbilityGrantSources.java
@FunctionalInterface
public interface GrantSource {
    // 这份身体此刻期望的 source -> 技能 id 集合；不持有的来源返回空
    void collect(LivingEntity entity, ProgressionAttachment progress, Sink sink);
    interface Sink { void want(Identifier source, Holder<Ability> ability); }
}
```

- `AbilityGrantService` 只保留三件事：**按 `grant/` 前缀的全量差分**、**唯一的存储清理出口**（§8 的 F03/F04）、重建触发器订阅；来源由 `AbilityGrantSources.register(...)` 注入。
- 三个提供者各自回到自己的模块：`runtime/cultivation/CultivationGrantSource`（灵根 / 体质 / 功法 / 子境界）、`runtime/creature/CreatureGrantSource`（生物档案 progression）、`runtime/creature/ContractGrantSource`（`ContractGrantService.heldTypes`）。注册写在各自的静态块里，由一个 `initialize()`（`AbilityEventBridge.initialize()` 现在那个位置）强制类加载，照 `AbilityEventBridge` 注册 rehydrator 的写法。
- **契约不变**：来源命名仍是 `mxt:grant/<类目>/<命名空间>/<路径>`，账本与附件格式一字不改，因此不需要迁移存档。

被动属性用同形的注册点：`PassiveAttributeSources.register(provider)`，provider 返回 `(kind, source, index, AttributeEntry)` 四元组；`modifierId` 的生成规则不动（`passive/<kind>/<origin>/<index>/<原 id>`），所以已存在的 modifier 仍能被清理掉。顺手把 `entries` 里的 `getData` 换成 `getExistingData`（拿不到就不收集，不再创建空附件）。

### 1.3 主 tick 阶段化

新建中立调度器 `runtime/EntityTickStages`：一条**显式声明顺序**的阶段表，每个阶段由所属模块注册（`register(String id, int order, Consumer<LivingEntity>)`），平台订阅只有一个地方（`@EventBusSubscriber` 的 `EntityTickEvent.Post`）。

现有 `AbilityEventBridge.onEntityTick` 的八件事各归其位，顺序照今天逐条搬（数值只表示先后，不代表"越靠前越重要"）：

| order | 阶段 | 现在住哪 |
| --- | --- | --- |
| 100 | 资源附件与 HUD 资源初始化 | `AbilityEventBridge.initializeHudResources` |
| 200 | 灵气自然回复（`handlesNaturalRegeneration` 为真则跳过） | `AbilityEventBridge` + `ResourceService` |
| 300 | `TICK` 触发器派发 | `TriggerPublishing` |
| 400 | 被动属性 tick | `PassiveAttributeService.tick` |
| 500 | 每 20 tick：Curios 同步 + 成长推进 + 授予重建 | `AbilityEventBridge` / `ProgressionDriver` |
| 600 | 技能主 tick（存储 tick、刻距、生效边沿、`activeTick`） | `AbilityEventBridge.tickAbilities` |
| 700 | 到期施法结算 | `AbilityEventBridge.finishDueCasts` |
| 800 | 引导维持 | `AbilityEventBridge.onEntityTick` 末行 |

`AbilityEventBridge` 保留其余原版事件订阅（伤害 / 攻击 / 死亡 / 装备 / 使用 / 方块）与技能相关信号适配。这样"顺序"是一张可读的表而不是方法体的行序，移动阶段不再靠碰运气。

### 1.4 数值服务去领域化

`ResourceService` 只留数值、上下限与事务。境界相关的公式变量改由**注册的变量提供者**注入：

- `FormulaContexts.forEntity` 已经会拼实体上下文；把"这个值对应哪个境界、排名多少、吸了多少"做成 `runtime/resource/ResourceFormulaVariables` 的一类注册项（`withResource(...)` 现在读 `aura` / `realmRank` 的那部分搬过去）；
- 提供者由 `runtime/cultivation` 注册（它才认识 `Aura` / `RealmStage` / `ServerCache`）；
- `ResourceService.formulaContext(LivingEntity, …)` 只负责"把上下文的资源变量填上"这一句，不再 import 修炼包。

**"没有服务器索引"与"服务器已判定坏链"必须分开**（审计 D01 第 3 条）：`ServerCache.get()` 为空时才允许按定义链接回退（客户端预测）；`ServerCache` 在且查不到该境界，一律按"无排名"返回，不再自己从 `firstRealm` 走链。

## 2. 链条统一与整链拒收（D01）

### 2.1 目标形状

通用直线图的一切（走链、成环、分叉、并入、整链拒收、排名、上一档/下一档）只在 `util/ChainCache` 一份；领域只回答四件事：哪些链接算数、哪一条是入口、这条链叫什么、每条问题怎么写（照 `QualityLadders.diagnose` 与 `ServerCache.rebuildRealmChains` 今天的口径）。

### 2.2 `ChainCache` 的两处补强

1. **分叉 = 整链拒收。** 今天的 `Builder.build` 只把 `follows both A and B` 记一条 report，谁先入索引由调用方 map 顺序决定；`Builder.forks` 返回的 report 不影响索引。改成：先把"被两个以上条目指向"的 id 收成一个拒收集合（和 `refuse` 的语义一样），任何走到它的链整条不索引——对应 `ChainCache` 类注释里本来就写的"a line whose entry refuses, repeats, or runs into another line is left out whole"。
2. **领域级的整链判定放进 builder。** 新增一个可选的逐链校验回调（`Builder.check(ChainCheck<T>)`：返回非空字符串＝这条链整条拒收，原因照报），让"整条链合法"的领域规则（progression 的 `mastery` 不许下降）能落在公共 walk 里，而不是各写一个 walker。

### 2.3 五个走链点的归位

| 现状 | 改后 |
| --- | --- |
| `ServerCache.rebuildProgressionChains`（自带走链 + rank + 分叉 + mastery 单调） | 用 `ChainCache` 建索引（`next_level` 缺失 → `refuse`，mastery 单调 → `Builder.check`），rank 从 `chainOf(id).indexOf(id)` 读；"没接上入口"的报告照 `reportUnreachedRealms` 的写法 |
| `ProgressionService.follows`（自己走，上限 512） | `chainOf(entry)` 与 `chainOf(level)` 同链，且 `rankOf(level) >= rankOf(entry)` |
| `ResourceService.realmRank`（自己走，上限 1024） | 只读 `ServerCache.rankForRealm`；缓存不在时才按定义回退（§1.4） |
| `CultivationService.next`（索引答空就吃定义链接） | 缓存不在 → 定义链接；缓存在但链被拒收 → 明确按"没有下一档"处理 |
| `TechniqueProgress.chainLength` / `rankOf`（自己走，上限 512） | `cache.chainOf(...)` + `rankOf` |
| `ServerCache.validateTechniqueLevels`（自己走） | `cache.chainOf(...)` + 沿链读 `configuration` |

### 2.4 影响面

分叉从"报告后照旧可用"变成"整链不可用"，是**数据包作者的可见行为变化**，要同步 `docs/数据包格式.md` 与文档站（中英）；测试包里若有分叉夹具，加一条负例探针。

## 3. 阵法：供给归属与授予身份（F06/F07）

### 3.1 供给归属（F06）

今天 `BlockAuraService.rebuild` 每格只写一个 `boolean insideFormation`，`AuraChunkAttachment.absorbedAura()` 是"本区块所有处于任意阵法内的 emitter"的合成总量，`FormationAbsorption.absorbedFor` 又把包围框涉及的区块总量全加起来——没有实例归属，也没有三维距离复检，于是同区块两个阵法、上下堆叠、框角，都能互相领对方的供给。

改：**emitter 记录归属实例**。

- `BlockAuraContribution` 的 `boolean` 换成"吸收它的阵法实例键集合"（`Set<BlockPos>` 控制器位置，空集＝不被任何阵法吸收）。控制器位置就是 `mxt:formation_world` 里那条实例的键，跨维度由区块自身所在维度保证。
- `AuraChunkAttachment` 的聚合从"吸收总量"改成"按控制器分组的总量"（`Map<BlockPos, Map<Holder<Aura>, AuraValue>>`；`absorbed_aura` 这个存档字段随之变形，属**破坏性变更**，旧存档里那一项按宽容读法丢弃、下次重建即恢复）。
- `FormationAbsorption.absorbedFor(level, controller, radius)` 只取该 controller 名下那一组，再按三维距离复检（emitter 到控制器的距离 ≤ radius）；`Sources.of(...).absorbed(pos)` 同样按实例判。
- 环境浓度（`environmentSupply`）不动：它本来就是"这一格的地面灵气减掉自己 emitter 供给的部分"，按实例算。

### 3.2 授予身份（F07）

`FormationSources.of(formation)` 只含定义 id，于是同一定义的两个实例互相撤销。**不改 source 字符串**（数据包按约定写的 `source` 一字不动，避免破坏现有包），改成**实例计数**：

- 每个阵法实例本来就在 `FormationEntityActions` 里维护"当前在范围内的实体集合"（`remember(level, controller, present)`）；
- 释放时不再"只要不在这个实例里就撤"，而是问**同定义的全部实例**：这个实体是否还在其中任意一个的范围内；只有都不在，才撤这一份定义级 source；
- 停用 / 销毁一个实例时，同样先看该实体是否还被同定义的其他实例覆盖。

这样"定义级 source"成为**该定义所有实例共享的一份授予**，与 `AbilitySources.CURIOS`（一份 shared source 不能互相撤销）是同一个形状。跨维度、离线、重建后的清理一并按"同维度 + 同定义的全部实例"判。

## 4. 受控交易的提交边界（F12/F13）

### 4.1 问题

`CostTransaction.commit` 的回退只覆盖**它自己那一次调用**写入的部分。调用者要付两笔（修炼：环境灵气 + 身体费用；复合技能：每个子技能一笔）时，后一笔失败就把前一笔留在原地：

- `CultivationMethodService`：`:174` 提交环境灵气 → `:176` 提交身体费用，`:177` 失败直接返回；
- `AbilityService` 复合：`:410` 逐个 child `commit`，后续失败在 `:414` 返回，前面的资源 / 冷却 / 次数不回滚，效果还在 `:417` 之后没跑。

### 4.2 形状

给 `CostTransaction` 加一个**多计划同一边界**的提交：

```java
public record Payment(Planning plan, CostContext context) {}
public static PayResult commitAll(List<Payment> payments);
```

- 内部沿用现有实现：把 `commit` 的 `rollbacks` 列表提出到外层，逐计划执行，任一计划拒付就**按逆序回滚已写入的部分**（资源快照、物品草稿、银行与共享池的还原都是现成的）；
- 现有单计划 `commit` 改成 `commitAll(List.of(...))` 的一层薄封装，行为与今天逐字节相同；
- **脚本（`mxt:js`）的外部副作用仍然不可回滚**——这是已经公开的限制，不因为有了 `commitAll` 就变成"事事原子"；改变的是模组自己控制的资源 / 物品 / 灵气 / 冷却 / 次数。

用法：

- 修炼一拍：把环境灵气计划与身体费用计划放进同一个 `commitAll`（顺序仍按今天：灵气在前）；
- 复合技能：把全部 child 的 `commit` 合成一个 `commitAll`，全成功才进效果循环；次数 / 冷却这类**状态写入**也要跟着挪到边界之后（`applyAbilityState` 目前在上面的预演循环里，一次失败会留下先写的状态）。

### 4.3 与 F05 / F08 的关系

- **F05（阵法维护）**不是"两笔提交"，而是"先按全额校验了主人的余额"。改法在调用侧：`MaintainRule.plan` 先用 `planDeferred` 求出费用数额，再按供给 → 库存 → 主人差额的顺序分摊，**只对主人差额**做可用性校验与提交；主人的动作在提交失败时不写库存（现有约束保留）。
- **F08（符箓）**是"先跑技能、后付载体价"。改法：把载体价与每个待发动技能的费用**一起预演**（技能侧需要一个只算钱不执行的入口），一起过一遍草稿；总价付得起才发动，发动后按今天的位置提交载体价——这样"载体与技能抢同一份资源"不再出现"技能已扣、载体付不出"，同时保留"所有技能都拒绝则不收载体费"的现行语义。技能动作自己改付款资源的情形仍是固有边界，写进注释。

## 5. 临时使用组件的所有权（D03）

今天两个模块各写各的：

- `HoldService`：类注释自称"全模组唯一写 `minecraft:consumable` 的地方"（**失实**，`PillUseService:62` 也写），写完在周期开始时摘掉组件，靠 `ours()` 的启发式识别"这个组件是不是自己写的"；
- `PillUseService`：保留组件让原版吃完，再回收；只用一个 `static Set<UUID> ARMED` 记"谁被武装过"，`takeBack` 只剥主副手，且按组件值相等判定。

三处具体缺口：① 记录只有 UUID，原堆被服务端逻辑移到别的槽就找不到；② 值相等不足以证明"这一份就是本次武装的那一份"；③ `ARMED` 是**同一个 JVM 里两端共享**的静态集合（单机下客户端与集成服务端同进程），一端先回收会把另一端的记录摘掉。

改：抽一个 `runtime/hold/TemporaryUseComponent`，两个模块共用：

- 记录按**逻辑侧**分开（`level().isClientSide()` 两套表），修 ③；
- 记录"实体 + 槽位 + 写入的组件实例"，回收时先看记录的槽位、再看整份玩家背包（只对已武装的实体做，代价有界），并且**只移除实例相同的那个组件**（`stack.get(CONSUMABLE) == armed`），修 ①②；
- 两个模块各自的策略不动：hold 在周期开始后摘组件、pill 让原版吃完再摘，各自的"要不要吃 / 什么时候撤"仍归自己；
- `HoldService` 的类注释改成"本模组写这个组件的两处之一，且只接管自己写的那一份"。
