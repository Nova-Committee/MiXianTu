## 0. 范围（先读这一节）

### 0.1 管：使用消耗

只处理「**发动 / 维持某件事时要扣掉什么**」的字段：

| 定义 | 字段 |
| --- | --- |
| `ability` | `costs` |
| `ability` 的 `mxt:channelled` | `upkeep_costs` |
| `realm_stage` | `costs`（突破） |
| `cultivate_action` | `costs`、`aura_costs` |
| `formation` | `activation_costs`、`maintenance_costs` |
| `forging_method` | `costs` |
| `artifact` 的 `mxt:flight` / `mxt:upkeep` | `costs` |
| `mxt:spirit_shaped` / `mxt:spirit_shapeless` 配方 | `aura` |

### 0.2 不管：货币（2026-09-23 已定）

**货币跟本稿无关，一个字都不动。**

- `currency` 定义的 `exchanges[].cost`：那是"一件货值几个货币物品"的**价格**（整数 `1..99`，`ExchangeStationMenu` 收钱发货），不是"发动一次要扣什么"。
- `item_quality.value_multiplier`、`CurrencyValueService`、货币 Tooltip 与兑换站：同样是价值/价格。
- 它们**不进来当 `Cost` 类型**，不改形状、不改成数组、不加 `aura`/`item` 的写法；本稿的任何一条拍板都不牵扯货币系统。货币自己的字段变动是另一件事。

### 0.3 也不管：长得像但不是消耗的

- **门槛**：`minimum_aura`（炼丹配方、`creature_profile`）、`use_condition` 这类"要有多少才能开始"不扣任何东西。
- **容量**：`artifact.spirit_capacity`、`formation.storage.capacity`、`mxt:buff` 的 `max_bonus`。
- **动作即代价**：法器认主的血量代价今天是 `claim_action` 的 `mxt:consume_health`（它同时是一个行为、还要写进 tooltip）。
- **符箓 `talisman.aura_cost`**：语义是"载体要灌满这么多才能发动"，是**要求**不是支付——归哪边见 §6 与待拍板。

## 1. 现状：三套口径

| 口径 | 谁在用 | 能表达的代价 | 付款者写死成谁 |
| --- | --- | --- | --- |
| 通用 `Cost`（`type` 分派：`mxt:resource` / `mxt:item` / `mxt:js`，外加 `{id, amount}` 简写） | **只有** `ability.costs` | 资源、玩家背包物品、脚本 | `Player`（`Cost#check(Player)` / `consume(Player)`） |
| `ResourceCost` 数组（`{id, amount}`，`AutoIgnoreListCodec`） | `upkeep_costs`、`realm_stage.costs`、`cultivate_action.costs`、`formation.activation_costs` / `maintenance_costs`、`forging_method.costs`、`artifact` 的 `mxt:flight.costs` / `mxt:upkeep.costs`（8 个字段、6 种定义） | 只有资源 | 调用方自己决定（各自直接调 `ResourceTransactions`） |
| 灵气 map（`{<aura id>: NumberProvider}`） | `talisman.aura_cost`、`cultivate_action.aura_costs`、`mxt:spirit_shaped` / `mxt:spirit_shapeless` 的 `aura`、（门槛）`alchemy` 的 `minimum_aura`、`creature_profile.minimum_aura` | 只有灵气 | 各写各的：世界灵气池 / 工作台银行 / 灌满要求 / 只比不比 |

四个具体的痛点，按严重程度排：

1. **类型分裂**：只有 `ability.costs` 能写物品与脚本代价；其余 8 个字段只吃资源，而它们的列表 Codec 是 `AutoIgnoreListCodec`——写了 `{"type": "mxt:item", ...}` **不报错**，只打一条 WARN 把这一项丢掉，等于"这一笔悄悄没扣"。
2. **付款者被写死成 `Player`**：`Cost#check/consume` 只收玩家，可**资源附件本身是实体附件**（`MxtAttachments.RESOURCE_HOLDER` 是 `entity(...)`），`ResourceTransactions.evaluate/tryConsume` 收的也是 `LivingEntity`——也就是说"生物付资源"底层早就能跑（`AbilityService.requiresPlayerCost` 里资源项本来就允许非玩家），但形状上表达不出来；于是"世界池付修炼费""阵法仓库付维护费""工作台银行付合成费"只能各自另写一套（`AuraService.consume`、`FormationService.PaymentPlan`、`SpiritCraftingTableBlockEntity.consumeAura`）。
3. **失败方式不一致**：`data/resource/ResourceCost.evaluate` 在**运行期抛 `IllegalStateException`**（扣费那一刻崩），`ResourceTransactions` 对重复资源 id 抛 `IllegalArgumentException`，而各模块自己又有 `Failure` 枚举（如 `Failure.INSUFFICIENT_AURA`）。同一个"付不起"在三处是三种东西。
4. **事务边界不一**：资源在技能路径上走**草稿**（`resources.copy()` → `tryConsume(payer, draft, …)` → 最后 `commit`），物品是**预留**（`ItemCostDraft`），而灵气与银行是**直接扣**（`AuraService.consume` / `consumeAura`）。数组里混写多种代价时，谁先谁后、失败了退不退，没有统一答案。

## 2. 目标与非目标

**目标**

- **一个元素形状**，任何"要扣东西"的字段都能照抄（资源 / 灵气 / 物品 / 脚本）。
- **付款者是 `LivingEntity`**（不是 `Player`）：玩家、生物、召唤物都能是付款者；只有"需要背包 / 需要脚本"的代价才额外要求它是玩家。通道（世界池、方块实体银行、脚本）由**调用点**提供，不由数据包决定。
- **校验与扣除在同一个对象上**：一个 `Cost` 同时回答"付得起吗"和"扣掉"，不允许拆成两套实现。
- **一次支付的整组原子**：要么全扣，要么一点都不动；失败路径必须能回退。
- 付不起是**结果记录**而不是异常；能静态判定的错误在**加载期**拦。
- KubeJS 侧读写的是**同一个形状**，不另开一套。

**非目标**

- 货币（§0.2）、门槛、容量、动作即代价（§0.3）。
- **不做跨业务的原子**：本稿保证的是"这一次支付"的整组原子；"扣完钱再产出物品、产出失败要把钱退回来"属于各业务自己的事务，不在消耗层解决。
- `mxt:cost_type` 仍是固有注册表：包不能新增 `type`，`mxt:js` 依旧是唯一把行为交给脚本的口子（与 `docs/数据包格式.md`「数据包无法向固有注册表新增 `type`」一致）。

## 3. 元素形状（本设计的核心）

所有消耗字段都是**同一个数组**，元素是下面五种之一：

```jsonc
// 通用写法：带 type 分派
{"type": "mxt:resource", "resource": "example:qi", "amount": "5 + level"}
{"type": "mxt:aura",     "aura": "example:fire_qi", "amount": 2}
{"type": "mxt:item",     "items": ["minecraft:emerald", "#c:gems"], "amount": 2}
{"type": "mxt:js",       "id": "my_cost", "params": {}}

// 简写（历史写法，等价于 mxt:resource；字段名是 id 不是 resource）
{"id": "example:qi", "amount": 5}
```

| `type` | 字段 | 需要的通道 | 语义 |
| --- | --- | --- | --- |
| `mxt:resource` | `resource`（`Holder<resource>`）、`amount`（`NumberProvider`） | `ENTITY_RESOURCES` 或 `AURA_BANK` | 扣**数值**本身 |
| `mxt:aura` | `aura`（`Holder<aura>`）、`amount` | `WORLD_AURA` / `AURA_BANK` /（落到实体时经 `aura.resource()` 走 `ENTITY_RESOURCES`） | 扣**某一种灵气**；池子与银行是按 aura 开键的，所以这一项必须知道是哪一种 |
| `mxt:item` | `items`（`ItemMatcher` 条目数组）、`amount` | `PLAYER_INVENTORY` | 从背包扣匹配的物品 |
| `mxt:js` | `id`、`params`（可选对象） | `SCRIPT` | 检查与支付都由脚本回调决定 |
| （简写） | `id`、`amount` | `ENTITY_RESOURCES` / `AURA_BANK` | 等价 `mxt:resource` |

约定：

- `amount` 一律 `NumberProvider`，运行期必须求成**有限正数**；`mxt:js` 没有 `amount`。
- 不允许"部分支付"：每一项都要么整项成立、要么整笔失败。
- `mxt:aura` 落在实体身上时经 `Aura#resource()` 折算成数值（"存储按 aura 键、钱按 resource 键"这一既有口径不变），不需要新的映射表。
- 每个元素自带它求值用的公式上下文（资源项用"该资源所属灵气"的上下文，见 `ResourceTransactions.evaluate(LivingEntity, …)`），所以同一个数组里的两项可以在不同的上下文里求值。

## 4. 付款者与支付上下文

```
PaymentContext
├─ payer: LivingEntity?    付款者。有付款者时一定是生物（玩家 / 生物 / 召唤物），不是 Player 特化；为空 = 没人付
├─ level / pos             位置（世界灵气池按位置查）
├─ formula: FormulaContext
├─ origin: CostOrigin      谁在扣：技能 / 突破 / 修炼周期 / 阵法的激活或维护 / 锻造 / 法器维护 / 飞行 / 配方 …
└─ channels               这一处提供的通道集合（可能带一个方块实体的银行）
```

| 通道 | 读 / 写 | 谁能提供 | 备注 |
| --- | --- | --- | --- |
| `ENTITY_RESOURCES` | 付款者的 `mxt:resource_holder` 附件 | `payer` 非空 | 实体附件，任何 `LivingEntity` 都有；底层今天已支持非玩家 |
| `PLAYER_INVENTORY` | 玩家背包 | `payer` 是 `Player` | `mxt:item` 需要；非玩家付不起（`Failure.NO_CHANNEL`） |
| `WORLD_AURA` | 该 `pos` 的灵气池（`AuraService`） | `level` + `pos` | 修炼周期今天就是这个语义 |
| `AURA_BANK` | `AuraAccess`（工作台、阵法仓库） | 调用点把方块实体传进来 | 合成与阵法维护 |
| `SCRIPT` | `mxt:js` 回调 | 装了 KubeJS，且 `payer` 是 `Player`（今天的回调签名收 `Player`） | 要不要放宽到任意 `LivingEntity` 见待拍板 |

规则：

- 每个 `Cost` **静态声明**它需要哪些通道；上下文没有该通道 = **付不起**（`Failure.NO_CHANNEL`），不是异常、也不是加载错误：同一个定义可以在"有池子的地方"成功、在"没池子的地方"失败。
- 通道由**调用点**决定，不由数据包决定：阵法维护天然带 `AURA_BANK` + `ENTITY_RESOURCES`（主人补足），飞行天然是 `ENTITY_RESOURCES`。数据包只写"要什么"，不写"谁付"。
- 付款者类型是 `LivingEntity`，所以"傀儡/灵兽用自己的资源付技能"不需要新机制；反过来"一定要玩家"的地方由通道（背包、脚本）自动表达出来。

## 5. 校验与扣除：同一个对象、两阶段、可回退

### 5.1 一个对象两件事

`Cost` 接口保持"同时用于校验与扣除"：

```
boolean check(ctx)     // 只读：付得起吗（不改任何状态）
void    consume(ctx)   // 写：扣掉（自己保证不半扣）
```

不做"校验类 + 执行类"两套实现——两套实现会漂移，而且 `plan` 阶段就必须能用同一份逻辑判断"整组是否成立"。要求：`check` 为真 ⇒ `consume` 必须能成功（`consume` 里**不允许**再出现"忽然不够了"的分支，除非那部分由脚本/外部状态负责，见 5.4）。

### 5.2 数组级三段式

一次支付（一个 `costs` 数组）由统一的事务器执行：

1. **`plan(ctx)`**（纯函数、无副作用）：逐项 `check` + 逐项求值。**这一阶段就把"付不起"全部判掉**，任何一项不成立 → 整笔失败，返回 `CostFailure`（含是哪一项、哪个资源）。
2. **`stage(ctx)`**：在**草稿**上扣，不落盘。
   - 资源：`ResourceHolderAttachment.copy()` → `ResourceTransactions.tryConsume(payer, draft, evaluation)`（**已有**，技能路径就是这么做的）。
   - 物品：`ItemCostDraft`（**已有**）。
   - 世界灵气池、方块实体银行：**需要新增**"池子草稿"（快照现有量 → 在副本上扣）。
3. **`commit()`**：一次性把草稿写回去。正常路径下 `plan` 已经判过，这里不会失败。

### 5.3 回退（rollback）

- **首选不是"回退"，而是"草稿 + 丢草稿"**：`stage` 阶段任何一项失败，直接丢弃全部草稿，**原状态一个字节都没动**，不需要回退逻辑。这是原子性的主路径。
- **回退是最后手段**，只在"提交阶段仍失败"时使用（外部状态在 `stage` 与 `commit` 之间变了：脚本、方块实体被拆、玩家退出）。要求每个通道在 `stage` 时留下**可还原快照**：
  - 资源附件的还原必须连 audit 快照一起还（`minSnapshot` / `maxSnapshot` / `lastChangedTick`）——今天的 `holder.set(resource, value, previous.minSnapshot(), …)` 已经在传这几个字段，草稿要继承同样的字段。
  - 物品背包：`InventoryUtil` 已有快照/还原工具（`snapshot` / `restore`）。
  - 灵气池与银行：`stage` 时存下被扣项的旧值即可（纯数值，还原廉价）。
- **回退失败要吵**：还原不上时必须打 `ERROR` 并放弃后续业务（宁可整笔不生效，也不要留下一笔看不见的错账）。

### 5.4 无法草稿化的通道：`mxt:js`

脚本自己改玩家状态，没法在副本上预演。规则：

- `mxt:js` 项**一律排在整个数组的最后**执行（在其它通道已经提交之后）。
- 脚本回调必须**幂等或自带回退**：`MxtJsCostCallbacks` 的契约里写清"`consume` 可能被调用两次"或"`consume` 失败要自己还原"。
- 更严格的做法（待拍板）：`mxt:js` 只允许出现在**单项数组**里，从根上不让它跟别的代价混写。

### 5.5 原子性的边界

本稿的原子性是"**这一次支付的整组**"：数组里 5 项，要么 5 项全扣，要么一项都不扣。它**不**覆盖"支付 + 后续业务"（例如技能扣完钱之后施法被打断要不要退钱）——那是各业务自己的事，今天也没有统一答案，本稿不扩张到那一步。

## 7. 加载期校验与失败语义

**加载期拒绝**（能静态判定就绝不留到运行期）

- `amount` 是常量且 ≤ 0 或非有限。
- 同一数组里出现**指向同一个 resource 的两项**（含"一个 `mxt:aura` + 一个指向同一 resource 的 `mxt:resource`"——它们会重复扣同一个池子，顺序还不可见）。
- `mxt:item` 的 `items` 为空。
- 未知 `type`（原版 dispatch 已经会拒）。

**运行期失败**（结果记录，不抛异常）

- 公式求值非正/非有限 → `INVALID_AMOUNT`（**取代**今天的 `IllegalStateException`）。
- 通道不足 → `NO_CHANNEL`；余额不足 → `INSUFFICIENT_RESOURCE` / `INSUFFICIENT_AURA` / `MISSING_ITEM`。
- 脚本拒绝 → `SCRIPT_REJECTED`；回退失败 → `ROLLBACK_FAILED`（打 `ERROR`）。

**列表容错**：建议**取消**消耗数组上的 `AutoIgnoreListCodec` 静默丢弃，改成整条加载失败。理由：丢掉的是一笔"应该扣的钱"，静默失效比报错危险。这条会改动 `AGENTS.md` §4 现有的"列表容错"口径，见待拍板。

## 13. 落地记录（2026-09-23）

代码：`data/cost/`（根：`Cost` 契约 / `Charge` 求值载荷 / `Costs` 校验与求值 / `CostTransaction` 交易器 / `ItemCostDraft` 物品预留；`builtin/` 四种固有类型 `ResourceCost` / `AuraCost` / `ItemCost` / `JsCost`；`context/` 付款上下文 `CostContext` / `CostChannel` / `CostFailure` / `CostOrigin`；注册在 `registry/MxtCosts`，新增 `mxt:aura`）、11 个消耗字段的调用点、探针 `verify` 的第 4 条腿。

**与设计稿不同的地方（都是落地时的实现选择）**

1. **接口是 `charge` 一个方法，不是 `check` + `consume` 两个**：一个 `Cost` 只回答"这一项要扣什么"（`charge(CostContext) -> Either<Charge, CostFailure>`，只读，顺带做通道检查）；校验与扣除都由 `CostTransaction` 用同一份 `Planning` 完成——"同一对象既校验又扣除"的要求落在**交易器**上而不是每个类型上，避免三份实现各写一遍。`mxt:js` 是唯一例外：它的可用性由脚本自己回答，所以 `charge` 会调用脚本的只读回调。
2. **`Charge` 是密封接口的四种载荷**（`Resources` / `Auras` / `Items` / `Script`）：交易器按载荷种类分批，同一个通道只写一次（资源一次性原子事务），而不是逐项写。
3. **通道改名并加了一个"账户"概念**：`RESOURCE_ACCOUNT` / `PLAYER_INVENTORY` / `WORLD_AURA` / `AURA_BANK` / `SCRIPT`。资源通道不是"付款者的附件"，而是"上下文里的资源账户"——`CostContext.account(...)` 让阵法在**阵主离线**时直接点名一个账户（设计稿 §4 只写了"付款者可能为空"，落地时发现阵法连付款者都没有，只有账户）。
4. **灵气目标由调用点选**：`AuraTarget.VALUE`（按它计量的数值扣，付款者/账户）、`POOL`（场地灵气池）、`BANK`（方块实体库存）。`mxt:aura` 条目本身不决定从哪扣。
5. **写入顺序**：银行 → 灵气池 → 资源 → 物品（只**预留**）→ 脚本 → 物品落账。脚本排在所有"还能回退"的通道之后，物品落账排在最后（那一步不会再失败），于是最常见的中途失败根本用不上回退逻辑。
6. **回退是最小实现**：资源按写入前的快照（值 + `min`/`max`/`lastChangedTick`/`source`）还原，灵气池用 `AuraService.change` 退还，银行用 `insert` 还回去；脚本无法回退，只能在契约上要求幂等（`MxtJsCostCallbacks.consume` 改成返回 `boolean`，好让"脚本不存在/抛异常"能触发前面的回退）。
7. **容错取消**：`Cost.LIST_CODEC` 用 `Codec.listOf()`（不再有 `AutoIgnoreListCodec`），常量非正数金额与"同一 store 写两次"由 `Costs.validate` 在**加载期**拒绝；运行期公式求不出正数返回 `CostFailure.INVALID_AMOUNT`，不再抛 `IllegalStateException`。
8. **`data/resource/ResourceCost` 已删除**；`ResourceTransactions` 只保留"先全判后全写"的写入部分（`evaluate(...)` 两个重载删除），`ResourceLedger` 改成只接已经求值好的金额（它本来零引用）。
