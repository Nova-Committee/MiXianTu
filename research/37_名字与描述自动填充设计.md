# 37 —— 定义文本字段的自动填充（`ContextNameCodec` / `ContextNameListCodec`）

> **状态**：已落地（2026-09-23）。
> **修订（2026-09-23）**：`NameMapCodec` 按"两个 Codec 独立成两个类"的要求拆成 `ContextNameCodec`（单条文本）与
`ContextNameListCodec`（一组文本），两者共享 `ContextNameCodec.baseKey`；键的拼法与行为不变。**同日再按「统一成
ContextNameCodec 的键」应用到 18 张注册表，并废弃本文 §3 的"两套键"，见 `38_定义文本字段全量应用.md`。**
> **基准**：对着 `util/codec/{ContextNameCodec,ContextNameListCodec}.java`、`util/codec/MiscCodecs.java`、
`accessor/ResourceLoadingOps.java`、`mixin/codec/{RegistryOpsMixin,RegistryDataLoaderMixin}.java`、
`data/quality/ItemQuality.java`、`data/cultivation/RealmStage.java` 与 `docs/数据包格式.md` 写的。字段级权威仍是代码与
`docs/数据包格式.md`，本文记"为什么是这个形状"。

## 1. 需求与定下的口径

用户原话（2026-09-23）：

1. 「display_name（改成 name），description 都做成可选的方案，直接写一个特殊的 NameCodec，可以直接从 RegistryOps 拿到 id
   自动填充」（这个类后来按"构造函数传 key + 静态包装"的要求改名成 `NameMapCodec`，2026-09-23 再拆成 `ContextNameCodec` /
   `ContextNameListCodec`，见文首修订）
2. 「我记错了，我是用了个 mixin 的，你看这里面的：`E:\Java\Origins-NeoForge\src\main\java\com\iafenvoy\origins\mixin\codec`
   」（外部工程 Origins-NeoForge 的做法：给 `RegistryOps` 加一个字段装当前条目 key，再由加载器在解码前后设置/清除）
3. 「你想复杂了，直接 `PendingRegistration.loadFromResource` 的头部给 `RegistryOps` 带上 `ResourceKey`，末尾 remove 就行」
4. 生成的键拼法 `<category>.mxt.<namespace>.<path>.description`，「**保留**，因为前面两部分是注册表键的反写」
5. 「modifier 这种应该是不填写就不显示，也就是完全靠指定。只有 name 和 description 和我说的其他几个地方适用自动生成」
6. 子境界的整数写法用**翻译键、0 开始计数**；旧的 `mxt.minor_stage.<值>` 兜底查询**删掉**

## 2. 机制

- **注入点**：26.1.2 里 1.21.1 的 `RegistryDataLoader.loadElementFromResource` 已经搬进
  `net.minecraft.resources.RegistryLoadTask$PendingRegistration`，于是注入的是它的两个静态方法：
    - `loadFromResource(Decoder<T>, RegistryOps<JsonElement>, ResourceKey<T>, Resource)` —— 服务端从数据包文件解码；
    - `loadFromNetwork(Decoder<T>, RegistryOps<Tag>, ResourceKey<T>, Tag)` —— 客户端解码服务器同步过来的同一份 JSON。
      两条都在 `HEAD` 把 `elementKey` 放到 `ops` 上、`RETURN` 清掉。**只注入 `loadFromResource` 不够**：定义会同步到客户端，客户端拿不到
      id 时 `name` / `description` 会解码失败（`DefaultedCodec` 那类"失败就吞掉"的口径这里刻意不用，见 §6）。
- **载体**：`RegistryOps` 上一个 `@Unique` 字段（`mixin/codec/RegistryOpsMixin`），由 accessor 接口
  `accessor/ResourceLoadingOps`（`mxt$setKey` / `mxt$getKey`）暴露给普通代码。
- **消费**：`NameMapCodec` 的 `decode` 里 `ops instanceof ResourceLoadingOps` 取 key，拼出
  `base = <category>.<注册表命名空间>.<定义命名空间>.<定义路径>`；取不到就返回 `DataResult.error`，消息写明"
  这个字段必须自己写出来"。
- **不做懒加载**：Origins 那边是 `Optional<Component>` + 读的时候再按 id 拼；这里按用户要求**在解码期就填上**，模型里就是普通
  `Component`，消费者不用再判断 Optional。
- **不缓存**：一次解码拼一次字符串，成本可忽略。

## 3. 键的拼法（`38` 之后只有一套）

| 场景                                 | 键                                                             | 例（`mxt_test` 包里的一条定义）                                |
|------------------------------------|---------------------------------------------------------------|------------------------------------------------------|
| id 派生显示名（`DefinitionText`，所有注册表共用） | `<类别>.<注册表命名空间>.<定义命名空间>.<定义路径>`                              | `aura.mxt.mxt_test.qi`                               |
| 自带 `name` 字段省略时（与上一条同一个键）          | 同上                                                            | `quality.mxt.mxt_test.poor`                          |
| 自带 `description` 字段省略时             | 上一条 + `.description`                                          | `quality.mxt.mxt_test.poor.description`              |
| `minor_stages` 写整数时的第 n 个名字        | `realm_stage.mxt.<定义命名空间>.<定义路径>.minor_stage.<n>`，n 从 **0** 起 | `realm_stage.mxt.mxt_test.qi_refining.minor_stage.0` |

- 类别取 `DefinitionText` 注册的类别（`mxt:item_quality` → `quality`，其余是注册表路径），所以"前两部分"对 `item_quality` 是
  `quality.mxt`——正是注册表键 `mxt:item_quality` 的反写。
- **2026-09-23（`38`）起只有一套**：`DefinitionText` 的 id 派生键也补上注册表命名空间，于是"字段省略时的默认键"与"
  没有字段的定义读的键"完全相同，显示点读字段还是读键结果一样。本文此前记的"两套键都要给"作废。

## 4. `item_quality` 的变化

- `display_name`（必填）→ **`name`**（可选，省略时按 §3 自动填）。
- 新增 **`description`**（可选，同上），画在物品 Tooltip 的品质名下面一行（灰色）。
- `Modifier.description`：必填 → **可选**，省略就**不画那一行**（修正照样生效）。文案完全由数据包指定，没有自动生成——这是用户第
  5 条口径。
- `Modifier.modifier` 仍可选（默认 `1`）；三个修正对象本身仍可选（省略 = 没有修正）。
- 消费者跟着改名：`ItemQualityTooltipAppender`（多画一行描述）、`ItemPickerManager`（选择器读 `name()`）。

## 5. `realm_stage.minor_stages` 的变化（`36` 的修订）

- `List<String>` → **`List<Component>` 或一个整数**：数组就是名字本身（字符串=翻译键、对象=完整组件），整数 N 就是"这么多重"（
  `1..1024`），名字按 §3 自动生成。
- 删掉 `DefinitionText.minorStage` 与 `mxt.minor_stage.<值>` 查表约定。
- 其余语义（按本境界 `breakthrough_exp` 均分、超阈值夹到最后一重、凡人与未配置读 `NaN`）**不变**，见 `36_子境界设计.md`。

## 6. 不做 / 推迟 / 待拍板

- **拼法已在 `38` 统一**（用户拍板"统一成 `ContextNameCodec` 的"）：34 张注册表的 id
  派生键都补上注册表命名空间，代价是内容包要改键；本文写作时这条还挂在"不在本轮范围"。
- **字段覆盖范围已在 `38` 扩到 18 张注册表**（本文写作时只有 `item_quality` 一个）；其余 16 张仍只有 id 派生键。
- **取不到 id 时报错而不是兜底**：命令、KubeJS 的 `MxtKubeJsDataCodec`、存档解码这些路径没有条目
  id，这时省略字段就是硬错误（而不是静默给空文本）。选择报错是因为静默兜底会造出"界面上少一行字、没人知道为什么"的哑巴
  bug；如果将来真有需要，再给一个显式的兜底键。
- **没有专门的 UI 端兜底**：翻译键没翻就显示裸键，与仓内一贯口径一致。

- 探针 `/mxt_test verify` 第三条腿（`verifyGeneratedNames`）：
