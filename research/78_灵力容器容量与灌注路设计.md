一句话：把 `mxt:spirit_vessel` 改成"**一件容量组件 ＋ 一件存量组件**，**长按往外倒**，并且能被两处灌注——展示台的灵力射线、以及对着它发射灵力"。

## 1. 用户拍板（2026-10-08）

| # | 问题 | 拍板 |
|---|------|------|
| 1 | 上限／存储量的形状 | **多资源 ＋ 每资源各自一份上限**：存储量仍是"资源 → 数量"的表，上限也是"资源 → 上限"的表 |
| 2 | 没写上限时 | **没有默认**：该资源上限 0，存不进（不是"无限"，也不是配置项） |
| 3 | 手感（二次调整后） | **长按右键输出**——每 tick 每种资源 1 单位；**没有模式、没有切换**，潜行右键不做事 |
| 4 | "放展示台上不受影响" | **要让展示台能给容器灌**，且那条路不看方向 |
| 5 | 发射灵力（二次调整新增） | **手上是灵力容器就充能而不是发射**：同一次付款，不生成射线实体 |

## 2. 动手前核实的现状

- 存储量组件 `mxt:resource_container` 是**裸 map**：`CollectionCodecs.doubleMap(Resource.CODEC)`（`ResourceContainerComponent:35`），键是 `Holder<Resource>`、值是 double；底层 `TolerantMapCodec` 容错，坏条目打日志丢弃。构造函数再要求有限、非负。
- 上限原写死在 `SpiritVesselItem.CAPACITY_PER_RESOURCE = 1000.0`，**每种资源各 1000**——"一个容器装多种资源"今天就已经成立，只是上限不可配。
- 手感原本在 `SpiritVesselItem.use`：右键＝`release`（容器 → 持有者账户），潜行右键＝`store`。**两次调整把它整个换掉**。
- 长按框架：`HoldBinding`（声明）+ `HoldSource`（模块登记，`ModuleHooks.register(HoldSource.class, …)`）+ `HoldLookup`（按栈解析）+ `HoldService`（arm 原版 `consumable` 组件驱动使用周期、播音效）。模块自己的动作由各自的 `LivingEntityUseItemEvent.Tick` 监听器做（`SpiritChargeService` 就是这么驱动的）。
- 展示台 `DisplayStandBlockEntity implements AuraAccess`：`getCapacity` 与 `insert` **只对实现 `ItemAuraAccess` 的展示物**起作用，`extract` 恒返回 `amount`（只进不出）。灵力容器原本不是 `ItemAuraAccess`，所以展示台对它什么都不做。
- **aura 与 resource 的关系写在定义里**：`Aura#resource()`（`data/aura/Aura.java:34`；doc 见 `api/AuraAccess.java:13-16`——"resource 只是个数，aura 才是身份；resource 是它被计量的单位"）。所以"灌 N 单位某 aura"＝"存 N 单位它计量的那个 resource"，**不需要换算表**。
- 发射灵力的唯一出口：`SpiritBurstService.tryFire`（`runtime/spirit/SpiritBurstService.java:104-116`）——算量 → 查余额 → 扣款 → `addFreshEntity(new SpiritBurstEntity(...))`。射线实体命中方块实体时只调 `AuraAccess.insert`（`SpiritBurstEntity:93-94`）。
- 展示台改了展示物之后原本只在展示物是 `UseItemAuraAccess` 时 `markChangedAndSync()`（`:67-72`）——只实现 `ItemAuraAccess` 的展示物改了却不同步（本轮修掉）。

## 3. 组件（两个）

| 组件 | 形状 | 缺省 |
|------|------|------|
| `mxt:resource_capacity`（新） | 裸 map：资源 → 上限（double，有限、非负；0 与不写是一回事） | **无默认**：没写＝该资源上限 0，存不进 |
| `mxt:resource_container`（不动） | 裸 map：资源 → 数量 | 物品默认 `EMPTY` |

上限写成"表"而不是一个数：一个容器可以同时装好几种资源，每种各自一份容量。**不加配置项**，上限只由组件（命令／数据包／内容包）给。

## 4. 手感：长按倒出

容器走**长按框架**，不在自己的 `use` 里搬东西：

- 新增 `runtime/resource/VesselPourHold`（`HoldBinding`）+ `runtime/resource/VesselPourService`（`HoldSource` 登记 + tick 监听），在 `ModuleHooks.initialize` 里登记；它认栈的判据是新条目类型 `mxt:resource_container`（`ResourceContainerEntry`，`instanceof` 级别的能力判据，`itemLevel() = false`——组件是逐堆的）。
- **按住右键每 tick 把容器里每种资源各 1 单位倒进持有者账户**（`POUR_PER_TICK = 1`，与充能同速）。账户自己的上下界决定收多少（`ResourceService.change` 的钳制），收不进去的留在容器里。
- **长按长度由上限给**：`clamp(ceil(max(上限, 存量) / 1), 1, 200)`——与充能同一个 200 上限、同一个理由（长度每 tick 都被读，缩水的数字会把音效节奏带跑）；**容器空着就是 `NO_HOLD`**，那一次点击交回给物品，`use` 说一句"容器内没有可用灵力"。
- 潜行右键不是长按（框架的规则），现在什么都不做（没有模式可切了）。
- 第一次真的倒出东西的那一 tick 报一句 action bar（复用 `item.mxt.spirit_vessel.released`）；输入方向的 `store` 分支与那两个键（`stored` / `store_failed`）连同一起删掉。
- 姿态 `BUNDLE`、音效 `SoundEvents.BOTTLE_EMPTY`（每 4 tick 一次，原版节奏）。

## 5. 两条灌注路

### 5.1 展示台（容器实现 `ItemAuraAccess`）

- `insert(entity, stack, aura, amount, simulate)`：落进容器的是 `aura.resource()` 这个资源，收多少由**那个资源的上限**与已存量决定；返回没搬进去的部分。**不看任何"方向"**——展示台只会往里灌。
- `getCapacity(entity, stack)` / `(entity, stack, aura)`：按 `aura.resource()` 的上限减已存量，向下取整（aura 是整数单位）；前者走一遍 aura 注册表（`MxtDatapackRegistries.holdersOrEmpty`，不抛），`entity` 为空时答空表——**展示台与射线走的是按 aura 问的那个重载**，所以不受影响。
- `extract(...)`：**恒拒**。容器是"往里灌"的东西，出来的路是长按。
- 不实现 `UseItemAuraAccess`：那会把"按住右键往我身上灌"也挂上（`SpiritChargeHold` 对每个 `UseItemAuraAccess` 栈生效），多出一条输入路，还要再处理 tooltip 充能线与点击时的 "unchargeable" 提示。因此**展示架的 Jade 也没有灵力百分比条**（那条走 `SpiritChargeService.resolve`，对"没有 `pour`、也没有 `item_aura` 定义"的物品答空；逐资源的容器本来也说不清"一个百分比"是谁的）。
- **顺带修**：展示台改成"真的搬进去了就 `markChangedAndSync()`"，`onCharged` 仍只对 `UseItemAuraAccess` 调。

### 5.2 发射灵力：手上有容器就充能（二次调整新增）

- 挂点就是**唯一生成射线实体的地方** `SpiritBurstService.tryFire`。
- 顺序：算量 → 查余额（照旧）→ **付款之前**问一句"主手是不是灵力容器、并且真的收得下"（`insert(…, true) < amount`，即至少能进 1 单位）：
  - 收得下 → 照常扣款 → `insert(…, false)` 进容器 → 报一行进度（复用 `actionbar.mxt.charge.progress` 的读数与配色，数字取容器在该资源上的"已存 / 上限"）→ **不生成实体**，返回 true（冷却照记，与发射同频）。
  - 收不下（满了，或这个资源没有上限）→ **整个 burst 拒绝**：不扣款、不进冷却，与"付不出就拒绝"同一口径。
  - 手里不是容器 → 完全照旧发射。
- 判据是**具体类型** `SpiritVesselItem`（用户原话"手上是灵力容器"），不是"任何 `ItemAuraAccess`"——灵石之类手上的其它存储物不因此改变行为。

## 6. 不做

- 不做模式（当日第二条指令取消），也不做"切换后立即执行一次"。
- 不做手上的"存入"：输入只有展示台与发射灵力两条。
- 不给容器加长按灌注（理由见 §5.1），不改存储量的 JSON 形状。
