# 技能系统与固有注册表

## 架构结论

大量技能内容采用 Origins-NeoForge 的两层模式：能力实例由数据包定义；能力的类型、动作、条件和持久化组件由 Java 固有注册表提供。原版
Loot Function 的模式正是这一原则：JSON 选择类型并传递参数，类型的 Java 类和 Codec 必须在加载期注册。

```text
Java 固有类型注册表（加载期，不可热重载）
  AbilityType / ActionType / ConditionType / TriggerType / ComponentType
                       ↓ MapCodec 按 type 解码
数据包动态定义注册表（重载期）
  Ability / Technique / Element / SpiritRoot / Physique / Resource / Curse / ItemArchetype / Formation / Tribulation
                       ↓ 授予与引用
运行时附件（存档、同步）
  AbilityHolderData: 来源、能力 ID、每能力组件状态、冷却、引导状态
```

“固有”条目需要 Java 类、`MapCodec`、原版事件订阅、网络语义或原版注册表接入。它只定义 JSON 的语法与运行算法，不包含某个门派、法术或数值。

除 `MapCodec` 的 `type` 分派外，数据包也可直接引用无参数的固有行为 ID；两种联动的选择规则见 `08_注册表协作规范.md`。

## 统一能力模型

`Ability` 是数据包注册表中的具名定义。功法、灵根、体质、头衔、法宝、阵法、宗门或外部模组均可作为来源授予它。`AbilityHolderData`
应按“能力 ID + 来源集合”保存，只有最后一个来源移除时才撤销能力和其状态组件。

首批固有 `ability_type`：

| 类型               | 用途               | 典型配置                   |
|------------------|------------------|------------------------|
| `mxt:active`     | 主动术法、神通、法宝技能     | 槽位、目标规则、`costs`、吟唱、动作。      |
| `mxt:triggered`  | 命中、受击、击杀、突破等事件触发 | `trigger`、条件、概率、动作、冷却。 |
| `mxt:modifier`   | 被动数值改变           | 查询点、条件、修饰器列表。          |
| `mxt:aura`       | 周期范围效果、领域、护体     | 周期、范围、目标条件、对目标/自身动作。   |
| `mxt:channelled` | 持续引导、御剑、持续施法     | 启动/维持/停止动作、每周期成本、打断条件。 |
| `mxt:composite`  | 成套或互斥能力组合        | 子能力引用、启用条件、共享状态规则。     |

功法只定义学习条件、冲突标签、修炼修正和 `ability` 引用。灵根只根据其绑定元素授予元素相关能力和修炼修正；体质只授予独立加成；法宝同样只授予能力。这样“火球术”和“雷灵根受击放雷”共用冷却、成本、条件、网络与存档逻辑。

## Ability 数值公式

`Ability` 定义树内的**全部业务数值字段**必须按 `NumberProvider` 解码：伤害、治疗、护盾、范围、距离、持续时间、冷却、吟唱时间、概率、资源回复与 `costs[].amount` 均适用。MC Codec 应支持以下三种等价输入：JSON 数字是 `mxt:constant` 简写；JSON 字符串是 `mxt:expression`（exp4j）简写；带 `type` 的 JSON 对象用于 `attribute`、`resource`、`range` 等需要额外参数的 Provider。`schema_version`、数组长度、枚举序号等结构性整数不属于业务数值，仍必须为常量。

```json
"base_damage + caster_level * 2 + caster_spell_power * 0.35"
```

表达式只能使用白名单变量和函数。首批变量为 `caster_level`、`target_level`、`caster_realm`、`target_realm`、`caster_health`、`target_health`、`caster_<attribute_id>`、`target_<attribute_id>`、`caster_<resource_id>`、`target_<resource_id>` 与上下文 `base_damage`；资源和属性 ID 中的非字母数字字符在变量名中使用下划线。函数仅开放 `min`、`max`、`abs`、`floor`、`ceil`、`round`、`clamp` 和必要的确定性数学函数。不开放随机数、时间、世界查询、脚本回调或反射。

数据包重载时必须用 exp4j 解析并编译表达式，校验变量名、函数名和有限结果约束；运行时只填入当前动作的只读上下文，不能重复解析字符串。缺失上下文、非有限结果或不满足字段边界时，当前能力安全失败并记录定义 ID/字段路径。资源成本在提交前计算 `amount`，每项结果必须为正且有限，然后再执行完整预检和原子扣除。

## 自定义固有类型注册表

以下注册表是 `Registry<MapCodec<? extends T>>`。在 `NewRegistryEvent` 创建默认映射注册表，在 `DeferredRegister` 注册条目；接口使用
`registryDispatch` 根据 JSON 的 `type` 字段解码。每类必须有安全默认实现：无操作动作、恒真条件、空能力和空组件。

| 固有注册表                          | 上下文                 | 首批内置类型                                                                                                                    |
|--------------------------------|---------------------|---------------------------------------------------------------------------------------------------------------------------|
| `mxt:ability_type`             | `AbilityDefinition` | active、triggered、modifier、aura、channelled、composite、empty。                                                                |
| `mxt:ability_component_type`   | 单能力持久化状态            | cooldown、charges、toggle、timer、resource、target_lock、empty。                                                                 |
| `mxt:ability_trigger_type`     | 原版/模组事件到能力触发        | use、tick、attack、hurt、kill、block_break、block_use、item_use、equip、death、breakthrough。                                        |
| `mxt:entity_action_type`       | 单实体                 | no_op、sequence、damage、heal、apply_effect、add_resource、apply_curse、remove_curse、grant_ability、remove_ability、teleport、spawn_entity、spawn_projectile。 |
| `mxt:bi_entity_action_type`    | 执行者与目标              | no_op、sequence、damage_target、heal_target、knockback、transfer_resource。                                                     |
| `mxt:block_action_type`        | 世界与方块位置             | no_op、sequence、set_block、break_block、emit_particle、change_aura。                                                           |
| `mxt:item_action_type`         | 实体与物品栈              | no_op、sequence、damage_item、modify_component、consume_item、charge_artifact。                                                 |
| `mxt:entity_condition_type`    | 单实体判定               | always_true、and、or、not、realm、has_ability、has_curse、has_tag、resource_compare、sneaking。                                               |
| `mxt:bi_entity_condition_type` | 执行者与目标判定            | always_true、distance、team、relation、element_advantage。                                                                     |
| `mxt:block_condition_type`     | 方块与位置判定             | always_true、block_tag、biome_tag、aura_range、formation_member。                                                              |
| `mxt:item_condition_type`      | 物品栈判定               | always_true、item_tag、archetype、owned_by、energy_range。                                                                     |
| `mxt:damage_condition_type`    | 伤害事件判定              | always_true、damage_tag、amount_range、attacker_type、directness。                                                             |
| `mxt:number_provider_type`     | 延迟数值求值              | constant、range、attribute、resource、aura、context_variable、expression（exp4j）。                                             |
| `mxt:value_modifier_type`      | 数值叠加规则              | add、multiply_base、multiply_total、clamp、set。                                                                               |
| `mxt:curse_type`               | `CurseDefinition`       | timed、permanent、triggered、empty。                                                                                             |
| `mxt:resource_value_provider_type` | 资源当前值/最大值/回复求值 | current、max、regen、missing、constant。                                                                                      |
| `mxt:resource_bar_renderer_type` | 客户端资源条渲染          | textured_bar、segmented_bar、radial_bar、text_only、missing。                                                                  |
| `mxt:resource_bar_visibility_type` | 客户端资源条可见性      | always、non_full、recently_changed、resource_range、has_ability、and、or、not。                                                |

动作和条件应支持“单对象或数组”解码为顺序组合/逻辑组合。这样可以组合“受击后、距离小于 8、造成伤害并回复灵力”，而不必新增一个组合专用能力类。

## 原版固有注册表接入

下表必须使用 NeoForge `DeferredRegister` 注册到原版 `Registries` 或相应总线，不能放在数据包动态注册表中。

| 原版扩展点                            | 建议条目                                                  | 用途                      |
|----------------------------------|-------------------------------------------------------|-------------------------|
| `Registries.LOOT_FUNCTION_TYPE`  | `grant_ability`、`remove_ability`、`apply_curse`、`set_artifact_owner` | 战利品给予/移除能力、施加诅咒、设置法宝归属。      |
| `Registries.LOOT_CONDITION_TYPE` | `has_ability`、`has_curse`、`realm`、`spirit_root`、`physique`       | 按能力、诅咒、境界、灵根和体质筛选战利品。     |
| `Registries.RECIPE_SERIALIZER`   | `alchemy`、`refining`、`formation`                      | 专属匹配或产物逻辑的配方。           |
| `Registries.DATA_COMPONENT_TYPE` | `artifact_state`、`spirit_storage`、`item_abilities`    | ItemStack 可同步且可复制的法宝状态。 |
| NeoForge AttachmentType          | `cultivation`、`spirit_identity`、`spirit_stats`、`ability_holder`、`aura_chunk` | 实体、区块和世界的权威持久化数据；修炼进度、身份数据与灵魂属性分别独立存储。 |
| Payload 注册                       | ability use/toggle、附件快照、注册表版本                         | 客户端请求与服务端同步。            |
| `Registries.TRIGGER_TYPE`        | 突破、学习功法、炼丹、渡劫                                         | 进度和成就接入。                |
| 实体/方块/菜单/粒子注册表                   | 投射物、丹炉、阵旗、容器、表现粒子                                     | 仅在确实需要原版对象时注册。          |

## 数据包示例

`example:fire_ball` 是动态能力定义；`mxt:active`、`mxt:has_resource` 和 `mxt:spawn_projectile` 才是 Java 固有类型。

```json
{
  "type": "mxt:active",
  "activation": {
    "slot": "primary",
    "cast_time": "max(0, 12 - caster_level / 5)"
  },
  "costs": [
    {
      "id": "example:spirit_power",
      "amount": "12 + caster_level * 2"
    }
  ],
  "components": [
    {
      "type": "mxt:cooldown",
      "ticks": 40
    }
  ],
  "condition": {
    "type": "mxt:has_resource",
    "resource": "example:spirit_power",
    "min": 20
  },
  "entity_action": {
    "type": "mxt:spawn_projectile",
    "projectile": "example:fire_ball"
  }
}
```

优先用已有动作、条件和数值修饰器组合。只有需要新物理行为、原版事件时序或网络语义时，才新增 Java 类、`MapCodec` 和固有类型条目，并补充测试。

## 生命周期与安全

1. 固有类型在模组加载期完成注册；数据包重载只重新解码动态定义，不能改变 Codec 集合。
2. 加载顺序：固有类型 -> 元素/能力定义 -> 解析灵根、体质、功法和物品等引用 -> 校验循环引用 -> 发布不可变快照。
3. 类型或组件消失时，保留附件的原始数据并禁用能力，供迁移处理；不得直接丢弃存档状态。
4. 原版事件由触发器统一订阅、筛选并分发给能力持有者。禁止每个能力类型全局遍历实体或重复订阅同一事件。
5. KubeJS 可以新增动态能力定义、授予来源和监听 `AbilityUseEvent`，但不能注册新的固有 `type`、跳过服务端成本校验或直接写组件私有状态。
