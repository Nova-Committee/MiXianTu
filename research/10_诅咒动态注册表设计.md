# 诅咒动态注册表设计

## 定位

`curse` 是具名的数据包注册表，用于描述可施加、可叠层、可持续、可净化的负面状态。它不是 `Ability` 的别名：

- `Ability` 描述持有者主动或被动执行的能力；
- `curse` 描述附着在实体或物品上的外来状态，并拥有独立来源、层数、到期时间和净化规则；
- 诅咒的具体效果仍复用既有的动作、条件、数值修饰器和资源系统，避免另建一套技能执行框架。

因此一个诅咒 ID 可以被能力、物品、锻造结果、丹方、阵法、劫数、妖兽、契约、战利品和 KubeJS 事件统一引用，而不会复制定义或让各模块直接篡改附件。

路径：`data/<namespace>/mxt/curse/<path>.json`；资源 ID 例如 `mxt_test:soul_scorch`。

```text
curse（数据包定义）
       ↓ 由动作或原版扩展引用 ID
CurseApplication（本次施加参数）
       ↓ 服务端校验、叠层和生命周期
CurseHolderData / CurseContainerData（运行时状态）
```

## 固有与动态边界

| 层级         | 对象                                   | 职责                                                                                                                                                |
|------------|--------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------|
| 数据包注册表     | `curse`                              | 具名诅咒的显示、叠层、生命周期、动作、标签和引用关系。                                                                                                                       |
| Java 固有注册表 | `mxt:curse_type`                     | `CurseDefinition` 的 `MapCodec` 分派和生命周期算法。                                                                                                         |
| Java 固有动作  | `mxt:apply_curse`、`mxt:remove_curse` | 在给定实体上下文中引用诅咒 ID 并执行受校验的施加/移除事务。                                                                                                                  |
| Java 固有条件  | `mxt:has_curse`                      | 以诅咒 ID、标签、层数或剩余时间判定实体。                                                                                                                            |
| 运行时附件      | `CurseHolderData`                    | 实体当前拥有的诅咒实例。                                                                                                                                      |
| 物品组件       | `CurseContainerData`                 | ItemStack 固有诅咒及其转移规则。**已实现**：`mxt:curse_container` 的条目与 `mxt:apply_curse` 同形，六个装备槽与 Curios 上装即施加、脱下即移除（只撤自己那一份源），携带期间最多 20 tick 自愈，且不抢别的来源已持有的实例。 |

首批 `mxt:curse_type`：

| 类型              | 用途                                     |
|-----------------|----------------------------------------|
| `mxt:timed`     | 有确定持续时间的诅咒；到期后执行移除动作。                  |
| `mxt:permanent` | 除非被净化、覆盖或特定事件移除，否则不会自然到期。              |
| `mxt:triggered` | 只在预定义触发器到达时生效，例如受击、施法、死亡或突破；可同时具有持续时间。 |
| `mxt:empty`     | 安全降级类型，不产生效果。                          |

复杂机制必须新增 Java Codec 类型，例如需要特殊碰撞、跨维度索引或网络语义时。数据包和 KubeJS 只能选择已注册的 `type`
，不能写入任意脚本回调。

## 定义字段

所有 `curse` 定义至少拥有基础公共字段，`type` 之后的字段由对应 `MapCodec` 决定：

| 字段                      | 必填 | 含义                         |
|-------------------------|----|----------------------------|
| `schema_version`        | 是  | 数据格式版本。                    |
| `type`                  | 是  | 固有 `mxt:curse_type` ID。    |
| `display`               | 是  | 本地化名称、说明、图标、提示颜色和是否对持有者显示。 |
| `tags`                  | 否  | 供净化、免疫、掉落或条件批量匹配。          |
| `application_condition` | 否  | 施加前必须满足的实体条件。              |
| `stacking`              | 是  | 最大层数和叠层策略。                 |
| `on_apply`              | 否  | 首次施加成功后执行的实体动作。            |
| `on_tick`               | 否  | 周期、动作和执行条件。                |
| `on_expire`             | 否  | 自然到期后执行的实体动作。              |
| `on_cleanse`            | 否  | 被解毒后执行的实体动作。               |

`stacking.mode` 仅允许已定义的有限枚举：

- `ignore`：已拥有时拒绝新的施加请求。
- `refresh_duration`：保持层数，刷新持续时间。
- `add_stacks_refresh_duration`：增加至上限后刷新持续时间。
- `add_stacks_keep_duration`：增加至上限，但不延长既有到期时间。
- `replace`：移除旧实例再创建新实例；被覆盖不算诅咒自己的时刻，所以不执行任何行为（实现目前也不发 `replaced` 原因的移除事件）。

示例，带层数的神魂灼烧：

```json
{
  "schema_version": 1,
  "type": "mxt:timed",
  "display": {
    "translation_key": "curse.mxt_test.soul_scorch",
    "icon": "mxt_test:curse/soul_scorch",
    "color": "#7155b8"
  },
  "tags": [
    "mxt_test:fire",
    "mxt_test:soul"
  ],
  "application_condition": {
    "type": "mxt:resource_compare",
    "resource": "mxt:soul_power",
    "min": 1
  },
  "duration_ticks": 600,
  "stacking": {
    "max_stacks": 3,
    "mode": "add_stacks_refresh_duration"
  },
  "on_tick": {
    "interval": 20,
    "entity_action": {
      "type": "mxt:damage",
      "amount": 1.0,
      "damage_type": "mxt_test:soul_burn"
    }
  }
}
```

## 解毒：由解毒剂 + 标签管理（2026-09-19 定案）

定义侧**不**声明"谁能解我"。曾经预留的 `cleanse_tags` 与 `allow_force_remove` 已从实现、数据包文档与网站一并删除，理由是方向反了：原版效果系统曾有的
`EffectCure`（后被删除，NeoForge 后来自己补过一个同名类）也是这个方向——**解药带上标签，效果进标签**，效果自己不声明任何东西。

因此：

- 解毒剂（丹药、术法、法阵、物品）用行为 `mxt:remove_curses_by_tag` 声明它能解的 `mxt:curse` 标签，`tags` 写 `"#命名空间:标签"`
  （与 `mxt:entity_tag` 同一套写法），命中任意一个即解；
- 标签文件 `data/<namespace>/tags/mxt/curse/<path>.json` 列出该标签下的诅咒，内容方由此决定"哪种毒怕哪种解药"；
- 移除原因是 `cleansed`，因此走同一套移除事务并执行被解诅咒的 `on_cleanse`；
- `mxt:remove_curse` 按同一个原因移除单个具名诅咒；
- 查询侧（`:41` 那行的"以诅咒 ID、标签、层数或剩余时间判定实体"）已接入：`mxt:has_curse` 的实体与战利品两个版本共用
  `CurseFilter`，四个字段全部可选、必须由同一条实例满足，`stacks` / `remaining_ticks` 是 `{min?, max?}`
  闭区间，永不到期的实例在剩余时间上视作无穷。

### 类型、禁用与重入（2026-09-19 二轮定案）

- **`mxt:triggered` 接进 trigger 系统**：类型自带 `triggers`（`Trigger` 列表，必填非空），持有期间任一触发器命中的信号到达就对持有者执行一次
  `on_tick`，`tick_interval` 不参与；订阅由 `CurseTriggerSubscriptions` 作为 `TriggerRehydrators` 的 `curse`
  模块重建（施加/移除/到期与 `/reload` 都会重建）。
- **`mxt:empty` 成为真正无行为的占位类型**（`CurseType.inert()`）：不到期、不执行任何行为、也不排进周期队列。
- **加载期校验**：`mxt:timed` 的常量时长必须为正、`mxt:triggered` 的 `triggers` 不得为空；运行期遇到兑现不了的时长（公式算坏）是
  **拒绝这次施加**（`INVALID_DURATION`），不再抛异常穿透 tick 与事件处理器。
- **重入保护**：同一实体的同一条诅咒在事务中不可再次进入（`CurseService` 的 ThreadLocal 守卫，`REENTRANT`），自引用的
  `on_apply` 不再无限递归。
- **冻结语义**：`#mxt:disabled` 或被删除的定义让已有实例停止周期/触发/到期、拒绝解毒，只有 `explicit`
  能取下；定义回来即恢复（rehydrator 里补一次重排）。
- **时长覆盖只能收紧**：引用方给的时长可以缩短定义声明的时长，不能延长、也不能把限时变成永久。
- **来源账本与技能共用（2026-09-19 三轮，即原计划④）**：抽了 `util/SourceLedger`，`AbilityAttachment` 与
  `CurseHolderAttachment` 都用它——「只要还有一份来源持有就存在，最后一份松手才移除」在两边是同一条规则。诅咒的来源从单字符串变成一个
  **标识符集合**（`mxt:ability`/`mxt:loot`/`mxt:command`/`mxt:equipment/<槽位>/<物品>`/`mxt:curios_equipment`/脚本自述），施加即
  `grant`、装备对账与脚本可 `release` 单份来源、命令与解毒仍是整条移除；旧存档的单字符串 `source`
  在解码期并入账本。层数与到期时间仍是这条实例共享的，来源只决定存续。
- 执行顺序是附件里的施加顺序（随存档稳定），不按定义 ID 重排——排 ID 要读 Holder 的 key，而重载后那份 key 未必可靠。

诅咒自己的生命周期只留两个行为：`on_expire` 与 `on_cleanse`。显式移除、管理员、被 `replace` 覆盖都是外部决定，定义上不给行为（
`replace` 覆盖时会补发一条 `replaced` 原因的移除事件，但被覆盖的实例不执行行为）。

### 展示：只做 `display_condition`（2026-09-19 定案）

设计稿里那套 `display`（本地化名、说明、图标、提示颜色、是否对持有者显示）**没有实现**，只落地了一件事：`display_condition`
——人物信息面板的「诅咒」一行是否列出这条实例。不满足时**整行不留**（不是留空行），所以隐藏诅咒、逐步显形这类内容都能表达。名字走既有的
`DefinitionText`（`curse.<命名空间>.<路径>` 翻译键），因此不需要自定义展示字段；图标与颜色等美术面留待将来单独定案。

本节的字段表与示例仍是**理想形状**（嵌套 `stacking` / `on_tick` / `display`、`schema_version`、`tags` 顶层字段）；实际实现是扁平字段，且没有
`display` 与 `schema_version`，以 `docs/数据包格式.md` 为准。

## 引用与施加格式

仅引用定义 ID 时，使用完整资源 ID。需要在当前触发点覆盖默认层数或持续时间时，使用 `curses` 数组；每项的 `id` 必填，`stacks` 和
`duration_ticks` 可选：

```json
{
  "type": "mxt:apply_curse",
  "curses": [
    {
      "id": "mxt_test:soul_scorch",
      "stacks": 1,
      "duration_ticks": 200
    },
    {
      "id": "mxt_test:sealed_meridians",
      "stacks": 1
    }
  ]
}
```

覆盖值只能收紧或在定义明确允许时改变；不能以引用方绕过 `max_stacks`、`application_condition` 或固有类型边界。数组中同一诅咒
ID 不得重复，加载器必须报错。

`mxt:remove_curse` 按具名 ID、`mxt:remove_curses_by_tag` 按标签批删，两者的移除原因都是内部固定的 `cleansed`（另有
`expired` 由调度器
发出）；定义侧只有 `on_expire` / `on_cleanse` 两个行为，`on_remove` 那种"按原因分支的单一行为"已不再存在。

## 各模块引用点

| 消费者                                  | 推荐引用方式                                                      | 典型时机                 |
|--------------------------------------|-------------------------------------------------------------|----------------------|
| `ability`                            | `entity_action: { type: "mxt:apply_curse", curses: [...] }` | 命中、引导 tick、被动触发。     |
| `item_archetype` / 物品                | 装备、使用、命中或掉落生命周期动作                                           | 诅咒法器、遗物、护甲。          |
| `forging_blueprint`                  | `on_complete`、`on_fail` 生命周期动作                              | 锻造失败时附加裂纹诅咒，或成品自带诅咒。 |
| `alchemy_recipe`                     | 成功、失败、服用效果动作                                                | 丹毒、反噬、净化丹。           |
| `formation`                          | 激活、维持、进入/离开范围、触发动作                                          | 诅咒阵、净化阵。             |
| `tribulation`                        | 阶段与结算动作                                                     | 心魔、劫后虚弱。             |
| `creature_profile` / `contract_type` | 攻击、死亡、契约违约或协同动作                                             | 妖兽毒咒、契约反噬。           |
| 战利品                                  | 原版 `apply_curse` Loot Function                              | 被诅咒战利品或开启容器时的施加。     |
| KubeJS                               | 调用受校验的 `applyCurse` / `removeCurse` API 或监听事件               | 剧情、任务和低频联动。          |

各模块不得直接写 `CurseHolderData`、在自身定义中复制诅咒效果，或把诅咒 ID 偷换成能力 ID。若某个引用点已经具备通用 `on_*`
动作字段，应仅通过 `mxt:apply_curse` / `mxt:remove_curse` 进入系统，不另加专属回调字段。

## 运行时状态、顺序和安全性

`CurseHolderData` 每项保存 `curse` ID、层数、首次施加 tick、到期 tick、来源描述、定义版本和该诅咒类型需要的组件状态。
`CurseContainerData` 只保存物品固有状态；物品影响实体时仍发起一次服务端施加事务。

施加顺序固定为：解析定义 -> 校验目标/免疫/施加条件 -> 触发可取消 `CurseApplyEvent.Pre` -> 计算叠层结果 -> 原子写入实例 ->
执行 `on_apply` -> 广播 `CurseApplyEvent.Post`。任一前置步骤失败或被取消时，不写入实例，也不执行动作。

自然到期、解毒、替换和显式移除都使用同一移除事务，其中只有到期与解毒会执行定义上的行为（`on_expire` / `on_cleanse`），其余原因由调用方
决定跑什么。同一 tick 内的多个诅咒按实例 ID
稳定排序；动作不能递归立即重入同一实例，新的施加请求排入当前事务后的队列，防止无限循环。

诅咒仅在需要时进行周期处理，按最短下次 tick 建立调度队列，禁止每 tick 遍历全世界实体。客户端只接收自身和明确可见目标的显示快照，不能施加、叠层或净化诅咒。

## 热重载与兼容

- 重载先校验所有 `curse` ID、`type`、动作、条件、标签和跨定义引用；成功后才发布新快照。
- 已存在实例保留 `curse` ID、层数和到期 tick。新定义的后续 tick/移除行为从新快照解析；正在执行的单次事务使用启动时快照。
- 删除定义时保留实例原文并标记为未知/停用，禁止继续触发或净化为默认效果；迁移器或兼容别名恢复后再重新解析。
- KubeJS 可以创建 `curse` 数据包定义和监听诅咒事件，但不能注册新的 `mxt:curse_type`、直接修改附件，或绕过服务端施加事务。
