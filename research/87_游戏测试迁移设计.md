# 87 —— `/mxt_test` 与探针迁移到 NeoForge GameTest

状态：**已完成**（2026-10-15）。全部 `/mxt_test` leg 与十个 `*Probes` 已迁成 **278 个 GameTest**，
`runGameTestServer` **全绿**（退出码 0，退出码即失败的 required 测试数）。落地过程与修掉的 bug 看第 8 节，
别信这里的叙述。

## 1. 为什么迁

迁移前，行为验证只有一条路：`/mxt_test <leg>`（`MxtTestCommands`，约 5000 行）加十个 `*Probes` 类。
它有几个结构性问题：

- **必须有人**。要开一个专用服务端、有 OP 玩家、手敲命令、读聊天栏里的 `OK` / `MISMATCH`。
  结果是大量探针"写了但没实跑"——`research/` 里多篇稿子的状态列都写着"探针未实跑"。
- **一个 leg 一次性跑一大堆**。`QualityProbes.run` 是 28 条断言串在一个方法里，第一条失败之后
  人只看到那一行，剩下的跑没跑、对不对都不知道。
- **进不了 CI**。`.github/workflows/build.yml` 只跑 `./gradlew build`，连 `compileTestModJava` 都不含。
- **玩家操作测不到**。控制台没有玩家，于是有的探针自己造 NeoForge `FakePlayer`，而 `FakePlayer`
  的 `openMenu` / `tick` 都是空实现——**画符工作站那条腿（`drawing_station`）因此是唯一一条只能人肉看的**。

## 2. 这个版本的 GameTest 是什么形状（关键结论，别照别的版本的经验走）

MC 26.1.2 / NeoForge 26.1.2.99 的 GameTest **已经不是注解版**：`@GameTest` / `@GameTestHolder` /
`@PrefixGameTestTemplate` 都不存在了。取而代之的是三个**数据包注册表**：

| 注册表 | 装什么 |
| --- | --- |
| `minecraft:test_function` | `Registry<Consumer<GameTestHelper>>`，**内置注册表**，由 `TestFunctionLoader` 在 bootstrap 时填 |
| `minecraft:test_environment` | 一次批次的 setup / teardown（`all_of` / `game_rules` / `clock_time` / `timeline_attributes` / `weather` / `function`） |
| `minecraft:test_instance` | `TestData` ＋ 一个 `GameTestInstance`（内置两种：`minecraft:function`、`minecraft:block_based`） |

两条声明路径：

1. 数据包：`data/<ns>/test_instance/<name>.json` + `data/<ns>/structure/<name>.nbt`；
2. 纯代码：`RegisterGameTestsEvent`（**mod 总线**，只在 `GameTestHooks.isGametestEnabled()` 为真时由
   `RegistryDataLoader` 触发）的 `registerEnvironment` / `registerTest`。

几个必须记住的点：

- **`neoforge.enabledGameTestNamespaces` 已经没有人读了**。26.1.2.99 里只有 `neoforge.enableGameTest`
  有读者（`GameTestHooks`）；`build.gradle` 里那几行只是历史遗留，`runGameTestServer` 会跑**全部**
  已注册的实例。改动仍然留着这条属性，只为和别的 run 保持一致，不要指望它过滤命名空间。
- **`test_function` 是内置注册表**，bootstrap 之后就 freeze 了；但 NeoForge 在 mod 载入期把所有内置注册表
  解冻并逐个发 `RegisterEvent`（`GameData.unfreezeData` / `postRegisterEvents`），所以 mod 可以在
  `RegisterEvent` 里往 `minecraft:test_function` 注册自己的 `Consumer<GameTestHelper>`。
- **`test_instance` 是同步给客户端的注册表**（`RegistryDataLoader.SYNCHRONIZED_REGISTRIES`）。所以
  测试实例必须**能被 `GameTestInstance.DIRECT_CODEC` 编码**——自定义一个 `GameTestInstance` 子类并且
  不在 `test_instance_type` 里登记自己的 codec，在集成服务端（`runTestClient` 那类）会炸在同步上。
  **本迁移因此只用原版的 `minecraft:function` 实例类型**，把自己那份逻辑挂在函数上。
- **一个测试必须自己叫 `succeed()`**（`BuiltinTestFunctions.ALWAYS_PASS_INSTANCE` 就是
  `GameTestHelper::succeed`）。函数直接返回不会算通过，只会耗到超时。
- **`GameTestInfo` 的超时来自 `TestData.max_ticks`**，`helper.fail(...)` 抛的是 `GameTestAssertException`，
  一路冒到 `GameTestInfo.startTest` 的 catch 里被记成失败。
- `runGameTestServer` 的**退出码 = 失败的 required 测试数**（`GameTestServer.onServerExit`），所以它天然
  可以当 CI 门禁；ModDevGradle 的 `gameTestServer` run 类型已经带上了 `-Dneoforge.enableGameTest=true`。

## 3. 玩家：为什么不用 `GameTestHelper.makeMockServerPlayerInLevel`

原版给了 `helper.makeMockServerPlayerInLevel()`，它 `new` 一个真 `ServerPlayer`、开一个 netty
`EmbeddedChannel` 当连接、再 `PlayerList.placeNewPlayer`。**在这套环境里它直接不可用**：
`placeNewPlayer` 会 fire `OnDatapackSyncEvent`，Curios 与 JEI 都会回一个自定义载荷，而 NeoForge 的
`NetworkRegistry.checkPacket` 对"没握过手的连接"一律拒收：

```
java.lang.UnsupportedOperationException: Payload curios:sync_data may not be sent to the client!
    at NetworkRegistry.checkPacket(NetworkRegistry.java:436)
    at ServerCommonPacketListenerImpl.send(...)
    at PlayerList.placeNewPlayer(...)
```

解法是 NeoForge 自己留的口子 **`NetworkRegistry.configureMockConnection(Connection)`**（注释就写着
"for use in game tests"）：它把连接标成"对端也是 NeoForge 且全部通道都协商过"，`hasChannel` 于是全真。
探针因此自己拼一个玩家：`new ServerPlayer(server, level, profile, ...)`（`gameMode()` 覆盖成
CREATIVE）＋ `new Connection(SERVERBOUND)` ＋ `EmbeddedChannel` ＋ `configureMockConnection` ＋
`placeNewPlayer`。**没有用 `FakePlayer`**：它的 `tick()` 与 `openMenu()` 都是空实现，而"真的能开菜单"
正是这次迁移要解锁的东西。

**补全的东西**：探针跑起来之后，`player.openMenu(...)` 是真的开菜单（包写进 `EmbeddedChannel` 后丢掉），
`level.players()` 与 `PlayerList` 里都真的有这个人，玩家自己会被 tick。于是
`/mxt_test drawing_station` 那条"控制台没有玩家，只能人肉看"的腿第一次成了可断言的测试。

## 4. 隔离：一个探针一个批次

`GameTestBatchFactory.divideIntoBatches` 按 `environment` 这个 holder 分组，**同一组里的测试是同时跑的**
（`GameTestRunner.runBatch` 一次把整批塞进 `GameTestTick`），批次之间才串行。而这套探针里有改
`MxtServerConfig` 的（肩挂）、有改 level 时钟的、有开一整个维度的（秘境）——同批跑必然互相踩。

所以 `ProbeTests.registerTests` **给每个探针注册一个自己的 `test_environment`**（一个空的 `all_of`），
一个 environment 一个批次，批次大小恒为 1，于是全部串行。代价是每个探针多一次批次切换，收益是
"探针之间不可能互相干扰"这条不用再一条条论证。

配套的一条：`ProbeContext` 在构造时**把上一个探针留下的玩家退掉**（`PlayerList.remove` + `discard`），
所以任何时刻 `level.players()` 里只有一个探针的人。

## 5. 竞技场

结构模板是**全空气**的（`palette` 只有一个 `minecraft:air`），两个尺寸：

| 结构 | 尺寸 | 给谁 |
| --- | --- | --- |
| `mxt_test:arena` | 32 × 12 × 32 | 默认 |
| `mxt_test:grid` | 72 × 12 × 72 | 要把生物铺在 12 格网格上的探针（`Probe.grid(index)`） |

真正的地板和围墙不是结构给的，是**测试框架自己砌的**：`TestInstanceBlockEntity.encaseStructure` 沿结构
包围盒放一圈 `minecraft:barrier`，**地板在结构下一层**（`minY - 1`），所以 `arena` 相对坐标 `y = 0` 就是
站立面，`y = -1` 是屏障地板。`sky_access: true` 让顶上不封盖（否则 `processStructureBoundary` 也会给
顶面铺屏障、`canSeeSky` 与光照全变）。结构放置前 `StructureUtils.clearSpaceForStructure` 会把包围盒内
清成空气——空气块 `Level.setBlock` 会提前返回，所以这个"清空"实际上很便宜。

**结构模板是 gzip 的 NBT**，格式与 `data/minecraft/structure/empty.nbt` 一致：
`{size:[x,y,z], entities:[], blocks:[{pos:[..],state:0}], palette:[{Name:"minecraft:air"}], DataVersion:4790}`。
（第一版试过把 `blocks` 写成空表，`NbtIo` 读到一半报 `EOFException`；照抄原版那份、只改 `size` 三个
int 就没问题。要改尺寸就照这个办法改，别手拼。）

## 6. 代码落点与拆分口径

```
src/test-mod/java/com/iafenvoy/mxt/probe/
    Probe.java            一个测试：id、用哪个竞技场、tick 预算、body
    ProbeContext.java     helper + 真玩家 + 断言账本 + 注册表查询 + 竞技场坐标
    ProbeTests.java       唯一一份域清单，两个注册口（RegisterEvent / RegisterGameTestsEvent）
    ProbeDefinitions.java 夹具定义 id 常量
    ProbeKit.java         清霄场景（原 /mxt_test kit）那一套给物
    <域>/<域>Probes.java  各域探针，一个测试一个方法
src/test-mod/java/com/iafenvoy/mxt/testmod/   测试包自己的物品 / 方块 / 实体 / 渲染注册，不写断言
```

**拆分口径**：原来是"一个 leg 一大堆断言"，现在是**每个独立场景一个 `Probe`**。旧代码里那些
`private static void xxx(source, level, player, pos, ...)` 的场景方法正好就是边界，一个方法一个测试。
`Probe.of("域/名字", Class::method)` 的 id 用 `/` 分层。

`ProbeContext` 的口径：`check(String, boolean)` **记账不抛异常**（返回那个 boolean，所以旧代码的
`ok &= check(...)` 原样保留），body 跑完之后一次性把所有失败拼起来 `helper.fail(...)`——一个测试
报出它发现的**全部**不一致，而不是第一条。`after(ticks, Runnable)` 是唯一的延时口，且**只能在 body 里
登记**：`GameTestInfo` 是一边遍历 `runAtTickTime` 表一边执行回调的，回调里再登记会破坏迭代。

  `command.mxt_test.*` 键）。`testmod` 现在只剩测试包自己的注册（物品 / 方块 / 实体 / 渲染 / `ProbeBeast` /

  两个探针是**两个批次**、先后没有保证，所以并成 `world/secret_realm/keep_and_reopen`。

## 8. 落地记录

- 2026-10-15：框架就位（`Probe` / `ProbeContext` / `ProbeTests` / `ProbeKit` / `ProbeDefinitions`）、
  两个竞技场模板、`gameTestServer` run 指向 `mxt_test` 并配 `gameDirectory = run-game-test-server`、
  新增 `-PmxtGameTestSelection` 选择器。全部 `/mxt_test` leg 与探针类迁成 **278 个 GameTest**，
  旧的 `MxtTestCommands` 与十几个 `testmod/*Probes`（连同 28 条 `command.mxt_test.*` lang 键）已删除。
- **旧 harness 有一个隐含前提**：很多 leg 是"先 `/mxt_test kit` 再跑"写的，payer 的修为决定价格公式读什么，
  裸玩家付不出任何东西。迁移后用 `Probe.kitted(...)` 把这个前提显式写出来（`ProbeContext.run` 里先跑
  `ProbeKit.scenario`）。整个 contract 域（23 个测试）就是这样从 7 红变全绿的。
- 顺手修掉两处**挡住整个世界加载**的既有数据问题（不是本次迁移引入的）：
  `data/mxt/mxt/ability/sky_swallowing_sword_qi.json` 的两个 8 位十六进制颜色（`ExtraCodecs.STRING_RGB_COLOR`
  只收 6 位，`#C7FF2020` / `#CCFF5522` → `#FF2020` / `#FF5522`，**丢掉了两位 alpha，视觉效果会变**，
  要保住 alpha 得改 codec 而不是改数据）；以及 `data/mxt_test/mxt/aura_zone/overworld.json` 的
  `"dimensions"` 还写着裸字符串（字段已改成列表）。
- **迁移当场抓到的真正 bug（已修）**：`SpriteIcon` 的 `SPRITE_CODEC` / `TEXTURE_CODEC` 声明在它们包起来的
  `CODEC` **之前**，字段初始化时 `CODEC` 还是 null，于是两个 codec 各自持有一个 `second == null` 的
  `EitherCodec`——**任何**走 `mxt:textured_bar` / `boss_bar` 图形字段的解码都抛 NPE（数据包里的坏条目被
  `TolerantListCodec` 吞掉，所以一直没人发现）。把 `CODEC` 挪到前面即可。这条是 `verify/sprite_icons` 抓出来的。
- 迁移中一并修掉的**探针自身缺陷**（都不是新行为）：
  - `verify/sprite_icons` 最后一条"boss bar 不该吃 GUI sprite"永远不可能成立——`OriginsRenderData` 每个字段
    都是可选，任何对象都解得开；改成断言解析出来的 boss bar 仍用默认贴图（没有被 GUI sprite 顶替）。
  - `verify/upkeep_bill` 用 `JsonOps.INSTANCE` 解析带 `Holder<Resource>` 的消耗，永远解不开（旧 leg 会直接抛
    异常中止整条 `verify`）；改用 `RegistryOps.create(..., registries())`。
  - `alchemy/pill/pill_color` 拿整个 int 比 fixture 写的 6 位色（`0x8F3FA8`），而颜色实际带 alpha；改成比低 24 位。
  - `verify/generated_names` 拿 `Component.getString()` 比生成键，而 game test 服务端**是有语言文件的**
    （测试包 `en_us` 里就翻译了那几个键）；改成读 `TranslatableContents.getKey()`。
  - `verify/minor_stages` 的"凡人读 minor_stage 应为 NaN"用的是 `FormulaContext.value`，而那一层**故意**把
    变量给的 NaN 洗成 0（`FormulaVariables.read`）；改用 `FormulaVariables.peek` 读原始值。
  - `alchemy/limits_and_parts` 的 `missing-material` 期望 `STRUCTURE`，但炉壁方块还在、只是材料空了，
    `AlchemyWorkstationService` 的结构判定在先且通过，塌掉的是炉温上限 → 期望改成 `TEMPERATURE`
    （与 AGENTS 里"炉壁或供热缺一就是这台炉子根本不能开"一致）。
  - `QualityProbes.ingredient_needs_items` 旧 leg 把判定写死成 `false`（永远 MISMATCH 的占位），
    按它自己写下的期望改成真的算：`mxt:quality` 材料不给 `items` / 给空 `items` 都必须解不开。
  - `MessageProbes` 的 channel 选择写的是 `actionbar`，而 `MessageChannel` 的序列化名是 `action_bar`；
    这条 leg 从没跑过（`research/82` 记着只编译未运行），所以一直是错的。
- **第二轮的成果与两条平台硬约束**（2026-10-15，续）：
  - **探针玩家必须是 `ServerPlayer` 的子类，而且必须是生存模式。** 两条都是踩出来的：
    `ConfigSync.syncPendingConfigs`（NeoForge）对 `player.getClass() == ServerPlayer.class` 的玩家**直接抛异常**
    （"configsToSync should contain an entry for …"），对**子类**则静默跳过——它注释里写的 "null for GameTestPlayer"
    就是这个意思，所以探针玩家只能是匿名子类或具名子类（先用具名子类反而让 `player.connection` 变 null，最后用匿名子类）；
    而创造模式的身体**能力无敌、且不消耗任何东西**（`abilities.invulnerable` + `hasInfiniteMaterials`），
    于是"要付代价"的探针全都静默不付——所以建好之后要把 `instabuild` / `invulnerable` 清掉、模式读生存。
  - **`TriggerRuleService.dispatch` 的冷却读的是 level 自己的时钟，不是发布时传进去的 `gameTime`**
    （`long gameTime = actor.level().getGameTime();`），所以"把时间往前传"永远绕不过冷却，探针得**推 level 时钟**
    （照 `DrawingProbes` / `PillProbes` 的做法）。这条是 `verify/trigger_gates` 抓出来的。
  - **再修掉一个真 bug**：`FlightService` 的起剑快照对**任何**骑手都读 `NeoForgeMod.CREATIVE_FLIGHT`，
    而那句话上面自己的注释写着"只有玩家有这些要记"——猪/灵宠起剑会抛
    `Can't find attribute neoforge:creative_flight`。改成只在 `holder instanceof Player` 时读。`artifact/flight`
    与 `artifact/flight/crash` 因此转绿。
  - 迁移中一并修掉的**探针自身缺陷（第二轮）**：`verify/sprite_icons` 最后一条断言不可能成立（`OriginsRenderData`
    每个字段都可选，改成断言"boss bar 没把 GUI sprite 当贴图读"）；`verify/upkeep_bill` 用 `JsonOps` 解不开带
    `Holder<Resource>` 的消耗（改 `RegistryOps`）；`artifact/storage/address` 的夹具 id `mxt_test:probe` 早已不存在，
    容错列表把它丢掉后**两边都"解析成功"**（换成真注册的 id，并断言解出来确实是 1 条）；
    `artifact/hold/claim` 曾被我错加了 `kitted`（kit 给法器会先 claim 一次、扣血会让 `invulnerableTime` 吞掉本次），
    已去掉；`world/secret_realm/keep_and_reopen` 打开/认领的实例会在测试结束后留在注册表里，
    让后面的 `border` 读到别的种子（补终于 destroy）。
- **第三轮的成果（2026-10-15，续）**：
  - **又一条平台硬约束，这次是"探针玩家默认无敌"**：`ServerPlayer.isInvulnerableTo` 除了无敌旗标，还有
    `|| !this.connection.hasClientLoaded()` 这一条，而 `hasClientLoaded()` 的计时器在建 listener 时被设成 60 拍、
    由 `ServerboundPlayerLoadedPacket`（真实客户端在区块加载完后发的那个包）清零。假连接永远不发这个包，
    于是**探针玩家在头 60 拍里对所有伤害免疫**——代价是"按生命计价"的探针全都静默不扣血。
    修法是建好玩家后调一次 `connection.markClientLoaded()`（公开方法）。这条值得单独记住：
    它不影响任何"返回数字"的断言，只影响"身体真的变了没有"，所以特别难发现。
    排查过程用了：伤害事件监听（`seen=[]` → 事件根本没发）、`EntityInvulnerabilityCheckEvent`
    （`orig=false now=false` → 不是别人翻的）、`EnchantmentHelper.isImmuneToDamage`（false）、
    装备栏（全空），最后回到 `ServerPlayer#isInvulnerableTo` 的第三个条件。
  - 因此 `artifact/hold/claim` 现在真的会掉血了，但它暴露了**下一层问题**（见下面的未绿清单）。
- **第四轮：把最后六个红点逐个查清（2026-10-15，续）**。这一轮里有 **四个是真 bug**，全都只能由"非玩家身体"
  或"真跑一遍"才暴露得出来，正是这次迁移想要的：
  1. **`mxt:conditional` 只对玩家算分支**（`util/formula/number/Conditional#evaluate` 读的是 `context.player()`，
     没有玩家就直接走 fallback）。于是**任何生物**的资源上限都取 fallback：`mxt_test:spirit_power` 的 `max`
     写的是"站在 `spirit_power_refining` 才给 100+level*10，否则 0"，猪的境界明明设进去了，上限仍读 0，
     灌资源被夹成 0，突破/妖burst 都因"pay 不出"被拒。改成问**这个数字所属的身体**（`context.caster()`，
     没有 caster 才退回 player）。`lifespan/breakthrough` 与 `cultivation/identity/mob_burst` 的一半因此转绿。
  2. **`TemporaryUseComponent` 的记录只按身体存，没按模块存**：记录表是 `Map<UUID, Written>`，而注释写着
     "each takes back only its own"。`HoldService.onUseStart`（**任何**物品开始使用时都会 fire）无条件
     `takeBack(entity)`，于是把**丹药模块**刚写上的 `minecraft:consumable` 一起摘掉了——挂在普通物品上的丹
     （`plain_item_pill`）因此永远不被原版吃掉，而丹药效果照样结算（`Finish` 事件拿到的是使用前的 **copy**，
     上面还有组件）。修法：记录加 `Owner`（`HOLD` / `PILL`），每个模块只收回自己那一份。
  3. **定义写的粒子颜色会让妖burst 抛异常**：`Resource.particle_color` 用的是原版
     `ExtraCodecs.STRING_RGB_COLOR`，它解出来的 int **带 alpha 字节**（`AuiStyles` 的注释早就写着这件事），
     而 `SpiritBurstEntity#setParticleColor` / `SpiritWispParticleOptions` 的构造器按"必须是 RGB"直接抛
     `Particle color must be an RGB value`。凡是在数据包里写了 `particle_color` 的资源，第一次发妖burst 就炸
     （`mxt:spirit_wisp` 粒子同理，等于 JSON 里根本写不出这个粒子）。改成两处出口都丢掉 alpha、只留 RGB。
  4. **秘境传送假设"身体对象不变"**：`Entity#teleportTo(ServerLevel, …)` 只返回 boolean，**把真正搬过去的那个
     身体丢掉了**；非玩家跨维度时平台会 `EntityType.create(DIMENSION_TRAVEL)` + `restoreFrom(旧)` +
     `removeAfterChangingDimensions()`，即**换了一个新实体**。`SecretRealmService` 却继续拿旧引用写传送状态、
     发事件、跑 `exit_action`——旧身体已被移除，新身体身上什么都没有，于是"生物进秘境"看起来 `changed=true`
     却待在原地，真进去的那只也没有回程记录（永远出不来）。修法：新增 `move(...)` 直接构造
     `TeleportTransition` 调 `Entity#teleport` 拿到**到达的身体**，之后所有状态/事件/行为都落在它上面，
     并由 `Result.traveller()` 交回给调用方（玩家是在原地传送，还是自己那份引用）。
  5. 剩下的红点是**探针自己的期望**错了（不是行为）：
     - `artifact/flight/directed`：探针玩家是裸玩家，而 `mxt_test:qi` 这个灵气的 `use_condition` 是
       `mxt:has_realm`——**没入过境界的身体花不掉自己身上的气**（`ResourceUseService.canUse` 在扣费前把它们
       全部拒掉，报的是 `INSUFFICIENT_RESOURCE`）。补上"站在 `qi_refining` 且 80 修为"，与猪那两条腿一致。
     - `alchemy/pill/plain_item_armed`：除上面的真 bug 外，还要确认"原版确实吃掉一个"——断言保持不变，
       组件收回后 `ingots-1` 现在成立。
     - `cultivation/identity/mob_burst`：上限修好之后，账户起始值是定义自己的 `default_value`（100），
       价格要按**差值**读（`before - after == 10`），而不是断言"发完剩 10"。
     - `world/secret_realm/traveller`：跟随 `Result.traveller()` 拿到达的身体去读维度、成员行与回程。
     - `herb/stability`（原来时红时绿）：`rewind` 把行的时钟往回拨 400 拍，**越过了 0**——而负时钟是引擎自己
       "未结算的野生 roll"标记，于是这一行被当成刚 roll 出来的野生植株、当场重新按"现在"计时，年龄回到 0。
       批次跑得早（level 时钟 < 400）就必红，跑得晚就绿，这正是它"依赖时钟与顺序"的原因。改成回拨后
       `Math.max(0, clock)`：真实行的最早合理起点就是世界自己的年龄。
- **结果：278 个 GameTest 全绿**（`runGameTestServer` 退出码 0，此后又复跑多次一致）。上面第 4 条那个 `Result`
  记录多了一个分量，`/secret_realm` 命令与秘境符箓两个调用点只读 `changed` / `failure` / `message`，未受影响。
- **第五轮：`AuraZone.dimensions` 取不到注册表（2026-10-15，续，已修）**。迁移收尾时把它记成了"待拍板"，
  查清之后是真 bug，按用户拍板改成 **id（`ResourceKey<LevelStem>`）**：
  - **原形状**：`List<Either<Holder<LevelStem>, TagKey<LevelStem>>>`。`mxt:aura_zone` 属于**自定义数据包注册表**，
    NeoForge 把它们全部并进 `WORLDGEN_REGISTRIES` 那一批（`DataPackRegistriesHooks.DATA_PACK_REGISTRIES =
    new ArrayList<>(WORLDGEN_REGISTRIES)` ＋ `DataPackRegistryEvent.NewRegistry` 注册的表），由
    `WorldLoader` 的**第一次** `RegistryDataLoader.load` 加载；而 `minecraft:dimension`（`Registries.LEVEL_STEM`）
    在 `RegistryDataLoader.DIMENSION_REGISTRIES` 里，是那一次 future 完成之后的**第二次** load。
    同一批内的互相引用是成立的（`RegistryDataLoader.createContext` 在解码前就把这一批所有表都放进 ops，
    所以 `Holder<Biome>` / `dimension_type` 都没问题），但 `LEVEL_STEM` 那时**根本不存在**，于是
    `RegistryFixedCodec.create(LEVEL_STEM)` 报 `Can't access registry … minecraft:dimension`，
    `MiscCodecs.combineCodec`（`either(单值, TolerantListCodec)`）只能把元素一个个丢掉。
    日志里正好 **4 条**警告 ↔ 测试包正好 **4 个** `aura_zone` 各写了 1 条 `dimensions`。
  - **后果比"不限维度"更糟**：`RegistryCodecs.matches(空表, …)` 是 `anyMatch` ⇒ **false**，那 4 个只写
    `dimensions`、不写 `biomes` 的灵气区（含 `priority: 100` 的 `overworld_priority`）**匹配不到任何位置**。
    而 `verify/aura_priority` 是**自己**从内存里的 `dimensions()` 判断有没有维度区的，于是它悄悄退到生物群系那一档、
    照样绿——**维度那一档等于没测**（这次一并把这条腿改成"两档都必须存在"，否则直接报出原因）。
  - **修法**：字段改成 `List<Either<ResourceKey<LevelStem>, TagKey<LevelStem>>>`
    （`RegistryCodecs.keyOrTagList`，`ResourceKey.codec` / `TagKey.hashedCodec` **都不需要注册表访问**），
    注册表只在**查询期**问：新增 `RegistryCodecs.matchesKeys(...)`，`AuraService.matchesDimension` 用的
    仍是它手里那份 `Registry<LevelStem>`（tag 也在那里展开）。模组里早有这个形状的先例：
    `StemGeneration` / `TemplateGeneration` 的 `stem` 就是 `ResourceKey.codec(LEVEL_STEM)`。
    数据包写法**不变**（`["minecraft:overworld"]`、裸字符串、`"#tag"` 都照旧），所以对已写好的包是纯修复。
  - 改完 `runGameTestServer` 仍然 278 全绿，且那 4 条警告消失、`verify/aura_priority` 第一次真的按维度档断言。
  - **这条是数据包字段形状变更**：文档站的「灵气区」页要把 `dimensions` 从"维度 holder / 标签"改成
    "维度 id / 标签"（写法一样，描述要改）。本仓库 `docs/` 已停用，没动。
