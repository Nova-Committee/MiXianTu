# 74 —— 消耗草稿（CostDraft）与统一执行

> 用户 2026-10-05 直接给定形状（"忽略上一轮的要求，重新按下面的设计"）：新加 `CostDraftManager` 与
> `CostDraft<T extends Cost>`；管理器负责"Cost 注册表 ↔ CostDraft"的映射；草稿要实现**装入 cost / test /
> commit**；处理流程是"按需创建草稿（构造函数创建可复制快照）→ Cost 装入 → test → commit"，且**前三步可以合并**
> 成一个动作，这样"付不出"在第一时间就返回；`Cost` 自己保留 `codec` / `test` / `commit`，其余读写与逻辑全归草稿；
> **某个 Cost 类型没有注册草稿构造器时，直接调它自己的 `test` / `commit`**（用户举的例子是 KJS，因为脚本的
> 状态没法统一执行）。
>
> 本篇是这次重构的设计稿；落地形状以代码为准（`data/cost/`）。它**取代** `39_全局消耗定义设计.md` 里
> "`Cost#charge` + `CostTransaction` 的 plan/commit"那一层形状，`39` 的数据包字段形状（`Cost[]` 四种类型、
> `CostContext` 通道、`CostFailure`）不变。

## 0. 为什么改

旧形状（`research/39` / `research/71`）是：

- `Cost#charge(CostContext) -> Either<Charge, CostFailure>`：**只读求值**，把"这一项要扣什么"变成一个被动载荷
  （`Charge.Resources` / `Auras` / `Items` / `Script`）；
- `CostTransaction` 把载荷按**通道**归并成一份 `Planning`（资源按 id 合并、灵气按身份合并、物品一列、脚本一列），
  `plan` 检查、`commit` 按通道写入，中途拒付用 `List<Runnable>` 回退；
- 复合技能要"第二个子技能按第一个扣完之后的账检查"，靠传一份 **detached 副本**（`ResourceHolderAttachment.copy()`
  ＋ 一份共享 `ItemCostDraft`）来模拟。

问题有三个，都是"形状本身"的问题：

1. **付款不是对象**。一次付款的中间状态散在 `Planning` 的可变 map、`List<Charge.Items>`、`List<JsCost>` 与调用点
   自己攥着的副本里；"装进去多少、还差什么、写完没有"没有单一归属。
2. **同一件事有两套实现**。求值在 `Cost` 里（`charge`）、校验在 `CostTransaction.checkAvailability`、写入在
   `CostTransaction.stage`，三处都要各自认识"资源 / 灵气 / 物品"三个通道；`ItemCostDraft` 又是第四处。
3. **多笔付款的边界靠调用点自己维护**（`commitAll` + 共享物品草稿 + 手动回退清单），形状重、容易漏。

用户给的新形状把这三件事一次收掉：**草稿是唯一的通道实现**，一次付款就是一组草稿，`Cost` 退回成纯数据。

## 1. 形状

### 1.1 `Cost`（`data/cost/Cost.java`）

只剩三个方法：

```java
Optional<CostFailure> test(CostContext context);    // 这一项单独能不能收
Optional<CostFailure> commit(CostContext context);  // 单独收下它
MapCodec<? extends Cost> codec();                   // 数据包分派（不变）
```

`charge` 与 `Charge` 删除。三种有草稿的类型（`mxt:resource` / `mxt:aura` / `mxt:item`）把 `test` / `commit`
**各写一行转发**给 `CostPayment.test/commit(entry, context)`——它们自己的"怎么算"已经全在草稿里，转发就是
"把这一项当成一笔只有一项的付款"。

`mxt:js` 不注册草稿，因此 `JsCost.test/commit` 就是脚本回调本身（check / consume）。这就是用户说的那条退出通道：
**没有草稿的类型自己回答**，`CostPayment.load` 遇到它就调 `cost.test(...)`，提交阶段最后调
`cost.commit(...)`。

### 1.2 `CostDraft<T extends Cost>`（`data/cost/CostDraft.java`）

```java
Optional<CostFailure> load(T cost);   // 装入：把这一项并进本草稿已经攒下的东西
Optional<CostFailure> test();         // 只读：现在攒下的这些，store 付得起吗
Optional<CostFailure> commit();       // 写入；store 中途变了可以在这里拒
void reset();                         // 把 commit 真正写下的那部分放回去（别的改动不动）
default @Nullable Identifier failedResource();   // 拒付原因是 INSUFFICIENT_RESOURCE 时，是哪个资源
```

- **构造即快照**（用户要求的那句）：`ResourceCostDraft` 在构造时 `context.resourceTarget().copy()`（这份副本是
  `test()` 的判据，也是"按需创建"便宜的底气）；`ItemCostDraft` 构造时把每个格子的数量抄一份（`test` 的判据）；
  `AuraCostDraft` 构造时不碰 store。**快照只用于校验**：`reset()` 不是"把 store 放回构造时"，而是**只把
  `commit` 真正写下的那部分放回去**，中途别处发生的改动不动它——资源在写前记下被覆盖的值、灵气记下取走的
  单位与退款表、物品记下被改写的那几格原数量，都是这个意思。
- `load` 只负责**求值与通道检查**（公式算不出有限正数、这个 context 没有这条通道），不判够不够——够不够是
  `test` 的事。这样"只想要价格"的调用点（阵法维护拆分、飞行燃料按法器存量抵扣）可以只 load 不 test。
- `reset` 是给**多笔付款的边界**用的：`payAll` 里后一笔拒付时，把先写下的草稿倒着放回去。`commit` 失败的
  **那一份也要回退**——银行是按单位逐笔取的，可能已经取走了一部分。

三种内置草稿（都在 `data/cost/`，与 `Cost` 同级；`builtin/` 里仍旧只放数据定义）：

| 草稿 | 它在哪条通道上做什么 |
| --- | --- |
| `ResourceCostDraft` | 把每项的资源 id 并入它自己持有的账户表（付款持有同一个 map）；`test` 在构造快照的副本上跑唯一出口 `ResourceTransactions.tryConsume`（先全判后全写）；`commit` 对**活账户**再跑一次，写前逐个记下被覆盖的值与它们的审计，`reset` 只把这些值写回去；求值仍带那项资源自己的公式上下文 |
| `AuraCostDraft` | `VALUE`：把灵气换算成它被计量的资源，并进**账户表**（真正的检查与写入交给资源草稿）；`POOL`：并入它自己持有的灵气表，`test` 问区块附件 `canConsume`，`commit` 走 `AuraService.consume` 并记下退款表；`BANK`：逐项 `extract(simulate)` 后真取，取走的单位记在 `taken` 里；`reset` 只把这些单位插回、把退款表还回去 |
| `ItemCostDraft` | 构造时抄下每个格子的数量当 `test` 的判据；`load` 只记下条目；`commit` 按**当时**的格子数量重算一遍"每一格留多少"（所以第二项按第一项取完之后算）再写回，同时记下被改写的每一格原数量，`reset` 只把这几格写回去 |

### 1.3 两张表：各归各的草稿

一次付款要扣的数额是两张表：**资源账户**（按 `Identifier`）与**灵气**（按 `Holder<Aura>`）。**每张表都在扣它的那份
草稿里**，付款只持有同一个 map——因为付款的公开面要答得出这份价，调用点又要在付之前改它：

1. **资源表是 `ResourceCostDraft` 的**（`test`/`commit` 扣的就是这一张），付款把表建好、连着 context 一起交给它。
   付款自己必须在**任何草稿之前**就持有并给出它：一笔付款里可能**一条 `mxt:resource` 都没有**，而 `mxt:aura` 在默认
   的 `VALUE` 目标下要落进这张表（"账户里存的是资源"，所以扣它的仍旧是资源草稿那一次原子事务）；调用点也会在付
   之前改价（`ResourceConsumeEvent.Pre` 换掉整张资源表、飞行法器抵扣自己那部分燃料）。
2. **灵气表是 `AuraCostDraft` 的**，只有它读写（`POOL` 走 `AuraService.consume`、`BANK` 逐单位 `extract`，`VALUE`
   压根不进这张表）。它经 `CostDraft.auras()` 交出来，付款在建草稿时取一次留着，`CostPayment.auras()` 转发它——
   共享灵气池按比例缩放（`CultivationMethodService`）改的就是这一张。

于是工厂收 `(CostContext, Map<Identifier, Double> account)`：要这张账户表的（`mxt:aura` 的 `VALUE` 分支）就用它，
不要的（物品）只拿 context。原先那份"把两张表一起交给每份草稿"的 `CostPrice` **整个删掉**。

### 1.4 `CostDraftManager`（只注册与创建）与 `CostPayment`（真正处理）

**`CostDraftManager` 只做两件事：登记"类型 ↔ 草稿工厂"、按类型造一份草稿。** 它不认识任何具体 Cost 类型（除了
`static` 那份注册表，一行一种），也不 load / test / commit：

```java
static {                                    // 内置四种：三种有草稿，mxt:js 没有
    register(ResourceCost.class, ResourceCostDraft::new);
    register(AuraCost.class,       AuraCostDraft::new);
    register(ItemCost.class,       (context, account) -> new ItemCostDraft(context));
}

CostDraft<T> create(Class<T> type, CostContext context, Map<Identifier, Double> account);  // 没有就是 null
List<Class<? extends Cost>> types();                                                       // 已登记的类型，登记顺序
```

按**类型类**做键：注册表 `mxt:cost_type` 的条目就是这几个 `MapCodec`，草稿这边按同一个类型登记一行即可；
附属模组新增一种 Cost 就在这里补一行（不登记＝走它自己的 `test`/`commit`）。工厂收 `(CostContext, account)`——
context 是"谁在付、在哪付"，account 是那张**资源账户表**（唯一一张要交出去的；灵气表归灵气草稿自己）。

**`CostPayment` 才是一次处理**：它拿着 context、本次用到的草稿，以及它对外要答的那两张表（账户表自己建，灵气
表向灵气草稿取），把装入 / test / commit 跑完。

```java
CostPayment payment = CostPayment.of(context);      // 每笔付款一个
Optional<CostFailure> f = payment.loadAndTest(list);  // 装入 + test 合并执行：第一个付不出的地方立刻返回
payment.load(entry);                                  // 只装入（只要价格的调用点用这个）
payment.resources().clear(); payment.resources().putAll(event.amounts());   // 改价就是改付款将要扣的那张表
CostPayment.Result paid = payment.commit();           // 写；写完草稿就没了
```

**草稿调用点一个都不建**：`CostPayment` 第一次遇到某个类型的条目才向管理器要一份，**同一次处理里同类型的
所有条目都装进这同一份草稿**（所以同一个 store 的数额天然相加）；草稿的生命周期就是这一次处理——`payAll`
写完就把草稿丢掉（`CostPayment` 只留结果，重复 `commit()` 返回同一份结果，不会付第二次），管理器不缓存任何草稿。

- 草稿**按需创建**（`load` 第一次遇到某个类型才要），到 `test`/`commit` 时把**每种已登记类型**的草稿补齐——没用
  上的那份是空操作（`test`/`commit` 在"什么都没装入"时直接答成功、什么都不写）。补齐全类型是为了 `VALUE` 灵气
  换算出来的资源：它从灵气草稿进资源表，没有任何 `mxt:resource` 条目，那份资源草稿只能这样补出来。
- `load` 对没有草稿的类型调 `cost.test(context)`，成功就把它记进 `direct` 列表。
- `beyondResources()` 问"这份价里有没有资源表说不出来的东西"（灵气 / 物品 / 脚本），第三项由草稿自己的
  `chargesAmounts()` 回答（物品草稿答否）。
- 多笔（复合技能、修炼的"环境灵气 + 身体费用"）就是**多笔 `CostPayment` + 一个 `payAll` 边界**：后一笔拒付就把
  已经写下的倒序回退。**没有跨付款共享的草稿**——资源与灵气草稿的 store 与公式上下文都写在构造函数里，各付款
  各一份；`mxt:item` 的账在 `commit` 时才按**当时**的格子数量重算，所以"两个子技能各要 32 个、背包只有 40 个"
  由边界抓住（第一个已经写了、第二个拒付 → 第一个回退）。
- `CostPayment.Result` 只留 `paid` / `failure` / `failedResource` / `resources` / `auras`（旧 `failedIndex` 没有
  任何调用点，删掉；`ok()` 也不再需要——所有调用点都是在拿到 `Optional<CostFailure>` 的那一刻决定去向）。

**写入顺序**（`payAll`，一次付款就是"只有一个元素的 payAll"）：

1. 每笔付款的草稿按创建顺序 `commit`；
2. 所有**没有草稿**的条目（脚本）——它拥有自己的状态，既不能合并也不能回退，所以排在"还能回退的通道"之后。

任何一步拒付：把已经写下的草稿（**包括刚刚失败的那一份**）倒序 `reset`，返回 `CostPayment.Result.denied`。

## 2. 各调用点怎么改

| 原来 | 现在 |
| --- | --- |
| `CostTransaction.pay(costs, ctx)` | `CostPayment.pay(costs, ctx)`（契约、法器维护、灵植、灵气合成、品质升级、KubeJS） |
| `plan(...)` + `commit(plan, ...)` | `CostPayment p = CostPayment.of(ctx); p.loadAndTest(costs); p.commit()`（技能 prepare/finish、突破、锻造、画符工作站） |
| `planDeferred(...)`（只要价格） | `CostPayment p = CostPayment.of(ctx); p.loadAll(costs);` 然后读 `resources()` / `auras()`（阵法维护拆分、飞行燃料） |
| `plan(costs, ctx, resourceDraft, itemDraft)`（复合技能的自建副本） | 每个子技能**自己一笔 `CostPayment`**（各自的公式上下文与事件），最后 `payAll` 收成一条边界；不再有调用点自建的资源副本或物品草稿 |
| `AbilityService.reserveCost(..., draft, itemDraft)` | `reserveCost(..., payment, ...)`：把子技能的价并进调用点那笔"预演付款"（画符一次发动：载体价 + 所有铭刻价） |
| `CostTransaction.Payment(plan, ctx, view)` | 就是 `CostPayment` 本身（`CostPayment.payAll(List<CostPayment>)`） |
| `WheelTooltips`：逐项 `cost.charge` 取 `Charge.Resources` | 整份数组装进**同一笔付款**，读 `resources()`（同 store 的数额合并成一行，`beyondResources()` 负责"还有别的"那一行） |
| `Costs.auras(costs, ctx)`（求灵气数额） | 先要求整份数组都是 `mxt:aura`（否则 null），再整份装进**同一笔付款**读 `auras()` |

`ItemCostDraft` 的构造从 `(Container | Player)` 改成 `(CostContext)`（自己从 context 的 `itemTarget` / 玩家背包里
取 store），`AbilityService` 里那套"detached 资源副本"整段消失——因为**合并已经发生在草稿里**了。

## 3. 行为不变的地方（逐条核对过）

- **整组原子**：`pay`/`payAll` 里任何一项付不出，写下的部分全部回退；脚本最后跑。
- **同一个 store 只写一次**：资源一次性原子事务（`ResourceTransactions.tryConsume` 仍是唯一出口）、灵气池
  all-or-nothing、物品按格写一次。
- **整组之和仍然是"先校验、后付费"**：每个子技能各自的 `test` 保证它自己付得出，整组之和由 `payAll` 边界保证
  ——后一笔拒付时前面那些按逆序回退，世界动作还没跑（它们在边界成功之后才跑），所以"两个子技能各要 5 点、身上
  只有 8 点"的结果仍然是"什么都没付"（旧形状靠一份 detached 资源副本在预演时就拒，差别只是现在拒在边界上、
  并顺手给出 `failedResource`）。
- **物品的账按付款那一刻的背包算**：旧形状在预演时共用一份物品草稿、写入放最后；现在每个物品草稿在 `commit`
  时按**当时**的格子数量重算，因此第二个子技能的物品不够会在边界上拒付并回退第一个（结论一样）。
- **拒付原因**：`CostFailure` 七个值一个没改；顺序也保持（求值/通道问题在 load，够不够在 test，写在 commit）。
  差别只有一处：`pay` 在 test 阶段就能给出 `failedResource`（旧 `plan` 那一步不给），玩家反馈因此更具体。
- **脚本不可回退**：仍然只有它排在最后，且它自己的 `test` 在装入时就被问过一次（与旧 `charge` 问一次一致）。
- **数据包格式**：`Cost[]` 的四种类型、`{id, amount}` 简写、`Costs.validate` / `validateAuras` 的加载期校验、
  `mxt:cost_type` 注册表：一字未改。
- **`mxt:aura` 在 `VALUE` 下的求值上下文**：仍旧是 `context.formula()`（不换成资源自己的公式上下文），所以老包
  里读 `realm_rank` 的公式结果不变。

## 4. 明确不做 / 已知限制

- **脚本的副作用永远不可回退**（脚本自己拥有状态）。这一条旧形状也一样，只是现在写在 `payAll` 的顺序里。
- **`CostPayment.test/commit(entry, ctx)` 只服务"有草稿的类型"**：没有草稿的类型必须自己实现 `Cost.test/commit`
  （接口是抽象方法，编译期就会逼它写），拿它去转发会自己递归，所以那里有一句 `IllegalStateException` 兜住这个
  编程错误。这两个方法各自是一整次处理（建草稿、装入、test/写、丢掉），KubeJS 那边一次问一项就是这么用的。
- **一次处理跨 tick 时草稿跟着那笔付款活着**：写技能是"prepare 定价、cast 结束才付"，那笔付款（连同它的草稿）
  活到这次施放结束——它就是"一次处理"。写完（或这次施放结束被丢掉）之后不留任何草稿，管理器也不缓存。
- 探针 `/mxt_test cost` 的断言一条没改（它只用 `paid()` / `failure()` / `failedResource()`），但**本轮只编译，
  未实机跑**。
