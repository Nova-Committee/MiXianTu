# 固有注册表与数据包注册表协作规范

## 目标

注册表分为两层，通常需要配合：

- **固有注册表**：Java 在模组加载期注册。条目是代码对象、行为实现、`MapCodec`、原版扩展类型或其他不能由数据包创建的内容。
- **数据包注册表**：服务器资源重载期加载。条目是内容定义、数值、引用关系和可组合参数，可由数据包或 KubeJS 的定义构建器提供。

两层不能互相替代。固有注册表决定“系统能够做什么”；数据包注册表决定“这次存档实际启用哪些内容和参数”。

```text
Java 加载期
  固有行为 / 固有 MapCodec / 原版注册表条目
                    ↓
数据包重载期
  具名内容定义 + 直接行为 ID 引用 + type 对象
                    ↓
服务端运行时
  附件状态、事件、网络校验、数据包快照
```

## 两种联动模式

### 模式 A：固有行为，数据包直接引用 ID

固有注册表注册可直接执行的 Java 行为，例如 `mxt:grant_ability`、`mxt:remove_ability`、`mxt:teleport_to_spawn`。数据包只保存行为的资源 ID，运行时按 ID 查找后传入标准上下文执行。

```json
{
  "on_complete_behavior": "mxt:grant_ability"
}
```

该模式适用于行为的算法和参数完全固定，数据包只需选择启用哪个行为的情形。行为实现必须：

- 定义明确的输入上下文和返回结果，例如 `FormationContext -> Result`。
- 可由服务端校验，并对不存在的 ID 给出加载期错误。
- 不依赖 JSON 中未声明的任意对象或脚本函数。

若同一个行为需要每条数据包定义提供不同参数，不能只塞一个 `behavior` ID；应使用模式 B，或让数据包额外引用另一个具名定义。

固有行为注册表不得做成不带上下文的全局 `handler` 集合。每个直接引用字段必须对应一个明确的行为接口和注册表：

| 固有行为注册表 | 固定上下文 | 可由数据包引用的字段示例 |
| --- | --- | --- |
| `mxt:forging_completion_behavior` | `ForgingCompletionContext` | `on_complete_behavior`、`on_fail_behavior` |
| `mxt:formation_lifecycle_behavior` | `FormationLifecycleContext` | `on_activate_behavior`、`on_deactivate_behavior` |
| `mxt:tribulation_stage_behavior` | `TribulationStageContext` | `on_stage_start_behavior`、`on_stage_end_behavior` |
| `mxt:contract_lifecycle_behavior` | `ContractLifecycleContext` | `on_bind_behavior`、`on_break_behavior` |
| `mxt:cultivation_outcome_behavior` | `BreakthroughContext` | `on_breakthrough_success_behavior`、`on_breakthrough_fail_behavior` |
| `mxt:alchemy_outcome_behavior` | `AlchemyOutcomeContext` | `success_behavior`、`failure_behavior` |
| `mxt:realm_lifecycle_behavior` | `RealmLifecycleContext` | `enter_behavior`、`exit_behavior` |
| `mxt:artifact_lifecycle_behavior` | `ArtifactLifecycleContext` | `refine_behavior` |
| `mxt:creature_spawn_condition` | `CreatureSpawnContext` | `creature_profile.spawn_conditions[]` |
| `mxt:cultivation_condition` | `CultivationContext` | `cultivate_action.start_conditions[]`、`stop_conditions[]` |

一个行为实现只能接受所属上下文，不能被错误地填进其他领域的 `_behavior` 字段。需要跨领域复用时，提炼其共同上下文或使用模式 B 的动作对象，不通过 `Object`、反射或强制转换复用。

当前底层以 `BehaviorContext` 传递只读服务端快照；其中 `kind` 是对应领域的枚举值。注册表仍然按上表分开，因此同名 ID 不能跨领域调用。缺失 ID 或行为抛出异常会记录定义 ID 和行为 ID，并且只禁用该次附加回调，不回滚已完成的主事务。

### 模式 B：固有 `MapCodec`，数据包通过 `type` 分派

固有注册表注册 `MapCodec<? extends T>`。数据包对象使用 `type` 指明 Java 结构和算法，并提交该 Codec 定义的字段。

```json
{
  "type": "mxt:spawn_projectile",
  "projectile": "mxt_test:small_fire_orb",
  "speed": 1.25,
  "lifetime": 40
}
```

该模式适用于同一抽象接口有多种结构，或行为本身需要数据包参数的情形。典型接口为 `AbilityDefinition`、`EntityAction`、`EntityCondition`、`AbilityComponent`、`NumberProvider`。

Java 使用 `registryDispatch` 根据 `type` 找到 Codec 并构造对象。数据包不能注册新的 `type`，第三方 Java 模组可以在加载期向同一固有类型注册表注册新的 Codec。

## 选择规则

| 需求 | 使用方式 | 示例 |
| --- | --- | --- |
| 完全固定、无每条定义参数的代码行为 | 模式 A，直接行为 ID | 阵法失效时执行固定的返还行为。 |
| 有不同字段、不同参数或不同嵌套结构的行为 | 模式 B，`type` + Codec 字段 | 投射物、治疗、范围伤害、条件组合。 |
| 可复用且有名称的静态游戏内容 | 数据包注册表条目 ID | `mxt_test:fire_root`、`mxt_test:foundation_realm`、`mxt_test:small_fire_orb`。 |
| 运行中持续变化的数据 | Attachment / Data Component，不进入任一静态注册表 | 冷却、当前灵力、正在运行的阵法、锻打历史。 |
| 原版必须识别的扩展类型 | 原版固有注册表 | Loot Function Type、Recipe Serializer、Data Component Type、Payload Type。 |

## 两层组合示例

### 具名能力定义 + `type` 分派

`ability` 是数据包注册表，`mxt_test:ember_orb` 是具名内容；其内部 `type` 由固有 `ability_type` 决定。

```json
// data/mxt_test/mxt/ability/ember_orb.json
{
  "type": "mxt:active",
  "costs": [
    {
      "id": "mxt_test:spirit_power",
      "amount": "12 + caster_level"
    }
  ],
  "entity_action": {
    "type": "mxt:spawn_projectile",
    "projectile": "mxt_test:ember_orb_projectile",
    "speed": 1.1
  }
}
```

这里 `mxt_test:ember_orb` 可被功法、体质或法宝引用；`mxt:active` 和 `mxt:spawn_projectile` 则是固有 Codec 类型。前者可随数据包增删，后者只能由 Java 加载期注册。

### 具名蓝图 + 固有行为 ID

某个锻造蓝图可选择固定的完成行为。行为 ID 只表示代码路径，具体输入和结果仍由蓝图字段定义。

```json
// data/mxt_test/mxt/forging_blueprint/training_blade.json
{
  "result": "mxt_test:training_blade",
  "on_complete_behavior": "mxt:apply_forging_quality",
  "on_fail_behavior": "mxt:return_scrap"
}
```

`mxt:apply_forging_quality` 和 `mxt:return_scrap` 必须在固有行为注册表中存在。若需要“不同品质算法”，应改为 `quality_policy: { "type": "...", ... }`，让其进入模式 B，而不是增加不可见的 ID 参数约定。

### 嵌套使用

一个 `type` 对象也可以引用固有行为 ID，但两者职责不变：Codec 解析结构，行为 ID 选择固定分支。

```json
{
  "type": "mxt:triggered",
  "trigger": "mxt:on_breakthrough",
  "on_success_behavior": "mxt:notify_holder"
}
```

`mxt:triggered` 是 `ability_type` 的 Codec；`mxt:on_breakthrough` 可以是触发器类型或固定触发器 ID，必须在字段文档中明确其所属注册表；`mxt:notify_holder` 是固定行为 ID。

## 注册与加载生命周期

1. **Java 初始化**：用 `NewRegistryEvent` 创建自定义固有类型/行为注册表；用 `DeferredRegister` 注册 Java 行为、`MapCodec` 以及原版 `Registries` 条目。
2. **数据包加载**：固有注册表已冻结后，加载 `data/<namespace>/mxt/<registry>/...json`，解析直接 ID 引用和 `type` 对象。
3. **完整校验**：检查引用存在、Codec 能解码、数值边界、跨定义循环、权限和可达性；任一严重错误阻止发布新快照。
4. **原子发布**：仅在全部注册表成功加载后替换服务端只读快照，并同步需要发往客户端的数据定义版本。
5. **运行时**：附件只保存数据包定义 ID 与自身状态；执行时从当前或会话快照解析定义，所有客户端请求由服务端复核。
6. **热重载**：仅重建数据包快照。固有注册表、Codec 集合、网络包与 Attachment 编码不允许在重载时变化。

## 命名与字段约定

- 所有跨层引用使用完整资源 ID，例如 `mxt:apply_forging_quality`，不使用字符串类名。
- `type` 字段只能指向 `Registry<MapCodec<? extends T>>` 中的条目；普通数据包内容 ID 不应误写进 `type`。
- 直接行为字段以 `_behavior` 结尾，例如 `on_complete_behavior`；Codec 分派字段固定为 `type`；数据包定义引用使用业务字段名，例如 `ability`、`realm`、`element`。
- 直接行为 ID 和 Codec ID 必须有稳定的命名空间与文档，不允许 KubeJS 在服务器运行中临时注册。
- 数据包定义缺失或固有 ID 缺失时，加载器必须指出“字段路径、期望注册表、缺失 ID”，不能只报泛化解析错误。

## 版本兼容与测试

- 固有行为或 Codec 被删除前，应保留兼容别名或数据迁移器；否则旧存档/旧数据包会失去解析能力。
- 数据包定义被删除时，运行时保存未知 ID 原文并禁用对应能力/物品功能，不丢弃附件数据。
- 每个固有行为测试正常结果、无效上下文和异常回滚；每个 Codec 测试最小 JSON、完整 JSON、未知字段和非法引用。
- 每份数据包注册表至少测试：有效定义、缺失固有行为 ID、未知 `type`、循环引用、热重载替换和客户端同步。

## 禁止事项

- 不用数据包 ID 模拟 Java 类名或反射调用。
- 不让 KubeJS 注册运行时 Codec、直接行为或修改固有注册表。
- 不把冷却、当前灵力、实体 UUID 等动态状态塞进数据包定义。
- 不用一个万能 `handler` 字符串承载类型、行为、脚本函数和数据包 ID；每个字段必须明确属于哪一种注册表。
