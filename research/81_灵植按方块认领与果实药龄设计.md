## 1. 为什么换身份

`79` / `80` 里，灵植是"给一件**已有物品**挂元数据"，而"这一格长的是哪种草"由方块自己实现 `api/SpiritHerbPlant` 回答。这条分工有两个绕不开的毛病：

1. **接口是白拿的负担**：一个只想让自家方块算灵植的内容包，必须实现一个 Java 接口、编译一个模组。数据包做不到"我这个方块是灵植"。
2. **两项事实分居两处**：定义按物品认领、方块自己说自己是哪株草，两边是**同名但独立**的两份信息，对不上时没有编译期或加载期可以裁决。

改成按方块认领之后，**"这一格长的是哪种草"只有一个来源**：`blocks` 命中就是。接口 `api/SpiritHerbPlant` 整个删掉，`data/alchemy` 里的定义不再 `implements ItemMatcher`。

水果的身份是另一件事，不能靠方块回答（一块方块可以结好几种东西），所以它单独有一个 `drops`。**两条认领各有各的用处**，也不能互相推导：`blocks` 回答"这格是什么草"，`drops` 回答"这堆是谁的果实"。

## 2. 定义形状

```json
{
  "blocks": ["example:spirit_soil", "#example:herb_blocks"],
  "growth": {
    "mature_age": 100,
    "max_age": 200,
    "growth_rate": 25,
    "condition": { "type": "mxt:always" },
    "costs": [{ "type": "mxt:aura", "aura": "example:spirit_power", "amount": 1 }],
    "drops": "minecraft:red_mushroom",
    "wild_age": { "type": "mxt:uniform", "min": 1, "max": 3 }
  }
}
```

改动清单：

| 旧 | 新 |
|---|---|
| `items: ItemMatcher` | `blocks: List<Either<Holder<Block>, TagKey<Block>>>`，**必填非空** |
| `growth.seeds: ItemMatcher`（必填） | **删除**（没有播种这回事） |
| `growth.harvest: ItemStackTemplate`（必填） | `growth.drops: List<Either<Holder<Item>, TagKey<Item>>>`，**必填非空** |
| `SpiritHerb implements ItemMatcher` | 不再实现；`DEFAULT_PRIORITY` 由自己声明 |
| `api/SpiritHerbPlant` | **整个删除** |
| `util/matcher/BlockMatcher.java` | **整个删除**（用户口径：直接写 `List<Either>`） |

`drops` 挂在 `growth` 里面而不是定义顶层：**没有 `growth` 就没有药龄**，而没有药龄就没有什么可写给果实的，两者的生命周期是一致的。

### 物品侧的两条匹配路线（2026-10-10 补）

按方块认领之后，**物品**侧只剩一条路可走：`growth.drops`。但炼丹炉夹具那类**只写药力、不写 `growth`** 的定义因此变成了死定义——药力字段还在，却没有任何物品能触发它们（用户实机发现 `/picker mxt:spirit_herb` 里仙人掌之类的行没有药的 tooltip）。所以 `SpiritHerbService.claims` 定成两条：

```
有 growth  → 只认 growth.drops 命中（果实路线）
没有 growth → 只认它认领的方块对应的物品（方块物品路线）
```

**两条互斥**：写了 `growth` 的草不会同时按方块匹配，否则一块方块掉出的果实与那块方块本身都会命中同一条定义、而两条不同的定义也可能同时命中同一堆。`Provider` 与无 `Provider` 两个重载共用同一个私有判据，后者给 `HerbTagEntry` 用（物品匹配器在客户端也会被求值，那时只能读静态方块注册表）。

`/picker mxt:spirit_herb` 也照这条走：**一行是果实物品**（`growth.drops` 展开，与 tooltip / 丹炉实际去问的那一堆一致），没写 `growth` 的退回方块对应的物品。原来那版统一显示 `block.asItem()`，于是 `honeycomb_block`（方块）与 `honeycomb`（果实）分成两行、看的那一行没有 tooltip。

`growth.validate` 仍然拒绝 `max_age < mature_age` 与空 `drops`；新增的一条是 `blocks` 不得为空——空表会让这株草谁也认不着，是写错了而不是"这株草不认领任何方块"。

### 认领必须唯一

`SpiritHerbService.validateExclusiveClaims` 在加载期检查：**同优先级的两条定义不得共享同一个 `blocks` 条目或同一个 `drops` 条目**，否则抛 `IllegalStateException`。

这是一条新加的硬约束，理由是**两条认领方向都不接受"按注册表顺序裁决"**：

- `blocks` 决定"这一格长的是哪种草"，两株草抢一块方块时，谁赢直接决定那块地上是哪种药龄曲线；
- `drops` 决定"这堆是哪株草的产物"，两株草共用一个果实时，**同一个物品堆被两条定义同时认领**，药龄的读法就不再唯一（`default_age` 该用谁的？`quality_by_age` 该查谁的？）。

`priority` 仍然可以从"同一片方块被一株草的多条定义覆盖"这类**有意的**覆盖里表达先后；但**同分**时无解，所以拒收。（`62` 之前用 `validateBoundHarvests` 检查"`harvest` 必须能解析回这条灵植"，那条检查随 `harvest` 一起消失。）

## 3. 区块附件

```java
private final Map<Long, Plant> plants;   // packed BlockPos -> {age, clock}

public record Plant(double age, long clock) { }
```

- **没有行** = 这株草从没被框架看过。
- **`clock >= 0`** = 已有档案的植株：`clock` 是**结算到的 gameTime**，`age` 是**它当时的药龄**。
- **`clock < 0`** = 自然生成、还没被读过：**掷出的岁数停在 `age` 里**，`clock` 只是一个"未定档"的标记（固定 `-1`）。

> **别把 roll 编进 `clock` 的数值里**（第一版是 `-roll-1`）。`wild_age` 是 `NumberProvider`，可以是 `2.5`；用 `long` 编码会**截断小数**，而且 `resolve` 第一次读返回的是原始 roll、第二次读返回的是截断后的值 —— 于是 Jade 先显示 `2.9`、再显示 `2.0`，又是一次"读取不幂等"。**符号只用来标记，值一律放 `age`**（`double`）才能无损往返。这条是 2026-10-10 复查时抓出来的。

### 为什么必须同时存 age 和 clock（2026-10-10 修 bug）

第一版**只存一个 clock**，药龄靠"把 `gameTime - clock` 那段时间逐期重放"现算。这是错的，实测表现为**野生虞美人的 Jade 药龄在 0 和 2 之间反复跳**，原因有三层：

1. **重放有上限**（`catchUpPeriods` = 1 年 = 1200 期）。世界跑了超过 1 年后，重放窗口被夹住，于是"重放出来的药龄"与"clock 在哪"强相关——clock 一被推进，重放窗口就缩回去，药龄跟着塌回 0；
2. **`settle` 会把野生行的 roll 直接丢掉**（当时那版把它改写成 `gameTime`），于是这株草从"掷出来的岁数"变回"刚种下"，下一次读取就是 0；
3. **`resolve` 的正数分支用了 `fold` 之前的旧 `clock` 变量**去算药龄，而 `fold` 只改了附件、没回传，所以同一次读取里"存进去的 clock"和"用来算 age 的 clock"不是同一个。

三条叠起来就是那个抖动：settle 把 clock 推到 now → 下次读算出 0 → 再过 20 tick 重放出一期 → 2 → settle 又推一次 → 0……

**修法是让 age 成为被持久化的状态**：`age` 是这株草真正长到的岁数，`clock` 只用来回答"还欠多少时间"。于是

- 读取是**幂等**的：连读 8 次答案完全一样（Jade 每帧都在读，这条是硬要求）；
- 推进是**单调**的：时间往前走，药龄只增不减；
- **同一段时间只结一次**：`resolve` / `settle` 把 clock 推进的正好是它结算过的期数，所以同一 tick 里的第二次调用看到 `periods == 0`，直接返回存下来的 age，不会重复扣灵气。

这也让"补算上限"变成一件安全的事：上限只影响**一次结算最多补多少期**，不再影响"这株草现在几岁"，因为岁数是存着的、不是推出来的。补算期间用 `grow`（不求值环境、不扣灵气），只有**最后一期**走 `period`（真条件 + 真扣费），与在线结算同一条公式。

`HerbChunkAttachment` 额外提供 `plants()`（返回一份副本给结算遍历用）、`find` / `set` / `remove` / `isEmpty`；它是**服务端专用**附件，不加 `.sync`。

> **存档兼容**：`age` 是新增字段，老存档的行里没有它 —— 按 `Codec.DOUBLE.fieldOf("age")` 解码会**整行失败**，被 `CollectionCodecs` 容错丢掉（日志 `Ignoring invalid list element`），于是那些植株退化成"野生、重新按 `wild_age` 掷一次"。这是可接受的（本模组不写旧存档兼容），但要知道老世界里已存在的灵植会重新掷岁数。

## 4. 生命周期

### 4.1 放下就是种植

`HerbChunkTicker.onBlockPlace` 听 `BlockEvent.EntityPlaceEvent`，调 `SpiritHerbGrowthService.placed(level, pos, state)`：`blocks` 认领这个方块、且这株草有 `growth` 时，写入 `level.getGameTime()` 并 `markUnsaved()`。

**不读放置者、不读手上的物品、不消耗任何东西**——放置者是谁与这株草几岁无关。同一格重复放置不会叠出第二行（一行就是一个坐标）。

### 4.2 每 20 tick 结算

`HerbChunkTicker.onLevelTick` 在 `getGameTime() % 20 == 0` 时对每个已加载区块调 `settle`。每一行：

1. 方块不再被任何草认领 → **丢掉这一行**（草没了，时钟没有描述对象）；
2. 方块被认领但这株草**没有 `growth`** → **原地暂停**（不删行），这样数据包临时改坏定义不会静默丢掉地图上所有植株；
3. `clock < 0`（自然生成、还没读过）→ 把它改成 `gameTime`，**从这一刻开始按普通植株走**（`resolve` 里读过的那种会带着掷出年龄转正，见 §4.3）；
4. 否则 `fold`：`periods = min((gameTime - clock) / 20, catchUpPeriods())`，逐期推进、逐期付费，最后把 `clock` **推高恰好 `periods * 20`**（`catchUpPeriods = max(20, ticks_per_year) / 20`，默认 `24000/20 = 1200` 期 ≈ 1 年）。

第 4 条的关键是：**补算多少期，就把时钟推进多少期**（`clock += periods * PERIOD`），所以同一段时间不会被算第二次——同一 tick 里的第二次读取看到 `periods == 0`，直接返回存下来的 `age`。

### 4.3 自然生成：第一次读就定起点

`resolve` 是**唯一**读取一处（Jade 与破坏都经它）：

```
没有行   → roll(wild_age) → 写成 {age: rolled, clock: -1} → 返回 rolled
负数行   → 把 age 当起点（min(max_age) 封顶），写成 {age, clock: now} → 返回它
已有行   → 结算欠着的期数，把 age 与 clock 一起推进 → 返回 age
```

`wild_age` 为 `NumberProvider`，在**植株位置**求值（所以能读场地灵气）；`<= 0` 或非有限值读作 `0`；结果 `min(max_age)` 封顶，再按"世界已开多久"（同样封顶 1 年）补算一次——**所以老存档里自然生成的药草一开始就很老**。

**"看一眼就会写档案"是这条设计的已知代价**（`80` 拍板 ② 的代价照旧）：Jade 一看，或任何一次 `ageAt`，就把这株草从"野生的"变成"有档案的"，此后照扣 `costs` 灵气。没被读过的区块一个字节都不会写。

### 4.4 果实：`BlockDropsEvent`

`HerbChunkTicker.onBlockDrops` 听 `BlockDropsEvent`，调 `harvested(level, pos, state, drops)`：

1. `resolve` 拿到当下药龄（`years = floor(max(0, age))`）；
2. 遍历 `event.getDrops()`，**只对匹配 `growth.drops` 的堆**写 `mxt:herb_age` 组件，并按 `qualityFor(years)` 写 `mxt:quality`；
3. `forget(pos)` 丢掉这一行——草没了。

**不匹配的掉落物一个字节都不动**，所以一块方块顺手掉出来的别的东西不会被误标（这是 `drops` 存在的全部意义）。框架**不生成、不替换、不增删任何掉落**，只改匹配到的那些堆的组件——这也正是 `BlockDropsEvent#getDrops` 的 `@apiNote` 推荐之外的用法：**改组件**不改变掉落集合，所以不必去写 `LootModifier`。

**没有任何右键交互**（`79` 的空手右键采摘 / 潜行拉苗都删了）：成熟与否不改变掉落内容，那是方块自己战利品表的事。

## 5. 已知边界

- **爆炸绕开 `BlockDropsEvent`**：`ServerExplosion.interactWithBlocks` 走 `BlockBehaviour.onExplosionHit` → `state.getDrops(params)` + `Block.popResource`，**不经过 `Block.dropResources`**（`CommonHooks.handleBlockDrops` 只被后者调用）。所以被炸掉的灵植**不会**被写药龄。`79` 的 B9「爆炸、活塞、`/setblock` 都一样有掉落」这条结论对爆炸是错的。要不要在爆炸那条路上补一次，留给以后按需决定。
- **创造模式破坏不出事件**：`ServerPlayerGameMode.destroyBlock` 在 `player.preventsBlockDrops()` 时提前返回，`BlockDropsEvent` 根本不发。
- **`drops` 只认组件，不认产出**：一块方块若把果实写进自己的战利品表，它就是普通掉落 + 一个被写上的药龄组件；框架不会因为它匹配就把别的产物改成它。

测试包：`HerbTestBlocks` 改成三个普通方块（无 `STAGE`、无交互）、三个 blockstate 去掉 `stage` 变体、30 份 `mxt/spirit_herb` JSON 全量改写（`items`→`blocks`、`harvest`→`growth.drops`、删 `seeds`）、新增 `tags/block/spirit_herbs.json`（原来那份是物品标签）、`HerbProbes` 按新形状重写（**七条腿**：认领、放下写时钟、野生 roll、结算推进、药龄稳定性、果实写药龄、未认领方块无反应；共 35 条断言）。

`stabilityLeg` 是抖动 bug 的回归腿，盯两件事：**连读 8 次答案完全一样**（Jade 每帧都读，这条最容易崩）、**时间往前走时药龄只增不减**。`wildRollLeg` 另外钉住**掷出的岁数无损往返**（连读两次都得同一个值），夹具 `herb/aging` 的 `wild_age` 因此写成小数 `5.25..15.75`——整数区间跑不出截断那条 bug。

修 bug 时另用一段独立的算术模拟对着 `growth_rate = 2 / max_age = 20` 跑过：修前是 `0,2,2,2…` 并会在重新掷 roll 时塌回 0，修后是 `0,0,0,0,0`（时间不走就纹丝不动）→ `2,4,6,8,10,12`（时间每走 20 tick 涨一期）。③ 也用一段模拟验证过：把 roll 编进 `clock` 时 `2.5 → 2.0`、`2.999 → 2.0`（首次读返回原始值、第二次返回截断值），改存 `age` 之后 `0.0 / 0.4 / 0.9 / 2.5 / 2.999 / 7.5` 全部无损。

`findBlockLeg` 里新加的三条断言把「只写药力、没写 `growth`」这条路线钉住：仙人掌（`alchemy/rank`，无 `growth`）能从物品认出来、`honeycomb_block`（有 `growth` 的草认领的方块）**不**被认出来、`honeycomb`（果实）被认出来。这三条正好覆盖「两条路线互斥」这个约束。
