# 通用资源与资源条注册表设计

## 目标

“蓝条”不应硬编码为灵力 HUD，而应实现为可复用的通用资源显示系统。灵力、神魂、体力、护盾、飞剑御使能量等均可定义为独立 `resource`；是否显示、显示在哪里、采用何种样式，则由独立 `resource_bar` 定义。

这样可避免把“数值存在”与“必须显示一条蓝条”绑定：有些资源只参与条件或成本，完全可以没有 HUD；同一个资源也可在不同上下文采用不同显示条。默认内容包可将灵力配置为玩家生命条下方的蓝色条。

锻造界面的 `forging_value` 数值条是一次锻造会话的专用 UI，不属于实体 `resource`，也不进入本设计的 HUD 注册表。

```text
resource（数据包：资源规则）
        ↓
ResourceHolderData（服务端：实体当前数值）
        ↓
resource_bar（数据包：显示条定义）
        ↓
resource_bar_renderer_type（固有：客户端 MapCodec 渲染器）
```

## 注册表边界

| 层级 | 注册表/对象 | 职责 | 能否数据包定义 |
| --- | --- | --- | --- |
| 数据包 | `resource` | 资源上下限、回复、持有条件、默认显示条引用 | 可以 |
| 运行时附件 | `ResourceHolderData` | 实体按资源 ID 的当前值、审计和同步版本 | 不可以 |
| 数据包 | `resource_bar` | 绑定资源、可见性、布局、排序、渲染器 `type` 和参数 | 可以 |
| Java 固有 | `mxt:resource_value_provider_type` | 资源当前值、最大值和回复规则使用的 `MapCodec` | 不可以 |
| Java 固有（仅客户端消费） | `mxt:resource_bar_renderer_type` | HUD 绘制方式的 `MapCodec` | 不可以 |

`resource` 与 `resource_bar` 使用标准路径：

```text
data/<namespace>/mxt/resource/<path>.json
data/<namespace>/mxt/resource_bar/<path>.json
```

所有运行时数值由服务器权威保存和计算。客户端只能根据同步快照绘制条，不能提交“当前资源值”或绕过消耗校验。

## `resource` 数据包定义

资源定义只说明“资源是什么、如何计算”，不携带客户端纹理或坐标。建议字段如下：

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `schema_version` | 是 | 定义版本。 |
| `display` | 否 | 本地化键、图标等非 HUD 的通用展示信息。 |
| `min` | 否 | 最低值，默认 `0`。 |
| `default_value` | 是 | 首次获得资源时的当前值，必须在最小值和最大值之间。 |
| `max` | 是 | `mxt:resource_value_provider_type` 对象，计算动态上限。 |
| `regen` | 否 | 同一固有类型对象，计算每 tick 或离散周期的回复/损耗。 |
| `holder_condition` | 否 | 哪些实体可持有该资源；不满足时不创建或停用对应条目。 |
| `default_bar` | 否 | 默认 `resource_bar` ID；显示层可覆盖它。 |
| `allow_negative` | 否 | 默认为 `false`；只有明确的债务/反噬玩法才允许负数。 |

资源 ID 必须完整命名，例如 `mxt:spirit_power`。`max`、`regen` 等 `type` 对象只能使用 Java 已注册的 Codec；数据包不能加入新的数值算法。

示例，灵力资源：

```json
{
  "schema_version": 1,
  "display": { "translation_key": "resource.mxt.spirit_power" },
  "min": 0,
  "default_value": 100,
  "max": {
    "type": "mxt:attribute",
    "attribute": "mxt:spirit_power_max",
    "fallback": 100
  },
  "regen": {
    "type": "mxt:constant",
    "per_tick": 0.05
  },
  "default_bar": "mxt:spirit_power"
}
```

## `resource_bar` 数据包定义

一个显示条绑定一个 `resource`。同一 `resource` 可以有多条定义，例如常规 HUD、Boss 战 HUD 和观察目标信息，但同一 HUD 上下文内只选择一条最终定义，避免重复显示。

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `schema_version` | 是 | 定义版本。 |
| `resource` | 是 | 要显示的 `resource` ID。 |
| `context` | 否 | `self_hud`、`target_overlay`、`boss_overlay` 等受限枚举；默认 `self_hud`。 |
| `anchor` | 是 | 受限布局锚点，例如 `below_health`、`above_hotbar`、`top_left_stack`、`top_right_stack`。 |
| `order` | 否 | 同一锚点的稳定排序，数值小者在前。 |
| `visibility` | 否 | 固有可见性 `type` 对象，例如资源未满、最近变更、持有特定能力或始终显示。 |
| `renderer` | 是 | `mxt:resource_bar_renderer_type` 对象，使用 `type` 选择绘制方式和参数。 |
| `replace_default` | 否 | 为 `true` 时覆盖该资源的 `default_bar`；用于内容包明确换肤。 |

灵力蓝条示例：

```json
{
  "schema_version": 1,
  "resource": "mxt:spirit_power",
  "context": "self_hud",
  "anchor": "below_health",
  "order": 20,
  "visibility": {
    "type": "mxt:non_full_or_recently_changed",
    "hold_ticks": 60
  },
  "renderer": {
    "type": "mxt:textured_bar",
    "background_sprite": "mxt:hud/spirit_power_empty",
    "fill_sprite": "mxt:hud/spirit_power_fill",
    "width": 81,
    "height": 5,
    "fill_color": "#3f8fff",
    "show_value": false
  }
}
```

其中蓝色是该定义的 `fill_color`，不是注册表语义。内容包可以为神魂配置紫色环形条，或把体力配置为分段条，而无需改变资源系统。

## 固有渲染器与可见性类型

`mxt:resource_bar_renderer_type` 是客户端 Java 固有注册表。数据包以 `renderer.type` 分派，参数由对应 `MapCodec` 校验。首批内置类型：

| 类型 | 用途 | 关键参数 |
| --- | --- | --- |
| `mxt:textured_bar` | 普通横向填充条，灵力蓝条的默认实现 | 背景/填充 sprite、宽高、颜色、数值开关、填充方向。 |
| `mxt:segmented_bar` | 格数明确的体力、充能或剑气条 | 段数、间距、空/满 sprite 或颜色。 |
| `mxt:radial_bar` | 环形神魂、护盾或目标标记 | 半径、角度范围、厚度、颜色、背景 sprite。 |
| `mxt:text_only` | 只显示数值或本地化文本 | 格式、颜色、是否显示最大值。 |
| `mxt:missing` | 客户端缺少所需类型时的安全降级 | 仅记录一次诊断并不绘制。 |

可见性同样采用固有 `MapCodec`，建议在 `mxt:resource_bar_visibility_type` 注册表中提供：`always`、`non_full`、`recently_changed`、`non_full_or_recently_changed`、`resource_range`、`has_ability`、`and`、`or`、`not`。

新的复杂绘制、动画或 shader 必须由客户端 Java 模组注册新的 `renderer.type`，且连接该服务器的客户端都必须具备实现。数据包和 KubeJS 只能选择已有类型并填参数，不能注入任意客户端脚本、着色器源码或绘制回调。

## 统一资源成本格式

所有需要消耗实体资源的数据包字段统一命名为 `costs`，类型固定为数组，数组元素只包含 `id` 与 `amount`：

```json
{
  "costs": [
    { "id": "mxt:spirit_power", "amount": 20 },
    { "id": "mxt:soul_power", "amount": 5 }
  ]
}
```

规则：

1. `id` 必须引用存在的 `resource`；`amount` 是 `NumberProvider`，数字字面量为常量简写，字符串为 `mxt:expression`（exp4j）简写，也可使用带 `type` 的对象形式按能力上下文计算。数组为空或字段缺失均表示无资源成本。
2. 同一 `id` 在单个数组中只能出现一次；加载器拒绝重复项，不在运行时隐式合并。
3. 任何动作都先计算全部 `amount`，并验证每项结果为有限正数，再完整预检并一次性扣除；任一资源不足、公式失败、条件失败或事件取消时，所有资源保持原值。
4. 使用 `costs` 的位置包括：主动/引导能力、修炼与突破动作、锻打方式、阵法激活与维持、飞剑御使、法宝充能/技能、契约及后续内容定义。物品材料消耗仍使用其各自的物品输入字段，不混入本数组。
5. 资源恢复使用独立的 `gains` 或动作字段，不允许以负 `amount` 表示恢复。

事件和 KubeJS API 接收并返回完整 `costs` 数组。事件监听者可取消或替换整个数组；替换后服务端必须重新执行引用、数值、持有条件和余额校验。

## 同步、热重载与降级

- 服务器将玩家可见的资源当前值、最大值、`resource_bar` 定义版本和必要显示定义同步给客户端；`ResourceHolderData` 的审计来源不必同步。
- 客户端以 `resource` ID 聚合显示值，并按 `anchor`、`order` 稳定布局；数据包不能提交任意像素坐标，避免 HUD 互相遮挡和分辨率失配。
- 资源或资源条定义热重载后，客户端重新解析静态定义；已有资源当前值保留。被删除的资源 ID 保留未知原文并禁用相关成本/显示，不能静默丢弃存档数据。
- `renderer.type` 缺失、参数非法或资源不可见时，使用 `mxt:missing` 降级并在日志中记录定义 ID、字段路径和缺失类型；不得导致整个 HUD 或客户端崩溃。
- `resource_bar` 只决定显示，绝不能决定资源最大值、回复、消耗、能力可用性或服务端规则。
