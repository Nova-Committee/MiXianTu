# 53 绑定表与物品组件的重划设计

> **状态：已落地**（2026-09-26 实现；设计当天两删：先去掉 `mxt:item_conditions` / `mxt:weapon_attributes` / `mxt:weapon_actions`，再去掉 `mxt:item_actions`，原子定为 **6 个**。落地记录见 §11）
> **基准**：工作树 = `HEAD 2ecbccd` 之后未提交的两轮改动（绑定表职责审计 + `attributes` 累加修复）之后的状态；表与字段的现状以 `docs/数据包格式.md`、`src/main/java/com/iafenvoy/mxt/data/item/`、`data/forging/`、`registry/MxtDataComponents.java` 为准。
> **一句话**：六张绑定表一律 `implements ItemMatcher`（定义**自动认领**物品），并把每张表的载荷拆成可复用的**原子组件**——物品上只出现原子，不再出现"绑定"这个对象。

## 0. 本稿的依据（用户口径）

2026-09-26 的三句原话是本稿唯一的设计来源：

1. **"让 Binding 都实现 ItemMatcher 自动附加在物品上，同时也支持组件的。"** —— 定义端要走物品匹配（自动），组件端要保留。
2. **"不要给物品直接上 binding，可以直接揉碎了附加上，比如 ItemBinding 可以变成 QualityChain 和 Element 两个组件。"** —— 组件里**不放** `Holder<XxxBinding>` 这种间接层；放的是拆开的原子。
3. （就 `technique_binding` 提问的答复）**组件优先，定义作默认**。
4. **"组件里面，`mxt:item_conditions`、`mxt:weapon_attributes`、`mxt:weapon_actions` 是没必要的，去掉。"**
5. **"`mxt:item_actions` 也去掉，然后开始实现。"** —— 原子定稿为**六个**（§2.2）；条件、物品行为、武器属性、武器动作都只由定义给（理由见 §2.2 的第二张表）。

由此划定的边界：**"组件指向定义"这条老路整体退场**（`mxt:tool_binding` / `mxt:blueprint_binding` 两个 Holder 组件删除），换成"组件携带原子"。

## 1. 现状（改前的证据）

### 1.1 六张表其实是三种形状

| 表 | 取定义 | 怎么附加到物品 | 载荷 | 谁读 |
| --- | --- | --- | --- | --- |
| `item_binding` | `ItemMatcher`（`items` + `priority`） | 定义自动认领 | actions / quality_chain / conditions / element | `ItemBindingService`（唯一出口） |
| `weapon_binding` | 同上 | 定义自动认领 | attributes / use_action / attack_action / tick_action / quality_chain / conditions / element | 同上 |
| `pill_binding` | 同上 | 定义自动认领 | on_consume / 丹毒四件套 / quality_chain / conditions | 同上 |
| `technique_binding` | **按功法 id**（无 `entries`/`priority`） | 堆上 `mxt:technique` 组件 | carrier_item / quality_chain / conditions / learn_time / hold_animation / hold_sound | `ItemBindingService.technique`、`TechniqueHold` |
| `tool_binding` | **按 Holder 组件** | 组件 `mxt:tool_binding = Holder<定义>` | methods | `ForgingWorkstationService`、`ForgingSurface`、tooltip |
| `blueprint_binding` | **按 Holder 组件** | 组件 `mxt:blueprint_binding = Holder<定义>` | blueprints | 同上 |

`item_binding` / `weapon_binding` / `pill_binding` 的 `items` 可以省略吗？不行——它们是必填（`ENTRIES_CODEC.fieldOf("items")`）。`tool_binding` / `blueprint_binding` / `technique_binding` 则**没有 `items` 这个概念**，一件孤品工具也必须先写一份注册表定义才能用。

### 1.2 三处已有先例（本稿沿用它们的口径，不另立一套）

- **`mxt:item_abilities`**：法器 `abilities`（定义）+ 组件里的能力 id，**取并集**（`ArtifactService.abilities`）。这是"定义给一批、组件给这一堆"的第一处实现，本稿的内容列表原子照抄这条口径。
- **`mxt:item_quality`**：堆上的品质档位**覆盖**定义给的默认档（`ItemQualityService.intrinsic` 排在解析顺序最前）。单值原子照抄这条。
- **`mxt:technique`**：功法手册的身份在**堆**上，不在物品 id 上（`34_功法载体物品组件设计.md`）。technique 那一问的答复正是这条的延伸。

### 1.3 现在的洞

1. **形状不一致**：三张表能自动认领、三张表只能靠组件指认，作者要记两套写法。
2. **单件物品也要写定义**：一把内容包自带的锤子，即使只有它自己用，也得先占一个 `tool_binding` 条目。
3. **逐件微调没有出口**：同一份图纸物品想多带一张图纸，只能新增一个定义（或改定义、影响所有同类物品）。
4. **物品上多一层间接**：`Holder` 组件要解析注册表才有意义，tooltip、槽位规则、条件都要先"翻译"一次。

## 2. 结论（新形状）

### 2.1 两张网，同一批原子

```
                   ┌──────────── 定义（批量投放）────────────┐
   数据包 mxt/<表>/xxx.json ： items + priority + 载荷字段
                   └───────────────────┬───────────────────┘
                                       │ 命中即附加
   物品堆 ─────────────────────────────┴───────────────────
                   ┌──────────── 原子组件（逐件投放）────────┐
   {"mxt:quality_chain": "...", "mxt:element": [...], ...}
                   └───────────────────────────────────────┘
```

**定义是给一族物品的投放，组件是给这一堆物品的投放；两者是同一批原子的两种写法，可以叠加。** 物品上永远不出现"绑定对象"。

### 2.2 原子清单（本稿的核心）

| # | 原子 | 组件 | 载荷 | 由哪些定义字段拆出 | 合成规则 |
| --- | --- | --- | --- | --- | --- |
| 1 | 品质链 | `mxt:quality_chain` | `Holder<QualityChain>` | item / weapon / pill / technique 的 `quality_chain` | **组件优先**（单值） |
| 2 | 元素 | `mxt:element` | `List<HolderOrTag<Element>>` | item / weapon 的 `element` | **并集**（组件 ∪ 定义 ∪ 法器定义的 `element`） |
| 3 | 丹药 | `mxt:pill` | `{on_consume?, toxicity_gain?, toxicity_threshold?, on_overdose?, toxicity_after_overdose?}` | `pill_binding` 的五个字段 | **字段级覆盖** |
| 4 | 功法阅读 | `mxt:technique_reading` | `{learn_time?, hold_animation?, hold_sound?}` | `technique_binding` 的三个字段 | **字段级覆盖**；功法身份仍看 `mxt:technique`（见 §3.6） |
| 5 | 锻打方式 | `mxt:forging_methods` | `List<Holder<ForgingMethod>>` | `tool_binding.methods` | **并集**；**替换**旧的 Holder 组件 |
| 6 | 图纸 | `mxt:forging_blueprints` | `List<Holder<ForgingBlueprint>>` | `blueprint_binding.blueprints` | **并集**；**替换**旧的 Holder 组件 |

组件的 JSON 形状全部是"该载荷自己的 codec"，不带壳：`mxt:quality_chain="mxt_test:forged"`、`mxt:element=["mxt_test:fire"]`、`mxt:forging_blueprints=["example:spirit_sword"]`。

**明确不给组件、只由定义给的四样**（2026-09-26 用户两次点名去掉）：

| 只由定义给 | 为什么不必 | 逐件想改时怎么办 |
| --- | --- | --- |
| `conditions`（绑定门） | 条件是"这条定义什么时候生效"，本来就是定义的属性；它读的是持有者/环境，不是这一堆物品的固有数据 | 为该堆写一条定义（`items` 点名它即可），或把条件写进它引用的品质档/元素里 |
| `item_binding.actions`（物品行为） | 行为只在"用完那一刻"发生，逐件塞一段行为会让"这件物品做什么"散在两处；动作本来就该由定义承载 | 写一条 `item_binding` 定义并用 `items` 点名这件物品 |
| `weapon_binding.attributes` | 物品自己的属性修正**原版已经有出口**：`minecraft:attribute_modifiers` 组件（配方组件补丁 / KJS），本体不需要再造一个同义组件；定义里的 `attributes` 仍是"叠加在物品自身之上"的那一份 | `/give @s minecraft:iron_sword[minecraft:attribute_modifiers=[...]]`，或 KJS/配方组件 |
| `weapon_binding` 的三个动作（use/attack/tick） | 武器钩子是行为，逐件给"半套行为"会让"这件武器能干什么"散在两处 | 写一条 `weapon_binding` 定义并用 `items` 点名这件物品 |

取舍可以归纳成一句：**有原版出口的不重造，纯数据、且原版没有对应物的才给组件。** 所以剩下的六个全是"这一堆自己是什么/会什么数据"（品质链、元素、丹药、阅读法、手法、图纸），而"什么时候能生效、打出去做什么、数值怎么算"仍由定义说话。

**保留不动的既有组件**：`mxt:technique`（功法身份，最高优先）、`mxt:item_quality`（档位覆盖）、`mxt:item_abilities`（法器能力叠加）、`mxt:spirit_storage` / `mxt:item_aura`（灵气，元素回落的第二顺位）、`mxt:curse_container` 等与绑定无关的。

**退场**：`mxt:tool_binding`、`mxt:blueprint_binding`（都是 Holder 型间接层）。

### 2.3 合成规则只有三句话

1. **单值原子**（`quality_chain`）：组件是显式声明 → 组件优先，定义作默认。
2. **列表原子**（`element` / `forging_methods` / `forging_blueprints`）：**并集**，定义在前、组件在后，按 id 去重。
3. **记录原子**（`pill` / `technique_reading`）：**字段级覆盖**——组件只写 `learn_time` 时，`hold_animation` / `hold_sound` 仍来自定义；一个键都不写就等于没写这个组件。

没有被组件覆盖的东西（条件、物品行为、武器属性、武器动作、定义认领本身）一律只由定义说话。

### 2.4 定义端的字段不动

定义表**保留现在所有字段名**，只补 `items` / `priority`。理由：

- 现有包、现有文档、编辑器 schema 的改动面小一半；
- "定义 = 批量投放的原子"这个说法要成立，定义字段与组件名一一对应即可，不必把定义也改成组件引用（那会让一份定义读起来像拼装清单）；
- 老包写的是 `methods` / `blueprints`，改成别的名字属于纯改名，没有语义收益。

对照关系就是 §2.2 的表格本身：`technique_binding.learn_time` ↔ `mxt:technique_reading.learn_time`、`tool_binding.methods` ↔ `mxt:forging_methods`，以此类推；**没有组件的那几列（conditions / attributes / 三个动作）就是没有对应项**。

## 3. 六张表改后的形状

### 3.1 `item_binding` / `weapon_binding` / `pill_binding`

形状不变（已经是 `ItemMatcher`），只是读法多一层：

- 定义命中 → 得到一批原子；
- 堆上原子组件 → 覆盖 / 并入；
- 两者都没有 → 这张表对这堆物品不生效。

三张表各自的**组件形态**（定义字段照旧，一行是一张表）：

| 表 | 有组件的部分 | 只有定义的部分 |
| --- | --- | --- |
| `item_binding` | `mxt:quality_chain`、`mxt:element` | `actions`、`conditions` |
| `weapon_binding` | `mxt:quality_chain`、`mxt:element` | `attributes`、三个动作、`conditions` |
| `pill_binding` | `mxt:quality_chain`、`mxt:pill` | `conditions` |

即 `ItemBinding` 按用户点名的例子**只**拆成 `mxt:quality_chain` + `mxt:element` 两个组件：`actions` 与 `conditions` 仍只由定义给。

### 3.2 `tool_binding`

```json
{
  "items": ["example:smith_hammer", "#example:forging_tools"],
  "priority": 0,
  "methods": ["example:light_strike", "example:heavy_strike"]
}
```

- `items` **必填非空**：旧 Holder 组件退场后，没有 `items` 的定义永远读不到，加载期直接拒绝（空表用 `.validate(...)` 拒绝是本仓既有口径）。
- 物品侧两条路：被 `items` 认领（自动），或带 `mxt:forging_methods=["example:light_strike"]`（逐件）。
- 工具槽的规则从"**带 `mxt:tool_binding` 组件**"改成"**能解析出至少一种手法**"（定义 ∪ 组件非空）。

### 3.3 `blueprint_binding`

```json
{
  "items": "example:sword_manual",
  "priority": 0,
  "blueprints": ["example:spirit_sword"]
}
```

```mcfunction
/give @s minecraft:paper[mxt:forging_blueprints=["example:spirit_sword"]]
```

这就是用户举的例子：一份图纸物品只带一张图纸时，**不需要任何定义文件**。`items` 同样必填非空。

### 3.4 锻造台的读法（双端一致是硬约束）

- `selectableBlueprintIds(container, registries)` = 三格蓝图物品各自"定义 ∪ `mxt:forging_blueprints`"，按格子顺序去重；
- `availableMethodIds(...)` 不变（蓝图 `allowed_methods` ∩ 工具并集）；
- `ForgingSurface.canPlace` 现在只看组件，改成调一个解析器 → 必须把 `Provider`（或 `RegistryAccess`，`availableMethodIds` 已经是这个形状）串进来。两侧都有同步过来的数据包注册表：服务端用 `level.registryAccess()`，客户端菜单用 `player.level().registryAccess()`。
- **没有"列出全注册表"的回退**这条仍然成立：三格空 = 蓝图列表空。

### 3.5 `technique_binding`

```json
{
  "technique": "example:azure_breath",
  "items": ["example:azure_manual"],
  "priority": 0,
  "carrier_item": "example:azure_manual",
  "learn_time": 60,
  "hold_animation": "block",
  "hold_sound": "minecraft:item.book.page_turn"
}
```

- `items` **可选**：省略时这份声明只能按功法 id 被读到（今天的形状）；写了就额外认领一批物品，**这些物品不必带组件**。
- 解析（用户已拍板）：**堆上的 `mxt:technique` 组件优先**（它是"这堆教哪门功法"的身份），没有组件时用 `items` 命中的那条定义的 `technique`，两者都没有则这堆不是手册。
- `mxt:technique_reading` 组件可以覆盖 `learn_time` / `hold_animation` / `hold_sound`（例如同一门功法给两件物品配不同姿势）。
- **picker 的载体**：有 `items` 的声明，那一行直接给被认领的物品（不带组件）；没有 `items` 的仍按 `carrier_item` 生成一份带 `mxt:technique` 的堆（创造栏现在不生成载体，见 §4 末尾）。

### 3.6 `technique_binding` 与"功法身份"的关系（容易读错的一点）

组件 `mxt:technique` 说的是"**这一堆**教哪门功法"；`technique_binding` 说的是"**这门功法**怎么被读"。加 `items` 之后两者仍是两件事，只是"这门功法可以顺带认领一批物品"。所以：

- 同一门功法**只有一条** `technique_binding`（按功法 id 唯一）；
- 它的 `items` 只是"哪些物品不带组件也算这门功法的手册"；
- 两个定义都认领同一件物品时，按 `priority` 取一条（`ItemMatcher` 的既有规则）。

## 5. 数据格式示例

一件内容包的锤子，**两种写法等价**：

```json
// data/example/mxt/tool_binding/smith_hammer.json —— 批量：认领一族工具
{
  "items": ["example:smith_hammer", "#example:forging_tools"],
  "priority": 0,
  "methods": ["example:light_strike", "example:heavy_strike"]
}
```

```mcfunction
:: 逐件：只给这一把（不必有任何定义文件）
/give @s example:smith_hammer[mxt:forging_methods=["example:light_strike","example:heavy_strike"]]
```

一堆图纸 = 定义给的一张 + 这一堆自己多带的一张：

```mcfunction
/give @s example:sword_manual[mxt:forging_blueprints=["example:moon_blade"]]
:: example:sword_manual 被某条 blueprint_binding 认领 → 结果是 [example:spirit_sword, example:moon_blade]
```

单件武器：元素 + 品质链走原子，数值走**原版**组件（本体不重造 `attributes` 组件）：

```mcfunction
:: 这一堆的额外攻击力：写原版组件（配方组件 / KJS 同形）
/give @s minecraft:iron_sword[minecraft:attribute_modifiers=[{"type":"minecraft:attack_damage","id":"example:iron_sword/damage","amount":7,"operation":"add_value"}],mxt:element=["example:metal"],mxt:quality_chain="example:forged"]
```

一堆丹药：数据走 `mxt:pill`，其余（条件）仍由定义给：

```mcfunction
/give @s example:qi_pill[mxt:pill={toxicity_gain:2,toxicity_threshold:20}]
```

KubeJS 侧同形（组件补丁本来就是脚本能写的东西）：

```js
ItemEvents.rightClicked('minecraft:iron_sword', event => { /* 规则仍来自定义/组件，脚本不注入定义 */ })
// 造一堆带原子的物品：
event.player.give(Item.of('minecraft:paper', { mxt: { forging_blueprints: ['example:spirit_sword'] } }))
```

## 6. 兼容与迁移

| 变化 | 老包会怎样 |
| --- | --- |
| `mxt:tool_binding`（Holder）退场 | 老物品上这个键变成原版的"未知组件"，被丢弃并（可能）记一条日志；**改成 `mxt:forging_methods`** |
| `mxt:blueprint_binding`（Holder）退场 | 同上，**改成 `mxt:forging_blueprints`** |
| `tool_binding` / `blueprint_binding` 新增必填 `items` | 老定义文件没有 `items` → **加载期报错并点名**（不是静默忽略）。这是刻意的：这两张表没有 `items` 就永远读不到，静默接受等于留一份死定义 |
| `technique_binding` 新增可选 `items` | 老文件不受影响 |
| 六张表的 `priority` | 默认 `0`，老文件不受影响 |

未发布阶段不做迁移脚本、不做数据修复（与 2026-09-26 删 `attack_damage` / `attack_speed` 同一口径）。

## 7. 性能与缓存

- 现在是"每 tick 每只 LivingEntity × 双手"各解析一遍三张表，且**没有缓存**（上一轮审计的开放项）。
- 组件路线本身很便宜（读堆），定义路线要扫注册表 → **先问组件、再问定义**；组件已给全的原子不必为了答案再扫表。
- 槽位规则会被"每格每次放入"问到，比每 tick 更频繁 → 本稿落地时**应当一起做**"按物品开键 + `itemLevel()` 分界"的缓存（`HoldLookup` 已有同形实现可照抄）。
- 缓存键必须按**注册表实例**开，并在 `ServerCache.onDatapackLoaded` 显式 `invalidate()`（`/reload` 不换实例）。

## 8. 不做 / 推迟

- **不做**"组件里放 `Holder<XxxBinding>`"（用户已否）。
- **不给** `conditions` / `weapon_binding.attributes` / `weapon_binding` 的三个动作做组件（2026-09-26 用户点名去掉）：条件是定义的属性，属性修正有原版 `minecraft:attribute_modifiers` 出口，武器钩子逐件拆半套没有收益。逐件想改就走"写一条定义 + `items` 点名"或原版组件。
- **不做**老包迁移与存档修复。
- **不给** `artifact` / `spirit_herb` / `item_aura` / `currency` 加组件路线——它们是内容表，不是绑定表（`artifact` 要不要读 `mxt:element` 见 §10 问题 3）。
- **不动** action / condition / number provider 的类型系统本身。
- **不动**`mxt:item_quality` 与 `mxt:quality_chain` 的分工（一个是档位覆盖，一个是链条引用）。
- 上一轮审计的其它开放项（三个已删字段是否加载期拒收、`ItemCost` 是否该实现 `ItemMatcher`、tooltip 里的 `GrantSpiritRootAction` 特判）不在本稿范围内。

## 11. 落地记录（2026-09-26）

按上面定稿实现，`compileJava` / `compileTestModJava` / `processTestModResources` 通过（`--rerun-tasks` 全量一次）。实际形状与设计的差异、以及实现时才定下来的细节：

1. **组件共 6 个**（品质链、元素、丹药、功法阅读、锻打方式、图纸）。品质链与元素没有新建记录类型——载荷就是现成的 `Holder<QualityChain>` 与 `holderOrTagList(Element)`，直接 `register(...)` 注册；`mxt:pill` / `mxt:technique_reading` 各是一个新记录（字段全可选 + `applyTo(定义)` 做字段级合并），锻打方式/图纸直接用定义同款 `AutoIgnoreListCodec`。
2. **`mxt:forging_methods` / `mxt:forging_blueprints` 顶替两个 Holder 组件**：`MxtDataComponents` `+6 / -2`；`ToolBinding` / `BlueprintBinding` 的 `CODEC`（`RegistryFixedCodec`）随之删除。
3. **三张表实现 `ItemMatcher`**：`ToolBinding` / `BlueprintBinding` 的 `items` **必填**（`.validate` 拒绝空表，理由见 §3.2）；`TechniqueBinding` 的 `items` **可选**，`defaults(...)` 一并补 `entries`/`priority`。
4. **解析位置**：`ItemBindingService.resolve(Provider, ItemStack)` 现在合成"定义 + 组件"——丹药按字段合并（没有定义时用 `PillBinding.defaults()` 兜底）、功法阅读按字段合并、`mxt:quality_chain` 作为 `ResolvedBindings.qualityChainOverride` 排在解析顺序最前；`technique(...)` 是两步（组件优先 → `items` 命中的定义），没有组件且没有定义时照旧 `empty`。
5. **锻造模块新增 `ForgingBindingService`**（`methods` / `blueprints` / `isTool` / `isBlueprint`），`ForgingSurface.canPlace` 因此多收一个 `@Nullable Provider`；`ForgingWorkstationService` 的两个清单方法与 `ForgingTableBlockEntity` / `ForgingMenu` 三处调用点跟着串 `registryAccess()`（双端都有同步的注册表）。槽位规则从"带组件"改成"能解析出至少一种手法 / 一张图纸"。
6. **功法手册的第二条路一直通到长按**：`TechniqueItemService.initialize()` 除 `TechniqueHold.INSTANCE`（认组件）之外，为每条带 `items` 的声明再注册一个 `TechniqueHold(entries)`（认物品），所以不带组件的被认领物品一样能长按阅读——否则 `learn_time > 0` 的声明会变成"右键什么都不发生"。`TechniqueHold` 因此从无参记录变成 `record TechniqueHold(List<Entry> entries)`。
7. **picker**：`tool_binding` / `blueprint_binding` 进分类（它们现在有 `items` 了）；`techniqueCarrier` 改为——声明点名了具体物品就给那件物品（**不带**组件，因为它靠匹配就是手册），否则按 `carrier_item` 生成一份带组件的。
8. **降级项**：设计 §7 说"缓存本稿一起做"，实际**没有做**——它要按物品开键 + `itemLevel()` 分界 + `/reload` 失效，与本稿的解析改动叠在一起风险太大，留作下一稿（当前成本与改动前一致：组件读取很便宜，只有命中定义时才扫注册表）。
9. **已知松弛**：`mxt:technique_reading` 组件不参与 `HoldBinding.validate`（"写了姿势却没有长按"这种组合不会被加载期拒绝，因为合并在读取时发生）；组件与定义给出的修饰符 id 相同时按 id 去重（组件覆盖）。
10. **未做**：探针腿（§9 那 9 条）没有加，只做了编译验证；文档站中英同步在本次改动里一并处理。
