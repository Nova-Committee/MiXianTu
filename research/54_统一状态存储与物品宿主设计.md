# 54 统一状态存储与物品宿主设计

> **状态：已落地**（2026-09-26 实现；落地记录见 §7）
> **基准**：工作树 = `HEAD f89bbf9` 之后未提交的几轮改动（绑定表重划、HUD 锚点等）之后的状态；组件清单以 `registry/MxtDataComponents.java`、字段以 `docs/数据包格式.md` 为准。
> **一句话**：数据包声明的状态统一走 `DataStorage`；**物品堆也成为宿主**（一个组件 `mxt:storage` 装 `DataStorageHolder`），`mxt:storage` 技能的容器从专用组件搬成类型 `mxt:container`，能力侧那份与 `CooldownDataStorage` 重复的冷却表删除。

## 0. 本稿的依据（用户口径）

2026-09-26 的原话与本稿的三问答复：

1. **"检查一遍当前的物品组件，因为 ability 系统里面有专门的 DataStorage 统一存储数据，考虑直接进行通用归一化处理。其他给单一 ability 存临时数据的地方也考虑用 DataStorage。"**
2. 范围选了**乙**：物品接入 + 清重复（不做地址加 family、不搬触发器/灵气爆发/修炼三张表）。
3. `mxt:storage` 的**格数留在技能类型上**（`slots` 不动），`DataStorage` 类型只放状态。
4. 物品上的存储**先只给运行时**：不加物品侧的 `mxt:modify_storage` 与 storage 条件。

## 1. 审计（改前的证据）

### 1.1 26 个物品组件分成三组，只有一个是"某条技能的状态"

| 组 | 组件 | 判断 |
| --- | --- | --- |
| **这一堆"是什么"**（定义/身份载荷） | `forging_result`、`forging_methods`、`forging_blueprints`、`item_quality`、`quality_chain`、`element`、`pill`、`technique_reading`、`technique`、`item_abilities`、`curse_container`、`contract_scroll`、`secret_realm_token`、`rift`、`identification`、`cheque`、`token`、`talisman`、`formation_plate` | 不动 |
| **这一堆"自己的状态"** | `spirit_storage`、`item_aura`、`resource_container`、`artifact_state`、`spirit_beast`、`contract_bell` | 不动（理由见 1.2） |
| **某一条技能的状态** | `artifact_storage` ↔ `mxt:storage` | 归一化 |

### 1.2 为什么第二组不搬

1. **地址表达不了**：`DataStorageHolder.Address` 是 `(id, 类型类)`，**同一宿主上每个类型最多一个值**；`spirit_storage` / `resource_container` 是"一个键一张表"（灵气/数值 → 数量），搬进去要给每种灵气、每种数值各注册一个类型。
2. **它们靠"有名字的组件"活着**：两个 tooltip appender、`ArtifactDescription`、物品条件 `mxt:spirit_storage_not_full`、`ItemAuraAccess` 协议、`/data get` 的可读性。
3. **与 53 号稿同一条口径**：逐件附加的那一半就是组件（属性修正的原版出口是 `minecraft:attribute_modifiers`）。
4. `artifact_state` 归 `artifact` 定义（不是技能）；`contract_bell` / `spirit_beast` 是身份快照。

### 1.3 能力侧"给单一定义存临时状态"的地方

| 位置 | 存什么 | 结论 |
| --- | --- | --- |
| `AbilityAttachment.cooldowns` | 每技能一个 long（下次可用 tick） | **与 `CooldownDataStorage` 同 tick 双写**（`AbilityService:248/249`、`451/452`），读的人也是两套（闸门 `:74/108/236` 与轮盘 `AbilityWheelEntry:82` 读表、`:92` 读 DataStorage）→ 本稿删除 |
| `TriggerCooldownAttachment` | 每条 `trigger` 规则一个 long | 形状相同，但 `TriggerRule` 没有 `DataStorageDeclaration`、家族 `mxt:trigger` 未注册 → 留给后续 |
| `SpiritBurstCooldownAttachment` | 每种灵气一个 long（要同步） | 同上，家族 `mxt:aura`；运行时特性，只能走 `RuntimeStorage` |
| `CultivationAttachment.cultivateCooldowns` | 每条 `cultivate_action` 一个 long | 同上，家族 `mxt:cultivate_action` |
| `SpiritIdentityAttachment` / `CultivationAttachment` / `ElementAttachment` / `ResourceHolderAttachment` / `CurseHolderAttachment` 的按定义键的表 | 一个宿主对**多个**定义 | 单值寻址表达不了，不搬 |
| `TribulationAttachment.state` | 天劫当前节拍的游标 | **已经是** DataStorage，刻意的单槽（`data/timeline/TimelineState`） |
| `FlightAttachment`、`PillToxicityAttachment`、工作站会话、各种手势/节流缓存 | 一次活着的会话 / 与定义无关 | 不搬 |

### 1.4 三个结构卡点（本稿只解决与物品有关的那一个）

1. **只有一个家族**：`MxtDataStorageHosts` 只注册了 `mxt:ability`，`Ability` 是全仓唯一实现 `DataStorageDeclaration` 的类型。
2. **地址不含 family**：所以两个家族共用一个 holder 会撞 id —— 这就是"搬第二张表"必须先改地址的原因（本稿不碰）。
3. **宿主写死 `Entity` 且就地改**：`Function<Entity, DataStorageHolder>` 让物品接不进来；写入语义是"就地改 + `markDirty`"，而**组件是值**（可比对、会复制、要同步），就地改会让菜单与副本看到同一个实例。

## 2. 结论（新形状）

```
数据包：  mxt:ability/<id>.json    type: mxt:storage, slots: 9
                     │ 声明状态种类（隐式：这条技能自己的容器）
                     ▼
宿主 ── 实体： mxt:ability_holder 附件（按 family+id 寻址，今天仍只有 ability 一族）
      └─ 物品： 组件 mxt:storage = DataStorageHolder（按 (技能 id, 类型类) 寻址）
                     ▼
状态 ── 类型 mxt:container(contents)：装满一格的空堆表示"这一格是空的"
```

- **规则**：一条技能的状态住在哪，由"这条状态是承载物的还是持有者的"决定。**容器归承载物**（箱子长在物品上）；**冷却、充能、开关仍归持有者**（今天如此，语义不变，只是冷却从两张表并成一张）。
- `mxt:storage` 技能的 `slots` 仍是**类型字段**（声明），容器内容是新类型 `mxt:container` 的**状态字段**；格数不进组件，组件里那份列表由服务按格数补齐。
- 物品侧的写入是**换值**：`stack.set(mxt:storage, holder.with(id, value, gameTime))`，从不在原 holder 上原地改。

## 4. 不做（本稿明确排除）

- 地址加 family、宿主全面泛化，以及触发器 / 灵气爆发 / 修炼三张冷却表的收编 —— 每一条都要先给对应定义加 `DataStorageDeclaration` 并注册家族，且会换存档格式。**2026-09-26 用户拍板：不做**——DataStorage 的定位就是"只存技能相关数据"，地址保持 `(id, 类型)` 两维、直接用 map 即可；**但接入位要留着**（`MxtDataStorageHosts` 那张 family 表 + `DataStorageDeclaration` + 内容寻址里本来就有的 `family` 字段），将来同类地方要当宿主时自带一份 holder 就能接进来。这条口径已写进 `MxtDataStorageHosts` 的注释与 `docs/数据包格式.md`。
- 物品侧的 `mxt:modify_storage` 与六个 storage 条件（内容暂时碰不到物品存储）。
- 26 个组件里那 25 个的搬家（§1.2）。

## 5. 数据包影响

- **删除** 组件 `mxt:artifact_storage`：老包/老存档里的这个键不再被读；`/give` 再写它会直接报"未知组件"。内容改为 `mxt:storage`（运行时自己写，作者不必手写）。
- `mxt:storage` 技能的字段**不变**（仍是 `slots`），写法与老包一致。
- `cooldown` 字段的说明**更准确**：它写进 `mxt:cooldown` 状态这一点没变，但这下真的只有这一份（原先同 tick 还写一张附件里的表）。

## 7. 落地记录（2026-09-26）

### 7.1 物品宿主

- 新类型 `data/storage/builtin/ContainerDataStorage`（`mxt:container`，状态字段 `contents`，`ItemStack.OPTIONAL_CODEC` 保洞），注册进 `MxtDataStorages`；`DataStorageHolder` 增 `with(id, value, gameTime)`（返回新实例，物品是值）与 `count(kind)`（`/mxt info`）。
- 新组件 `mxt:storage`（`MxtDataComponents`，载荷 `DataStorageHolder`，持久化 + 同步），删 `mxt:artifact_storage` 与 `ArtifactStorageComponent`。
- 新出口 `runtime/item/ItemStorageService`（`get(stack, id, kind)` / `set(stack, id, value, gameTime)`，写入一律换值）。
- `ISpiritStorage` 三处签名带上 `Holder<Ability>`；`ArtifactStorageService` / `ArtifactStorageContainer` 全部改走「技能 id + `ContainerDataStorage`」；`StorageAbilityType` 把 `Holder<Ability>` 交给容器；`ArtifactDescription` 的「已用 / 总格数」改读新组件。**一件承载物上两条储物技能因此各有各的箱子**（旧写法取"第一条储物技能"）；`ArtifactService` 里那个"取第一条储物技能"的 `storageSlots(Provider, ItemStack, FormulaContext)` 与它的私有助手 `first(...)` 随之删除（运行时不再有第二个入口，探针改用自己的一行 helper）。
- `DataStorageHolder` 还补了 `equals` / `hashCode`（按 `values`）：**组件是按值比较的**，而这个类原本只有身份相等——两个内容相同的存储会被当成两个不同的组件，多出无谓的同步与"不匹配"的栈。`owner` 不参与（它是附件的反向指针）。注：`ContainerDataStorage` 的载荷是 `List<ItemStack>`，而 `ItemStack` 自己就是身份相等，所以含容器的两个存储本来就只在共享同一批堆实例时才相等——这一点与旧的 `ArtifactStorageComponent`（record 包 `List<ItemStack>`）完全一致，不是新引入的。
- 测试包：`roundTripsStorage` 原来是个**从未被调用的死助手**（它命中的正是"列表里出现空堆导致同步包编码失败"，等于那条腿从来没跑过），改成对 `mxt:storage` 组件的往返 + 一条真腿（jade 27 格、写第 1 格 3 个石头、第 0 格仍是洞、越过容量的第 27 格为空、另一条技能 id 读不到、并把 `mxt:storage` 组件送进网络 codec 再解回来）。腿挂在 `artifact roster` 上（`/mxt_test artifacts`）。

### 7.2 冷却归一

- `AbilityAttachment` 删 `cooldowns` 字段、codec 项、两个访问器与 `revoke` 里的清除；`AbilityStorage` 增 `remaining` / `onCooldown`（`duration - (gameTime - changedAt)`，与 `StorageCooldownEntityCondition` 同一条换算）；`AbilityService` 三处闸门改读它、两处 `setCooldownUntil` 删除（`CooldownDataStorage` 的写入保留）；`AbilityWheelEntry.cooldownTicks` 改读 `remaining`；`/mxt info` 的冷却项数改数存储里的 `mxt:cooldown`。
- 老存档里附件 JSON 的 `cooldowns` 键会被 `RecordCodecBuilder` 忽略；同一刻已经写过 `CooldownDataStorage`，不丢信息。

### 7.4 未跑 / 遗留

- **探针未实跑**（只编译）。首次实机要盯的是那条新腿与日志里的 `Failed to encode`（`clientbound/minecraft:container_set_slot`）——`mxt:storage` 是本模组第一个把 `List<ItemStack>` 塞进同步组件里的组件，空堆口径就是这个坑。
- `mxt:container` 的**门口径**：它注册在同一张 `type` 表里，所以内容其实**可以**在技能的 `components` 里声明它、并用 `mxt:modify_storage` 写进实体附件（声明校验只比对类），只是**六个 storage 条件里没有读它的那一个**，写进去等于一个没人看的槽。物品宿主那一侧则完全不在内容寻址范围内。这里选择"照实写清楚"而不是给它加 `RuntimeStorage` 标记（它存的是持久的、玩家可见的状态，不是运行时游标），也没为它加第七个条件（用户明确选了"先只给运行时"）。
- 有意不做（§4）：地址加 family、触发器 / 灵气爆发 / 修炼三张冷却表、物品侧的 `modify_storage` 与 storage 条件。地址加 family 这一条已于 2026-09-26 被用户**正式关闭**（定位=技能专用、直接用 map；接入位保留），不再是"待办"，而是设计口径。
- 顺手发现，**已修（2026-09-26 同日）**：`CreatureSpiritAttachment.apply()` 补上了 `markDirty()`（此前只有构造器标记，往一份已存在的附件里写灵宠档案不会同步给客户端；探针 `contract probe` 加了 `synced=` 一行断言）；`ArtifactService` 两处过期注释已清（`upkeep` 的"price is stored under an id"已无该字段，`slotsOf` 的取整说明原先挂错了方法）。
- 顺手发现但**未处理**：`AlchemyWorkstation` 接口零实现者（整条炼丹工作站/会话层是死代码）——用户明确"先不要动"；`mxt:timer` 等四种类型没有 Java 写者，但那是设计（生产者是内容侧的 `mxt:modify_storage`），不是缺口。

### 7.5 跟进（2026-09-26，同一轮）

- **迁移审计**：按「授予的技能还留了什么状态」逐条查过一遍，**per-ability 的状态已经全在 DataStorage 里**——冷却（`mxt:cooldown`）、充能（`mxt:charges`）、施法截止（`mxt:cast_deadline`）、引导脉冲（`mxt:channel_pulse`）、灵气脉冲（`mxt:aura_pulse`）。仍在 DataStorage 之外的都不是"某条技能的状态"：`AbilityAttachment.sources`（授予台账）与 `channelledAbility`（当前这一条引导，单值游标）、`FlightAttachment`（当前这次飞行，单值会话）、`TriggerCooldownAttachment`（键是**规则** id）、`SpiritBurstCooldownAttachment`（键是**灵气**）、`CultivationAttachment.cultivateCooldowns`（键是**修炼动作**）。
- **一对一映射改为强制**（用户点名：`(ability, class) -> storage` 必须是一对一）：`components` 里同一个类型写两遍**在加载期报错并点名该类型**；`DataStorageHolder` 的解码遇到两条同地址记录**拒绝**（正常代码写不出来，之前是静默后者覆盖前者）；运行时的 `set` / `with` 仍然是替换语义。地址本身没变，`family` 仍在推迟项里。
- **定位与预留定案**（用户点名："DataStorage 目前只用来存 ability 相关数据，直接用 map 就行，不过保留给其他类似地方用的预留"）：地址就是 `(id, 类型)`、一个宿主一份 map，不再加维度；`MxtDataStorageHosts` 那张 family 表与 `DataStorageDeclaration` 作为**接入位**留着（另一张注册表的定义要当宿主：实现 `DataStorageDeclaration` + 注册一行指向自己那份 holder，内容侧写法不变），限制是两家不能共用同一份 holder。
