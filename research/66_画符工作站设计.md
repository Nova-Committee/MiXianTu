# 66 画符（符箓）工作站设计

> 状态：**设计稿（未实现）**。2026-09-30 按用户要求"先做设计"落稿。
> 基准：当前工作树的 `mxt:talisman` 一系（`data/Talisman.java`、`data/item/TalismanComponent.java`、
> `runtime/talisman/TalismanService.java`）、原版配方三件套（`registry/MxtRecipeTypes.java` 与
> `recipe/AlchemyRecipe.java`）、品质一系（`runtime/item/ItemQualityService.java`）、ApricityUI 宿主
> （`screen/AuiContainerScreen.java`、`screen/AuiPages.java`）与 **ApricityUI 1.2.5 的 `<canvas>`**

> 本稿是这一轮**唯一**的设计说明；实现之后的形状以代码为准，届时在本稿末尾加"落地记录"节。

## 0. 一句话

新增一座**画符工作站**（方块）：玩家在界面里从"当下可选的符方"里挑一份 → 用鼠标在 **canvas** 上照符形画出来 →
**服务端**按正确率打分 → 按配方里写的档位决定**写哪一份 `talisman` 定义**（威力）与**哪个品质**（`mxt:quality`），
产出一张符箓。

范围：**符方走原版配方系统**（`Recipe` / `RecipeType` / `RecipeSerializer`，照 `mxt:alchemy`），
**不是**新的数据包注册表；符形、容差、判档规则都写在配方 JSON 里。

## 2. 名词

- **符方**：一份 `mxt:talisman_drawing` 配方。**符形**（pattern）是它的字段之一。
- **符形**：若干条**折线笔画**（归一化坐标）+ 容差，玩家要照着画的图案。
- **正确率**：玩家笔画与符形的吻合度，`[0,1]`，**服务端算的唯一一份**。
- **判档**：配方里按 `min_accuracy` 排的档位表，命中哪一档就按那一档产出。
- **威力**：本稿里**不是一个新数值**，而是"命中的档写了哪一份 `talisman` 定义"（见 §5.2）。

## 3. 四条硬约束（形状就是被它们定下来的）

1. **26.1 的客户端没有配方表。** `ClientboundUpdateRecipesPacket` 现在只带 `RecipePropertySet` 与石切配方，
   客户端手里是 `ClientRecipeContainer(Map.of(), SingleInputSet.empty())` + 只装"已解锁显示"的 `ClientRecipeBook`
   （`ClientPacketListener.handleUpdateRecipes/handleRecipeBookAdd`）。仓库里的先例也是这么写的：所有 `getRecipeFor`
   都走 `level.getServer().getRecipeManager()`，`AlchemyFurnaceView` 的类注释就是"客户端只画，绝不重算配方"。
   ⇒ **符形必须由服务端推给客户端**，而且**只推给正在这台工作站上画的那个人**（符形是几十上百个点，塞进配方就等于
   随配方广播给所有人）。
2. **画符界面必须能拿到逐点鼠标输入，而 AUI 的 canvas 在 Java 侧就够用。** 核过 1.2.5：`<canvas>` 有
   `@ElementRegister`，解析/插入 DOM 时 `Element.init` 会把它升级成 `com.sighs.apricityui.element.Canvas`；
   `width/height` 属性是**位图**尺寸、CSS 是显示尺寸；Java 侧可以直接 `getContext("2d")` 画，也可以直接
   `canvas.getSurface()` 拿 `BufferedImage`；Java 侧 `element.addEventListener("mousedown", e -> ...)` 拿到的
   `MouseEvent` **自带 `offsetX/offsetY`（相对该元素的文档坐标）与 `buttons`**。⇒ **笔画采集放 Java，页面不写 JS**。
3. **刷新会清空 canvas 与 JS 状态。** 热重载 / `document.refresh()` 重建 DOM，位图随之清空，JS 变量与监听器全失效。
   ⇒ 采集与重绘都由 Java 持有，挂在既有的"按 `Document.getRefreshGeneration()` 重绑"机制上（`AuiContainerScreen.rebind` 那套）。
4. **canvas 很贵，而且要 1:1 画。** 每次改都会 `markSurfaceDirty`（脏区并集），后端上传是**整张**贴图；
   最后那张四边形是 `LINEAR` 采样。⇒ 只画**增量**（收到一段画一段），位图尺寸 = 显示尺寸，别每帧整图重绘。

## 4. 数据形状

### 4.1 配方 `mxt:talisman_drawing`

位置：`data/<命名空间>/recipe/<路径>.json`（与 `mxt:alchemy` 同一条路，不是数据包注册表）。
`isSpecial() == true`、`showNotification() == false`、`PlacementInfo.NOT_PLACEABLE`、空 `RecipeBookCategory`
——它不在配方格里做，也不进配方书。

```json
{
  "type": "mxt:talisman_drawing",
  "name": { "translate": "recipe.example.fire_talisman" },
  "description": { "translate": "recipe.example.fire_talisman.desc" },

  "unlock_condition": { "type": "mxt:realm", "realm": "example:qi_refining", "comparison": "at_least" },
  "costs": [
    { "type": "mxt:item", "items": ["mxt:blank_talisman"], "amount": 1 },
    { "type": "mxt:item", "items": ["mxt:talisman_ink"], "amount": 1 }
  ],

  "pattern": {
    "canvas": [256, 160],
    "tolerance": 0.06,
    "strokes": [
      [[0.50, 0.06], [0.50, 0.94]],
      [[0.22, 0.28], [0.50, 0.10], [0.78, 0.28]]
    ]
  },

  "judgement": {
    "shape_weight": 0.7,
    "order_weight": 0.3,
    "stroke_count_strict": false,
    "min_stroke_length": 0.02,
    "grades": [
      { "min_accuracy": 0.35, "talisman": "example:weak_fire_talisman",   "quality": "mxt:inferior" },
      { "min_accuracy": 0.70, "talisman": "example:fire_talisman",        "quality": "mxt:common" },
      { "min_accuracy": 0.92, "talisman": "example:perfect_fire_talisman", "quality": "mxt:perfect",
        "max_damage": 8, "outputs": [{ "id": "mxt:talisman_ink" }] }
    ]
  },

  "failure_outputs": [],
  "success_action": { "type": "mxt:..." },
  "failure_action": { "type": "mxt:..." }
}
```

字段口径：

| 字段 | 必填 | 口径 |
| --- | --- | --- |
| `name` / `description` | 否 | 走 `MiscCodecs.TRANSLATABLE_COMPONENT`，与 `mxt:alchemy` 一致；省略时用 `recipe.mxt.<命名空间>.<路径>`（路径 `/` → `.`，见 `docs/guide/java/screens.md`） |
| `unlock_condition` | 否 | `EntityCondition.optionalCodec("unlock_condition")`；缺省 = 人人可选。**每次开界面现算**（见 §11 问题 2） |
| `costs` | 否 | `Cost.LIST_CODEC`，付款者是**玩家**（`CostContext.of(player, context, CostOrigin.TALISMAN_DRAWING)`）。符纸/符墨就在玩家的背包里，工作站**不建内部库存**（见 §11 问题 6） |
| `pattern.canvas` | 是 | 位图尺寸 `[宽, 高]`，也用于换算归一化点；客户端 canvas 的 `width/height` 属性就用它 |
| `pattern.tolerance` | 是 | **画布高度的比例**，`> 0`；判分前换算成像素 `tol_px = tolerance × 高`（这样宽高比不会让容差在 x / y 上不一致） |
| `pattern.strokes` | 是 | 每笔一条折线，点是 `[u, v]`，`[0,1]²` 内、有限；至少一笔、每笔至少两点 |
| `judgement.shape_weight` / `order_weight` | 否 | 默认 `0.7` / `0.3`，都 `≥ 0` 且不同时为 0 |
| `judgement.stroke_count_strict` | 否 | 默认 `false`；`true` = 笔数不等直接按 0 处理（见 §4.3） |
| `judgement.min_stroke_length` | 否 | 默认 `0.02`（画布高度比例）；短于它的笔画在计分前丢弃（手抖点） |
| `judgement.grades` | 是 | 至少一档；`min_accuracy` 必须**唯一且升序**（加载期 `.validate` 拒绝重复与乱序） |
| `grades[].talisman` | 是 | `Talisman.CODEC`（`Holder`）；命中即写进 `TalismanComponent` |
| `grades[].quality` | 否 | `ItemQuality.CODEC`；写了就用 `ItemQualityService.set` 写组件，不写就落到定义自己的 `quality` |
| `grades[].max_damage` | 否 | 覆盖载体耐久上限（走 `TalismanService.applyDurability` 的同一形状；**`talisman.durability` 已经能表达这件事**，这里只是给"画得好所以更耐用"留一个口子） |
| `grades[].charge` | 否 | `true` = 产出时按 `TalismanService.capacity` 灌满（与 `/talisman give charged` 同一实现） |
| `grades[].outputs` | 否 | `ItemStackTemplate` 列表，额外的产物 |
| `success_action` / `failure_action` | 否 | `EntityAction`，成功 / 失败各跑一次（反馈、统计、解锁后续都用现成动作） |
| `failure_outputs` | 否 | 默认空 = 只烧掉材料 |

**加载期校验**（`.validate(...)`，房规：空表 / 乱序 / 重复要拒收）：`strokes` 非空且每笔 ≥ 2 点、点有限且在 `[0,1]`、
`canvas` 两维 ≥ 1、`tolerance > 0`、`grades` 非空且 `min_accuracy` 唯一升序（最低档即失败线）、`costs` 里至少一条
物品消耗（否则"画空手符"）。

两处形状以代码为准，别照抄旧写法：`mxt:item` 的字段是 **`items`**（`ItemCost.CODEC` 读 `ItemMatcher` 的条目表，
裸物品 id / `#标签` / 类型化条目都收），不是 `item`；`mxt:realm` 的字段是 **`realm`** + 可选 `comparison`
（默认 `exact`，另两个取值 `at_least` / `at_most`）+ 可选 `min_minor_stage`。`Cost` 的 `{"id": ..., "amount": ...}`
简写只等于 `mxt:resource`，物品消耗不能这么写。

### 4.2 判档

按 `min_accuracy` **从高到低**找第一个 `accuracy ≥ min_accuracy` 的档；**都没命中 = 失败**，也就是**最低那一档的
`min_accuracy` 就是及格线**（只写一处，不另设一个 `min_accuracy` 与它重复）。同一份配方里"弱 / 中 / 完美"三档
就是三份 `talisman` 定义，这是**威力**的表达方式（§5.2）。

### 4.3 正确率算法（唯一实现：`runtime/talisman/TalismanDrawingScorer`）

纯函数、只读、无副作用，common 侧，客户端可以调同一份做本地预览。

```
输入：pattern（归一化点）、canvas 尺寸、tolerance、权重、玩家笔画（同一位图坐标系）
1. 归一化点 → 像素点：x = u × 宽, y = v × 高
2. 每条笔画按弧长等距重采样：S = clamp(round(长度px / 3), 16, 256)
3. 丢弃短于 min_stroke_length × 高 的玩家笔画
4. 距离 d(点, 折线) = 到最近**线段**的距离（不是到采样点，否则快慢会给不同分）
5. 对"期望笔 i × 玩家笔 j"：
   cover(i,j) = 期望点中 d(·, 玩家笔 j) ≤ tol_px 的比例
   prec(i,j)  = 玩家点中 d(·, 期望笔 i) ≤ tol_px 的比例
   pair(i,j)  = (cover + prec) / 2
6. shape = 期望笔取 max_j pair(i,j) 后的平均     （不看笔序、多画的笔不得分、少画必然掉分）
7. order = 笔数相等时：pair(i,i) 的平均
           笔数不等时：(公共前缀 pair(i,i) 的平均) × 公共笔数 / 较多笔数
           stroke_count_strict = true 时笔数不等直接 order = 0
8. accuracy = clamp(shape_weight × shape + order_weight × order, 0, 1)
   玩家一笔都没画 → 0
```

- **为什么要双向**：只涂满整张纸 `prec` 低，只描一小段 `cover` 低——乱涂与描一半都拿不到高分，这是不需要额外
  反作弊规则的最小设计。
- `stroke_count_strict` 给"道门严苛"的符方用；默认宽松（多一笔、少一笔按 `shape` 自然扣分）。
- 阈值与权重全部来自配方，本体不硬编码分数。
- 同一位图坐标系：客户端 canvas 的位图尺寸就是 `pattern.canvas`，所以像素点直接可比。

## 5. 品质与威力怎么来

### 5.1 品质

命中档的 `quality`（可选）→ `ItemQualityService.set(stack, holder)` 写组件 `mxt:quality`。
不写则落到定义自己的 `quality`（`TalismanService.quality` 已经在读这条链）。**不在本体里造第二套品质表**。

### 5.2 威力 = 写哪一份定义

`grades[].talisman` 点名定义：同一张符的"下品 / 常品 / 完美"是**三份 `talisman` 定义**，各自写 `abilities`、
`capacity`、`durability`、`costs`。这样"威力"完全由数据包表达，本体不引入"威力系数"，也不给 `talisman` 定义
开第二个数值入口（它已经有 `capacity` / `costs` / `durability` 三个出口）。

### 5.3 附加可写的

- 耐久上限：`grades[].max_damage`（照 `TalismanService.applyDurability`）。
- 初始灌注：`grades[].charge`（照 `/talisman give charged` 的 `insert` 循环）。
- 额外产物：`grades[].outputs`；成功 / 失败的反馈：`EntityAction`。
- 公式：任何 `NumberProvider` 字段都在注入了 `accuracy` 的上下文里求值
  （`FormulaContext.of(player, Map.of("accuracy", value))`，照 `TalismanService` 注入 `block_x` 的用法），
  所以"按正确率给灵气 / 给持续时间"这类需求不需要新字段。

## 6. 运行流程与会话

```
右键工作站（服务端）
  → 算一次"此刻可选的符方"：RecipeManager 里所有 mxt:talisman_drawing
     逐个问 unlock_condition（EntityCondition.test(player, context)）+ 材料是否够
  → TalismanDrawingListS2CPayload(条目: id, 名字, 材料是否够)
  → 同时用 player.openMenu(...) 打开界面（原版开菜单路径；菜单类型登记在 MxtMenus，
     客户端屏幕在 MxtRenderers.registerScreens 里绑），列表在菜单打开后推

玩家点一份符方
  → TalismanSelectC2SPayload(recipeId)
  → 服务端校验：在可选列表里 + 材料够 + 没有正在结算的会话
  → 回 TalismanPatternS2CPayload(recipeId, canvas, tolerance, strokes)      ← 符形只推给这一个人

玩家画完松手
  → TalismanSubmitC2SPayload(recipeId, List<List<[x,y]>>)
  → 服务端：**重新算分**（不信客户端的分数）→ 判档 → 扣材料 → 写符箓 → 进背包
  → TalismanResultS2CPayload(accuracy, 档位名, 结果文本) 给页面显示
```

**会话归属（硬约束）**：绘制会话（当前选中的 `recipeId` + 符形）**挂在服务端菜单上，不挂在方块实体上**——
两个玩家同时用同一座工作站时必须互不干扰；方块实体只管朝向，材料在玩家背包里（§11 问题 6）。

会话要有一个**生命周期出口**（关界面 / 断线 / 换维度都要丢掉），所以这一版做成**零槽位的菜单**
（`TalismanWorkstationMenu extends AbstractContainerMenu`，不注册任何 `Slot`）：`AbstractContainerMenu.removed(Player)`
正好是那个出口，`stillValid` 自带"还在不在工作站旁"的校验，`ContainerLevelAccess` 也现成。
代价是客户端要用 `AuiContainerScreen` 并接受"0 槽时槽位几何对账是空转"（实现时确认它在没有任何槽位时
一个字节都不写、也不去读页面几何）。

**备选（不选）**：纯 `Screen`（照 `MultiblockStructureScreen`）+ 服务端按玩家记一张会话表。省掉菜单，
但会话的过期、登出、换维度清理全要自己补，"玩家还在不在这个界面上"也退化成"离方块多远"。

**缓存的失效口径**（房规）：按类型索引配方（`getRecipes()` 过滤）的缓存要在 `ServerCache.onDatapackLoaded`
（`TagsUpdatedEvent.ServerDataLoad`）里 `invalidate()`，否则 `/reload` 后会一直用旧索引。

## 7. 网络

| payload | 方向 | 内容 | 备注 |
| --- | --- | --- | --- |
| `TalismanDrawingListS2CPayload` | S→C | 条目列表（id、名字、材料够不够） | 打开界面时推一次；材料变化时重推可选 |

| `TalismanSelectC2SPayload` | C→S | `recipeId` | 校验后才回符形 |
| `TalismanSubmitC2SPayload` | C→S | `recipeId` + 笔画点序列 | 见 §8 的限流 |

登记两处照 `NetworkManager` 的既有形状（`playToServer` + `playToClient` 的 dedicated-server 分支只登记 codec，
handler 只在客户端命名——这条注释已经在 `NetworkManager` 里写着了，照做）。

- 宿主：`TalismanWorkstationScreen extends AuiContainerScreen<TalismanWorkstationMenu>`，**零槽位**（§6：
  选它的唯一理由是 `removed(Player)` 那根会话生命周期钩子）。`extractRenderState` 先
  `ApricityGuiLayers.submitUi(graphics)` 再 `super`，不画原版整屏暗化，页面对账照既有宿主那套
  （`bindPage` / `onPageBound` / `refresh` / 按 `getRefreshGeneration()` 重绑）。
  零槽位意味着 `bindPage` 不注册任何 `cells`，页面里的节点全是自绘内容。
- 页面骨架：符方列表（左）＋ 画布（中）＋ 结果与按钮（右/下）。皮肤走 `mxt/common/theme.css` 的扁平半透明深色。

### 8.2 画布

```html
<canvas id="paper" width="256" height="160"></canvas>
```

- `width` / `height` 属性由 Java 按 `pattern.canvas` **写死**（`setAttribute`），CSS 尺寸与位图**1:1**
  （§3.4：四边形是线性采样，放大就糊）。
- 参考符形（淡影）用页面里**第二个 canvas**（`<canvas id="guide">`，同尺寸，叠在 `paper` 上的一层），
  只在"选中符方 / 尺寸变化 / 重绑"时画一次；**玩家笔画只画进 `paper`**。两层的叠放要写**显式 `position` +
  `z-index`**（AUI 里绝对定位的兄弟之间别指望 DOM 顺序，轮盘踩过这个坑）。两者**不共用一条 surface**：
  共用就意味着每次重画参考都要整图重绘（§3.4）。`OffscreenCanvas` 在这里没有用武之地
  （它是"画好再 `transferToImageBitmap`"的一次性素材）。
- **笔画采集（Java 侧）**：在 canvas 元素上 `addEventListener` 听 `mousedown` / `mousemove` / `mouseup` / `mouseleave`：
  - `mousedown`：开一笔，`ctx.beginPath/moveTo`；
  - `mousemove` 且 `buttons != 0`：把点加入当前笔、`ctx.lineTo/stroke`（**只画新增段**）；
  - `mouseup` / `mouseleave`：收笔；
  - 坐标直接用 `MouseEvent.offsetX/offsetY`（**已经是相对该元素的文档坐标**），按"位图 ÷ CSS 尺寸"缩放到位图坐标；
    CSS 尺寸只在布局变化时通过 `Size.of(element)` 读一次并缓存（房规：不回读几何、按需读）。
- **不在页面里写 JS**：刷新会清 DOM/JS 状态并清空位图（§3.3）。绘制逻辑放在
  "按 `Document.getRefreshGeneration()` 重绑"的那条路上（`AuiContainerScreen.rebind` 的形状），热重载后自动重来。
- 增量绘制期间的性能：AUI 每次 `ctx` 调用都会 `markSurfaceDirty`（脏区并集）+ 一次整张贴图上传。所以：
  一节 `stroke()` 画一段（不是每个采样点一次 `stroke`）、拖动采样按"距离上一个点 > 1px 才记"抽稀、
  不在页面里挂 `@keyframes` 之类的每帧动画。

### 8.3 手势与槽位并存

页面**不写 `aui-mouse-events=intercept`**（`AGENTS.md` 硬约定）——本工作站没有原版槽位，但保留了"以后加材料槽"
的余地：DOM 拖拽与槽位拖拽靠"指针落在画布上与否"天然分开。

### 8.4 本地预览

客户端可以用同一份 `TalismanDrawingScorer` 算一份本地分数显示（可选，见 §11 问题 9）；
**服务端返回的那一份才是权威**，两者不一致时以服务端为准（并记一条 debug 日志便于发现实现漂移）。

## 10. 防作弊与边界（服务端权威）

- **分数由服务端算**：客户端只送原始点序列；`accuracy` 一律不发（发了也不读）。
- **限流**：单笔点数 ≤ 512、总点数 ≤ 4096（超出丢弃整次提交并记一条 warn）；同一玩家每秒最多 1 次提交；
  会话在结算后立即结束（要重画就得再花一张符纸——材料本身就是重试成本）。
- **必校验**：`recipeId` 必须等于当前会话选中的那份；材料仍够；提交时玩家仍在同一座工作站的界面上
  （`stillValid` 那一套）；配方仍存在且仍是这个类型。
- **点数与坐标清洗**：`double` 必须有限、clamp 到位图范围内、NaN/Infinity 直接拒收（房规：运行期遇到
  NaN/Infinity 记一次警告并按失败处理）。
- **不做"笔画重放"**：服务端只认这一次提交的点序列，签名 / 时间戳这类机制在这个规模上不划算（见 §12）。

## 11. 需要先问的开放项（不猜，逐条等你拍板）

1. **配方 id**：`mxt:talisman_drawing`（我建议，动作口径）／`mxt:talisman_recipe`（你原话）／`mxt:draw_talisman`。
2. **解锁语义**：**无状态**（每次开界面按 `unlock_condition` 现算，条件失效就又不能选）还是**一次性解锁**
   （满足过就永久可选，要落一份按玩家记的集合附件）。
   我建议先做无状态：条件本身就是"境界 / 功法 / 持有物"，无状态版**不需要新附件**，也不会引入迁移；
   要"永久解锁"再加 `once` 开关与一份集合。
3. **符形坐标系**：归一化 `[0,1]²`（我建议，与画布尺寸解耦、作者对着任意画布写）还是绝对像素。
4. **笔顺 / 笔数算不算分**：默认 `shape 0.7 + order 0.3`、笔数宽松；要不要给"必须按笔顺"的道门符方
   `stroke_count_strict`（已有）之外的更严规则（比如必须从下往上）？
5. **容差与权重的可调范围**：我建议全开但都给默认值，最小配方只写 `pattern.strokes` + 一档；
   要不要连 `min_stroke_length` 也给作者调？
6. **材料位置**：符纸 / 符墨从**玩家背包**扣（我建议，走 `Cost[]`，工作站无内部库存，界面最简单）还是
   工作站内建槽位（要回到 `AuiContainerScreen` 的槽位对账）？符笔要不要参与（耐久 / 必须手持 / 只是配方原料）？
7. **方块本体**：单方块（我建议，先做最小闭环）还是照丹炉做多方块（成型判定 + 炉壁式部件）？
8. **入口**：只给工作站方块，还是同时给一条命令 / KubeJS 入口（`/talisman draw`）方便测试与脚本驱动？
9. **本地预览分数**：画的过程中显示实时正确率（体验好，但客户端要跑同一份算法）还是不显示（只有结算后给结果）？
10. **失败惩罚**：低于最低档（及格线）时只烧材料（默认）还是要产出"废符"（复用 `failure_outputs`）？
11. **参考符形**：默认显示淡影参考（`guide: true`），要不要允许配方关掉做成"背画"（`guide: false`）？

## 12. 不做 / 推迟

- **不用原版 recipe book 的 `has()` 解锁**：那要给每份配方配一个 advancement，而 `isSpecial()` 的配方本来就不进
  配方书；我们的解锁是"能不能在这座工作站上选"，与配方书是两件事。
- **不做符形图片比对**：要读贴图 / 像素（服务端没有画布），收益不如折线，而且会让"作者写符形"变成"作者画 PNG"。
- **不做自由涂鸦的存档 / 导出 / 分享**。
- **不做多方块工作站**（先单方块；真要做按 §11 问题 7 另开一节）。
- **不做笔画签名 / 防重放**：见 §10。
- **不新增"威力数值"字段**：见 §5.2。

## 13. 验证方式

1. **编译三连**：`compileJava` + `compileTestModJava` + `processTestModResources`。
2. **算法腿（可无头，写在 `/mxt_test talisman` 上）**：固定输入断言 `accuracy` 与判档——
   完美复刻（≈1.0）、整体平移一个容差（应显著掉分但不为 0）、缺一笔、多一笔、整张乱涂（`prec` 低）、
   只画一笔的一小段（`cover` 低）、笔数不等时 `stroke_count_strict` 两种取值。
3. **实机（要先问）**：画一笔成符 / 失败；页面刷新后能继续画；GUI scale 1、3、6 下坐标对得上（AUI 文档提醒
   "GUI scale ≥ 6 时 MC GUI 坐标与文档坐标会分叉"）；材料不足时列表灰掉；两个玩家同时用同一座工作站互不干扰；
   关界面 / 断线后会话不残留。
4. **文档同步**：`docs/数据包格式.md` 新增 `mxt:talisman_drawing` 一节（挨着 `### mxt:alchemy`，第 2159 行附近）
   + `### talisman`（第 2868 行）里补一句"工作站产出"；`docs/guide/play/items.md`（物品与组件）与
   `docs/guide/datapack/` 对应页；两份 README 的完成度表；**文档站仓库中英各一份**；编辑器 schema 重新生成。

## 14. 被否决 / 备选方案的对比（留档，免得下次重新讨论）

| 方案 | 为什么否掉 |
| --- | --- |
| 符形存数据包注册表（`talisman_pattern`）而不是配方 | 用户明确要"走原版配方系统"；而且符形与"消耗什么、产出什么、什么条件能选"是同一件事的三面，拆两张表会出现两处真值 |
| 客户端读配方拿符形 | 26.1 客户端没有配方表（§3.1），做不到 |
| 客户端算分、服务端信 | 直接可作弊；且算法一旦两端各写一份迟早漂移 |
| 页面 JS 采集笔画 | 刷新清状态 + 要跨语言传点（§3.2/§3.3）；Java 侧已经在同一个进程里，没有理由绕一圈 |
| 用 `<svg>` / 贴图当符形 | SVG 无渐变 / 变换 / 文本，且比对要栅格化；贴图比对要服务端读像素 |
| "威力"做成新组件 + 新公式变量 | 与 `capacity` / `costs` / `durability` 三个既有出口重复，且让"同一份定义两种威力"变成两组真值 |
| 符纸 / 符墨做成工作站内部库存 | 多一套槽位对账与容器同步；背包扣费已经是全仓统一的 `Cost` 形状 |
| 零槽位菜单改纯 `Screen` + 服务端按玩家记会话表 | 会话的过期 / 登出 / 换维度清理要自己补，且"还在不在界面上"退化成距离判定；菜单的 `removed` 与 `stillValid` 是现成的（§6） |
