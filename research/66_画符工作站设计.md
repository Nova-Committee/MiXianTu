## 0. 最终主设计（一句话）

工作站**展示符形**（默认描红：**浅黄纸底、红笔画**——两个颜色由配方给，§8.3）→ 玩家在纸面上**誊写** → **服务端**用唯一一份算法算
**完成度**（`completion`）→ 完成度决定**是否成功**（及格线 = 最低档），并且**它本身就是产物公式里唯一的数值**
（注入的变量名 `percentage`，`0~1`；没有"再映射一层威力"这回事，第九问，§5.2）；**画出来的是哪一张符**
由配方顶层的 `talisman` 点名（`mxt:talisman` 注册表，**一份符方一种符**），画得更好的差别落在**命中档的品质 /
耐久 / 灌注 / 额外产物**上（§5.1 / §5.3）。
判分口径：**位置与大小不判**（平移 + 缩放归一化），**朝向要判**（旋转不归一化、要扣分）；笔画**逐笔上报**
（服务端收一笔、按这一笔的长度**从笔上扣一笔颜料**），玩家点左栏的**提交**按钮时再把**整幅图案**发一次给服务端对账、
判分，然后把**产物直接放进界面那一格**（§6.1；关界面时它跟着那一格回玩家背包）；**两笔之间有最小间隔**（默认 0.3s，可调）当反作弊（§6.3 / §7）。
纸面是 **9:21 的竖长条**（与符箓本体同比例，§3.6）；材料从**界面里那一格**出（**菜单自己的临时格**，照工作台：
关界面时格子里剩下的直接回玩家背包，2026-10-02 第三修，§6.2）
（**默认就扣符纸槽里的 1 张符纸——配方里不用写**，`costs` 只写额外的，第八问，§4.2 / §6.4；
**颜料不进 `costs`**、站内也没有它的槽位，只靠蘸料手势加进笔里，§6.5）；
**符笔提在光标上**（原版容器界面里"鼠标上那一份临时堆"，`AbstractContainerMenu.getCarried()`）——
`mxt:talisman_brush` + `mxt:cinnabar`（朱砂）**合成**加颜料，绘制时由服务端按画出来的长度**逐笔从那一份上扣**（规格见 §6.5）。
左栏只有**提交**与**取消**两个按钮（§8.5）；开画时取走的东西（默认那张符纸 + `costs` 额外项）在两个出口的处置是
**画过就没了**（关界面与取消都走判失败那条路，跑配方的 `failure_action`），**一笔都没画时不算**、会放回那一格
（§6.4）。

范围：**符方走原版配方系统**（`Recipe` / `RecipeType` / `RecipeSerializer`，照 `mxt:alchemy`），**不是**新的数据包
注册表；符形、容差、判分参数、判档表都写在配方 JSON 里，**判分参数（`judgement`）与结算（`result`）分两块**
（第五问拆开：前者连客户端预览都要，后者只有服务端读，§4.2）；**结果本体是顶层 `talisman`**，引用 `mxt:talisman`
注册表，**配方的名字与描述也走那份定义**（第六问，§4.2）。

## 2. 名词

- **符方**：一份 `mxt:talisman_drawing` 配方。**符形**（pattern）是它的字段之一。
- **符形**：若干条**折线笔画**（归一化坐标）+ 容差，工作站里**展示给玩家照着写**的图案。
- **纸面**：界面中间那块画布区域，**9:21 的竖长条**（§3.6），叠着"参考层"与"墨迹层"（§8.2）。
- **誊写**：玩家用鼠标在纸面上照着符形描一遍。**位置与大小不判**（§4.3 第 2 步的归一化吸收：画在纸的哪一处、
  画多大都不影响），**朝向要判**（转过来要扣分）。
- **完成度** `completion ∈ [0,1]`：誊写与符形的吻合程度，**服务端算的唯一一份**（§4.3）。**字段**与代码里的名字是
  `completion`（初稿里的 `accuracy` **改名**，因为用户口径就是"完成度"；配方与代码都还没落地，改名零成本）；
  **注入公式的变量名是 `percentage`**（用户 2026-10-01 第四问指定，见 §5.2）。
- **判档**：配方里按 `min_completion` 排的档位表（`result.grades`），命中哪一档就按那一档的
  **品质 / 耐久 / 灌注 / 额外产物**产出（**档位不再点名符箓定义**，见下一条）。最低档就是及格线。
- **结果 / 出什么符**：配方**顶层** `talisman` 指向的那一份定义（`mxt:talisman` 注册表）。产物就是它的载体、
  名字与描述也是它的（§4.2）。**一份符方只出一种符**：想要"下品 / 常品 / 完美"三种不同定义，就写三份符方
  （各自的 `unlock_condition` 与及格线）。
- **威力**（第九问口径）：**不是一个单独的数值**——这张符多强由顶层点名的 `talisman` 定义写死
  （`abilities` / `capacity` / `durability`），而"画得多准"以**完成度本身**（公式变量 `percentage`，`0~1`）
  直接进各字段的公式。用户原话里的"根据完成度计算威力"就是这一条（§5.2）。
- **颜料**：**符笔自己带的一口存量**（单位＝点，1 点 ＝ 1 像素弧长），不是会被消耗掉的物品堆；绘制时**逐笔按这一笔的长度从笔上扣**（§6.5）。
  `mxt:cinnabar`（朱砂）是加料的原料；**蘸料**（光标提着笔对颜料物品点一下，哪里都行，§6.5）把一份朱砂换成一份颜料加进笔里。
  **「墨迹层」是纸面上画玩家笔画的那层 canvas**（§8.2），与颜料是两件事，别混。
- **蘸料**：给符笔加颜料的那一步——**光标提着符笔，对着一格颜料物品点一下**（左键右键都算，哪个容器都成立），颜料按份累加（§6.5）。
- **持笔 / carried（光标上那一份）**：用户口径里的"**拿着符笔**"指的是**把符笔提在光标上**——原版容器界面里那份
  "鼠标上的临时堆"（`AbstractContainerMenu.getCarried()`，两格之间转移物品时临时放东西的那一份），
  **不是快捷栏、也不是主手**。它是服务端权威的一份真实堆，客户端有一份完整同步副本（§6.2 末尾）。
  把笔**放进任何槽位**（或丢出去）就是"放下笔"，那一笔之后就不能再画了。
- **会话**：一位玩家在一座工作站上的一张纸——从点选符方（付材料）到提交或放弃。

## 3. 六条硬约束（形状是被它们定下来的）

1. **26.1 的客户端没有配方表。** `ClientboundUpdateRecipesPacket` 现在只带 `RecipePropertySet` 与石切配方，
   客户端手里是 `ClientRecipeContainer(Map.of(), SingleInputSet.empty())` + 只装"已解锁显示"的 `ClientRecipeBook`。
   仓库里的先例也是这么写的：所有 `getRecipeFor` 都走 `level.getServer().getRecipeManager()`，`AlchemyFurnaceView`
   的类注释就是"客户端只画，绝不重算配方"。⇒ **符形必须由服务端推给客户端**，而且**只推给正在这张纸上写的那个人**
   （符形是几十上百个点，塞进配方就等于随配方广播给所有人）。
2. **画符界面必须能拿到逐点鼠标输入，而 AUI 的 canvas 在 Java 侧就够用。** 核过 1.2.5：`<canvas>` 有
   `@ElementRegister`，解析 / 插入 DOM 时 `Element.init` 会把它升级成 `com.sighs.apricityui.element.Canvas`；
   `width/height` 属性是**位图**尺寸、CSS 是显示尺寸；Java 侧可以直接 `getContext("2d")` 画，也可以直接
   `canvas.getSurface()` 拿 `BufferedImage`；Java 侧 `element.addEventListener("mousedown", e -> ...)` 拿到的
   `MouseEvent` **自带 `offsetX/offsetY`（相对该元素的文档坐标）与 `buttons`**。⇒ **笔画采集放 Java，页面不写 JS**。
3. **刷新会清空 canvas 与 JS 状态。** 热重载 / `document.refresh()` 重建 DOM，位图随之清空，JS 变量与监听器全失效。
   ⇒ 采集与重绘都由 Java 持有（**点列在客户端 Java 侧留一份，同时逐笔上报给服务端**，§6/§7），挂在既有的
   "按 `Document.getRefreshGeneration()` 重绑"机制上（`AuiWrappedScreen.auiRebind` 那套）：重绑后按手上那份点列
   **重画**，玩家写到一半的符不会因此消失；两边对不上时结算是过不去的（§10）。
4. **canvas 很贵，而且要 1:1 画。** `renderOperation(action)` 会把**整张表面**标脏；1.2.5 另给了两个省钱的入口：
   `renderOperation(action, dirtyBounds)` 只标这一块脏、`clearSurfaceRect(...)` 是清一块的快速路径，而 `syncTexture`
   只把**脏区并集**重传给贴图。最后那张四边形是 `LINEAR` 采样。⇒ 只画**增量**（收到一段画一段）**并把这
   一段的矩形交出去**，整层重画只留给"真的要抹掉"的场合；位图尺寸 = 显示尺寸，别每帧整图重绘。
5. **判分在"归一化坐标系"里做：平移与缩放要做对齐，旋转不做**（用户 2026-10-01 拍板）。
   DTW.md 的平移（质心）与缩放（RMS）归一化**采纳**——画在纸的哪一处、画多大都**不判**（鼠标手绘的位置与大小
   本来就会漂，符形是"图形"而不是"纸上的某个位置"）；**旋转搜索不采纳**——朝向是符箓的语义（符头符脚、正倒），
   转过来**要扣分**（逐条理由见 §4.4）。
   ⇒ 判分前把两边都归一化（参考侧预计算并缓存），距离在归一化单位里算；位图尺寸只用于显示与采点换算。
6. **纸面是 9:21 的竖长条，界面按物品槽宽分栏**（用户 2026-10-01 定，同日给了草图）：符箓本体就是竖长条，纸面与它
   同比例——**画布固定 `90 × 210`（9 : 21），不可配**（第八问把 `canvas` 字段整个去掉；它是右栏 5 格宽 × 纸面
   高度的必然结果，Java 侧一个常量，§4.2 / §8.1），这样贴到物品贴图上不会变形；配方里的
   `[u, v]` 因此是"3 : 7 的比例空间"（`u` 按 90、`v` 按 210 换算）。布局按**物品槽宽**排（1 格 = 18px）：
   **左栏 4 格宽（72px）**＝符方选择 + 操作按钮 + 站内一格符纸（颜料槽 2026-10-02 当天删掉），**右栏 5 格宽（90px）**＝绘制区域＝纸面 **90×210**
   （顶满区域，与位图 1:1，§3.4），底栏是玩家物品栏（9 格宽 = 162px）。面板因此是 **178×306**，逐像素见 §8.1。

### 4.2 字段口径

> 例子里**没有 `costs`**：**默认那条成本（站内槽里的 1 × `mxt:blank_talisman`）由配方类型自己扣**，写不写 `costs`
> 都存在、也删不掉（第八问）；`costs` 只用来**加额外的**消耗。
> 例子里**没有 `judgement`**：这一块**整块可选**，不写就是表里那套默认值（**作者基本不用碰它**）。
> 例子里也**没有墨**：颜料是**符笔自己的存量、逐笔按长度扣**（§6.4 / §6.5），不是一个由配方写死的数量，所以不进 `costs`；
> `costs` 只放符纸这类固定消耗。"这一笔还画得动吗"由**光标上那支笔还剩多少颜料**回答（开画只要求符纸够、且光标上提着一支还有颜料的符笔）。

配方分五块，各答一件事（**第五问把判分与结算拆开、第六问把结果提到顶层、第八问砍掉"作者不该想的东西"**）：
`talisman`＝**出什么**、`costs`＝**花什么**、`pattern`＝**画什么**、`judgement`＝**怎么判**、`result`＝**判完给什么**；
**2026-10-02 第五次修正**另加两个只改纸面观感的颜色字段（`background_color` 纸底、`foreground_color` 笔画）。
**最小配方只需要 `talisman` + `pattern.strokes` + `result.grades`（一档）** —— 其余全有默认值，画布尺寸更是连字段都没有。
顶层与 `pattern`：

| 字段 | 必填 | 口径 |
| --- | --- | --- |
| `talisman` | 是 | **这个符方的结果本体**：`Talisman.CODEC`（`RegistryFixedCodec` 的 `Holder`）指向 `mxt:talisman` 注册表里的一份定义；命中任意一档产出的就是它，写进组件 `mxt:talisman`（`TalismanComponent`）。**一份符方一种符**——要"下品 / 常品 / 完美"三份不同定义就写三份符方（§5.2）。写错 id 会**加载期报错**：配方解码带 `RegistryOps`（`RecipeManager.fromJson` → `registries.createSerializationContext(JsonOps.INSTANCE)`），`RegistryFixedCodec.decode` 查不到就返回 `Failed to get element <id>`，整个文件加载失败——属"定义写错必须报错"那一类 |
| `unlock_condition` | 否 | `EntityCondition.optionalCodec("unlock_condition")`；缺省 = 人人可选。**每次开界面现算**（§11 问题 2） |
| `costs` | 否 | `Cost.LIST_CODEC`，**只写"额外"消耗**（第八问）：**默认那条成本是配方类型自己扣的——界面那一格里的 1 × `mxt:blank_talisman`**，配方写不写 `costs` 都存在，也**删不掉/改不掉**（想要两张符纸就在 `costs` 里再写一条 `mxt:item` 的符纸）。付款通道：**物品类成本（`mxt:item`）从界面那一格扣**（不是玩家背包，§6.4 的容器通道；那一格是菜单自己的，关界面就回背包），其余类型（`mxt:resource` / `mxt:aura` / `mxt:js`）照 `CostTransaction` 的既有规则由**玩家**付；取走时机与结算跟默认那条一样（开画时取走占住，离开会话时按画没画过结算，§6.4）。**颜料不进这里**——它扣的是符笔自己的存量（§6.4 / §6.5）。**那一格的 `mayPlace` 只认符纸**，所以 `mxt:item` 条目实际上只能写"符纸"（写别的会永远付不出、整份符方永远灰着）；那一格**收一整叠**符纸，就是为了让"两张符纸"这种写法真的付得出来（§6.2） |
| `pattern.tolerance` | 否 | **判分容差**，`> 0`（写了才校验），**缺省 `0.06`**（第八问：这个数对作者太难解释，先给一个能用的默认值）。口径是**画布高度的比例**：`tol_px = tolerance × 210`（`0.06 → 12.6px`），再按参考点云的 RMS 半径换算成归一化单位 `tol_norm = tol_px / rms_ref`（`≈ 0.2`，缩放归一化之后两边都是参考的尺度）。它同时喂 RDP 阈值（本体常量 `SIMPLIFY_EPSILON × tol_px`，那个系数不是字段，见下面 `judgement` 一节）与"闭合笔"判据（`2 × tol_px`） |
| `pattern.guide` | 否 | **参考层怎么显示**，默认 **`fade`**（第八问）＝半背临：起笔后参考层淡到约 `0.15`，停笔 2 秒回到 `0.35`；`always` = **描红**（一直显示）；`none` = **背临**（不画） |
| `pattern.show_order` | 否 | 默认 `false`；`true` = 在每笔起点画一个小点与笔序号（帮玩家记笔顺，与 `guide` 取哪一档无关） |
| `pattern.strokes` | 是 | **符形本体**：每笔一条折线，点是 `[u, v]`，`[0,1]²` 内、有限；至少一笔、每笔至少两点。**画布尺寸不可配**（第八问）：固定 **90 × 210**（右栏 5 格宽 × 纸面高度，9 : 21，§3.6 / §8.1），是 Java 侧一个常量；`[u, v]` 就按它换算成采点坐标（`u` 按 90、`v` 按 210），**判分不碰这两个数** |
| `background_color` | 否 | **纸面底色**（`MiscCodecs.RGB_COLOR`），缺省 **`#FFFE85`（浅黄）**。屏幕在绑定时把它写成 `#paper_frame` 的内联 `background-color`：`theme.css` 只留纸框描边，**这个颜色只有一个来源**（§8.2） |
| `foreground_color` | 否 | **玩家笔画（墨迹层）的颜色**，同一个 codec，缺省 **`#FF0000`（纯红）**。**参考层不跟它走**——那一层是淡褐常量，同色就与笔画分不开（§8.2 / §8.3） |

**画折线有工具**：`tools/talisman_strokes.html`（浏览器里直接打开的单文件编辑器，**只负责折线部分**）按同一块 90 × 210 画布与 `[0,1]²` 的写法画线，复制出来就是 `pattern.strokes`，并会先报出四种加载期会被拒的形状（单点笔、笔数超 256、一笔超 4096 点、所有点重合）。

**配方不声明 `name` / `description`**（第六问）：符方列表的条目名、产物 tooltip 里那条符箓名、以及将来任何
"这个符方是什么"的地方，一律走**那份 `talisman` 定义**——
`DefinitionText.name(holder, "talisman")`：定义自带 `name` / `description` 就用它（`Talisman` 实现 `NamedDefinition`），
省略时按 `ContextNameCodec` 的自动键 `<类别>.<注册表命名空间>.<id>` = **`talisman.mxt.<命名空间>.<路径>`**。
名字只有这一个来源，**别在配方里再声明一份**（会与定义打架，重命名定义时也漏改）。列表包里的名字由**服务端**算好再发——
客户端没有配方表（§3.1），它不知道这个符方指向哪份定义（§7）。

**`judgement`：判分参数（整块可选）。** 唯一消费者是 `TalismanDrawingScorer`（§4.3）——**这一块里没有一个字段影响产物**，
改它只动完成度；客户端算本地预览用的就是这一份（`preview: false` 时连参数都不下发，§8.7）。
**表里每一行都有默认值，所以 `judgement` 整块可以不写**（codec 用 `optionalFieldOf`，缺省 = 这套默认值）；
默认值凑成一份好记的预算：**形状项写死 `1.0`（没有字段），方向 / 拓扑 / 笔序各 `0.25`**，四项加起来最坏 `1.75`
（`completion` 下限 ≈ `0.17`，由最低档的及格线决定成败）。
**这一块只剩六个键**（第十一问）：预处理里那两个数——**重采样步长与 RDP 阈值系数**——**不是字段**，
是本体常量 `RESAMPLE_STEP = 2.0`（像素）与 `SIMPLIFY_EPSILON = 0.5`（× 容差），与画布常量 `90 × 210` 放在同一侧。
理由：这两个数作者几乎不可能调对，开成字段只会给出"看着能调、其实一调就悄悄变差"的余地；`sigma` 与三个权重
才是真正决定手感的旋钮，留给他们。**配方里写了这两个键按房规静默忽略**（`RecordCodecBuilder` 不认识未知键、
不报错也不生效），所以老包搬过来不会报错、只是那两个键不再生效。
**这些数是几何推算的初值**：推导过程、实机标定结果与实测分布表属于**实现完成后的技术细节文档**（§15），
配方里与代码注释里都不解释。

| 字段 | 必填 | 默认 | 口径 |
| --- | --- | --- | --- |
| `judgement.sigma` | 否 | `1.0` | 完成度映射的宽容度，`> 0`。**唯一的手感总旋钮**：`D_total = 1` 大约是"少画三笔中的一笔"或"普遍偏出一个容差"，映射成 `0.37`（单位口径见 §4.3 第 6 步） |
| `judgement.direction_weight` / `topology_weight` / `order_weight` | 否 | `0.25` / `0.25` / `0.25` | 三个辅助项的权重，都 `≥ 0`。**等额**是有意的：三项各答一件事、没有谁该比谁低，形状项（固定 `1.0`）仍然是主项。三个都为 0 时只剩形状项（允许，但加载期记一条 warn） |
| `judgement.stroke_count_strict` | 否 | `false` | `true` = 笔数不等直接让笔序项判满（§4.3 第 5 步）；默认宽容，留给"道门严苛"的符方 |
| `judgement.min_stroke_length` | 否 | `0.02` | 短笔门槛，**画布高度比例**（`0.02 × 210 ≈ 4px`）：这是"手抖点一下"的量级，短于它的整笔在计分前丢弃、总弧长也不够就按退化输入算 0 |
| `judgement.preview` | 否 | `true` | `false` = 客户端不算本地完成度（§6.3 的收紧旋钮之一，§11 问题 3）。**实现口径**：判分参数照发（多几个字节），客户端拿 `preview` 自己决定算不算——不为它把一个必填字段改成可选 |

**`result`：结算。** 拿到完成度之后才有意义——判档、写产物、跑动作；这一块里的 `NumberProvider` **都直接读
`percentage`（完成度，0~1）**，没有第二层映射（第九问）。
**整块只有服务端读**（客户端看到的完成度来自结果包，§8.6 / §8.7）。**档位不点名符箓定义**（那是顶层 `talisman`
的事），它只决定**品质 / 耐久 / 灌注 / 额外产物**与及格线。

| 字段 | 必填 | 口径 |
| --- | --- | --- |
| `result.grades` | 是 | 至少一档（可写一档 `min_completion: 0` = 必然成功，见 §11 问题 17）；`min_completion` 必须**唯一且升序**（加载期 `.validate` 拒绝重复与乱序）；最低档即及格线 |
| `result.grades[].quality` | 否 | `ItemQuality.CODEC`；写了就用 `ItemQualityService.set` 写组件，不写就落到**顶层 `talisman` 定义自己的 `quality`**——这是"画得更准 → 品阶更高"的主要旋钮 |
| `result.grades[].max_damage` | 否 | 覆盖载体耐久上限（走 `TalismanService.applyDurability` 的同一形状）；`NumberProvider`，可以读 `percentage`（完成度） |
| `result.grades[].charge_ratio` | 否 | `NumberProvider`，**产出时灌注的比例**，`[0,1]`，**默认 `0` = 不灌**（第七问：没有 `charge` 开关，就靠这一个字段）。缺省时产物载体上那口 `mxt:spirit_storage` 是空的，与 `/talisman give`（不带 `charged`）拿到的东西同形；写了正数就按 `TalismanService.capacity` 灌（与 `/talisman give charged` 同一实现），`"0.5 + 0.5 * percentage"` 就是"画得越准灌得越满"。落到整单位的口径（本稿定，可推翻）：每个 aura 条目灌 **`ceil(units × ratio)`**，与 `TalismanService.capacity` 自己"向上取整到整单位"同一套；**算出来 0 就一项都不灌**（照 `TalismanCommand.charge` 的 `if (units > 0)` 写，不白调 `insert(0)`）。结果 clamp 到 `[0,1]`，非有限值记一条 warn 并按 `0` 取——语义是"给多少灵气"，失败就该少给而不是白送 |
| `result.grades[].outputs` | 否 | `ItemStackTemplate` 列表，额外的产物 |
| `result.failure_outputs` | 否 | 默认空 = 只烧掉材料 |
| `result.success_action` / `result.failure_action` | 否 | `EntityAction`，成功 / 失败各跑一次（反馈、统计、解锁后续都用现成动作） |

**加载期校验**（`.validate(...)`，房规：空表 / 乱序 / 重复要拒收）：`strokes` 非空且每笔 ≥ 2 点、点有限且在 `[0,1]`、
写了就 `tolerance > 0`（缺省 `0.06`）、`sigma > 0`、
`result.grades` 非空且 `min_completion` 唯一升序、
符形点云的 RMS 半径 > 0（所有点重合的符形没有意义，§4.3 第 2 步要拿它做分母）、**各消费公式**（`max_damage` /
`charge_ratio` / 两个 action 里的 `NumberProvider`）出现的变量名
要么是注册表变量要么是 `percentage`（白名单，别让写错的公式静默变 0）。
**预处理那两个数已经没有可校验的字段**（第十一问）：`RESAMPLE_STEP > 0` 与 `SIMPLIFY_EPSILON ≥ 0` 由常量自己保证，
配方里写了也只是被忽略的未知键。
**"画布尺寸"那两条校验随字段一起消失**（第八问）：尺寸是常量 `90×210`，配方的 `[u, v]` 只在 `[0,1]²` 里被检查。
**"至少一条物品消耗"这条校验已经作废**（第八问）：默认那张符纸由配方类型保证，`costs` 为空是正常配方。

**默认成本与站内槽的 `mayPlace` 是同一个物品**（`mxt:blank_talisman`，§6.2）：两处写岔会出现"放得进去却扣不动"
或者反过来的死锁——实现时让它们读同一个常量，别各写一份 id。

`result` 是**必填块**（`result.grades` 至少一档）：上一稿那种把档位与产物写在 `judgement` 里的配方会**在加载期报缺字段**，
而不是静默"画出来什么都没有"（`judgement` 里的未知键仍按房规静默忽略，所以别指望它报错提醒你搬字段）。
顶层 `talisman` 同样是必填（没它就不知道画出来是什么），而**旧稿写在档位上的 `talisman` 键按房规静默忽略**——
所以老包搬过来时**不会**报"档位上多了个键"，只会因为顶层缺 `talisman` 报错（缺字段在 codec 这一层是硬的）。

两处形状以代码为准，别照抄旧写法：`mxt:item` 的字段是 **`items`**（`ItemCost.CODEC` 读 `ItemMatcher` 的条目表，
裸物品 id / `#标签` / 类型化条目都收），不是 `item`；`mxt:realm` 的字段是 **`realm`** + 可选 `comparison`
（默认 `exact`，另两个取值 `at_least` / `at_most`）+ 可选 `min_minor_stage`。`Cost` 的 `{"id": ..., "amount": ...}`
简写只等于 `mxt:resource`，物品消耗不能这么写。

### 4.3 算法（唯一实现：`runtime/talisman/TalismanDrawingScorer`）

纯函数、只读、无副作用，common 侧；**客户端本地预览与服务端判分是同一份实现**（§8.7），参数也从同一个 payload 来。
它的输入**全部来自 `judgement` 那一块**（§4.2）加 `pattern` 的 `tolerance`，再加三个**本体常量**（画布、重采样步长、
RDP 阈值系数——常量跟着代码走，不进 payload）；`result` 一个字段都不读。
参考侧（像素点、重采样点云、简化关键点）按配方**缓存**，玩家侧每次提交只算一次。

```
输入：pattern（归一化点）、本体常量（画布 90 × 210、重采样步长 RESAMPLE_STEP = 2.0、RDP 阈值系数
      SIMPLIFY_EPSILON = 0.5，§4.2）、tolerance（缺省 0.06）、四个权重与 sigma、
      min_stroke_length、stroke_count_strict、玩家笔画（位图坐标系；判分前归一化）
输出：completion ∈ [0,1] + 各分量（cover / precision / direction / topology / order）+ 退化与回退标志
```

**第 0 步：退化输入。** 玩家总点数 < 2、或总弧长 < `min_stroke_length × 高` → `completion = 0`（不抛异常、
不记错误日志；这是"玩家还没画完就提交"的正常情况）。

**第 1 步：预处理**（参考与玩家**同一套**；DTW.md §1 的口径）：

1. **抽稀**：丢弃与上一个保留点距离 < 1px 的点（鼠标事件的重复点）。
2. **丢短笔**：玩家笔画弧长 < `min_stroke_length × 高` 的整笔丢弃（手抖点一下）。
3. **重采样**：每笔按弧长等距重采样，点数 `S = clamp(round(长度px / RESAMPLE_STEP), 16, 256)`（快慢不影响判分）。
4. **关键点**：RDP 简化（阈值 `SIMPLIFY_EPSILON × tol_px`）得到角点；同笔首尾距离 < `2 × tol_px` 记为**闭合笔**
   （这一步在**像素空间**做，所以用 `tol_px`；归一化在第 2 步）。
5. **交点分割**：线段两两求交（先按 AABB 预筛），在交点处把两条线段各切一刀，同时数出交点数。
6. **三份表示**：① **线段集合**（算距离、算方向、算拓扑）② **采样点云**（算 Chamfer）③ **简化关键点图**
   （算拓扑的节点数；**图匹配第一版不做**，见 §4.4）。

**第 2 步：归一化（平移 + 缩放，不做旋转）**（DTW.md §2；旋转为什么不做见 §4.4）：

1. **平移**：分别算出参考点云与玩家点云的质心，各自平移到原点。
2. **缩放**：算出各自到质心的 RMS 距离，各除以它，使尺度归一（此时两边都是"尺寸 1"）。
3. **容差跟着换算**：`tol_norm = tolerance × 高 / rms_ref`（参考侧预计算并缓存）。
4. **不做旋转**：不搜索角度、也不对齐主方向（DTW.md 自己也说了不要用 PCA，对称图形会有歧义）；
   朝向差异**全部**落到第 3 / 4 步的距离与方向项上。
5. **退化**：玩家点云的 RMS ≤ `1e-6`（只点了一下、或所有点重合）→ `completion = 0`（与第 0 步同一出口）。

参考侧的第 1～2 步（重采样、归一化、容差换算）**按配方缓存**，玩家侧每次提交现算。

**第 3 步：逐点误差。**

```
d'(p, 对方) = 到对方【最近线段】的距离，**在归一化坐标系里量**（不是到最近采样点，否则笔的快慢会改变分数）
e(p)       = min(1, (d' / tol_norm)²)      ∈ [0,1]，容差之外饱和为 1
```

平方是**本体口径**（不开放给配方）：让"贴着画"与"擦着容差画"拉开距离。归一化之后"偏差"是**相对参考尺寸**量的
（画得小不会因此更容易、也不会更难）：容差是画布高度的比例，而参考点云的半径大约是 `0.3 × 高`，所以
`tol_norm ≈ tolerance / 0.3 ≈ 0.2`——**与画布开多大无关**。以 90×210 为例：`tol_px = 12.6`、`rms_ref ≈ 63`，
2px / 5px / 12.6px 的偏差换算过去是 0.032 / 0.079 / 0.2，分别记 **0.03 / 0.16 / 1.0**。
作者的两个旋钮是 `tolerance`（缺省 `0.06`）与 `sigma`（缺省 `1.0`），不再多开；两者的实际手感要等
§13.2 标定，取值依据写进 §15 的技术细节文档。

**第 4 步：三项几何距离。**

```
覆盖  C = 1 - mean_{参考点} e(·, 玩家笔画)      （符形被墨迹盖住的程度）
精确  P = 1 - mean_{玩家点} e(·, 参考笔画)      （墨迹落在符形上的程度）
贴合  shape = 2·C·P / (C + P)                  （F1；C + P = 0 时 shape = 0）
D_shape = 1 - shape

方向  D_dir：参考点 p 的切线方向 vs 它在玩家笔画上最近点的切线方向，夹角折到 [0, π/2] 再除以 π/2；
             按 (1 - e(p)) 加权平均（离得远的点方向没有意义，不参与）；权重和为 0 时 D_dir = 1
拓扑  D_topo：五项计数——笔画数、端点数、交点数、闭合区域数（欧拉公式 faces = 边 - 节点 + 分量 + 1）、总长度；
             逐项 slack 软化（笔画数 0 / 端点 1 / 交点 0 / 闭合区域 0 / 总长度 5%），
             即 max(0, |a-b| - slack) / max(a, b, 1)，再按 0.15 / 0.25 / 0.25 / 0.25 / 0.10 加权

D_geo = D_shape + direction_weight × D_dir + topology_weight × D_topo
```

**位置与大小已经在第 2 步归一化掉了，所以这两项不惩罚它们；旋转没有归一化，朝向差异实打实进分**
（`D_shape` 会因为点对不上而掉、`D_dir` 会因为走向转了而掉）。

**为什么贴合项用 F1 而不是 DTW.md 的"两个方向相加 / 取平均"**：算术平均对"整张乱涂"太宽容——乱涂的覆盖很高、
只有精确掉下去，平均下来仍有 0.6 左右；F1 对两个方向的**失衡**更敏感，同一组输入下乱涂掉到 0.2 上下，
而"描得准"几乎不受影响：

| 画法 | C（覆盖） | P（精确） | 算术平均 | F1（本稿） |
| --- | --- | --- | --- | --- |
| 描红画准 | 0.95 | 0.95 | 0.95 | 0.95 |
| 少画一笔（三笔中缺一笔） | 0.66 | 0.97 | 0.81 | 0.79 |
| 整张乱涂 | 0.85 | 0.10 | 0.48 | 0.18 |

**第 5 步：笔序与笔数 `D_order`**（DTW.md 没有这一项，本稿自加——"誊写"曾经想按笔顺）：

```
逐笔贴合 pair(i,j) = 2·C(i,j)·P(i,j) / (C(i,j) + P(i,j))
                     C(i,j)、P(i,j) 与上面同形，只是把范围限制在"参考第 i 笔 × 玩家第 j 笔"
配对：把 n×m 的 pair 矩阵按**贪心取最大**摘出 min(n,m) 对（每笔只用一次），取这些对的平均
笔数相等：D_order = 1 - mean(pair)
笔数不等：D_order = 1 - mean(pair) × min(n,m) / max(n,m)
          stroke_count_strict = true 时笔数不等直接 D_order = 1
```

**这一项在 2026-10-01 手测后从"按先后配对"改成"按形状配对"**（用户点名："我描的很像了，但还是只有 76%"）：
按先后配对时，**同样的三笔换个顺序画就从 `0.93` 掉到 `0.80`**，而参考层默认**不显示笔序号**
（`pattern.show_order` 为假时上屏的只是一团淡影）——扣的是玩家看不见的东西。改成按形状配对之后，
"换个顺序"与"原顺序"得分**完全相同**；笔数不等（少一笔 / 多一笔 / 半途抬笔把一笔拆成两笔）照旧扣。
**仍然不做全局最优匹配**：贪心足够，`n`、`m` 都是个位数（§4.4），别为它引入匈牙利算法。

**第 6 步：总距离与完成度。**

```
D_total   = D_geo + order_weight × D_order
completion = clamp(exp(-D_total / sigma), 0, 1)
```

指数映射照 DTW.md §7，但 **`sigma` 的默认值不照抄**：DTW.md 的 0.15–0.25 是它自己那套 RMS 归一化距离下的口径，
我们的 `D` 是无量纲的"贴合距离"（各项都在 `[0,1]` 量级），所以默认 `sigma = 1.0`——`D_total = 1` 大约是
"少画三笔中的一笔"或"普遍偏出一个容差"的量级，映射成 0.37。

**首版预期分布**（90×210 画布（9:21）、`tolerance = 0.06`、**`sigma = 1.0`、三个权重各 `0.25`**，加上三个本体常量
（`RESAMPLE_STEP = 2.0`、`SIMPLIFY_EPSILON = 0.5`）——也就是**整块 `judgement` 不写**时的那套参数；
**实机后用 §13.2 的探针腿标定，这张表是实现时的期望值与回归基准，不是实测值**）：

| 画法 | 预期 `completion` | 说明 |
| --- | --- | --- |
| 照描红画准（平均偏差 ~2px） | 0.90–0.95 | 最高档（0.88）**可达** |
| 略有抖动（~4–5px） | 0.70–0.80 | 落到常品档 |
| 多画一笔 | 0.65–0.75 | `P` 掉、笔序项掉 |
| 少画一笔（三笔中缺一笔） | 0.58–0.70 | `C` 掉、笔数不等再扣 |
| 只描一半 | 0.45–0.60 | `C` 掉一半 |
| 整张乱涂 | ≤ 0.40 | F1 把 `P` 的塌陷放大（实测 `0.386`，比上一稿估的 `0.30` 高一点） |
| 把符形**转 15°** 的完美复刻 | ≤ 0.55 | **故意**：旋转不做对齐，朝向要扣分 |
| 画在画布的任意位置（含角落） | 0.88–0.95 | **故意**：平移已归一化，位置不判 |
| 画得比参考大 2× | 0.88–0.95 | **故意**：缩放已归一化，大小不判 |
| 画得比参考小到一半 | 0.80–0.95 | **实测 `0.886`**：RDP 与闭合笔判据按绝对像素算，半尺寸会把缓弯误判成闭合笔——见下面那两条不一致 |
| 空 / 单点 / 极短线段 | 0 | 退化输入 |

**这张表里的区间是给实现留的余量**：三个权重从 `0.30 / 0.20 / 0.30` 调成等额 `0.25` 之后，各项罚分略有挪动
（总预算 `1.80 → 1.75`，最坏情况 `completion` 从 `0.165` 抬到 `0.174`），区间本身吸收得下——**标定时以探针实测为准，
表是回归基准不是结论**。

**现状（2026-10-01 实测，`/mxt_test talisman` 的算法腿在专用服务端上打日志，一条腿跑全部用例）**——这就是上面那张表的实测对照，
"手描"两行是**合成的确定性手迹**（抖动 + 弧度 + 两端出头），用来把"人画的样子"与"各几何项扣多少"对上账：

| 画法 | completion | shape | direction | topology | order |
| --- | --- | --- | --- | --- | --- |

| 整体平移（+60, −40） | `0.998` | 1.000 | 0.006 | 0 | 0 |
| 放大 2× | `0.998` | 1.000 | 0.006 | 0 | 0 |
| 缩到 0.5× | `0.934` | 0.968 | 0.037 | 0.042 | 0.069 |
| 转 15° | `0.545` | 0.594 | 0.363 | 0 | 0.445 |
| 转 90° | `0.239` | 0.055 | 0.976 | 0 | 0.968 |

| 空 / 单点 / 全 NaN | `0` | —— | —— | —— | —— |

**同一天按实测做的两处调参**（详见 §13.3 手测记录）：① 第 5 步改成**按形状配对**——原来是按先后，导致"同样的三笔
换个顺序"从 `0.933` 掉到 `0.797`；② 交点数与闭合区域数**允许 ±1**——一条稍带弧度的忠实描红会丢掉"竖笔与斜笔
在顶上交汇"这一个交点，白扣 `0.125`；顺带让"整体平移/放大"从 `0.978` 回到 `0.998`（精确复制不该在拓扑项上丢分）。
两处都只动了"玩家看不见的东西"，少一笔 / 多一笔 / 乱涂的区分度没变（`0.818 / 0.677 / 0.398`）。

还有一处与上表**不一致，是设计口径本身的问题，不是实现的 bug**：**缩到 0.5× 只有 `0.934`**（上表写"大小不判、
0.88–0.95"）。原因是 §4.3 第 1 步的 RDP 阈值与闭合笔判据都是**绝对像素**（`6.3px` / `25.2px`），半尺寸的图里
示例第 2 笔首尾距离踩到闭合阈值，于是被判成闭合笔；±1 松弛之后它只影响端点/闭合那一项，罚分已经很轻，但根因
还在。要修只能改设计：**归一化之后再找角点与判闭合**，或者让这两个阈值随图形尺寸缩放。仍然没有**真人手感标定**：
`sigma`、`tolerance`、三个权重、`min_stroke_length` 都还是几何推算的初值。

档位阈值（`min_completion`）应当照着这份分布写：上表"转 15°"落在及格线附近是有意的——**整体画歪 = 下品符**，
要不要直接判失败由配方的及格线决定（也可以把最低档写到 0.55 以上让"歪"直接废掉）。

**第 7 步：输出。** `completion`、命中的档、以及 `C / P / D_shape / D_dir / D_topo / D_order`、简化后的关键点数、
是否闭合、是否触发退化——调试与探针用；客户端只拿 `completion` 做预览。

**性能与缓存**：玩家侧点数上限 4096（§10），重采样后 ≤ 数百点；单次判分是 O(参考点 × 玩家线段)，量级在 10⁵ 以内，
**一次结算算一次就够**（逐笔推进时只量这一笔的弧长用来扣颜料，**不跑判分**，§6.4）。参考侧的预处理**按配方缓存**（键 = 配方 id + 注册表实例，并在 `ServerCache.onDatapackLoaded`
里 `invalidate()`——房规：索引来自数据包的缓存必须在数据包重载时显式失效）。

> **实现现状（2026-10-01）**：落地时 `TalismanDrawingScorer` 是**无状态纯函数**，参考侧预处理**每调用一次算一次**（没有缓存）。
> 结算每张符只跑一次，客户端预览限流 200ms 也在这个量级里，所以先按"不缓存"发；**缓存是待办**，要加就按上面那条口径加，
> 别在别处再造一份参考侧数据。

### 4.4 与 `DTW.md` 的逐条对照

| DTW.md 的步骤 | 本稿 | 为什么 |
| --- | --- | --- |
| §1 预处理：去抖、重采样、RDP、合并端点、交点分割 | **采纳** | 手绘点列的固有噪声；交点分割让交点数/闭合区域可数 |
| §1 三份表示：线段集合 + 点云 + 关键点图 | **采纳（图只用来数节点）** | 距离用线段与点云就够；图匹配的收益见下 |
| §2 平移归一化（质心） | **采纳** | 鼠标手绘的位置本来就会漂；符形是"图形"而不是"纸上的某个位置"（用户 2026-10-01 拍板保留） |
| §2 缩放归一化（RMS） | **采纳** | 同上：大小不判，画大画小用同一把尺子量（容差 `tol_norm` 跟着换算） |
| §3 旋转搜索（粗搜 + 细搜） | **不采纳** | **用户点名"旋转需要扣分"**：符箓有正倒，转过来的符不是同一张符；手抖的几度偏差由容差吸收（要更严就把 `tolerance` 调小）。**"采纳平移与缩放、不采纳旋转"是本稿与 DTW.md 的唯一分歧点** |
| §4 对称 Chamfer | **采纳，合成改 F1** | 两个方向都要（§4.3 第 4 步），但算术平均对乱涂太宽容 |
| §4 方向一致性 | **采纳** | 抓"描成了另一条走向"（例如把弧画成了反向弧）；按 `1 - e` 加权，远离的点不参与 |
| §4 拓扑惩罚（笔画数 / 端点 / 交点 / 闭合区域 / 长度） | **采纳，软化口径更宽** | 断笔与手抖必然多出端点；slack 让它"多一个端点不判零分" |
| §5 图匹配增强（匈牙利 / 等价匹配） | **推迟** | 收益只在"交点 + 闭合区域密集"的图形上；实现成本与"两端必须同算"的代价不划算。口子先留成 DTW.md §5 的融合形式 `D_total = (1 - alpha)·D_geo + alpha·D_graph`（`alpha` 初始 0.3–0.5），触发条件是"实机发现纯几何分不开描歪的闭合符" |
| §6 线段匹配回退 | **部分采纳** | 逐笔 `pair(i,j)`（第 5 步）就是它的最简形态，用来做**按形状配对**；不做整体线段集的最优（匈牙利）匹配 |
| §7 `score = 100·exp(-D/σ)`、σ 可调 | **采纳形式，不采纳默认值** | 我们用 `[0,1]` 与 `exp(-D/σ)`（显示成百分比由界面做）；σ 的默认值跟着我们自己的距离单位（§4.3 第 6 步） |
| §7 不同复杂度图形用不同 σ | **采纳** | `judgement.sigma` 就是给作者的旋钮 |
| §8 返回分量与回退标志、退化输入返回 0 不崩、多画降分不归零、少画明显降分 | **采纳** | §4.3 第 0 / 7 步 + §13.2 的断言逐条钉住 |

### 4.5 判档

按 `min_completion` **从高到低**找第一个 `completion ≥ min_completion` 的档；**都没命中 = 失败**，也就是
**最低那一档的 `min_completion` 就是及格线**（只写一处，不另设一个全局及格线与它重复）。命中哪一档**不换符箓定义**
（定义固定是顶层 `talisman` 那一份），换的是**品质 / 耐久 / 灌注 / 额外产物**（§5.3）。

## 5. 完成度 → 是否成功 / 品质 / 产物数值

### 5.1 是否成功

- **成功** = 完成度落在任意一档里；**失败** = 低于最低档。
- 成功：把**顶层 `talisman` 那份定义**写进组件 `mxt:talisman`，再按命中档补上**品质 / 耐久 / 灌注 / 额外产物**，
  跑 `result.success_action`。
- 失败：跑 `result.failure_action`，给 `result.failure_outputs`（默认空 = 只烧掉材料，默认口径见 §11 问题 9）。
- 结算结果（完成度、产物的**品质名**、成功与否、产物）由服务端返回并显示（§8.6）；**客户端算的那份只用于预览**。
  （没有"档位名"这种东西了：档位不再点名定义，界面上显示的档次就是**产物的品质**，§8.6。）

### 5.2 产物数值：定义本身 + `percentage`

> **第九问把"威力"这一层去掉了**：原来 `result.power` 把完成度映射成一个叫 `power` 的变量、各字段再读它；
> 但所有消费者（耐久、灌注、动作）本来就可以直接读完成度，多这一层只是多一个变量名、多一份白名单、
> 多一处"两个数不一致"的可能。现在**完成度（`percentage`，0~1）就是那个数**。

1. **出什么符由配方顶层决定**：`talisman` 点名一份 `mxt:talisman` 定义（第六问），命中哪一档都产出它；
   "这张符本身有多强"写在这份定义里（`abilities` / `capacity` / `durability` / `costs`）——
   完全由数据包表达，本体不参与，**与完成度无关**。
   **完成度不换"哪一种符"**：一份符方一种符（要"下品 / 常品 / 完美"三份定义就写三份符方，各自的
   `unlock_condition` 与及格线）；画得更准的差别落在**品质 / 耐久 / 灌注 / 额外产物**上（§5.3）。
2. **完成度直接进公式**：唯一的注入变量是 **`percentage` ＝ 完成度**（用户指定的名字），上下文是
   `FormulaContext.of(player, Map.of("percentage", completion))`——基础上下文 + 这一个显式值。
   完成度本身已经 clamp 在 `[0,1]`（§4.3 第 6 步），**不再有第二层映射、也不再有第二次数值 clamp**。
   想做非线性就直接写在消费它的那个字段里：`"0.5 + 0.5 * percentage"`（线性）、
   `"percentage * percentage"`（罚手抖）、`"sqrt(percentage)"`（宽容）。
3. **消费者的完整清单**（别的地方读不到它）：
   `result.grades[].max_damage`、`result.grades[].charge_ratio`、`result.success_action` /
   `result.failure_action` 里的 `NumberProvider`。**`outputs` 读不到**——`ItemStackTemplate` 的数量是写死的，
   不是公式（要按完成度给不同数量就分档写）。
4. **不写进产物**：仍然**不新增任何"完成度 / 威力"组件**，也不给 `talisman` 定义开第二个数值入口——
   它是**结算那一刻的标量**，不是物品上的持久属性。**如果以后要"这张符打出去更强"，
   就必须把它落到物品上（组件或定义字段）**，那是另一次拍板，取舍见 §11 问题 15。
5. **与 `judgement` 的分工没变**：`judgement` 只装"喂给判分器的那几个数"，完成度是它的**输出**；
   `result` 里的公式只是**消费者**（§4.2）。

一句话：**完成度算出来的那个 0~1 数（`percentage`）直接喂给各字段的公式；这张符本身有多强则由配方顶层
点名的那份定义写死。**

### 5.3 品质与产物

- 品质：命中档的 `quality`（可选）→ `ItemQualityService.set(stack, holder)` 写组件 `mxt:quality`；不写则落到
  顶层 `talisman` 定义自己的 `quality`（`TalismanService.quality` 已经在读这条链）。**不在本体里造第二套品质表**。
- 耐久：`result.grades[].max_damage`（照 `TalismanService.applyDurability`）。
- 灌注：**只看一个字段 `result.grades[].charge_ratio`，缺省 `0` = 不灌**（第七问：没有 `charge` 开关）——
  不写它时产物载体上那口 `mxt:spirit_storage` 是空的，与 `/talisman give`（不带 `charged`）同形；定义里若写了
  `mxt:aura` 条目，玩家得自己**按住符箓**把灵气灌进去（`TalismanItem implements UseItemAuraAccess` →
  `SpiritChargeHold` / `SpiritChargeService`，一 tick 一单位）。写了正数就在产出时灌：量 =
  `TalismanService.capacity` 的整单位数 × 比例再向上取整（§4.2），与 `/talisman give charged` 的 `charge`
  循环是同一实现；`"0.5 + 0.5 * percentage"` 就是"画得越准灌得越满"。
- 额外产物：`result.grades[].outputs`；反馈：`result.success_action` / `result.failure_action`。

## 6. 运行流程、付款与扣除、会话

### 6.1 流程

```
右键工作站（服务端）
  → 算一次"此刻可选的符方"：RecipeManager 里所有 mxt:talisman_drawing
     逐个问 unlock_condition（EntityCondition.test(player, context)）+ **界面那一格里的材料够不够**（默认那张符纸 +
     配方 `costs` 里的额外项，§6.4）。**不要求笔在手**：颜料是逐笔扣的，笔在落笔那一刻才校验（§6.5）
  → player.openMenu(...)（方块自己给一个匿名 MenuProvider；菜单类型登记在 MxtMenus，客户端屏幕在
     MxtRenderers.registerScreens 里绑）
  → TalismanDrawingListS2CPayload(条目: id, 名字, 材料是否够)      ← 名字 = 那份 talisman 定义的名字，服务端算好

玩家点一份符方
  → TalismanSelectC2SPayload(recipeId)
  → 服务端校验：在可选列表里 + （没有进行中的会话，或那个会话**一笔都还没画**——那就当作换符方）+ 那一格材料够
  → 把**默认那张符纸 + `costs` 里的额外项**从那一格取走（`CostTransaction.plan → commit`，物品成本的付款者是
     那一格，§6.4）——格子随之空出来，这些东西由这个会话**占住**（别的菜单看不见它），离开会话时才结算
     （画过 → 判失败、材料不退；一笔没画 → 放回那一格，§6.4）。**换符方就是"结算掉这个没画过的会话（纸原样放回）
     + 开一个新的"**，所以落笔之前换是免费的；落笔之后服务端直接拒绝（换就等于把那一笔扔掉，§8.3）
  → TalismanDrawingStartS2CPayload(recipeId, 符形, 呈现方式, （preview 时）判分参数)
  → 进入誊写（**笔画只留在客户端，页面上一个字节都不发给服务端**）

誊写期间（每一笔一个包，§6.3）
  → 收笔 → Java 侧记点列、增量画墨迹层，并发 TalismanStrokeC2SPayload(recipeId, 这一笔的点列)
  → 服务端：记下这一笔 → 按长度**从会话锁定的那一份 carried 堆上扣颜料**（§6.4 / §6.5）→ 回"收下 / 拒收"（回执带上这笔扣了多少）；
     **过快**（与上一笔间隔 < 0.3s）、**颜料不够**、**光标上已经不是那一支笔了** → 拒收
  → 客户端收到拒收 → **把这一笔抹掉**（不抹掉的话结算对账必挂，§10）
  → 热重载 / 重绑：按本地那份点列重画（§3.3），不额外发包
  → 本地预览（可选）：用同一份算法算完成度给自己看（§8.7）
  （**没有"清空画布"这个动作**：左栏只有提交与取消两个按钮，§8.5）

玩家点"提交"（左栏两个按钮之一，§8.5）
  → TalismanSubmitC2SPayload(recipeId, 整幅图案的点列)          ← 整幅再发一次，用于对账
  → 服务端：**先对账**（与逐笔记录逐点比，§10）→ 对上了才量总长度、算完成度、判档（各字段公式直接读 `percentage`）→
     写符箓（顶层 `talisman` 那份定义 + 命中档的品质 / 耐久 / 灌注 / 额外产物）→ **直接放进界面那一格**（开画时纸已
     取走，格子是空的；关界面时它跟着那一格回玩家背包）→ 消耗掉那一张符纸 → 会话结束；
     对账失败 → 判失败（纸照样消耗）并记一条 warn
  → TalismanResultS2CPayload(completion, 是否成功, 品质名, 产物, 文案)

玩家点"取消"（左栏两个按钮之一，§8.5）
  → 结束会话并把界面重置回"未选符方"（纸面清空、结果区清空、列表恢复可选）
  → 画过 → 与关界面同一条路：**判失败**（`abandon` → `fail`，跑配方的 `failure_action`），回执是 ABANDONED；
     一笔没画 → 材料放回那一格，回执是 CANCELLED（§6.4）
  → **一笔都没画时"取消"是空操作**（按钮灰着，点了不结束会话、不动那张纸）

关界面 / 断线 / 换维度
  → AbstractContainerMenu.removed(Player) → 会话丢弃（画过 → **判失败**；一笔没画 → 材料放回那一格），
     然后把那一格里剩下的东西**整个交给玩家**（`clearContainer`，工作台式；§6.2 / §6.4）
```

### 6.2 会话归属与菜单自己那一格（硬约束）

两件东西分开记：

- **绘制会话**（选中的 `recipeId` + **占住的那一张符纸** + 有没有提交过）**挂在服务端菜单上**——两个玩家同时用同一座
  工作站时，谁在画哪张符互不干扰（纸也是他占着的那一张）。**笔画逐笔上报、服务端另存一份用于对账**（§6.3 / §7）。
- **那一格是菜单自己的临时格**（`new SimpleContainer(1)`，2026-10-02 第三修）：照原版工作台，**它跟着屏幕走**——
  方块实体整个没有了（`TalismanWorkstationBlockEntity` 删除、注册表条目删除），所以**不落盘、不共享、破坏方块也
  没有东西要掉**；关界面时格子里剩下的东西用原版的 `clearContainer` **直接回玩家背包**（这一句照
  `CraftingMenu.removed` 包在 `this.access.execute(...)` 里：客户端那份菜单拿的是 `ContainerLevelAccess.NULL`，
  它的 `evaluate` 恒返回空、永不执行 —— 所以扫格只发生在服务端）。
  **纸从这一格出，不从背包出**（用户 2026-10-01 拍板，取代初稿"背包扣费"的建议；第三修只是把这一格从方块实体
  搬到菜单，取料这一步一个字没改）。
  **墨槽在第二轮退出、笔槽在第三问退出**（颜料改成"笔自己的存量"、笔改成"提在光标上"，§6.5），
  那一行空出的格子里**2026-10-02 曾启用一格颜料槽，当天晚些又删掉**：蘸料本来就不挑槽位，那一格只是"给料
  安个家"，而服务端画符从不读它（§6.5 / §8.1）。空槽底下有一张符纸轮廓的贴图提示（§8.1）。
- 槽是**限定物品**的：那一格的 `Slot.mayPlace` 只认 `mxt:blank_talisman`，放错不收——它**就是默认那条成本的
  物品**（第八问；同一格、同一个常量）。
  **符方能点的条件是"默认那张符纸够 + 配方 `costs` 里的额外项也够"**，与笔、与颜料都无关；
  没有进行中的会话时这一格就是格里的实际内容，**有一个"一笔没画"的会话时算上它正拿着的那张纸**
  （换符方会把纸放回来，所以那时列表不能整片灰掉，§8.3），否则列表整体灰掉（§6.1）。
- **笔不在界面里、也没有笔槽**：用户 2026-10-01 第三问澄清——"**拿着符笔**"就是**提在光标上**的那一份
  （原版容器界面的 carried，两格之间转移物品时临时放东西的那个"鼠标槽位"，`AbstractContainerMenu.getCarried()`）。
  会话锁定的是**开画那一刻 carried 上的那一支**（按物品 + 组件身份比），之后**每一笔都要重新确认光标上还是它**；
  玩家把笔放进任何槽位、换成别的物品、或丢出去 → 后面每一笔都拒收（原因"笔不在光标上了"，§6.3），
  已画的与已扣的都不退。**"身份"按实现只能认到物品**：颜料正是那个要变的东西，所以逐笔扣完之后不可能再按
  "组件完全相等"去认它——`mxt:talisman_brush` 是唯一一支笔，按 `ItemStack.is(笔)` 认它就够，且它 `stacksTo(1)`（§6.5）。
- **carried 是服务端权威的一份真实堆，客户端有完整同步副本**（26.1 源码）：服务端改它之后，**最迟下一 tick**
  由 `ServerPlayer.tick` 的 `containerMenu.broadcastChanges()`（`ServerPlayer.java:610`）→
  `synchronizeCarriedToRemote()`（`AbstractContainerMenu.java:274-284`）→ `ServerPlayer.sendCarriedChange`
  （`:315-317`）发一个 `ClientboundSetCursorItemPacket`（**整份带组件**，`ItemStack.OPTIONAL_STREAM_CODEC`）
  → 客户端 `ClientPacketListener.handleSetCursorItem`（`:1436-1443`）直接 `containerMenu.setCarried(...)`。
  ⇒ **逐笔扣颜料不需要为本模块另写同步包**，客户端读自己的 `getCarried()` 就有最新颜料值（判据与颜料条都用它）。
- **关界面时笔不会消失**：`AbstractContainerMenu.removed(Player)`（`:598-616`）把 carried 交回
  ——正常关界面 → `placeItemBackInInventory` 回背包；玩家被移除 / 断线 → 掉在地上。颜料已扣的那部分照旧不退（§6.4）。

会话要有一个**生命周期出口**（关界面 / 断线 / 换维度都要丢掉），所以仍然用**菜单**：
`TalismanWorkstationMenu extends AbstractContainerMenu` 注册 **1 格（菜单自己的）+ 玩家背包 36 格**
（照原版 `addStandardInventorySlots`），`AbstractContainerMenu.removed(Player)` 正好是那个出口（会话判失败/退款 →
再 `clearContainer` 把那一格交给玩家），`stillValid` 自带"还在不在工作站旁"的校验。**菜单不再是零槽位**（初稿选
零槽位只是为了省掉槽位对账），所以 `AuiContainerScreen` 的槽位几何对账在这一页是**真需求**（§8.1）。

**备选（不选）**：纯 `Screen`（照 `MultiblockStructureScreen`）+ 服务端按玩家记一张会话表。省掉菜单，但会话的
过期、登出、换维度清理全要自己补，"玩家还在不在这个界面上"也退化成"离方块多远"。

**缓存的失效口径**（房规）：按类型索引配方（`getRecipes()` 过滤）的缓存、以及 §4.3 第 7 步的参考侧预处理缓存，
都要在 `ServerCache.onDatapackLoaded`（`TagsUpdatedEvent.ServerDataLoad`）里 `invalidate()`，否则 `/reload` 后会
一直用旧索引 / 旧符形。

### 6.3 逐笔上报与时间检测（反作弊的一半）

用户 2026-10-01 定下的形状：**画一笔发一个包，服务端收一笔、扣一笔的颜料**；最后点"提交"时**把整幅图案再发一次**，
服务端拿它跟自己的记录对账（§10）。所以上一版"整场只在结束时提交一次、省流量"**作废**——代价是流量与实现量都涨，
换来的是"服务端手里有一条可信的、带时间的增量记录"。

- **每一笔**（`TalismanStrokeC2SPayload`）：服务端记下这一笔、**按这一笔的长度从会话那一支笔上扣颜料**（§6.4 / §6.5），
  再回一个"收下了 / 这一笔被拒"的通知（回执带上**这一笔扣了多少**，页面拿它显示"这次花了多少"；剩余颜料不用发，
  客户端读自己 carried 上那一份就有）。被拒的笔，客户端**必须抹掉**（否则结算时对账必挂，§10）。
- **三种拒收**（原因分开报，判定全在服务端）：**过快**（与上一笔的间隔 < `min_stroke_interval`）、**颜料不够**
  （笔上余额不够这一笔要扣的量）、**笔不在光标上了**（会话锁定的那一份 carried 已经不是同一支笔）。前两种进
  "被拒笔数"计数；**"笔不在"不计入**——它是"玩家把笔放下了 / 换成别的东西"的物理事实而不是作弊，
  而且那一笔拒收之后**后面每一笔都会拒收**（没笔就没颜料），玩家自己会去交卷或关界面。
- **没有"清空画布"这个动作**（用户 2026-10-01 第四问只给了**提交**与**取消**两个按钮，§8.5）：中途画砸了只能
  **取消**重来，而取消会消耗这一张纸（§6.4）。因此 `TalismanClearC2SPayload`、以及建立在"服务端看得见每次清空"
  之上的 `clear_limit` 一起作废（§11 问题 11 / §12）。服务端手里的记录仍然只由"逐笔 + 提交的整幅"构成，
  对账口径一个字都不变。
- **时间检测（核心）**：相邻两次"落笔"包之间、以及"开画包 → 第一笔"之间，间隔必须 ≥ `min_stroke_interval`
  （**默认 300ms**，配置项可调，`0` = 关闭）。判定用**服务端收到包时的 `getGameTime()`**，
  **不看客户端给的任何时间戳**（客户端说的时间一律不读）。不足间隔的那一笔**拒收**，并记进一个计数器；
  被拒笔数超过 `max_rejected_strokes`（默认 3）→ **本次会话判失败**（材料不退）。
- **为什么只说"一定程度"**：它拦的是"一瞬间灌进来几百笔"（脚本、改包）；**拦不住**"按 0.3s 节奏自动描图的脚本"——
  那种脚本画得就是准。这条口径写在 §10 的"已知缺口"里，别在别处把它说成万无一失。
- **付款时机**：符纸在**开画时取走**（占住这张纸）、在**离开会话时结算**它（画过就判失败、一笔没画就放回，见下），
  笔上的颜料**逐笔扣**（§6.4）；颜料一律不退——已经蘸在笔上、又画进纸里了，没有"退"这回事（§6.5）。
- 预览（§8.7）仍然是"可以先看分再交卷"的口子——现在多了一层时间成本（每笔至少 0.3s）；嫌松就关掉预览（§11 问题 5）。

### 6.4 扣费：两样东西走两条路（符纸走代价，颜料走笔的存量）

**谁出料 / 怎么算**：**界面里那一格**（菜单自己的临时格，符纸 1 格，§6.2），不是玩家背包；**长度由服务端自己量**——
它只拿收到的点列自己算（每条折线弧长之和，用原始点列，在预处理之前量），客户端上报的长度不读。

| 扣什么 | 从哪扣 | 什么时候 | 走哪条路 |
| --- | --- | --- | --- |
| **默认成本：符纸 1 张**（**配方里不写**，由配方类型自带，第八问） | 界面那一格 | **开画时取走（占住）**，**离开会话时结算**（判失败 / 放回，见下表） | `Cost` + `CostTransaction.plan → commit`，来源 `CostOrigin.TALISMAN_DRAWING` |
| **`costs` 里的额外项**（第八问：作者只写"额外"） | **物品类**（`mxt:item`）走界面那一格；`mxt:resource` / `mxt:aura` / `mxt:js` 走**玩家** | 与默认那条**同一时刻、同一套结算**（同一份计划，不是第二次扣费） | 同上 |
| **颜料**（按这一笔的长度） | **会话锁定的那一份 carried（光标上那支笔）自己的组件** | **每一笔到达时** | **不走 `Cost`**：像符箓载体的灵气存量那样直接读写那口容器（§6.5）；服务端 `setCarried` 之后由原版自动同步回客户端 |

- **开画（点选符方）时**：把**默认那张符纸 + `costs` 里的额外项**用**同一份计划**从那一格 / 玩家账上取走——
  格子空出来，这些东西由这个会话**占住**（别的菜单看不见它，也不会有第二个人用同一张纸开画）；
  **材料不够 → 列表那一行灰掉**（笔不参与这个判断，§6.1）。**会话要记的是"实际扣走了什么"**：
  付完账**前后各看一次那口容器、按槽记差额**（不是记开画前那一摞——那会把格里剩下的也算成"取走的"），
  数值类记的是**快照**（值，不是差额）。0 笔离开时**按这份差额放回**：格里已经有同类物品就只补到原来的数量，
  那格被换成别的东西、或补不下（超过堆叠上限）的部分回玩家背包。
- **落笔之前可以换符方**（用户 2026-10-01 手测后点名）：换＝把当前这个**还没画过**的会话结算掉（纸与额外项原样放回）
  再开一个新的，所以**免费**；已经落笔就拒绝（那一笔对不上新符形，换等于把它扔掉）。
  ⇒ 这也是"列表在会话开着时仍然可点"的原因：判断材料时要把**没画过的会话正拿着的那张纸**算进去（§6.1 / §8.3）。
- **这些东西什么时候真的消耗掉：看离开会话那一刻画没画过**（用户 2026-10-01 第四问："这两种都会消耗符纸；
  一笔没画的点取消没用"；**2026-10-02 第三修把"画过"那一档从"静默消耗"改成"判失败"**，用户原话
  "同时判断这次画符失败"）：

  | 离开方式 | 一笔都没画 | 画过（≥1 笔） |
  | --- | --- | --- |
  | **提交** | 不可能（提交要求 ≥1 笔，0 笔时按钮灰着） | **成功就产出**；对账失败则判失败（走 `finish(..., false)`，那一条会给 `failure_outputs`） |
  | **取消** | **空操作**：不结束会话、也不动已取走的东西（按钮灰着） | **判失败**：`abandon` → `fail`（跑 `failure_action`，回执 ABANDONED），材料不退；界面重置回"未选符方" |
  | 关界面 / 断线 / 换维度 | **放回**（物品回那一格，再由关界面那次 `clearContainer` 交给玩家；玩家付的数值还回玩家） | **判失败**：`abandon` → `fail`（跑 `failure_action`），材料不退；那一格里剩下的东西照旧交给玩家 |

  ⇒ "提交与取消都消耗符纸"成立于"画过"那一行；"一笔没画时取消没用"就是它左边那一格。**判失败不给失败产物**：
  `failure_outputs` 属于"提交到了结算但对账失败"那一条（`finish`），放弃的会话走的是 `fail`，只跑 `failure_action`。
  **默认那条与 `costs` 额外项一起按这张表走**（要不要让额外项"开画即扣死、不退"，见 §11 问题 18）。
- **每一笔到达时**：量这一笔的弧长 → 换算成颜料（§6.5）→ 从光标上那一份（会话锁定的 carried）扣；扣不动就把这一笔**拒收**
  并通知客户端抹掉——这就是"笔干了画不动"（§6.3）。
- **结算（"提交"）时**：先用整幅图案与逐笔记录**对账**（§10），对上了才算完成度 → 判档 → 产出符箓，
  然后**直接放进界面那一格**（开画时纸已取走，格子是空的；关界面时它跟着那一格回玩家背包）；
  `outputs` 里的额外产物一格放不下，其余走玩家背包。
- **断线 / 判失败**：开画时取走的东西按上表结算（画过就没了），**已经扣掉的颜料一律不退**（已经画进纸里了）。
- **那一格里的材料怎么扣**：仍然只有一套扣费——`Cost` + `CostTransaction.plan → commit`。但 `mxt:item` 本来**只认玩家背包**
  （`ItemCostDraft` 绑死 `Player.getInventory()`；`CostTransaction.commit` 与 `checkAvailability` 两处都取
  `context.player()`，取不到就是 `NO_CHANNEL`），而我们要从那一格扣，所以：
  - `ItemCostDraft` 的绑定**放宽**成"任意 `Container` + `setChanged`"（玩家背包包一层、那一格包一层）；
  - `CostContext` 加一个**物品目标**（`PLAYER_INVENTORY` / `CONTAINER`），上面两处取目标时跟着改。
  **这是本模块唯一要动共享基建的地方**，玩家那条路的行为一个字节都不变。
  - 备选（不动基建）：用现成的 `InventoryUtil.removeItems` 从槽里扣——但它是**精确物品匹配**
    （`isSameItemSameComponents`），配方写 `#标签` 就失效，而且"快照还原"与 `CostTransaction` 的"预览 → 提交"是两套
    回滚口径。**不选**，理由记在 §14。
- **颜料为什么不走 `Cost`**：它不是"付款者账上的一笔钱"，而是**被使用的那件工具自己的状态**——符箓的灵气条目
  已经是这一类（`AGENTS.md` 里记为"载体自己的存量"的例外），笔的颜料是第二个实例。硬做成 `Cost` 就得凭空造一个
  "付款者"（笔不是付款者），还要给容器目标再开一条"只改组件、不动格子"的路（§14）。
- **别和 §4.3 拓扑项里的"总长度"混淆**：那个是判分用的软化比值，这里的长度是扣颜料用的**绝对像素长度**（同一次量、两处用）。

### 6.5 颜料：符笔的存量、蘸料、容量与换算

用户 2026-10-01 第二轮拍板（原话："符笔设计为可以和朱砂合成添加颜料，然后绘制的时候再扣除"）：**颜料在符笔上**，
绘制时**逐笔扣**。所以"墨"不再是一个会被消耗掉的物品堆，而是**一支笔自己的一口存量**。
**加料方式已于 2026-10-02 改掉**（用户原话："取消掉原来的给笔加颜料的合成表吧，改成一个tag，然后如果准心上是符笔，
然后右键颜料槽位就可以直接加颜料（可以看一下储物袋的逻辑）"）：原方案是一份 `mxt:talisman_brush_dipping`
原版工作台配方（`implements CraftingRecipe` 的自定义 serializer），当天**连同那份 serializer 一起删除**，
改成"一个物品标签 + 蘸料手势（照原版储物袋，挂在物品上）"，见下面的"怎么加"。

**存在哪**：新组件 `mxt:brush_pigment`，**一个非负整数**（单位＝点，1 点 ＝ 1 像素弧长——与画布同一把尺，最好解释）。
标量就够，不需要新 record：照 `MxtDataComponents.HERB_AGE`（`registry/MxtDataComponents.java:65`，`Codec.intRange`）写即可，
注册走同一个 `register(id, codec)`（:69-71，落盘与同步一行就有）。**这里"缺省"与"0"是同一件事**（都是空笔），
所以只有两态；`SpiritStorageComponent` 那套"缺省 / 空 / 有值"的三态口径在这里用不上（它是为了区分"没写过"与"被抽干"）。

**一支笔一支**：`mxt:talisman_brush`（`registry/MxtItems.java:63`，现在是默认的 64）要改成 `properties.stacksTo(1)`。
三个理由：① **颜料是单支笔自己的状态**（一叠里"哪一支蘸了料"没有答案）；② 蘸料一次只给一支笔加料，
可叠放之下"1 支 + N 份朱砂"的语义无法定义；③ **它要提在光标上**，而 carried 就是"一份堆"，`stacksTo(1)` 才让它
与"手里只有一支笔"这件事同形。这与 `TalismanService.durability` 对"载体不叠放"的口径也是同一条
（`runtime/talisman/TalismanService.java:150-153`）。
**加料与绘制是两个时刻**：蘸料时笔可以**提在光标上**、也可以**放在某个槽里**（见下），画的时候必须提在光标上——
所以"笔不在光标上"只否决绘制（§6.3 的第三种拒收）。

**怎么加（蘸料手势，2026-10-02；同日第二轮改成"挂在物品上、照原版储物袋"）**：
**光标提着符笔，对着一个颜料物品点一下**，笔一次吸进**一份**（一个物品）；笔满时一点都不吃。
形状与量都抄**原版储物袋（`minecraft:bundle`，"储物袋"就是它）**：

- **钩子在物品上，不在菜单里**：`item/TalismanBrushItem` 覆盖原版那两个点击钩子
  ——`overrideStackedOnOther(self＝光标上那支笔, slot＝被点的那一格)`（笔在光标上）与
  `overrideOtherStackedOnMe(self＝槽里那支笔, other＝光标上的颜料)`（笔在槽里）。于是**任何容器界面都成立**
  （背包、箱子、工作站），不限于工作站那一格；工作站里**已经没有颜料槽**（2026-10-02 当天晚些删掉，
  见文首再修正），蘸料在背包或箱子里一样成立。
- **一次点击＝一份**（用户 2026-10-02 点名："一次只能用一个"）：取一个物品、加 `pigment_per_item` 点，**不是**原版那种"能塞多少塞多少"；笔装不下一份时**一份都不取**（不白吃、也不溢出），只响一声 `BUNDLE_INSERT_FAIL`，成功则 `BUNDLE_INSERT`。
- **左键与右键都蘸**：原版储物袋是**左键放入、右键取出一件**；笔没有"取出一件"这个形态（颜料是数值，不是物品），
  所以右键也拿来蘸——否则原版会把它当成"拿笔去换那叠料"。`Shift` 点击（`QUICK_MOVE`）根本不会走到物品钩子上，
  照旧是原版搬运。
- **两侧都吞掉这次点击**（否则客户端会把点击预测成原版的移动），**但只有服务端动东西**：
  carried 上的组件改完由原版下一次 `broadcastChanges()` 同步回客户端（与逐笔扣颜料同一条路，§6.4）；
  笔在槽里那一支由钩子顺手 `slot.setChanged()`。
- **为什么不再是配方**：要表达"1 支笔 + N 份朱砂 → 同一支笔、组件累加"就必须自定义 serializer
  （普通 `shaped` / `shapeless` 的结果是一个写死的 `ItemStackTemplate`，**带不出输入那支笔的组件**），
  而"一份颜料值多少"还得写进配方 JSON——**结果是每个内容包都要抄一条配方才能用符笔**。
  改成标签 + 蘸料手势之后：**加什么料＝物品标签**（`#mxt:brush_pigment`）、**一份多少＝服务端配置**
  （`talisman.pigment_per_item`，默认 1000），数据包一条 JSON 都不用写。
- **不是 `Cost`**：颜料是"被使用的那件工具自己的状态"，照 §6.4 的理由直接读写那一份 carried 的组件。

**怎么扣（换算规格）**：服务端量出这一笔的弧长 `len_px`，`扣 = clamp(ceil(len_px × rate), floor, cap)`：

| 参数 | 建议默认 | 说明 |
| --- | --- | --- |
| `rate`（点 / 像素） | `1.0` | 先给 1:1（单位就是像素弧长），手测后再调 |
| `floor`（每笔保底） | `1` | 免得"点一下"不花钱；也让颜料为 0 的笔真的画不动 |
| `cap`（单笔封顶） | `0`（不封顶） | 长度是服务端自己量的、点又都在画布内；手测发现"一笔能吃掉一整支笔"再加 |
| `容量`（一支笔装多少） | `4000` | 一张 90×210 的符，笔画总长通常在 400–1200px，所以 ≈ 描满 3–5 张 |
| `一份颜料给多少` | `1000` | 服务端配置 `talisman.pigment_per_item`；4 份朱砂装满一支笔 |

**这些数是几何推算的建议值、没手测过**，请按 §11 问题 3 拍板；容量、`rate` / `floor` / `cap` 与 `pigment_per_item`
放服务端配置（`MxtServerConfig` 的「符箓」页），**只由服务端算**——客户端报上来的用量一律不读（§10）。

**怎么显示**：**覆盖 `isBarVisible` / `getBarWidth` / `getBarColor`**——原版自己的 `BundleItem` 用"背包重量"当电量就是
这么干的（`Item` 的这三个方法本来就是留给物品覆盖的，`GuiGraphicsExtractor` 画物品格时只认它们）。好处是
**光标上那一支（以及它被放进任何槽位时）都直接看得到还剩多少**，页面不必为它再开一块几何；tooltip 再加一行"颜料 x / y"
（照 `runtime/talisman/TalismanTooltipAppender` 的写法，别开第二个 appender）。⇒ `mxt:talisman_brush` 要从 `Item::new`
换成一个 `TalismanBrushItem`（只为这三个方法与那一行 tooltip 存在）。
**别改用耐久条那套 `MAX_DAMAGE` / `DAMAGE`**：0 = 空在原版那里是"已损坏"（`isBroken()` 常真、`getDamageValue()` 被 clamp、
`max_damage` 的 codec 还拒收 0），§14 有对照。

**蘸料不占 payload**（2026-10-02）：它就是一次原版槽位点击，判定写在笔自己的那两个原版钩子里（§6.5）——
客户端那一半只吞掉这次点击、什么都不改，改的只有服务端，之后靠原版的 carried 与槽位同步回到客户端，
所以表里一个新包都不加。

**列表什么时候推**：`TalismanDrawingListS2CPayload` 在菜单**开着的第一个 tick** 推（`broadcastChanges` 里发一次），不在 `createMenu` 里发——那时客户端的菜单还不存在，包会早到。之后**只要那一格的内容变了就再推一次**（开画把纸取走、换符方把纸放回、玩家自己塞纸进去都会让它变），另加每秒一次的兜底推送，管玩家自己账上的额外成本、解锁条件与数据包重载；会话结束（提交 / 取消 / 判失败）之后也再推一次。

整场流量 ≈ 1 个列表 + 1 个符形 + N 个笔包（+ N 个回执）+ 1 个整幅 + 1 个结果。**最终包带整幅**是用户口径（用来对账）；
想省流量也可以只带摘要（笔数 + 每笔点数 + 点坐标哈希），两种都能校验，见 §14 的对比。

登记两处照 `NetworkManager` 的既有形状（`playToServer` + `playToClient` 的 dedicated-server 分支只登记 codec，

### 8.2 纸面：三层，两层 canvas

```html
<div id="paper-frame">                     <!-- 纸框 + 纸底（底色由屏幕按配方的 background_color 写成内联样式） -->
  <canvas id="guide" width="90" height="210"></canvas>   <!-- 参考层：符形淡影（Java 画一次，淡褐） -->
  <canvas id="paper" width="90" height="210"></canvas>   <!-- 墨迹层：玩家笔画（Java 增量画，配方的 foreground_color） -->
  <div id="paper-grid"></div>                             <!-- 可选：淡格线（CSS，压在最上层但不吃鼠标） -->
</div>
```

- `width` / `height` 属性由 Java 按**固定画布常量 `90 × 210`** 写死（`setAttribute`，§4.2 没有可配尺寸），CSS 尺寸与位图**1:1**
  （§3.4：四边形是线性采样，放大就糊）。纸面占满右栏整块 **90×210**（§8.1），不额外留边。
- **参考层与墨迹层不共用一条 surface**：共用就意味着每次重画参考都要整图重绘（§3.4）。参考层只在
  "会话开始 / 尺寸变化 / 重绑"时画一次；玩家笔画只画进墨迹层。
- 两层的叠放要写**显式 `position` + `z-index`**（AUI 里绝对定位的兄弟之间别指望 DOM 顺序，轮盘踩过这个坑）。
- `OffscreenCanvas` 在这里没有用武之地（它是"画好再 `transferToImageBitmap`"的一次性素材）。

**配色：黄纸 + 红笔画**（用户 2026-10-01 第四问："绘制区域以黄色为底，线条为红色"）。**2026-10-02 第五次修正**：
纸底与笔画这两个颜色**改由配方给**（`background_color` / `foreground_color`，缺省浅黄 `#FFFE85` 与纯红，§4.2），所以色值只有
两个来源——**配方那两个字段**与**参考层那一个本体常量**；页面自己的 CSS 照旧只写几何。

| 元素 | 色值 | 说明 |
| --- | --- | --- |
| 纸底（`.paper`，即 `#paper-frame`） | 配方的 `background_color`，缺省 `#FFFE85`（浅黄） | 屏幕在绑定时写成内联 `background-color`；**`theme.css` 里不再写这个颜色**（只留纸框描边），免得两处各说一套 |
| 玩家笔画（墨迹层 canvas，Java 里的 `ctx.strokeStyle`） | 配方的 `foreground_color`，缺省 `#FF0000`（纯红），线宽 2px、圆头圆角 | "线条为红色"就是它；**同一支笔的所有笔迹同色**（不按笔序变色，符箓不是涂鸦），换一份符方才换色 |
| 参考层符形（guide canvas，Java 定色） | `rgba(93,64,28,0.35)`（淡褐），本体常量 | **不跟 `foreground_color` 走**——同色就和玩家笔画分不开；描红看的是"底稿"而不是已经画上的线 |
| 可选格线（`.paper-grid`，若保留） | `rgba(120,90,40,0.10)` | 极淡，不抢笔画 |

- 黄底与笔画的对比度足够，所以**不需要再给笔画加描边或阴影**；纸面**不做圆角**（原版 GUI 是直角）。

### 8.3 参考符形怎么展示（用户主设计的第一半）

| `pattern.guide` | 呈现 | 用途 |
| --- | --- | --- |
| `fade`（**默认**，第八问） | 起笔后参考层淡到更低（约 0.15），停笔 2 秒回到 0.35 | **半背临**：逼玩家记住走向，但给描边的余地 |

### 8.4 采集与手势（Java 侧）

在纸面容器（或墨迹层 canvas）上 `addEventListener` 听 `mousedown` / `mousemove` / `mouseup` / `mouseleave`：

- `mousedown`：开一笔，`ctx.beginPath/moveTo`；
- `mousemove` 且 `buttons != 0`：把点加入当前笔；与上一个保留点距离 > 1px 才记（抽稀），`ctx.lineTo/stroke`
  **只画新增段**；
- `mouseup` / `mouseleave`：收笔 → 进本地点列、**立刻发 `TalismanStrokeC2SPayload`**（§7）；收到"拒收"回执就把这一笔
  从点列与画面上**抹掉**（§6.3）；
- 坐标用 `MouseEvent.offsetX/offsetY`（**已经是相对该元素的文档坐标**），按"位图 ÷ CSS 尺寸"缩放到位图坐标；
  CSS 尺寸只在布局变化时通过 `Size.of(element)` 读一次并缓存（房规：不回读几何、按需读）；
- **越界点**：超出画布的点 clamp 到边缘并记入当前笔（不丢弃，否则一笔划出纸外会接不上）；一旦指针离开纸面，
  当前笔照常收笔（`mouseleave`）。
- **不在页面里写 JS**：刷新会清 DOM/JS 状态并清空位图（§3.3）。绘制逻辑放在"按 `Document.getRefreshGeneration()`
  重绑"的那条路上（`AuiWrappedScreen.auiRebind` 的形状），重绑后按**本地那份点列**重画。
- 增量绘制期间的性能：AUI 每次 `ctx` 调用都会 `markSurfaceDirty` + 一次整张贴图上传。所以：一节 `stroke()`
  画一段（不是每个采样点一次 `stroke`）、拖动采样按上述抽稀、不在页面里挂 `@keyframes` 之类的每帧动画。

**"能不能画"的闸门，以及这一次点击要不要交给原版**（AUI 1.2.5 源码逐条核过，用户 2026-10-01 第三问）：

- **闸门是个纯 Java 条件**：AUI 里没有"必须持有某物品"这种概念，也不需要——`mousedown` 的监听器自己判。
  **判据（用户 2026-10-01 第三问拍板）= 光标上那一份 carried 是符笔、且颜料 ≥ `floor`**（§6.2 / §6.5）：
  客户端直接读自己的 `getCarried()`（同步副本，服务端每笔再判一次，§10），不满足就**直接 return**：
  不起笔、不改画面、**也不动原生事件**，纸面此时与一块普通面板没有区别。
- **持笔期间点不到槽位**：光标上提着笔时点任何槽位都是"把笔放下"，所以绘制期间玩家本来就不该点槽位
  ——这与"放下笔就不能画"自洽。而起笔那一下已经被 consume、拖动又不会武装快速合成（见下一条），
  所以**画的过程中指针滑过背包格也不会掉东西**。
- **`MouseEvent.consumeNative()` 是公开的、逐事件可调的**（`event/MouseEvent.java:94`）：在监听器里调它，
  等 AUI 派发完这一轮，**这一次原生鼠标事件就被取消**，原版 `Screen.mouseClicked` 收不到。链路是
  `Client.mouseButton`（`client/Client.java:221-229`，屏幕开着时）→ `Operation.onMouseDown/onMouseUp`
  （`render/Operation.java:42-71`，返回值就是 `event.isNativeConsumed()`）→ `event.setCanceled(true)`。
  ⇒ **起笔那一次 `mousedown`、以及配对的 `mouseup` 应当 consume，其余一概不 consume。**
  两个细节：`mousedown` 与 `mouseup` 是**两个独立的事件对象**（`Operation.onMouseUp` 现 new 一个），要各调一次；
  而克隆体**共享同一个 `NativeDispatchState`**（`MouseEvent.java:587`，`:32/591-593`），所以在 `click` 回调里
  consume 也能落到那次 `mouseup` 上。
- **别用页面 meta 代替它**：`aui-mouse-events=intercept`（`init/Document.java:133/144-149` 与
  `MouseEvent.java:141-143`）是"整页都吃"，槽位点击 / 拖拽 / 双敲一起废（`AGENTS.md` 硬约定）。
  要的是**逐事件**吃，那就只有 `consumeNative()`。
- **"DOM 收到了" ≠ "原版收不到"**：`Event.tiggerEvent` 里只要有一个非 internal 的监听器，事件就被标成 consumed
  （`event/Event.java:293-295`），而**取消原生只看 `isNativeConsumed()`**。所以"监听器挂着"本身不会抢走原版的事件。
- **不 consume 的后果（26.1 原版源码，逐条核过）**：落在纸面上的点击在原版里**本来就是空操作**——
  `AbstractContainerScreen.mouseClicked` 算出 `slotId = -1`（面板内、但不是槽位），而 `:356` 的
  `if (slotId != -1)` 挡着后面全部处理；**拖动同样安全**，因为"快速合成"只在 `isQuickCrafting` 为真时才有破坏性
  （`shouldAddSlotToQuickCraft` 的第一项就是它，`:685-692`），而它**只可能被"按下时命中槽位"武装起来**
  （`:383-394`），纸面上的按下不会。真正会把手上物品丢出去的是**点在面板外**
  （`clickedOutside → slotId = -999 → ContainerInput.THROW`，`:340-349/375-377`），所以门控必须把
  "指针在纸面矩形内"判准。
- **`mousemove` 没有取消通路**：`Operation.onMouseMove`（`render/Operation.java:91-110`）无返回值、`Client` 也不取消
  移动事件——所以拖动期间不靠 consumeNative 兜底，靠的就是上一条那件事：**按下那一下没被原版接走**。

### 8.5 两个按钮（左栏下部，§8.1）

| 按钮 | 行为 | 备注 |
| --- | --- | --- |
| **提交** | 把**整幅图案**发一次（§7）→ 等结果 → 产物**直接进界面那一格** | 唯一的"交卷"入口；**一笔都没画时灰着**，提交后与"取消"一起灰掉 |
| **取消** | 结束会话 + **把界面重置回"未选符方"**（纸面清空、结果区清空、列表恢复可选） | **一笔都没画时是空操作（灰着）**：不结束会话、也不动那张纸；画过再取消 → **判失败**（跑 `failure_action`，回执 ABANDONED、文案 `screen.mxt.talisman.result.abandoned`）、材料不退（§6.4） |
| **关闭** | 关界面（= 放弃会话，与 Esc 同义） | 走 `removed(Player)`：画过 → **判失败**（跑 `failure_action`）；一笔没画 → 放回那一格；**然后把格里剩下的整个交给玩家**（工作台式，§6.2 / §6.4） |

**"提交"是一个独立按钮，不靠"抬笔"或"画到第几笔"自动触发**（用户 2026-10-01 点名）：什么时候交卷由玩家决定，
所以中间可以慢慢画，而网络上一个字节都不发。
**没有"清空画布"、也没有单笔撤销**（用户 2026-10-01 第四问把按钮区定成**两个**）：一笔画砸了只能整体取消重来，
而取消要花掉这一张纸——**这是本设计里最贵的一次误操作**；要不要给它留点余地（例如"清空画布"也算一个动作、
或 0 笔之外再放宽一档），见 §11 问题 16。

### 8.6 结算反馈

服务端返回后页面显示（都在左栏结果区，§8.1）：**完成度**（`completion × 100` 的整数 + 一条 `.bar` 进度条；
**这就是唯一的数值反馈**——不再单独显示"威力"，第九问）、命中的
**品质名**（产物上那份 `mxt:quality` 的名字，`ItemQualityService.coloredName(holder, DefinitionText.name(holder))`，
照 `QualityCommand` 的写法；档位不再点名符箓，所以这里显示的是品质而不是"档名"）、**产物**（`<item>` + 名字）、
失败时给失败文案；外加**本次扣掉的颜料**（服务端算的那一份，§6.4 / §6.5；还剩多少由光标上那支笔自己显示）。
再想画 = 先把笔蘸满（§6.5），再重新点一次符方（新的一张纸）。

**颜料本身不必在页面里画条**：笔上的条是原版条（§6.5 覆盖那三个画条方法的结果）——物品槽里、快捷栏与容器界面里
都直接看得到，页面只负责"这一次花了多少、还剩多少"这行字。

### 8.7 本地预览（可选）

客户端可以用**同一份** `TalismanDrawingScorer`（common 侧）算一份本地完成度，画在进度条上，但**标记为"预览"**；
限流成"笔画有变化时最多每 200ms 一次"，不要在 `mousemove` 里逐点重算（那是在拖鼠标时跑 O(10⁵) 的循环）。
**服务端返回的那一份才是权威**，两者不一致时以服务端为准（并记一条 debug 日志便于发现实现漂移）。
开关：默认给预览，配方可用 `judgement.preview` 关掉（§11 问题 5）。预览是**纯客户端**的（不上报、不消耗任何东西），
它也正是 §6.3 里"耐心的玩家可以先看分再交卷"的直接原因——嫌松就把它关掉。

### 8.8 手势与槽位并存

页面**不写 `aui-mouse-events=intercept`**（`AGENTS.md` 硬约定）——本工作站**有**原版槽位（站内 1 格 + 背包 36 格），
所以这条尤其要守：写了它 AUI 就会 `consumeNative`，原版收不到鼠标事件，槽位的点击 / 拖拽 / 双敲全废。
DOM 拖拽（在纸面上画符）与槽位拖拽靠"指针落在纸面矩形里与否"天然分开。

## 10. 防作弊与边界（服务端权威）

三道闸门，从弱到强：

1. **逐笔上报 + 服务端扣费**（§6.3 / §6.4）：服务端手里有一条"什么时候收到哪一笔"的记录，扣颜料也按它自己的账走
   （每一笔都要问一次"光标上还是那一支笔吗"）。
2. **时间检测**：相邻两笔（含"开画包 → 第一笔"）间隔 < `min_stroke_interval`（默认 300ms，可调）→ **拒收该笔**；
   被拒笔数 > `max_rejected_strokes`（默认 3）→ **本次会话判失败**。判定只看**服务端收到包时的 `getGameTime()`**，
   客户端给的任何时间一律不读。
3. **最终对账**：`TalismanSubmitC2SPayload` 带整幅图案，服务端把它与逐笔记录**逐点比对**——多一笔、
   少一笔、坐标变了、顺序变了，都算不一致 → **判失败**（材料不退）并记一条 warn。于是"离线画好再交""改包塞一笔"
   这类花招会卡在结算这一步。

- **服务端权威 = 判分与产物**：完成度一律由服务端拿（已对账的）点列重算；客户端预览那份不回传、也不被采信。
- **已知缺口（接受，用户自己说的是"一定程度上"）**：按 0.3s 节奏自动描图的脚本拦不住——它画得就是准，在数据上
  和"人照描红画得很准"完全同形。时间检测能关掉的是"一瞬间灌进来几百笔"那一档，**不宣称杜绝脚本**（§6.3）。
- **限流与上限**：单笔点数 ≤ 512（超了**拒收该笔**，与时间检测共用同一条"被拒"路径）；会话总点数 ≤ 4096、
  笔画数 ≤ 64（超了**拒收整次提交**并记一条 warn）；同一玩家同一时刻只有一个会话，一个会话只能结算一次。
- **必校验**：`recipeId` 必须等于当前会话选中的那份；**符纸已占住**（会话握着那一张）、未结算过；提交时玩家仍在同一座
  工作站的界面上（`stillValid` 那一套）；配方仍存在且仍是这个类型；**符纸只从菜单那一格出（关界面就交回玩家）、颜料只从会话锁定的那一份
  carried（光标上那支笔）上扣**——carried 本来就是玩家自己拿着的，不经过背包格；每一笔扣颜料之前都要问
  "光标上还是开画时那一支笔吗"（不是就按"笔不在光标上了"拒收，§6.3）。**注入公式的 `percentage` 就是完成度本身**
  （完成度在 §4.3 第 6 步已经 clamp 到 `[0,1]`，不再有第二层 clamp）；消费者公式自己的值域由各自的字段管
  （例如 `charge_ratio` clamp 到 `[0,1]`、非有限值按 `0` 取，§4.2）。
  **扣颜料的长度只认服务端自己量的那一份**——客户端上报的长度 / 用量一律不读（§6.4）。
- **点数与坐标清洗**：`double` 必须有限、clamp 到位图范围内、NaN/Infinity **丢弃该点**（房规：运行期遇到
  NaN/Infinity 记一次警告并按失败处理）；清洗后点数 < 2 就按退化输入结算为 0。
- **不做"笔画重放"**：服务端只认这一条连接上收到的点序列，签名 / 时间戳这类机制在这个规模上不划算（§12）。
- **付款不退款**：**默认那张符纸 + `costs` 里的额外项**都按"离开会话时画没画过"结算——画过就判失败
  （提交、取消、关界面、断线都一样，材料不退、跑 `failure_action`），一笔没画就放回（物品回那一格，关界面时
  再由 `clearContainer` 交给玩家；玩家付的数值还回玩家）（§6.4 的表）；**颜料**一律不退
  （笔上剩下的还在笔上，但已经画掉的不还）。**"至少一条物品消耗"那条加载期校验作废**：默认那张符纸由配方类型
  保证，`costs` 为空是正常配方（§4.2）。

17. **`result.grades` 还要不要必填**（第六问的连带）：档位现在**只**决定品质 / 耐久 / 灌注 / 额外产物与及格线
    （符箓定义已经提到顶层），所以"不想要分档"的配方也得写一档 `min_completion: 0`。
    两种收法：① 保持必填（建议，及格线只有一处真值，且一眼看得出"低到多少算失败"）；
    ② 改成可选，缺省 = 单档 `min_completion: 0`（必成功、品质走定义自己的 `quality`）——省掉一行，
    但"这个符方永远不会失败"就变成隐式的了。另外**"档位是否要一个显示名"**也一并定：现在结算区显示的是
    **产物的品质名**（§8.6），档位自己没有名字。
18. **`costs` 额外项的退款口径**（第八问的连带，§6.4）：默认那张符纸按"画没画过"结算是用户口径，
    但**额外项**（作者在 `costs` 里加的东西）没说。两种：
    ① **跟符纸同一条路**（本稿默认）：开画时取走占住，一笔没画就一起放回、画过就一起消耗——
    好处是只有一套规则，代价是**会话要把取走的东西记下来**（物品堆 + 玩家付的数值）；
    ② **额外项开画即扣死、永不退**：会话只需记那张符纸，实现更省，但"一笔没画"时玩家白亏额外材料。
    **建议 ①**（与"取消是空操作"同一套直觉）；另外**额外项能不能写 `mxt:aura`**（用玩家自己的灵气开画）
    也一并定：建议**能**（`Cost` 本来就有这一族，没有理由在这里禁掉）。

## 12. 不做 / 推迟

- **不做旋转对齐**：`DTW.md` 的旋转搜索**不采纳**（平移与缩放**采纳**，见 §3.5 / §4.4）——符箓有正倒，
  "转过来也算对"会让"誊写"变成"摆姿势"。
- **不做图匹配增强**（DTW.md §5 的节点图 + 匈牙利匹配）：第一版只做几何距离；留 `D_graph` 与 `alpha` 的口子，
  触发条件写在 §4.4。
- **不做整体线段集的最优（匈牙利）匹配**（DTW.md §6）：逐笔 `pair` + 贪心配对已经够（笔数是个位数，§4.3 第 5 步）。
- **不做单笔撤销**：一笔画砸了只能整体放弃（而且没有"清空画布"，见 §8.5）。
- **不做"清空画布"**：用户 2026-10-01 第四问把左栏按钮定成**提交 + 取消两个**，于是 `TalismanClearC2SPayload`
  与 `clear_limit` 一起作废（§6.3 / §8.5）；重画只能取消重来，代价是那一张符纸。
- **不做"从玩家背包直接扣材料"**：材料走**界面里那一格**（用户 2026-10-01 拍板，§6.2；2026-10-02 第三修只是把这一格从方块实体搬进菜单，扣的仍然是"格子里的东西"）；背包只作为"格满时的退路"（§6.4）。
- **不在工作站里设笔槽、也不看主手 / 副手**：用户 2026-10-01 第三问澄清——"拿着符笔"是**提在光标上**那一份
  carried（§6.2 / §6.3），所以站内不留笔槽、会话也不锁主手栏位。
- **不给笔加颜料做配方**（2026-10-02 起）：普通 `shaped` / `shapeless` 的结果是一个写死的 `ItemStackTemplate`，
  **带不出输入那支笔的组件**，所以那种走法必须自定义 `implements CraftingRecipe` 的 serializer；用户点名改成
  "物品标签 + 蘸料手势（照原版储物袋，挂在物品上）"之后，那条配方连同 serializer 一起删除（§6.5）。
- **不把颜料做成一种会被消耗掉的"墨"物品**（第一版及之前的口径，2026-10-01 第二轮改掉）：那样答不出"这支笔还能画多少"，
  也没法在槽位里显示；颜料改成笔自己的存量之后 `costs` 里也不再需要它（§6.5 / §14）。
- **不把蘸料做成站内按钮**（第一版，2026-10-02 改）：蘸料是笔自己身上的原版点击钩子
  （照原版储物袋 `minecraft:bundle`），站内连颜料槽都不留，左栏按钮区仍然只有提交 / 取消两行（§6.5 / §11 问题 13）。
- **不自己 `removeItem` 扣材料**：走 `Cost` + `CostTransaction`（§6.4）；`InventoryUtil` 只借鉴它"预览 → 提交"的形状，
  不拿它当扣费实现（精确匹配认不了 `#标签`）。
- **不做"整场只提交一次"**（上一版方案，2026-10-01 被反作弊需求取代，§6.3）：一次性提交省流量，但服务端在交卷前
  看不到画布，也没有"什么时候画了哪一笔"这条记录——时间检测与最终对账都无从谈起。
- **不读客户端的时间戳 / 长度**：时间检测只看服务端收到包时的 `getGameTime()`，扣颜料的长度只认服务端自己量的那份（§10）。
- **不做"最终包只带摘要"**（第一版）：带整幅图案更好调试，也真能逐点对账；摘要方案见 §14。
- **不做限时**（用户 2026-10-01 明确不要）：交卷只看玩家点不点"提交"，没有倒计时，也不预留 `time_limit_ticks`。
- **不用原版 recipe book 的 `has()` 解锁**：那要给每份配方配一个 advancement，而 `isSpecial()` 的配方本来就不进
  配方书；我们的解锁是"能不能在这座工作站上选"，与配方书是两件事。
- **不做符形图片比对**：要读贴图 / 像素（服务端没有画布），收益不如折线，而且会让"作者写符形"变成"作者画 PNG"。
- **不做自由涂鸦的存档 / 导出 / 分享**。
- **不做多方块工作站**（先单方块；真要做按 §11 问题 7 另开一节）。
- **不做笔画签名 / 防重放**：见 §10。
- **不做"完成度 → 威力"的映射层**（第九问）：`result.power` 与公式变量 `power` 一起去掉——所有消费者直接读
  `percentage`（完成度），少一个变量名、少一份白名单；代价是"想统一把完成度做非线性"要写在每个消费字段里
  （§5.2 / §14）。
- **完成度不落物品**：`percentage` 只在**结算那一刻**的公式上下文里（§5.2）；
  不新增"完成度 / 威力"组件、也不给 `talisman` 定义开第二个数值入口。要落物品 = 另一次拍板（§11 问题 15）。
- **不做"判分与结算同一块"**（上一稿的 `judgement`）：判分参数与档位/产物挤在一个对象里，客户端预览要跟着
  连产物一起收（或者得在序列化时挑字段）；第五问拆成 `judgement` / `result` 两块（§4.2 / §14）。
- **不做"一份符方出多种符箓定义"**（第六问）：结果只有顶层 `talisman` 这一处真值，档位不再点名定义——
  否则"配方显示的名字"与"实际拿到的符"可能对不上（名字走顶层那份定义，§4.2）。要三种定义就写三份符方。
- **配方不再有 `name` / `description`**（第六问）：名字与描述走 `talisman` 定义（`NamedDefinition` + 自动键
  `talisman.mxt.<命名空间>.<路径>`），**不在配方里再声明一份**（§4.2）。
- **不给配方开预处理粒度**（第十一问）：重采样步长 `RESAMPLE_STEP` 与 RDP 阈值系数 `SIMPLIFY_EPSILON` 是本体常量，
  作者调不到；`judgement` 里写了同名的键按未知键静默忽略。真要按符方区分再开字段（§4.2 / §14）。

### 13.1 编译

### 13.2 算法腿（可无头，写在 `/mxt_test talisman` 上）

固定输入（一份写死的符形 + 一组写死的玩家点列）断言 `completion` 与判档。**每条给一个区间，不给死值**
（算法是启发式的，写死值会让微调必挂），但**顺序与量级必须成立**：

| 断言 | 期望 |
| --- | --- |
| 完美复刻（照符形取点） | ≥ 0.90，且是全部用例里最高（实测 `0.999`） |
| 整体抖动 ±2px | 0.85–0.98，且低于完美复刻（实测 `0.961`） |
| **整体转 15°** | **显著低于抖动用例**（钉住"旋转要扣分"；实测 `0.533`） |
| 整体转 90° | **≤ 0.30**（朝向完全不对；实测 `0.234`。默认权重下 `completion` 下限本来就是 ≈0.17，"接近 0"写不成断言） |
| **整体平移（+60, −40） / 放到 2×** | **与"完美复刻"同档（差值 ≤ 0.05）**（钉住"位置与大小不判"；实测都是 `0.978`） |
| **缩到 0.5×** | **0.80–0.95**（实测 `0.886`，低于"完美复刻"——RDP 与闭合笔判据是绝对像素，半尺寸会把示例的一笔误判成闭合笔，见 §4.3 的两条不一致） |
| 0.5× + 挪到角落 + ±2px 抖动 | 0.70–0.90（归一化吸收位置与大小，只罚抖动） |
| 缺一笔（三笔中缺一笔） | 低于抖动、高于只描一半（实测 `0.818`） |
| 多一笔 | 低于抖动（精确掉；实测 `0.677`） |
| 只描一笔的一小段 | 明显低（覆盖掉） |
| 整张乱涂 | ≤ 0.45（实测 `0.398`；`shape` 只有 `0.472`） |
| **两笔互换顺序** | **与"完美复刻"同分**（差值 ≤ 0.01；笔序项按形状配对，实测两者都是 `0.998`）——玩家看不见"第几笔"，所以不判先后 |
| **手描（2px 抖动 + 3px 弧 + 两端各出头 8px）** | **≥ 0.85**（实测 `0.933`；这是"认真描一份"该拿到的分） |
| 同样的手描**换个笔画顺序** | 与上一行**同分**（差值 ≤ 0.02，实测两者都是 `0.933`） |
| 同样的手描**半途抬笔拆成两笔** | 低于手描但仍高（实测 `0.857`；笔数不等照扣） |
| 手糙一点（5px 抖动 / 6px 弧 / 出头 16px） | ≥ 0.70 且低于认真手描（实测 `0.815`） |
| `stroke_count_strict` 两种取值 | 笔数不等时 true 更严 |
| 空 / 单点 / 长度为 0 的笔 / 点云半径为 0 | 恰好 0，且不抛异常 |
| 判档边界 | `completion` 正好等于某档 `min_completion` 时命中该档；全部不命中 → 失败 |
| 结果只有一处真值（§4.2 / §5.2） | 同一份配方在**任意**一档下产出的 `mxt:talisman` 组件都是**顶层那一份 holder**；档位的 `quality` 只改 `mxt:quality` 组件、改不动定义 |
| 顶层 `talisman` 写坏 id（§4.2） | 加载期报错（`Failed to get element <id>`）、整份配方加载失败，不是运行期空产物 |
| 旧的档位 `talisman` 键（§4.2） | 写在 `result.grades[]` 里**静默忽略**（房规：永不读的键不报错），产物照顶层走 |
| 参考侧缓存 | **待办**：这一版判分器是无状态纯函数、不做参考侧缓存（§4.3 实现现状）；有缓存之后要断言"同一配方算两次结果一致、`/reload` 后新符形生效" |
| `judgement` 整块可选（§4.2） | 同一份符形 + 同一份点列，**不写 `judgement`** 与**写全那六个键的默认值**（`sigma 1.0`、三个权重 `0.25`、`min_stroke_length 0.02`、`stroke_count_strict false`、`preview true`）算出的 `completion` **完全一致**（钉住默认值只有一处真值）。**算法腿已断言后一半**（`Judgement.DEFAULT` 与逐字写出的同一组值给出同一个 `completion`）；"不写整块时 codec 解出默认值"由 `TalismanDrawingRecipe.JUDGEMENT_CODEC.optionalFieldOf(..., DEFAULT)` 一处保证 |
| 预处理常量不是字段（§4.2，第十一问） | 在 `judgement` 里写 `resample_step: 8` / `simplify_epsilon: 3`（未知键）时**加载期不报错、结果与不写时逐位相同**（重采样步长仍是 `2.0`、RDP 阈值仍是 `0.5 × tol_px`）；把两个常量按 §4.3 的公式代入时，同一点列的 `completion` 与常量改动前可复算 |
| 总长度统计（扣颜料依据，§6.4） | 给定点列的总弧长与手算一致；**只认服务端量的那一份** |
| 蘸料（§6.5） | 那一格只收 `mxt:blank_talisman`（朱砂放不进去）；**一次点击取 1 个物品、笔上恰好 +`pigment_per_item`**（颜料放在**玩家背包的格子**里点，工作站没有颜料槽）；**满笔时一个都不取**（只响失败音）；左键与右键都算蘸料，`Shift` 点击照旧走原版搬运；光标上不是符笔时点击照旧走原版（不蘸料）；笔放在槽里、颜料在光标上时同样能蘸 |
| 扣颜料（§6.5） | 给定一笔弧长与 `rate` / `floor` / `cap`，扣量恰好 `clamp(ceil(len × rate), floor, cap)`；余额不足时这一笔被拒且**余额一分不动** |
| 默认不灌灵气（§5.3） | 档位没写 `charge_ratio`（或缺省即 `0`）时，产物的 `mxt:spirit_storage` **是空的**（与 `/talisman give` 同形），且**没有**任何 `insert` 调用；定义里带 `mxt:aura` 条目时它确实发动不了，直到被手灌 |
| 灌注比例（§4.2） | `charge_ratio: 0.5` → 每个 aura 条目灌 `ceil(capacity_units × 0.5)`；`charge_ratio: 0` → **一项都不灌**（不写空值组件、不调 `insert(0)`）；写成 `"0.5 + 0.5 * percentage"` 时跟着完成度走；写成 `"2"`（超范围）时 clamp 到 `1` = 灌满，写成非有限值时记 warn 并按 `0` 取 |
| 完成度进公式（§5.2） | 注入的 `percentage` **恰好等于** `completion`（第九问：没有中间层）；消费字段写 `"percentage * percentage"` 时结果等于完成度的平方；表达式产出非有限值（例如 `"1/0"`）→ 记一条 warn 并按该字段的语义取（`charge_ratio` 按 `0`） |
| 判分与结算分块（§4.2） | 两块各自独立：把 `charge_ratio` / `max_damage` 改写成非线性（如 `"percentage * percentage"`）时**完成度一分不动**、只有产物变；`judgement` 里写产物字段（`grades` / `outputs`）**一律不生效**（判分器不读，产物照 `result` 走） |
| 加载期变量白名单（§4.2） | 消费字段里写成不认识的变量名（如 `"foo"`）→ **加载期拒收**，不是运行期静默变 0；`power` 现在也是"不认识的变量名"（第九问删掉了它），写了它同样被拒 |
| 符纸结算（§6.4） | 画过 1 笔之后取消 / 关界面 / 断线 → **判失败**（跑 `failure_action`），那一格里那张纸**不再回来**；一笔没画就关界面 → 纸**回那一格**，随后由 `clearContainer` 交给玩家 |
| 默认成本（§4.2 / §6.4） | **`costs` 为空**的配方照样要求（并扣掉）那一格里的 1 × `mxt:blank_talisman`；把它替换成 2 张符纸要在 `costs` 里**额外**再写一条 `mxt:item`，最终扣 2 张 |
| 额外成本的结算（§6.4） | 写了 `costs`（例如 1 份朱砂）时：开画后格里少一张纸**和**一份朱砂；一笔没画就关界面 → **两样都回来**；画过一笔再取消 → **两样都没了** |
| 时间检测（§10） | 相邻两笔间隔 < 阈值时该笔被拒；被拒数超阈值时会话判失败（判定用服务端时钟） |
| 最终对账（§10） | 提交的点列与逐笔记录不一致（多一笔 / 少一笔 / 坐标变了 / 顺序变了）→ 判失败 |

> （付账前后各看一次容器，`charged(before, after)` 按槽记），退款只补差额、只补到原来的数量、放不下才回背包；

> （站内 3 张、换一次、关一次，全程**玩家背包里的符纸数不变**）。

## 14. 被否决 / 备选方案的对比（留档，免得下次重新讨论）

| 方案 | 为什么否掉 |
| --- | --- |
| 符形存数据包注册表（`talisman_pattern`）而不是配方 | 用户明确要"走原版配方系统"；而且符形与"消耗什么、产出什么、什么条件能选"是同一件事的三面，拆两张表会出现两处真值 |
| 客户端读配方拿符形 | 26.1 客户端没有配方表（§3.1），做不到 |
| 客户端算分、服务端信 | 直接可作弊；且算法一旦两端各写一份迟早漂移 |
| 页面 JS 采集笔画 | 刷新清状态 + 要跨语言传点（§3.2/§3.3）；Java 侧已经在同一个进程里，没有理由绕一圈 |
| 用 `<svg>` / 贴图当符形 | SVG 无渐变 / 变换 / 文本，且比对要栅格化；贴图比对要服务端读像素 |
| 旋转对齐后再比（DTW.md §3） | §4.4：符箓有正倒，"转过来也算对"会让"誊写"变成"摆姿势"。**平移与缩放反而采纳**（画在纸的哪一处、画多大都不判） |
| 判分只做 Chamfer（两个方向取平均，不做方向与拓扑） | 乱涂与"描成了另一条走向的弧"分辨不出来（§4.3 第 4 步的表） |
| 整场只在结束时提交一次（省流量，上一版方案） | **2026-10-01 被反作弊需求取代**：没有"什么时候画了哪一笔"的记录，时间检测与最终对账都做不了；用流量换反作弊，值（§6.3 / §10） |
| 最终包只带摘要（笔数 + 每笔点数 + 点坐标哈希） | 省一半流量、也能校验；但对不上账时查不出是哪一笔出了分歧，调试与日志都更难——先带整幅（§7） |
