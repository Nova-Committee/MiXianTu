## 1. 结论

**能，而且缺的东西集中在一处**：本仓库已经有一条完整的服务端飞行控制器（挂载 / 每 tick 校验 / 收费 / 下马 / 归属 /
状态同步 / 轮盘入口 / 探针），缺的只是**载具的"样子"**——它今天是个 `NoopRenderer` 的空实体，几何写死在 `EntityType`
注册里，朝向不跟人。

把"样子"补齐不需要新系统、不需要新注册表、不需要新包：**在已有的 `mxt:flight` 条目上加一个可选的 `mount` 子对象**（外形 /
尺寸 / 乘客位置 / 步高 / 坐姿），**换掉一个 `NoopRenderer`**，实体加几个同步字段。老数据包不写 `mount`
就完全保持今天的行为（隐形载具），所以这次改动**没有破坏性**。

必要程度排序：**外观（否则玩家骑的是空气）> 几何与坐姿 > 朝向 > 托管物品 > 手感与边角**。

**截至 2026-09-22，两块已落地**（都只是"看得见"这一层，见 §6.7）：**站姿**（`shouldRiderSit()` → `false`）与**载具可见**（
`FlyingSwordRenderer` 把承载物的物品模型画在脚下）。**几何、朝向、托管、碰撞语义仍是方案**。

## 3. 原作拆解：哪些是**机制**，哪些是**那 10 件东西**

原作 15 个类 1276 行，真正可复用的机制只有**五条**——外观（画承载物的物品模型）、几何（由物品声明）、朝向（跟驾驶者）、无重力（不调
`super.travel`）、托管（拿走→归还）——另加两条口径不同的运动学与一个可选的禁攻；其余全是那 10 件东西的硬编码（逐条核对见 `05`）。

## 4. 今天实机是什么样（改之前的事实）

- 按下轮盘上那格「飞行」→ 服务端建一个 `FlyingSwordEntity` 并把玩家放上去；**玩家骑着一个看不见的东西在飞**（`NoopRenderer`
  ），而且是**坐着**的——平台给 `shouldRiderSit()` 的默认值就是 `true`（`IEntityExtension.java:53-60`，NeoForge 的默认方法），
  `FlyingSwordEntity` 没覆写它。**这两条（看不见、坐着）已于 2026-09-22 各自单独改掉，见 §6.7；本节其余各条仍是改动前的事实。**
- 玩家被放在载具上方 `0.35` 格（`passengerAttachments(0.35F)`），碰撞箱 `0.35 × 0.12`，`maxUpStep()` 是普通 `Entity` 的默认
  `0.0`（`Entity.java:3849`）——**一点台阶都上不去**。
- 移动是每 tick 一个固定位移向量（`speed` 夹 `0.01~1.0`，冲刺 ×1.5），方向来自客户端输入，位移前先做一次 `noCollision` 预测。
- 松开按键立刻停在空中；没有重力、没有惯性、没有倾斜、没有音效粒子。

### 5.2 现有设计稿里**没有**的东西（不要以为漏读了）

全仓 `research/` + `docs/` 检索 `御剑|载具|外观|渲染|托管|几何` 之后：**载具的外观、造型、模型、贴图、per-定义几何、飞行期间的物品归属，一条设计稿都没有
**。唯一沾边的两句是**划界**：

- `research/01_模块划分与依赖.md:39`：`artifact` 的"不应承担"列 = "固定法宝外观和属性"；
- `research/03_功能清单与运行流程.md:56`：飞剑与飞行一行，框架只做"挂载、移动安全检查、消耗与下马清理"，"
  外观、速度、攻击和解锁条件"列给**内容层**。

本设计**不推翻**这两条：它们说的是"框架不要去**固定**外观与数值"，本设计加的是"外观与几何**可被数据声明**"的**表达力**

### 5.3 几何为什么必须由数据给（而不是加常量）

原作是"每件法器各有一套几何"（`ItemFlyingInstrument:19-61`：葫芦 1.6×1.2 偏移 0.9 坐姿、叶 4.0×0.3、舟 5.0×1.4、山河图
6.0×0.2，四件法宝步高无条件 `32.0F`）。本仓库"法器 = 已有物品 + 一份定义"，所以**几何只能挂在定义上**——给某件物品写常量就等于把内容搬进本体，违反
`AGENTS.md` §1 铁律 9。

## 6. 设计草案

原则：**只加可选字段，不改已有语义**。`mxt:flight` 仍然是"这件法器能载人飞行"的唯一声明处，仍然"一个定义最多一条"。

### 6.1 数据形状：`mxt:flight` 加一个可选 `mount`

```json
{
  "type": "mxt:flight",
  "speed": {
    "type": "mxt:conditional",
    "branches": [
      {
        "condition": {
          "type": "mxt:realm",
          "realm": "mxt:qi_refining"
        },
        "value": 0.08
      }
    ],
    "fallback": 0.12
  },
  "costs": [
    {
      "id": "mxt:qi",
      "amount": 2
    }
  ],
  "mount": {
    "visual": "carried",
    "width": 3.0,
    "height": 0.2,
    "ride_offset": 0.5,
    "step_height": 0.2,
    "sit": false,
    "pitch_ratio": 0.5
  },
  "custody": false
}
```

| 字段                             | 类型                                           | 默认                                             | 语义                                                                                                                                                                        |
|--------------------------------|----------------------------------------------|------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `display`                      | 对象：`translation` / `rotation` / `scale` 各三个数 | `[0,0,0]` / `[90,0,-45]` / `[2,2,2]`           | **已落地（2026-09-22，见 §6.7 第九条）**：载具怎么画，取名与语义照原版物品模型的 `display`（`translation` 以 **1/16 格**记、`rotation` 度并按 `rotationXYZ` 复合、`scale` 倍数）。默认值就是"放平 + 剑刃朝前 + 两倍大"，即此前写死在渲染器里的那套 |
| `mount`                        | 对象                                           | 省略 = 今天的碰撞箱（`0.35 × 0.12`、偏移 `0.45`、步高 `0`、不坐） | 载具描述；省了就是零行为变化                                                                                                                                                            |

> 上面那段 JSON 只为说明形状：`NumberProvider` 既接受裸数字/表达式字符串，也接受 `{"type": …}` 分派（
`NumberProvider.java:19-24`），`mxt:conditional` 的字段是 `branches[{condition, value}]` + `fallback`（
`Conditional.java:33-36`），`mxt:realm` 的字段是 `realm` + 可选 `comparison`（`RealmEntityCondition.java:27-30`）。其中
`mxt:qi_refining` 只是占位，境界 id 由包定义。

为什么 `custody` 不放进 `mount`：`mount` 回答"载具长什么样"，`custody` 改的是**物品归属语义**（会牵动三处判权），放在同一层会让读者以为它只是外观开关。

**姿态改由 `display` 声明（本节原写"姿态不设字段"，2026-09-22 按用户要求改掉）**：原先的设想是"模型怎么摆交给物品模型自己的
`display` 段，数据包只管多大、人站哪"。实机走下来这个分工不够用——渲染器里写死的 `+90° 放平`、`45° 剑刃转正`、`×2` 三件事*
*每件法器都想不一样**，而它们又都不属于资源包（资源包管的是"这件物品长什么样"，不是"它当载具时怎么摆"）。所以现在：*
*姿态归 `mxt:flight.display`**（与原版物品模型的 `display` 同名同义，见上表），资源包仍然决定模型与贴图本身。`mount.*`
那组几何（碰撞箱/座位/步高/站坐）**仍未落地**。

骨架直接照 `ItemEntityRenderer`（`net/minecraft/client/renderer/entity/ItemEntityRenderer.java`）。**落地的形状**（
`render/FlyingSwordRenderer.java` + `render/FlyingSwordRenderState.java`）：

| 决定                   | 取值                                                                                                                                                   | 依据                                                                                                                                                                                                                                                                                                                                                                                                                              |
|----------------------|------------------------------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `ItemDisplayContext` | **`FIXED`**                                                                                                                                          | 原版 `item/generated` 的 `fixed` 就是**展示框**用的那套：`rotation [0,180,0]`、**无位移、缩放 1**（解包 `assets/minecraft/models/item/generated.json` 得到）——即"原始大小的卡片，正反面朝南北"。第一版选的 `GROUND` 是**错的**：`ground` 是 `rotation [0,0,0]` + `translation [0,2,0]` + `scale [0.5,0.5,0.5]`，也就是**立着的半大小卡片**，实机里那把剑是竖着插在身体里的（用户截图确认）。`DisplayStandBlockEntityRenderer:40` 用同一个上下文，但它要的正是"立在展示台上"，与本处需求不同                                                          |

| 视觉高度                 | 模型的**最低点**放在 `0.0` 格（= 实体原点 = 碰撞箱底面），再叠 `display.translation`；自动落位那部分取 `REST + scale.z × maxZ`                                                       | 让"看得见的剑"就是"撞得到的箱"：箱 `sized(0.35F, 0.12F)` 是 `y ∈ [0, 0.12]`，剑从 `0` 往上长**多高取决于模型自己**（薄片模型 `0.0625 × 2 = 0.125`，有厚度的 3D 剑模型更高），所以座位也得跟着模型走——见 §6.2 的乘客位置。**这个位移必须写在"转平"之前**：写在之后时 `(0,t,0)` 会被转平那一步转成前后偏移（第四条落地时就是这么写的，所以那一条"箱与渲染重合"实际没成立，见第五条）；`maxZ` 是因为转平后竖直方向 = 模型 Z 的**反向**（`(x,y,z) → (x,-z,y)`），最低点 = `-maxZ`；用 `scale.z` 是因为竖直方向对应的正是模型的局部 Z                                                                              |
| 视觉大小                 | **`display.scale`**（默认 `[2,2,2]`，来自数据包）                                                                                                              | `FIXED` 是**原始大小**（1 格见方的卡片），原作在 1.12 的裸模型渲染上也是 `scale(2.0)`（`RenderFlySword:36`），所以约 2 格长的剑。现在每件法器自己声明，渲染器里没有写死的倍数了                                                                                                                                                                                                                                                                                                             |
| 身体朝向                 | `mulPose(Axis.YP.rotationDegrees(-state.yRot))`                                                                                                      | 新渲染管线**不替渲染器转向**（`EntityRenderDispatcher.submit` 只平移）；照 `AbstractMinecartRenderer:75` 的写法。载具的 yaw 自 2026-09-22 起跟驾驶者（见 §6.2），所以这一层现在是活的                                                                                                                                                                                                                                                                                         |
| 光照                   | 不写                                                                                                                                                   | 基类 `finalizeRenderState` 已经调 `getPackedLightCoords` 填好 `state.lightCoords`                                                                                                                                                                                                                                                                                                                                                      |
| 剔除                   | `affectedByCulling` 返回 `false`                                                                                                                       | 物品模型可以有好几格宽，而碰撞箱只有 `0.35 × 0.12`；按箱子剔除会让剑在还看得见的时候消失                                                                                                                                                                                                                                                                                                                                                                             |
| 空堆                   | 不画（`state.item.isEmpty()`）                                                                                                                           | 没有承载物的载具（探针/别的调用方造的）保持不可见                                                                                                                                                                                                                                                                                                                                                                                                       |

其余要点：

1. 姿态的**基座**（展示框/掉落物/手持）由渲染器选上下文，**微调**（怎么躺、多大、偏多少）由数据包的 `mxt:flight.display`
   声明，物品模型自己的 `display` 段仍然影响最终样子。
2. 不画名牌、不画血量（原版对普通实体本来也不画坐骑血条）。
3. 渲染器是纯客户端代码，进 `MxtRenderers`；`MxtEntityTypes` 不动。

### 6.4 托管模型（`custody: true`）——**它不是纯加法**

原作是"召唤即把物品从手里拿走、副本进载具、落地归还（背包满则掉地上）"。本仓库现状是相反的硬口径：`FlightEventBridge` 每 tick
要求**主手还是那件**（`ownsEquippedArchetype`）。所以打开托管必须同时改三处，否则一按就掉：

| 冲突点                                                               | 症状                            | 处理                                                                                                           |
|-------------------------------------------------------------------|-------------------------------|--------------------------------------------------------------------------------------------------------------|
| `FlightEventBridge:28` + `FlightService.ownsEquippedArchetype:59` | 起剑的同一 tick 就被判 `NOT_OWNED` 下马 | "**载具持有也算携带**"：飞行激活且是本载具托管时放行                                                                                |
| `ArtifactToggleService.of(...)`（读装备栈生成从盘）                         | 飞行中轮盘上那格消失 → **玩家没法落剑**       | 从盘来源加一条"载具托管的法器"，或把托管堆并进 `ArtifactService.carried` 的口径（后者顺带修好储物窗口：`research/32:132` 的 `stillValid` 读的是同一个口径） |
| 归还没人做                                                             | 落剑时物品凭空消失                     | `FlightService.dismount` 是**唯一**出口，归还写在这里；`addItemStackToInventory` 失败则 `player.drop(...)`                   |

**托管的持久化位置**：放 `FlightAttachment`（已序列化 + 已同步给本人）而不是实体 NBT —— 这样"载具实体意外消失"不会吃掉物品，且客户端
**同时**拿到了渲染需要的物品堆与从盘需要的那一格，一个字段解决三件事。代价是两个副本（附件=记录、实体同步字段=展示），必须只把附件当唯一真源。

**必须补的两条出口**（今天无所谓，有托管就是丢东西）：

1. **离线**：载具会被存档、附件也留着，理论上自愈；但要在这一步确认"下一次登录物品确实回到背包"。
2. **死亡 / 重生**：`MxtAttachments:48` 明确 `entityWithoutDeathCopy`（不 copyOnDeath）。要么在死亡事件里先把托管物还回去（玩家物品本来就会掉），要么在
   `PlayerEvent.Clone` 里带过去 —— **二选一，待拍板（§7）**。

**幂等**：`dismount` 可能被同一 tick 的多个调用方打到（原作就是在这里复制物品的），归还前必须先清空记录字段。

### 6.5 明确**不动**的东西

- `speed` 的**单位与夹取**（每 tick 位移，`Math.clamp(0.01, 1.0)`）——文档写的就是"飞行载具速度"，改单位属于倍率语义（§7）。
- `costs` 的结构与结算时机（每 tick、全有或全无）。**但口径要写清楚**：原作"练气筑基 3、其余 6"是**每秒**（20 tick 累加一次，
  `EntityFlyingInstrument:202-210`），本仓库是**每 tick** 结算一次——照抄数字会贵 20 倍，要写 `0.15` / `0.3`或直接用表达式折算。这一条必须进
  `docs/数据包格式.md` 的字段说明与文档站，否则第一个照抄原作的包就会破产。
- 轮盘链路：仍然"请求只说按了哪一格"，方向归服务端。
- `mxt:storage` / `mxt:upkeep` / 认主长按：与飞行无关。
- 实体类型名 `flying_sword`：改名只是好看，会牵动探针与文档，**建议留着**（§7 可议）。
- 玩家入口：维持"轮盘一格"，不加按键、不加右键（§7 若要加，属于先问的事）。

## 8. 不做与推迟

- **不做**：右键起剑（入口维持轮盘）；禁用攻击（原作那条"拿在手里就禁"更像独立法器规则，先不混进飞行；要做就单开一条）；坐骑血条相关代码（原版已不需要）；原作那套
  `Power`/`JingJieNum` 字符串键与境界数字；把飞行载具做成"多种实体类型"。
- **推迟**：惯性/加减速；起飞、飞行、落地的音效与粒子；多乘客与座位数；载具被攻击/被主人打一下收回；`pitch_ratio`
