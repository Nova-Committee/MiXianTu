## 1. A. 通用逻辑未完成（`GEN`，3 项，A1 / A2 / A3 均已关闭）

### A1 ✅ 已于 2026-09-25 关闭 —— 「子境界 / 层数」的条件

- **当时的缺什么**：注册的 **65 项 `entity_condition` 里没有任何一项能比较子境界**（`registry/MxtEntityConditions.java:17-82`）→ 纯条件式的「层数门槛」没有内建条件可用。
- **当时的已核事实**：`minor_stages` 可写整数（1–1024）或组件数组，并且已经是内置公式变量 `minor_stage`（`data/cultivation/RealmStage.java:67`、`registry/MxtFormulaVariables.java:152,166-167`）；`breakthrough_exp` / `max_experience` 的公式在带 `ResourceSubject` 的上下文里求值（`runtime/cultivation/CultivationService.java:219-232`，重入守卫 `RESOLVING_MINOR_STAGE` 就是为此而加）。
- **当时的复核修正（口径收窄）**：缺口比"没有内建条件"更深一层——**条件侧的字段形状里根本没有「取当前链的阶段 + 进度」这个入参**：`mxt:realm` 只落在阶段 holder 或登记链 rank 上，`mxt:resource_compare` 只拿到一个数。所以不是"少写一条条件"，而是条件与 `minor_stage` 公式**不在同一条算术上**。
- **关闭方式（用户拍板：不新增类型，给现有 `mxt:realm` 加字段）**：`mxt:realm` 新增可选 `min_minor_stage`（0 起，与公式变量同一套编号）。它读的不是实时进度，而是 `spirit_identity` 附件里那份**只增不减的层数记录**（`minor_stage_records`），所以「炼气期层数达到过 500」这类门槛在突破离开之后仍然成立——这正是本体 `LayerNum >= 500` 需要的单调语义。
- **现在的实现点位**：`data/condition/builtin/entity/RealmEntityCondition.java`（字段 + 记录读取）、`attachment/SpiritIdentityAttachment.java`（`minor_stage_records` / `minorStageRecord` / `raiseMinorStageRecord`）、`runtime/cultivation/MinorStageService.java`（刷新记录）、`runtime/cultivation/CultivationService.java`（加进度与突破成功后各刷一次）、`command/server/RealmCommand.java`（`/realm set` 后刷一次）。
- **影响与替代**：本体（层数门槛）现在可以直接写条件；原先的替代（`mxt:js`、自建 resource 计数器）仍然可用，但不再是唯一出路。逐条语义见 `research/49_灵根多元素与子境界条件设计.md`。

### A2 ✅ 已于 2026-09-25 关闭 —— 寿元没有闭环

- **当时的缺什么**：`LifeSpanService` 只有倒计时 + `LifeSpanEvent(Pre/Post)`，**「寿元耗尽 → 死亡 / 转世」没有任何默认实现**；同时**没有任何把 `lifespan_remaining` 写成正值的生产者**。
- **当时的已核事实**：`lifespan_remaining` 默认 `-1`（`attachment/SpiritStatsAttachment.java:13`），全仓唯一写入点是 `LifeSpanService`，且只在原值 `> 0` 时递减（`runtime/cultivation/LifeSpanService.java:19-28`，tick 挂在 `runtime/cultivation/LifeSpanEventBridge.java:14`）；`LifeSpanEndEvent` 在 `src/main` 里**零 Java 业务监听者**（`compat/kubejs/MxtKubeJsPlugin.java:84-85` 是唯一监听者，只做转发）。
- **当时的复核修正**：「没入口」**只在 Java 层成立**——事件已转发给 KubeJS 的 `lifespanEnd`（`compat/kubejs/MxtKubeJsEventDispatcher.java:311-313`，文档见 `docs/guide/kubejs/api.md`），脚本侧还能经公开的 `spirit()` / `setLifespanRemaining` 写入正值。真正缺的是**两条**：耗尽后的默认后果，以及基座自己的"获得寿元"生产者。
- **当时需要补全的内容**：①`LifeSpanService` 在计数归零且 `Pre` 未被取消时缺一个默认分支；②一条给 `SpiritStatsAttachment` 写正值的注册点；③可选：境界 → 寿元的默认换算，否则闭环永远从 `-1` 起算。**三条都做了。**

### A3 ✅ 已于 2026-09-25 关闭 —— 灵根只能绑单一元素

- **当时的缺什么**：`SpiritRoot.element` 是 `fieldOf` **必填单值**（`data/cultivation/SpiritRoot.java:28,38`，类注释明写 always binds exactly one element）→ 一个灵根**不能绑两个元素**。
- **当时的复核修正**：`conflicting_elements` 只表达"不能共存"，**不表达"同时持有几个、各占多少"**；真灵根 / 伪灵根 / 废灵根即使要近似，也还缺一个多元素容器。
- **关闭方式（用户拍板：列表 + 占比权重、旧字段删除）**：`element` 删除，改为 `elements`（列表中每项是裸条目 id 或 `{element, weight}`，必填且非空；空数组、重复元素、非正权重、权重和不正都是加载错误）。**权重是占比不是倍率**，读取时按总和归一化（`[1,1]` 与 `[0.5,0.5]` 等价）。名下的读法一次定死——持有哪些元素取并集（`Elements.of`）、修炼亲和取各元素浓度的**加权平均**、对立惩罚取各元素对立度的**加权平均**、`element_ability_modifier` 一条灵根只算一次、互斥按集合双向判定；这三处（并集 / 能力加成 / 互斥）与元素关系倍率一律**不看权重**。命令与信息面板逐个元素显示、权重不为 1 时后缀数值。老包的 `element` 会**加载失败**（未发布阶段允许不兼容）。
- **现在的实现点位**：`data/cultivation/SpiritRoot.java`（形状 + 校验 + `conflictsWith`）、`runtime/cultivation/Elements.java`（并集）、`runtime/cultivation/CultivationAffinity.java`（亲和 / 惩罚 / 能力加成）、`command/server/SpiritRootCommand.java` 与 `screen/information/InformationManager.java`（显示）、`compat/kubejs/MxtKubeJsApi.java`（"这个灵根算不算数"= 任一元素是活的）。
- **影响与替代**：灵根 / 本体。原先只能拆成多个单元素灵根定义近似，现在一条定义就能表达混合灵根与"火七水三"这类占比；"按占比分别加成元素亲和倍率"（权重进伤害管线）仍**不做**，要做需另开一稿。逐条语义见 `research/49_灵根多元素与子境界条件设计.md`。

### B2 ✅ 已于 2026-09-25 关闭 —— 目标选择器只有 3 种

- **当时的缺什么**：`ability_target_selector_type` 只有 `self` / `area` / `js`（`registry/MxtAbilityTargetSelectors.java:16-18`）；**无射线、锥形、最近 N、随机 N**。
- **当时的复核修正**：`area` 是球体范围全选，无排序、无数量上限、无朝向过滤；`mxt:js` 只实现两参数 `select`，从展示台这类非施法者位置发动时会丢掉发生位置。该注册表是普通静态注册表，别的 Java 模组可以加类型，缺的只是本体自带的那几种。
- **关闭方式（用户拍板：两个几何选择器 + `area` 加限量/排序；几何 + 方块遮挡、不穿墙）**：新增 `mxt:ray`（沿视线的圆柱：`length` + `radius`）与 `mxt:cone`（沿视线的锥体：`length` + 半角 `angle`）；`limit`（默认不限）与 `order`（`nearest` / `farthest` / `random`）做成三种范围选择器共用的筛选，由 `TargetSelector.limited(...)` 一处实现；射线与锥形都先沿视线中心线做方块裁剪，**不穿墙**（锥体侧面不做逐目标遮挡）。
- **现在的实现点位**：`data/ability/target/RayTargetSelector.java`、`ConeTargetSelector.java`、`TargetOrder.java`、`TargetGeometry.java`；`AreaTargetSelector` 新增 `limit` / `order`；`registry/MxtAbilityTargetSelectors.java` 注册 `ray` / `cone`。
- **影响与替代**：神通 / 功法 / 符箓 / 法器的选敌现在可以直接写"前方一条线""锥形横扫""最近三个"；原先的替代（`area` + `mxt:target_condition`、`mxt:js`）仍然可用。**已知边界**：`mxt:js` 仍不认 `origin`（未在本次范围内）。逐条语义见 `research/50_目标选择器与轮盘扩展点设计.md`。

### B3 ⚪ 载具实体类与渲染器硬编码

- **缺什么**：座驾实体类与 renderer **硬编码为 `mxt:flying_sword`**，换"实体种类"必须写 Java。
- **已核事实**：`FlightService` 直接 `new FlyingSwordEntity(...)`（`runtime/artifact/FlightService.java:68`）、用 `instanceof` 判定（`FlightService.java:130,233`，同类判定还在 `command/server/FlightCommand.java:32` 与 `registry/MxtKeyMappings.java:95`）；renderer 绑定唯一（`registry/MxtRenderers.java:31`）。**几何 / 座位数与落点 / 坐姿 / `display` 变换 / 尾迹都已数据驱动**（`data/ability/type/MountAbilityType.java:42-53`、`runtime/artifact/FlyingSwordEntity.java:219-228`、`render/FlyingSwordRenderer.java:50-52`）。
- **复核修正**：外部清单把证据行写在 `FlyingSwordEntity.java:219`（那其实是数据驱动的 `getDimensions`），真正的硬编码点是 `FlightService.java:68,130` 与 `MxtRenderers.java:31`。结论不变：**外观可换，行为不能换**。
- **需要补全的内容**：一个"载具种类"的注册点，或 `mxt:mount` 上的 `EntityType` / 工厂字段；把上述四处 `instanceof` 换成按该类型的判定，并约定按类型解析 renderer。

### B4 ✅ 已于 2026-09-26 关闭 —— 符箓没有使用次数 / 耐久 / 触发条件

- **当时的缺什么**：`talisman` 注册表只有 `name` / `description` / `abilities` + `aura_cost`（`data/Talisman.java:30-32,35-40`）；**无** `uses`、**无** `use_condition`、**无**品阶字段。
- **复核修正**：外部清单说的"现有机制：KubeJS，或附属自带 Java 物品"不完整——**物品绑定层已经能表达一部分**：`mxt:item_binding` 的 `conditions` + `quality_chain` 与 `ItemQuality.condition` 会在 `RightClickItem` 之前拦下不满足条件的物品（`data/item/ItemBinding.java:31-38`、`runtime/item/ItemQualityService.java:175-178`）。但那些 matcher 读不到符箓组件，粒度是"**整个 `mxt:talisman` 物品**"而不是"某一张符箓定义"；次数当时只能靠堆叠数量表示（每次发动固定消耗一个载体）。
- **关闭方式（用户拍板：耐久上限 + 每次消耗两点旋钮、门槛用 `Cost` 表达、品阶照品质那一套）**：`Talisman` 新增**四个可选字段**——
  1. `durability`（默认 0＝不靠耐久记账，仍是"一次一张本体"）与 `consume`（默认 1，每次激发扣几点，必须 ≥ 1；`durability` 为 0 却写了别的值是加载错误）。上限按铭刻条目**相加**，写进 stack 的**原版组件三件套**（`minecraft:max_damage` + `max_stack_size: 1` + `damage: 0`：少任何一件，载体不是"不可损伤"就是被原版按"既耐久又能叠放"拒绝），所以耐久条、原版的修复与附魔、`mxt:durability` / `mxt:relative_durability` 物品条件与 `mxt:damage_item` 物品行为直接可用；耐久只属于**单张**载体（`/talisman give count` 给多份单张），**扣满上限那一次销毁载体并把没烧掉的灵气按灌注价退回给行为者**。
  2. `costs`（`Cost[]`）＝向**持有者**收的那笔代价，与 `ability.costs` 同一套形状与同一个 `CostTransaction`：激发前先规划，**付不出就拒绝这次激发**——"灵力不足无法使用"这类门槛因此用 `Cost` 表达，**本体不再另立条件字段**；规划只读，真正扣除发生在至少一道能力真的发动之后。
  3. `quality`（`Holder<ItemQuality>`，符纸 / 符宝分档）：由 `ItemQualityService.definitionDefault` 解析成载体的默认品阶，tooltip、`mxt:quality`、品质自己的 `condition`、沿品质链升级全部照常，框架不往 stack 写品阶组件。一张载体铭刻多条时取**第一条声明了品阶**的条目。
- **现在的实现点位**：`data/Talisman.java`（四个字段 + 校验）、`runtime/talisman/TalismanService.java`（`durability` / `durabilityCost` / `applyDurability` / `quality` / 代价的 plan+commit / 发动后的 `spend` 与 `refund`）、`data/cost/context/CostOrigin.java`（新增 `TALISMAN`）、`runtime/item/ItemQualityService.java`（品阶解析加了符箓一支）、`command/server/TalismanCommand.java`、`runtime/talisman/TalismanTooltipAppender.java`（tooltip 一行"耐久：剩余 / 上限"）、测试夹具 `mxt_test:durable_sigil` / `graded_sigil` / `refund_sigil` 与 `/mxt_test talisman`（无玩家也能跑）。
- **已核事实（实机验证）**：`/mxt_test talisman` 在专用测试服务端（无玩家、探针生物驱动）通过：上限 5 / 每次 2 从定义读出、三发后按 4→越限销毁、代价付不出时激发根本不发生、付得出时恰好扣 5、品阶经品质模块解析为 `mxt_test:poor`、耐久耗尽那次把 2 点灵气退回。
- **影响与替代**：符阵（**117 个符箓物品**，分符纸 / 符宝等档，有耐久、有"灵力不足无法使用"的门槛、飞行符有 36000 tick 持续时间）——**三样现在都能纯数据驱动**：耐久写 `durability` / `consume`，门槛写 `costs`，分档写 `quality`。仍**明确不做**的是"按定义写任意 `EntityCondition`"（`costs` 覆盖了它的实际用途：付得出就能用）。

### B5 🟠 契约不能给主人授予能力 / 加成

- **缺什么**：`contract_type` 有 `owner_condition` / `creature_condition` / `follow_action` / `combat_action` / `release_action` / `death_action` / `costs` / `max_owned` / `recall_cooldown`，但**没有任何"授予主人"的代码分支**。
- **已核事实**：四个 `*_action` 的宿主实体都是**生物**（`runtime/creature/ContractEventBridge.java:52,67`、`runtime/creature/ContractService.java:88,130`）；`owner_condition` 只对主人求值、`costs` 只是主人付钱（`ContractService.java:52,63-64`）；`grant_ability` 落在 `ctx.entity()`（`data/action/builtin/entity/GrantAbilityAction.java:28-29`）→ 会给到生物。
- **复核修正**：唯一能间接落到主人身上的通道是 `combat_action` 的 target 恰好是主人（灵宠打主人时），不是"授予主人"的分支。替代路径比外部清单写的更具体：`SpiritContractEvent.Pre/Post` 已转发给 KubeJS 的 `spiritContract` 事件组（`compat/kubejs/MxtKubeJsPlugin.java:95-96`），脚本或 Java 监听者在绑定时即可给主人 grant。
- **需要补全的内容**：`contract_type` 需要一个**以主人为目标**的动作通道——例如 `owner_action`（绑定 / 解除 / 死亡时对 owner 执行 `EntityAction`），或给现有 `*_action` 增加目标选择参数，并让动作上下文能引用 owner。
- **影响与替代**：神通与妖兽（**4 只灵宠的全部价值就是给主人的一条 +10% 加成**）。纯数据包无法表达；**可替代**：KubeJS `spiritContract` 事件或 Java 监听 `SpiritContractEvent`。

### B6 🟠 没有"肩挂"设施

- **缺什么**：基座**没有任何"生物挂在玩家肩上"的设施**。
- **已核事实**：`bi_entity_action.mount` 的语义是 `ctx.actor().startRiding(ctx.target())`（`registry/MxtBiEntityActions.java:23`）——**施放者骑到目标身上**；把 actor 写成生物、target 写成玩家，生物只能成为玩家身上的**普通乘客**（原版座位与碰撞箱位置）。玩家侧唯一的挂载渲染层画的是 `ItemStack`，不是实体（`render/accessory/BackWeaponRenderer.java:39-45`，注册见 `registry/MxtRenderers.java:63-71`）；座位附件只长在载具实体上（`runtime/artifact/FlyingSwordEntity.java:222-226`、`registry/MxtEntityTypes.java:20`）。基座也没有任何记录"某生物挂在某玩家哪个槽位"的附件或姿态数据。
- **需要补全的内容**：一条生物挂到玩家身上的新通道——记录宿主与槽位 / 偏移的附件（或给 `bi_entity_action.mount` 增加座位方向与偏移参数），加上玩家侧的实体渲染层或乘客附件。`mxt:mount` 是"玩家骑载具"，方向相反，**无法复用**。
- **影响与替代**：神通（4 只灵宠是**肩挂**形态）。**可替代**：附属自写 Java（普通乘客 + 自定义渲染），或把灵宠收进 `mxt:spirit_beast_bag` 这种"收进物品"的近似表现。

### B9 ✅ 已于 2026-09-25 关闭 —— 轮盘"来源页"不可扩展

- **当时的缺什么**：`WheelSource` 是 **5 值枚举**，第三方**加不了新页**；`WheelMenuContent.register` 是**"最后一次注册获胜"的单槽位**，且基座自己已占用；服务端 `switch` 只认 `ABILITY` / `AURA` / `BEHAVIOR` 三种 kind。

- **关闭方式（用户拍板：接口进 `api/` + 注册表 + kind 自处理）**：`api/WheelSource` 与 `api/WheelEntryKind` 成为**接口**，`runtime/wheel/WheelSourceTypes` / `WheelEntryKinds` 是代码注册表（内置项在静态块装入、先注册者胜、只在游戏线程读）；**页顺序＝注册顺序**；`WheelMenuContent.register(source, provider)` 按来源 id **多槽位**，第三方注册不再覆盖内置页；`WheelActionC2SPayload` 与 `WheelSlot` 的来源/类型字段改成 **id 字符串**（未知 id 在服务端被拒、在存档里读成空格子，都不是解码失败）；"按下做什么"从 `WheelService` 的 `switch` 搬进 kind 自己的 `trigger`。
- **现在的实现点位**：`api/WheelSource.java`、`api/WheelEntryKind.java`、`runtime/wheel/WheelSourceTypes.java`、`WheelEntryKinds.java`、`WheelService.java`、`WheelSources.java`、`screen/wheel/WheelMenuContent.java`、`screen/wheel/content/WheelContent.java`、`network/ServerNetworkHandler.onWheelAction`。
- **影响与替代**：助手 / 轮盘（界面入口的可扩展性）。原先"新增一页"做不到，现在内容模组实现一个接口 + 注册即可。**明确不做**：页顺序不可指定（就是注册顺序）、第三方 kind 的候选项暂时进不了配置界面的两个池子（见 `research/50` §5）。

## 4. U. 原「未确认」三项的复核结论

|---|---|---|---|
| **U1** | 突破是否支持**概率失败** | **不支持，且不需要新增字段就能表达**——`realm_stage.breakthrough` 只是一个 `CultivateConditions`（`data/cultivation/RealmStage.java:68`），后者只有 `conditions` / `triggers` / `action`（`data/cultivation/CultivateConditions.java:20-27`）；运行期判定是确定性的：进度、条件、能力要求全过即提交，任一不过就 `rejected` 并执行 `fail_action`（`runtime/cultivation/CultivationService.java:86-105`），`fail_action` 是"被拒后的补偿"，不是随机失败分支。**要概率**：把 `mxt:chance` 放进 `breakthrough.conditions`（`data/condition/builtin/entity/meta/ChanceCondition.java:18`，用实体随机数，失败落回 `fail_action`） | 同左 |
