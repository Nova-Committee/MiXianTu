## 1. 结论

当前实现已停止向实时物品栈写入临时 consumable，使用 `ItemUseCycle` 与解析事件建立运行期会话。用途判断、一次完成与生命周期清理由统一服务承担。原生组件不参与所有权猜测。

## 2. 已关闭问题（保留原始证据）

### ~~TU01：HOLD 完成被当成丹药消费，药效与真实消耗脱节~~（已修复）

位置：`runtime/item/ItemBindingService.java:252–265`、`runtime/item/PillUseService.java:59–60`、`runtime/hold/HoldService.java:84–86`。

`PillUseService` 明确让已声明且认领当前物品的 HOLD 优先，不为它建立 PILL 周期。HOLD 在服务端 Start 时移除临时 `consumable`，因此完成时原版 `Item.finishUsingItem` 返回原栈，不调用 `Consumable.onConsume` 的 `stack.consume(1, user)`。

但原版仍发布 `LivingEntityUseItemEvent.Finish`。`ItemBindingService.onUseFinish` 不辨别本次是阅读、灌注还是进食，只要输入副本能解析到丹药，就登记次数 / 冷却并执行药效。`Owner` 隔离没有传递到这层业务结算。

具体触发：给玉简附加 `mxt:pill` 的 `on_consume` 或丹毒配置，保持非零阅读时长；完成阅读后玉简仍在，丹药效果却执行。仅有组件而无 `pill_binding` 时没有绑定次数上限，可重复阅读领取效果。一般物品绑定的完成行为是否应执行是另一个问题，不能为了阻止药效把所有完成行为一起禁掉。

建议：以本次使用会话的用途判断是否进入丹药结算，保留真正原生食物及普通物品补入 PILL 周期的消费入口。不能只检查 `Owner.PILL`，否则原本自带 `consumable` 的丹药载体会被漏掉；也不能通过库存是否减少判断，创造模式合法消费不减数量。

### ~~TU02：回收范围和实例比较不足以保证临时组件不持久化~~（已修复）

位置：`runtime/hold/TemporaryUseComponent.java:49–56,69–73`、`runtime/item/PillUseService.java:70–88`。

`takeBack` 先删除记录，随后仅扫描持有人当前背包，其他实体只看两手。原栈、分出的栈、菜单光标、掉落物或另一持有人不在这个范围中时，记录已经消失，组件却仍留在物品上。

**丢弃路径**：普通物品被补成丹药并使用后，按 Q 或 Ctrl+Q 丢出。`ServerPlayer.drop` 经 `Inventory.removeFromSelected` 分离栈，再创建掉落物；`ItemStack.copy/split` 的组件值沿用原实例。PILL 的 Stop / 后续 Post 只能清持有人背包，无法清掉落物。部分丢弃即使清掉剩余栈，已经分出的那份仍带组件。死亡掉落也不能靠下一次实体 tick 保证回收。

**退出路径**：`PlayerList.remove` 先发 `PlayerLoggedOutEvent` 后保存玩家。本模块没有退出回收监听；使用中的原版 `minecraft:consumable` 被保存。它在 `DataComponents` 中明确登记了 `persistent(Consumable.CODEC)`，不是瞬时组件。重登解码得到等值的新实例，`== record.component()` 不成立；新进程则连记录也没有。`PillUseService.arm` 又因物品已经有 `consumable` 而跳过，遗留值不能被下一次正常武装自动认领并清理。

建议：临时修改须追踪实际写入对象与恢复状态，并覆盖分离 / 转移、实体移除和保存边界。跨序列化不能继续只靠实例比较。若保留持久化原版组件作为驱动，必须解决保存前恢复或重载后的可靠识别；只把表清空、改弱引用或把 `==` 换成 `equals` 都不能解决，后者还会误删等值原生组件。

### ~~TU03：HOLD 没有完整的回收生命周期~~（已修复）

位置：`runtime/hold/HoldService.java:64–98`、`runtime/item/PillUseService.java:81–88`。

全仓唯一的 `takeBack(..., HOLD)` 位于服务端 Start；客户端 Start 直接返回。长按停止、完成、换手、失去使用状态、断线或关服都没有 HOLD 回收。PILL 虽有 Finish / Stop 和非使用状态的 Post 兜底，该兜底只处理 PILL。

客户端会在点击及使用 tick 中写组件；一次正常的服务端长按只在同一调用中写入再移除，最终槽位可能与开始前完全相同，并不保证额外下发一份槽位更新。服务端回收不能代替客户端回收。客户端临时组件和 UUID 记录因此可能在阅读结束后保留，物品组件比较及后续用途判断都可能继续读到它；客户端遗留本身不等于生存模式服务端物品必然被吃掉。

服务端也有启动失败的漏口：组件先在 RightClickItem 中写入，如果物品自身 `use` 没有调用原版 Start，或者 Start 被更高优先级监听器取消，唯一的 HOLD 回收点不会执行。此后没有 HOLD 空闲兜底，原栈可以带着临时组件进入背包或保存。清理不能只挂在可能被取消、默认不接收已取消事件的普通监听器上。

建议：两端各自维护从尝试开始到结束的会话，统一涵盖未启动、正常完成、提前停止、使用状态消失、实体离开和会话关闭；客户端结束回收不能依赖 Finish，因为正常完成主要由服务端驱动。

### ~~TU04：重复写入只保留最后一份恢复记录~~（已修复）

位置：`runtime/hold/TemporaryUseComponent.java:41–43,77`；调用方 `runtime/hold/HoldService.java:95–98,122–128`。

表值为 `EnumMap<Owner, Written>`，每个 Owner 只能保存一个 `Consumable`。第二次 `write(holder, otherStack, newComponent, sameOwner)` 直接 `put`，既不清理旧栈，也不累计写入对象。两份栈仍在背包时调用 `takeBack`，只会移除后一份，前一份保留且已无记录。

调用接口没有“同一 Owner 只能写一份栈”的约束或拒绝结果。客户端路径还明确尝试维护使用栈和当前手部栈，不能把一条 Owner 记录视为所有副本的写入凭据；跨次阅读也可能被 TU03 留下的旧记录影响。

建议：按会话追踪所有实际写入目标及各自组件；对同一目标的重复武装做幂等更新，或明确先关闭旧会话再建立新会话。不能一边允许多个目标，一边只记最后一个组件。

### ~~TU05：`ours` 仍按形状猜测原生组件的所有权~~（已修复）

位置：`runtime/hold/HoldService.java:124–139`、`runtime/hold/TemporaryUseComponent.java:42,56`。

`ours` 只看无粒子、空消费效果、静音及相同动画，不核对这份组件是否由本模块写入，时长也不比较。数据包或其他模组合法写入相同特征的原生 `consumable`，只要物品同时匹配 HOLD，就会被当作本模块组件覆盖。

后续回收的实例比较没有保护原值：它只能证明当前值是本次覆盖后写入的值，而记录中未保存被覆盖的组件。Start 回收会直接 `remove`，物品原先的时长、消费能力等原生状态被抹掉；这与“自带 use 的物品不覆盖”的现有契约冲突。

建议：已知临时值通过真实所有权记录识别；覆盖原值时必须保存并准确恢复原来的组件 patch。未知原生值即使形状相同也不能被认作自己写入。

## 4. 修复前的验证与边界

隔离复现使用**原封不动的当前 `TemporaryUseComponent.java`**，其余 Minecraft 类型替换为只提供本类所需 API 的最小替身，由 JDK 25 编译执行。脚本位于忽略目录 `build/temporary-use-audit/run_repro.py`：

- 复现同 Owner 第二次写入后，第一栈残留、第二栈被清理且记录已不存在。
- 复现原栈离开持有人容器后，组件残留且记录已不存在。
- 复现同 UUID 重登、组件等值但实例不同后，清理失败且记录被丢弃。
- 对照检查 HOLD / PILL 互相隔离、服务端回收不消耗客户端记录，均成立。

这些只验证记录算法，不代替真实区块、玩家、网络或存档测试。TU01、TU03、TU05 的真实触发结果尚未运行 GameTest 或客户端；TU02 的实际丢弃 / 退出顺序由当前原版源码交叉确认。既有 `alchemy/pill/plain_item_armed` 和 `item/jade_slip/read_cycle` 覆盖普通服务端完整使用，不覆盖上述混合用途与异常生命周期。

审查阶段执行 `gradlew.bat compileJava compileTestModJava --console=plain` 成功，退出码为 0；日志见 `build/temporary-use-audit/compile.log`。编译通过不代表上述开放问题已修复。该隔离复现发生于实施修复前，没有启动 GameTest 或客户端；当前修复状态见第 3 节。

待实现时应补的回归：长按与丹药叠加不白拿效果、普通及原生丹药仍能消费、部分 / 全部丢弃、服药中退出重登、同 Owner 多目标、启动拒绝、客户端结束及槽位替换、原生同形组件保留。创造成果允许不减物品，不能误判成没有合法消费。

## 5. 临时组件方案复评

按用户提出的降低 Mixin 侵入要求，重新核对 `LivingEntityUseItemEvent`、原版物品使用、组件复制、存档与网络编码。结论及源码入口见 [103 设计稿 §7](../103_运行期物品使用会话设计.md#7-临时组件与事件方案复评)。

统一所有权记录、幂等恢复、`AutoCloseable` 与完整事件清理可以改进原方案，但不能自动恢复已流入副本或序列化结果的组件。直接恢复原方案并只补这些清理，会重新暴露 TU02；改用 `Finish` 才扣除又会改变剩余物品与冷却的处理顺序。

复评后按用户要求，在运行期会话方案上实施低侵入优化：四个 HEAD 提前返回改为两个原调用包装、两个返回值兜底，使用平台已有的 MixinExtras，不新增依赖。生命周期继续使用事件；完成回调仍在原版剩余物品和冷却包装以内。准备后或使用中加入原生使用组件会让出会话；原生完成已替换或改变栈时，不重复执行用途完成。

主代码与探针编译通过，本轮 **32/32** 组 GameTest 全部通过：会话 12、丹药 11、玉简 2、法器 Hold 6、灵气物品 1，5 个 Gradle 退出码均为 0；日志为 `build/temporary-use-audit/fallback_*.log`。210 页中英配对、站内链接和文档构建均通过。TU01–TU05 保持关闭，第 3 节保留上一轮验证记录；本轮探针边界及详细日志见设计稿 §7.5。客户端、真实断线重登和已有存档污染的边界不变。
