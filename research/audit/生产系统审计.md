审计对象：本仓库（NeoForge 26.1.2，修仙运行时**基座**）。
方法：逐文件读 `src/main` 实际 Java 源码，再对每个字段做全仓 grep 找消费者；"内容需要什么"一侧取自
本地分析工作区（不在本仓库内）的 `analysis/`（15 个 1.12.2 内容模组的反编译分析）与 `analysis\registries\`。
所有结论给 `文件:行号`。凡"未找到消费者"的，都是对该 accessor 做过全仓 grep 的结果。

`configureAuraCosts`(`:138-142`) 在"花费表变了"时**清空已灌灵气**。只要配方写的灵气量依赖玩家
（如 `level`、境界、资源），两张表就不同 → 已灌灵气被反复清零，玩家永远灌不满。

## 二、共性与差异

### 2.1 Q1：有没有**一个**通用「工位 + 配方 + 输入 + 成功判定 + 花费 + 失败产物」抽象？

**没有。四个系统四种形态，其中两套是"平行但互不共享"的 bespoke 复制品。**

| 系统   | 会话/状态类                                                                                                                     | 是否有统一接口                                                                                     | 事件                                      | KubeJS 事件组       |
|------|----------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------|-----------------------------------------|------------------|
| 锻造   | `ForgingPlan` + `ForgingSession` + `ForgingTableState` + `StartupMaterials` + `ForgingCancellation` + `ForgingRateLimiter` | `ForgingSurface`（**只覆盖槽位与放置规则**，`ForgingSurface.java:14-89`），不覆盖配方/结算                       | `ForgingEvent` 7 相（`ForgingEvent.java`） | ✅ `forging`      |
| 炼丹   | `AlchemySession` + `AlchemyWorkstationState`                                                                               | `AlchemyWorkstation`（覆盖 `alchemyState/furnaceTier/temperature/setChanged`，`:25-32`；**零实现**） | `AlchemyCraftEvent` 2 相                 | ✅ `alchemyCraft` |
| 灵材合成 | **无**（block entity 每 tick 循环 + 菜单重复实现）                                                                                     | 无                                                                                           | **无**                                   | ❌                |
| 符箓   | **无**（组件 + 静态服务）                                                                                                           | 无（借 `AuraItemAccess`/`HoldBinding`）                                                         | 借 `AbilityUseEvent`                     | ❌                |

**两套 bespoke 的重复度（可直接对照）**：

| 职责                  | 锻造                                          | 炼丹                                                         |
|---------------------|---------------------------------------------|------------------------------------------------------------|
| 配方快照                | `ForgingPlan`(`ForgingPlan.java:15-16`)     | 无（炼丹直接持 `RecipeHolder`）                                    |
| 会话快照 record         | `ForgingSession.Snapshot`(`:104-113`)       | `AlchemySession.Snapshot`(`:133-143`)                      |
| 可持久化状态              | `ForgingTableState`(`:22-30` MAP_CODEC)     | `AlchemyWorkstationState`(`:17-23` MAP_CODEC)              |
| `StartResult`       | `ForgingService.StartResult`(`:191-203`)    | `AlchemySession.StartResult`(`:101-113`)                   |
| `Failure` 枚举        | `ForgingService.Failure`(`:134-189`，22 项)   | `AlchemySession.Failure`(`:99`，6 项)                        |
| `lock/update/clear` | `ForgingTableState.java:95-120`             | `AlchemyWorkstationState.java:55-83`                       |
| 结算结果 record         | `ForgingResultComponent`（写进物品）              | `TickResult`(`AlchemyWorkstationService.java:123-145`)     |
| 材料匹配                | `StartupMaterials.resolve`(`:386-407`)，数量语义 | `sameMultiset`(`AlchemySession.java:91-97`)，**只比 ID，不比数量** |
| 花费/代价               | `ResourceCost` 逐次扣                          | ❌ 无逐次代价（只有开炼门禁）                                            |
| 失败产物                | `FailureSettlement`(`:205-225`，两个随机比)       | `failure_outputs`(`:78`)                                   |
| 取消                  | ✅ `cancel`(`:282-300`)+可换策略                 | ❌ 无                                                        |

结论：**"工位/配方/输入/结算"这一层是每个系统各写各的**；唯一真正共用的只有更底层的
`ResourceCost`、`FormulaContext`、`EntityAction`/`BlockAction`、`NumberProvider` 与注册表装载。
灵材合成甚至**连会话都没有**，且把配方匹配抄了两份。

### 3.4 成功率掷骰（通用）

  升级链内容（哪张符升哪张、淬炼数值表）**数据包**。

### 4.4 文档/代码的次要口径差异（低风险，列出以免误判）

- `ForgingMethod.java:40` 注释写显示名来自 `mxt.talisman.<path>` 风格的键；实际
  `DefinitionText.java:15-17` 生成 `talisman.<ns>.<path>`（`docs/数据包格式.md:1345` 是对的，**代码注释错**）。
- `ForgingPlan.CODEC`(`ForgingPlan.java:17-26`) 只存 8 个字段，`optimalSteps` 在构造器里**重算**
  (`:28-32,89-114`)；`research/06:64`、`research/16:300` 说最优步数"随 plan 冻结/存进 NBT"，
  措辞上不准确（`plan` 确实持久化于 `ForgingTableState.java:25`，但最优步数是重启后重算的）。
- `ForgingWorkstationService.java:188-190` 在检查 `max_steps`/条件/资源**之前**就调
  `ForgingRateLimiter.tryAcquire`，而该 limiter 在被允许时立即写时间戳(`ForgingRateLimiter.java:35-37`)
  → **一次被拒的锻打也会启动冷却窗口**。没有任何文档句子正面否认这点，属"文档未覆盖"而非"文档错误"。
- `ForgingPlan` 的 `optimalSteps` 用"全部已注册方式"(`ForgingBlueprint.java:82-86`) 做 BFS，
  不含工具限制；玩家实际只能用"工具并集"(`ForgingWorkstationService.java:86-94`)。
  `research/06:55` 未说明这点，属文档缺口。
- `docs/模块实现审计.md:26` 说 `ItemStackTemplate`"用于返还物、**配方产物**和聊天悬浮物品"：
  灵材合成对(`SpiritShapedRecipe.java:34`)、**炼丹不对**（`success_outputs` 仍是 `List<Identifier>`）。
