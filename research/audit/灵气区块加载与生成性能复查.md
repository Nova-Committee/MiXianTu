## 3. 问题明细

### AU01 旧格式解码在实际日志中大量刷 WARN

读取 `run-test-client/logs/latest.log` 的快照包含 8,659 行、1,766,510 字节。其中 **8,338 条** WARN 来自 `TolerantMapCodec`，全部标记为 Server thread：

| 被错误解析的 key | WARN 数 |
| --- | ---: |
| `amount` | 2,098 |
| `maximum` | 2,108 |
| `regen_per_tick` | 2,024 |
| `mxt_test:water_power` | 1,049 |
| `mxt_test:spirit_power` | 1,059 |

后两项合计 2,108 条 `Invalid integer map key`。这些数字是日志行数，**不是独立区块数**，也不是当前 tick 数。

只读抽样主世界前 6 个 region 文件、每文件至多 32 个已保存记录，共 192 个区块：33 个带旧平铺 aura map，14 个 aura map 为空，145 个无该附件；抽样未遇到读失败。这是定位样本，不是整个世界的格式占比。示例 `r.-1.0.mca` 中的 `[-32, 0]`、`[-31, 0]`，字段位于 `/neoforge:attachments/mxt:aura_chunk`。

旧形状为 `aura → aura id → pool`；当前 `AuraChunkAttachment.CODEC:28` 要求 `aura → sectionY 整数字符串 → aura id → pool`。`TolerantMapCodec.decode:29` 先解析 key 和 value，再检查 key 是否失败。因此旧 aura id 不能转为整数时，仍会进入下一层，把 `amount` 等池字段当作 aura id 解析，产生多条嵌套 WARN。

坏项最终被丢弃，恢复的库存表为空，`seeded()` 为 false，于是还需重新初始化。重置旧库存是附件注释中已经声明的策略，本次没有把“不迁移旧余额”另列为设计缺陷；问题是旧格式识别、日志放大及新状态写回不完整。

建议在 Aura 附件边界识别旧形状，按明确的重置策略处理，并保证新状态标脏保存；通用 map 解码应在 key 失败后跳过对应 value 解码。不要仅通过关闭 WARN 掩盖重复重建，也不需要为此删除世界。

### AU02 主要查询缓存的 tick 窗口错位

`AuraZoneEventBridge.onLevelTick:73` 使用 Post LOWEST，在 `AuraChunkTicker` 的 Post HIGH 之后调用 `AuraQueryCache.advance(level, gameTime)`。而 `AuraQueryCache.current:343` 要求 `EPOCH == location.gameTime`。

正常推进的原版调用顺序是：

```text
LevelTick.Pre
  → ServerLevel.tickTime：gameTime 从 t 增为 t+1
  → 实体 tick / 业务查询：缓存 EPOCH 仍为 t
LevelTick.Post HIGH：seedPending / 维护，EPOCH 仍为 t
LevelTick.Post LOWEST：advance(t+1)，然后进行玩家查询
```

原版证据在 `MinecraftServer:1147`、`ServerLevel:385/450/484`。因此实体、常规结算及 pending 初始化阶段的 `RESULT / STATIC / FORMATION / POOLS / BIOME` 查询大多直接未命中，而且不会写入当前窗口；LOWEST 之后的玩家同步阶段才能正常复用。

`AVAILABILITY` 则没有 `current` 检查，会一直保留到 LOWEST 清理，可能跨阶段沿用上一 tick 的环境值；它缓存的是环境浓度，真实库存和访客份额仍会现场读取，不能误报成“全部库存都读取上一拍快照”。

建议查询入口按真实 `gameTime` 惰性换代，并结合实际写入的版本或失效机制。**只把 advance 移到 Pre 仍不充分**：Pre 在原版 `tickTime` 增时之前。验证必须覆盖真实 tick 阶段，手动 advance 后立即查询的 memo 探针不足以发现本问题。

### AU03 初次播种没有预算，还顺带执行完整邻域查询

**部分修复：播种与完整查询共用 `ensureInitialized`，只做静态区域与当前区块库存初始化；pending 单拍数量限制尚未实施。** 下文保留原问题证据。

`AuraChunkTicker.seedPending:143` 复制整个 pending 集合并全部遍历，最后整体清空。没有“每拍最多若干区块”的限制。

每个未 initialized 的区块在最低世界高度、区块中心调用 `AuraService.getPositionAura`。`resolveAura:84` 首先初始化整列库存，随后仍继续执行自定义区域、阵法区域、池复制和 `applyBlockDistance:106`；seedPending 最终没有使用完整返回结果。

跑图时一批区块完成加载，后续一拍可能集中完成整列 map / pool 分配和邻域查询。AU02 还使这些查询缺少主要 memo。最低 Y 会裁剪一部分邻域范围，因此不能说每次播种必定扫描完整 27 个精确段。

建议按 97 稿收敛为统一 `ensureInitialized` 入口：后台播种使用同一初始化逻辑但不计算完整位置结果，并复用现有 dispatcher 分摊；消费者真的需要未就绪库存时，同步保证该目标就绪。消费、邻域贡献和分配器也必须接同一个入口，不能排队后把尚未初始化的来源误算为零。

### AU04 Load 回调同步重建整列，随机巡检不能替它削峰

`onChunkLoad:53` 调用整列 `BlockAuraService.rebuild:41`：对已有缓存段和最低段至最高非空段的并集逐段重建。新区块、重新加载的旧区块都执行，已 seeded 也不能跳过。

当前实现已有有效剪枝：`sectionAura:79` 对空气段和调色板不含灵气方块的段直接返回；命中后才调用 `PalettedContainer.count`。混合状态的段会遍历 4096 个存储项，单值段计数可直接完成。不能沿用早期“每列无条件逐方块扫描”的描述。

这仍是没有预算的同步整列工作。后续 600～1199 tick 的随机巡检只分散定期重建，不会分散这次 Load 重建。

建议先消除 AU08 的同步等待并处理 AU01～AU03，再测量该路径占比；若需延迟重建，要明确段级就绪状态，保证真实读取前能通过统一入口补齐，不能直接信任旧缓存或在另一套实现里重复计数。

### AU05 区域事件追踪使用完整数值查询，精确环重复读方块

`AuraZoneEventBridge.onEntityTick:43` 对所有服务端实体执行追踪判断，没有仅限玩家或生物的过滤。`AuraQueryCache.needsQuery:171` 在首次查询、跨任意一个方块、默认满 10 tick 时重新查询。区域 Enter / Leave 最终比较的是 `source` 与 `sourceKind`，但为得到它们会计算完整库存及距离加权结果。

另外 `onLevelTick:85` 每 tick 对每名玩家做完整查询，不受实体 10 tick 间隔限制；默认每 5 tick 发包时还会调用 sensed 查询。后者在该阶段可命中结果缓存，不能算成必然完整重算，但实体阶段和尾部阶段的同点查询会受 AU02 影响重复执行。

一次完整查询的 `applyBlockDistance:284` 会尝试 7×7 共 49 个区块列，以 `hasChunk` 筛选来源；**该筛选不能保证后面的 `getChunk` 不阻塞，见 AU08**。Y 筛选后最多覆盖 343 个段。内环 3×3×3 使用 `BlockAuraService.visitSources:99`，没有运行期来源位置索引：一个混合段即使只有一个灵气矿，也需检查 4096 格。27 段均命中且可用时，理论上最多 110,592 格访问，再加真实来源的距离计算；这是条件上限，不是每次查询的固定成本。

建议把区域身份解析与完整数值结果拆开，但复用同一套区域优先级；事件只取身份，真正消费者才计算数值。精确环可使用段级、可失效的运行期来源索引；所有更新和修复仍由现有 BlockAuraService 出口维护，不增加第二套贡献算法。不能单纯把静止实体的间隔调大当作完整修复，因为移动会绕过间隔。

### AU06 初始化、消费与修复写入未统一标脏或失效

**部分修复：`ensureInitialized` 实际初始化后会标脏拥有区块并失效位置结果缓存；消费、修复与其他写入的一致边界仍开放。**

`AuraService.initialize:158` 修改附件里的 map / template，但没有持有区块并 `markUnsaved()`。`consume:143`、`change:151` 也直接修改附件内部对象。`BlockAuraService.rebuild` 更新段缓存同样没有标脏；方块实际放置本身通常会标脏，定期纠正则不能依赖这个条件。

NeoForge 的 `ChunkAccess.getData` 和 `AttachmentHolder.getData` 不会因为内部对象被修改而自动标脏；`setData/removeData` 才会明确标记。当前代码中 `AuraMaintenanceState.regenerate:87` 仅在再生量确实变化时标脏，因此零再生、满库存等场景不能保证初始化后的新格式写回。

这既有保存正确性风险，也会让旧格式在后续加载时继续解码报错和重新播种。不能据此断言每次卸载都会重复：区块也可能因其他原因被保存。

同 tick 缓存失效也没有覆盖全部写入。建议沿用 97 稿的统一库存读写边界，实际改变时集中标脏和失效，避免只在后台再生路径补救。不要给每个消费者再造一份初始化或保存协议。

### AU07 现有细分诊断可能给出错误的均值

`AuraZoneEventBridge:80` 先调用 `reportQueryStats`，其内部 `:106` 执行 `resetStats()`；随后才调用 `reportDiagnostics` 和 `reportStageCosts`。

后两者读取的查询数已清零，stage 统计分母用 `max(1, QUERIES)`，输出可能把整个窗口的时间误当作单次查询时间；hit / miss 又不是同一处整体清零，窗口不一致。当前日志快照没有开启这些统计的输出，本次没有拿它们计算耗时。

建议先统一获取一次窗口快照，让所有日志使用同一份计数，最后整体重置；性能对比前先修正观测口径。

### ~~AU08 播种的邻区块查询同步等待 FULL，Spark 已确认主要慢路径~~

**已修复，原 P1；静态复核、编译及 21/21 组 GameTest 通过，尚无修复后的 Spark 数据。** 本节保留原采样证据，修复内容见 §6。

[用户报告](https://spark.lucko.me/8miTh71oNS) 的 metadata 显示：采样间隔 4 ms，阈值 100 ms，观测约 28.8 秒、573 个 tick，其中纳入 3 个慢 tick。Server thread 调用树的累计采样权重为 1,328 ms：

| 路径 | 累计采样权重 | 相对线程样本 |
| --- | ---: | ---: |
| `AuraChunkTicker.seedPending → AuraService.applyBlockDistance → getChunk → managedBlock` | 1,072 ms | 80.72% |
| 上述 `managedBlock` 内的 `waitForTasks` | 948 ms | 71.39% |
| 上述 `managedBlock` 内的 `pollTask` | 124 ms | 9.34% |

这些是抽样权重而非精密计时，父子节点不能累加。报告 metadata 的全局 MSPT 数值也不能用作这 3 个筛选 tick 的均值。

主要业务调用链：

```text
AuraChunkTicker.seedPending:146
  → AuraService.getPositionAura
  → resolveAura:106
  → applyBlockDistance:289
  → Level.getChunk
  → ServerChunkCache.getChunk:169
  → BlockableEventLoop.managedBlock
  → waitForTasks → LockSupport.parkNanos
```

`applyBlockDistance:288` 先检查 `hasChunk`，但 `ServerChunkCache.hasChunk:265` 只根据 holder 和 ticket level 判断是否允许 FULL。目标可能仍在读盘、生成或处理状态依赖；检查通过不等于对应 future 完成。

随后 `level.getChunk(x,z)` 默认请求 `FULL, loadOrGenerate=true`，可以添加 UNKNOWN ticket，再通过 `getChunkFutureMainThread` 获取或安排状态任务，`managedBlock` 等待 future 完成。等待期间主线程会继续泵送区块任务；无可执行任务时 `waitForTasks` 短暂 park。**这份报告证明同步等待，不足以证明锁竞争、循环依赖或死锁。** 只采样 Server thread 也不能确定后台具体卡在读盘、地形、光照还是其他依赖。

同类入口一并检查：

- `AuraService.loadedChunk:116`：同样用 `hasChunk + level.getChunk`，名称和注释承诺的非加载读取没有落实。
- `AuraDistributionService.ground:200`：同样组合，阵法扫描也有同类风险。
- `AuraDistributionService.withdraw:118`、`reserve:247`：使用 `getChunk(FULL,false)`；false 只是不主动增加加载 ticket，holder 符合 ticket 条件但 future 未完成时仍可进入 `managedBlock`，不能当作绝不等待。
- `AuraService.staticZone:188`：`level.getBiome` 经 `BiomeManager` 调用 `LevelReader.getNoiseBiome`，后者请求 `getChunk(BIOMES,false)`。群系边界采样还可能落到相邻区块；这是源码确认的额外风险，本报告的主要等待栈没有指向它，不能混为此次直接原因。
- `CreatureProfileService.apply` 在实体入世时也调用完整 Aura 查询，报告另有约 4 ms 同类 `applyBlockDistance → getChunk` 样本；不是本次主要耗时分支。

建议修复边界：服务端已就绪区块读取统一使用 `ServerChunkCache.getChunkNow`，拿不到则跳过或返回明确的未就绪结果。该方法用已完成结果的 `getNow`，不创建 ticket 或调度生成；NeoForge 还会暴露 `currentlyLoading`，所以涉及完成状态或生命周期的地方仍需遵守 Load 事件边界，不能借此在回调里提前播种。

群系读取需另外保证非阻塞，优先短路已命中的维度绑定；确需群系时，明确只读已就绪采样块或延迟查询的规则。后台播种应直接调用统一初始化入口，不计算邻域贡献。**仅给 pending 加数量上限无法根治：单次同步 getChunk 仍可能等待上百毫秒。** 无需修改原版 event loop，也不应把 LevelChunk / 附件运算挪到异步线程规避等待。

## 4. 已完成优化与次要放大因素

- 子区块巡检已使用 dispatcher；预算是 `max(8, ceil(任务数 / 600))`，不是恒定每 tick 8 段。主世界 24 段、1,000 个区块时约 24,000 个任务，数量上限为 40。
- 再生已分相位；默认间隔 10 时，数量预算约为 `max(1, ceil(区块数 / 10))`，没有恢复成全部区块每 10 tick 同拍执行。
- 数量预算不是毫秒预算，任务变多会提高执行量；单个任务中的昂贵扫描也不能由数量限制打断。
- 访客覆盖已采用差量索引，静止玩家不会每拍重建整个覆盖立方体；区块加载时填充该列覆盖仍有成本。
- 每列所有段包括空气段都登记巡检，加载 / 卸载要注册或取消多项任务。这是次级成本，不能在没有采样时优先归因于队列本身。
- `staticZone` 已先解析维度绑定，命中便跳过群系读取；群系回退与 `formationZone` 遍历仍有成本。AU02 和 AU05 会放大这些成本，但没有阵法的世界不应归因于阵法供给扫描。

另有一个需确定语义的边界：附件只有一个整列 template，而初始化采样最低 Y。若数据包仅按群系绑定、同列不同高度或水平位置解析到不同 template，`resolveAura:84` 会因 template 不同反复清空整列库存。当前测试包存在主世界维度绑定，不能把它直接当成本次日志场景的原因。后续调整应先确定整列模板的归属规则。

## 5. 建议顺序与验证

1. AU08 已实施非阻塞就绪读取、独立初始化与群系回退，正确性探针已通过，下一步用同场景 Spark 确认实际耗时变化。
2. 处理旧格式识别和新状态标脏，修复缓存时间窗及统计快照，再测真实查询复用率。
3. pending 接统一调度，真实消费者通过同一入口保证库存初始化；数量限制不能代替非阻塞读取。
4. 身份事件改用轻量区域解析；按采样结果决定精确环来源索引及 Load 重建的进一步分摊。

行为修改后需要覆盖：ticket 允许但 FULL future 未完成时不等待、不添加 ticket；群系边界查询不等待；后台初始化不进入邻域查询；旧形状恢复后重新保存及重载；零再生库存保存；真实实体 tick 与 HIGH / LOWEST 查询复用；同 tick 库存写入失效；pending 突发加载与按需初始化；未就绪邻段贡献；方块单点更新与巡检修复；跨高度 template 切换。
