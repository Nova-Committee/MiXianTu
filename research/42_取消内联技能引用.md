# 取消内联技能引用（`Artifact.abilities` 只收 id 与标签）

> **状态：已落地（2026-09-23，同日第二次变更）。** 触发原话：「直接不允许内联吧，只能在 ability 注册表注册然后使用 id 或者 tag 引用，也节省逻辑」。本文记录这次收缩的动机、删掉的东西、破坏性影响与落地结果。
>
> **基准**：`41_能力与法器能力合并设计.md` 当天落地后的工作树——`data/ability/{AbilityRef,AbilityEntry,AbilityRefs,Toggable}.java`、`data/artifact/{Artifact,ArtifactDescription}.java`、`runtime/artifact/ArtifactService.java`、`util/codec/RegistryCodecs.java`、`runtime/wheel/{WheelEntryKind,WheelSources}.java`、`src/test-mod/**`。MC 26.1.2 / NeoForge 26.1.2.99。

## 0. 一句话

`Artifact.abilities` 的条目**从两种形状收成一种**：**一个 `mxt:ability` 注册表条目的 id，或一个技能标签 `#命名空间:路径`**。技能的定义位置只剩 `data/<命名空间>/mxt/ability/<路径>.json` 一处，**"写在宿主定义里的内联技能"整个形状取消**，连带删掉为它发明的派生 id（`<宿主 id>/<key>`）与两个已经没人调用的 `Toggable` 成员。

## 1. 为什么（"节省逻辑"具体省在哪）

合并那一版为了给内联技能一个**稳定身份**，发明了派生 id：内联条目的地址是"宿主 id + `/` + key"，于是同一个 `abilities` 字段要同时接受「注册表引用」和「内联对象」，身份也要分两路解析。这套东西的每一分复杂度都只服务于那一种写法：

| 为内联存在的东西 | 它的作用 | 取消后 |
| --- | --- | --- |
| `data/ability/AbilityEntry.java`（sealed `Registered` / `Inline` + `DerivedIdCodec`） | 一个字段收两种形状；内联条目在解码时把 ops 的当前 key 换成派生 id，让默认 `name` / `description` 键与注册表条目同形 | **整个类删除**（含那段"解码期间改写 loading key"的编码器） |
| `AbilityRef.inline` 字段 + `AbilityRef.inline/derive/hostOf/keyOf` | 记住"这条技能从宿主来"，并在两处按最后一个 `/` 拆 id | `AbilityRef` 收成 `(Identifier id, Ability definition)` |
| `AbilityRefs.resolve` 的内联分支 | 注册表查不到时，把 id 切成 host + key 再回宿主定义里找 | 只剩注册表查找 |
| `Artifact` 的构造期"同一 key 只能写一次"校验 | 内联 key 的唯一性 | 删除 |
| `Toggable.key()` | 内联条目的 key（`flight` / `storage`），用来拼派生 id | 删除（**零调用点**：`AbilityWheelEntry` 一直用的是技能自己的 `name`） |
| `Toggable.displayName()` + 语言键 `wheel.mxt.artifact_skill.{flight,storage}` | 一格没有技能名时的兜底 | 删除（技能名永远存在，这层兜底从没被调用） |
| `Artifact.storage()/upkeep()/flight()` | 直接在定义对象上扫 `entry.ability().type()` | 迁到 `ArtifactService`（要展开标签才能回答，必须带 Provider） |

省下来的不只是代码行数：**能力只有一个来源、一种身份、一条解析路径**。任何"拿到一个能力 id"的地方（授予账本、冷却、状态存储、轮盘格子、事件、命令、KubeJS）都不需要再问"它是注册表里的还是内联的"。

## 2. 代价与取舍

- **内容必须注册。** 一件法器想配一条只属于它自己的技能，以前可以写在同一个文件里；现在要单独开一个 `mxt/ability/<path>.json`。换来的是这条技能天然可被技能书、命令、战利品、功法、脚本共用——同一条定义在哪都是同一个 id，不需要复制两套数值。
- **复用靠标签。** 多件法器共用一组被动时，写 `#mxt_test:artifact_passive` 比逐件抄 id 更省事；标签在授予时展开（顺序 = 注册表顺序），与 `element`、`granted_abilities`、`spirit_capacity` 之外那些 `HolderOrTag` 字段完全同一套口径（`RegistryCodecs.holderOrTagList`）。合并那一版曾把 `#标签` 一起取消，本次把标签**恢复**——它本来就是这套写法唯一剩下的复用手段。
- **已知成本（暂不处理）**：展开标签要对注册表做一次 `listElements` 遍历，而 `ArtifactService.abilities` 会在轮盘池、提示框等路径上被调用。这与 `Technique.granted_abilities` / `SpiritRoot.granted_abilities` / `Talisman.abilities` 的既有口径一致（它们也是每次现展开），所以本次不引入缓存；真出现"能力注册表上千条 + 每帧展开"的场合，再按 `DamageElements` 那样按注册表实例开键缓存。
- **`mxt:disabled` 不参与展开**：`RegistryCodecs.resolve` 的口径是不看禁用标签（既有四个 `HolderOrTag` 能力字段都这样），本次沿用，没有为 `artifact.abilities` 单独开一条规则。

## 3. 落地改动

**数据层**

- `Artifact.abilities`：`List<AbilityEntry>` → `List<Either<Holder<Ability>, TagKey<Ability>>>`，编码器 `RegistryCodecs.holderOrTagList(MxtResourceKeys.ABILITY).optionalFieldOf("abilities", List.of())`（单条或数组都收）。
- 删除 `data/ability/AbilityEntry.java`。
- `AbilityRef`：`record AbilityRef(Identifier id, Ability definition)`，只留 `of(Holder<Ability>)`。
- `AbilityRefs`：`resolve(Provider, Identifier)` 变成纯注册表查找（仍然认 `mxt:disabled`），新增 `resolve(Provider, List<Either<Holder<Ability>, TagKey<Ability>>>)` 做展开；`of(Provider, hostId)` 删除。
- `RegistryCodecs`：新增 `resolve(Collection<Either<Holder<T>, TagKey<T>>>, Provider, ResourceKey<? extends Registry<T>>)` —— 与既有的 `Registry` 版同形，但走 `access.lookupOrThrow(key)`，因此**客户端提示框与服务端授予用同一条展开路径**（客户端读同步下来的注册表）。
- `Artifact`：删掉 `storage()/upkeep()/flight()`、私有 `type(Class)` 与内联 key 唯一性校验；类注释改成"每条是 id 或标签"。
- `ArtifactService`：`abilities(...)` 用 `AbilityRefs.resolve` 展开声明的条目（`LinkedHashSet` 去重，与手写组件 `mxt:item_abilities` 合并）；新增私有 `first(access, stack, kind)` 取某类型的**第一条**（定义可以给多条，标签按注册表顺序贡献成员），`flight(...)` / `storageSlots(...)` / `upkeep(...)` 三个外部签名不变。
  - **一处顺带的口径放宽**：`flight(...)` / `storageSlots(...)` 以前直接扫定义里的条目，现在扫 `abilities(...)` 的解析结果，于是**手写在 `mxt:item_abilities` 组件上的飞行 / 储物技能也算数**了。这与 `ArtifactService.holds(...)` / `carried(...)` 的既有口径一致（那个组件本来就是"这个栈还手写了哪些技能"），所以是按同一份读取统一，而不是新语义。
- `ArtifactDescription.appendAbilities`：改成遍历 `ArtifactService.abilities(registries, stack)`（顺序仍是定义的顺序），储物那一行拿到的就是解析后的 `AbilityRef`。

**接口**

- `Toggable` 删除 `key()` 与 `displayName()`，四个实现（`mxt:active` / `mxt:channelled` / `mxt:flight` / `mxt:storage`）删掉对应方法，`FlightAbilityType.KEY` / `StorageAbilityType.KEY` 两个常量删除；`wheel.mxt.artifact_skill.{flight,storage}` 四条语言键（中英各两条）删除，两份文件键数 745 → **743**。

**测试包与探针**

- 原本内联的六条技能落成独立文件：`mxt_test:{azure_flight, bound_flight, bound_storage, bell_storage, jade_storage, probe_upkeep}`（字段一字未改，只是去掉了 `key`）。
- `azure_flight_sword` / `bound_sword` / `cloud_beast_bell` / `spirit_gathering_jade` / `upkeep_probe` 改成写 id；`ward_jade_talisman` 的 `abilities` 改成 `["mxt_test:artifact_guard", "#mxt_test:artifact_passive"]`，让名册腿同时验证"id + 标签 → 两个 id"。
- 探针：`/mxt_test artifact` 的飞行腿直接解析 `mxt_test:bound_flight`；名册腿的 `flight()` 判定改走 `ArtifactService`；轮盘第 6 条腿用两条技能的**真实 id** 并新增负例 `mxt_test:absent_storage`（输出 `named cells=`），第 10 条腿文案改成 `per-ability cooldowns independent=`（断言不变）。

## 4. 破坏性

- **把技能内联写在 `abilities` 里现在会让世界加载失败**：`abilities` 里出现对象就不再是合法条目（`{ "key": ..., "type": "mxt:flight", ... }` 这一形状没有迁移余地）。搬家＝把那一段对象剪成 `data/<命名空间>/mxt/ability/<路径>.json`（**删掉 `key`，其余字段一字不改**），再在法器里写它的 id。
- 老存档里若有引用派生 id 的东西（轮盘布局的格子 id），那些格子会解析不出来。未发布阶段不提供迁移：轮盘布局对解析不出的格子本来就是"`?` / 不画 / 服务端拒绝"，玩家重摆一格即可；能力账本与冷却按 id 存，内联时代留下的派生 id 不会再有定义，撤销时照常回收。
- 与合并那一版的 `mxt:passive` / `mxt:active` 旧写法一样，这一次也**不静默降级**：`abilities` 整段不可解析，加载期就能看到。
