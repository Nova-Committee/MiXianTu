# 55 技能数据与可变状态重设计

> 用户口径（2026-09-27，逐字）：
> 1. 「Ability 负责存储所有 json 加载上来的信息，包括一个 AbilityType」
> 2. 「AbilityType 只有 createComponents，isActive，grant，revoke，active，inactive，tick，activeTick，tickInterval 几个方法，AbilityType 根接口只处理 active 相关内容，tick 控制由主 tick 循环统一控制」
> 3. 「DataStorage 均为 Mutable，里面包括了 tick 方法和 isDirty 等方法（可以把接口改成类），然后里面的值应当是 mutable 的，也就是不要通过替换对象的方式更新数据」
> 4. 「至于可能的统一执行 execute 等操作，可以另外加接口实现」
>
> 两条追问的拍板：类型自己的参数**放进各自 AbilityType 的实现里，按需声明**（`Ability` 只放通用字段 + 一个 `type`）；上一轮的「发动型各自带 `effect` 指一条 `mxt:interval`」**取消**，每个类型直接跑自己身上的四个动作字段。
> 本稿是这一轮的形状记录；字段级权威仍是 `docs/数据包格式.md`。

## 1. 三层分工

| 层 | 是什么 | 放什么 |
| --- | --- | --- |
| `Ability` | 一条技能的**数据**（`mxt:ability` 注册表条目） | 所有类型共用的 JSON 键 + 一个 `type`（`AbilityType` 实例，各实现按需带自己的参数，平铺在同一个 JSON 对象里） |
| `AbilityType` | **行为**，无共用参数 | 根接口只有下面九个方法；参数放在各自的实现记录里 |
| `DataStorage` | 一个宿主的一份状态 | **可变对象**，自己 `tick`、自己记变更标记（无参 `isDirty()` 读一次即清）；运行时原地改，不换对象 |

`type` 仍由 `MxtRegistries.ABILITY_TYPE` 的 `dispatchMap("type", …)` 解码，所以 JSON 写法一个字不变（`{"type":"mxt:interval", …该类型的键…}`）。

## 2. `AbilityType` 根接口（九个方法）

```java
default void createComponents(Ability ability, DataStorageCollector collector) {}  // 默认加 mxt:active_state
default boolean isActive(AbilityContext context)                                    // 默认：求技能自己的 condition
default void grant(AbilityContext context) {}
default void revoke(AbilityContext context) {}
default void active(AbilityContext context) {}      // 不成立 → 成立的那一瞬间
default void inactive(AbilityContext context) {}    // 反过来
default void tick(AbilityContext context) {}        // 每拍
default void activeTick(AbilityContext context) {}  // 生效期间的每一拍
default int tickInterval(AbilityContext context) { return 1; }
```

- 原 `createStorages` 更名 `createComponents`（Origins 的 `createComponents`）。
- 原 `execute` / `executeOn` **不在根接口上**：见 §4。
- 原 `triggers()` **不在根接口上**：见 §5。
- 原先挂在默认 `tick` 上的「求 condition → 边沿 → active/inactive → activeTick」这一套**搬到主 tick 循环**：根接口只回答「我算不算生效」（`isActive`），边沿状态仍记在 `mxt:active_state` 里。这就是「tick 控制由主 tick 循环统一控制」。
- **状态种类按类型各自声明**（用户随后点名：「`actionComponents` 不要堆一起，还是分派一下，不要全无脑加上」）：根接口上**不放"统一加一份"的静态助手**，每个类型的 `createComponents` 自己列自己那条路需要的：
  | 类型 | 在默认 `mxt:active_state` 之上再加 |
  | --- | --- |
  | `mxt:active` / `triggered` / `channelled` / `aura` | `mxt:cooldown` +（写了 `charges` 时）`mxt:charges` + 四种内容自用种类 |
  | `mxt:interval` | **只有**四种内容自用种类（它没人按、也不付款，所以没有 `cooldown`/`charges`；它照样跑四个动作字段） |
  | `mxt:word` | `mxt:cooldown` + `mxt:charges` |
  | `mxt:flight_control` | `mxt:cooldown` |
  | `mxt:storage` | `mxt:cooldown` + `mxt:container` |
  | `mxt:modifier` / `mount` / `upkeep` / `composite` / `empty` | 无 |
  运行时的三个游标（`mxt:cast_deadline` / `mxt:channel_pulse` / `mxt:aura_pulse`）**谁都不声明**——它们是运行时写的，声明表正是用来把它们挡在内容之外的。

## 3. 主 tick 循环（`AbilityEventBridge.tickAbilities`）

每个已授予技能、每个 tick：

1. `ctx.abilities().storage().tick(id, ctx)` —— 该技能名下**已存下来的**每个 DataStorage 各自 `tick`（充能回复、计时到点等，与技能的刻距无关）；
2. 求 `int interval = type.tickInterval(ctx)`，`interval <= 0 || gameTime % interval != 0` 就跳过这一拍；
3. `type.tick(ctx)`；
4. `boolean active = type.isActive(ctx)`，与 `mxt:active_state` 比：变了就写回边沿并回调 `active` / `inactive`；
5. `active` 时 `type.activeTick(ctx)`。

## 4. 动作字段：每个类型自己带，共享执行放额外接口

上一轮的 `entity_action` / `target_selector` / `target_condition` / `bi_entity_action` 从 `mxt:interval` 一处、发动型 `effect` 指过来，改成：

- 会跑动作的五个类型（`mxt:active` / `triggered` / `channelled` / `aura` / `interval`）**各自在自己的记录里声明这四个字段**；
- 跑一次这件事本身是 `AbilityEffect`（`data/ability/AbilityEffect.java`：`execute` / `executeOn` + 静态 `run` / `runOn`，唯一调用点是 `AbilityService.executeEffects`，`mxt:word` 直接实现它跑自己的枚举）；四个字段的执行逻辑（含 try/catch 与日志）放在 `ActionCarrier extends AbilityEffect`（`data/ability/ActionCarrier.java`）的默认方法里：`entityAction()` / `targetSelector()` / `targetCondition()` / `biEntityAction()` 四个访问器 + 默认的 `execute` / `executeOn`；
- 五个动作类型 `implements AbilityType, ActionCarrier`，各自在自己的 `tick` / `activeTick`（或施放/脉冲路径）里调用 `execute`。
- `effect` 字段**删除**（写它 = 未知键静默忽略）；`mxt:interval` 不再是"别人的效果技能"，而是"按自己的节拍反复跑这套字段的类型"。测试包上一轮拆出来的 25 条 `*_effect.json` 合并回原技能后删除。

`mxt:word` 保留自己的效果枚举，`implements AbilityType, AbilityEffect`（它跑的是自己的枚举，不是四件套）。

## 5. 触发（`mxt:triggered`）

`triggers()` 不在根接口上，放额外接口 `TriggerSource`（`data/ability/TriggerSource.java`）：`List<Trigger> triggers()` + `boolean rolls(entity, formula)`（概率）。桥接层对 `type instanceof TriggerSource` 取用——这是**能力接口判断**，不是"问你是哪一个具体类型"（后者的 `instanceof` 仍然禁止）。

`grant` / `revoke`：技能被授予/撤销时回调一次（带实体、附件、刻）。用于类型自己需要"被持有时才成立"的准备与收尾；不承担信号订阅（订阅是每 tick/每次重算时按 `TriggerSource` 重建的，`/reload` 后必须重建，放在 grant 里会丢）。

## 6. `DataStorage` 改成可变类

```java
public abstract class DataStorage {
    private boolean dirty;
    public abstract MapCodec<? extends DataStorage> codec();
    public abstract DataStorage copy();                  // 物品宿主是值，必须能深拷贝
    public void tick(AbilityContext context) {}           // 自己那一拍（充能回复、计时到点…）
    public final boolean isDirty()                        // 读＝清：回答"上次读过之后有没有变"
    protected final void markDirty()                      // 只记标记，不通知任何人
}
```

- 接口改类：`EntryBegan`、`EmptyDataStorage` 原本是 `enum`（枚举不能继承类），改成 `final class` + `INSTANCE`。
- 所有种类从 `record` 改成 `final class`，值字段可变；更新走方法（`start(...)` / `set(...)` / `withRemaining(...)` 这类改成原地改），**不再 `new` 一个再写回**。
- **同步与否由 `isDirty` 判断，不靠回调**（2026-09-27 第二版，用户逐条给形状，同日纠偏一次）：`boundTo` / `clearDirty` 删除，`DataStorageHolder` 的 `owner` / `ownedBy` / `changed()` 一并删除——值不持有宿主指针、也不通知任何人；`markDirty()` 只记标记，无参 `isDirty()` 读一次就把它清掉。主 tick 循环在 `storage().tick(id, ctx)` 之后紧跟 `if (storage().isDirty(id)) abilities.markDirty();`，`DataStorageHolder.isDirty(id)` 逐个读掉该 id 名下所有值的标记并回答这一拍脏没脏，**同步因此只有这一个出口**（第一版曾在 `isDirty(holder)` 里回调 `holder.changed()`，被用户否掉）。`set`（内容整份写入）把新值也标成脏，好让这次读取看得见；`clear` 不标，撤销的调用方自己 `markDirty()`。改动最迟下一拍被读走；附件落盘不靠这个标记，不受影响。
- **`StoredData` 与条目上的 `changed_at` 删除**：时刻由需要它的种类自己带（`mxt:cooldown` 的 `started_at`、`mxt:charges` 的 `last_change`）。这是存档格式变更：老存档里 `{id, data:{value, changed_at}}` 这份形状解不出来，附件按 NeoForge 口径整份丢弃（未发布阶段的不兼容，已按用户口径接受）。
- 声明实例（`INSTANCE` / `NONE`）仍然只是"这个种类"的占位；有参数的声明（`mxt:charges` 的 `maximum` / `recharge_ticks`）照旧。

## 7. 内容侧与物品宿主

- `mxt:modify_storage`（`family` / `id` / `value`）：内容是**整份写入**，仍走 `holder.set(...)` 替换引用（这是"设置一个值"的语义，不是更新路径）；运行时一律原地改。
- **写入时刻由种类自己补**：条目不再记 `changed_at`，而"写入那一刻"对 `mxt:cooldown`（冷却从写下去开始）与 `mxt:charges`（回复间隔从写下去起算）仍是语义的一部分，所以 `DataStorage.writtenAt(gameTime)` 由 `holder.set` 调一次，这两个种类在那里重打自己的时钟——内容侧 JSON 只带 `duration` / `maximum` / `remaining` 时行为与从前一致（`started_at` / `last_change` 是状态半边，存档与同步用）。
- 物品宿主的存储是**组件的值**：写回时 `DataStorageHolder.copy()` 会调用每个值的 `copy()` 做深拷贝，避免组件之间共享同一个可变实例。

## 9. 按代码复核文档（2026-09-27 同日晚）

用户要求"按最细的代码"重核 `ability` 一节与字段表，逐处读了 13 个类型、`AbilityService`（`use` / `prepare` / `commit` / `useComposite` / `tickChannel` / `gate`）、`AbilityActivationService`、`WheelService` / `WheelSources` / `WheelContent`、`ArtifactDescription`、`ArtifactUpkeepService`、`AbilityModifierService`、`FlightService` 与四个目标选择器，改掉的**旧文档说法**（结论已写进 `docs/数据包格式.md` 与 `AGENTS.md` §4）：

- **技能上已经没有 `item_action`**：2026-09-27 从 `Ability` 删除（codec 里没有它，写它＝未知键静默忽略）；当天复核时它还剩一条过时的类注释与"只有 `Ability` 自己声明与解码"的旧结论，两者都已在同日晚修正。旧文写的"对承载物品执行、失败补偿"没有实现支撑。
- **四个动作字段不由 `Ability` 声明**（`entity_action` / `target_selector` / `target_condition` / `bi_entity_action` 在 JSON 里写在 `type` 同级，但由会跑动作的五个类型各自声明与读取），所以文档的"顶层字段表"里不该把它们记成 `Ability` 的字段。
- **`hidden` 只被 `ArtifactDescription` 读**（法器提示框跳行）；轮盘候选池只筛 `Toggable`（`WheelSources.abilities` 用 `AbilityActivationService::togglable` 过滤），**不看 `hidden`**。
- **`damage_condition` 只被 `mxt:triggered` 的订阅读**；别的类型写了不生效。
- **`mxt:composite` 自己的 `costs` / `cast_time` / `cooldown` / `charges` 都不生效**（子技能各自付款、状态记在子技能 id 下；预演阶段直接拒掉 `cast_time > 0` 的子技能）。
- **`charges` 只由施放管线扣**（`prepare` / `commit`），共用闸门（`mxt:flight_control` / `mxt:storage`）不扣；声明表只管内容侧能不能碰。

- **`mxt:upkeep` 只对在线玩家手中（双手 + Curios）的承载物结算**，`costs` 为空直接跳过，`interval` 求值不可用回退到 `20`。

## 10. 字段下移到读它们的类型（2026-09-27 同日晚，代码）

用户拍板："某个 type 特有的字段不要放在通用字段表里"，并要求**代码里也把字段移到正确的地方**。`item_action` 与四个动作字段此前已经不在 `Ability` 上（前者删除、后者自 2026-09-27 起由会跑动作的类型自带），这一轮把剩下两个同样只被部分类型读的字段也下移：

- **`cooldown` 从 `Ability` 移到会付款的七个类型**（`mxt:active` / `triggered` / `channelled` / `aura` / `word` / `flight_control` / `storage`），以新的额外能力接口 `CooldownSource`（`data/ability/CooldownSource.java`，成员只有 `cooldown()`）暴露。取长度的两条路都改成问接口：`AbilityService.cooldownOf`（施放管线的 `prepare` 与共用闸门 `gate` 共用它）与轮盘提示框 `AbilityWheelEntry`；不是 `CooldownSource` 的类型一律按 `0`（它们本来就不付款）。
- **`damage_condition` 从 `Ability` 移到 `mxt:triggered`**，方法挂进已有的 `TriggerSource`（`damageCondition()`）；唯一读它的地方是 `AbilityEventBridge` 的 `mxt:hurt` 订阅分支（从 `definition.damageCondition()` 改成 `source.damageCondition()`）。没有为此新开接口：`TriggerSource` 的唯一实现者就是它。
- `Ability` 记录从 13 个字段减到 **11** 个；顺带删掉那条过时的 `item_action` 类注释残留与六个不再使用的 import。
- **JSON 形状一个字都没变**：`type` 是平铺分派（`dispatchMap`），类型自己的字段与 `type` 同级，所以老的 `{"type": "mxt:active", "cooldown": 100}` 照常解析；变的只是"谁声明、谁读"。
- 探针 `MxtTestCommands` 的 `offhand_flight` 那条腿原来直接读 `Ability#cooldown()`，改成读 `FlightControlAbilityType#cooldown()`；那条腿的 `cooldown=40` 断言不变。
