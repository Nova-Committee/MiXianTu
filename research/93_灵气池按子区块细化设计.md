# 93 灵气池按子区块细化

> 2026-10-19，用户给定："把池子进行细化，细化到子区块级别"，并指定存成 `Int2ObjectMap`（照 `block_aura_sections`）。
> 本文取代 [`92`](92_阵法作为灵气消费者与统一分配设计.md) §2 里"按区块切同一个池"的粒度，以及 [`91`](91_方块灵气子区块重建与位置现查设计.md)
> 里"整块聚合 `blockAura`"这个字段本身。

## 1. 一句话

库存不再是"一个区块一份"，而是**每个 16 格高的子区块各一份**：`auras` 从 `Map<aura, AuraPool>` 变成
`Int2ObjectMap<Map<aura, AuraPool>>`，键与方块缓存用**同一个绝对 section Y**。整块的 `blockAura` 字段随之消失。

## 2. 形状

```json
"aura": {
  "<sectionY>": { "<aura id>": {"amount": …, "maximum": …, "regen_per_tick": …}, … },
  …
}
```

- `block_aura_sections`（方块贡献，按段）与 `aura`（库存，按段）现在是**同一把尺子**，键一致；
- 存量的单位从"区块"变成"子区块"：`amount` / `maximum` / `regen_per_tick` 都是这一段自己的；
- `supplied` 仍然只是查询期的瞬时值，不参与持久化。

## 3. 三个随粒度的规则

**播种**：区域声明的是"一个区块多少"，而一个区块有 `sectionsCount` 段（主世界 24），所以
`initializeAuras` 把区域基线**均分**到每一段（`amount` / `maximum` / `regen_per_tick` 各自 ÷ 段数），
**世界总量不变**。另外两个方案被否：

- 每段都拿全量 → 总量变成 24 倍，`maximum` 的语义也一起崩；
- 只按"有方块的段"分 → 依赖地形，且玩家站在空气段时那段没有库存、一点都花不了。

**消费**：`consume` / `change` / `canConsume` 收 `sectionY`，扣的是脚下那一段的池子。竖直跨过 y=16 就换池子。

**再生**：`regenerateAuras` 遍历所有段，每段按**自己的** `regen_per_tick` 回补（也就是区域值 ÷ 段数）。

**分配**：`AuraDistributionService` 的槽位从"区块"变成"(区块, 段)"——玩家按自己站的段领，阵法按
`BlockAuraService.groundInSphere` 返回的**分段**地面合计逐段领。一个 16 格高的段里，阵法和修炼者分的是同一个池。

**查询**：`applyBlockDistance` 只减**查询点所在段**的聚合（`sectionAura(sectionY)`），再叠加 7×7 区块的子区块级加权视图。

## 4. 删掉的东西

| 文件 | 删除 |
| --- | --- |
| `attachment/AuraChunkAttachment.java` | `blockAura` 字段、`aggregate(Int2ObjectMap<BlockAuraSectionCache>)`、`replaceBlockAura(...)`、`clearBlockAuraCache()`、**`initialized` 字段及其 codec 键**、**一次写整块的 `setBlockContribution(...)`**（只剩 `setSectionAura(sectionY, aura)` 这一条写入口）；新增 `pools(sectionY)` / `sectionAura(sectionY)` / `seeded()` / `ready(sectionY)` / `share(pool, sections)` |
| `runtime/world/AuraChunkTicker.java` | 命令路径里的 `clearBlockAuraCache()` 调用；主动播种的条件改成 `!seeded()` |
| `runtime/world/BlockAuraService.java` | `groundInSphere` 的返回值从"每区块合计"改成"每段合计"（`Int2ObjectMap<Map<aura, Double>>`）；`rebuild(level, chunk)` 把"实心段 ∪ 缓存里的段"并成一个 `IntSet` 后逐段调用 `rebuild(level, chunk, sectionY)`（回到空气的段、以及世界高度变过留下的残留都会被清掉） |
| `runtime/world/AuraService.java` | 查询/消费都带 `sectionY`；`initialize` 需要 `level` 才知道段数与起点 |
| `runtime/cultivation/AuraDistributionService.java` | claim 的键 `Slot(chunk, sectionY)`；阵法地面按段 |

**`clearBlockAuraCache()` 必须删**：它原来只清"每方块明细"、把整块聚合当差量基线留着；现在每段的聚合本身就是
方块缓存，清掉它等于假装"这块地原本没有方块灵气"，重建时会把整段方块灵气**再加一遍**。命令现在只做重建。

**`initialized` 必须删**：播种会给**每一个** section 写一份 map（哪怕是空 map），所以"这一段有没有 map"本身就
等价于"播过种没有"——`ready(sectionY)` 就是它，区块级的那个 bool 反而是第二份状态，还可能与数据打架
（旧档里 `initialized=true` 却没有任何 section map，守卫会放行、建出只有方块贡献、没有区域份额的池子）。
现在：查询的播种条件是 `!ready(sectionY) || template 变了`，方块差量的守卫是 `!ready(sectionY)`（按段，比原来按区块更准），
主动播种看 `!seeded()`（任何一种 section map 存在即算播过种）。

## 5. 迁移

旧档的 `"aura"` 是扁平 map（`{auraId: pool}`），新 codec 按段读不出来 → `lenientOptionalFieldOf` 回落成空表。
`AuraChunkAttachment.ready(sectionY)` 检测到"这一段没被播过种"，于是下一次查询走 `initialize`，按新规则重新播种。

结果：**旧世界的库存被重置为区域基线（÷段数），不崩溃、不重复累加**。这是仓库既定的迁移口径（不写兼容转换）。

## 6. 数值影响（必须知道）

一个区块从区域拿到的**总量不变**，但每一段只有 `1/sectionsCount`。所以：

- 站在某一层能消耗的量降到原来的 1/24（主世界）——**这是一次真实的下调**；
- 想让"这一层灵气更多"，正确的旋钮是区域定义的 `amount`，不是分摊规则；
- 区块内不同高度现在是分层的：地下与地表可以各花各的（同一份总量里，谁先用谁拿走）。

如果拍板要"每段都按区域值给"，那等于世界总量 ×24，得同时重定 `maximum` 的口径——不建议。

## 7. 代价

- 每区块 24 份小 map（每份几门灵气），内存与存档都比原来大一点；
- 分配槽位从 chunk 变成 (chunk, section)，大多数槽位只有 0~1 个消费者——`distribute` 的调用次数上去，但每个都极小；
- `regenerateAuras` 从一次 `replaceAll` 变成 24 次。

## 8. 验证

- `gradlew.bat compileJava compileTestModJava` 通过。
- **未实机、未跑 `runGameTestServer`**。建议补两条：① 一个区块的区域基线总量在细化前后相等（`Σ 各段 amount` 不变）；
  ② 同一位置 `consume` 只影响它所在段，相邻段的量不变。
- 实机观察点：`/mxt aura query` 在 y=0 与 y=64 的读数应当不同（分层生效），且修炼速度随之变化。
