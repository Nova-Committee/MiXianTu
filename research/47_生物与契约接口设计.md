## 0. 结论

**能改，而且改动集中在三处：资格、行为、档案字段。** 现状的两个毛病正好对着用户说的两句话：

1. **资格是数据给的，不是代码给的**——`creature_profile.contract_tags` 与 `contract_type.creature_condition`
   取并集（`ContractService:40-47`），所以**任何**生物（含原版狼）都能被数据包写成可契约，本体无法表达
   "这一族就是不能契约"。
2. **行为全写在框架里，而且绑死 `Mob`**——跟随、召回落地、协战、收纳的代码都在 `ContractEventBridge` /
   `SpiritBeastBagItem` 里，内容方**没有位置**说"我这只灵兽盘旋着跟""我这只不收进袋"。契约类型上那四个
   `*_action` 是**数据动作**，对同类型的所有生物共用，表达不了"这一只"。

建议形状：**三个接口 + 一个上下文记录 + 一个唯一查找入口**。

- `Contractable`（资格与契约生命周期回调）
- `ContractOperations`（跟随 / 召回落地 / 协战：**每个默认实现就是今天框架里那段硬编码**）
- `Capturable`（能不能收进灵兽袋）
- `creature_profile.contract_tags` **删除**，档案退回纯属性。

代价是两处破坏性变化：**写了 `contract_tags` 的数据包会静默失去契约资格**（狼因此不可契约），
测试包要换成实现了接口的探针实体；契约**状态**仍归框架（`mxt:contract` 附件是唯一记录）。

今天**根本不存在**、而这次要一并补齐的四件事（已拍板）：契约代价（`contract_type.costs`，复用现成的
`Cost` + `CostTransaction`）、调试与管理员入口（`/mxt contract`，顺带把**零调用**的
`ContractService.breakContract` 接上）、每主人契约上限（`max_owned`）、召回冷却（`recall_cooldown`）。
后两件需要一个**主人索引**（§4.3），它同时是 `/mxt contract list` 的数据来源。

### 1.1 资格：两条并集的路，没有否决权

- `contract_type.creature_condition`：一个 `EntityCondition`，写"这类契约要什么样的生物"；
- `creature_profile.contract_tags`：档案自己按 `mxt:contract_type` 注册表解释（id 或该表下的标签）给资格背书；
- 两者**取并集**（`ContractService:44-45` 的 `||`），注释原话是"只会放宽、不会收窄"。

所以数据包无法表达"狼不能被契约"，只能表达"某契约类型接受狼"。反过来，本体也没有任何"这个实体不可契约"
的判据——资格完全是可加不可减的。

### 1.2 行为：框架全包，且要求 `Mob`

`ContractEventBridge` 三条腿：

| 事件 | 条件 | 做什么 |
| --- | --- | --- |
| `EntityTickEvent.Post` | `instanceof Mob` + 已绑定 + 主人在线且**同维度** | `recalled` → 传送到主人并清标志；否则 >32 格传送、>4 格 `getNavigation().moveTo`；最后执行 `follow_action` |
| `LivingDamageEvent.Post` | 伤害来源是 `Mob` + 有契约类型（不要求已绑定） | 执行 `combat_action` |
| `LivingDeathEvent` | `instanceof Mob` + 已绑定 | `break_action` + `penalty_action` + 清附件 |

三个要注意的事实：

- **主人离线/跨维度时整条 tick 腿直接 `return`**，`recalled` 标志会留着，等主人回到同一维度才消费；
- **`break_action` 今天只在死亡时执行**。`ContractService.breakContract`（唯一会"主动解除"的方法）**零调用**，
  而且它**不执行任何动作**——主动解除契约在游戏里没有入口，只有"灵宠死了"这一条路；
- **`combat_action` 不要求已绑定**，只看有没有 `contract_type`（附件里类型存在而 owner 为空的状态目前构造不出来，
  但判据本身松）。

### 1.3 档案：两个只写不读 / 只解不用的字段

## 2. 目标与非目标

**目标**

1. **资格是代码事实**：只有实现接口的实体能被契约；数据包不能再制造资格（这是"不是所有生物均可契约"的落地）。
2. **档案退回属性**：匹配条件 + 属性写入，与契约资格彻底解耦。
3. **行为归实体**：跟随、召回落点、协战、收纳由实体回答；框架只负责附件、事件、数据动作的执行与顺序。
4. **既有行为不倒退**：接口的每个默认实现 = 今天框架里的那段硬编码，"实现接口但不覆写"= 从前的灵宠行为。
5. **不引入 mixin**：原版生物默认不可契约，这是特性不是缺口。

**非目标**

- 妖兽修炼 / 进化 / 成长曲线（`realm_stages` 本期只留数据，见 §4.1）。
- 通用实体 AI 框架（寻路、行为树、生成权重）；接口只回答"契约关系里的动作"。
- 原版生物适配（mixin 或登记表）——见 §8 剩余 Q4。
- 档案的匹配规则与套档时机（除 §8 剩余 Q5 的 `Mob` 放宽外不动）。
- **契约界面与 KubeJS 桥接**：本期只给命令（§4.4），界面与脚本另开一轮。

## 3. 接口设计

### 3.1 放在哪

`AGENTS.md` §3：`api/` 只放"别的模组会实现或调用"的契约（只有接口 + `package-info`）。这三个接口的实现方
正是**内容模组的实体类**，所以进 `api/`：

| 类型 | 位置 | 理由 |
| --- | --- | --- |
| `Contractable` / `ContractOperations` / `Capturable` | `com.iafenvoy.mxt.api`（与 `AuraAccess` 等平级） | 别的模组实现 |
| `ContractContext`（记录） | `data/creature/`，与 `ContractType` 同目录 | `api/` 不能放记录；同 `ToggleContext` 放 `data/ability` 的先例 |

（备选：`api/creature/` 子包。纯外观，现有五个接口都是平铺的，建议先平铺。）

### 3.2 `Contractable` —— 能不能签、签了会怎样

```java
public interface Contractable {
    // Which contract types this creature signs. The default accepts every type.
    default boolean acceptsContract(Holder<ContractType> type) {
        return true;
    }

    enum Cause {RELEASED, DEATH, FORCED}

    // After the attachment is written, before the post event: the attachment already reports the new state.
    default void onContractBound(ContractContext context) {
    }

    // Before the attachment is cleared, so it still reports the ending state, and the cause distinguishes a
    // death (no owner to name) from a release.
    default void onContractBroken(ContractContext context, Cause cause) {
    }
}
```

**契约状态不在接口里**（硬约束）：`mxt:contract` 附件是唯一记录，物品、命令、其它模块都读它，实现方
**不要自己再存一份**。接口只回答"接不接受这份契约类型"和"签订/解除时我要做什么"。

### 3.3 `ContractOperations` —— 签了之后做什么

```java
public interface ContractOperations {
    // The bell rang: the recall flag is already set and this call consumes it. Default moves the creature to
    // the owner; an implementation that walks there instead can leave the entity where it is.
    default void recall(ContractContext context) {
        ServerPlayer owner = context.owner();
        if (owner == null || owner.level() != context.self().level()) return;
        context.self().teleportTo(owner.getX(), owner.getY(), owner.getZ());
    }

    // Once per server tick while bound, with the owner online and in the same level. Default is the walk-up
    // the framework used to hardcode: teleport past 32 blocks, pathfind past 4.
    default void follow(ContractContext context) {
        // Only a Mob walks; anything else that wants to keep up overrides this.
        if (!(context.self() instanceof Mob mob)) return;
        ServerPlayer owner = context.owner();
        if (owner == null || owner.level() != mob.level()) return;
        double distance = mob.distanceToSqr(owner);
        if (distance > 32.0D * 32.0D) mob.teleportTo(owner.getX(), owner.getY(), owner.getZ());
        else if (distance > 4.0D * 4.0D) mob.getNavigation().moveTo(owner, 1.0D);
    }

    // After damage this creature dealt is resolved. The hit itself is never mutated here.
    default void onDealtDamage(ContractContext context, LivingEntity target, double damage) {
    }
}
```

**接口缺席 = 不要这套默认。** 只实现 `Contractable` 不实现 `ContractOperations` 的实体能签契约，但框架
不会替它跟随、召回或协战——连带那三个数据动作也不跑（见 §3.6 的顺序表）。这是刻意的：数据动作本来就是
为这套通用行为服务的，跑在一只从不跟随的灵兽身上没有意义。实现方一般两个都实现。

### 3.4 `Capturable` —— 能不能收进容器

```java
public interface Capturable {
    // Default is storable; a boss overrides this to false and stays out of every portable container.
    default boolean capturable(ContractContext context) {
        return true;
    }

    default void onStored(ContractContext context) {
    }

    default void onRestored(ContractContext context) {
    }
}
```

拆成第三个接口的理由与 `ItemAuraAccess` / `UseItemAuraAccess` 同理：**"能不能签"和"能不能装进口袋"是两个
问题、在两个时刻被问**，而且答案可以相反（能签不能收）。不实现 `Capturable` 的实体**收不进灵兽袋**
（与 `UseItemAuraAccess` 的口径一致：不实现就不参与）。若嫌接口多，把这三个方法并进 `ContractOperations`
（已拍板：**拆开**。把这三个方法并进 `ContractOperations`、默认 `true` = 默认能收的写法**未采纳**，
理由是不能收的 Boss 不该同时被要求实现跟随与协战。）

### 3.5 `ContractContext`

```java
public record ContractContext(LivingEntity self, @Nullable ServerPlayer owner, Holder<ContractType> type) {
}
```

- `self` 就是被契约的那只生物，`type` 是本次涉及的契约类型（解除时附件已经/即将清空，类型必须由上下文带）；
- `owner` 为空表示"没有可以点名的主人"：灵宠自己死亡、强制解除、主人离线。绑定时的 owner 与服务端玩家同物。

用上下文而不是让接口假设 `this` 是谁，是因为**接口的默认实现需要读实体状态（位置、寻路、传送）**，而
Java 接口里的 `this` 不是 `Entity`；上下文把实体显式带进来，实现方自己的类里当然继续用 `this`。

### 3.6 唯一查找入口与调用顺序

```java
// runtime/creature/Contracts.java
public static Optional<Contractable> of(Entity entity);
public static Optional<ContractOperations> operations(Entity entity);
public static Optional<Capturable> capturable(Entity entity);
```

**全仓只有这一处写 `instanceof Contractable`**（硬约束）：卷轴、御兽铃、灵兽袋、tick 桥、死亡桥、以后的
命令与脚本都走它，别在别处再散一套判断。

调用顺序（**顺序即契约**，写进实现处的注释）：

| 时刻 | 顺序 |
| --- | --- |
| 签订（卷轴 / 命令） | ① 附件已绑定？→ `ALREADY_BOUND` ② `Contracts.of` 缺席 → `NOT_CONTRACTABLE` ③ 契约类型已停用 → `DISABLED` ④ `acceptsContract(type)` ⑤ `owner_condition` ⑥ `creature_condition` ⑦ 上限（`max_owned`，读索引）→ `LIMIT_REACHED` ⑧ `Pre(BIND)`（可取消，**此时一分钱没花**）⑨ `costs` 付款 → `INSUFFICIENT_COST` ⑩ 写附件 ⑪ 写主人索引 ⑫ `onContractBound` ⑬ `Post(BIND)` |
| 摇铃（御兽铃 / `recall`） | ① owner 校验 ② 冷却（附件里的 `recall_at` + `recall_cooldown`）→ `RECALL_COOLDOWN` ③ 置 `recalled` 并记 `recall_at` ④ `Post(RECALL)`。**tick 才落地**（下一条） |
| 每 tick | ① `recalled` → `operations.recall(ctx)` → 清标志 ② `operations.follow(ctx)` ③ `follow_action`（数据动作） |
| 自己打出伤害（结算后） | ① `operations.onDealtDamage(ctx, target, damage)` ② `combat_action` |
| 灵宠死亡 | ① `break_action` ② `penalty_action` ③ `onContractBroken(DEATH)` ④ 清附件 ⑤ 删索引条目 |
| 主动解除（今天无入口，本次接上） | ① owner 校验 ② `Pre(BREAK)` ③ `onContractBroken(RELEASED)` ④ 清附件 ⑤ 删索引条目 ⑥ `Post(BREAK)`（`break_action` 是否也执行见 §8 剩余 Q7） |
| 收纳（灵兽袋） | ① owner 校验 ② `Capturable` 缺席或 `capturable()` 为假 → `NOT_STORABLE` ③ `onStored` ④ 存 NBT + `discard`（索引条目**不动**：还是同一只灵宠，只是换了个地方） |
| 放出（灵兽袋） | ① 还原实体 ② `onRestored` |

**付款必须排在 `Pre` 之后**（硬约束，理由要写进注释）：`Pre` 可取消，而这些代价里的脚本通道**退不了款**；
把付款放在事件之前就等于"事件取消后要还钱，但还不了"。所以顺序是"先问完所有条件与事件，再收钱"。

两条不对称是**故意**的，别"顺手改齐"：`onContractBound` 在写附件**之后**（回调里读附件看到的是新状态），
`onContractBroken` 在清附件**之前**（看到的是结束前的状态）。

### 3.7 档案值怎么读

接口实现要读档案（例如"灵智 ≥ 20 才签"）就直接读附件：`self.getData(MxtAttachments.CREATURE_SPIRIT)`。
**不新增访问器**——档案只有一个来源，多一层包装只会多一个要同步的口径。

> 因此整块从档案里拿掉：§1.3 里"`realm_stages` 只进 Codec"那行、§4.1 上表的 `realm_stages` 行与 §8 的 Q3 结论
> （"先留着不动"）**随之作废**，妖兽修炼将来要重开数据形状。同样走"未知键静默忽略"口径：旧包里的
> `realm_stages` 不报错、只是不再生效。

### 4.2 `contract_type`：新增三个字段（已拍板：本期做）

| 字段 | 类型 | 默认 | 用途 |
| --- | --- | --- | --- |
| `costs` | `Cost[]` | `[]` | 签订代价。`research/09:161` 早就把"契约"列为 `Cost` 的使用点，今天签订是**免费**的 |
| `max_owned` | `int` | `0`（不限） | 每个主人同时持有的本类型契约数，按主人索引计数 |
| `recall_cooldown` | `int` | `0` | 御兽铃召回冷却，**单位 tick**（与全仓其它冷却一致：技能 `cooldown` 也是 tick） |

**代价怎么付**（不与别处再造第二套）：

- 一次 `CostTransaction.pay(definition.costs(), context)`，其中
  `context = CostContext.of(owner, CostOrigin.CONTRACT).withFormula(FormulaContexts.forEntities(owner, creature, Map.of()))`
  ——付款者是**主人**（`LivingEntity`，公式上下文用卷轴今天那一份 `FormulaContexts.forEntities`），通道天然是
  主人的资源账户 + 背包 + 脚本；生物**不是**付款者（"灵兽自己付"要另给 `CostContext.account`，本稿不做）。
- `CostOrigin` 新增 `CONTRACT`（枚举现在 12 个取值，日志里"谁在收费"要能分辨）。
- 与 §3.6 的顺序表一致：**先审完条件与上限、再收钱、最后写附件**。付款失败给 `INSUFFICIENT_COST`，
  附件与索引都不动，契约不成立；`commit` 中途拒付由 `CostTransaction` 自己回滚。
- 卷轴与命令走同一条路：`/mxt contract bind` 的付款者也是参数里那个主人，管理员要免单用 `force`。

**顺手接线（今天是缺陷）**：`Failure.DISABLED` 声明了却从没用过。按全仓约定
（"`mxt:disabled` 停用条目会进补全、执行时被拒绝"），绑定前应加
`MxtDatapackRegistries.isDisabled(CONTRACT_TYPE, type)` 判定 → `Failure.DISABLED`。

**失败名表**（`ContractService.Failure`，新值加在这些位置）：

| 新值 | 何时 |
| --- | --- |
| `NOT_CONTRACTABLE` | 目标实体没实现 `Contractable`（§3.6 第 ②步） |
| `LIMIT_REACHED` | 主人名下该契约类型的数量已达 `max_owned` |
| `INSUFFICIENT_COST` | `costs` 付不起（与技能的同名失败同义） |
| `RECALL_COOLDOWN` | 御兽铃还在 `recall_cooldown` 里 |
| `NOT_STORABLE` | 目标没实现 `Capturable`，或 `capturable()` 为假（灵兽袋） |
| `NOT_LOADED` | 索引里查到但实体所在区块未加载（命令与惰性清理用） |

### 4.3 主人索引（`bound_beasts`，新）

上限、冷却下的 `list`、以及以后的灵兽面板都要回答"这个主人有哪些灵宠"，而附件的真值在**灵宠身上**，
遍历已加载实体既慢又不准（未加载的灵宠会漏，上限就会放水）。所以要一份主人侧的名单：

- **形状**：玩家附件 `bound_beasts`（`BoundBeastsAttachment`），照 `FriendAttachment` 的
  `entityServerOnly`（`copyOnDeath`、**不同步**客户端）：条目 = 灵宠 UUID + `Holder<ContractType>` +
  维度 `ResourceKey<Level>` + 绑定 gameTime。不存名字：`list` 显示"契约类型 + UUID"，实体加载时再补名字。
- **唯一维护出口**：`runtime/creature/BoundBeastService`（加/删/查/计数/惰性清理）。写点只有三处——
  绑定成功、解除、灵宠死亡；别在命令或物品里各自改这一份表。
- **索引是名单，不是真值**（硬约束）：真值永远是灵宠身上的 `mxt:contract` 附件。所以
  - **计数与 `list`** 读索引（未加载的也算数，这正是上限需要的）；
  - **动手（`break` / `recall` / `info`）** 一律按 UUID 回查实体（跨 `server.getAllLevels()` 找，只有已加载
    区块找得到）**并核对附件**后才执行；查不到就报 `NOT_LOADED` 并**顺手删掉这条索引**（惰性清理）。
- 已知的口径取舍：索引可能比真实多一条（外部手段搬走实体、存档手改），靠上面的核对与惰性清理收敛；
  反向"真值有、索引没有"只可能来自索引文件被删，此时灵宠仍能被卷轴/铃正常对待（只是不计入上限）。

### 4.4 `/mxt contract` 命令（已拍板：本期做）

一个节点一个类：`command/server/ContractCommand.java`，`ROOT` 是
`Function<CommandBuildContext, LiteralArgumentBuilder<CommandSourceStack>>`（要点名契约类型，必须建树时拿上下文），
注册进 `ServerCommandManager.NODES`（→ `MxtServerConfig.Commands.contract`，默认 `true`，顶层别名 `/contract`）。

| 节点 | 参数 | 权限 | 做什么 |
| --- | --- | --- | --- |
| `list [<player>]` | `EntityArgument.player()`（缺省 = 自己） | 只读 | 按索引列出该主人的契约：类型 + UUID + 是否已加载 |
| `info <target>` | `EntityArgument.entity()` | 只读 | 读附件：契约类型、主人、`bound_at`、召回状态、冷却剩余 |
| `bind <player> <target> <contract_type> [force]` | `EntityArgument` + `ResourceArgument.resource(context, CONTRACT_TYPE)` | `requires(mayChange)` | 走 `ContractService.bind`，代价由 `<player>` 付；`force` 跳过代价与上限 |
| `break <target> [force]` | `EntityArgument.entity()` | `requires(mayChange)` | 走 `ContractService.breakContract`（今天零调用）；`force` 跳过 owner 校验 |
| `recall <target> [force]` | `EntityArgument.entity()` | `requires(mayChange)` | 等价摇铃：置 `recalled`；`force` 跳过冷却 |

- 契约类型参数用原版 `ResourceArgument`（解析 / 补全 / "没有这个条目"三件事一起拿来，`AGENTS.md` §4）；
  被 `mxt:disabled` 停用的条目会进补全，执行时按 §4.2 的 `DISABLED` 拒绝。
- 实体参数用原版 `EntityArgument`（选择器、名字、UUID 都现成）；**没有**"按主人召回"的节点——那需要
  索引 → 实体的回查，等价于 `recall <target>` 看得见的那只，先不做。
- 读节点不写状态，因此**不**加 `requires(mayChange)`；三个写节点照约定加。
- 两份 lang：`command.mxt.contract.*` 一套，`config.mxt.server.commands.contract[.tooltip]` 两个键；
  `docs/guide/play/commands.md` 的别名计数 **16 → 17**。

## 6. 破坏性影响与迁移

1. **数据包**：`creature_profile.contract_tags` 静默失效。靠它契约的包会出现"卷轴突然没用了"，且**没有报错**。
2. **测试包**：`spirit_wolf.json` 的 `contract_tags` 删除；`minecraft:wolf` 不再可契约，`kit` 里那张卷轴
   对狼无效（这正好是探针要断言的第一条）。探针改用**实现了接口的探针实体**（§7）。
3. **签订不再免费**（如果包写了 `costs`）：不写就是 `[]`，与今天一致，所以默认包**不破坏**；
   `max_owned` 默认 `0`、`recall_cooldown` 默认 `0`，同理。
4. **行为面**：跟随/协战/死亡三条链只对实现 `ContractOperations` 的实体生效；原版生物（本来也签不了契约）
   不受影响。
5. **存档**：`ContractAttachment` 只加一个字段（旧的按缺失读），格式兼容。旧存档里"契约了一个没实现接口
   的实体"怎么处理见 §8 剩余 Q8（建议：保留附件、停摆功能，不自动解除——别吞玩家存档）。
6. **接口缺席的三种表现**要写进文档，别让内容方猜：
   - 不实现 `Contractable` → 完全不可契约（`NOT_CONTRACTABLE`）；
   - 实现 `Contractable`、不实现 `ContractOperations` → 能签，但不跟随/不召回/不协战；
   - 不实现 `Capturable` → 能签，但收不进灵兽袋。

### 11.2 与稿子的三处偏离（都是拍板或实现细节）

3. **`penalty_action` 直接删除**（用户 Q7 的"不要一个 action 负责多处行为"）：解除与死亡各一个字段，

### 11.3 落进去了但稿子没写的小决定

- 签订成功时对灵宠 `setPersistenceRequired()`：被契约的灵兽如果自然消失，主人索引会留下删不掉的一行、

- `completeRecall` 只发 `Post`，不发可取消的 `Pre`：取消一个"闩已被消费"的事件会让闩永远卡住。
- 事件 `SpiritContractEvent.Action` 的取值改成 `BIND` / `RELEASE` / `DEATH` / `RECALL` / `RECALL_COMPLETED`，

  `TamableAnimal` 已有的 `getOwnerReference` / `setOwner` 那一对，其它生物自己存一个
  `EntityReference<LivingEntity>`（并把它放进自己的存档/同步数据）。

- **解除契约不抹掉主人**：要不要连主人一起忘掉由生物自己在 `onContractReleased` 里决定——"解约"与

- 探针兽 `ProbeBeast` 自己持有 `EntityReference<LivingEntity>`，所以 `/mxt_test contract` 整条腿走的都是
  "实体自己的 owner"这条路；断言里既有 `Contracts.ownerOf(...)`（UUID），也有 `beast.getOwner() == player`
  （原版解析）。
- 影响面：`ContractService`（bind 写主人、release/recall/death 读主人）、`ContractEventBridge`（上下文里的
  在线主人改由原版解析）、灵兽袋与 `/contract info`（主人显示），全部改走 `Contracts`。

## 14. 追加：契约兽的行为与御兽铃的轮盘输入（2026-09-25）

用户要求：「做一下契约兽的行为，比如游荡、跟随等，`ContractOperations` 接口实现一下输入」，并点名
**行为不要用 enum，建一个类装载，方便扩展**；入口拍板为「命令 + 御兽铃：御兽铃右键生物绑定（＝对准这只
兽），不是生物的时候展示轮盘选择行为」，召回**当作轮盘里的一项**；内置命令集合拍板为
**跟随（默认）+ 游荡 + 驻守**。

### 14.1 行为是类，不是 enum

| 东西 | 位置 | 说明 |
| --- | --- | --- |
| `ContractBehavior` | `data/creature/` | **普通类**：`id`（`Identifier`）、`momentary`（一次性还是常驻）、`name()`（键 `contract.mxt.behavior.<命名空间>.<路径>`）；`equals`/`hashCode` 只认 id，所以存档里读回来的对象与当初写进去的是同一个行为 |
| `ContractBehaviors` | `data/creature/` | **装载类**：内置 `FOLLOW` / `WANDER` / `STAY` / `RECALL` 与 `BUILT_IN` 列表，外加 `register` / `byId` / `isKnown` / `known` |

**"不是 enum"落地成两件事**：① 内容方 `new ContractBehavior(自己的 id, false)` 再 `ContractBehaviors.register(...)`
就多了一种命令，框架**不需要**改自己的清单，也不需要动轮盘；② 装载类只负责"id ↔ 行为对象"，不是注册表
（不写数据包、不进 `MxtDatapackRegistries`），因为**行为由实体回答**，数据包没有位置声明它。
`RECALL` 是唯一 `momentary = true` 的内置项。

### 14.2 `ContractOperations` 上的"输入"

接口新增三件事，旧的 `recall` / `follow` / `onDealtDamage` 全部保留：

| 成员 | 方向 | 默认 |
| --- | --- | --- |
| `behaviors()` | 问实体 | `ContractBehaviors.BUILT_IN`（跟随 / 游荡 / 驻守 / 召回），**两侧都要能答**，铃读它填轮盘页 |
| `onBehaviorSelected(context, behavior)` | **输入**：主人下了命令 | `true`；返回 `false` 即拒绝，记录保持原样 |
| `tick(context, behavior)` | 每 tick 驱动 | 分派到 `follow` / `wander` / `stay`，不认识的命令什么都不做 |
| `wander(context)` | 新增默认 | 主人 32 格外传送过去（和跟随同一道保险，免得游荡的兽被丢下），否则每约 2 秒、且**寻路空闲时**在主人周围 3–8 格挑一个点走过去；**不加 goal** |
| `stay(context)` | 新增默认 | 停寻路 + 清攻击目标（"停下来"而不是"冻住"，所以仍然会转头看） |

刻意不做的事：**框架不往别人的实体里塞 goal**（`wander` 因此是无状态的一次性寻路请求，生物自己的
`RandomStrollGoal` 该怎样还怎样，要改由它自己覆写）；`stay` 也不动 `setNoAi`（那会连带冻住战斗与转头）。

### 14.3 命令记在哪、谁能下

- **记录**：`mxt:contract` 附件新增 `behavior`（存 id，`lenientOptional`）。读出来解析不到就**退回跟随**
  （旧存档、内容方删掉自己的行为、手改存档三种情况同一条路），所以"契约状态只有一份"没被破坏——
  轮盘页读的组件只是**铃自己的一份快照**，真值永远是这只兽的附件。
- **唯一入口**`runtime/creature/ContractBehaviorService.request(creature, requester, behavior, force)`：已绑定 →
  主人（`force` 可跳）→ 实体实现 `ContractOperations` 吗（否则 `NOT_CONTRACTABLE`）→ **这条命令在它的
  `behaviors()` 里吗**（否则 `UNSUPPORTED_BEHAVIOR`）→ `onBehaviorSelected`（`false` → `BEHAVIOR_REFUSED`）→
  一次性就直接结束，否则写记录。**召回是框架自己的一条**：它的闩与冷却记在契约记录上，所以走
  `ContractService.requestRecall`（冷却 `RECALL_COOLDOWN` 与事件都还在），不写 `behavior`。
- **铃**（`item/BeastTamingBellItem`）两个右键：**右键生物**＝对准它（服务端写组件 `mxt:contract_bell` =
  生物 UUID + 显示名 + 它自己答的命令 id 列表；不是"自己的、已绑定的、能操作的兽"就按契约失败文案拒绝），
  **右键空处**＝客户端开轮盘并停在「契约灵兽」页（页里没有东西就报铃自己的那一句）。
- **轮盘**：`WheelSource.CONTRACT`（第 5 页，和主手 / 副手 / 法器一样是**派生页**，不存布局）、
  `WheelEntryKind.BEHAVIOR`、客户端条目 `ContractWheelEntry`。`WheelSources.offers` 按**铃组件里的命令表**
  判断（"玩家手里那件东西还认不认这条命令"），`WheelService.trigger` 再走 `ContractBehaviorService`
  （真值、主人、记录都在这边重查）。轮盘页**从组件读**，因此不需要在客户端解析一只可能没加载的灵兽。
- **数据动作**：`follow_action` 现在只在**当前命令是跟随**时跑——它就是给"跟随那一刻"配色的。
- 失败名 +2：`UNSUPPORTED_BEHAVIOR`、`BEHAVIOR_REFUSED`（文案仍走 `ContractFeedback` 一张表）；
  命令新增 `/contract behavior <target> <behavior> [force]`（`behavior` 用 `IdentifierArgument` + 框架自己的
  完成列表，因为命令在代码里而不在注册表里），`/contract info` 多打一行当前命令。

### 14.4 探针与遗留

- 探针（`/mxt_test contract`，**只编译未实跑**）：铃对准（组件里是这只兽、命令表在）与"对准原版狼被拒"；
  轮盘下令生效且记录变了；`onBehaviorSelected` 返回 `false` 时记录不动；注册了但没提供给这只兽的命令
  报 `UNSUPPORTED_BEHAVIOR`；召回是"执行一次、不改当前命令"；`ContractEventBridge.onEntityTick` 真的把
  当前命令交给实体，且游荡把被丢在 40 格外的兽带回主人身边。调用序列断言相应加长。
- 遗留：轮盘页**不显示"当前命令"**（那要在客户端解析灵兽，先不做，命令面由 `/contract info` 回答）；
  `WheelEntryKind.BEHAVIOR.exists` 只对**注册过**的 id 为真（没注册的行为连手改布局也留不下来）；
  `/contract behavior` 仍是 op 入口（主人自己的入口是铃 + 轮盘）。

## 15. 追加：灵兽袋的存储改成"一份说清自己的组件"（2026-09-25）

用户要求：「写一下灵兽袋的存储，方法是把信息做一个物品组件」，并给了自己在 1.20.1 Fabric 上的参考实现
（TameTools 的 `StoreStoneItem`：把生物的 NBT 与**实体类型 id 分开**存，提示框用类型名说清袋里是什么）。
拍板：**组件里除实体数据之外还要带契约快照（契约类型 + 主人）**；释放手势改成**对着方块右键、在方块上方放出**。

### 15.1 组件形状（`mxt:spirit_beast`）

| 字段 | 类型 | 写什么 |
| --- | --- | --- |
| `entity` | `CompoundTag` | `mob.saveWithoutId(...)` 的原样结果。**NeoForge 附件就写在里面**（`Entity#saveWithoutId` 会 `serializeAttachments` 到 `NeoForgeData`/附件键），所以契约记录与生物档案一起过袋 |
| `entity_type` | `Identifier` | 生物类型 id，**放在数据旁边而不是塞进数据里**：参考实现就是这个形状，好处有两个——(a) 放出来时按它建实体（`EntityType.create` 再 `load`），被存档的数据不必带自己的 id；(b) 类型解析不出来时（内容模组被删）只是"放不出来"，袋子仍然读得动、提示框仍然说得出名字 |
| `name` | Text Component | 收纳那一刻的 `getDisplayName()`（自定义名优先），**快照**：提示框画在渲染线程上，不许去解析 NBT |
| `contract_type` | `Holder<ContractType>` | 契约快照，`/reload` 后仍按 id 解析（与卷轴组件同一套 `RegistryFixedCodec`） |
| `owner` / `owner_name` | `UUID` / String | 主人的身份与**写下来的名字**（`PlayerNames` 的既有口径：工具提示不发网络请求，所以名字在收纳时记下来，见 `ChequeComponent` 的 `issuer`） |

- `stored()` 要求 `entity` 与 `entity_type` **同时在**，缺一个就当空袋。
- 真值仍是**放出来以后那只实体自己**：快照只用于"不加载实体也能说清袋里是谁"，释放时以存档数据为准
  （所以袋里的契约类型快照过期也不会把契约改坏）。
- 参考实现里的黑名单标签与游戏规则**不采纳**：本体的规则是灵兽袋自己那一条（"你自己的已契约灵兽、一次一只"），
  其它内容方的规则属于它们自己的捕捉物品。
- 提示框：状态一行 + 灵宠名 / 契约类型 / 主人各一行（灰字）；`item.mxt.spirit_beast_bag.not_owner`
  这个**从没被读过的键**顺手删掉（失败文案早就统一走 `ContractFeedback`）。

### 15.2 释放手势

- `useOn`（对着方块右键）在**点击面的相邻方块**上方放出（比参考实现的"永远往上"更顺手，墙边也能放）。
- `use`（对着空气右键）**不再释放**：袋子有灵兽时报一句"对着方块右键，在方块上方放出灵宠"，空袋照旧 PASS。
- 释放失败（类型没了 / 建不出来 / 加不进世界）报既有的 `release_failed`，袋子内容不动。
- 探针相应改成走 `useOn`（自建 `UseOnContext` + `BlockHitResult`），并**新增断言**：组件里的类型 / 名字 /
  契约类型 / 主人 / 主人名都写对了、**放出前后的 UUID 相同**，以及**放出来的那只仍然带着契约**
  （`mxt:contract` 附件确实随 `saveWithoutId` 过袋）——这条以前没人验过。

### 15.3 已知的破坏与取舍

- **旧袋子读成空袋**：改动前那个形状只有 `entity`（生物的 id 塞在 NBT 里），新形状要求 `entity_type` 与
  `entity` 同时在，所以老存档里已经装好的袋子会被当成空袋——`stored()` 判的是"数据与类型同时在"。
  仓库口径是**未发布阶段不保留旧数据兼容**（`docs/SKILL.md`），所以没加回退分支；真要救的话，
  读 NBT 里的 `id` 就够了，但那会让"这只生物是什么类型"多出第二条读法，不划算。
- 契约快照可能过期（放出来以后契约以实体自己那份为准），袋子不去改任何契约状态，只读快照显示。
