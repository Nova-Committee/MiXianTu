# research/ —— 设计稿存档

**这里是本仓库放设计稿的地方：任何新设计、重构方案、系统改版，动手写代码之前（或同时）都要在这里留一份档。**

代码只回答"现在是什么样"，`docs/` 回答"怎么用"，而**为什么这么设计、当时否掉了哪些方案、边界在哪里**只活在这个目录里。没有留档的设计过一个版本就查不回来了，所以这条是硬要求，不是建议。

**先看下面的[目录](#目录)。** 它按主题列出每份稿的一句话主旨与当前状态：**"这篇还能不能信"看状态列；完成度永远以代码与 [`docs/模块实现审计.md`](../docs/模块实现审计.md) 为准，不以研究稿为准。**

## 目录

状态口径：

| 状态 | 意思 |
| --- | --- |
| 现行 | 结论仍然成立。动这块之前先读它 |
| 已落地 | 设计已经实现。读它是为了知道"为什么这么设计"，实现细节以代码为准 |
| 部分有效 | 文内已有作废标注，或留了"不做 / 推迟"段；按文内的修订节读 |
| 分析 / 研究 | 外部工程阅读、可行性分析或原版源码研究；未必产生代码 |
| 素材 | 不是设计稿（清单、备忘、脚本、配图） |

## 什么时候必须写

- 新增一个模块、注册表、系统，或对现有系统做改版（哪怕最后没做）。
- 做出会影响数据包格式、公开 API 或运行时语义的决定——包括**推翻**以前的设计。
- 一次审计得出了结论：现状与设计不符、字段没有消费者、某处实现与文档矛盾。

不需要写：改错别字、加断言、修单个 bug、补一句 Javadoc 这类局部改动。

## 放哪里、怎么命名

| 内容 | 位置 | 命名 |
| --- | --- | --- |
| 设计稿 / 方案 / 改版 | 本目录根下 | `NN_<主题>设计.md`，`NN` 取当前最大编号加一（现到 `35_御剑飞行系统设计.md`，下一个是 `36_`） |
| 实现说明（已经落地的机制怎么跑） | 本目录根下 | `<模块>实现.md`（如 `裂缝渲染实现.md`；`方块灵气实现.md` 沿用这个名字，内容是提案留档） |
| 审计与差距清单 | `audit/` | 按模块或主题命名（`content-coverage-gaps.md`、`technique.md`…） |
| 测试设定参考 | `测试设定参考/` | 场景矩阵、常见设定与来源记录 |
| 研究用的脚本与配图 | 本目录根下 | 与它服务的文档同名（`aura_subchunk_value.py` / `.png`） |
| 外部工程阅读（Immortal 等） | `immortal/` | `<主题>.md`（如 `傀儡与符文编程.md`），**不占编号** |
| 清单 / 备忘 / 原始素材（不是设计稿） | 本目录根下 | 中文名说清是什么（`原始需求清单.txt`、`备忘录.md`），**不占编号** |

写进去的稿子要能独立读懂：**基准**（对着哪份代码/文档写的）、**结论**、**与现状的差异**、**不做或推迟的部分**、**验证方式**。设计被推翻时不要删旧稿，在原文上标注"已于 <日期> 被 <新稿/提交> 推翻"并写清新行为——旧结论同样是资产，`audit/` 里就是这么做的。
