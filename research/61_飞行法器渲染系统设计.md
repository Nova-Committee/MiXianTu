## 1. 结论

**一个实体类型、一个注册进原版的 `EntityRenderer`，里面分三层。**

1. **`FlyingSwordRenderer` 变成分派器**：只负责「把载具摆到它的 yaw 上」+ 挑一个渲染器，剩下的交给被挑中的那个。
   原版一条实体类型只能注册一个 `EntityRenderer`（`EntityRenderDispatcher.renderers` 按 `EntityType` 开键），
   所以「一辆车一个模型、一辆车一个渲染器」只能在**这一个**渲染器内部做分派——这也是本设计的地基。
2. **默认＝今天的物品模型**（新类型 `mxt:item`）：把现在 `FlyingSwordRenderer.submit` 里那 20 行原样搬进
   `ItemMountRenderer`，**逐像素不变**（`ItemDisplayContext.FIXED`、落位用 `state.item.getModelBoundingBox().maxZ`、
   `display` 的缺省值照旧）。
3. **GeckoLib 是可选的一档**（新类型 `mxt:geckolib`）：数据包写模型 / 贴图 / 动画三个 id + 一段「状态 → 动画名」，
   客户端在**装了 GeckoLib 时**才去注册它的渲染器；没装就**回落到物品模型**并只警告一次——
   **数据包在两台机器上都解得开**，这就是「不强制安装」的落地方式。
4. **自定义渲染器**：内容模组注册一对（**common 侧**一个 `MapCodec`、**client 侧**一个渲染器），
   数据包写 `"type": "<它的 id>"`。两个注册点的形状抄 `ResourceBarRenderData` + `ResourceBarRendererDispatcher`
   这对既有先例。

**用户已拍板的四条（2026-09-29，见 §11.1）**：渲染定义**内联**在 `mxt:mount`（就三个类型，不再开一张定义注册表）；
**客户端与服务端不许串线**（§4.0 是硬约束）；`display` **可选**、缺省就是现在的渲染方式；
包用了 GeckoLib 模型而**这台机器没装** → **仅提示 + 回落到默认**（物品模型）。姿态表**一次给满**（§3.6，7 个值两组）。

一句话：**`mxt:mount` 多一个 `render` 字段（一个按 `type` 分派的渲染定义），客户端按 `codec` 找渲染器，
找不到就用物品模型顶上去。**

## 2. 与现状的差异

| 维度 | 现在 | 改成 |
|---|---|---|
| 画什么 | 唯一一条路：承载物品的物品模型 | 数据包的 `render` 说了算；缺省还是物品模型（`mxt:item`） |
| 渲染器从哪来 | 写死在 `FlyingSwordRenderer.submit` 里 | 客户端注册表 `MountRenderers`，按渲染定义的 `codec` 开键 |
| GeckoLib | 无 | 可选类型 `mxt:geckolib`；没装则**仅提示 + 回落物品模型** |
| 自定义 | 不可能（除非 mixin 掉 `MxtRenderers`） | common 注册类型、client 注册渲染器 |
| 客户端 / 服务端边界 | —（没有这一类东西） | **数据与类型注册在 common、渲染器与回落在客户端**，§4.0 五条硬约束 |
| `display` | `FlightDisplay`，缺省 `FlightDisplay.DEFAULT`（物品那套 90/0/-45、×2） | 字段改成**可选**；缺省由渲染器给：**物品那一档仍是今天那套**（"现在的渲染方式"），GeckoLib 那一档是恒等 |
| 定义的读取 | 渲染器每帧 `ArtifactService.mount(registryAccess, visual)` 解一遍 | 读 `FlyingSwordEntity.mountDefinition()`（实体已经按 `visual` 缓存好的那份） |
| 渲染状态 | `FlyingSwordRenderState`（物品状态 + yaw/xRot/display） | 加「这一帧用哪个渲染器 + 它自己的那份状态 + 两条姿态轴快照」 |
| 载具几何 | `width` / `height` / `seat_offsets`（数据给） | **不动**——渲染器只管画，箱子仍然是数据 |
| 身体姿态 | 渲染器自己 `mulPose(YP/-yRot)` | 分派器做 yaw，**pitch 与 `display` 交给渲染器**（见 §4.4，为了老包不移位） |
| 新同步字段 | — | **不加**（两条姿态轴从客户端可见的位置差 / 乘客数算，见 §4.6） |

## 3. 数据形状

### 3.1 `mxt:mount` 上的新字段 `render`

**（2026-09-29 用户拍板：内联在 `mxt:mount` 上，不另开 `mxt:vehicle_render` 定义注册表——内置类型只有三个，
多一层引用没收益；`render` 是 common 的数据，服务端也解码它，但服务端永远不解析渲染器，见 §4.0。）**

`MountAbilityType`（`data/ability/type/MountAbilityType.java`）加一个组件：

```java
MountRender.CODEC.optionalFieldOf("render", ItemMountRender.INSTANCE).forGetter(MountAbilityType::render)
```

* **不写就是 `mxt:item`**，与今天的观感完全一致（老包一个字都不用改）。
* 写了就必须有 `type`（`dispatch("type", …)` 的字段是必填的），写法与 `mxt:resource_bar` 的
  `render` / 各种 `mxt:*_type` 同口径。
* `type` 必须是**已注册的渲染类型**：未知 id 会在**加载期报错**（`Registry.byNameCodec` 走
  `MappedRegistry.get(Identifier)` → 空 → `Unknown registry key in mxt:mount_render_type: …`；`DefaultedMappedRegistry`
  只覆盖 `getValue`/`getId`/`byId`，**不覆盖 `get`**，这条是逐行核过的）。所以 `create("item", MOUNT_RENDER_TYPE)`
  的第一个参数只影响 `getId`/`getValue` 那几条回落路径，**不是**「写错就用物品模型」。
* 与 `mxt:mount` 现有的「不读的字段静默忽略」口径不冲突：`render` 是**读**的字段。

```json
// data/example/mxt/ability/azure_sword_mount.json（片段）
{
  "type": "mxt:mount",
  "speed": 0.12,
  "seats": 2,
  "render": {
    "type": "mxt:geckolib",
    "model": "example:vehicle/azure_sword",
    "texture": "example:textures/entity/vehicle/azure_sword.png",
    "animations": "example:vehicle/azure_sword",
    "states": { "idle": "hover", "moving": "fly", "ascending": "climb", "descending": "dive" },
    "transition_ticks": 5,
    "scale": 1.0
  }
}
```

### 3.2 `mxt:item`（默认那一档）

零字段，`enum ItemMountRender implements MountRender { INSTANCE; }` + `MapCodec.unit(INSTANCE)`
（形状抄 `MissingRenderData` / `NoOpAction`）。显式写法是 `"render": {"type": "mxt:item"}`；
`type` 是**必填**的（`dispatch` 的键字段缺失会报 `Input does not contain a key [type]`，所以 `"render": {}` 不成立），
多写的未知键照全仓统一口径静默忽略。

### 3.3 `mxt:mount_render_type`（新的一张固有分派表）

| 项 | 值 |
|---|---|
| 注册表 | `MxtRegistries.MOUNT_RENDER_TYPE = create("item", MxtResourceKeys.MOUNT_RENDER_TYPE)`（**内置分派表那一段**，与 `ABILITY_TYPE`、`RESOURCE_BAR_RENDER_DATA_TYPE` 同列；**不动** `MxtDatapackRegistries` 那 38 张数据包注册表） |
| key | `MxtResourceKeys.create("mount_render_type")` |
| 注册器 | `registry/MxtMountRenders.java`（`DeferredRegister<MapCodec<? extends MountRender>>`，形状抄 `MxtResourceBarRenderers`） |
| 内置两条 | `mxt:item`（`ItemMountRender`）、`mxt:geckolib`（`GeckoLibMountRender`） |
| 分派 codec | `MountRender.CODEC = MxtRegistries.MOUNT_RENDER_TYPE.byNameCodec().dispatch("type", MountRender::codec, Function.identity())` |

数据侧目录：`data/ability/render/{MountRender.java, MountPose.java, builtin/ItemMountRender.java,
builtin/GeckoLibMountRender.java}`（放在 `MountAbilityType` 旁边；`MountPose` 见 §3.6）。
**`GeckoLibMountRender` 是纯数据**——只有 `Identifier`、`String`、数字与一张枚举表，**一个 `com.geckolib` 类型都不引用**，
所以它在没装 GeckoLib 的机器上也照常注册、照常解码（这是 §1 第 3 条能成立的前提）。

### 3.4 `display` 的语义收口

今天的 `display` 是 `mxt:mount` 的字段、默认 `FlightDisplay.DEFAULT`（`rotation [90,0,-45]`、`scale [2,2,2]`），
它其实描述的是**物品模型**怎么躺。GeckoLib 模型是照着 Y 轴向上做的，套上 90/-45 就趴了。

改成（**2026-09-29 用户拍板：可选**）：**`display` 仍然写在 `mxt:mount` 上、仍然是「模型相对载具原点怎么摆」那一件事，
但字段变成可选，缺省值由渲染器自己给。**

* `MountAbilityType.display()` 的类型从 `FlightDisplay` 变成 `Optional<FlightDisplay>`；
* `mxt:item` 的缺省仍是 `FlightDisplay.DEFAULT`——**"缺省就是现在的渲染方式"，所以不写 `render` 也不写 `display`
  的老包行为一个字不变**；
* `mxt:geckolib` 的缺省是恒等（新增常量 `FlightDisplay.IDENTITY = (0,0,0)/(0,0,0)/(1,1,1)`）：
  geo 模型是照着 Y 轴向上做的，套上物品那套 90/-45 会趴下去；要平躺就在自己那份定义里写 `display`；
* 第三方渲染器拿到的是 `Optional<FlightDisplay>`，自己决定缺省。

`FlightDisplay` 的**构造器把 `translation` 除以 16**、`validate` 只查有限性这两条都不动，
老包从物品模型 `display` 里抄过来的数字仍然能直接用。

### 3.5 `mxt:geckolib` 的字段

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `model` | `Identifier` | **必填** | `.geo.json` 的**去掉前后缀的 id**，见 §5.2 |
| `texture` | `Identifier` | **必填** | 正常贴图 id（`assets/<ns>/textures/…png`） |
| `animations` | `Identifier` | 可选 | `.animation.json` 的 id；**不写＝静态模型**（不注册任何控制器，见 §5.5） |
| `states` | `Map<MountPose, String>` | `{}`（＝恒等） | 姿态 → 动画名；**键可以跨两组写**（§3.6）；没写的项按**姿态自己的名字**取 |
| `transition_ticks` | int ≥ 0 | `5` | `AnimationController` 的过渡刻数 |
| `scale` | double > 0 | `1.0` | 乘在 GeckoLib 模型自己的尺度上（1 模型单位 = 1/16 格，GeckoLib 自己换算） |

`states` 的键是**固定词表** `MountPose`（`StringRepresentable`，7 个值见 §3.6），写未知取值**加载期报错**
（未知枚举取值在 `Codec.unboundedMap` + `StringRepresentable.fromEnum` 上本来就会拒，符合本仓口径）。
第一版**不做** `glow` / `render_type` / molang 变量 / 关键帧音效，见 §7。

### 3.6 姿态表（一次给满，7 个值分两组）

词表 `MountPose` 一共 **7 个值**，一次定全，分两组；**每组各自是一个总函数**（任何时刻每组恰好命中一个值），
所以缺省（`states` 不写）等价于"每个姿态都去找与它同名的动画"：

| 组（`MountPose.axis()`） | 值 | 客户端的判据 | 默认动画名 |
|---|---|---|---|
| 运动（`MOTION`） | `idle` | 这一 tick 位置没变 | `idle` |
| | `moving` | 水平位移 > ε | `moving` |
| | `ascending` | 竖直位移 > ε | `ascending` |
| | `descending` | 竖直位移 < −ε | `descending` |
| 载员（`CREW`） | `empty` | 乘客数 = 0 | `empty` |
| | `ridden` | 乘客数 = 1（只有驾驶者） | `ridden` |
| | `carrying` | 乘客数 ≥ 2 | `carrying` |

* **一个枚举、一张 `states` 表**（键跨两组都能写），**但两组各起一个 `AnimationController`**（§5.5）：
  "载人时上升"这种组合是两条动画同时播（各自管自己的骨骼）——这是 GeckoLib 本来就用多控制器表达
  "多条互不干涉的轴"的方式；只用一个控制器就得在优先级里丢掉一整个维度。
* 判据全部来自**客户端可见**的东西：位置差（§4.6）与 `entity.getPassengers().size()`，**不加同步字段**。
* 载员那组对"载具"是有意义的：`empty` 只在起剑那一瞬间可能出现（无人载具会自清），
  但 `carrying`（多座位载具后座有人）是稳定可见的状态。
* 竖直优先于水平：`ascending` / `descending` 一旦成立就不再是 `moving`（`MountPose.motion(...)`，§4.6）。
* 巡航（按冲刺键的 ×1.5）**不做成姿态**：别的玩家的输入在客户端看不到，
  按位移大小判会让"同一辆车在不同客户端上姿态不同"。

## 4. 客户端架构

### 4.0 客户端 / 服务端边界（**不许串线**）

这是本设计里最容易出错、也最需要在实现时盯着的一条。**载具渲染定义是数据、渲染器是客户端产物**，
两者必须待在不同的层里：

| 放哪 | 内容 | 两端都加载吗 |
|---|---|---|
| `data/ability/render/**`（`MountRender` / `MountPose` / 两个内置记录） | 纯数据：`Identifier`、`String`、数字、枚举。**import 里不许出现 `net.minecraft.client.*` 与 `com.geckolib.*`** | **是**（common）：服务端也要解码它（数据包在服务端加载、`mxt:mount` 里有这个字段） |
| `registry/MxtMountRenders.java` + `MxtResourceKeys.MOUNT_RENDER_TYPE` + `MxtRegistries.MOUNT_RENDER_TYPE` | 类型分派表的注册（`DeferredRegister` 挂 **mod bus**，与 `MxtResourceBarRenderers` 同一处） | **是**（common） |
| `api/MountRenderer` / `api/MountRenderContext`、`render/mount/**`、`compat/geckolib/**` 的 client 半 | 渲染器接口、注册表、具体渲染器、GeckoLib 适配 | **否**：只在 `Dist.CLIENT` 一侧被加载 |
| `render/FlyingSwordRenderer.java` 本身 | 分派点 | 否（它已经是客户端类） |

五条硬约束：

1. **服务端一行都不引用渲染器**：`MountRenderers.resolve` 只在 `FlyingSwordRenderer` 里被调用，
   全仓没有任何 `ServerLevel` / 服务端服务引用 `MountRenderer`、`MountRenderContext`、`MountRenderers`
   或 `compat/geckolib/**`。
2. **注册点不混**：类型 codec 在 common 的 `MiXianTu` 构造里 `MxtMountRenders.REGISTRY.register(bus)`
   （与 `MxtDataStorages` / `MxtAbilityTypes` 同一处）；渲染器只在
   `@EventBusSubscriber(Dist.CLIENT)` 的 `MxtRenderers` 里注册。**两者的类不要合并**。
3. **"没装 GeckoLib"的提示只在客户端**：专用服务端不渲染，所以它不会、也不该为这件事打任何日志
   （它连 `MountRenderers` 都加载不到）；服务端眼里 `mxt:geckolib` 与 `mxt:item` 一样只是"一段解出来的数据"。
4. **回落是客户端的判决**：`resolve` 找不到渲染器 → 用 `mxt:item` 顶上 + 一行 WARN，这件事在服务端不存在。
5. **服务端不做客户端校验**：`GeckoLibMountRender` 的加载期校验只回答"字段本身合不合法"
   （有限性、非空、枚举取值），**不查模型 / 贴图 / 动画文件在不在**——那些文件在客户端资源包里，
   专用服务端根本看不到；查了就会变成"服务端报错、客户端没事"这种反过来的串线。
   文件缺失的表现是 §5.6 那张表里的**客户端**行为。

实现时用两条 grep 自查（写进 §9.1）：

```bash
# common 侧不许出现客户端 / GeckoLib 类型

# 服务端侧不许碰渲染器
rg -n "MountRenderers|MountRenderer\b|MountRenderContext" src/main/java/com/iafenvoy/mxt/runtime src/main/java/com/iafenvoy/mxt/command/server
```

### 4.1 分派点

```java
public final class FlyingSwordRenderer extends EntityRenderer<FlyingSwordEntity, FlyingSwordRenderState> {
    // createRenderState → new FlyingSwordRenderState()（不变）
    // extractRenderState：yaw / xRot / partialTick / lightCoords / moving / 升降 + 解出渲染器与它那份状态
    // submit：mulPose(YP, -yRot) → 交给渲染器；最后 super.submit(...)（名牌与拴绳那套不动）
}
```

* `affectedByCulling` 仍然返回 `false`（长条模型比箱子大得多，理由见今天的注释）。
* `shadowRadius = 0.4F` 不动。

**渲染器的解析（每帧，但结果是缓存的）**：`entity.mountDefinition()`（实体已经按 `ItemStack.matches` 缓存）
→ `mount.render()` → `MountRenderers.resolve(render)`；把解析出来的 `MountRenderer<?>` 与它的状态存进
`FlyingSwordRenderState`，**当 `render` 对象 `equals` 仍相等时复用**（`/reload` 换了定义 → 不等 → 重新解析）。
`ArtifactService.mount(…)` 这条每帧多解一遍定义的老路顺手删掉。

### 4.2 渲染器契约（`api/MountRenderer.java`）

**它是对外契约**（别的模组要实现），所以按 `WheelMenuEntry` 的先例放进 `api/`（`api/` 里已经有客户端接口）。

```java
public interface MountRenderer<T extends MountRender> {
    // 每辆车一份的草稿状态；渲染状态每帧新建（原版 EntityRenderer.createRenderState(entity, partialTick)
    // 就是 new 一个），所以历史只能存在渲染器自己的缓存里，不要指望它跨帧。
    MountRenderState createState();

    // 这一帧要画的东西都从 context 读走；context 出了这一帧就不再有效。
    void extract(T definition, MountRenderContext context, MountRenderState state);

    // poseStack 已经停在载具原点、已经转过 yaw；俯仰与 display 由实现自己接（见 §4.4）。
    void submit(T definition, MountRenderState state, PoseStack poseStack,
                SubmitNodeCollector collector, CameraRenderState camera);
}
```

`MountRenderState` 是 `api/` 里的空标记接口（每辆车一份、由 `createState()` 造）；`MountRenderContext`
也是接口（实现留在 `render/mount/`，符合 `api/` 「只放接口」的房规）：

```java
public interface MountRenderContext {
    ItemStack visual();              // 载具承载的那件法器（只读）
    Optional<FlightDisplay> display();
    float yRot(); float xRot(); float partialTick();
    int lightCoords();               // EntityRenderState.lightCoords
    MountPose motion();              // §4.6 运动组
    MountPose crew();                // §4.6 载员组
    int riders();                    // 乘客数（含驾驶者）
}
```

**不把 `MountAbilityType` 塞进 context**：第三方要的是「怎么摆、几点光、什么姿态」，不是载具的速度与座位；
真要读整条定义，它自己的渲染类型里写自己的字段。

### 4.3 注册表（`render/mount/MountRenderers.java`）

照抄 `ResourceBarRendererDispatcher` 的形状：**按 codec 开键**，不另造 id（免得 common 侧注册的 id 与 client
侧注册的 id 不一致）。

```java
public final class MountRenderers {
    private static final Map<MapCodec<? extends MountRender>, MountRenderer<?>> RENDERERS = new HashMap<>();

    public static <T extends MountRender> void register(MapCodec<T> codec, MountRenderer<T> renderer);

    // 找不到就回 mxt:item，并**每个 codec 只警告一次**（不是每帧一行）。
    public static MountRenderer<?> resolve(MountRender definition);
}
```

* 注册时机：客户端 mod bus 的 `EntityRenderersEvent.RegisterRenderers`（`MxtRenderers.registerRenderers`）里
  先注册内置两条，再在 GeckoLib 的门里注册 GeckoLib 那条（§5.1）。**只在游戏线程读**，不加锁
  （与 `WheelSourceTypes` 同一条约定）。
* 先注册者胜（`putIfAbsent`），后注册的同 `codec` 忽略。
* 回落路径必备：`resolve` 永不为空——「这个渲染器这台机器上没有」表现为**物品模型 + 一条日志**
  （日志内容点名是哪个渲染类型、以及 GeckoLib 未安装这种最常见的原因）。

### 4.4 变换契约（谁负责哪一段）

今天的顺序（`FlyingSwordRenderer.submit`，逐行）：

```
mulPose(YP, -yRot) → translate(display.translation.x, 落位 + display.translation.y, z)
→ mulPose(XP, xRot) → mulPose(rotationXYZ(display.rotation)) → scale(display.scale) → item.submit(...)
```

注意 **`translation` 是在 yaw 之后、pitch 之前**叠加的（也是在**世界轴**上加的，所以 `y` 还是"上"）。

新契约：**分派器只做 `mulPose(YP, -yRot)`；从 pitch 往里全部归渲染器**。

* `ItemMountRenderer` 接着做 `translate → XP → rotationXYZ → scale → item.submit`，**与今天逐字相同**，
  老包写过的 `display.translation` 语义一个字不变；
* `GeckoLibMountRenderer` 接着做 `XP → display（缺省恒等）→ scale`；
* 第三方渲染器**第一件事就应该是 `XP`**（写进 `api/` 的 Javadoc 与文档站）。

另一条路的代价写在这里、供拍板：**让分派器连 pitch 一起做、把 `translation` 挪到 pitch 之后**，
好处是契约更对称，坏处是**已经写了 `translation` 的包视觉会变**（`translation.y` 会从"世界上方"变成
"模型上方"）。本文选前者。

**落位（模型底面贴在箱子底面上）**:今天靠 `scale.z * item.getModelBoundingBox().maxZ` 算出来，
这是物品模型特有的问题。GeckoLib 的模型在 Blockbench 里就是照着"原点＝底面中心"做的，所以
**不自动落位**，要挪就写 `display.translation`。`ModelProperties.visibleBoundsHeight/Offset`（GeckoLib 5.5.2 有）
**不拿来做自动落位**：它来自 `visible_bounds`，很多模型根本不写，写了也不等于碰撞底面——
拿它算会让"同一个模型在两台机器上落位不同"。这条进 §11 待拍板。

### 4.5 每帧状态

`FlyingSwordRenderState` 加这三个字段（其余不动）：

```java
public class FlyingSwordRenderState extends EntityRenderState {
    public final ItemStackRenderState item = new ItemStackRenderState();  // 只给 mxt:item 用
    public float yRot; public float xRot;                                  // 不变
    public Optional<FlightDisplay> display = Optional.empty();             // 由分派器填

    public @Nullable MountRenderer<?> renderer;                            // 这一帧用谁
    public @Nullable MountRenderState rendererState;                       // 它的草稿状态
    public MountPose motion = MountPose.IDLE;                              // §4.6 两条轴（各占一组）
    public MountPose crew = MountPose.RIDDEN;
    public int riders;
}
```

`partialTick` 与 `lightCoords` 用原版 `EntityRenderState` 自带的两个字段（`EntityRenderState.partialTick:39`、
`lightCoords:30`，26.1.2 源码），不再另存。

`mountId` 是给 `MountRenderer` 里的 GeckoLib 那一档用的：`GeoObjectRenderer` 把我们的渲染状态当
`relatedObject` 递给 `getInstanceId(animatable, relatedObject)`，动画状态才分得开（§5.3）。

### 4.6 姿态从哪来（**不加同步字段**）

GeckoLib 的动画选择需要一个"现在是什么状态"的输入。候选有三条路：

| 方案 | 依据 | 评价 |
|---|---|---|
| **A（本文选）位置差** | 平台每 tick 在 `Entity#tick` **之前**调 `entity.setOldPosAndRot()`（`ClientLevel.tickNonPassenger`，26.1.2 `ClientLevel.java:360`；`Entity#setOldPos` 写 `xo/xOld` 等六个字段），收到服务端位置后走 `moveOrInterpolateTo` → `InterpolationHandler.interpolate()`（`Entity.java:2482-2493`、`InterpolationHandler.java:77-108） | 不需要新同步字段；`entity.position().distanceToSqr(entity.oldPosition())`（`Entity#oldPosition()` 是 public 的）超过 `1e-8` 即"这一 tick 真的动了"，`y` 的差给升/降。悬停（服务端位置不变、只有朝向变）**不会**被误判成移动——这正是不能直接用 `InterpolationHandler.hasActiveInterpolation()` 的原因：驾驶者转头也会让它为真 |
| B 同步一个 `EntityDataAccessor<Byte>` | `FlyingSwordEntity.tick` 已经在算 `moving`（`emitTrail(!collided)`） | 最权威、跨客户端一致；代价是多一个同步项与一处协议面 |
| C 客户端速度 | `getDeltaMovement()` | **不可用**：客户端的位移由插值写坐标，`deltaMovement` 并不跟着同步（`interpolateTo` 不碰它） |

`MountPose`（common 的**一个**枚举、7 个值、`StringRepresentable`，每个值知道自己属于哪一组）由两个纯函数给出，
**所以服务端探针也能断言它们**：

```java
public enum MountPose { IDLE, MOVING, ASCENDING, DESCENDING, EMPTY, RIDDEN, CARRYING;
    public enum Axis { MOTION, CREW }
    public Axis axis();
    // 竖直优先：一旦有竖直位移就不算 moving（§3.6）
    public static MountPose motion(double horizontalDelta, double verticalDelta);
    public static MountPose crew(int riders);   // 0 / 1 / ≥2
}
```

两个控制器各拿**同一个枚举**里属于自己那一组的值（一个 `states` 表、一个 codec，键不重复，所以不需要两张表）。

选 A 的理由是"零协议面"，但它**必须在实机里验一次**（§9.3 第 4 条）；不成立就退到 B（一处 `set`、一处读）。

## 5. GeckoLib 接入

### 5.1 可选依赖的隔离（`FtbChunksCompat` 同款两半）

```
compat/geckolib/GeckoLibCompat.java          // 不含一个 com.geckolib 类型：loaded()、MOD_ID
compat/geckolib/GeckoLibMountRenderers.java  // client：引用 com.geckolib.* —— 只在门里被加载
compat/geckolib/GeckoLibMountRenderer.java   // client：MountRenderer<GeckoLibMountRender>
compat/geckolib/MountAnimatable.java         // client：单例 animatable（GeoAnimatable）+ 有界缓存
compat/geckolib/MountGeoModel.java           // client：GeoModel，三个资源 id 从渲染状态里读
```

`FtbChunksCompat` 的类注释已经把这条口径写死了：**「这个类不声明任何 FTB 的东西、无条件可达；引用 FTB 的那个类
只在门内被触及，因为这里出现一个 FTB 类型就会让每台没装 FTB Chunks 的服务器起不来。」** GeckoLib 照办：

```java
@EventBusSubscriber(Dist.CLIENT)
public final class MxtRenderers {
    public static void registerRenderers(RegisterRenderers event) {
        ...
        MountRenderers.registerBuiltins();                                  // mxt:item
        if (GeckoLibCompat.loaded()) GeckoLibMountRenderers.register();      // mxt:geckolib（类在这一行才被加载）
    }
}
```

**编译期**只要现有的 `compileOnly "com.geckolib:geckolib-neoforge-${minecraft_version}:${geckolib_version}"`
（`build.gradle:154`）；**运行期**不装也照样启动。要能在开发客户端里真的看到模型，另需 dev 侧的运行时依赖，见 §8。

### 5.2 资产路径（GeckoLib 5.5.2 的实际约定，逐行核过）

| 资产 | 放哪 | 写进 `render` 的值 |
|---|---|---|
| 模型 | `assets/<ns>/geckolib/models/<path>.geo.json` | `"model": "<ns>:<path>"` |
| 动画 | `assets/<ns>/geckolib/animations/<path>.animation.json` | `"animations": "<ns>:<path>"` |
| 贴图 | 正常贴图位置 `assets/<ns>/textures/…png` | `"texture": "<ns>:textures/…png"` |

依据：`GeckoLibResources.MODELS_PATH/ANIMATIONS_PATH` 是 `geckolib/models` 与 `geckolib/animations`（按命名空间
落在各自的 `assets/<ns>/` 下），`bakeResource` 用 `stripPrefixAndSuffix` 把 `geckolib/models/` 前缀与
`.geo.json`/`.animation.json` 后缀**剥掉**当缓存键。所以**写裸 id**；写带前缀/后缀的"旧写法"虽然还能命中，
但 GeckoLib 会为它打一行 `Superfluous prefix or suffix found in …` 的 error——文档里直接写裸 id。

**加载不需要我们做任何事**：GeckoLib 自己的 `PreparableReloadListener` 在资源重载时把这两个目录整个烘一遍，
`/reload` 改模型立刻生效（与数据包里的 `render` 同一条节奏）。模型文件缺失时 GeckoLib 自己回落成
"missingno"（紫黑方块）并打 error，这是它的既有行为，我们不遮。

### 5.3 每个模型一个 `GeoObjectRenderer`

`GeoObjectRenderer<T extends GeoAnimatable, O, R extends GeoRenderState>` 正是"既不是实体、也不是物品"的
那一档（它的类注释就是这么写的），而我们的载具**不能**是 `GeoAnimatable`——`FlyingSwordEntity` 是常驻类，
一旦 `implements GeoAnimatable`，没装 GeckoLib 的机器加载这个类时就会 `NoClassDefFoundError`。

所以：**实体不是 animatable，渲染器是。** 一辆车一次 `performRenderPass`：

```java
objectRenderer.performRenderPass(animatable, null, poseStack, collector, camera, state.lightCoords(), state.partialTick());
```

`GeoObjectRenderer` 的三处覆写是必须的（都是逐行看过的）：

1. **`adjustRenderPose`**：基类里写死 `translate(0.5f, 0.51f, 0.5f)`（它是给"方块中心为原点"的对象用的）。
   我们**覆写成空**，改成在这里叠 `display`（`XP` 由分派器之后的这一段负责）。
2. **`getInstanceId(animatable, relatedObject)`**：基类默认 `animatable.hashCode()`，对单例 animatable 就是
   一个常数——那样所有载具会共享一套动画状态。覆写成**载具实体的 id**（`relatedObject` 里带过来），
   于是每辆车各播各的。
3. **`createRenderState`** 用基类默认的 `GeoRenderState.Impl` 即可（它是 GeckoLib 自带的 `GeoRenderState` 实现，
   不依赖原版 `EntityRenderState`，所以我们**不需要** GeckoLib 往 `EntityRenderState` 上注入的那个 duck 接口）。

每个"模型 + 贴图 + 动画"组合**一个** `GeoObjectRenderer` 实例，按 `GeckoLibMountRender`（record，`equals` 可用）
开一张客户端缓存（定义数量有上界，不用淘汰）。

### 5.4 单例 animatable 与有界缓存

```java
final class MountAnimatable implements GeoAnimatable {
    private final AnimatableInstanceCache cache = new MountAnimatableCache(this);   // 见下
    @Override public void registerControllers(AnimatableManager.ControllerRegistrar controllers) {
        if (definition.animations().isEmpty()) return;                 // 静态模型：一个控制器都不加（§5.5）
        controllers.add(motionController);                             // 运动组（MountPose.Axis.MOTION）
        controllers.add(crewController);                               // 载员组（MountPose.Axis.CREW）
    }
    @Override public AnimatableInstanceCache getAnimatableInstanceCache() { return this.cache; }
}
```

**一个** `MountAnimatable` 实例服务所有载具，动画状态按 §5.3 的 `getInstanceId`（实体 id）分家。

**缓存不能无限长**：`SingletonAnimatableInstanceCache.getManagerForId` 是
`managers.computeIfAbsent(id, …)`（`Long2ObjectOpenHashMap`，**没有任何移除入口**），而载具是瞬发的、
实体 id 只增不减——照默认写法，"每飞一次留一个 manager"。所以自建一个子类，
`getManagerForId` 在 `getAndMoveToFirst` 之外**限制容量（建议 128）**，超了就丢最久没被问到的那个。
被丢掉的载具下次渲染时动画从头开始，视觉上无从察觉；同时这也顺手把"长途会话"的泄漏钉死。

（`AnimatableManager` 只暴露 `markRenderedAt`/`getFirstRenderTick`，**没有**"最后渲染时刻"的读法——
`AnimatableManager.java:116-123`。所以淘汰按"我们自己 LRU 的顺序"，不按时间。）

### 5.5 控制器与状态映射（两组各一个控制器）

* **不写 `animations` 就不注册任何控制器**（`registerControllers` 加 0 个）：`AnimationProcessor.extractControllerStates`
  在 `controllers.isEmpty()` 时直接跳过整段（`AnimationProcessor.java:54`），等于纯静态模型，也不会去查动画文件。
* 写了 `animations` 就**两个**控制器（`mxt_motion` / `mxt_crew`），各读自己那条轴（§3.6）；过渡刻数都用
  `transition_ticks`，两条轴各自过渡、互不影响：

```java
private PlayState motion(AnimationTest<MountAnimatable> test) {
    MountPose axis = test.getData(ANIMATION_MOTION);          // 我们自己往 GeoRenderState 里塞的 DataTicket
    return play(test, definition.animationFor(axis));          // states 缺项 → 姿态自己的名字（§3.5）
}
private PlayState crew(AnimationTest<MountAnimatable> test) {
    MountPose axis = test.getData(ANIMATION_CREW);
    return play(test, definition.animationFor(axis));
}
private PlayState play(AnimationTest<MountAnimatable> test, String name) {
    return animationExists(definition, name)                   // 见下：静默存在性检查
            ? test.setAndContinue(RawAnimation.begin().thenLoop(name))
            : PlayState.STOP;
}
```

* 两个 `DataTicket`（`ANIMATION_MOTION` / `ANIMATION_CREW`，
  `DataTicket.create("mxt_mount_motion" | "mxt_mount_crew", MountPose.class)`）由渲染器在
  `addRenderData(animatable, relatedObject, renderState, partialTick)` 里塞进 GeckoLib 的渲染状态
  （`relatedObject` 就是我们的 `FlyingSwordRenderState`，等于把 §4.6 的两条轴喂给两个控制器）。
* **动画名查不到不能每帧刷屏**：GeckoLib 在找不到动画时**每帧**打 `Unable to find animation: '…'`。
  所以我们**自己做静默存在性检查**，绕开它那条 error 分支：
  `GeckoLibResources.getBakedAnimations().cache().get(动画文件)` → `BakedAnimations.getAnimation(名字)`
  （`BakedAnimationCache` 是 record，`cache()` 与 `BakedAnimations.getAnimation` 都是 public 且不打日志），
  结果按 `(动画文件, 名字) → 有没有` 记成一张 memo。**缺省（`states` 不写）意味着 7 个名字全都要查一次**，
  一台客户端上绝大多数是"没有"——所以 memo 与静默检查是必需的，否则每个载具每帧都在报错。
  建议：每个 `(动画文件, 名字)` 的缺失**只留一行 WARN**（点明是哪个动画文件、哪个名字），便于作者发现拼写错误。
* `definition.animationFor(MountPose)` 是**纯数据函数**（`GeckoLibMountRender` 上的方法，`states` 里查不到就用
  姿态自己的名字），所以服务端探针能断言它（§9.2）。

### 5.6 缺 GeckoLib / 缺模型时的表现

| 情况 | 表现 |
|---|---|
| 没装 GeckoLib，包写了 `mxt:geckolib` | 数据**照常加载**；客户端回落到 `mxt:item` + 警告一次（点名渲染类型） |
| 装了 GeckoLib，没装模型文件 | 画 GeckoLib 的 missingno 方块 + GeckoLib 自己的 error 日志 |
| 装了 GeckoLib，动画名写错 | 静态姿态（不播动画）+ 每个 `(动画文件, 名字)` 一行 WARN（§5.5 自己做的静默检查，**不是** GeckoLib 的每帧 error） |
| `texture` 指向不存在的贴图 | 原版缺失贴图（黑白格），与原版物品模型同一种表现 |
| 定义被 `/reload` 改掉 | 下一帧重新解析渲染器（§4.1）；模型/动画文件随 GeckoLib 自己的重载器换 |

## 6. 内容模组怎么加一个自定义渲染器

```java
// common：注册渲染类型（mod 构造期，DeferredRegister 到 MxtMountRenders.REGISTRY）
MxtMountRenders.REGISTRY.register("my_vehicle", () -> MyVehicleRender.CODEC);

// client：注册渲染器（EntityRenderersEvent.RegisterRenderers 之后随便哪个客户端 setup）
MountRenderers.register(MyVehicleRender.CODEC, new MyVehicleRenderer());
```

* 两边都以 **`MapCodec` 为键**，所以不存在"id 写得不一致"这种错；
* 只在客户端注册渲染器、common 不注册类型 → 数据包写这个 `type` 会在加载期报未知注册表键（§3.1）；
* common 注册了类型、这台机器没注册渲染器（比如渲染器在那次客户端初始化里没跑到）→ 回落物品模型 + 日志；
* **服务端**永远不碰渲染器：`mxt:geckolib` / 自定义类型在专用服务端上只是"解出来的一份数据"。
* KubeJS / 数据包**进不来**（渲染器是 Java 对象），与 `WheelSource` / `WheelEntryKind` 同一条口径。

## 7. 不做与推迟

1. **物品栏 / 手上的 GeckoLib 模型**：法器可以是**任意物品**（`artifact.items` 指向别的模组的物品），
   要把"某件物品在背包里也画成 geo 模型"就得替别人的物品改物品模型/特殊渲染器——那不是本体该做的事。
   出路留给内容模组自己实现 `GeoItem`（或 `GeoRenderProvider`）。本轮只做**载具实体**。
2. **骨骼挂点**：把乘客摆到 GeckoLib 骨骼上、或从骨骼上挂武器（`GeoLocator` / 图层的用法）。
   座位的几何属于服务端（`seat_offsets`），跨端对齐是另一个话题。
3. 发光层（`AutoGlowingGeoLayer`）、自定义 `RenderType`、染色、molang 变量、关键帧音效 / 粒子。
   `GeoRenderer` 的 `setMolangQueryValues` / `getRenderColor` / `getRenderType` 都是现成的扩展点，
   但先把这一档做稳；尾迹粒子仍由 `trail` 字段发（与服务端权威的口径一致）。
4. **渲染器影响几何**（按模型自动算箱子）：不做，`width`/`height` 仍然由数据给（`48` §6.4 的取舍不变）。
5. **GUI / 轮盘里的载具模型预览**：`screen/multiblock` 那套 PictureInPicture 能复用，但不在本轮。
6. **按品质 / 境界换模型**（多套视觉）：属于"未来的字段"，不预留。

### 9.3 实机（**先问**再起；客户端才有渲染）

1. **没装 GeckoLib**：`runTestClient` 起剑 → 与改动前**逐像素一致**（物品模型、朝向、站姿、座位）。
   这是本轮的回归基线，也是 `mxt:item` 唯一能证明"没变"的方式。
2. **装了 GeckoLib**（§8 的 `localRuntime`）：把测试包里 `azure_sword_mount` 换成 `mxt:geckolib` 版本 →
   模型出现在脚下、朝向跟人、`moving` 时切动画、升降切动画、过渡不闪。
3. **回落（用户点名的行为）**：装 GeckoLib 的客户端上把类型写成 `mxt:geckolib`、但把模型**定义**删掉 →
   应该看到紫黑 missingno + 一行 error（§5.6）；**不装 GeckoLib 的客户端进同一个世界** →
   应该看到**物品模型** + 一条回落 WARN，**世界照常进、飞行照常能飞**。
4. **姿态输入**（§4.6 方案 A 的实机确认，最重要的一条）：悬停不动但转头 → **不应**被判成 moving；
   按 W 前飞 / 按 X 下沉 / 跳跃上升 → 三条运动动画分别生效；`/mxt flight fill` 塞满座位 → `carrying` 那组切过去。
   对不上就改用 §4.6 的方案 B。
5. `/reload` 改 `render` 后不重进世界即生效（模型文件与数据包各一次）。
6. `/mxt flight fill` 填满座位时模型/动画不崩（多辆载具同屏，验 §5.3 的 per-instance 动画与 §5.4 的缓存）。
7. 长会话泄漏：连续起落 100 次，看 `MountAnimatableCache` 的条目数不涨（§5.4）。
8. 日志干净度：`states` 完全不写时，每个 `(动画文件, 名字)` 最多一行 WARN，**不能**出现每帧刷屏
   （§5.5 的静默存在性检查没做对就会这样）。

### 13.2 与本文（设计）的出入——**以代码为准**

1. **`MountRenderer` 的两个阶段都收 context**（`submit(T, context, state, poseStack, collector, camera)`），
   不是只收 state：载具的 pitch / 光照 / `display` 都在 context 里，渲染器不必抄进自己的草稿状态。
   草稿状态因此只剩"可变的东西"（物品那档是 `ItemStackRenderState`，GeckoLib 那档根本不用自己的 state）。
2. **`MountRenderContext` 多一个 `vehicle()`**（返回 `Entity`）：`ItemModelResolver.updateForTopItem` 需要
   载具实体与它的 `Level`，第三方想读乘客 / id / 维度也从这里读。原设计说"不把实体塞进 context"，
   实现时证明**必须塞**（否则物品那一档没法解析模型），实体类型是 common 的 `Entity`，不破坏边界。
3. **每帧解析 + 每帧 `createState()`，没有按定义缓存**（原 §4.1 写的是"equals 相等就复用"）：
   原版 `createRenderState(entity, partialTick)` 本来就是每帧新建，跟着它走最简单，也没有陈旧问题
   （`resolve` 只是一次 map 查询，警告有 `Set` 兜底不会刷屏）。
4. **姿态是"一个枚举 7 个值 + 两条控制器"**（原 §3.6 一度写成两个枚举）：一个枚举、一张 `states` 表、
   一个 codec，`Axis` 只用来决定哪个值归哪条控制器。
5. **GeckoLib 那档的变换放在 `submit` 里**（`translation → pitch → rotation → scale`），
   `adjustRenderPose` 只是**清掉基类的方块中心偏移**——这样两档的 `display` 语义与顺序逐字相同，
   不必把 display 塞进 DataTicket 再在 `adjustRenderPose` 里读。
6. **动画存在性检查绕开 GeckoLib 的 error 分支**（`GeckoLibResources.getBakedAnimations().cache()` +
   `BakedAnimations.getAnimation`），所以缺动画名只留**一条 WARN**，连 GeckoLib 自己的 `Unable to find animation`
   都不会出现；memo 以 **baked 实例**为键，`/reload` 自动失效。
7. **`MountAnimatableCache` 直接继承 `AnimatableInstanceCache`**（原 §5.4 写的继承 `SingletonAnimatableInstanceCache`）：
   基类只有一个抽象方法，自己拿一个 `Long2ObjectLinkedOpenHashMap` 更干净，也不白留一个用不到的 map。
8. **`display` 的缺省按渲染器分**：物品那档 `FlightDisplay.DEFAULT`（＝"现在的渲染方式"），GeckoLib 那档 `IDENTITY`。
9. **新增/改动面向玩家的文案：零条**（回落只写日志），所以两份 lang 与 `check` 都没动。
