## 1. 范围与职责

新增 `com.iafenvoy.mxt.util.dispatcher`，调度逻辑只使用 JDK，参数注解沿用项目现有约定：

| 类 | 职责 |
| --- | --- |
| `TickDispatcher<K>` | 按唯一任务键管理一次性/周期任务、到期执行、取消、重排和执行报告 |
| `TickInterval` | 固定或闭区间随机周期 |
| `TickExecutionLimit` | 固定/自适应的每 tick 数量上限及其开关 |

调度器不持有世界、实体、区块或全局实例，不订阅 tick 事件，不自动记录日志，也不自行创建线程。业务在自己的 tick 入口推进实例，在卸载或停服时取消对应任务、释放实例。

这不是任务线程池，也不接管 Aura 的库存和消费规则。随机间隔只决定何时再次调用回调，实际重建内容仍由原业务实现。

## 2. 调度与随机周期

实例由 `initialTick`、随机种子和可选执行策略构造；默认不限制数量。每个实例绑定创建线程，所有读写都必须在该线程完成。未来按维度实例化时，应在对应维度的实际持有线程创建，不能先在其他线程构造后直接转交。

| 操作 | 规则 |
| --- | --- |
| `scheduleOnce(key, delayTicks, action)` | 一次性任务，允许 0 延迟 |
| `schedule(key, interval, action)` | 周期任务；第一次与以后每次都按 interval 安排 |
| `reschedule(key, delayTicks)` | 从当前调度时间重新计时，保留原周期或一次性属性 |
| `reschedule(key, interval)` | 更换周期并重新抽样；也能把一次性任务改为周期任务 |
| `cancel(key)` / `clear()` | 主动移除索引和排队状态 |
| `advanceTo(now)` | 只校准调度时间，不执行回调；用于 tick 入口之外的登记和重排 |
| `contains` / `size` / `nextExecution` | 查询登记状态、任务数量和下次到期时间 |

注册同键任务返回 `false`，保留原回调和期限，也不消耗随机数；重排、取消未知任务同样返回 `false`。键不能为 null，登记期间的 `equals/hashCode` 必须保持稳定。

`TickInterval.fixed(n)` 使用固定正间隔；`TickInterval.random(min, max)` 在两端均包含的区间重新抽样，要求 `0 < min <= max`。随机周期在首次登记、周期执行结束和显式更换 interval 时抽样，不在每 tick 重新洗牌整张表。

例如随机范围为 600～1199 tick，某次实际执行在 1000，新抽到 800，则下一次为 1800。即使它原本在 900 到期，也不会先追赶 900 之后错过的周期。

实例持有独立的 `SplittableRandom`，不会消耗 `level.getRandom()` 的玩法序列。**相同 seed 和相同操作顺序可复现期限**；它不保证取消、增删或重排其他任务后，单个任务仍拥有原来的随机序列。

所有相对延迟以 `currentTick()` 为基准，即构造时刻或最近一次 `tick(now)` / `advanceTo(now)` 的时刻。业务应统一时钟和调用阶段；tick 入口之外登记时先 `advanceTo`，避免新加载任务以旧 tick 为起点。这个操作不会执行其他已到期任务，也不会重置连续相同时间的已用预算；回调中不能用它改变自己调度器的时钟。

## 3. 到期队列与批次边界

核心使用两份互补索引：

- `HashMap<K, Task>` 查找任务身份。
- `TreeSet<Task>` 按 `(dueTick, sequence)` 排序；同刻任务按登记/重新安排的顺序执行。

登记、重排、取消和单次出队为 O(log M)，任务查找平均 O(1)，内存 O(M)。取消会直接删除队列条目，不累积失效节点；稳定 tick 不扫描尚未到期的全部任务。

每次 `tick(now)` 先按本拍预算取出到期批次，再逐项执行：

1. 预算在本拍开始时计算，回调改变策略或任务数量不扩充当前批次。
2. 调用回调前核对任务对象身份，已取消或已重排的旧批次成员跳过。
3. 周期任务执行后从实际执行时刻安排下轮；显式自取消或自重排优先。
4. 回调新建或重排的任务，即使 0 延迟，也要等下一个不同的调度 tick。

连续传入相同 `now` 只允许一次派发，包括首次调用没有到期任务的情况。再次调用返回执行数为 0 的当前状态报告，不能通过重复调用、清空任务或切换上限绕过本拍边界。

预算限制的是**选入批次的条目数**。回调取消了本批次后续任务时，实际执行数可能低于上限，不再从队列补满。这保证回调不能不断补充同拍工作；关闭数量限制也不会出现回调制造零延迟任务的无限链。

执行过程中，按键查询仍能看到尚未完成的批次成员；无参数 `nextExecution()` 只查看队列，不包含已取出但尚未调用的批次成员。业务诊断优先在 `tick` 返回后读取报告。

## 4. 每 tick 执行上限

| 策略 | 行为 |
| --- | --- |
| `TickExecutionLimit.unlimited()` | 处理本拍开始时全部到期任务，不设数量预算 |
| `TickExecutionLimit.fixed(B)` | 最多选取 B 个到期任务，B 必须为正 |
| `TickExecutionLimit.adaptive(minimum, spreadTicks)` | `max(minimum, ceil(M / spreadTicks))`，M 为本拍开始时的全部登记任务数 |

自适应策略按完整登记规模计算，包含尚未到期的任务；不是看本拍到期数量再临时扩大预算。任务增减会在下一拍重新计算，不需要事先知道世界最终有多少任务。

97 稿建议的策略可以直接表达为 `adaptive(8, 600)`：24000 个登记任务对应 40 个/拍，24001 个对应 41 个/拍。整除向上取整不使用可能溢出的整数加法。

`setLimitEnabled(false)` 关闭数量限制，`true` 恢复原参数；`setExecutionLimit(...)` 更换策略。默认 unlimited 没有另藏一组业务参数，需要先配置 fixed/adaptive 才有具体上限可恢复。上限不能设为 0；暂停推进由业务决定是否调用 `tick`。

该预算限制工作项数量，**不承诺毫秒上限或最大逾期时长**。昂贵回调不可抢占，任意规模和随机集中到期仍可能积压；关闭上限则可能一次处理大量任务。

## 5. 失败、重入和时钟边界

### 5.1 回调与异常

回调允许登记、取消、清空、修改策略、重排自己或其他任务。同键取消后重新登记会得到新的任务身份，旧批次不能误执行新回调，也不能将旧周期任务复活。

回调抛出 `RuntimeException` 时，该次执行计入预算，异常和任务键进入返回报告，继续执行其余任务；周期任务仍安排下一轮。核心不会吞掉后自行打印一条无法关联业务的日志，调用者必须检查报告并决定诊断方式。普通业务失败应由回调自己的结果处理，不用异常表达。

`Error` 继续向外传播；当前任务按完成规则移除或安排下轮，已取出但尚未执行的有效任务恢复到队列。同拍再次调用仍不会重新获得预算。

重入守卫使用 `ThreadLocal<Set<...>>` 和 `finally` 清理；同一实例递归 `tick` 被拒绝，独立实例可以嵌套推进。错误参数、跨线程访问与重入是编程错误，直接拒绝，不作为日常业务失败。

### 5.2 时钟

- 时间和延迟必须非负；一次性 0 延迟允许，周期必须为正。
- 时间向前跳跃只执行一轮已到期任务，不补跑错过的周期。
- 时间倒退时按原调度时刻的剩余等待时长重建期限，原本已到期的任务仍到期；这是 O(M log M) 的异常路径。完成的任务不会复活，也不会撤销已产生的业务效果。
- deadline 加法溢出时饱和到 `Long.MAX_VALUE`，不变成负数提前执行；周期任务在该最终时刻运行后退出，因为已经没有可表示的未来 tick。

“一拍一次”指连续相同调度时间的调用边界；显式时间倒退会开启一个新的调度阶段，不维护无限历史时间去重表。业务应持续传入同一时间域，不能交替使用游戏时间和其他计数器。

## 6. 执行报告和生命周期

`tick` 返回不可变 `TickReport<K>`：

| 字段/方法 | 含义 |
| --- | --- |
| `tick` | 当前调度时间 |
| `executed` | 实际进入回调的次数，包含抛异常的回调 |
| `scheduled` | 本拍结束后全部登记任务数，包含未到期任务 |
| `nextDueTick` | 队列最早期限，无任务则为空 |
| `failures` | 本拍回调的 RuntimeException 列表及其任务键 |
| `hasDueTasks()` | 本拍结束后是否还有到期任务 |
| `oldestOverdueTicks()` | 最老期限距当前时刻的逾期 tick 数，无逾期则为 0 |

报告只保留本次状态，不会随之后的调度变化而更新。核心没有为求精确到期积压数量而扫描全队列；若业务需要更细诊断，接入时另行评估代价。报告也不计量实际耗时，外层可以使用现有 profiling。

调度器强引用任务键与回调。区块卸载必须取消其任务，维度卸载或服务端停止必须清空并释放对应实例；取消不能中断已经进入执行的回调。装载代次、区块索引与有效性检查仍由业务负责，不能只凭相同坐标认定是同一轮装载。

调度状态不持久化。重新构造时由业务按实际时间、种子和已加载对象重新登记，不提供全局静态队列或后台自动清理。

## 7. Aura 方块缓存接入

`AuraChunkTicker` 每个维度持有一个刷新状态，内部复用 `TickDispatcher`，默认数量策略为 `adaptive(8, 600)`，周期为 `random(600, 1199)`。

具体行为：

- 装载时保留整列同步重建，再为全部有效子区块登记随机周期，包含当前为空的段；缓存里残留的越界段也纳入登记范围。
- 登记前只校准时钟，不在装载回调执行其他区块的到期工作。随机种子由世界种子与维度 ID 派生，不消耗玩法随机数。
- 每次 level Post 在 pending 初始化后推进刷新队列；移除旧的 deadline map 全扫。刷新不再受库存维护周期的取模门限制。
- 回调仍使用原有的子区块重建入口，不复制调色板统计、单方块增量或库存差量逻辑。异常报告由业务输出含维度、区块与 section Y 的 WARN，其余任务继续。
- 每个区块保留自己的任务键列表；区块卸载逐项主动取消。任务身份包含真实区块对象，同坐标的新对象不会接收旧对象的任务，迟到的旧对象卸载也不能移除新对象。
- 维度卸载清空调度器并移除持有状态，停服有全表释放兜底。
- 管理命令即时重建指定范围后，取消旧任务并以当前时间重新登记，避免刚刷新完就执行旧的过期期限；范围外的队列不改变。

到期顺序由全维度队列统一决定，不再每个区块单独收集到期段。原有配置键与默认值保留，只控制库存再生目标周期，访问人数改为每 tick 增量维护；两份 tooltip 和相关中英文说明同步该口径。没有新增上限配置项；工具本身仍支持关闭上限，当前业务默认启用自适应预算。

待实施项仍包括：唯一初始化入口、全部库存写入的后处理与缓存纪元、所有写入路径的保存标脏，以及实机性能验证。再生自身的锚点、部分周期、标脏和位置结果失效已实现，玩家覆盖差量复用现有附件计数。

## 9. 区块再生与玩家覆盖接入

`AuraMaintenanceState` 每维度持有独立的 `TickDispatcher<LevelChunk>`，与子区块随机巡检队列各自计算预算，互不占用任务额度：

- 一个加载区块对应一个固定周期任务，周期取现有服务端配置，默认 10 tick。初次登记选择区块数最少的相位，同负载用轮转游标；选相位只在加载和周期重排发生，稳定 tick 不扫描全维度区块。
- 再生预算为 `max(1, ceil(登记区块数 / 周期))`，首次期限目标为未来 1 至 I tick。积压时可延后，周期从实际执行时刻安排；数量预算不保证毫秒上限。
- 附件的运行期 `regenerationTick` 在加载及初始化时建立，到账只计算实际经过时间，重复时刻不重复增加；卸载主动取消，重新加载不领取离线时间。
- 周期变更先按原锚点结算到当前时刻，再重排相位与预算。这是一次显式 O(N) 区块遍历及池访问，运行期稳定 tick 不执行它。倒退时间只重置锚点并重排剩余等待，不重放历史库存。
- 再生跳过零速率及无效写入；正向溢出饱和到有限上限或 `Double.MAX_VALUE`，负向溢出归零。真实再生标记区块未保存，并清除该维度的位置结果缓存。
- `AuraVisitorIndex` 每 tick 只比较玩家所在段；静止不产生覆盖写入，跨一段只更新两个边界面，离开则减去旧覆盖。高度裁剪后将差量写入已经加载且属于当前维护状态的区块，禁止为更新计数加载区块。
- 覆盖计数继续保存在原有附件，索引只保存玩家 UUID 和段坐标。新加载区块按索引补齐本列，既不保留双份权威计数，也不改 Codec 字段。计数变化失效位置结果；维度卸载和停服清理队列、玩家位置与计数。

`BlockAuraRefreshVerifyProbes` 新增 6 组 `verify/aura_maintenance/*`：均摊、周期切换、时钟与生命周期、数值边界、覆盖差量、随机覆盖参考模型。获用户授权后实跑 `mxt_test:verify/aura_*/*`，原 4 组缓存探针与新 6 组共 10 组全部通过，游戏测试运行阶段耗时 1.970 秒。没有启动客户端，没有场景级前后性能对比。
