## 1. 三件事与结论

| # | 缺口 | 结论（本次选定的形状） |
|---|---|---|
| **A3** | `SpiritRoot.element` 是必填单值 → 一个灵根只能绑一个元素 | `element` **删除**，改为 `elements`：`ElementWeight` 的**列表**（裸 id 或带 `weight` 的对象），**权重是占比、读取时归一化**。多元素的语义在下面 §2.2 逐条定死 |
| **A1** | 65 项 `entity_condition` 里没有一项能比较子境界 | **不新增类型**：给现有 `mxt:realm` 加 `min_minor_stage`（可选整数），与 `comparison` 组合使用 |
| **新功能** | 境界的 `minor_stages` 只是名字与公式变量，没有"到了第几层就解锁"的字段 | `realm_stage.minor_stage_abilities`：`[{"stage": N, "ability": [...]}]`，**累计**（层数 ≥ N 生效），**解锁过就永久保留** |

用户拍板的五项（两轮问答）：`elements` 纯列表（A）· `stage` 字段 + 累计（A）· **永久保留**（B）· `mxt:realm` 加字段而不是新类型（B）· **权重按占比、读取时归一化，只进亲和与对立惩罚**（A，第二轮追加）。

## 2. A3 · 灵根多元素

### 2.1 数据形状

```json
{
  "elements": [
    { "element": "mxt_test:fire", "weight": 0.7 },
    { "element": "mxt_test:water", "weight": 0.3 }
  ],
  "cultivation_multiplier": 1.25,
  "element_ability_modifier": 1.1,
  "conflicting_elements": ["mxt_test:inert"]
}
```

- 类型：`ElementWeight` 的列表；每一项可以是**裸条目 id**（= 该元素占满整条灵根，权重 `1`）或 `{"element": …, "weight": …}`，写出时权重恰好为 `1` 的会写回裸 id（与 `IconReference` 那类"简写优先"的 codec 同一口径）。
- **必填且非空**（旧 `element` 也是必填，语义上没有"没有元素的灵根"）。
- 校验（加载期）：空列表拒绝；同一元素写两次拒绝；`weight` 必须**有限且为正**；权重总和必须是正的有限数（否则加权平均没有分母）。只认 `mxt:` 元素注册表的 holder（**不收标签**——"某个灵根持有标签里的哪些元素"没有确定答案）。
- **权重是占比不是倍率**：读取时一律除以权重总和，所以 `[1, 1]` 与 `[0.5, 0.5]` 等价，单元素灵根写多少权重都一样（写 `0.5` 不会被当成打折）。

### 2.2 多元素在每一处的读法（一次定死，别处不再另算）

| 读法 | 位置 | 语义 |
|---|---|---|
| **持有哪些元素** | `Elements.of(...)` | 各灵根的 `elements` **取并集**、**与权重无关**（原来是一个元素，现在是一组）。`mxt:has_element`、战利品条件、物品元素比较都走这一处，因此自动支持多元素 |
| **修炼亲和** | `CultivationAffinity.multiplier` | 浓度取该灵根**各元素对应灵气池浓度的加权平均**（`1 + Σ(权重 × 浓度) / Σ权重`）；"这里有没有我这门灵气"= 任一元素有池子且 `amount > 0`（决定 `element_fit_bonus` 是否加），这一步也**不看权重** |
| **元素对立惩罚** | 同上 | 各元素 `opposition` 的**加权平均**，再乘 `element_conflict_penalty`：主修火的混合灵根在水地里比主修水的挨罚更狠，但都不如纯火灵根（第二稿由"取最大"改成加权平均——权重按用户要求进这一处） |
| **能力加成** | `CultivationAffinity.abilityMultiplier` | 只要该灵根**任一元素**命中 `element_affinity`，这条灵根就贡献一次 `element_ability_modifier`——**不是每个命中元素各贡献一次，也与权重无关** |
| **互斥** | `SpiritRoot.conflictsWith` | 集合对集合、**与权重无关**：A 的任一元素出现在 B 的 `conflicting_elements`，或反过来，即冲突。仍保留"停用元素不参与"的口径 |
| **显示** | `SpiritRootCommand list`、信息面板 | 逐个元素各自上色、多个用 `/` 连接；权重不是 `1` 时后缀该数值（`TooltipText.number`，最多两位小数）；停用元素不显示 |
| **脚本** | `MxtKubeJsApi.activeSpiritRoots` | "这个灵根算不算数"= **任一**元素是活的（不看权重） |
| **武器冲突** | `DamageCalculationService.conflicts` | 不读 `elements`，只读 `conflicting_elements`，**不受影响** |
| **元素关系（克 / 适）** | 元素定义各消费方 | 按**元素**逐条成立、**不读权重**：混合灵根的两个元素各自与目标结算（写进文档，免得有人以为权重会削弱克制倍率） |

### 2.3 破坏性

`element` 字段删除 → 老包的灵根定义会**加载失败**（`elements` 必填缺失），不是静默失效。未发布阶段，按仓库口径不做兼容迁移；同步改了 `src/test-mod` 的 9 个灵根夹具，并新增 `dual_root`（0.7 / 0.3）与 `dual_even_root`（1 / 1）两个多元素夹具（后者专门用来证明权重是占比：同一个地方、同一份 `cultivation_multiplier`，0.7 占比读出 1.87、1/1 平均占比读出 1.65）。

## 3. A1 · `mxt:realm` 的 `min_minor_stage`

```json
{ "type": "mxt:realm", "realm": "mxt_test:qi_refining", "comparison": "at_least", "min_minor_stage": 4 }
```

- 字段：`min_minor_stage`（可选整数，`0` 起，与公式变量 `minor_stage` **同一个下标**）。
- 判定：先按原有 `comparison`（`exact` / `at_least` / `at_most`）判定境界，通过后再要求**身体在该境界上达到过的最高层数 ≥ `min_minor_stage`**。
- "达到过"读的是持久化的**层数记录**（§4.2），所以在该境界里升级会即时生效，突破离开之后**仍然成立**——这正是本体 `LayerNum >= 500` 那类门槛需要的单调语义；想表达"此刻正在这一层的窗口里"就配 `comparison: exact`。
- 没到过那个境界（含凡人）→ 记录不存在 → 假。

## 4. 境界按子境界解锁 ability

### 4.1 数据形状

```json
{
  "minor_stages": 9,
  "minor_stage_abilities": [
    { "stage": 2, "ability": ["mxt_test:qi_sense"] },
    { "stage": 5, "ability": ["mxt_test:spirit_flying"] }
  ]
}
```

- 仿功法的 `configuration`：条目 = `stage` + `ability`（`#标签` 与 id 都可以，写成数组是顺序表）；**累计**（层数 ≥ `stage` 即生效），与功法"最低要求"的口径一致。
- `stage` 是 0 起下标：`stage: 0` 就是进入这一境的第一层。之所以用下标而不是"第 N 层"，是为了跟 `minor_stage` 公式变量、`minor_stages` 的名字下标保持同一套编号——仓库不接受第二套编号。
- 加载期校验：`stage` 非负；条目存在时 `minor_stages` 不能为空；`stage` 必须小于 `minor_stages` 的元素个数；同一个 `stage` 写两次拒绝。`ability` 允许省略（与功法一致，那一层不授予任何东西）。
- 记录组件：`RecordCodecBuilder` 的那一组已经排到 16 个组件，所以 `minor_stage_abilities` 与相邻的 `ability_requirements` 用 `MiscCodecs.pair` 并成一组（JSON 键不变）。

### 4.2 层数记录（"解锁过就永久保留"的载体）

- `SpiritIdentityAttachment` 新增 `minor_stage_records`：`Map<Holder<RealmStage>, Integer>`，键的存在即"**到过这个境界**"，值是**到过的最高层数**（0 起）。放在这一个附件里而不是 `CultivationAttachment`，是因为它与 `technique_stages`（功法水平）是同一类"掌握程度"，而且授予重建只拿得到这一份附件（见 4.3）。
- 写入：`MinorStageService.refresh(...)` 在两条路径后被调用——①每 tick 修炼加的进度落地之后（`CultivationService.addProgressForChain(entity, …)`）；②突破成功、新境界已写入之后（`CultivationService.attempt` 的 `advanced` 分支）。它把当前层数与记录取最大值写回；**只增不减**，降境 / 回退 / 突破都不会清掉。
- 读：`minorStageRecord(stage)` 不存在时返回 `-1`（比任何合法下标都小），所以"没到过"天然不满足任何 `min_minor_stage`。

### 4.3 授予

- `CultivationGrantService.recalculate` 在原有三类来源（灵根 / 体质 / 功法）之后，按记录逐境界授予：来源 `mxt:grant/realm_stage/<ns>/<path>`，即**同一个境界的授予同属一个来源**，与功法"晋级只改等级、授予整份重建"的写法一致。
- 因为记录只增不减，重建出来的集合也是单调的：**离开境界不掉能力**（用户选的 B）；只有"内容包删掉那条 `minor_stage_abilities`"或"停用该技能"才会掉。
- 触发时机：只在**记录真的涨了**的时候才 `recalculate`，所以每 tick 修炼不会反复重建授予与触发器订阅。

## 5. 不做 / 推迟

- **不给 `minor_stage_abilities` 加每条自己的 `condition`**（功法 `StageConfiguration` 有）。层数是进度算出来的，加条件就要每 tick 复查条件并可能撤回能力，与"永久保留"直接冲突；要条件请写在境界的 `cultivate_condition` 或那一层的其它门槛上。
- **权重只进亲和与对立惩罚**（§2.2）：持有元素、能力加成、互斥、元素关系倍率一律**不看权重**。"多元素按主次分别加成"（例如"火占比高则火法更强"）不做——那要给每条灵根算一个元素权重系数并接进伤害管线，属于另一件事。
- **不做每层解锁的界面提示**：解锁走的是授予，提示交给内容包（`minor_stage_abilities` 里那条能力的 `entity_action` 或 `mxt:play_sound`）。
- **不给 KubeJS 加"查已解锁层数"的绑定**；需要的话用 `mxt:realm` 条件或读附件。
