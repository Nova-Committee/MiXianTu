# 技能与法器能力的统一可行性（`Ability` vs `ArtifactAbility`）

> **基准**：2026-09-23 的工作树。逐字核过 `data/ability/{Ability,AbilityType}.java`、`data/ability/type/*`（8 个）、`data/artifact/ability/*`（7 个）、`data/artifact/Artifact.java`、`registry/MxtAbilityTypes.java`、`registry/MxtArtifactAbilityTypes.java`、`runtime/ability/{AbilityService,AbilityEventBridge,AbilitySources,AbilityModifierService}.java`、`runtime/artifact/{ArtifactService,FlightService,ArtifactUpkeepService,ArtifactToggleService,ArtifactCapability}.java`、`runtime/ServerCache.java`、`runtime/wheel/{WheelSources,WheelEntryKind}.java`、`screen/wheel/content/AbilityWheelEntry.java`、`docs/数据包格式.md` 的 `ability` / `artifact` 两节、`docs/模块实现审计.md:191,193`。
> **状态**：可行性分析与方案对比，**未拍板、未写任何代码**（也没有编译——纯文档）。按 `README.md` 的状态口径属于「分析 / 研究」。

## 0. 结论

**能统一，但"统一"分四层，收益与代价差一个量级；只有前两层值得现在考虑。**

| 层 | 统的是什么 | 判定 |
| --- | --- | --- |
| ① 机制层 | "可发动条目"的身份与校验、来源、付款、tooltip | **值得做**：`ToggableArtifactAbility` 与 `ActiveAbilityType` 是同一个概念的两份实现，轮盘现在为此各维护一套 kind / 身份 / 校验（§3 方案 A） |
| ② 形状层 | 法器能力从内联条目变成**命名注册表条目**（可被多件法器引用、可打标签） | **可做**：不动运行模型，解决"每把剑重复写一份参数"的真实痛点（§3 方案 B） |
| ③ 实体层 | 把 `mxt:flight` / `mxt:storage` / `mxt:upkeep` 变成 `AbilityType`，法器退回"授予来源" | **不建议现在做**：`flight` / `storage` 的状态、身份、驱动三项都与 `Ability` 的模型对不上（§2），换来的只是"概念数 2→1" |
| ④ 反向 | 把 `Ability` 并进法器能力 | **不可行**：技能必须能脱离物品存在（技能书 / 命令 / 修炼 / 战利品 / 阵法 / KubeJS 都在授予技能） |

一句话概括：**`Ability` 是"你会什么"（注册表单例 + 持有者身上的授予与状态），`ArtifactAbility` 是"这件东西能让你做什么"（物品堆 + 定义上的性质与状态）。两者只在一处真的相交——`mxt:passive` / `mxt:active`——而那一处本来就是"法器把技能授予出去"，不是"两种能力"。**

## 1. 现状对照

| 维度 | `Ability` | `ArtifactAbility` |
| --- | --- | --- |
| 定义位置 | `data/<ns>/mxt/ability/<path>.json`，34 张数据包注册表之一 | `artifact` 定义里的 `abilities[]`，条目**匿名** |
| Java 入口 | `data/ability/Ability.java` | `data/artifact/ability/ArtifactAbility.java` |

| 类型表 | `mxt:ability_type`：`active` / `triggered` / `modifier` / `aura` / `channelled` / `composite` / `word` / `empty` | `mxt:artifact_ability_type`：`empty` / `passive` / `active` / `flight` / `storage` / `upkeep` |

| 驱动者 | 8 种：按键（`active`）、事件触发（`triggered` → `AbilityEventBridge` 订阅）、范围脉冲（`aura`）、常驻属性（`modifier`）、引导（`channelled`）、组合（`composite`）、口令（`word`）、空 | 4 种：授予技能（`passive` / `active`）、载人飞行（每 tick 状态机）、储物（界面入口）、周期扣费（`ArtifactUpkeepService`，按世界时间） |

桥梁只有一条：`GrantArtifactAbility`（`mxt:passive` / `mxt:active`）→ `Artifact.grantedAbilities()` → `ArtifactService.abilities/abilityIds`（同时合并手写的 `mxt:item_abilities` 组件）→ `AbilityEventBridge.onEquipmentChange` / `syncCuriosAbilities` 按 `AbilitySources` 授予或撤销；`ServerCache.checkGrantedAbilityKinds` 交叉校验 `intent` 与被引用技能自身的 `ActiveAbilityType` 是否一致。

## 2. 对不上的三点（实体层合并的硬阻碍）

### 2.1 状态归属：持有者 vs 物品

`Ability` 的运行状态全在**持有者**身上，键是 `Holder<Ability>`：技能撤销再授予、换一件物品，冷却与充能都还在——技能是"人"的属性。`flight` / `storage` / `upkeep` 的状态全在**物品**上：飞的是哪件法器（`FlightAttachment.archetype`）、箱子里装了什么（物品组件）、这件东西归谁（`mxt:artifact_state`）。

合并必须二选一：

- 把法器状态搬进持有者附件 → 同一个玩家同时带两把剑就分不开了，除非把物品堆身份写进键，"技能状态"实际变成"物品实例状态"；
- 或者给 `Ability` 引入 **per-item 实例**（`scope: entity | item` + 实例键）→ 给现在很干净的"注册表单例 + 持有者账本"加一层实例化，`AbilityStorage` 的键要从 `Holder<Ability>` 变成 `(Holder<Ability>, 实例)`。

### 2.2 身份与参数：注册表 id vs 物品堆

`Ability` 是**共享**的：同一份技能定义可以被法器、技能书、命令、战利品分别授予，参数写在定义里、所有持有者一样。`flight.speed` / `storage.slots` 是 **per-artifact** 的：两把剑要不同速度，现在各自在自己的 `artifact` 定义里写一份。

合并必须二选一：

- 每把剑写一个独立的技能定义（参数随定义走）→ 包作者从"一个文件写完"变成"两个文件 + 引用"，`mxt:flight` 这类能力会大量重复；
- 或者允许**内联定义 / 参数覆盖**（`Artifact.abilities[]` 里直接写技能对象）→ 形状上等于"注册表条目可以内联"。`util/codec/RegistryCodecs` 目前只有 `holderOrTag` / `holderOrTagList` / `keyOrTagList`，**没有** inline-or-holder 助手，要新增一个。

### 2.3 驱动者：一次施放 vs 别的东西

`AbilityService` 只有一条主线：**校验 → 计划付款 → 提交 → 跑动作**，一次施放有开始有结束（读条与引导只是把它拉长）。`flight` 是持续状态机（每 tick 位置、朝向、消耗、下马），`storage` 是一个界面入口——它们都不是"施放"。塞进 `AbilityType` 只会得到两个"看着像技能、其实不是"的类型，`AbilityService` 里要多两条旁路——**那不是统一，是把两个系统搬进同一个 switch**。

反过来，`mxt:upkeep`（携带期间按周期付 `costs`，付不出跑 `on_fail`）与 `ChannelledAbilityType`（引导期间按 `tick_interval` 付 `upkeep_costs`）**是真的挨着**：差别只在"谁在维持"（持有者主动引导 vs 物品被动索取），以及 `on_fail` 走的是 `ItemAction` 通道。

## 3. 四个方案

### 方案 A（建议先做）：统一"可发动条目"这一层

现状里最明显的重复：`ToggableArtifactAbility`（`key()` / `displayName()` / `state()` / `activate()`）与 `ActiveAbilityType`（"轮盘能不能触发它"的判据）**是同一个概念的两份实现**。轮盘为此维护两套东西：

- `WheelEntryKind.{ABILITY,ARTIFACT}` 两个 kind，两套身份（注册表 id vs `法器id/key`）；
- 两处存在性校验：`WheelEntryKind.exists` 的 `ABILITY` 与 `ARTIFACT` 两个 case；
- 两处授予校验：`WheelSources.offers` 的 switch（`abilities(...)` vs `ArtifactToggleService.find(...)`）；
- 配置界面左右两个池，以及 `WheelSources.abilities` / `toggles` 两条来源读取路径。

可以做的：把"可用性 + 触发"的判定收成一份（`WheelMenuEntry` 已经是渲染与交互侧的共用契约，缺的是**身份与可用性**的共用部分）——一个 `EntryRef(kind, id)`，加 `usable(player)` / `trigger(player)`；两个 kind 的 `exists` 与 `offers` 收进一张表。配置界面的左右分池**不必合并**（玩家看得懂"技能 / 法器"两栏），合并的只是判定。

代价：`WheelSlot(kind, id)` 是**落盘附件**（`wheel_layout`）也是网络包字段，kind 收窄是破坏性变更（`kind` 收成 3 值需要迁移或作废旧布局）；配置界面分池与文案要跟着改。收益：新增一种"可发动的东西"只实现一个接口，不再动两处 switch。

### 方案 B（建议，独立于 A）：把法器能力做成命名注册表条目

新增数据包注册表 `mxt:artifact_ability`，条目形状就是现在的 `ArtifactAbility`（`type` 仍走固有 `mxt:artifact_ability_type` 分派），并让 `Artifact.abilities[]` 接受 **id** 或 **内联对象**（需要新增 `RegistryCodecs` 的 inline-or-holder 助手；`Artifact` 的字段类型相应从 `List<ArtifactAbility>` 变成 `List<Holder<ArtifactAbility>>` 或 `Either` 形态）。

- **收益**：两把剑共用一份 `mxt:flight` 参数；`#tag` 可以把一族法器共有的能力打包；`ServerCache.checkGrantedAbilityKinds` 这类跨定义校验可以升级成注册表级校验；tooltip 与文档有稳定引用对象（`DefinitionText` 的 `name` / `description` 可以直接给法器能力用，现在它们连显示名都只能写代码常量或语言键）。
- **代价**：数据包注册表 34 → 35 张（`docs/数据包格式.md`、`docs/模块实现审计.md`、`docs/guide/**`、文档站中英各一份全部要同步）；`Artifact` 的取值路径（`abilities()` / `flight()` / `storage()` / `upkeep()` / `toggables()` / `grantedAbilities()`）都要改成先解析 Holder；`ServerCache` 的校验时机从"随法器定义就地检查"变成"注册表加载后统一检查"。
- **不动的**：运行模型。`FlightService`、`ArtifactUpkeepService`、`ArtifactStorageService`、轮盘、状态归属、存档全部不变。这是它比方案 C 划算的原因。

### 方案 C（不建议现在做）：`flight` / `storage` / `upkeep` 变成 `AbilityType`

做法：新增三个 `AbilityType`，法器只用 `mxt:passive` / `mxt:active` 把它们授予出去，`artifact_ability_type` 整张表退役，`ServerCache` 的 intent 校验换成"这三个类型是不是主动"。

必须一起解决：

1. **物品作用域**（§2.1）：`AbilityStorage` 的键与 `FlightAttachment.archetype` 的语义都要改（现在是法器定义 id）；
2. **物品通道**（§2.3）：`upkeep.on_fail` 是 `ItemAction`，`Ability` 只有 `EntityAction` / `BiEntityAction`；`Ability` 的 16 个 group 槽已经用 `MiscCodecs.pair` 撑满，再加通道要么再并一组、要么给 type 引入子对象；
3. **授予模型的副作用**：飞行从"拿着剑就能飞"变成"被授予期间能飞"，同时背上冷却 / 读条 / 充能 / 元素亲和 / 目标选择器这一整套对飞行无意义的字段（它们在 `Ability` 上，不按 type 可选）；
4. **轮盘身份**：等于方案 A 的全部内容；
5. **存档迁移**：`wheel_layout`、`FlightAttachment`、老包的 `artifact.abilities[]` 写法；
6. **语义倒退**：`storage.slots` 是"这件东西的容量"，共享技能定义后"每件法器不同格数"只能靠独立定义表达。

### 方案 D（不可行）：把 `Ability` 并进法器能力

技能必须能脱离物品存在：功法手册（`mxt:technique` 载体）、`/mxt ability`、`GrantAbilityAction`、`GrantAbilityLootFunction`、`CultivationGrantService`（突破授予）、`FormationActionRunner`（阵法授予）、KubeJS 都在授予技能。法器只是**其中一个来源**（`AbilitySources.equipment` / `CURIOS`）。

## 4. 终局形态：如果一定要"概念数 = 1"

要让 `flight` / `storage` / `upkeep` 变成普通技能类型，`Ability` 要先长出三样东西：

1. **作用域与实例键**：`scope: entity | item`，状态索引从 `Holder<Ability>` 变成 `(Holder<Ability>, 实例)`；
2. **物品通道**：`ItemAction`，或一个"物品槽上下文"（`upkeep.on_fail`、托管组件的读写）；
3. **per-instance 参数覆盖**：内联定义或参数覆盖子对象（否则每把剑一份定义）。

代价：`AbilityService` 的"一次施放"主线要为"持续状态机"开旁路；`Ability` 的字段继续膨胀；`AbilityAttachment` 从"技能账本"变成"技能 + 物品实例账本"。**收益是概念数，代价是内核复杂度**——按 [`05_技能系统与固有注册表.md`](05_技能系统与固有注册表.md) 记的现状，这笔交易不划算。

## 5. 若采纳，建议的推进顺序

1. **方案 B**：法器能力注册表化 + 允许 id 引用与内联对象。独立、不破坏运行模型，先解决复用。
2. **方案 A 的"判定只留一份"**（不动存档的那一半）：把 `WheelEntryKind.exists` 与 `WheelSources.offers` 两个 switch 收成一张表；kind 收窄留到下一次破坏性窗口。
3. **`upkeep` 单独起一稿**：要不要给 `Ability` 加物品作用域与 `ItemAction` 通道；不加就让它留在法器侧。
4. **`flight` / `storage` 保持现状**，除非出现"同一个能力需要由非物品来源提供"的真实需求。
