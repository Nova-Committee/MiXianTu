# 锻造系统设计

## 目标与范围

锻造用于制作武器、装备或法器坯体。玩家在锻造台中反复选择“锻打方式”；每次操作只改变一个有符号整数 `forging_value`。页面不显示数值文本，只显示一条以 `0` 为中点的数值条、目标区间和最近六次锻打方式。

一次锻造成功必须同时满足：

1. 最终 `forging_value` 落在当前蓝图定义的闭区间内。
2. 蓝图要求的末尾 `1` 至 `6` 步，与配置中的顺序完全一致。

成功后的品质仅由实际总步数相对“最优步数”的额外步数决定。它不改变成功判定，也不额外引入随机品质。

本设计只定义运行时、数据包和结算规则；不包含锻造台 UI 美术、动画、具体武器或编辑器。

## 模块与数据

新增 `forging` 模块，依赖 `core`、`artifact` 和材料品质 API。

| 对象 | 保存位置 | 内容 |
| --- | --- | --- |
| `ForgingMethod` | 动态注册表 | 一次锻打的 ID、`value_delta`、条件、可选 `costs` 消耗数组和表现定义。 |
| `ForgingBlueprint` | 动态注册表 | 输入、允许方式、数值条边界、成功区间、末尾规则、最大步数、品质曲线和输出。 |
| `ForgingSessionData` | 锻造台 Block Entity/世界持久化数据 | 蓝图 ID、输入物品、当前值、实际步数、最近六步、预计算最优步数。 |
| `ForgingResultData` | 成品 `ItemStack` Data Component | 蓝图 ID、最终值、实际步数、最优步数、额外步数和品质 ID。 |

同一锻造台同一时刻只能存在一个会话。会话和输入物品只在服务端结算；客户端只接收显示所需的数值条位置、目标区间、最近六步和可用锻打方式。

## 数值条规则

- 会话开始时 `forging_value = 0`，显示在数值条正中。
- 每个 `ForgingMethod` 定义一个非零整数 `value_delta`；正数向右，负数向左。每次成功执行方法后，`forging_value += value_delta`，且总步数加一。
- 蓝图定义 `meter_min`、`meter_max` 和 `target_min`、`target_max`；必须满足 `meter_min < 0 < meter_max`、`meter_min <= target_min <= target_max <= meter_max`。
- 若一次锻打后的值超出数值条边界，或 `costs` 中任一资源不足，该次操作被服务器拒绝，不扣除任何资源、不计入步数、不写入历史。
- 成功区间为闭区间：`target_min <= forging_value <= target_max`。
- 最近六步是固定长度环形历史。页面按时间由旧到新显示，不足六步显示空位；不显示原始数值文本。

数值条上可绘制目标区间色带和当前指针，但不得以文字泄露 `forging_value`。这保留“只用一条”观察进度的玩法。

## 末尾序列规则

蓝图可选 `finish_pattern`，其中 `steps` 始终为六个 `forging_method` ID，`required_suffix_steps` 为 `0` 至 `6`：

- `0`：不要求固定收尾，但仍显示最近六步。
- `1`：最后一步必须等于 `steps[5]`。
- `N`：最后 `N` 步必须逐项等于 `steps[6-N]` 至 `steps[5]`，顺序和 ID 均不能不同。
- `6`：完整六步必须精确匹配。

若 `required_suffix_steps > 0`，实际步数少于该值时必定失败。玩家可以在达标区间后继续锻打，但最终点击结算时仍按“当时最近 N 步”判定，因此多余操作会自然降低品质或破坏收尾序列。

默认页面显示实际最近六步。目标收尾序列是否展示给玩家由蓝图的 `show_finish_pattern` 控制，默认 `true`；该选项只影响显示，绝不影响服务端校验。

## 最优步数

最优步数必须把收尾序列纳入计算。它定义为：从 `0` 开始，在不越过数值条边界的前提下，使用蓝图允许的锻打方式，最终落入成功区间且满足末尾规则所需的最少操作次数。

由于锻打值为有界整数且每次操作成本恒为一，数据包加载时可在每份蓝图上执行广度优先搜索：

1. 状态为 `(forging_value, suffix_state)`；`suffix_state` 记录当前历史与所需末尾模式的匹配进度，最大只需保留六步信息。
2. 初始状态为 `(0, empty)`，每个允许的 `forging_method` 是一条成本为 `1` 的边。
3. 到达“数值位于目标区间且末尾规则满足”的第一个状态时，其距离即 `optimal_steps`。
4. 若不存在可达终点，数据包加载必须报错并禁用该蓝图，不能让玩家投入材料后才发现无法成功。

会话开始时把蓝图的 `optimal_steps` 写入会话快照。热重载后，已开始会话继续使用快照，避免玩家进行到一半因配置变化而改变品质；新会话使用新蓝图计算结果。

## 品质结算

结算时，先检查数值区间和末尾序列。任一条件失败即锻造失败，不生成成功成品。成功时：

```text
extra_steps = actual_steps - optimal_steps
```

`extra_steps` 理论上不小于零；出现负数说明服务端状态或数据包校验存在错误，应拒绝结算并记录错误。蓝图以从小到大排列的阈值定义品质：首个满足 `extra_steps <= max_extra_steps` 的条目即为成品品质，最后一个条目必须覆盖无限额外步数。

品质可控制成品的材料品质、耐久、基础属性修正、词条池或外观引用，但“额外步数到品质”的映射必须是确定性的。

## 数据包草案

锻打方式，路径：`data/example/mxt/forging_method/heavy_hit.json`：

```json
{
  "schema_version": 1,
  "value_delta": 7,
  "costs": [
    { "id": "example:spirit_power", "amount": 2 }
  ],
  "conditions": [{ "type": "mxt:item_tag", "tag": "example:forgeable" }],
  "display": { "icon": "example:heavy_hammer" }
}
```

锻造蓝图，路径：`data/example/mxt/forging_blueprint/iron_sword.json`：

```json
{
  "schema_version": 1,
  "input": { "item": "example:iron_sword_blank" },
  "allowed_methods": ["example:heavy_hit", "example:light_hit", "example:fold"],
  "meter_min": -20,
  "meter_max": 20,
  "target_min": 8,
  "target_max": 12,
  "finish_pattern": {
    "steps": [
      "example:heavy_hit", "example:fold", "example:light_hit",
      "example:light_hit", "example:fold", "example:light_hit"
    ],
    "required_suffix_steps": 3,
    "show_finish_pattern": true
  },
  "max_steps": 32,
  "quality_by_extra_steps": [
    { "max_extra_steps": 0, "quality": "example:perfect" },
    { "max_extra_steps": 3, "quality": "example:fine" },
    { "max_extra_steps": 2147483647, "quality": "example:rough" }
  ],
  "result": "example:forged_iron_sword"
}
```

`max_steps` 是会话保护上限，必须不小于 `optimal_steps`。达到上限后不再接受锻打，只允许结算或取消；它不参与品质公式。

## 运行流程与事件

1. 放入坯体并选择蓝图，服务器验证输入、材料品质和访问权限，创建会话快照。
2. 玩家选择锻打方式，服务器校验其属于 `allowed_methods`、条件成立、未达最大步数、新值未越界，并预检该方式 `costs` 中所有资源。
3. 服务器原子扣除全部 `costs`，再更新值、步数和最近六步，向客户端同步数值条和历史；任一项不能提交时，数值和历史均不变。
4. 玩家结算时，服务器验证区间和末尾序列，成功则按额外步数写入 `ForgingResultData` 并生成结果；失败产物、返还比例和材料损耗由蓝图单独配置。

建议事件：`ForgingSessionEvent.Start/Cancel`、`ForgingStrikeEvent.Pre/Post`、`ForgingCompleteEvent.Pre/Post`。`Pre` 事件可取消或替换完整 `costs` 数组，但不能直接篡改会话值、历史、最优步数和品质结果；替换后必须重新预检。

## 校验与性能约束

- `value_delta` 不得为零；`allowed_methods` 不能为空且所有引用必须存在。
- 末尾模式只能引用允许的锻打方式；`required_suffix_steps` 必须在 `0..6`。
- 目标区间、数值条边界、最大步数和品质阈值在数据包重载时完整校验。
- 最优步数计算仅发生在数据包加载期，并缓存到蓝图快照；正常锻打只做常数时间的加法、边界检查和六项历史更新。
- 所有锻打和结算均由服务端重新校验，客户端发送的只应是“选择哪个锻打方式”或“请求结算”。
