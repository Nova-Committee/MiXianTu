# 36 —— 境界子境界（`minor_stages`）设计

> **状态**：已落地（2026-09-23）。
> **2026-09-23 同日修订**（用户追加要求，机制见 [`37_名字与描述自动填充设计.md`](37_名字与描述自动填充设计.md)）：
`minor_stages` 从"字符串列表 + `mxt.minor_stage.<值>` 翻译查表"改成 **组件数组 或 一个整数**（整数 = 这么多重，名字按条目
> id 自动生成，下标从 0 起）；本文里关于"字符串列表"与 `mxt.minor_stage.*` 查表的描述（§1 第 1 条、§2 字段行、§5
> 验证段）按此修订读，其余口径（按 `breakthrough_exp` 均分、NaN、夹取）不变。
> **基准**：对着 `data/cultivation/RealmStage.java`、`runtime/cultivation/CultivationService.java`、
`registry/MxtFormulaVariables.java`、`screen/information/InformationManager.java`、`util/DefinitionText.java` 与
`docs/数据包格式.md` 的 `realm_stage` 一节写的。**字段级权威仍是代码与 `docs/数据包格式.md`**，本文只记"为什么是这个形状"。

## 1. 需求与当场定下的三个选择

用户原话：「给 realm_stage（境界）加入 minor_stages 数组（子境界，比如 一重~九重 这种），这个只用于两个用途：面板显示 和 formula
添加一个 minor_stage 参数（比如 0~8）。分割方式为均匀切分（比如 9 个子境界、这个大境界一共 900（按照升级要求计算），则每个子境界为
100，0~100 为一重，minor_stage=0）」

同一天问过用户、按回答定的三件事：

1. **元素是字符串列表，面板优先查翻译键** `mxt.minor_stage.<值>`，查不到原样显示——与 `rarity`、功法 `grade` 同一口径（
   `DefinitionText.packText`）。**（已于 2026-09-23 修改：改成组件数组或整数，见文首修订；`DefinitionText.packText`
   与 `mxt.minor_stage.*` 查表都已删除。）**
2. **不适用时公式读 `NaN`**，而不是 `0`——与 `secret_realm_*` 的"无法提供"口径一致，条件可以据此区分"没有子境界"和"
   在第一重"。
3. **面板显示在境界行**：`<数值名>: <境界名> <子境界名>`。

## 2. 现在的行为

- 字段 `realm_stage.minor_stages`：组件数组或整数，默认 `[]`（**2026-09-23 修改**；原为 `Codec.STRING.listOf()`）。
- **切分口径**：当前所站阶段自己的 `breakthrough_exp` 求值后均分。理由是修为进度就是朝它涨的——
  `CultivationService.threshold()` 拿 `transition.current()` 的 `breakthroughExp` 当最小值，突破成功后进度清零（`commit()`
  里的 `setCultivationProgress(aura, 0.0D)`），所以"这个大境界一共多少"就是该阶段的 `breakthrough_exp`。`max_experience`
  不是那个数：它是允许囤积的上限，测试包 `mxt_test:foundation` 就是 100 的要求配 250 的上限。
- **下标**：`floor(进度 × 条目数 ÷ breakthrough_exp)`，从 `0` 起，夹到 `条目数 - 1`。恰好落在边界（9 条、要求 900、进度正好
  100）算第二个子境界。
- **读 `NaN` 的四种情形**：附件里没有当前阶段（凡人）、`minor_stages` 为空、`breakthrough_exp` 求值非有限或 `≤ 0`、进度非有限或为负。
- **唯一算法入口**是 `CultivationService.minorStage(RealmStage, double, FormulaContext)`；
  `minorStage(Holder<Aura>, CultivationAttachment, FormulaContext)` 只负责挑出"当前阶段 + 进度"。信息面板与公式变量都走它，不各算一套。
- **公式变量 `minor_stage`** 挂在 `MxtFormulaVariables.RealmVariable` 上，与 `realm` / `realm_rank` / `level` /
  `absorbed_aura` / `cultivation_progress` 同族，只在数值（资源）上下文里存在。
- **重入守卫**：求 `breakthrough_exp` 时置 `ThreadLocal`，期间再读 `minor_stage` 直接给 `NaN`——否则把 `minor_stage` 写进
  `breakthrough_exp` 的公式会无限递归。

## 3. 两个刻意的取舍

### 3.1 凡人读 `realm` 是 `0`、读 `minor_stage` 是 `NaN`

`ResourceService.realmRank` 对"还没有阶段的凡人"返回**首境界的序号**（也就是 `0`），所以 `absorbed_aura` /
`cultivation_progress` 对凡人也照常给数。但凡人的进度是朝 `aura.start_exp` 涨的，那份阈值不属于任何 `realm_stage`，没有"
子境界"可谈。让 `minor_stage` 读 `NaN` 是诚实的：公式能区分"还没进任何一个大境界"和"在第一重的开头"
。代价是同一上下文里两个变量的"不适用"口径不同，这一点两边的文档都写明了。

### 3.2 超过 `breakthrough_exp` 后停在最后一重

进度可以超过升级要求（上限是 `max_experience`
），此时夹取到最后一重，而不是继续往外推——推出去没有名字可用。被否掉的另一种口径是"按 `max_experience` 分段"
：那样每重的宽度与"要多少修为才能突破"无关，而且 `max_experience` 默认是 `Double.MAX_VALUE`，等于默认不可用。

## 4. 不做 / 推迟

- **不参与任何结算**：不加权、不改阈值、不影响突破判定与消耗。需求里明确写了范围（"只用于两个用途"）。
- **不做"每重不同效果"**：条目只是名字，不是子定义；真要每重不同效果，那是"第二层链"的设计，等有需求再谈。
- **不扩玩家侧入口**（HUD、tooltip、按键）：只进信息面板，与当前"玩家入口先不扩"的口径一致。
- **不校验名字非空**：名字是自由文本，空串与拼错一样属于内容问题；`"minor_stages": []` 是合法写法（等于没有子境界）。
- **不为公式阈值做快照**：`breakthrough_exp` 写成公式时段宽每次求值都可以不同，与现有阈值口径一致。

## 5. 验证方式

- 编译：`./gradlew.bat compileJava compileTestModJava --console=plain`。
- 资源：`./gradlew.bat processTestModResources --console=plain`（夹具与测试包 lang 都改了）。
- 测试包：`mxt_test:qi_refining` 声明 9 个 `minor_stages`（它的 `breakthrough_exp` 是 100），测试包 lang 中英各加 9 条
  `mxt.minor_stage.*`；`/mxt_test verify` 新增一条腿（`MxtTestCommands.verifyMinorStages`）：
    - 纯算术：进度 `0 → 0`、`11 → 0`、`12 → 1`、`50 → 4`、`99 → 8`、`100 → 8`（夹取）、`150 → 8`；
    - `mxt_test:foundation`（没写 `minor_stages`）读 `NaN`；
    - 把玩家设到 `qi_refining`、进度 80，走 `ResourceService.formulaContext(...).value("minor_stage")` 读 `7`
      ——证明变量真的注册进了注册表，而不只是函数算得对；
    - 清空 `realm_stages` 后同一个上下文读 `NaN`（凡人腿）。
- 面板：`/mxt_test info` 打印面板同一份行模型，境界行应形如 `Qi Refining: Qi Refining Eighth Layer`。**专用服务器没有语言文件
  **，所以那里永远是原文；客户端装了 lang（测试包给了 `mxt.minor_stage.Eighth Layer` = 八重）才显示翻译。
