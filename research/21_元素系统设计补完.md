## 0. 结论摘要

1. **定义层是完整的**：`overcomes` / `adapted_to` / `color` 三个字段都有消费方，双层伤害管线（第一层出力、第二层减免）已闭环。
2. **缺的是"以元素为键的查询"**：元素只在 3 个数据字段里作为**值**被消费（`Relation.elements`、`ability.element_affinity`、`creature_profile.preferred_aura_elements`，即 `RegistryCodecs.holderOrTagList(ELEMENT)` 的全部 3 个调用点），没有任何地方拿"一个元素"去反问实体、世界或这一击。
3. **两个真缺陷**（D1 停用标签对元素失效、D2 `/mxt aura query` 的补全与取值分属两张注册表）无条件修。
4. **一个核心设计**（E1：元素认领伤害类型）一次解决三件事——伤害条件能问元素、环境伤害有元素、术法的属性不再被灵根集合绑架。**建议先只拍这一个**，其余都是它的下游或独立小件。

## 2. P0 缺陷（建议直接修，几行代码量级）

### D1 `#mxt:disabled` 对 element 失效

**现象**：把某元素写进 `data/mxt/tags/mxt/element/disabled.json` 后，它只从列表/补全里消失；克制、适应、配色、技能亲和、生物偏好**全部照旧生效**。

**约定**：`docs/guide/datapack/overview.md:26-32` 写的是"每个动态注册表都支持固定的 `mxt:disabled` 标签……被列入的条目不会参与运行时查询"；`registry/MxtDatapackRegistries.java:102-125,146-176,183-185` 为每张表提供了过滤读取口；`CultivationAffinity.rootElements` 也确实对**灵根**用了它。只有元素这一层被漏掉。

**根因**：`rootElements` 拿到 `SpiritRoot::element` 之后直接返回（`CultivationAffinity.java:117-120`），`DamageCalculationService` 与 `Aura.auraType` 的读取点又都是 `Holder#value()`，全程没有一次 `MxtDatapackRegistries.isDisabled(ELEMENT, holder)`。

**设计**：

新增一个收口点——`runtime/cultivation/Elements`（名字与 `AuraLookup` 同级风格）：

```java
public final class Elements {
    // 服务端：读当前注册表
    public static Optional<Holder<Element>> enabled(Holder<Element> element);
    // 客户端：读同步注册表（照 MxtDatapackRegistries.get(Provider, key, holder) 的既有写法）
    public static Optional<Holder<Element>> enabled(HolderLookup.Provider access, Holder<Element> element);
    // 灵根 → 启用元素集合（rootElements 的新家，不再直接暴露 SpiritRoot::element）
    public static Set<Holder<Element>> roots(LivingEntity entity);
}
```

改点（一次做完，否则又会漏一处）：

| 文件 | 改法 |
| --- | --- |
| `CultivationAffinity.rootElements` | 返回前过 `Elements.enabled`；`DamageCalculationService.elements`、`ElementOvercomesBiEntityCondition` 自动继承 |
| `DamageCalculationService.overcomeMultiplier/adaptationMultiplier` | 元素集合改由 `rootElements`（已过滤）提供，删除本地 `.value()` 直读 |
| `CultivationAffinity.multiplier`（两处 `auraType().filter(root.element()::equals)`） | 先判 `Elements.enabled(auraType)`，停用的元素不再作为修炼匹配键 |
| `CreatureProfileService.java:47-49` | 同上 |
| `AuraCommand.resourceName`、`SpiritJeiText:48`、`AuraZoneRenderer:73` | 客户端两处走 Provider 版本；命令侧走服务端版本，停用元素不再追加"(元素名)"也不再染色 |
| `SpiritBurstService` 的 `auraType().isPresent()` 判据 | 改判"启用的元素"，避免停用元素的灵气还能发射 |

**验收**（测试包 `mxt_test` 新增夹具元素 + `data/mxt/tags/mxt/element/disabled.json`，照 `spirit_root/disabled.json` 的先例）：

1. 停用元素的对水灵根 10 点伤害回到 10（克制与适应都不生效）；
2. `/mxt aura query` 不再给该元素灵气追加元素名，JEI 灵气消耗行不染色；
3. `preferred_aura_elements` / `element_affinity` 不再命中该元素；
4. 未停用元素一切照旧（回归）。

### D2 `/mxt aura query [type]` 的补全与取值分属两张注册表

**现象**：补全列表来自 ELEMENT（`command/AuraCommand.java:52`），取值来自 AURA（`:72`）；语言文件 `command.mxt.aura.unknown_type` 说的是"未知灵气元素"；`docs/guide/play/commands.md:20` 说的是"`type` 是资源 ID"。三种说法互不相同，按补全选出来的 id 基本必然报 unknown。

**设计**：把 `type` 的语义钉成**灵气 id**（与 `auraReport` 的 `Holder<Aura>`、与"资源名（元素名）"的展示形状一致）：

- 补全改 `MxtDatapackRegistries.holders(access, MxtResourceKeys.AURA)`；
- `command.mxt.aura.unknown_type` 文案改成"未知灵气"（中英同步）；
- 文档 `docs/guide/play/commands.md:20` 的"资源 ID"改成"灵气 ID"；
- 可选增强（E8）：另开 `/mxt aura query element <元素>`，或让 `type` 接受 `#` 前缀按元素聚合——**推荐另开子命令**，不进同一个参数。

## 3. P1 核心设计：E1 元素认领伤害类型（伤害的元素通道）

### 3.1 要解决的问题

1. `research/audit/content-coverage-gaps.md:248` 留的"伤害类型与元素之间没有映射"；
2. `research/18_阵法系统设计.md:893` 留的"伤害无元素通道"（阵法 attack 只能给 `damage_type`，给不了元素）；
3. 多灵根双吃：`overcomeMultiplier` 遍历**全部**灵根元素（`DamageCalculationService.java:112-119`），所以火+水双灵根玩家放一门只亲和火的术法时，火、水两条边同时乘进去。

### 3.2 数据格式

`mxt:element` 新增一个字段：

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `damage_types` | `HolderOrTag<DamageType>[]` | `[]` | 这个元素认领哪些伤害类型（原版与模组自己的都行，`#` 标签可用） |

```json
{
  "overcomes": [{ "elements": ["example:water"], "multiplier": 1.5 }],
  "adapted_to": [{ "elements": ["example:fire"], "multiplier": 0.5 }],
  "damage_types": ["minecraft:in_fire", "minecraft:on_fire", "minecraft:lava", "#minecraft:is_explosion"],
  "color": "#ff5522"
}
```

**语义（一句话）**：伤害类型是元素的**标签**，元素是伤害类型的**含义**；一次 strike 的元素由它的伤害类型反查得到，灵根只在"这个类型没人认领"时作为缺省。

### 3.3 运行时设计

新增 `runtime/damage/DamageElements`：

```java
public final class DamageElements {
    // 反查索引按 damage type 注册表实例缓存（照 FormulaNames.indexResources 的 MAX_CACHED_REGISTRIES 写法）
    public static Set<Holder<Element>> of(HolderLookup.Provider access, Holder<DamageType> type);
    public static Set<Holder<Element>> of(Level level, DamageSource source); // source.typeHolder()
    // 这一击的元素：认领者优先，没有认领者才回落到攻击者灵根；两者都空 = 无元素
    public static Set<Holder<Element>> strike(Level level, Optional<Holder<DamageType>> type, @Nullable Entity attacker);
}
```

`DamageCalculationService` 的签名随之加一个显式参数（**不查表，调用方决定**，与现有"管线不带数值"的风格一致）：

```java
public static double deal(@Nullable Entity attacker, Entity target, double amount,
                          Optional<Holder<DamageType>> damageType, @Nullable FormulaContext context) {
    Set<Holder<Element>> elements = DamageElements.strike(target.level(), damageType, attacker);
    double shaped = outgoing(attacker, target, amount, context, elements);
    ...
}

public static double outgoing(@Nullable Entity attacker, Entity target, double amount,
                              @Nullable FormulaContext context, Set<Holder<Element>> elements);

// 第二层改成收 DamageSource：它唯一的用处就是"这一击是什么元素"
public static double incoming(LivingEntity target, DamageSource source, double amount);
```

`DamageEventBridge.onIncomingDamage` 传 `event.getSource()`；`ExplodeAction.ShapedCalculator.getEntityDamageAmount`（`data/action/builtin/entity/ExplodeAction.java:99-102`）继续用缺省元素集合（爆炸还没有 source 可读，第一层的元素仍按灵根；第二层会在真正结算时按 `minecraft:explosion` 认领结果算）。

**优先级（写死，不给开关）**：

| 情况 | 这一击的元素 |
| --- | --- |
| `damage_type` 被一个或多个元素认领 | 全部认领者（与灵根一致：多条成立时**相乘**） |
| 未被认领、有活体攻击者 | 攻击者灵根的启用元素（= 现状） |
| 未被认领、无攻击者 | 空 = 无关系（= 现状） |

**白拿的收益**：

- 岩浆/闪电/摔落这类**环境伤害**只要被认领，第二层立刻生效——"火灵根怕水不怕岩浆"从此可表达，且不碰原版代码；
- `mxt:explode` 用的是 `level.damageSources().explosion(...)`（`ExplodeAction.java:53`），认领 `minecraft:explosion` 就能让爆炸带属性；
- 阵法 attack 已经带可选 `damage_type`（`FormationActionRunner.java:75`），内容方写一个类型即可获得属性。

**配套条件**：新增伤害条件 `mxt:element`（`HolderOrTag<Element>[]`），读**同一份**解析（`DamageConditionContext` 已有 `source()`，`data/condition/DamageCondition.java:28-34`）。这样"条件说的元素"与"管线算的元素"永远同源，不会出现条件判火、管线按水算。

### 3.4 可选件 E1b：动作自己声明元素（"术法属性覆盖灵根"）

如果内容方要"火灵根玩家放水术法就是水属性"，给伤害动作加可选 `element`：

```json
{
  "type": "mxt:damage_target",
  "amount": "12 * element_modifier",
  "element": "example:fire",
  "damage_type": "minecraft:magic"
}
```

**硬约束**（这条是整个设计的地基，不能松；**落地时修正**：改为**首次使用时**核对并各报一次日志，因为加载期拿不到跨注册表的值——见 §9 与 `DamageElements.resolveType`）：

1. 声明了 `element` 就**必须**声明 `damage_type`；缺一即加载失败；
2. 该 `damage_type` 必须被该元素（或其标签）在 `damage_types` 里认领。

理由：第二层只能从 `DamageSource` 读世界，跨事件的"这一击是火"账本既脆又会在取消/重入时错位；把元素做成"伤害类型的含义"之后，声明元素 = 选一个已经被认领的类型，第二层与条件侧**不需要任何新通道**。

可行性：`element`/`damage_type` 都是 `RegistryFixedCodec`，数据包解码本来就带 `RegistryOps`（KubeJS 侧同样，见 `compat/kubejs/codec/MxtKubeJsDataCodec.java:41`），所以 `RecordCodecBuilder.validate` 里能同时拿到两个 holder 并比对认领关系。

**明确不做**：不给 `Ability` 加 `element`。能力的动作树不可枚举，验证不了"每个伤害动作都声明了匹配的类型"，结果就是第二层静默失效——这类"能写但没人算"的字段是本仓一贯要避免的。

| `mxt:has_element`（实体条件） | `HolderOrTag<Element>` 列表 | 实体任一灵根元素命中（`RegistryCodecs.matches`） |
| `mxt:has_element`（战利品条件） | `entity` 目标 + `HolderOrTag<Element>` 列表 | 同上，供掉落表按"火灵根的人"分池 |

同时把 `HasSpiritRootEntityCondition.java:15` / `HasSpiritRootLootCondition.java:21` 的 `spirit_root` 从 `Holder<SpiritRoot>` 改成 `HolderOrTag<SpiritRoot>`：`docs/数据包格式.md:602` 早就写了"灵根分组、兼容与筛选使用原版标签"，但全仓 `holderOrTagList(SPIRIT_ROOT)` **零调用点**，这是条空头承诺。JSON 兼容（`holderOrTagList` 同时接受单值与数组）。

### E3 `Element` / `Relation` 的加载期校验

现状：`Element.validate`（`data/cultivation/Element.java:41-52`）只校验 multiplier；`Relation.elements` 允许空数组（静默什么都不匹配），重复条目也没有诊断。对照 `BlockAura.validate`（`data/aura/BlockAura.java:28-31`，`blocks` 非空）与 `HerbTagEntry.validate`（`runtime/alchemy/HerbTagEntry.java:28-32`，两个字段至少写一个），元素这里明显更松。

补：

1. `elements` 为空 → 加载期**拒绝**（整表加载失败，与 multiplier 同一条规则）；
2. 同一 `overcomes`/`adapted_to` 里两条 `Relation` 指向同一元素 → **诊断**（不拒绝，"相乘"是合法语义，只是几乎总是手误）；
3. 同一 `damage_type` 被多个元素认领 → **诊断**并定义语义为"相乘"（与灵根一致）；
4. 诊断一律走既有 `util/formula/FormulaDiagnostics` 风格，能在日志里看见，不静默。

### E4 按元素查询灵气环境

`AuraRangeEntityCondition`（`data/condition/builtin/entity/AuraRangeEntityCondition.java:22-31`）只按 `mxt:aura` 开键，问不了"脚下是不是火属性灵脉"。**新增** `mxt:aura_element`（不动既有 codec 的语义）：

```json
{ "type": "mxt:aura_element", "elements": { "example:fire": { "min": 20 } } }
```

语义：把该元素（或其标签）下**所有启用的灵气**在当前坐标的量求和后比较（元素是聚合键，灵气才是池子）。同时给 `command/AuraCommand` 的 E8 提供实现基础。

### E5 公式变量：让打包者看得见元素

在 `FormulaNames` 里补一个元素索引（照 `indexResources` 的写法），并让 `EntityVariable`（`registry/MxtFormulaVariables.java:99-123`）在属性、资源都没命中时再查元素：

| 名字 | 值 |
| --- | --- |
| `caster_element_<flattened id>` / `target_element_<flattened id>` | 1 / 0：是否带该元素（启用元素集合的成员判定） |
| `caster_element_count` / `target_element_count` | 元素个数 |

不做：把克制倍率做成公式变量。倍率是管线的事，要进公式的话应走显式上下文值（另一个议题），否则同一件事会有两个算法。

### E6 面板与提示把元素显示出来

现状：人物信息面板的"灵根"一行只有灵根名（`screen/information/InformationManager.java:40` → `InformationHelper.joinDefinitions` 返回 `String`），看不出它是火是水；`Element.color` 只在灵气语境里出现。

设计：`InformationHelper` 增一个返回 `Component` 的变体（`InformationCollector.add` 已支持 `Component` 与颜色），灵根行渲染成 `灵根名(元素名)`，元素名取 `Element.color`。客户端读元素走 D1 的 `Elements.enabled(Provider, ...)`。Jade/物品 tooltip 本轮不做。

### E7 灵草元素词汇与 `mxt:element` 互认

现状是两套互不相认的词汇：`SpiritHerb.element_tags` 是 `Identifier[]`（`data/alchemy/SpiritHerb.java:19,24`），`mxt:herb_tag` 的 `element` 用**字符串相等**匹配（`runtime/alchemy/HerbTagEntry.java:46`），既不查 `mxt:element` 也不支持 `#` 标签。定义了一条元素之后，每株草还得手抄同一个 id，写错没有任何提示。

设计（推荐）：两个字段都改成 `HolderOrTag<Element>`，匹配走 `RegistryCodecs.matches`。

- 兼容：现有 `"element_tags": ["mxt_test:fire"]` 只要 `mxt_test:fire` 确实是元素，JSON 一个字符不用改（`RegistryFixedCodec` 解出 holder）；原本"写了个不存在的 id"从**静默不匹配**变成**加载期失败**，这正是想要的。
- 备选（不推荐）：保留 `Identifier[]`，只在 `HerbTagEntry` 侧做"元素 → 标签"展开——两套词汇会继续存在。

### E8 命令按元素查询

见 D2 的可选增强：`/mxt aura query element <元素>`（按元素聚合当前坐标所有灵气），与 `/mxt aura query <灵气>` 并列。补全来自 `MxtResourceKeys.ELEMENT`（这次名实相符）。

### E9 内容层：内置元素集

现状：jar 只带 `mxt:common`（`data/mxt/mxt/element/common.json`，两个关系都是空数组），语言名还是 `element.mxt.common` = "通用灵气 / Common Aura"，而内置 `mxt:common` 灵气（`data/mxt/mxt/aura/common.json`）的 `aura_type` 正指向它。也就是说**不装任何数据包时整套元素机制空转**，真实元素只存在于测试包。

这是决策点而非缺陷：如果期望"开箱五行"，需要一份内置元素集（含 `damage_types` 认领与两条关系）；如果不期望，至少把 `element.mxt.common` 的措辞改成"通用元素"这类不与灵气混淆的说法，并在 `docs/guide/datapack/overview.md` 明说"元素由内容包提供"。
