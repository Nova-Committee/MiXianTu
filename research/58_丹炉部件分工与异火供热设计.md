# 丹炉部件分工与异火供热设计

## 基准与状态

2026-09-27，基于 `feature/dan` 的 Minecraft 26.1.2 / NeoForge 26.1.2.99 / Java 25。用户实机查看后要求重做丹炉部件、供热与界面；本稿取代 `57_炼丹丹药与灵植闭环设计.md` 中的集中式丹炉、灵气银行供火、炉型自带温度上限和原版集中界面。药性配伍、灵田、丹药与冻结批次规则仍沿用 57，但玩家选丹方和炉内指引页已由下面的开炉判定修订取代。放入材料不会自行开炉，主辅角色也不自动分配。**部件、异火、四个原生页面与无选方开炉已经实现并实跑；合并主分支前的证据见第八节。第七节保留修订前的历史结果，不混用两轮探针数和截图；主分支合并后的复验另行记录。**

用户另行确认：直接切换为异火，移除旧供火字段和丹炉灵气银行，不保留两套机制；测试异火装入核心后持续供热、不消耗。新版实机测试已获准使用本次专用测试世界及双客户端，在独立空白区手搭、运行探针、验证完整流程及原生编辑器；保留原炉，允许保存证据并重启本次自有进程。

## 修订：开炉时判定产物（2026-09-27）

用户明确要求丹炉不再显示丹方，也不要玩家在多条匹配里点选。[觅长生百科·炼丹入门](https://wiki.biligame.com/mcs/炼丹入门)写丹方不是必须；百科链接的[第三方丹方模拟器](https://github.com/Rock-Ayl/MiChangSheng-DanFangMoNiQi)有更高品级和冲突处理，**不照搬固定品级、枚举或源码，也不把需求向量支配说成原作的逐字复刻**。

`mxt:alchemy` 仍是后端药性规则，不是固定物品 ID 清单。公开数据包字段故意不改，包括 `name`、`description` 和可选 `guide`。不新增优先级、家族或品级字段。`guide` 只是作者留下的示例元数据。丹炉不读取、不展示它，也不另做查看器。

完全匹配的候选里，只保留唯一一条需求向量，它必须严格支配其余每一条。比较主药阈值表、辅药阈值表和药引需求。两边药性键集合相同，每一项要求都大于或等于对方，并且至少有一项严格更大，才算严格支配。不比较品质名、品质链序号、药力总和、温度、时长、配方 ID 或加载顺序。加权寒热和无额外药性规则不变。

实现上先提升一个支配候选，再确认它严格支配其余每一个匹配项，不做候选矩阵，也不为比较额外分配。没有唯一支配结果时返回配伍冲突，界面不写“请选择丹方”，不扣料。零匹配仍给出原来的不足、冲突或失衡原因。玩家在核心点击开炉后才做这次判定，它发生在品质、规格、环境、温度和输出容量检查之前。温度够不到或产物仓满，不会静默改选另一条丹方。

每次开炉只判定一次，把选定配方和产物冻进既有批次。`AlchemyWorkstationService.preview(ServerPlayer, AlchemyWorkstation)` 与 `start(ServerPlayer, AlchemyWorkstation)` 不再接收所选配方。`AlchemyPreview` 用 `resolvedRecipe()` 表示实际解析结果，不再有玩家选择。工位、控制器和持久状态删除 `select`、`clearSelection`、`selected`；旧存档里的选择字段忽略，活动批次保持不动。会话仍保存冻结后的 `recipeId`，事件和进度条件仍用这个身份。

动作包是 `AlchemyActionC2SPayload(int containerId, Action action, double temperature)`，`Action` 只有 `TEMPERATURE`、`START`、`ABORT`。客户端发送是 `send(Action, double)`，三个字段，没有丹方或页码。视图只有状态和读数，没有指引页。状态保留炉型、品质、阶段、原因、能否开炉、锁定、成型和主辅槽数，不带丹方名或所选 ID。`recipeTarget` 与容差只作为温度读数；`total` 只表示活动批次，空闲为 0。温度确认纪元不变。网络协议版本同步升为 `2`；客户端与服务端必须一起更新，不为旧动作序号或旧字段顺序保留适配。

监控稳定 ID 是 `title`、`player_inventory`、`inventory_0`–`inventory_35`、`fire`、`monitor`、`temperature`、`limit`、`status`、`progress`、`target`、`apply`、`start`、`abort`。四个模板共用 `player_inventory` 和 `inventory_0`–`inventory_35`。源模板已删掉丹方名、丹方按钮和整个选择子树，不再有 `recipe`、`recipes`、`chooser`、`guide_close`、`prev`、`next`、`page`、`recipe_0`–`recipe_7`、`detail_scroll`、`detail`。监控画布现为 188×211，原先高 224；剩余内容上移 13，开炉与终止各宽 85、间隔 4。玩家背包内容不改。三个仓页模板不改。Java 不在运行时另造布局树，也不做模板版本号或别名。已有游戏目录副本仍只在缺失时种入，不静默覆盖作者改过的文件。旧的 `alchemy_monitor.ui.nbt` 若还留着丹方或选择节点，要由作者自己删掉，或手工换上新监控模板。自有甲乙运行副本按源哈希刷新，供验收使用。源监控 SHA-256 为 `e84b500401e797955e229e24540ddac06e5b5a3073afffeb36247da221f1266f`。当前实跑证据在 `build/alchemy-verification/auto-brewing/`，结果见第八节；玩家仍要点击开炉。

## 一、物理部件与职责

仍为手动搭建的 3×3×3，中间空气。局部坐标为 `(x,y,z)`，前面是 `z=0`，局部编号 `x+3*z+9*y`；核心朝向玩家，结构向核心背后延伸。

| 部件 | 坐标 / 编号 | 交互与所有权 |
| --- | --- | --- |
| 丹炉核心 | `(1,1,0)` / 10 | 监控、设温、开炉、终止；持有炉型单件快照、异火槽与活动批次，不保存药材仓或产物仓的第二份库存，也不保存玩家选中的丹方 |
| 主药投料仓 | `(2,1,1)` / 14 | 面向正面时左侧；两个主药槽，持有自己的真实物品 |
| 辅药投料仓 | `(0,1,1)` / 12 | 面向正面时右侧；两个辅药槽与一个药引槽，持有自己的真实物品 |
| 产物仓 | `(1,2,1)` / 22 | 顶部；四个输出槽，只能提取，不接受外部投料 |
| 炉壁 | 其余 22 格 | 组成壳体并提供耐温约束；不打开监控或仓库界面 |
| 中空格 | `(1,1,1)` / 13 | 必须为空气 |

两个投料仓属于同一功能类别，但使用不同方块 ID 固定角色，避免旋转或重新认领把药引变成隐藏物品。角色不由玩家在 UI 中反复选择。低规格炉型仍可禁用第二个主药或辅药槽；禁用格不接受物品。

结构完整且炉壁材料均有效后才成型。成型模型沿用整座 Blockbench 鼎形，部件分别显示其所在格的几何；未成型分别显示核心、仓口和炉壁构件，而不是一件已经成型的小鼎。成型以后从前面、左右和顶部点击分别打开对应页面，不再把所有点击路由到同一个页面。

主药、辅药与产物仓各自保存、同步、掉落自己的库存。核心只持有异火与批次待输出。运行服务通过固定九槽的实时组合 `Container` 访问两座投料仓与产物仓，不复制库存。接口映射保持主药 0–1、辅药 2–3、药引 4、产物 5–8。

## 二、炉壁材料与温度

新增数据包注册表与同名物品组件 `mxt:alchemy_wall_material`，定义 `AlchemyWallMaterial`：

| 字段 | 形状 | 规则 |
| --- | --- | --- |
| `name` / `description` | 既有定义文本 | 使用 `NamedDefinition` 与统一自动名字键 |
| `max_temperature` | Double | 必填，有限且大于 0 |

炉壁物品通过 Holder 组件选择材料；放置、保存、同步、创造取样和正常拆回保留材料身份。定义缺失时不能成型，不以本体硬编码数值兜底。合并主分支后，停用定义改用加载期 `neoforge:conditions`，不再读取 `mxt:disabled`。Picker 提供各材料炉壁。本体不内置铜、铁或灵材的温度表，代表性材料只放测试包。

混合材料的整炉耐温上限取 **22 块炉壁的最低值**。不能用高耐温材料平均掉薄弱处。炉型品质仍只用于既有品质显示和使用条件，不乘温度、不根据品级名称推导耐温。

保留 `mxt:alchemy` 丹方的 `target_temperature`、`temperature_tolerance` 与 `max_bad_ticks`。目标温度须在整炉耐温和异火能力内；配方温区不可达时拒绝开炉，且不扣料。调整到非法温度的网络请求同样拒绝。

炉型保留名称、描述、主辅槽数、品质、容量及 `cooling_per_tick`；删除 `max_temperature`、`heating_per_tick`、`aura_capacity`、`heating_costs`。更新全部调用者与测试 JSON，不保留兼容别名或无消费者字段。

## 三、异火供热

本次不实现异火捕获、炼化、升级、成长或独立内容系统。真实扩展边界为 `api/AlchemyHeatSource`，由异火物品实现，提供有限正的最高温度与每 tick 升温速度。数值可依据物品、世界和核心位置回答，所有写入仍由服务端炼丹服务完成。

核心有一个真实异火槽。仅接收实现该接口的物品，一次只放一件；活动批次中不可取换。测试模组注册测试异火物品，用确定的温度和升温值走完整运行路径，不写固定假温度、不在界面模拟进度。本体没有默认异火。

实际可设上限为 `min(整炉最低耐温, 异火最高温度)`。预热、炼制按异火速率接近设温，不越过设温；高于目标时或停止供热后按炉型冷却速度回落。无异火或异火返回非法数值时不能开炉。测试异火不消耗，不再引入灵气付款、`poweredTicks` 或燃料银行状态。

配方的 `minimum_aura` 仍是环境门槛，`alchemy_env_bonus` 仍只作用于门槛；二者不是热源，与删除炉内银行不冲突。

## 四、事务、掉落与加载边界

- 开炉重读三个仓库的实际库存、结构、材料耐温、异火、品质及配伍；Pre 取消或库存被回调改变时拒绝，不扣料。
- 成功提交时一次性消耗两侧输入仓的材料，批次只保存不可领取的摘要和冻结工艺；输入仓在批次期间锁定。
- `WARMING → RUNNING → READY`、温区累计越界判废和行为一次性规则不变。输出入仓后清旧会话，在事务守卫内执行完成行为与进度条件，释放守卫后再发 `Post`；`Post` 新开批次不被旧收尾覆盖。
- 输出按真实堆叠余量整体接纳，兼容的待输出条目允许合并；产物仓满或暂不可用时保留核心内的一份待输出，不丢物、不复制、不重新产出。
- 拆仓只掉该仓自己的物品；拆核心只掉核心单件、异火和已生成待输出，不再把其他仓库的物品掉第二遍。
- 活动期间确实破坏结构走一次失败，不退已消费材料；仅邻区块未加载则暂停，不强载。共享部件拒绝认领。解除认领不清仓内物品。
- 存档恢复、暂停、多人查看、非法旧菜单请求不能绕过锁定或改变结算归属。服务端不依赖客户端模板来决定槽位权限。

## 五、LDLib 原生可编辑界面

> **本节已于 2026-09-30 作废**：四个页面从 LDLib2 的 `.ui.nbt` 模板改成 ApricityUI 的 HTML/CSS 页面，LDLib2 依赖与游戏内 UI 编辑器这条路径一并去掉（当时的 AUI 三篇设计稿已于同日按用户要求删除，现行约定见 `AGENTS.md` §4 的 AUI 条款与 [`docs/guide/java/screens.md`](../docs/guide/java/screens.md)）。下面是当时的设计，保留作历史；当前形状以代码与 `docs/数据包格式.md` 的丹炉一节为准。

使用仓库已固定的 LDLib2 `26.1.2.39`，核对当前 26.x API，不照搬 1.21.1 的模板编码或菜单构造签名。

提供四个独立原生 `.ui.nbt` 模板：监控、主药仓、辅药／药引仓、产物仓。布局、尺寸、颜色、背景、控件、槽位、文本与动态行原型全部保存在模板；Java 只按稳定 ID 绑定数据、槽位和行为。不能以 Java 手写整棵 UI 树，再导出一个编辑不了的空文件冒充模板。

监控面板只常驻炉温与目标、有效温度上限、进度／阶段、异火槽、开炉／终止。不显示丹方名，不提供丹方按钮或指引页。耐温来源、品质和配伍不足放进悬浮提示，不常驻旧的药性长表、灵气银行和成片解释文字。其余三个页面以对应槽位和玩家背包为主，不复制整套监控。进度和总数只读取活动批次；空闲与预热为零，完成但等待产物仓时保留完成进度。`recipeTarget` 与容差只是温度读数，不是所选丹方的预览时长。

首次将缺失的 bundled 模板种到 `<gameDir>/ldlib2/assets/mxt/ui/`，以绝对规范化目录注册可写资源 provider。已有用户文件不覆盖；每次重新开界面读取新模板。当前 LDLib 的 `/ldlib2_ui_editor` 只在单人世界可用；从编辑器资源浏览器打开模板并保存后，关闭再打开对应界面即使用保存的布局，不要求重新编译 Java。

模板节点类型、ID 和实际槽位顺序构成绑定合同；视觉重排不能改变网络槽索引。发包、开菜单与专用服类加载必须保持客户端边界。`AlchemyFurnaceScreen` 替换为原生模板的数据／槽位／事件绑定器；旧集中式布局实现、旧不再消费的 view 字段及协议分支删除，不并存第二种入口。
