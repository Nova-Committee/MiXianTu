# 46_品质链条与升级设计

> **基准**：`main` 工作树（2026-09-23，含同日新增的 `ItemQuality.color`）。对着这些代码与文档写的：
> `data/quality/ItemQuality.java`、`data/quality/ItemQualityTags.java`、`runtime/item/ItemQualityService.java`、
> `runtime/item/ItemBindingService.java`、`data/forging/ForgingBlueprint.java`、`registry/MxtDatapackRegistries.java`、
> `docs/数据包格式.md` 的 `item_quality` / `forging_blueprint` 两节。
>
> **起因**：用户要求「整合品质系统，满足：① 多个一组成链条；② 可选择升级；③ 可以给任何需要的物品附带」。
>
> **状态**：方案，未落地。文末 §7 的六项要拍板后才动手。

## 0. 结论

**能整合，而且三件事都能落在现有构件上**：tier 定义有 `item_quality`，代价有统一的 `Cost` + `CostTransaction`，
条件有 `EntityCondition`，显示有刚接好的 `color`。真正的缺口只有两个：

1. **链条没有载体**——今天"顺序"只写在标签 `values` 的书写顺序里，而读它的代码（`ordered()`）**零调用**；
2. **没有任何写入入口**——`ItemQualityService.set/clear` **零调用**，游戏里唯一真的给物品写上品质的是锻造结算（写 `FORGING_RESULT` 组件）与灵植定义。

代价是一次**破坏性迁移**：4 张绑定表的 `quality_group`（标签）合并成链引用，默认档规则随之改变。见 §4。

## 2. 三件事各自缺什么

| 需求 | 已有 | 缺 |
| --- | --- | --- |
| ① 多个一组成链条 | 标签顺序（无人读）、组标签（只表成员与默认档） | **载体**：一个能被引用、能校验、能查出"下一档"的对象 |
| ② 可选择升级 | 代价系统、条件系统、`set()` | **每步代价/条件的数据** + **写入服务** + **入口** |
| ③ 任何物品可附带 | 组件读取对所有堆通用；`item_binding` 可按物品/标签匹配 | **主动附上某一档的入口**；`tool_binding` / `blueprint_binding` **没有**品质字段；升级需要知道"哪条链" |

## 3. 建议形状（待拍板）

### 3.1 新注册表 `mxt:quality_chain`（链条载体）

```json
{
  "name": "example:forged_ladder",
  "tiers": ["example:poor", "example:normal", "example:excellent"],
  "default": "example:poor",
  "upgrades": [
    { "costs": [ { "id": "example:spirit_iron", "amount": 2 } ],
      "condition": { "type": "mxt:always_true" } },
    { "costs": [ { "id": "example:spirit_iron", "amount": 4 } ],
      "condition": { "type": "mxt:always_true" } }
  ]
}
```

- `tiers`：**低 → 高**，数组顺序就是链条顺序（不再依赖标签合并顺序）。
- `default`：可选，省略取 `tiers[0]`。取代今天"组里最后一个 enabled 成员"那条隐晦规则。
- `upgrades`：可选，`upgrades[i]` 描述 `tiers[i] → tiers[i+1]` 这一步；比 `tiers.size() - 1` 短就表示后面的步不可升。
- 文本字段 `name` / `description` 走既有的 18 张表那套（`ContextNameCodec`，省略按 id 生成）。
- 加载期校验：`tiers` 非空且不重复；`default ∈ tiers`；`upgrades.size() ≤ tiers.size() - 1`；步的 `costs` 走 `Cost.LIST_CODEC`（解码失败**不静默丢弃**，与其它消耗字段同口径）；引用必须能解析。

为什么不是另两种形状：

- **标签 `chain/<name>`**：零新注册表，但顺序依赖多文件合并顺序、装不下每步代价、无法命名与并列多条链。
- **定义内 `next` / `upgrades_to` 字段**：最简单，但链是隐式的（无法命名、无法并列）、分叉表达不了、跨包续链只能靠改别人的定义。

### 3.2 组与链合并（这是"整合"的核心）

绑定表的 `quality_group`（`Tag<ItemQuality>`）**换成** `quality_chain`（`Holder<QualityChain>`）：

- 成员资格 = 链的 `tiers` 集合（`check` 的 `QUALITY_GROUP` 语义不变，判据从标签变成链）；
- 默认档 = 链的 `default`；
- 顺序 = 链的顺序（`ordered()` 的活由链接手）。

### 3.3 `QualityChainService`（唯一读链入口）

`chainOf(access, id/holder)`、`tier(chain, quality) -> int`、`next(chain, quality) -> Optional<Step>`、
`isMember(chain, quality)`、`defaultTier(chain)`。`ItemQualityService` 的 `groupDefault` 与 `check` 改为走它，
**不再有第二处读标签顺序**。

### 3.4 升级服务（可选择升级）

`QualityUpgradeService.upgrade(actor, stack, target)`：

1. 解析这一栈属于哪条链（§3.6）；
2. 校验 `target` 比当前档高且在链内；
3. 逐步（或一次）检查 `condition`、用 `CostTransaction.plan` → `commit` 一次付清（**沿用唯一扣费实现**，整组原子）；
4. 写 `ItemQualityService.set(stack, target)`；
5. 全程 `Result(changed, failure)` 值返回（房规：失败用结果不用异常），只在服务端执行。

### 3.5 入口（**§7 待拍板**）

- **P1 最小集**：命令 `/mxt quality get|set|clear|upgrade`（写操作 `requires(ServerCommandManager::mayChange)`）+ KubeJS `MxtQuality`
  （内容方脚本、任务奖励、掉落时点）。这两条让"整合后的系统"立刻可玩、可测。
- **P2 界面**：锻造台/炼丹台的"提升品质"操作；Tooltip 增加"下一档：<名>（代价：…）"一行（`color` 已经就位）。

### 3.6 "任何需要的物品"怎么附带

1. 组件 `mxt:item_quality` 对所有堆通用（读已经通用），补的是**写入入口**（§3.5 的命令与脚本）。
2. 没有绑定表的物品：链从"该档**唯一**所属的链"反查；一档属于多条链时拒绝升级并报明确原因（否则链就是猜的）。
3. `tool_binding` / `blueprint_binding` 补可选 `quality_chain`，把它们也纳入"任何需要的物品"。

## 4. 与现状的差异 / 破坏性

| 变化 | 影响面 |
| --- | --- |
| 新注册表 1 张 `mxt/quality_chain/` | `MxtDatapackRegistries` + `MxtResourceKeys` + 文档总表 |
| `quality_group` → `quality_chain` | 4 张绑定表（item / weapon / pill / technique）+ 测试包 3 处引用 + 文档 4 页 + 文档站中英 |
| 默认档规则改变 | 从"组里最后一个 enabled"改成链的 `default`。**行为变化**：测试包 `#mxt_test:group/forged` 今天默认是 `poor`，迁移后由链声明决定 |
| `mxt:tooltip_order` 与 `ordered()/group()/groups()` 退休 | 要么删（推荐，零调用），要么接上显示排序；`docs/数据包格式.md:1083` 与 `research/audit/technique.md:361` 的表述要改 |
| 自由文本旁支（可选） | `technique.grade` 并入则删 `mxt.technique_grade.*` 那套；`rarity` 另议 |

## 5. 不做 / 推迟

- **不给品质加"效果强度"字段**：`content-coverage-gaps` 的「品相」需要强度档，但强度进哪条管线（属性？伤害？）没定，属另一稿。
- **不做随机品质与成功率**：`research/06` 明确"不额外引入随机品质"。
- **不做降档**：`upgrade` 只升；移除档位由命令的 `clear` 负责，不进链条语义。
- **不动 `spirit_root` / `physique` 的 `rarity`**：信息面板里的文本，改动面另算。
- **不做物品间的"品质转移"**（把 A 的档挪给 B）：留给将来的合成/升级配方稿。

## 7. 拍板结果与落地记录（2026-09-23 同日落地）

用户在读完本稿后给的原话是「直接进行接入，然后功法、法器等都在 json 里面给一个默认的品质（可选），然后同时加一个物品组件，允许进行品质覆盖」。
按此落地，六项的处理如下（**已实现，未实跑**）：

| 议题 | 结果 |
| --- | --- |
| 1 链的载体 | **采纳本稿推荐**：新注册表 `mxt:quality_chain`（`tiers` / `default` / `upgrades` + 加载期校验）。 |
| 2 组与链是否合并 | **合并**：4 张绑定表的 `quality_group` → `quality_chain`；`group/<name>` 标签与 `ItemQualityTags.group` / `groups` / `inGroup` / `groupDefault` 一并删除。 |
| 3 入口范围 | **命令 + KubeJS**（`/quality get\|set\|clear\|upgrade` 与 `MxtQuality`），界面（P2）**没做**。 |
| 4 升级粒度 | **一次一档**（`QualityUpgradeService.upgrade`），跳档没做。 |
| 5 `technique.grade` | **同批并入**：换成可选 `Holder<item_quality>`，`mxt.technique_grade.<值>` 那套查键退休；面板行首改为「功法名 + 等级」、名称按品阶上色，悬浮提示的品阶读该定义的名字与颜色。 |
| 6 `tooltip_order` + `ordered()` | **保留未动**（仍然零调用）。这是本稿唯一悬着的收尾，见下。 |

落地时的两处补充（用户原话里的第二、三件事）：

- **定义默认品质**：`technique.quality` 与 `artifact.quality`（都选填）进入了新的解析顺序——覆盖组件 → 锻造结果 → 定义默认（artifact / technique）→ 链的 `default` → 灵植声明（**五格**：灵植排在链的默认档之后，`ItemQualityService.find` 的最后一支；与 `docs/guide/play/commands.md`、`docs/guide/kubejs/api.md` 同一口径）。于是"给任何需要的物品附带品质"有了第二条路：不必写绑定表，定义自己就能说默认档。
- **组件覆盖真正可用**：`mxt:item_quality` 覆盖组件本来就存在，但 `ItemQualityService.set/clear` 一直是**零调用**；命令与 KubeJS 补上之后它才第一次有入口，`/quality clear` 的语义就是"回到定义默认档"。

顺带修掉的两处既有隐患：`ItemQualityService` 那两个"只在服务端可用"的重载（`find(ItemStack)` / `modifier(ItemStack, …)`）删除，`canUse` / `check` 改为从实体的 `registryAccess()` 取注册表（炼丹的 `inputModifier` 随之改成 Provider 口径）。

**仍未做**：`/mxt_test quality` 探针腿（§6 里承诺的那条）、升级界面（锻造台/炼丹台按钮、tooltip 的"下一档 + 代价"一行）、跳档、降档、`tooltip_order` 的收尾。

**同日追加（注册表改名）**：`mxt:item_quality` → `mxt:quality`（用户要求），数据包目录变成 `mxt/quality/`，注册表标题键变成 `mxt.registry.quality`（显示文本不变），测试包目录与 `tooltip_order` 标签文件一并迁移；`DefinitionText` 里那条只为它存在的类别例外表随之删除（注册表 path 现在就是文本类别 `quality`，`quality.mxt.<命名空间>.<路径>` 这套生成键一个都没变）。**覆盖组件 `mxt:item_quality` 是另一个东西，没有跟着改名**。记录见 `research/02_动态注册表清单.md` 同日条目。
