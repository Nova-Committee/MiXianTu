# 92 阵法作为灵气消费者：与玩家共用一套分配

> 2026-10-19，用户给定方向："阵法和玩家一起走分配灵气的逻辑，`rebuild` 只负责处理方块"，并采纳上一轮问答里的三条默认口径
> （按 tick 领、期内累计 / 覆盖到的每个区块各领一份 / `mxt:aura` 加 `upkeep_weight`、`RANDOM` 下也参与）。
> 本文取代 [`91`](91_方块灵气子区块重建与位置现查设计.md) §6 那条"吸收在区块重建时算"的结论。

## 1. 改之前的形状，以及它为什么必须改

方块发射器有两个消费者，而它们当时是**几何互斥**的：

- **玩家（修炼）**：`AuraDistributionService` 每 tick 预先把区块灵气池按策略分给"这一 tick 要修炼的人"，
  修炼侧用 `take(player)` 算 `allocationFactor`。
- **阵法（维护费）**：`FormationWorldTicker.chargeUpkeep` → `FormationService.maintain(..., supplied)`，
  而 `supplied` 来自 `FormationAbsorption.absorbedFor(...)`（球内发射器的合计，**缓存在区块附件的
  `absorbedAura` 里**）加上可选的脚下环境。

为了不让同一份灵气既进环境又进阵法，被吸收的方块**必须从区块聚合里排除**，于是 `BlockAuraService.rebuild`
被迫知道"这一块被哪几座阵覆盖"，覆盖到的区块只能走逐格扫描。后果是：

- 阵法越大，`rebuild` 越慢，而且是**按体积**慢（半径 128 ≈ 1400 万格，见 91 §8）；
- 立/撤阵要把半径内所有区块标脏，`markDirty` 当时还会 `getChunkAt` **强制加载**它们；
- `absorbedAura` 这份缓存本身带来时序问题（方块变化靠 10~30 秒的周期重建兜）。

## 2. 新形状

**一句话**：方块缓存只记"这一块地有哪些发射器"；谁从中拿多少，由**同一套分配器**决定，玩家和阵法都是消费者。

| 环节 | 现在 |
| --- | --- |
| 方块缓存 | `rebuild` 只做聚合（`count()`），与阵法无关；`block_aura_sections` 里没有任何"归谁"的信息 |
| 消费者清单 | `AuraDistributionService.prepare(level)` 每 tick 收集玩家 claim ＋ 阵法 claim |
| 阵法的请求量 | 一个阵法在**它覆盖到的每个已加载区块**各领一份，`requested` = 该区块球内发射器合计 ÷ `PERIOD` |
| 阵法的份额 | 与该区块里的修炼者**同台**，按该区块的 `Distribution` 策略切同一个池子 |
| 期内累计 | 每个 tick 分到的量累加进 `FORMATION_CREDITS`（键是维度 + 阵心），一期 20 tick 累加成"本期地面总共给我多少" |
| 付账 | `chargeUpkeep` 用 `takeUpkeep(level, controller)` 取这份累计，喂给 `FormationService.maintain(..., supplied)`；之后的顺序不变：自给 → 储备 → 主人账户 |
| 权重 | `mxt:aura` 新字段 `upkeep_weight`（`NumberProvider`，缺省 `1`）；`realm_weighted` 下与玩家的 `aura_share_weight` 同列比较 |
| 策略 | 区块里第一个带策略的 claim 说了算（玩家是它解析出的 zone，阵法是阵地位置解析出的 zone）；都没有则 `EQUAL` |

**地面怎么算**：`BlockAuraService.groundInSphere(level, chunk, center, radius²)`，逐 section：

- 球**够不着**这一段（最近的方块中心在球外）→ 跳过；
- 球**完全包住**这一段（最远的方块中心在球内）→ 用该段的 `count()` 聚合，一次到位；
- **跨球面**的段 → 只对这些段逐格判定。

所以成本跟着**球壳面积**走而不是体积：半径 128 的阵内部区块一个格子都不读，只有球面上的段要扫。
这份地面**每 period 算一次**（`GROUND`，键同上），不是每 tick。

## 3. 必须知道的行为变化

1. **阵法与玩家竞争同一口井。** 站在阵里修炼的人，速度会因为阵法按权重分走一部分而下降（幅度取决于
   `upkeep_weight` 与策略）。这正是本设计的目的，但它是一次**平衡变化**。
2. **被阵法覆盖的地面不再从环境里扣除。** 所以"站在阵里查灵气"看到的是**全部**发射器（包含供养这座阵的那些）。
   共享池仍然只有一份：阵法付账会真的扣池子，玩家的读数也跟着降——不会双计。
3. `drawsEnvironment` 的含义变成"**在自有地面之外，再把阵地位置的环境灵气也算进请求量**"（扣的是同一个池子）。
   关闭时阵法只领地面发射器那一份。
4. 一格同时在两座阵的球里时，两座阵**各领一份**（各自按自己那份 ground 申请，池子决定谁拿到多少）。

## 4. 删掉的东西

| 文件 | 删除 |
| --- | --- |
| `runtime/world/FormationAbsorption.java` | 整个删除（`Sources` / `absorbedFor` / `environmentSupply` 三个出口都不再有意义） |
| `runtime/world/BlockAuraService.java` | `absorption(...)`、`walk(...)`、`Sources`；`rebuild` 只剩聚合；`sources(...)` 不再过滤被吸收的方块；新增 `groundInSphere(...)` |
| `attachment/AuraChunkAttachment.java` | `absorbedAura` 字段、`absorbedFor(...)`、`setAbsorbedAura(...)` |
| `runtime/formation/FormationWorldService.java` | `invalidateAura(...)` 及其两个调用点（立/撤阵不再标脏任何区块） |
| `runtime/formation/FormationWorldTicker.java` | `supply(...)` 与 `combine(...)`；`chargeUpkeep` 改用 `takeUpkeep` |
| `runtime/cultivation/AuraDistributionService.java` | 旧 `reserve` 的"玩家只"形状 → 泛化成消费者；新增 `takeUpkeep` / `projectedSupply` |

`/formation upkeep` 现在用 `projectedSupply`（不参与竞争的"场地本身有多少"）来算"还欠多少"，
它是估计值而不是本期的实际分配。

## 5. 代价与已知缺口

- **每 period 每阵一次地面扫描**：覆盖到的区块数 × section 数（每段 2 次距离比较）＋ 球面段的格子。
  半径 128 ≈ 289 区块 × 24 段 ≈ 7000 次 O(1) 判断 / 20 tick，可接受；但一座半径极大的阵仍是这条链路最贵的地方。
- **只算已加载区块**：未加载区块不贡献地面（合理，也不会为了它加载）。
- **一期中途激活的阵**：第一期累计到的是"激活后到期末"的那些 tick，所以第一期可能偏少，由储备/主人先垫。
- **没有维护费的阵**：`chargeUpkeep` 不会被调用，它的 credit 会一直累到 period 翻页被丢弃（不会泄漏，但白算）。
- **`RANDOM` 策略**：阵法按 tick 领 1/20，方差很大；想要稳定收益就写 `equal` / `realm_weighted`。
- **结算顺序**：`FormationWorldTicker` 与 `CultivationEventBridge` 都挂在 `LevelTickEvent.Post`，谁先跑由注册顺序决定；
  差的一拍最多影响 1/`PERIOD` 的量。

## 6. 验证

- `gradlew.bat compileJava compileTestModJava` 通过。
- **未实机、未跑 `runGameTestServer`**。建议补两条 GameTest：
  ① 一个阵法 + 一个修炼者同区块：两人拿到的量之和 ≤ 池子初始量；
  ② 净空区块（没有阵法）的 `block_aura_sections` 与"有阵法但没人修炼"时完全相同（证明阵法不再影响方块缓存）。
- 实机观察点：大阵立起来那一 tick 的耗时（现在只剩"每 20 tick 一次地面扫描"），以及站在阵里修炼的速度变化。
