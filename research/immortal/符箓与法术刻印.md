> 21.1，依赖作者自己的外部库 `hungteen.htlib:HTLib`。
> **阅读方式**：只读源码，**未编译、未启动游戏**。结论一律给 `文件:行号`；本仓库侧的对照结论另见 §9。
> **路径约定**：下文路径省略 `neoforge/src/main/java/hungteen/imm/` 前缀（如
`common/item/talisman/TalismanItem.java:106`）。
> **性质**：外部工程分析稿，不是本仓库的设计稿。**本仓库已有更完整的符箓实现**（`research/audit/talisman.md`
> ），本文的价值在于"法术 + 等级 + 触发时机刻在物品上"这条 Immortal 做过、本仓库还没做的线。

## 1. 结论摘要

- 这条线在 Immortal 里是**活的**（与傀儡/符文那套正相反）：7 张符、符咒绘制台、3 个物品组件、10 种触发条件都接线了。
- 它的"编程"口径是：**把「法术 + 等级 + 触发时机」三件套刻在物品上**，由事件侧扫描物品上的 `imm:spell_instances`
  决定何时发动。这正是本仓库 `research/33_Trigger系统设计.md` 对应、而"法器刻印/触发器"尚未落地的那一块。
- 它还多做了一件本仓库没有的事：**法术 → 物品的反向绑定**（`TalismanSpell.getTalismanItem(level)`），让"画符"
  这一步有明确产出（黄纸 + 朱砂 → 对应符箓物品）。
- 但它的**校验是漏的**：不校验是否已学、不校验境界、`requireQiRoots()/requireElements()` 只用于 tooltip、`checkActivate` 返回
  false 也照样扣灵消耗；法术定义**只能 Java 硬编码**（内存注册表，无数据包注册），唯一数据驱动的是秘籍学习条件。
- **术语陷阱**：Immortal 里 `talisman_pattern`（"符箓"）其实只是一个**旗帜图案物品**，和法术毫无关系（§2）。

## 3. 数据模型：三件套刻在物品上

`common/item/IMMDataComponents.java:30-44`（我本人读过原文）：

| 组件                    | 类型                    | 说明                                                                                         |
|-----------------------|-----------------------|--------------------------------------------------------------------------------------------|
| `imm:spell_instances` | `List<SpellInstance>` | **法术 + 触发时机**；`persistent(SpellInstance.CODEC_LIST)` + `networkSynchronized(STREAM_CODEC)` |
| `imm:spell_level`     | `POSITIVE_INT`        | 符箓自身的法术等级，缺省读作 1（`TalismanItem.java:110-112`），只有符箓物品用                                      |
| `imm:max_spell_slot`  | `POSITIVE_INT`        | 法器可刻印条数上限，由 `SpellManager.setSpellSlot` 惰性写入                                               |

```java
// common/codec/SpellInstance.java（原文）
public record SpellInstance(Spell spell, TriggerCondition condition) {
    public static final Codec<SpellInstance> CODEC = RecordCodecBuilder.create(instance -> instance.group(
            Spell.CODEC.fieldOf("spell").forGetter(SpellInstance::spell),
            TriggerConditions.registry().byNameCodec().fieldOf("condition").forGetter(SpellInstance::condition)
    ).apply(instance, SpellInstance::new));
}

// api/spell/Spell.java:12-17
public record Spell(SpellType spell, int level)     // level 是 Codec.INT，无范围校验
```

⇒ 物品上的形状是 `imm:spell_instances=[{spell:{spell:"imm:fireball",level:1},condition:"imm:right_click"}]`。**这是
Immortal 的"可编程"部分**：同一件法器，写不同 `condition` 就在不同时机自动放法术。

槽位上限口径：`ArtifactItem.getMaxSpellSlot` 默认 1、原版 `Tags.Items.ENCHANTABLES`/`TOOLS` 记 1（
`common/cultivation/SpellManager.java:360-378`），而 `TalismanItem` 覆写为 **0**（`TalismanItem.java:127-130`）——**符箓不能再被刻印
**。

## 5. 触发时机：10 种条件 + "扫哪些装备槽"

`common/cultivation/TriggerConditions.java:25-34`（我本人读过原文）：

| 条件            | 扫描的装备槽        | | 条件         | 扫描的装备槽  |
|---------------|---------------|-|------------|---------|
| `attack`      | `HANDS`       | | `shoot`    | `HANDS` |
| `toss`        | `EMPTY`（不看装备） | | `impact`   | `ARMOR` |
| `hurt`        | `ALL`         | | `cast`     | `ARMOR` |
| `break`       | `HANDS`       | | `cooldown` | `ARMOR` |
| `right_click` | `EMPTY`       | | `swing`    | `HANDS` |

`compatWith(living, stack)` 过一遍。**"触发时机自己声明要扫哪些槽"这个设计是本仓库可以直接借的形状**：它把"刻在哪个格子里"
变成了条件的一部分，而不是扫描端硬编码。运行期由 `SpellManager.activateSpell(entity, condition, stack, consumer)`（
`SpellManager.java:169-180`）在对应事件里扫物品、取**第一个匹配项**执行（"重复条件不能共存"的 TODO 还在
`InscriptionTableMenu:185`）。

## 6. 使用链路：蓄力型 `DurationTalismanItem`（当前唯一在用）

`common/item/talisman/DurationTalismanItem.java`：`use` → `startUsingItem`（默认 `stacksTo(16)`）→
`getUseDuration = getSpell().getUseDuration(stack, owner)`（默认 30t）→ `onUseTick` 服务端**每 tick 复查灵力**，不够就
`stopUsingItem()` → `finishUsingItem`（`:88-109`，原文）：

```java
Spell spell = new Spell(getSpell(), getSpellLevel(stack));
SpellCastContext context = new SpellCastContext(entity, this.spell);
context.setSendTip(true);
if (EventUtil.post(new ActivateSpellEvent.Pre(entity, spell, context))) return stack;  // 被取消 → 不消耗、不扣费
if (!EntityUtil.notConsume(entity)) stack.shrink(1);
getSpell().checkActivate(context);
QiManager.addQi(entity, -getQiCost(stack, entity));                 // ← 无条件扣
if (entity instanceof Player player) PlayerUtil.setCoolDown(player, stack.getItem(), getCoolDown(stack, player));
EventUtil.post(new ActivateSpellEvent.Post(entity, spell, context));
```

值得记的三点：

1. **`Pre` 事件可取消**且取消后完全不付代价（`api/event/ActivateSpellEvent.java`）——这是本仓库 `AbilityService` 的 `Pre`/
   `Post` 同款形状。
2. **扣费与 `checkActivate` 的返回值无关**：法术自身拒绝也照扣照消耗。而轮盘路径 `SpellManager.postActivateSpell`（
   `:190-218`）只在 success 时扣 —— **同模组两条路径口径不一致**，属于坑，不是设计。
3. **只校验灵力**：不校验"是否已学"、不校验境界；`TalismanSpell.requireQiRoots()/requireElements()` **只在 tooltip 里显示
   **（`TalismanItem:118-124` + `common/menu/tooltip/TalismanToolTip.java`），施法链路从不读它们。所以火弹符的"需要火元素"
   是纯提示。

### 6.1 `TalismanSpell` 只比普通法术多 4 个成员

`api/spell/TalismanSpell.java:15-42`（原文）：

```java
ItemStack getTalismanItem(int level);                                            // 法术 → 符箓物品（反向绑定）
default int getUseDuration(ItemStack stack, LivingEntity owner) { return 30; }   // 吟唱时长
default List<QiRootType> requireQiRoots() { return List.of(); }                  // 灵根要求（只用于提示）
```

7 个实现**全部忽略 `level` 形参**，但绘制台仍会写 `imm:spell_level`、显示名也据此加后缀（lang 只有
`misc.imm.talisman.level_1..3`）——即"等级"这条线是半成品。

### 6.2 实体型符箓

`common/cultivation/spell/SummonTalismanSpell.java:24-39` 负责召唤并写入 `owner`/`spellLevel`/`center`/`maxExistTick`
；实体基类 `common/entity/misc/talisman/RangeEffectTalismanEntity.java`：同步 `EXIST_TICK`/`SPELL_LEVEL`/`CENTER`（
`:27-29`），`maxExistTick` 只是普通字段**不同步**（`:30`），`tick()` 仅服务端，超时 `discard()`（`:44-55`），渲染物品取
`getSpell().getTalismanItem(getSpellLevel())`（`:72-74`）。两个子类：

- `SproutTalismanEntity`：`600 * scale` tick；每 10t、50% 概率在 ±4 格随机催熟（打乱候选后只对第一个成功者施骨粉等价效果）。
- `WoodHealingTalismanEntity`：`400 * scale` tick；每 20t 给 5 格内**除主人外**的生物加再生 100t/0 级 + 强木元素。
- ⚠️ `WoodHealingTalismanEntity.getSpell()` 返回 `SpellTypes.SPROUT`（`:47-49`，复制粘贴残留）⇒ 它渲染/掉落的物品错成萌芽符。

## 9. 与本仓库符箓的对照

本仓库的符箓（`data/Talisman.java`、`data/item/TalismanComponent.java`、`runtime/talisman/TalismanService.java`，审计见
`research/audit/talisman.md`）在**灌注与激发**上已经比 Immortal 完整得多：账单即容量、多种灵气分别计量、`FIRE`/`STORE`
模式、展示架也能激发、位置进公式与行为、原版冷却按堆记。**不要反向抄 Immortal**。值得拿的只有两点：

1. **「法术 + 等级 + 触发时机」刻在物品上、由事件扫描触发**：对应本仓库 `research/33_Trigger系统设计.md` 与尚未落地的"
   法器刻印/触发器"。落点建议：`Talisman` 定义里加可选 `trigger`（或独立法器刻印组件），把 Immortal 的 `TriggerCondition`（含"
   自己声明扫哪些装备槽"）映射到本仓库的 Trigger 信号 + 槽位范围；发动仍走现有 `AbilityService.useCarried`。
2. **法术 → 物品的反向绑定**（`getTalismanItem(level)`）：本仓库的法术是定义注册表、不生成物品，所以"
   学会火弹术之后能得到火弹符"这一步现在没有落点；若要"画符"玩法，这是要补的一环。Immortal
   把这个映射写在法术接口上（一个方法），比在物品侧登记"我对应哪个法术"更少一处同步。

明确不该借的：`spell_type` 这种"只能 Java 扩展"的内存注册表；`requireElements/requireQiRoots` 这种"只在 tooltip 生效"的假校验；
`finishUsingItem` 里"法术拒绝也照扣"的扣费口径。
