> **基准**：外部工程 `Immortal`（作者 HungTeen，模组 id `imm`，**不在本仓库内**），commit `fafda5d7efd4e7fded12ddd90e0b12ef428bae1a`（2025-06-24，即该仓库 HEAD），目标平台 Minecraft 1.21.1 / NeoForge 21.1，依赖作者自己的外部库 `hungteen.htlib:HTLib`。
> **阅读方式**：只读源码，**未编译、未启动游戏**。结论一律给 `文件:行号`；凡"未实机验证"的判断在文中单独标注。
> **路径约定**：下文路径省略 `neoforge/src/main/java/hungteen/imm/` 前缀（如 `common/entity/golem/GolemEntity.java:172`）。
> **性质**：外部工程分析稿，不是本仓库的设计稿。它回答"Immortal 这套是怎么写的、哪些能借、哪些不能借"；本仓库真要做傀儡时，落点设计另立新稿（新编号 `35_`）。

## 0. 先看这条：这套在 Immortal 自己的 HEAD 上是停的

Immortal 的 1.21 迁移用的是"注释大法"（提交 `e799f05 改为了多模块的架构，现在可以正常进游戏了（注释大法）`，2024-11-20）。`ItemStack.getOrCreateTag()` 在 1.21 已被 DataComponent 取代，全仓 13 处调用**全部被注释**——其中 8 处正是符文这套的存储层。结果是：**分层、菜单、屏幕、AI 都在，接线断了**。

所以本文的用法是：**当"设计方案阅读"看，不要当"可运行实现"看**。凡结论都区分写清"设计上是这样"与"现在是死的"。这也解释了为什么傀儡/符文的实质提交停在 2023-04，之后再没维护过。

## 1. 结论摘要

- 这是一套**"一排行为节点 + 共享记忆黑板"**的可编程实体 AI：玩家把「行为符文」插进傀儡的 9 个槽，**槽位号就是优先级**，节点之间通过原版 `Brain` 的 Memory 传值；节点还可以带 1 个**条件过滤槽**，由「指示符文」+ 逻辑门组合成一棵 `Predicate` 树。
- 分层是干净的、值得借的：**声明表（行为节点）/ 物品（符文）/ 装配台（三页菜单）/ 执行（Brain）**互不越界，新增一个行为节点只动一处声明 + 一个行为类。
- 不该照搬的是它的**实现介质**：行为节点是 Java 内存简单注册表（htlib `HTSimpleRegistry`），记忆前置写在 Java 里、且声明表与行为类里**各写了一份**；过滤条件是自造的 `IFilterRune` + NBT 递归树；装配台三页是三个独立的 `AbstractContainerMenu` + 换标签重新 `openMenu`。
- 与本仓库的落点：**模型可借、介质要换**——条件落到现有 `Condition`/`NumberProvider`，节点声明落到动态注册表（可数据包、可 KubeJS），记忆状态不要暴露 `MemoryModuleType`。
- **现在跑不起来**（设计在、数据层断开）：指示符文存不下值、门页算不出结果、绑定页过滤槽恒为不可放、符文工作台与傀儡背包的 4 个 screen 未注册、符文物品不在任何创造栏、`less`/`greater` 序列化 dispatch 写错。详见 §7。

## 3. 编程模型

### 3.1 槽序 = 优先级，记忆 = 黑板

`GolemEntity.updateRuneInventory()`（`common/entity/golem/GolemEntity.java:172-186`）是整套的心脏：

```java
this.memoryModules.clear();
this.behaviorModules.clear();
for (int i = 0; i < this.runeInventory.getContainerSize(); ++i) {
    ItemStack stack = runeInventory.getItem(i);
    if (stack.getItem() instanceof BehaviorRuneItem behaviorRuneItem) {
        GolemBehavior behavior = behaviorRuneItem.getRune().getBehaviorFactory().create(stack);
        this.behaviorModules.add(Pair.of(i, behavior));      // 槽位号 → 优先级
        behavior.entryCondition.forEach((memory, status) -> this.memoryModules.add(memory));
    }
}
this.refreshBrain();
```

`refreshBrain()`（`:79-83`）重建 `Brain`，`registerBehaviors()`（`:100-105`）把列表整体挂到 `Activity.CORE` 并 `setDefaultActivity(CORE)` + `useDefaultActivity()`；tick 走 `customServerAiStep → tickBrain`（`:68-77`）。也就是说：

- 玩家写下的"程序"是**一条按槽位排序的节点序列**，不是控制流图、不是脚本；节点之间靠 Memory 耦合（前一个节点写 `ATTACK_TARGET`，后一个节点读它）。
- `Pair.of(i, behavior)` 的 `i` 就是原版 `Brain` 的优先级语义，**槽位越小越先跑**。
- `memoryModules` 只用来告诉 `brainProvider()` 要注册哪些记忆类型（`:91-93`）；真正的准入条件来自行为类自己传给 `super(...)` 的那张 `entryCondition`。

### 3.2 记忆前置与时长（声明表里的那份"说明书"）

`BehaviorRunes` 给每个节点声明 `requireMemoryStatus()`，取值是 `VALUE_PRESENT`（必须存在）／`VALUE_ABSENT`（必须不存在）／`REGISTERED`（只要注册即可）。

> ⚠️ **这份声明只用于 tooltip**。全仓 `requireMemoryStatus()` 的消费者只有 `BehaviorRuneItem.getMemoryComponents()`（`common/item/runes/BehaviorRuneItem.java:114-120`）；运行期的准入条件实际由每个行为类构造器传给 `super(...)` 的第二参决定，**同一件事写了两份**，改一处不会同步另一处。

### 3.3 三种行为基类

| 基类 | 时长 | 用途 | 例子 |
| --- | --- | --- | --- |
| `GolemBehavior` | 各自 `(min,max)` | 持续型 | `move_to_target` 150–250t |
| `GolemOneShotBehavior` | `(0,0)` | 一次性动作 | `find_*_target`、`melee_attack` |
| `GolemSensorBehavior` | 单值（如 20） | 在 `start()` 里往 Memory 写观测结果 | `sense_nearest_livings`、`sense_hurt_by` |

节点自带 `getMeleeAttackCD()` / `getRangeAttackCD()` 之类的**实体侧参数**也在傀儡子类上：铁傀儡 20t、雪傀儡远程 30t、苦力怕傀儡 1200t（`IronGolem:92-95`、`SnowGolem:67-70`、`CreeperGolem:139-142`），近战节点用 CD>0 当闸门（`GolemMeleeAttack:30-33`），所以**铜傀儡（`getMeleeAttackCD()` 走基类返回 0）插近战符文不会攻击**。

## 5. 过滤条件树（指示符文 + 逻辑门）

### 5.1 5 种指示符文：右击世界把值刻进自己

| 物品 id | 物品类 | 刻值方式 | 数据类型 | 合成成本（青金石/红石） |
| --- | --- | --- | --- | --- |
| `item_filter_rune` | `ItemFilterRune` | 右击掉落物 | `Item` | 3 / 3 |
| `block_filter_rune` | `BlockFilterRune` | 右击方块 | `Block` | 3 / 3 |
| `entity_filter_rune` | `EntityFilterRune` | 右击实体 | `EntityType<?>` | 3 / 3 |
| `bool_filter_rune` | `BoolFilterRune` | 右击空气切换 | `Boolean` | 1 / 1 |
| `percent_filter_rune` | `PercentFilterRune` | 右击空气 +0.1（1.0→0.0） | `Float` | 2 / 2 |

共同基类 `common/item/runes/filter/FilterRuneItem.java`：`getCodec()` 由子类给，`bind()` 只在"未绑定"时写入并给 10t 物品冷却，已绑定则提示 `info.imm.rune_already_bind`（`:60-67`）。数值型只有 `PercentFilterRune.isNumberData()=true`。

### 5.2 6 个逻辑门（不是物品，是类型）

`common/cultivation/rune/filter/FilterRuneTypes.java:19-25`：

| 类型 | 语义 | 最少/最多输入 | 基础类型 | 只吃数值 |
| --- | --- | --- | --- | --- |
| `and` | 全部满足 | 2 / ∞ | 否 | 否 |
| `or` | 任一满足 | 2 / ∞ | 否 | 否 |
| `not` | 取反 | 1 / 1 | 否 | 否 |
| `equal` | 相等 | 1 / 1 | 是 | 否 |
| `less` | 比目标小 | 1 / 1 | 是 | 是 |
| `greater` | 比目标大 | 1 / 1 | 是 | 是 |

- 数据形状是**递归的**：`BaseFilterRune.Info(Item item, CompoundTag tag)`（`:126-131`）把"哪枚指示符文 + 它的封装值"记下来，`warp/unWarp` 多套一层 `nbt` 键好让值可以是任意 Tag；`ListGateRune.Info(Item item, List<IFilterRune> filters)`（`ListGateRune:41-46`）自引用 `FilterRuneTypes.getCodec()`，于是 `and`/`or` 的入参本身可以是另一棵树。
- 编译成谓词在 `IFilterRune.getPredicate(FilterRuneItem<?>, Predicate<T> 默认值)`：`BaseFilterRune`（`:38-59`）用**反射读物品类的泛型实参**决定 `T`，再把"写下来的值"和"待判定的值"交给 `check(target, current)`；`AndGateRune:38-40` 就是 `filters.stream().allMatch(...)`。
- 判定时 `behaviorRune.getFilterItems().get(id).get()` 取的是**该槽位允许的指示符文物品**，用它去解自己那份数据（`GolemBehavior:45-51`）。

## 6. 傀儡侧

- 右键傀儡开 9 格符文界面（`GolemEntity.mobInteract:140-157`，`GolemInventoryMenu`）；`GolemRuneContainer.getMaxStackSize()=1`（`:297-300`），一个槽一颗符文。四种傀儡 `getRuneInventorySize()` **都返回 9**（`IronGolem:87-90`、`SnowGolem:62-66`、`CreeperGolem:159-162`、`CopperGolem:37-40`）。

## 8. 对本仓库的落点（借什么、不借什么）

**可借的模型**（三条，与 Immortal 的实现介质无关）：

1. **"槽序即优先级 + 共享状态黑板"**：比"动作树"简单、玩家一眼能解释，而且天然对应"给傀儡插卡"这种物品化编程。
2. **"节点声明 + 过滤槽"**：节点自己声明需要几个条件输入，装配台据此灰显槽位（`Slot#isActive`），玩家不会插错位置。
3. **条件树递归到物品上**：指示符文先"右击世界刻一个值"，再用逻辑门组合成树，最后挂到节点的一个槽上——**三步都在物品上完成、不写存档外的状态**。

**必须换掉的介质**：

| Immortal 的做法 | 本仓库应改成 | 理由 |
| --- | --- | --- |
| 行为节点 = htlib 内存简单注册表 + Java 工厂 | 动态注册表（可数据包） | 本仓库内容不进本体（`AGENTS.md` §1.9），且要能被 KubeJS/数据包扩展 |
| 条件 = 自造 `IFilterRune` + `BaseFilterRune.Info` NBT 树 | 现有 `Condition` + `NumberProvider` | 已经有一套，别再造第二套（`AGENTS.md` §4"元素相关规则只有一份实现"同理） |
| 准入条件写在 `MemoryModuleType` + `MemoryStatus` 上 | 抽象成"读黑板某键 = 某状态"的通用形状，再按需适配原版 `Brain` | `MemoryModuleType` 是原版枚举，数据包表达不了；直接采用会把扩展锁死 |
| 三页各是一个 `AbstractContainerMenu`，换页 `openMenu` | 一套 `Menu` + 页签状态，或让装配台走现有工作台会话 | 换页重开菜单会丢槽内容、每页都要一份 `stillUsed`/`quickMoveStack`（Immortal 三页各抄了一份 50 行的 `quickMoveStack`） |
| 成本契约 `ICraftableRune` | 现有 `Cost`/配方类型 | 本仓库已有资源成本模型 |

**两个待拍板的分叉**（决定将来 `35_` 怎么写）：

- **A. 程序形状**：①槽序节点序列（Immortal 这套，简单、可解释、可物品化）；②带条件的动作树/数据包行为图（表达力强，但要新注册表 + 运行器 + 校验）。
- **B. 执行基座**：①直接复用原版 `Brain`（做得快，但节点受 Memory 枚举限制、AI 调试难度高）；②自建"每 tick 求值 + 状态机"的小运行器（可控、可数据包化，但要自己处理寻路/目标选择的会话与冷却，工作量大）。
