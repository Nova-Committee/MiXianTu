## 一、共享数据契约

### 药性、药材和药龄

新增 `mxt:medicinal_property`（`data/alchemy/MedicinalProperty`），只有 `name` / `description`，实现 `NamedDefinition`；它不是 Element、Aura 或 Resource。

重整 `mxt:spirit_herb`：

|字段|规则|
|---|---|
|`items` / `quality` / `element_tags` / `material_tags`|保留绑定、品质、分类语义；首条匹配生效，不累加多个定义|
|`name` / `description`|既有自动名字键|
|`default_age`|非负整数，默认 0，替代旧 `age`|
|`main_effects` / `auxiliary_effects`|药性 Holder → NumberProvider；默认空；角色下每件药力|
|`catalyst_power`|非负 NumberProvider，默认 0|
|`thermal_bias`|有限 [-1,1]，默认 0|
|`growth`|可选培育配置；省略时可入药但不可种植|

`CODEC` 改为 Holder codec，`DIRECT_CODEC` 为定义 codec。新增持久、网络同步组件 `mxt:herb_age`；无组件读 `default_age`，背包、容器、掉落物不增龄。不同年龄遵循原版组件相等堆叠，不平均、不刷新。

`SpiritHerbService` 接收 Provider，统一解析 Holder、年龄、角色药力；公式局部变量 `herb_age`。年龄增益仅由公式表达，管线不再乘一次。直接 Holder 入口过滤 `mxt:disabled`。

### 炉型

新增 `mxt:alchemy_furnace` 数据包表，定义实现 `NamedDefinition`：

- `quality` 必填 ItemQuality Holder；不新增数字炉阶，不从品质名称或链索引推导能力。
- `main_slots` 1–2，`auxiliary_slots` 0–2，药引固定 1；`capacity` 1–320。
- `max_temperature` / `heating_per_tick` / `cooling_per_tick` 有限正值。
- `aura_capacity` 按 Aura Holder 分项的正整数银行容量。
- `heating_costs` 必填非空 Cost[]，仅 aura；所需 Aura 必须有容量，一周期账单必须能装下。动态公式在 Level 上下文求值。

同名物品组件保存炉型 Holder。BE 单件 `furnaceItem` 保存炉型和显式品质等物品组件，不再保存一份可漂移的品质。放置、存档、同步、拆回保留该快照；炉体不携带库存、银行、热量或批次。

### 唯一炼丹配方

保留 `recipe/AlchemyRecipe` 与 `mxt:alchemy` Recipe 类型，删除 `data/alchemy/AlchemyRecipe` 复制层、旧 ID 多重集、`inputs`、`minimum_furnace_tier` 和裸 ID 输出。

|字段|规则|
|---|---|
|`main_requirements`|非空，药性 Holder → 正药力阈值|
|`auxiliary_requirements`|同形，可空|
|`catalyst_requirement`|正调和阈值|
|`balance_tolerance`|[0,1]，默认 0|
|`target_temperature` / `temperature_tolerance`|有限非负 NumberProvider|
|`duration`|有限正 NumberProvider，tick|
|`max_bad_ticks`|非负整数，默认 0|
|`minimum_aura`|既有环境门槛，不是银行消耗|
|`success_outputs` / `failure_outputs`|ItemStackTemplate[]，分别 1–4 / 0–4 项，每项装得进一个输出格|
|成功/失败 EntityAction、BlockAction|保留，一次结算执行|
|`guide`|可选角色化示例，最多 2 主 / 2 辅 / 1 引，只展示不匹配|

新定义严格校验有限性、范围、非空、引用和列表容量；药性与消耗不得使用静默丢坏条目的容错集合。未知旧键继续遵循仓库现有 Codec 口径，不新增未知键框架。

## 二、配伍判定

`AlchemyMixture` / `AlchemyResolver` 是预览、`Recipe.matches`、开炉的唯一判定；输入保留五个角色格、空格位置和实际件数，不展开重复 ID 列表。

主/辅分别聚合对应药性；药引仅计 catalyst_power。材料 i 数量 n、所选角色每件总药力 p、寒热 b：

`balance = Σ(n × p × b) / Σ(n × p)`。

分母必须正，零药力材料不能放对应角色。同角色换格、拆堆、合堆不改变结果；换角色重算。要求全部阈值满足、无额外非零药性、调和达标、`abs(balance) <= balance_tolerance`。过量已要求药性允许但全部消耗，不返还、不增产、不升品。

一个匹配可自动确定，多解必须选目标，不取 RecipeManager 首条。指引不能覆盖真实判定。不匹配拒绝开炉，服务端重新读取实际库存。有效时长为 `声明时长 / 最低有效原料炼丹修正`，最少 1 tick；原料 alchemy_modifier 仅影响时长，炉体品质修正不叠乘。

测试例：A 主3热1、B 主6热1、C 辅3寒-1、D 引1平0，要求主6辅6引1且完全配平；2A+2C+D、B+2C+D 等效，百年A经公式主6也等效。

## 三、丹炉状态与事务

迁移工位接口至 `api/AlchemyWorkstation`；仅实际 Container、状态、位置、炉型、银行、`furnaceItem()` 和变更通知。唯一开炉 `start(ServerPlayer, station, @Nullable ResourceKey<Recipe<?>> selected)`；唯一 tick 有 ServerLevel 与 BlockPos。不保留绕过环境校验重载。

物理槽 2主、2辅、1引、4输出；低规格禁用格不可投料，运行锁输入，输出只取。漏斗仅从下方提输出，不自动投料或开炉。

状态 `IDLE → WARMING → RUNNING → READY → IDLE`：

1. 查有效品质及使用条件、炉型、真实库存、配伍、环境、设温、工艺数值、输出容量，再发可取消 Pre。同工位 ThreadLocal 重入守卫。
2. 回调后核对库存未变；主线程清空全部已用输入，建立冻结批次。拒绝不扣药不扣气。State 不持有第二份可领取输入。
3. 可达温区与配方容差须相交；初始设温必须在配方容差内。温度达到范围才从预热进入炼制。
4. RUNNING 每个加载 tick 推进一步；越界累计 badTicks，超过 max_bad_ticks 固定失败，回温不洗失败。
5. 完成只生成一次最多 4 项待输出，READY 等四格可整体接受才原子出货，不丢物、不掉地、不再付款。
6. 出货后先标记结算，再 Post、方块行为、原在线操作者行为和成功 criterion 各一次。离线不阻塞出货、不补发、不转给旁观者。
7. 终止走一次失败结果；拆除只掉单件炉体、真实库存、已生成待输出。活动输入已经消耗不返还，不额外生丹。普通拆除、爆炸、替换共用掉落出口，气与热消散。

冻结快照保存原 recipe key、配方内容、求值工艺与产物、操作者 UUID、混合物摘要、阶段/剩余 tick/badTicks、温度/设温/poweredTicks、待输出。`/reload` 不改活动工艺；卸载/停服不推进、不追赶。持久状态可选字段宽容读。

### 品质与供能

`ItemQualityService.definitionDefault` 在法器/符箓/功法后读炉型默认品质，外层显式 item_quality 与锻造结果优先级不变。开炉无有效品质返回 `FURNACE_QUALITY`，条件拒绝沿用品质原因。Tooltip/Picker/界面共用品质解析与 coloredName。品质升级只改组件、不切换炉型；换型必须取得对应炉型。

BE 实现 AuraAccess，沿用 SpiritBurstEntity.insert。炉内银行和环境灵气分开；`alchemy_env_bonus` 只顶环境门槛、不代付燃料。`CostContext.bank(..., RECIPE)` 和 CostTransaction 是唯一付款；每 20 个有加热需求的活跃 tick 支付一次，记 poweredTicks。预热/炼制/维温耗能，完成/终止/等输出不新付款；已付周期不退款。供能时按速率接近设温，超过设温冷却，不越过设温；断供冷却至0。设温有限且 0..max，可运行中调整。

### 界面与协议

原版 Menu/Screen，不引入 LDLib2。展示炉型/有效品质、角色格、药性对照/不足/冲突/过量、丹方示例、温度设定与实温、供能/进度、开炉/终止、输出和背包；用文字说明不可用原因。无内容包不伪造默认炉型。

一个 C2S 动作协议处理分页/选择/设温/开炉/终止，服务端从当前 Menu 找 BE，校验 containerId、距离、状态，不信任客户端坐标/产物/药力。S2C 专用快照传真 double/long，不塞 signed-short DataSlot；变更才发，连续读数最多每5tick。丹方按ID排序每页8条，服务端提供，专用服也可用。原生 openMenu，客户端 handler 与专用服 codec 注册分离。

资源包括鼎形模型、匹配碰撞、开火状态、blockstate/item model/贴图/掉落表与双语键，不用占位方块或缺失纹理。

### 多方块追加合同

- 固定 3×3×3 中空壳体：局部坐标 `(1,1,0)` 是前侧中层 `alchemy_furnace` 控制器，`(1,1,1)` 留空气，其余 25 格为 `alchemy_furnace_casing`。水平朝向由控制器决定。可用能力仍仅来自炉型定义，不新加一套数字炉阶或按结构体积隐式倍率。
- 控制器是库存、炉体快照、供能银行、工艺状态唯一所有者；完整结构才可开炉，缺失或冲突位置经服务端快照提示。不强载未加载区块，不允许两座炉认领同一炉体方块。
- 完成搭建后自动检查成型；组成方块被替换/破坏时通知控制器失效，周期检查兜住区块加载边界。结构中断使活动批次一次性走失败结果并停止供火，不返还原料；幸存控制器仍可取输出。只缺结构而未开炉时不扣任何材料或灵气。
- 成型炉体交互路由同一个控制器，灵气发射入口为前侧控制器。拆一块炉壳只掉那一块壳并解除其余壳的成型状态，不复制控制器或库存；破坏控制器走原有单次真实库存/待输出掉落出口。
- 控制器状态 `facing` / `formed` / `lit`；炉壳 `facing` / `part` / `lit`，`part=0` 未成型，成型为 `x+3*z+9*y+1`，中心与控制器格不放炉壳。该编号是模型拆分坐标，不是内容品级。
- Blockbench 建整座鼎形外观，再沿16单位格网分为各方块模型；每格碰撞体按对应可见几何取并集，不用大模型配单格碰撞。未成型炉壳是普通青铜构件，控制器显示小型炉芯；成型后显示整座鼎。三足、炉耳、炉盖及冷热炉口材质均保留。
- 验收额外覆盖四个朝向、逐格缺失/空气阻挡/共享结构拒绝、断结构不续费与一次失败、拆壳不复制炉体、区块未加载不强载、每格模型/碰撞与出入/右键路由一致。

## 四、灵田生命周期

`spirit_herb_plot` 是低矮土床，一格一株，原生交互，无GUI。growth：`seeds` 非空 ItemMatcher；`mature_age` / `max_age` 正整数且后者不小于前者；`growth_rate` 每20加载tick非负 NumberProvider；`condition` 既有 BlockCondition 默认真；`costs` 默认空、仅 aura；`harvest` 必填非空 ItemStackTemplate 且能解析回本草药；`texture` 必填交叉草叶纹理。

播种校验权限/空位后扣1种苗，保存定义 Holder、原单件种苗、浮点进度/周期余数，从0岁开始。每20加载tick先看定义启用、上限、环境和增长量，再从共享环境 AuraPool 用 `HERB_GROWTH` 事务付款，成功才长。增长 `growth_rate × max(0,1+spirit_plant_bonus)`，加成有限且 ≥-1，由管线仅乘一次。缺气/条件失败暂停不死苗不部分扣款；不需要玩家在线，不追赶卸载时间；到 max 停止花费。

空手右键未成熟显示药龄/要求/暂停原因；成熟原子清空，产物按模板并写 floor(age)，返原种苗1，背包余物仅掉一次。潜行拔除只回种苗；破坏成熟按采收，未熟回苗；停用/失效仍可回苗。药龄不自动升品质。删除旧顶层 growth_rate/drop_chance 和无消费者 natural_spawn_herb，野生获取交给原版世界生成/战利品/内容包。

Renderer 按26.1.2约定画两张交叉叶面，成长比例改变大小，播种/阶段/采收推送客户端，不只 setChanged。

## 五、丹药消费与排毒

扩展既有 pill_binding，不新增定义表。`name` / `description`，`items` 默认空，`max_uses` 可选正整数，`cooldown` 非负 NumberProvider 默认0；Holder CODEC / DIRECT_CODEC。通用可消费 `mxt:pill` + 同名 Holder 组件；显式组件优先，无效/停用拒用不回退 ItemMatcher。Item 仅原版消费动作/名称/Tooltip，扣物和容器交给 consumable，药效只有 ItemBindingService → PillService 一条。

`PillUsageAttachment` 按 PillBinding Holder 保存次数和冷却到期主世界 gameTime，保存同步并死亡复制；次数与丹毒不因重登/换维度/死亡清零。离线时服务器仍运行则冷却到期；耐药次数不重置。

Start/Tick 走统一 PillService.check（条件、品质、次数、冷却）。Finish 不再用吃完后饱食/生命条件拒掉已消费的药，也不承担取消原版效果。一次消费登记一次次数/冷却，重入守卫内按通用物品行为 → on_consume → 丹毒增量 → 达阈值 on_overdose → toxicity_after_overdose。过量条件仍 `累计 >= threshold`，不默认禁止消费。

新增实体条件/公式变量 `mxt:pill_toxicity`，行为 `mxt:modify_pill_toxicity` 沿 add/set，负add排毒，下限0，统一 PillService 写入口，只读 getExistingData。配置炼丹页 `toxicity_decay_per_second` 有限非负、默认0；每累计20实体活跃tick扣一次，仅处理已有非零丹毒附件、保存周期余数；离线不排毒、不为所有实体创建空附件。排毒不清次数，品质不额外放大药效。

## 七、验收

集中运行 `gradlew.bat compileJava compileTestModJava processTestModResources --console=plain`；检查两侧语言键、资源闭包和定义边界。仓库无JUnit，沿用真实世界/BE/容器探针 `/mxt_test alchemy|herb|pill`，每腿精确 actual/expected 和总计。

覆盖：替代/拆堆/角色/百年药龄；不足/额外药性/寒热/多解拒绝不扣款；容量/禁格/不可达温度；非数字品质、使用条件、显式覆写放置存档拆回、只换品质不换能力；环境与银行分离/真实灵气注入/整组周期付款；预热不判废、max_bad_ticks=2第三次固定失败；全数量扣一次、组件产物、READY满槽等待；Pre取消、Post/行为/criterion一次及离线操作者；各阶段存档与reload冻结；终止/破坏单次掉落；种植权限、成长2×1.5四周期12岁、暂停不扣、满龄停费、回苗/满包/重种0岁；原消费Start/Tick拒绝、Finish一次；次数2/冷却20边界、25×4到100后20、排毒到0但次数不退、自然排毒20活跃tick且默认0。

**启动 runTestClient / runTestServer 必须另外获准，本设计批准不等于运行许可。** 获准后核对专用服类加载，完成播种→采收→配伍→注气→开炉→取丹→服用→排毒，验证无包/有包、长中文、GUI缩放2/3/4、Shift点击、运行改温、重开、多人、旧请求、专用服指引，记录截图与外观更新。未获许可只能报告编译/静态检查与探针未实跑，不能把它们当视觉或运行证据。
