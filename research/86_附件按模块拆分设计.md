# 86 附件按模块拆分设计

**状态：已落地（仅编译验证，探针未实跑）。** 2026-10-11。用户要求："重新看一下所有 attachment，能不能重新排一下。
最好按照模块分 attachment，模块划分看 readme"；我第一版方案是**把附件文件搬进各自的模块包、统一改名
`*.Attachment`**，用户当即纠正方向：

> 有两个点：1.所有 attachment 都是附件数据模型，都放 attachment 包是没问题的，主要是拆分和合并问题，比如
> SpiritIdentityAttachment 里面负责了至少三个模块

随后追加："B，然后不用考虑数据迁移，只要用 `lenientOptionalFieldOf` 保证不崩溃就行"。

**上一版方案（搬包 + 改名）全部作废：0 处移动、0 处改名，`attachment/` 包名与每个类的名字都不动。** 本次做的
只有**拆分**。

## 1. 判据：什么时候该拆

不是"有几个模块读它"。`ResourceHolderAttachment` 被二十多个模块读，它是**一个东西**（数值账本），拆了反而
是错的。该拆的判据是**这些字段属不属于同一件事**，三条证据：

1. **不同的模块拥有这些字段**（写入口分属不同服务）；
2. **生命周期不同**——谁能清它、什么时候清，各自一条；
3. **转世配置里有各自独立的开关**。

反过来，**属于同一件事的字段哪怕跨模块读也必须留在一起**：`technique_levels` 与 `learned_techniques` 必须在
同一个附件里，因为 `ProgressionHolder.retainOnly(learnedTechniques)` 是"没学过的功法不该留层数记录"这条
不变量的实现，拆开就没有一处能同时看到两边。

## 2. 拆出来的形状

`SpiritIdentityAttachment` 一个类负责了三个模块，`SpiritStatsAttachment` 负责了两个：

| 原字段 | 归属模块（README 模块表） | 落点 |
| --- | --- | --- |
| `spirit_roots` / `physiques` / `disabled_spirit_roots` / `disabled_physiques` | 灵根与体质 | **留在 `SpiritIdentityAttachment`**（名字不变） |
| `learned_techniques` / `technique_levels` | 功法 | 新 `TechniqueAttachment` |
| `minor_stage_records` | 修炼与境界 | 新 `MinorStageAttachment` |
| `lifespan_remaining` / `lifespan_total` | 修炼与境界（寿元） | 新 `LifespanAttachment` |
| `soul`（`karma` / `heart_demon` / `strength` / `sense_range`） | 灵气系统（魂魄） | 新 `SoulStatsAttachment`（四个键平铺到顶层） |

`soul` 那四个数**目前没有任何读取方**，只有转世的 `keepSoul` 开关会调 `resetSoul()`。它仍然要单独成一份：
保留 `keep_soul` 这个**面向玩家的配置键**（配置不是能悄悄删的东西），而四个数的归属与寿元账本无关。

**为什么叫 `SoulStatsAttachment` 而不是 `SoulAttachment`**：后者已被"死后魂魄形态"那份占用。

注册 id：`spirit_identity` 保持不变；`spirit_stats` 注销，新增 `technique` / `minor_stages` / `lifespan` /
`soul_stats`，五份都走 `entity(...)`（存档 + 同步 + `copyOnDeath`）。

**各字段的 Codec 键一个都没改**（`spirit_roots`、`learned_techniques`、`technique_levels`、`minor_stage_records`、
`lifespan_remaining`、`lifespan_total`），只是搬到了新的顶层附件键之下。

`soul` 那一组是例外：拆分时顺带把那层 1:1 的包装 record 展开了，所以 `soul_stats` 的四个键
（`karma` / `heart_demon` / `strength` / `sense_range`）现在是**顶层键**，不再是 `soul` 之下的一层——
附件里正好一个它、它自己也没有任何行为，这层包装是多余的（`LifespanAttachment` 从一开始就是平铺的）。

## 3. 存档形状（破坏性，用户已接受）

老存档 `{"spirit_identity": {...7 个字段...}, "spirit_stats": {...}}` 里那四个字段/两份附件不再被读取——
新 id 是分开的顶层键，`RecordCodecBuilder` 对未知字段静默丢弃（既定口径，见 `AGENTS.md` §4）。所以
**老存档的功法、层数、子境界记录、寿元账本、魂魄四数会丢**，不写迁移工具、不做兼容读取，靠
`lenientOptionalFieldOf` 保证**不崩**（缺字段取默认值），而不是保证读回来。

## 4. 拆的时候必须一起动的几处

- **`LifeSpanService.reincarnate`**：那条"转世重置清单"原本一行一个开关、全部打进两份附件。拆完以后**一个开关
  只能够到它自己模块的那份附件**——`clearMinorStages` → `MINOR_STAGES`，`keepTechniques` → `TECHNIQUE`，
  `keepSoul` → `SOUL_STATS`，`keepSpiritRoots` → `SPIRIT_IDENTITY`。这是本次拆分最实际的收益：以前任何一条
  开关都能清到别人的状态。
- **`CultivationHooks`**：一个对象同时实现 `Grants` / `Attributes` / `Owns`，拆完要读**三份**附件
  （`SPIRIT_IDENTITY` 拿根与体质、`TECHNIQUE` 拿功法与层数、`MINOR_STAGES` 拿子境界）。它仍然只注册一次。
- **`CultivationAffinity.multiplier`**：它同时读 `activeSpiritRoots()`（灵根侧）与 `learnedTechniques()`
  （功法侧），因此签名从一份附件变成两份，`TechniqueAttachment` 那个参数可空（`null` = 没有功法）。
- **`MxtKubeJsApi`**：私有的 `identity(Entity)` 只服务灵根/体质了；功法那几个读法（`techniques` /
  `hasTechnique` / `learnTechnique` / `forgetTechnique` / `progressionLevel`）改走另一个私有 helper
  `techniqueState(Entity)`。
- **事件载荷**：`TechniqueLearnEvent.spirit` 改类型为 `TechniqueAttachment`（名字不动）；两个寿元事件的字段本来
  叫 `spirit`，现在装的是一本寿元账本，所以**私有字段改名 `ledger`**，但**公开访问器 `spirit()` 保持不动**——
  它是 KubeJS 事件表里写着的契约（文档站 `kubejs/api/events.md` 中英各一处），改名是另一件事，不在本次范围。

## 5. 顺手修掉的一个既有 bug

`CreatureSpiritAttachment` 的构造器直接把解码进来的 `ProgressionHolder` 收下（`this.profileLevels = profileLevels`），
而它的 Codec 给的是 `new ProgressionHolder<>()` 这个**每次解码共用的同一实例**：两份身体会共用一张 Map 互写。
`CreatureSpiritAttachment` 自己就 `override checkDirty()` 去标脏 holder，说明它本来就该是"持有并复制"的语义。
已改为 `new ProgressionHolder<>(profileLevels)`，与本次两个新附件的做法一致。

## 6. 顺带纠正 85 的一处过时描述

`85` §2.3 / §2.4 描述的 `ownedBy(ShouldSyncAttachment)` 形状**最终没有采用**：`ProgressionHolder` 里没有
`ownedBy`，也没有附件引用。今天的形状是**宿主附件自己 `override checkDirty()`**：

```java
@Override
public boolean checkDirty() {
    if (this.techniqueLevels.checkDirty()) this.markDirty();
    return super.checkDirty();
}
```

复制那条约束不变也更要紧：`lenientOptionalFieldOf` 把**同一个** default 实例交给每次解码，所以任何收下
`ProgressionHolder` 的附件都必须在构造器里复制（`ProgressionHolder(ProgressionHolder<T> source)`），
不能直接采用传进来的那份。已同步修正 `85` 的对应两节。

## 8. 审查过但**不**拆的附件

按第 1 节的三条判据过了一遍现存 26 份附件，其余都判为一份附件管一个模块：
