# 72 来源身份与模块钩子统一设计

> **基准**：工作区 `src/main`（HEAD `78115723` ＋ 工作树里未提交的 `audit/all.md` 修复）。
> **用户要求**："代码里面一堆 enum 变成了 Source，能不能把 Source 统一一下，不要每个人注册自己的，毕竟功能比较相似。"
> **范围**（用户拍板）：所有同骨架的注册点一起统一；只做骨架与身份，不改语义。

## 1. 现状：同一件事被写了三遍

`audit/all.md` 的 A01/A02 把"核心逐个认识业务模块"反过来变成"业务模块把来源交上来"，方向是对的，但**每个功能各造了一份注册表**，于是出现了六份同骨架的东西：

| 注册点 | 形状 | 谁注册 | 读的人 |
| --- | --- | --- | --- |
| `runtime/ability/AbilityGrantSources` | 按实体：`source id → ability` 差分 | `CultivationGrantSource` / `CreatureGrantSource` / `ContractGrantSource` | `AbilityGrantService.recalculate` |
| `runtime/ability/PassiveAttributeSources` | 按实体：`kind + 定义 → AttributeEntry[]` | `CultivationAttributeSource` | `PassiveAttributeService.entries` |
| `runtime/progression/ProgressionSources` | 按实体 → `Owner[]` | **写死的 `List.of(techniques, creatures)`**（唯一不注册的，反而不一致） | `ProgressionService` / `ProgressionDriver` / `ProgressionDamageMultiplier` / `ProgressionAdminService` / `ProgressionEntityCondition` |
| `runtime/hold/HoldLookup` | 按注册表 → `HoldBinding[]` | `TechniqueItemService` / `SpiritChargeService` / `ArtifactHoldService` | `HoldLookup.rebuild` |
| `runtime/trigger/TriggerRehydrators` | 按实体 → 重建钩子 | `AbilityEventBridge` / `CultivationTriggerService` / `CurseTriggerSubscriptions` | `TriggerRehydrators.rehydrate` |
| `runtime/EntityTickStages` | 按 tick 阶段 | `AbilityEventBridge` / `ResourceRegenStage` / `ProgressionTickStage` | `EntityTickStages.onEntityTick` |

三份"来源 id 的拼法"也是各写一套：`AbilitySources`（`equipment/` ＋ `curios_equipment` ＋ `grant/`）、`FormationSources.of`（`formation/`）、`PassiveAttributeService` 里的 `passive/`；`CurseEventBridge` 还把 `AbilitySources.equipment` 的拼法**抄了一遍**（`CurseEventBridge:134` 与 `AbilitySources:28` 逐字同形）。

启动侧因此有 9 个 `initialize()` 并排写在 `MiXianTu` 构造器里（`:31`–`:39`），其中 6 个是"静态块注册 + 空 `initialize()` 强制类初始化"：

```java
static { TriggerRehydrators.register(new TriggerRehydrator() { ... }); }

// Forces class initialization so the rehydrator is registered before the first server lifecycle event.
public static void initialize() {
}
```

（`AbilityEventBridge:57/75`、`CultivationTriggerService:27/45`、`CurseTriggerSubscriptions:34/54` 三处；`TechniqueItemService:80`、`SpiritChargeService:59`、`ArtifactHoldService:74` 是直接注册，不用静态块。）

**代价**：加一个新功能要挑一个注册表（并接受"它是哪一类"这个没有答案的问题）、每个注册表各带一个 `initialized` 标志与一份 `all()`、来源 id 的拼法散在四处、而"哪些模块在什么时候注册了什么"只能靠逐个 `initialize()` 反查。

## 2. 目标与边界

**做**：

1. **一个注册骨架**：`runtime/ModuleHooks`——`register(Class<T> capability, T hook)` ＋ `all(Class<T>)`，一个 `initialize()` 把全部模块的 `register()` 列成一份清单。**capability 接口本身就是键**，加一类钩子不再需要新注册表；一个对象可以同时注册在多个 capability 下。
2. **一份实体来源契约**：`runtime/EntitySources` 收三个 capability（`Grants` / `Attributes` / `Owns`）＋ `Owner` ＋ 两个读取助手，取代 `AbilityGrantSources` / `PassiveAttributeSources` / `ProgressionSources`。
3. **来源 id 一处造**：`runtime/Sources` 收全部**由框架生成**的来源 id（`equipment` / `CURIOS` / `grant` / `formation`）与两个**闭集**枚举（`Sources.Grant` 是 `grant/` 下的类目，`Sources.Declaration` 是 `passive/` 修饰符 id 里的类目）。取代 `AbilitySources` / `FormationSources`。
4. **每个模块一份 `Hooks`**：`CultivationHooks`（授予＋被动属性＋进度归属）、`CreatureHooks`（档案授予＋档案归属＋契约授予）取代 5 个小 provider 类。
5. **删掉"静态块 + 空 `initialize()`"**：注册全部改成显式 `register()`，由 `ModuleHooks.initialize()` 调用。

**不做**（逐条写明，避免下次被动摇）：

- **不动两条内容模组扩展点**：`WheelSourceTypes` / `WheelEntryKinds` 不是模块钩子，是给附属模组的开放注册（`first wins`、注册顺序＝分页顺序、`Codec` 按 id 回读）。它们保持自己的实现。
- **不动"按 id 查表"的注册表**：判据是"框架问的是**有哪些贡献者**，还是**这个 id 是什么**"。前者进 `ModuleHooks`，后者留在原地——`WheelSourceTypes` / `WheelEntryKinds`（id ↔ 对象，附属模组从自己的 setup 注册）、`ContractBehaviors`（命令 id ↔ 行为，被 `mxt:contract` 附件按 id 引用）、`InformationManager` / `HudManager` / `WheelMenuContent` / `MountRenderers`（客户端 id 派发）都属于后者。
- **`QualityService.carry` 特意留在原地**：它是"本体九个载体在前、附属模组的在后"的顺序，**靠 `QualityService` 的类加载**保证——附属模组调 `carry` 会先把本类初始化、本体那批先入列表。搬进 `ModuleHooks` 之后顺序变成"谁的构造器先跑谁在前"，而模组构造顺序不保证，这是**行为改变**，不做。
- **不动内容包自己写的 `source`**：`mxt:grant_ability` 动作与 `GrantAbilityLootFunction` 的 `source` 字段、`/ability grant` 与 KubeJS 的来源参数仍是**作者自由写的 `Identifier`**，`Sources` 只造框架自己那几条。
- **不改语义**：差分方向、`grant/` 前缀、`SourceLedger` 的"至少一个来源持有"、阵法"定义级 source + 实例计数"、`HoldLookup` 的 `priority` 排序与按物品缓存、`TriggerRehydrators` 的重入与失败清理，全部照旧。
- **不改任何对外 id 字符串**：`mxt:equipment/<槽>/<ns>/<path>`、`mxt:curios_equipment`、`mxt:grant/<类目>/<ns>/<path>`、`mxt:formation/<ns>/<path>`、`mxt:passive/<类目>/<来源 ns>/<来源 path>/<序号>/<原 modifier id>` 一字不动——老存档里的账本与属性修饰符仍能被正确释放（释放本来就按前缀/全量差分，形状不改则连"漂移"都不需要）。

## 3. 形状

```java
// runtime/ModuleHooks.java —— 唯一的注册骨架与唯一的启动口
public final class ModuleHooks {
    private static final Map<Class<?>, List<Object>> HOOKS = new LinkedHashMap<>();

    public static synchronized <T> void register(Class<T> capability, T hook) { ... }

    public static <T> List<T> all(Class<T> capability) { ... }

    // 这份清单是模块清单，不是业务规则：业务规则在各自的 register() 里。
    public static synchronized void initialize() {
        if (initialized) return;
        initialized = true;
        AbilityEventBridge.register();          // 7 个 tick 阶段 + 触发重建器
        CultivationHooks.register();            // 授予 / 被动属性 / 进度归属
        CreatureHooks.register();               // 档案授予 / 档案归属 / 契约授予
        CultivationTriggerService.register();   // 触发重建器
        CurseTriggerSubscriptions.register();   // 触发重建器
        TechniqueItemService.register();        // 长按声明
        SpiritChargeService.register();         // 长按声明
        ArtifactHoldService.register();         // 长按声明
        ResourceRegenStage.register();          // tick 阶段
        ProgressionTickStage.register();        // tick 阶段
    }
}
```

```java
// runtime/EntitySources.java —— "这个身体现在有哪些来源贡献"的唯一契约
public final class EntitySources {
    public interface Grants { void collect(LivingEntity entity, ProgressionAttachment progress, GrantSink sink); }
    public interface Attributes { void collect(LivingEntity entity, AttributeSink sink); }
    public interface Owns { List<Owner> held(Entity entity); }

    @FunctionalInterface public interface GrantSink { void want(Identifier source, Holder<Ability> ability); /* + 两个默认方法 */ }
    @FunctionalInterface public interface AttributeSink { void add(Sources.Declaration kind, Identifier source, List<AttributeEntry> values); }

    public record Owner(Identifier id, ProgressionOwner definition) { }

    public static List<Owner> heldBy(Entity entity) { ... }         // 原 ProgressionSources.heldBy
    public static Optional<Owner> held(Entity entity, Identifier owner) { ... }
}
```

```java
// runtime/Sources.java —— 框架自己造的来源 id 只有这一处
public final class Sources {
    public static final Identifier CURIOS = ...;                    // mxt:curios_equipment

    // grant/ 下的类目：闭集，框架自己的授予只可能是这几种
    public enum Grant { SPIRIT_ROOT("spirit_root"), PHYSIQUE("physique"), TECHNIQUE("technique"),
                        REALM_STAGE("realm_stage"), CREATURE("creature"), CONTRACT("contract") }
    // passive/ 修饰符 id 里的类目：闭集，"谁声明的这一条"
    public enum Declaration { ABILITY("ability"), REALM("realm"), TECHNIQUE("technique"), PHYSIQUE("physique") }

    public static Identifier equipment(EquipmentSlot slot, ItemStack stack);
    public static Identifier granted(Grant kind, Identifier content);      // mxt:grant/<类目>/<ns>/<path>
    public static Identifier formation(Identifier formation);              // mxt:formation/<ns>/<path>
    public static boolean isEquipment(Identifier source);
    public static boolean isGranted(Identifier source);
}
```

每个模块一份钩子类：

// runtime/cultivation/CultivationHooks.java —— 一个对象同时是三种来源
public final class CultivationHooks implements EntitySources.Grants, EntitySources.Attributes, EntitySources.Owns {
    public static void register() {
        CultivationHooks hooks = new CultivationHooks();
        ModuleHooks.register(EntitySources.Grants.class, hooks);
        ModuleHooks.register(EntitySources.Attributes.class, hooks);
        ModuleHooks.register(EntitySources.Owns.class, hooks);
    }
}

## 5. 落地记录

**同日一次落地**（用户看完现状表后拍板"顺带统一所有同骨架注册点"，没有分批）。

**新增三个中立类**：

- `runtime/ModuleHooks`：`register(Class<T> capability, T hook)` / `all(Class<T>)` / `initialize()`（唯一的模块清单，10 条）；
- `runtime/EntitySources`：`Grants` / `Attributes` / `Owns` 三个能力接口 ＋ `GrantSink` / `AttributeSink` ＋ `Owner` ＋ `heldBy` / `held`；
- `runtime/Sources`：`CURIOS` / `equipment` / `granted` / `formation` / `isEquipment` / `isGranted` ＋ `Grant` / `Declaration` 两个枚举。

**新增两份模块钩子**：`runtime/cultivation/CultivationHooks`（授予＋被动属性＋进度归属，三合一）、`runtime/creature/CreatureHooks`（档案授予＋档案归属，＋私有嵌套 `ContractGrants`）。

**删除九个类**：`ability/AbilityGrantSources`、`ability/PassiveAttributeSources`、`ability/AbilitySources`、`progression/ProgressionSources`、`formation/FormationSources`、`cultivation/CultivationGrantSource`、`cultivation/CultivationAttributeSource`、`creature/CreatureGrantSource`、`creature/ContractGrantSource`。

**改动的调用点**（都只换名字，语义不动）：

- `AbilityGrantService.recalculate` 问 `ModuleHooks.all(EntitySources.Grants.class)`，前缀判据换成 `Sources.isGranted`；
- `PassiveAttributeService.entries` 问 `EntitySources.Attributes`，`modifierId` 的 kind 由 `String` 换成 `Sources.Declaration`（拼出来的 id 一字未变）；
- 进度四处消费点（`ProgressionService` / `ProgressionDriver` / `ProgressionDamageMultiplier` / `ProgressionAdminService`）与实体条件 `ProgressionEntityCondition` 换 `EntitySources.heldBy` / `held`；
- `HoldLookup` / `TriggerRehydrators` / `EntityTickStages` 的内部列表换成 `ModuleHooks`，**对外方法一个没改**（`HoldLookup.hold` / `rebuild`、`TriggerRehydrators.rehydrate`、`EntityTickStages.register` / `onEntityTick`）；
- 六处注册入口：`AbilityEventBridge.register()`（原来的 `registerStages()` ＋ 静态块）、`CultivationTriggerService.register()`、`CurseTriggerSubscriptions.register()`、`TechniqueItemService.register()`、`SpiritChargeService.register()`、`ArtifactHoldService.register()`（后三个由 `initialize()` 改名）——**"静态块注册 ＋ 空 `initialize()` 强制类初始化"的写法全部消失**；
- `MiXianTu` 构造器里九个 `initialize()` → 一个 `ModuleHooks.initialize()`；
- `CurseEventBridge` 删掉自己那份 `equipment` 拼接与 `isEquipmentSource`，改用 `Sources`（诅咒侧把 Curios 当随身装备、技能侧把它当身体的一部分，这个差别写进了注释）；
- 轮盘三处（`WheelSources.handOnly`、`WheelSourceTypes` 的两个内置来源、`AbilityWheelEntry` 的"习得"判据）与阵法三处（`FormationActionRunner` / `FormationEntityActions` / `FormationWorldTicker`）换 `Sources`。

**验证**：`.\gradlew.bat compileJava compileTestModJava --console=plain` → `BUILD SUCCESSFUL in 18s`。**未实机**（房规第 4 条要求先问），所以"进游戏后授予 / 被动属性 / 轮盘 / 诅咒仍按老样子工作"目前只有静态依据：**所有 id 字符串与差分规则都没动**。

**落地时定的口径（与设计稿的差别）**：

1. `EntityTickStages` 的排序留在它自己手里：`ModuleHooks` 只回答"有哪些钩子"，顺序语义归使用者——所以阶段表在**首次服务端 tick** 惰性排一次（那时注册早已结束）。
2. `TriggerRehydrators` 不再按 module id 去重（原来是 `Map`，重复注册会打一条 warn）：现在注册只可能在唯一的 `initialize()` 里各发生一次；module id 仍用于日志与 `TriggerDispatcher.clearModule`。
3. `ModuleHooks.all(...)` 每次返回不可变拷贝。注册发生在模组构造期、读取发生在游戏线程（FML 的线程启动构成屏障），所以读侧不加锁。
4. `Sources.Grant` / `Sources.Declaration` 只承载**框架自己**的类目；内容包在动作 / 战利品函数里写的 `source` 不收窄（见 §2）。
5. `research/audit/依赖关系图.md` 与 `依赖关系总图.md` 只在文首加了过期标注，**图版没有按新形状重画**（26 张图版、逐节点重画是独立的一件事）。
