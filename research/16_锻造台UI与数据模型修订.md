# 锻造台 UI 与数据模型修订

> 本文是 [`06_锻造系统设计.md`](06_锻造系统设计.md) 的修订案，对应 2026-02 的 UI 定稿讨论。
> 与 `06` 冲突之处**以本文为准**；`06` 中未被本文推翻的部分（数值条规则、末尾序列规则、
> 最优步数算法、品质结算公式）继续有效。
>
> 记录目的：把"锻造台界面长什么样"和"为了支撑这个界面数据模型要怎么改"固定下来，
> 避免后续实现时反复推翻。

## 1. 结论速览

| # | 决定 |
| --- | --- |
| 1 | 输入改为**无序多材料**列表 |
| 2 | 新建锻造台方块 / 方块实体 / 菜单 / 界面（不含贴图） |
| 3 | 新增 `tool_binding`、`blueprint_binding` 两条数据包注册表 + 两个物品组件 |
| 4 | 同一个方块上的会话**全服共享**，多人可协作锻打 |
| 5 | **删除**"从主手取物品"的设计 |
| 6 | 客户端本地预测 + 服务端权威同步覆盖 |
| 7 | "预期结果" = 当前 value + 选中方法的 `value_delta`，**不显示可能产出**；品质留接口 —— **已实现**为值条上的黄色预测线 |
| 8 | **删除** `show_finish_pattern` 字段 |
| 9 | **要求**行的空位渲染屏障（barrier）图标，含 `N < 6` 两种情况；**当前**行不渲染占位符（没敲过的步就是不画） —— 无会话时两行都不画 |
| 10 | `quality_by_extra_steps` 的品质展示暂不实现，只留接口 |
| 11 | `ForgingMethod.display_icon` 由 `Identifier` 改为 `ItemStack` |
| 12 | 输出槽满 → 直接拒绝下一次锻打 |
| 13 | 失败唯一来源 = 蓝图定义的最大步数；未定义则永不失败 |
| 14 | 锻打按钮做限流 |
| 15 | 两个选择格都有**悬停 tooltip**：蓝图 = 材料清单（已备绿勾 / 缺少红叉，材料不足**不能开始**）；方法 = 名称 + `value_delta`（"数值影响"） |
| 16 | 蓝图取消 `allowed_methods` 的必填限制：可省略 / 可空 / 可写 `#标签`，**空即不限** |
| 17 | **自动结算**：值落入成功区间且末尾序列匹配时立即结束会话并产出结果。触发点 = 锻打后 / 开会话后 / 打开界面时 |
| 18 | 左下角加**取消**按钮；取消的代价走 `ForgingCancellation` 策略接口，默认"全部返还"，便于后续扩展 |

## 2. 界面布局定稿

### 2.1 整体结构

```
┌──────────────────────────────────────────────────────────────────┐
│ 锻造台                                                            │
│ ┌──────────┬───────────────────────────────────┬──────────────┐ │
│ │          │  ┌────┬────┬────┬────┬────┐       │              │ │
│ │ 蓝图      │  │    │    │    │    │    │       │   锻造方法    │ │
│ │ 列表      │  ├────┼────┼────┼────┼────┤       │   列表        │ │
│ │ (按钮)    │  │    │    │    │    │    │       │   (按钮)      │ │
│ │          │  ├────┼────┼────┼────┼────┤       │              │ │
│ │  可滚动   │  │    │    │    │    │    │  ┌──┐ │    可滚动     │ │
│ │          │  └────┴────┴────┴────┴────┘  │输│ │              │ │
│ │          │                               │出│ │              │ │
│ │          │                               └──┘ │              │ │
│ │          │                          [ 锻 打 ]  │              │ │
│ │          ├───────────────────────────────────┤ │              │ │
│ │          │        value 进度（仅显示）         │ │              │ │
│ │          ├───────────────────────────────────┤ │              │ │
│ │          │      最后 N 步（N 由蓝图决定）       │ │              │ │
│ └──────────┴───────────────────────────────────┴──────────────┘ │
│                       玩家物品栏                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 2.2 区域职责

| 区域 | 类型 | 内容 |
| --- | --- | --- |
| **蓝图列表**（左） | 切石机式滚动选择按钮，**3 列** | 列出**蓝图槽里那些蓝图物品所提供**的蓝图（槽位为空则列表为空）。点击即选中，选中只改本地高亮 |
| **物品放置区域**（中） | 容器槽位 | `5×3` 输入槽 + 右下外侧 `1` 个输出槽 + 输出槽下方 `锻打` 按钮 |
| **锻造方法列表**（右） | 切石机式滚动选择按钮，**3 列** | 列出当前选中蓝图的 `allowed_methods` ∩ 工具槽解锁的方式。蓝图未选或未声明该字段时不做限制，列表即工具并集。点击即选中 |
| **value 进度** | 纯渲染，无交互 | 值条：贴图画的凹槽 + **绿色目标块**（`target_min..target_max`）+ **灰色 0 线**（只要有刻度就画：会话中来自 plan，未开会话时来自选中蓝图的 `meter`）+ **红色当前值线** + **黄色预测线**（当前值 + 选中方法的 `value_delta`，未选方法则不画）。三条线比凹槽上下各出 2px |
| **最后 N 步** | 纯渲染 | 两列 6 格：左=**要求**（蓝图 `finish_pattern` 的**末 `N`** 项，其余格填屏障），右=**当前**（会话最近 `N` 步历史，没敲过的格**不画**）。悬停任一格显示该步方法的名称（高级提示框下另附注册表 ID）。无会话时两行连同标题一起不画 |
| **玩家物品栏** | 容器槽位 | 标准 `9×3` 主物品栏 + `9` 快捷栏 |

### 2.3 布局要点

- 左/右两侧**不再是物品槽**，全部是选择列表按钮。
- `蓝图`、`锻造方法`、`玩家物品栏` 三块**底边对齐**，视觉上等高。
- 中区内部是**垂直三段堆叠**：`物品放置区域` → `value 进度` → `最后 N 步`。
- 输出槽位于输入网格**右下外侧**，与网格第 3 行同高；`锻打` 按钮紧贴其下方。
- 具体像素坐标待贴图阶段确定；本文只固定**结构、槽位数量与相对位置**。

## 3. 数据模型修订

### 3.1 `forging_blueprint`

```jsonc
{
  "input": [                                    // 改动：无序多材料
    { "id": "minecraft:iron_ingot", "count": 3 },
    { "id": "minecraft:coal", "count": 1 }
  ],
  "allowed_methods": "#mxt:blade_methods",      // 改动：可省略/可空/可写标签；空即不限
  "meter_min": -10,
  "meter_max": 10,
  "target_min": 2,
  "target_max": 4,
  "finish_pattern": {                           // show_finish_pattern 已删除
    "steps": [ /* 恰好 6 项 */ ],
    "required_suffix_steps": 3
  },
  "max_steps": 32,                              // 改动：可选，见 3.5
  "quality_by_extra_steps": [
    { "max_extra_steps": 0,          "quality": "mxt:excellent" },
    { "max_extra_steps": 5,          "quality": "mxt:normal" },
    { "max_extra_steps": 2147483647, "quality": "mxt:rough" }
  ],
  "result": "minecraft:iron_sword",
  "complete_action": { "type": "mxt:no_op" },
  "fail_action":     { "type": "mxt:no_op" }
  // failure_settlement 随 3.5 一并简化或删除，见待定项 T3
}
```

| 字段 | 变化 | 说明 |
| --- | --- | --- |
| `input` | **改** `Identifier` → `List<ForgingMaterial>`（`{id, count}`） | 无序匹配，见 3.2 |
| `finish_pattern.show_finish_pattern` | **删** | 该字段此前全代码库无消费方，直接移除 |
| `max_steps` | **改** 默认必填 → 可选 | 语义见 3.5 |
| `result` / `complete_action` / `fail_action` | 不变 | 沿用现实现 |
| `quality_by_extra_steps` | 不变 | 品质展示留接口，见 §7 |

### 3.2 输入匹配规则（无序）

- `input` 是**材料清单**（`ForgingMaterial` = `Identifier id` + `int count`），**顺序无关**：服务端按 `(物品, 数量)` 做多重集合匹配。
- 数据包校验期拒绝重复条目（同一物品出现两次直接报错禁用该蓝图）、空列表、超过 15 项，以及无法解析的物品 ID。
- 匹配成功后**原子扣除**全部材料；任一材料不足则整次锻打被拒绝，**不扣任何资源、不计步数、不写历史**（沿用 `06` §数值条规则的最后一条）。
- 输入槽允许玩家任意摆放（无序），匹配只看总数。
- 输入槽的**上限是 15 格**，若 `input` 条目数 > 15，数据包校验期直接报错。
- 选中蓝图后，输入槽只接受该蓝图声明的材料；未选蓝图时输入槽开放，便于先装料后选图。
- 选中蓝图后，客户端可为"尚缺的材料"做高亮/置灰提示（可选，非必须）。

### 3.3 `forging_method`

| 字段 | 变化 | 说明 |
| --- | --- | --- |
| `value_delta` | 不变 | 非零整数 |
| `costs` | 不变 | 每次锻打的资源消耗 |
| `condition` | 不变 | 使用前置条件 |
| `display_icon` | **改** `Optional<Identifier>` → 保持 Identifier，新增 `iconStack()` 访问器 | `ItemStack` 编解码器在原生数据包注册表加载期无法解析物品组件（见 §11），因此数据包仍写裸 ID，由 `iconStack()` 惰性解析为 `ItemStack` 供界面渲染 |
| `cooldown` | **新增** `int`，默认 `0`，范围 `0..72000` | 单位 tick，用于按钮限流，见 §6 |

### 3.4 新增绑定注册表与物品组件

新增两条数据包注册表，以及对应的两个物品组件。**物品侧只存 ID，不存完整定义**。

#### `tool_binding`

路径：`data/<ns>/mxt/tool_binding/<id>.json`

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `methods` | `Holder<forging_method>[]` | **必填** | 该工具解锁的锻打方式，不能为空、不能重复 |

#### `blueprint_binding`

路径：`data/<ns>/mxt/blueprint_binding/<id>.json`

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `blueprints` | `Holder<forging_blueprint>[]` | **必填** | 该物品（蓝图/书籍）提供的蓝图，不能为空、不能重复 |

#### 物品组件

| 组件 ID | 类型 | 说明 |
| --- | --- | --- |
| `mxt:tool_binding` | `Holder<ToolBinding>` | 挂在工具物品上，指示其提供的锻造方法 |
| `mxt:blueprint_binding` | `Holder<BlueprintBinding>` | 挂在蓝图/书籍物品上，指示其提供的蓝图 |

两个组件都用 `MxtDataComponents.register(...)` 现有模式注册，即
`persistent(codec)` + `networkSynchronized(ByteBufCodecs.fromCodecWithRegistries(codec))`。

> **重要**：组件用的是 `RegistryFixedCodec`（`Holder`），需要 registry access 才能解码。
> 物品在背包/槽位中同步时走的是注册表感知的流编解码器，这是当前 `FORGING_RESULT`
> 已经在用的路径，可直接沿用。

### 3.5 失败条件

- **失败的唯一来源 = 会话步数超过蓝图定义的 `max_steps`。**
- `max_steps` **可选**：
  - **未定义** → 该蓝图永不失败，玩家可以一直敲到满足目标区间 + 末尾序列为止。
  - **已定义** → 达到上限后如果仍未满足完成条件，判定失败并按失败结算处理。
- 达到上限后**不再接受新的锻打**（按钮置灰 + 服务端拒绝），玩家只能结算或取消。
- `max_steps` 若定义，数据包加载期必须校验 `max_steps >= optimal_steps`，否则报错禁用蓝图。
- `failure_settlement`（输入返还比率 / 材料损耗比率）的存废见待定项 **T3**：
  输入变成多材料后，单一 `input_return_ratio` 已不足以描述 15 格输入的去向。

## 4. 运行时修订

### 4.1 会话模型：方块共享

- 会话仍然按**方块坐标**保存，但**不区分玩家**：同一锻造台上所有玩家看到并操作**同一个会话**。
- 现结构 `ForgingWorldAttachment.put` 中的 `if (sessions.containsKey(key)) return false`
  **保留但语义改变**：它现在只表示"这个方块上已有会话"，任何有权限的玩家都应能加入，
  而不是拒绝第二个玩家。
- `StationSession.owner` 字段语义从"独占者"改为"会话发起者"，仅用于记录，
  不再作为访问控制依据。
- **已注册但全代码库无人读取的 `MxtAttachments.FORGING_SESSION` 按现状保留**；
  共享会话模型下不需要它，可标记为将来用途或另行清理（待定项 T4）。

### 4.2 输入来源

- **删除**从玩家主手取物品的逻辑（原 `ForgingWorkstationService.start` 中的
  `player.getMainHandItem()` 分支）。
- 输入改为从**方块实体的输入容器**读取（15 格）。
- 输入快照仍然保存到会话里（用于失败返还与进度展示），但**权威副本是方块实体的容器**。
- 方块实体的容器必须写入 NBT 持久化，且 `WorldlyContainer` 的面过滤要禁止漏斗从输入槽
  抽取（防止玩家用漏斗绕过消耗），输出槽允许漏斗抽取。

### 4.3 蓝图与工具选择

- 玩家在**蓝图列表**里点击一个蓝图：**只是选中**（本地高亮），不发送任何包、不消耗材料、不开会话。
- 玩家在**锻造方法列表**里点击一个方法：同样只是选中。
- 两个列表各自只有一个输入源，但方法列表要过两道筛：
  - **可用蓝图 = 蓝图槽里那些蓝图物品提供的蓝图。** 槽位为空即列表为空；没有"回退到全注册表"的分支。
  - **可用方法 = 选中蓝图的 `allowed_methods` ∩ 所有已放置工具 `tool_binding.methods` 的并集。**
- 两个轴各管一件事，互不派生：
  - 蓝图管"值要落到哪里"（数值条、成功区间、末尾序列、品质、成品）和"这件东西允许用哪些手法"。
  - 工具管"这个人会哪些手法"。
  - 方法本身管"值怎么移动"。
- `allowed_methods` **可以省略、可以写空数组、也可以写 `"#标签"`**。省略或写空 = 不做限制，
  此时可用方法就只剩工具一侧，所以刚放上锤子、还没选蓝图时右侧就有内容。
- 工具槽在**会话进行中不锁定**，所以开局没带对工具也能中途加一把来拓宽列表；蓝图槽和输入槽在会话中锁定。
- 执行动作只由按钮触发：`蓝图` 按钮用当前选中的蓝图开会话，`方法` 按钮用当前选中的方法锻打一次。
- **蓝图格悬停显示材料清单**：每项材料一行，输入槽已备齐的用绿勾 `✔ 名称 已有/需要`，不足的用红叉
  `✖ 名称 已有/需要`；只要有一项不足，末尾再加一行灰字"材料不足，无法开始"。
  - 这一行同时是**开始条件**：材料未备齐时 `蓝图` 按钮置灰，服务端也照常以
    `INSUFFICIENT_MATERIALS` 拒绝。两边用的是同一个判定（`StartupMaterials.resolve`），
    所以不存在"按钮亮着但被拒"。
  - 计数来自 `availableCount`（逐项求和），判定来自 `materialsCovered`（多重集合匹配）。材料表
    校验期禁止同一物品出现两次，所以两者必然一致；启动审计里对这一点做了断言。
- **方法格悬停显示名称与数值影响**：第一行是方法名（用它的 `display_icon` 物品名，没有图标时退回
  ID），第二行是 `数值影响：+3` 这样的带符号 `value_delta`。
  - 名称规则唯一实现在 `ForgingMethod#displayName`，所以锤子物品的 tooltip 和这里的格子 tooltip
    不会把同一个方法叫成两个名字。
  - 数值影响不按正负着色，只有加号/减号：往右不等于"好"，往左也不等于"坏"，取决于当前值和目标区间。
- 选择动作**无需同步**——它是玩家自己的光标。请求到达服务端时携带 ID，服务端重新解析并校验：
  蓝图必须由蓝图槽提供，方法必须同时通过上述两道筛，否则拒绝。

### 4.4 锻打与结算

沿用 `ForgingService.strike` / `finish` 的现有流程，改动点：

1. `strike` 前的条件检查增加：输出槽未满（见 4.5）、未达 `max_steps`、限流未触发。
2. 材料消耗改为按 §3.2 的多重集合匹配，从方块实体容器扣除。
3. 失败分支只由 `max_steps` 触发（§3.5）。
4. 成功产物写入输出槽而不是玩家背包；输出槽满时**拒绝锻打**而非掉地。
5. **自动结算**（决定 17）：`strike` 提交之后如果 `session.canComplete()` 成立，直接调结算。
   - 判定是 `值 ∈ [target_min, target_max] && 末尾 N 步逐项匹配`，和 `finish` 用的完全是同一个
     方法（`ForgingSession#canComplete`），并且和 `finish` **共用同一段结算代码**，不是两份。
   - 触发点有三个：`strike` 之后、`start` 之后、以及**打开界面时**（`createMenu`）。前两个覆盖
     "会话状态刚变化"，第三个覆盖"已经是完成态但没结算掉"——脚本取消了 `CompletePre`、或者存档
     写于本功能之前，都属于这种。
   - 打开界面那一次带和 `finish` 一样的守卫（无会话 / 输出槽被占 / 距离过远都直接返回），并且
     **只结算已完成态**：未完成的会话调结算会走失败流程、把材料赔掉，所以这一条绝不能被"打开界面"
     碰到。
   - 打开 GUI 的这次**不是**为了处理数据包改动：`plan`（数值条边界、成功区间、末尾序列、deltas）
     在开会话时就快照进 `ForgingTableState` 并随方块实体存进 NBT，重启后原样读回，所以改数据包
     既不能让未完成的会话变成完成，也不能让完成的变回未完成。
   - 数值条**不再是**"看一眼决定要不要收手"的工具（本来也没有收手按钮），它变成纯进度显示。
   - 于是 `FINISH` 这个网络动作没有界面入口了，保留着给脚本/命令用。
6. **取消**（决定 18）：左下角 `取消` 按钮，会话进行中才可用。
   - 网络动作是已有的 `CANCEL`，不带参数——一张台子只有一个会话，服务端从 `player.containerMenu` 反查是哪张。
   - **"取消的代价"是一个可替换的策略**：`ForgingCancellation`，一个只有一个方法的接口，参数是
     `(player, surface, state, blueprint)`。默认实现 `RETURN_EVERYTHING` 就是现在的行为：把
     `state.consumed()` 原样塞回输入槽，塞不下就掉在脚边。用
     `ForgingWorkstationService.setCancellation(...)` 换。
   - 之所以做成接口而不是数据包字段：形态还没定，现在往蓝图格式里塞一个只有一个实现会读的字段太早。
     等某个变体证明有用，再给它加字段，读取点还是这个策略。
   - **"能不能取消"是另一个问题**，已经有答案了：`ForgingEvent.Cancel` 可以整个否决，会话原样留着。
   - 蓝图的 `fail_action` 仍然会跑（既有行为）：取消确实等于"没做出来"，想对这件事有反应的蓝图写在那里。

### 4.5 输出槽

- 输出槽 `mayPlace` 恒为 `false`（只能取不能放）。
- 输出槽非空时**拒绝下一次锻打**（决定 12）。
- 产物写入输出槽，写不下时拒绝锻打（不再有 `player.drop` 兜底）。

## 5. 网络同步

### 5.1 客户端预测 + 服务端权威

- 客户端选中锻造方法后，**本地立刻**计算 `预测值 = 当前 value + 选中方法 value_delta`
  并渲染到 value 进度条，不显示任何可能的产出物。
- **收到服务端同步后立即覆盖**本地预测值。本地预测只用于消除点击延迟感，不参与任何判定。
- 服务端在以下时机推送会话快照：会话创建、每次锻打成功、结算成功、取消、失败。
- 同步内容（客户端渲染 value / 最后 N 步 / 列表所需的最小集合）：

| 字段 | 用途 |
| --- | --- |
| 蓝图 ID + 其 `meter`/`target`/`finish_pattern` 末 N 项 / `required_suffix_steps` | value 条与目标列 |
| 当前 `value`、`steps`、最近 6 步 `history` | 数值条指针、当前列 |
| `optimal_steps` | 只在方块实体侧使用（品质公式与结算结果组件）；它是 `plan` 的属性，随 `plan` 一起冻结，**不存进会话快照**，同步时也直接取自 `plan` |

> 两个列表**不在**同步内容里：它们各自是"本方已持有的槽位内容"的纯函数，客户端手上就有。
> 选中状态同样不同步——它只是玩家的光标，见 4.3。

> 现有 `ForgingWorldAttachment` 注册时**没有** `.sync()`，客户端拿不到任何会话状态。
> 这是必须新增的工作量，不存在于当前网络层。

### 5.2 动作集合

`ForgingActionC2SPayload` 的动作集合。**选中不联网**，所以没有 `SELECT_BLUEPRINT` /
`SELECT_METHOD` 两个动作：光标是客户端的，只有按钮才发请求。

| 动作 | 说明 |
| --- | --- |
| `SELECT` | 用当前选中的蓝图创建会话（消耗材料） |
| `STRIKE` | 用当前选中的方法执行一次锻打 |
| `FINISH` | 结算 |
| `CANCEL` | 取消 |

服务端不接受任何坐标：请求由 `player.containerMenu` 反查是哪张锻造台。

## 6. 限流

- `ForgingMethod` 新增 `cooldown`（tick，默认 `0`，上限 `72000`）。
- 服务端为每个**玩家 × 方块**记录上次成功锻打的时间戳（game time）。
- 未满冷却的 `STRIKE` 请求**直接拒绝且不消耗任何资源**。
- 客户端根据同一份 `cooldown` 与剩余时间对按钮置灰 + 画冷却遮罩。
- 目的：既防连点器刷屏，也防错误客户端高频发包。
- 参考现有可配置冷却模式：`CultivateAction.cooldownTicks`（`Codec.intRange(0, 72_000)`）。

## 11. 实现记录（2026-02）

### 11.1 关键约束：数据包注册表里不能用 `ItemStack`

原生数据包注册表在**物品组件绑定之前**解析。把 `input` 或 `display_icon` 声明为
`ItemStack` 会让整个注册表加载失败：

```text
java.lang.IllegalStateException: Item minecraft:iron_ingot does not have components yet
```

`ItemStack.CODEC` 与 `ItemStack.OPTIONAL_CODEC` 都会失败（后者在物品存在时仍走完整组件路径）。
因此：

- `input` 使用新增的 `ForgingMaterial`（`Identifier id` + `int count`，`count` 默认 `1`），
  运行时再惰性解析为 `ItemStack` 做匹配。
- `display_icon` 保持裸 `Identifier`，由 `ForgingMethod.iconStack()` 惰性解析。

这是**数据包作者可见的格式约定**，未来不能改回 `ItemStack`。

### 11.2 存储落点

会话状态落在 `ForgingTableBlockEntity` 的 `ForgingTableState` 字段上，**同时**承载：

- `blueprint`（`Identifier`）、`plan`（`ForgingPlan`，冻结 `optimalSteps`）、`session`（`Snapshot`）
- `consumed`（开局从容器取走的材料快照，用于取消/失败精确返还）
- `starter`（会话发起者，仅记录用）

`result` / `quality_by_extra_steps` / `failure_settlement` **不再快照**，结算时从蓝图现查
（方案 A，与 `AlchemyWorkstationState` 只存 recipe id 的做法一致）。

布局：`0..2` 蓝图、`3..5` 工具、`6..20` 输入（5×3）、`21` 输出。

### 11.3 客户端同步

没有新增网络包。会话状态通过 `getUpdatePacket()` / `getUpdateTag()` → `saveWithoutMetadata()`
随普通方块实体更新下发，界面因此能在方块实体数据到达时立即刷新。

客户端本地预测（`当前 value + 选中方法 delta`）只用于消除点击延迟，服务端每次
`STRIKE` 都重新校验；`SELECT`/`STRIKE` 都要求目标坐标真的存在 `ForgingTableBlockEntity`，
所以"任意坐标开会话"的旧漏洞已随世界附件一起消失。

## 12. 界面实现记录（2026-09，原版 GUI + 贴图）

### 12.1 结论

界面一度用 LDLib2（`ldlib2:block_ui`）实现，理由是槽位坐标交给布局引擎后不会和手写
坐标漂移；实际结果是布局失控且难以核对。随后改为纯代码绘制底板，同样不对：面板底色
会吞掉槽位凹槽，手画的凹槽和原版槽位贴图对不齐。

**最终方案：底板用项目自己的贴图 `textures/gui/forging_table.png`，代码只画活的东西。**
当前实现里**没有任何 LDLib2 引用**，依赖仍在 `build.gradle` 中但不再被使用。

### 12.2 布局：坐标来自贴图，不是来自估算

帧 `322 × 234`，所有坐标以帧左上角为原点。这些数字是**从贴图上逐像素量出来的**，
方法是用 `tools/png-read.ps1` 解码 PNG 后扫描同一颜色连续段：

| 区域 | 位置 |
| --- | --- |
| 蓝图选择格（3×3 可见） | x=7 / y=17，格 18px，行距 19px |
| 蓝图槽 ×3 | x=58，y=17 / 35 / 53 |
| 材料输入 4×3 | x=80 / 98 / 116 / 134，y=17 / 35 / 53 |
| 输出槽 | x=197，y=35（与输入中行同高） |
| 工具槽 ×3 | x=301，y=17 / 35 / 53 |
| 方法选择格（3×3 可见） | x=250 / y=17 |
| 数值条槽 | x=80..242，y=88 |
| 要求 / 当前 六格 | x=133 起，格距 20px，y=111 / 130 |
| 玩家物品栏 9×3 | x=80，y=151，行距 18px |
| 快捷栏 | x=80，y=209 |

注意**槽位列用 18px 间距，两个选择格用 19px 间距**——贴图就是这么画的，两者不能互换。
`ForgingMenu` 持有全部这些常量，`ForgingScreen` 直接引用，避免两处各写一份。

### 12.3 绘制分工

| 层 | 位置 | 内容 |
| --- | --- | --- |
| 背景层 | `extractBackground` | **只做一次整帧 blit** |
| 前景层 | `extractRenderState` | 选择格图标 / 选中与悬停高亮 / 滚动条；六步图标；数值条填充与目标色带 |
| 标签层 | `extractLabels` | 标题、物品栏标题、数值与步数读出、要求 / 当前两个标签 |

**两层的坐标系不同，且不能混用**：`extractBackground` 在
`AbstractContainerScreen.extractContents` 把原点平移到帧角**之前**执行，那一层的坐标
要自己加 `leftPos`/`topPos`；`extractRenderState` 之后执行，原点和 `Slot.x/y` 一致。

**blit 的源矩形必须是帧而不是整张图**：GUI 贴图共用一张 `512×256` 画布，帧只占左上角
`322×234`。按图片尺寸 blit 会把帧拉伸到整张画布大小，每个槽位都会偏离贴图上画好的格子。

### 12.4 状态同步

会话状态（数值、步数、最优步数、数值条上下界与目标区间、末尾 6 步的目标与历史）
通过 `DataSlot` 同步：服务端在 `ForgingMenu.broadcastChanges()` 里把
`ForgingTableState` 写进 21 个 `DataSlot`（索引 `9..14` 是目标 6 步，`15..20` 是当前 6 步），
客户端读同样的下标。自 26.1 起 `registryAccess()` 已内置，因此同步的是**注册表整数 ID**，
客户端再用这个 ID 反查 `forging_method` 拿图标。数据槽在包体里是有符号 short，
所以只能承载注册表 ID 这类密集小整数。

两个选择列表**不同步**：各自是本方槽位内容（方法列表还要加上选中蓝图）的纯函数，客户端自己算。
选择状态也不同步：点击格子只改本地高亮，不发包、不消耗材料、不可被拒绝；只有 `蓝图` / `方法`
两个按钮发包，包里带的是选中项的 ID，服务端重新解析并校验。
