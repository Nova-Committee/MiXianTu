# 原版创造模式的信任模型

考察对象：Minecraft 26.1.2（`version.json` id `26.1.2`，protocol 775）反编译源码。
关注问题：创造模式物品栏能凭空给物品，为什么生存模式无法用同样的路径绕过。

---

## 0. 结论先行

原版的防线不是「创造界面写得很小心」，而是三条结构性事实：

1. **创造物品栏在服务端根本不存在。** 它是一个客户端私有的 `AbstractContainerMenu`，服务端不知道它、也没为它注册菜单类型。界面本身因此没有可被利用的攻击面。
2. **唯一的出库包在协议解码层就被模式判定拦掉。** 生存模式的客户端连处理器函数都进不去，而且失败是静默的：跳过该包、只打一条 debug 日志、不断线不踢人。
3. **`instabuild` 没有任何上行写入路径。** 客户端只能「被告知」自己是创造模式；没有任何一个客户端包能设置这个标志。

所有「能不能凭空拿」的判断最终都收敛到服务端自己那份 `abilities.instabuild` 上。客户端里的任何自我约束（包括 `MultiPlayerGameMode` 里那句 `hasInfiniteMaterials()`）只是省流，不是防线。

## 1. 界面侧：创造物品栏是客户端的幻觉

- `CreativeModeInventoryScreen extends AbstractContainerScreen<CreativeModeInventoryScreen.ItemPickerMenu>`（`CreativeModeInventoryScreen.java:60`）。
- `ItemPickerMenu` 的构造是 `super(null, 0)`（同文件 :944-957）：`menuType` 为 `null`，`containerId` 为 0。这个 0 和玩家 `InventoryMenu` 的 `containerId` 撞号，但**是另一个对象**——服务端从来没创建过它。
- 45 个格子的槽指向 `private static final SimpleContainer CONTAINER = new SimpleContainer(45)`（:105），一个客户端静态容器。
- 因此玩家的 `player.containerMenu` 全程都是 `InventoryMenu`。在创造界面里点**创造格子**不会产生任何上行包；点**快捷栏/背包槽**虽然有本地菜单运算（见 §5.3），但走的也是第 2 节那条 `SetCreativeModeSlot` 通道，而不是 `ServerboundContainerClickPacket`。
- `ItemPickerMenu.getCarried()` / `setCarried()` 直接代理到 `inventoryMenu`（:1021-1029）。也就是说「拿在手里」的那一摞，挂的是**真正的 `InventoryMenu`** 的客户端预测值。

这一层解释了为什么创造界面能复用原版那套槽位渲染与点击路由（`AbstractContainerScreen` 的 `extractSlots` / `slotClicked` 只认 `Slot`，不认菜单是不是「真的」），又不会污染服务端状态。

## 2. 唯一的出库通道

客户端有两个出口，都归到同一个包（`MultiPlayerGameMode.java:526-542`）：

```java
handleCreativeModeItemAdd(ItemStack clicked, int slot)
    -> ServerboundSetCreativeModeSlotPacket(slot, clicked)     // slot 1..45，写进背包槽

handleCreativeModeItemDrop(ItemStack clicked)
    -> ServerboundSetCreativeModeSlotPacket(-1, clicked)       // slot -1，掉到地上
```

两者在发送前都自查 `this.minecraft.player.hasInfiniteMaterials()`，但如上所述这只是省流。

还有一处容易看错的地方：`Player.handleCreativeModeItemDrop(ItemStack)` 在基类里是**空实现**（`Player.java:589-590`），只有 `LocalPlayer` 覆写它并转发到 `gameMode`（`LocalPlayer.java:1240-1242`）。所以 `AbstractContainerMenu.doClick` 的 THROW 分支里那两行 `player.handleCreativeModeItemDrop(itemStack)`（`AbstractContainerMenu.java:524, 533`）在服务端上是空操作——服务端那边真正让物品落地的是同一分支里的 `player.drop(itemStack, true)`；只有在客户端才会真的发出 `SetCreativeModeSlot(-1, ...)`。

## 3. 服务端的三道闸门

### 3.1 协议层：`GameProtocols.HAS_INFINITE_MATERIALS`

这是整套设计里最关键、也最容易漏掉的一层（`GameProtocols.java:40-58`）：

```java
public static final CodecModifier<RegistryFriendlyByteBuf, ServerboundSetCreativeModeSlotPacket, GameProtocols.Context>
    HAS_INFINITE_MATERIALS = (original, context) -> new StreamCodec<>() {
        public ServerboundSetCreativeModeSlotPacket decode(RegistryFriendlyByteBuf input) {
            if (!context.hasInfiniteMaterials()) {
                throw new SkipPacketDecoderException("Not in creative mode");
            }
            return original.decode(input);
        }

        public void encode(RegistryFriendlyByteBuf output, ServerboundSetCreativeModeSlotPacket value) {
            if (!context.hasInfiniteMaterials()) {
                throw new SkipPacketEncoderException("Not in creative mode");
            }
            original.encode(output, value);
        }
    };
```

挂载点：`.addPacket(GamePacketTypes.SERVERBOUND_SET_CREATIVE_MODE_SLOT, STREAM_CODEC, HAS_INFINITE_MATERIALS)`（:117）。

`Context` 的绑定：

- **服务端入站**（`PlayerList.java:162-165`）：`GameProtocols.SERVERBOUND_TEMPLATE.bind(..., playerConnection)`。上下文就是 `ServerGamePacketListenerImpl` 自己——它 `implements GameProtocols.Context`（`ServerGamePacketListenerImpl.java:229`），其 `hasInfiniteMaterials()` 返回 `this.player.hasInfiniteMaterials()`（:2229-2230）→ `Player.hasInfiniteMaterials()` → `this.abilities.instabuild`（`Player.java:1351-1352`）。
- **客户端出站**（`ClientConfigurationPacketListenerImpl.java:206-216`）：上下文是一个匿名类，`hasInfiniteMaterials()` **写死 `return true`**。客户端编码器从不拦截。

因为 `Context` 持有的是 packet listener、读的是实时状态，所以**切换游戏模式不需要重新绑定协议**。

失败路径（这条很重要，决定了「绕过」的代价）：

- `PacketDecoder.decode` 捕获异常时若 `instanceof SkipPacketException`，先 `input.skipBytes(input.readableBytes())` 把这条包剩下的字节丢掉，再抛出（`PacketDecoder.java:26-35`）。
- `Connection.exceptionCaught` 对 `SkipPacketException` 只做 `LOGGER.debug("Skipping packet due to errors", ...)`，**不断线、不踢人、不 warn 刷屏**（`Connection.java:108-111`）。
- `SkipPacketDecoderException implements IdDispatchCodec.DontDecorateException`，保证异常类型不被包装，`instanceof` 才成立。

### 3.2 处理器层：`handleSetCreativeModeSlot`

即便过了协议层（即服务端认为你在创造模式），处理器还会再查一遍（`ServerGamePacketListenerImpl.java:2038-2062`）：

```java
public void handleSetCreativeModeSlot(ServerboundSetCreativeModeSlotPacket packet) {
    PacketUtils.ensureRunningOnSameThread(packet, this, this.player.level());
    if (this.player.hasInfiniteMaterials()) {                       // ① 再查一次模式
        boolean drop = packet.slotNum() < 0;
        ItemStack itemStack = packet.itemStack();
        if (!itemStack.isItemEnabled(this.player.level().enabledFeatures())) {
            return;                                                  // ② 特性开关
        }
        boolean validSlot = packet.slotNum() >= 1 && packet.slotNum() <= 45;   // ③ 槽位范围
        boolean validData = itemStack.isEmpty() || itemStack.getCount() <= itemStack.getMaxStackSize(); // ④ 数量
        if (validSlot && validData) {
            this.player.inventoryMenu.getSlot(packet.slotNum()).setByPlayer(itemStack);
            this.player.inventoryMenu.setRemoteSlot(packet.slotNum(), itemStack);
            this.player.inventoryMenu.broadcastChanges();
        } else if (drop && validData) {
            if (this.dropSpamThrottler.isUnderThreshold()) {
                this.dropSpamThrottler.increment();
                this.player.drop(itemStack, true);
            } else {
                LOGGER.warn("Player {} was dropping items too fast in creative mode, ignoring.", ...);
            }
        }
    }
}
```

**槽位范围 1..45 的含义**：`InventoryMenu` 的布局是 0 = 合成结果槽，1-4 = 2×2 合成格，5-8 = 盔甲，9-35 = 主背包，36-44 = 快捷栏，45 = 副手（`InventoryMenu.java:49-79`）。总共 46 个槽（0..45）。所以 `1..45` 恰好是「除合成结果之外的全部」——**不能往合成输出槽里塞东西**，这是 ③ 的全部意义。

**数量校验 ④** 防的是「塞一个 `count = 2^31` 的堆」。注意它只校验 `<= getMaxStackSize()`，不校验下限；负数 count 在 `ItemStack` 里本身是非法的，由 3.3 的解码层兜住。

### 3.3 解码层：`validatedStreamCodec(OPTIONAL_UNTRUSTED_STREAM_CODEC)`

`ServerboundSetCreativeModeSlotPacket.STREAM_CODEC` 用 `ItemStack.validatedStreamCodec(ItemStack.OPTIONAL_UNTRUSTED_STREAM_CODEC)`（`ServerboundSetCreativeModeSlotPacket.java:11-17`）：

- `OPTIONAL_UNTRUSTED_STREAM_CODEC` 用 `DataComponentPatch.DELIMITED_STREAM_CODEC`（`ItemStack.java:126-128`）——「delimited」即带长度/条目上限，防组件炸弹。
- `validatedStreamCodec`（`ItemStack.java:197-213`）解码之后拿 `ItemStack.CODEC` **再编码一遍**，编不过就抛 `DecoderException`：

```java
public ItemStack decode(RegistryFriendlyByteBuf input) {
    ItemStack itemStack = codec.decode(input);
    if (!itemStack.isEmpty()) {
        RegistryOps<Unit> ops = input.registryAccess().createSerializationContext(NullOps.INSTANCE);
        ItemStack.CODEC.encodeStart(ops, itemStack).getOrThrow(DecoderException::new);
    }
    return itemStack;
}
```

畸形组件在进入游戏逻辑之前就报废了。

## 4. `instabuild` 是服务端独占的真相

写入路径只有一条：

- `ServerPlayerGameMode.setGameModeForPlayer(GameType, @Nullable GameType)` → `gameModeForPlayer.updatePlayerAbilities(abilities)`（`ServerPlayerGameMode.java:79-87`）→ `GameType.updatePlayerAbilities`（`GameType.java:62-80`）里 `CREATIVE` 分支设 `mayfly / instabuild / invulnerable = true`。
- 入口是 `changeGameModeForPlayer`（:55-77），由 `/gamemode` 命令、`PlayerList` 初始化、以及 `ServerboundChangeGameModePacket` 的处理器调用。

客户端是被**告知**的：`ClientboundPlayerAbilitiesPacket`，只用于 UI（决定要不要显示创造界面之类）。

上行侧完全没有写入路径：

- `handlePlayerAbilities`（`ServerGamePacketListenerImpl.java:2084-2087`）只接受一个字段，还附加 `player.mayFly()`：

```java
this.player.getAbilities().flying = packet.isFlying() && this.player.mayFly();
```

- `handleChangeGameMode`（:2116-2127）要 `GameModeCommand.PERMISSION_CHECK.check(this.player.permissions())`，非 OP 只记一条 warn。

**所以作弊客户端把本地 `abilities.instabuild` 改成 `true` 会怎样**：创造界面正常打开、格子能点、物品「进背包」（本地预测），但包一发到服务端就在 3.1 被丢。表现是**幽灵物品**——本地看得见，服务端不认，重开容器或重连即消失。这是惰性作弊，不是绕过。

## 5. 客户端怎么把「拿在手里」变成「真的进背包」

### 5.1 自动同步：`CreativeInventoryListener`

- 创造界面 `init()` 给 `player.inventoryMenu` 挂监听器（`CreativeModeInventoryScreen.java:375-377`），`removed()` 摘掉（:400-406）。
- `AbstractContainerMenu.broadcastChanges()` → `triggerSlotListeners(i, current, currentCopy)` 拿 `lastSlots` 做 diff，对每个 `ContainerListener` 调 `slotChanged(this, i, newItem)`（`AbstractContainerMenu.java:195-248`）。
- `CreativeInventoryListener.slotChanged` 直接转发 `this.minecraft.gameMode.handleCreativeModeItemAdd(itemStack, slotIndex)`（`CreativeInventoryListener.java:18-21`）。

于是「任何对 `inventoryMenu` 槽位的本地改动」都会自动升级成一个 `SetCreativeModeSlot` 包，不需要为每种操作手写一个包。这是整套同步的骨架。

### 5.2 显式同步

- 快捷栏：`handleCreativeModeItemAdd(this.menu.getSlot(45 + i).getItem(), 36 + i)`（`CreativeModeInventoryScreen.java:311`）。注意 `45 + i` 是**创造菜单**里的槽号，`36 + i` 是 **`InventoryMenu`** 里的槽号——`ItemPickerMenu` 的 `addInventoryHotbarSlots(inventory, 9, 112)` 建的槽索引是 45..53（`AbstractContainerMenu.java:73-77` 建的槽用容器索引 0..8），两边必须手工对齐。
- 丢弃：`handleCreativeModeItemDrop` → slot `-1`。

### 5.3 「从格子拿起」这一步本身不发包

`CreativeModeInventoryScreen.slotClicked`（:194-327）里，若 `slot.container == CONTAINER`（即创造/搜索页签的格子，判断见 :257 与 `isCreativeSlot` :329-331），则**完全不调 `this.menu.clicked`**，只在客户端改 carried：

- `CLONE`（中键）：`this.menu.setCarried(item.copyWithCount(item.getMaxStackSize()))`（:269-276）
- 普通左键 + 空手：`int count = quickKey ? clicked.getMaxStackSize() : clicked.getCount(); this.menu.setCarried(clicked.copyWithCount(count));`（:298-300）
- 同物品叠加 / 右键减一（:288-297）
- 丢弃（:278-286）→ `handleCreativeModeItemDrop`

**从创造格子取物 = 纯粹的客户端 carried 赋值。** 真正落地要等你在快捷栏/背包槽上再点一下，或者把 carried 直接丢出去。

### 5.4 顺带解释掉的几个「为什么」

- 为什么 `ItemPickerMenu` 要用 `super(null, 0)`：它就是个本地壳子，不需要 `menuType`，也不需要服务端注册。
- 为什么 `CustomCreativeSlot.mayPickup`（:930-936）只是客户端逻辑：它只用来防止把「被 `CREATIVE_SLOT_LOCK` 锁住」或「特性未启用」的物品画成可拿，**不是服务端校验**。真正的服务端校验在 3.2。
- 为什么 `AbstractContainerMenu.doClick` 的 `CLONE` 分支要 `player.hasInfiniteMaterials()`（`AbstractContainerMenu.java:509`）：中键克隆在**任何**容器菜单里都可用（`AbstractContainerScreen.java:367-368`），所以那个守卫是必需的；创造拖拽的 `type == 2` 同理（`AbstractContainerMenu.java:724-730` 的 `isValidQuickcraftType`）。

## 6. 其他创造专用路径的同类写法

- `handlePickItemFromBlock`（:715-733）：`boolean includeData = this.player.hasInfiniteMaterials() && packet.includeData();`；`tryPickItem` 里只有 `hasInfiniteMaterials()` 才 `inventory.addAndPickItem(itemStack)`（:775-777）。注意「选取方块」在生存模式**也是允许**的，只是走 `inventory.pickSlot`（在已有物品之间切换）而不是凭空生成。
- `handlePickItemFromEntity`（:748-763）：物品走同样的 `tryPickItem`；要带实体数据还需要 `canUseGameMasterBlocks()` = `instabuild && COMMANDS_GAMEMASTER`（`Player.java:1920-1922`）。
- 「用物品不消耗」：`ServerPlayerGameMode.java:410-419` 在 `useOn` 前存 `count`、后恢复。

可以看到原版对「创造特权」的判定几乎全部收敛在 `hasInfiniteMaterials()` 这一个谓词上，需要更高门槛时才叠加 `COMMANDS_GAMEMASTER`。

## 7. 节流

- 掉落：`private final TickThrottler dropSpamThrottler = new TickThrottler(20, 1480)`（`ServerGamePacketListenerImpl.java:244`），每 tick `tick()`（:299）。`TickThrottler` 的语义是 `increment()` 加 `incrementStep`、`tick()` 减 1、`isUnderThreshold()` 比 `threshold`（`TickThrottler.java`）。于是每掉落 +20、每 tick -1 → **稳态 1 次/tick ≈ 20 次/秒**，突发额度约 74 次。超了只 `warn`。
- 客户端自己也有一份 `LocalPlayer.getDropSpamThrottler()`，在 `handleCreativeModeItemDrop` 里 +1（`MultiPlayerGameMode.java:540`），但那是防自己刷包，不是防线。

## 8. 顺带学到的一条通用反作弊模式

`ServerboundContainerClickPacket`（`ServerboundContainerClickPacket.java`）携带的是：

```
containerId, stateId, slotNum, buttonNum, containerInput,
changedSlots: Map<Int, HashedStack>,   // 客户端预测出的「结果」
carriedItem: HashedStack
```

客户端侧 `MultiPlayerGameMode.handleContainerInput`（:478-516）先在本机执行 `containerMenu.clicked(...)` 做预测，然后把**执行后的槽位内容算成哈希**发上去。

服务端 `handleContainerClick`（`ServerGamePacketListenerImpl.java:1952-1988`）做的是：

1. 校验 `containerId` 与当前菜单一致；
2. `isValidSlotIndex(slotNum)`；
3. 在**服务端自己的菜单副本**上跑 `clicked(...)`；
4. 把客户端声称的 `changedSlots` 用 `setRemoteSlotUnsafe` 记进 `remoteSlots`（只用于「客户端以为它有什么」的比对，用来决定要不要补发/全量重同步）；
5. `setRemoteCarried(packet.carriedItem())`；
6. `broadcastChanges()` 或 `broadcastFullState()`。

关键点：**客户端发的是哈希而不是指令，服务端从不采用这些值。** 客户端预测的唯一用途是省掉冗余下发。这跟创造模式那条链路是同一种思路——上行只传「意图的最小索引」，真相永远在服务端重算。

## 9. 对 mxt `/picker` 的映射

我们的选择走的是**自定义 payload**（`ItemPickerChooseC2SPayload`），拿不到 `HAS_INFINITE_MATERIALS` 这个 codec modifier（那是原版包专属的），所以第 3.1 层必须由处理器层补齐。

| 层次 | 原版 | mxt picker | 结论 |
| --- | --- | --- | --- |
| 协议层 | codec modifier 直接丢弃 | 无（自定义 payload 挂不上） | 需靠处理器层补 |
| 模式判定 | `hasInfiniteMaterials()`（instabuild） | `player.isCreative()`（gameMode） | 等价，但建议对齐原版谓词 |
| 权限 | 只要求创造模式 | 额外要求 `COMMANDS_GAMEMASTER` | 更严 |
| 载荷内容 | 物品栈本体 | registry + 条目 id + pool | 更严（服务端重新解析） |
| pool 越界 | — | 与重算结果做相等匹配，越界解析为空 | 安全 |
| 数量 | `count <= maxStackSize` | `fullStack` 布尔，钳到 `getMaxStackSize()` | 相同 |
| 特性开关 | `isItemEnabled(enabledFeatures)` | **未校验** | 缺口 |
| 掉落节流 | `TickThrottler` | 无 | 可接受（OP 限定） |

建议对齐的两处：

1. `ServerNetworkHandler.onItemPickerChoose` 里把 `player.isCreative()` 换成 `player.hasInfiniteMaterials()`，跟原版用同一个谓词——`instabuild` 才是「能凭空造物」的真相，`gameMode` 只是它的来源之一（模组也可以独立设置 `instabuild`）。
2. `give()` 之前加 `if (!stack.isItemEnabled(player.level().enabledFeatures())) return;`，与 `handleSetCreativeModeSlot` 的第 ② 步对齐。`ItemPickerManager` 的 `ItemMatcher` 允许数据包指向任意已注册物品，特性开关之外的物品（原版 experimental 内容等）应该挡在门外。

结构性差异（不是问题，但要知道）：原版是「先落到 carried，再靠 `inventoryMenu` 的槽位 diff 自动上行」，我们是「服务端直接 `inventory.add` / `drop`」。后者少一层客户端预测，也就少一类不同步的可能。

同步侧不需要额外做什么：`InventoryMenu` 的槽读的就是同一个 `Inventory` 对象，而 `ServerPlayer.doTick()` 每 tick 都会调一次 `this.containerMenu.broadcastChanges()`（`ServerPlayer.java:610`），`triggerSlotListeners` / `synchronizeSlotToRemote` 会基于 `lastSlots` / `remoteSlots` 的 diff 把改动发下去（`Inventory.setChanged()` 本身只做 `timesChanged++`，不广播，`Inventory.java:456-459`）。所以 `inventory.add(...)` 最迟下一 tick 就会同步。要立即生效（避免那一 tick 的可见延迟）可以照 `GiveCommand.java:81` 的做法手动补一次 `player.containerMenu.broadcastChanges()`。

## 10. 一句话总结

创造模式的「能拿」和生存模式的「拿不到」并不靠同一段代码上的 `if`，而是靠**把特权判定下沉到协议解码之前**：唯一的出库包在 codec 层就被 `abilities.instabuild` 拦掉，失败静默且不踢人；而 `instabuild` 本身没有任何上行写入路径。客户端做的所有判断都只是预测与省流，随时可以被绕过——原版的设计正是建立在「承认这一点」之上的。
