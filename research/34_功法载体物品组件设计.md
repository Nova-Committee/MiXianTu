# 功法载体改为物品组件

**2026-09-22 定案（用户点名）**：功法手册不再是"某个物品 id 绑定了某条功法"，而是"**这叠物品身上带着哪个功法组件**"。本体按
`mxt:technique` 注册表给每个功法**自动生成一份玉简**，创造模式物品栏与物品选择器都能拿到。

一句话回顾起因：创造模式拿出来的 `mxt:cultivation_jade_slip` 会显示「功法：青霄吐纳诀 / 品质：粗劣」，因为测试包那条
`technique_binding` 把 `items` 写成 `mxt:cultivation_jade_slip`——**只要物品 id 对得上就生效**
，与这叠物品本身有没有东西无关。用户要的是"堆说话，不是物品 id 说话"。

## 1. 旧形状与它的问题

| 位置                                    | 旧行为                                                                          |
|---------------------------------------|------------------------------------------------------------------------------|
| `mxt:technique_binding`（数据包表）         | 字段 `items` 是**物品匹配器**；`ItemMatcher.find` 扫注册表，第一个物品匹配上的定义生效                  |
| `ItemBindingService.technique(stack)` | 按物品匹配取定义；`ResolvedBindings` 把它和 weapon / pill / item 三种绑定并列                  |
| `HoldLookup.hold(stack)`              | 按物品匹配取 hold，缓存键是 `Item`，注释写着"声明只看物品身份、从不看堆"                                  |
| `ItemBindingTooltipAppender`          | 物品匹配上就画「功法：X」，**不看堆**                                                        |
| picker                                | `registerMatcher(TECHNIQUE_BINDING, TechniqueBinding::entries)`：一个定义列出它匹配的物品 |
| 创造模式                                  | 什么都不知道，物品栏里的玉简就是普通物品                                                         |

问题不止"通用玉简被误认成手册"：**一叠物品无法各自不同**，同一个物品不可能既是空载体又是某条功法的手册；反过来，内容包想让自己的物品当手册，就必须写一条按
id 匹配的定义，而那会让**该物品的任何一叠**都变成手册。

## 2. 新形状

### 2.1 组件

新增数据组件 `mxt:technique`，载荷是 `Holder<Technique>`（`Technique.CODEC` = 注册表固定 Codec，落盘 + 同步客户端，与
`mxt:tool_binding` / `mxt:blueprint_binding` 同一形状）。

- **堆上有它 = 这一叠是那份功法的手册**。任何物品都能带，不需要内容包写定义。
- 物品栏里的空玉简（`new ItemStack(玉简)`）没有这个组件，因此**什么都不显示、也不能学**——这就是这次要修的那条。

### 2.2 定义：`mxt:technique_binding` 不再认物品

| 字段                                                                              | 变化                                                                                                        |
|---------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------|
| `items`                                                                         | **删除**（不再按物品匹配；这是本次唯一的删字段）                                                                                |
| `carrier_item`                                                                  | **新增**，可选，单个物品 id（`BuiltInRegistries.ITEM.byNameCodec()`）。本体为这条功法生成的载体用它；不写就是 `mxt:cultivation_jade_slip` |
| `technique`                                                                     | 不变（`Holder<Technique>`）；定义与功法**一一对应**，按它取"读这条功法的手感"                                                       |
| `quality_group` / `conditions` / `learn_time` / `hold_animation` / `hold_sound` | 不变，语义不变（品质组、可用条件、长按时长、姿势、音效）                                                                              |

取定义的方式从"物品匹配"变成"**按功法 id 匹配**"：`ItemBindingService` 在 `technique_binding` 里找 `technique`
等于堆上那条功法的定义；**找不到就用默认值**（`learn_time = 0` 即刻学会、默认姿势与音效、无品质组、无条件、载体是玉简）。所以"
有功法、没写定义"是可用的：它只是没有额外约束。

### 2.3 本体生成的载体

- 生成规则：遍历 `mxt:technique` 注册表，每条功法产出 `new ItemStack(carrier_item)` + `mxt:technique = 该功法`。
- 出现的地方：
    - **创造模式物品栏**（`MxtCreativeTabs.MAIN`，用 `ItemDisplayParameters.holders()` 读注册表）；
    - **物品选择器**（`ItemPickerManager` 把 `mxt:technique` 注册成一个分类，行就是那份生成的载体，行名用功法自己的显示名）。
- 于是 `/picker mxt:technique` 与创造模式都能"每个功法一份手册"，而**内容包自己的手册物品**只需在定义里写
  `carrier_item: <自己的物品>`，同样会出现在这两个地方。

### 2.4 内容包的自定义物品

三种用法，从省事到灵活：

1. **直接用品生成的那份**：不写 `carrier_item`，玩家从创造模式 / picker 拿到的是玉简 + 组件。
2. **换载体物品**：写 `carrier_item: "my_mod:my_manual"`，生成的载体就是那个物品（本体不生成物品本体，物品本身仍由内容包注册）。
3. **完全自己发**：任何途径（配方产物 `components`、战利品函数、`/give ... [mxt:technique="mxt:xxx"]`、KubeJS）把
   `mxt:technique` 写到堆上，那一叠就是手册。**注意**：这条路上"世界里自然生成的物品"不会自动带上组件——组件是堆数据，只有写上去才有。

### 2.5 长按手势要按堆解析

`HoldLookup` 现在把答案缓存在 `Item` 上（注释也写明"声明只看物品身份"），组件化之后这句话不再成立：同一个物品，带组件的那一叠要驱动手势、不带的那一叠不能。

- 新增按堆匹配的 `ItemMatcher.Entry`：`TechniqueEntry`（`{"type": "mxt:technique"}`，注册进 `MxtItemMatchers`），
  `matches(stack)` 只看堆上有没有组件。
- 新增 `TechniqueHold`（单例，注册进 `HoldLookup`）：`entries()` 返回那一个 entry；时长 / 姿势 / 音效**都按堆**
  取（从堆上的功法找到定义，取不到就用默认值）。
- `HoldBinding` 新增按堆的 `holdAnimation(Provider, ItemStack)` / `holdSound(Provider, ItemStack)` 默认方法（与已有的
  `holdTicks(Provider, ItemStack)` 同一套写法），`HoldService` 改为传堆；`TechniqueHold` 覆盖它们。
- `HoldLookup` 的缓存改成"**按物品缓存物品级匹配 + 每次按堆判堆级匹配**"：`ItemEntry` / `TagEntry` 是物品级（可缓存），其它自定义
  Entry 是堆级（每次都判）。这样每 tick 的额外成本只有一次组件查询。

### 2.6 阅读手势本身不变

`TechniqueItemService` 的判定、进度条、冷却、失败文案都不动，只把"绑定从哪来"换成"从堆上的组件来"：
`ItemBindingService.technique(stack)` 仍然返回一个 `TechniqueBinding`（定义存在就是那条定义，不存在就是按默认值合成的一条），所以工具提示、品质组、条件门（
`ItemQualityService`）、诊断命令（`/mxt technique diagnose`）都不用改形状。

## 3. 删与不改

- **删**：`TechniqueBinding.items`、`ItemBindingService` 里按物品匹配 technique 的路径、`ItemPickerManager` 的
  `registerMatcher(TECHNIQUE_BINDING, ...)`、`HoldLookup` "只看物品身份"的按物品缓存。
- **不改语义**：`learn_time` / `hold_animation` / `hold_sound` / `quality_group` / `conditions`
  的含义与校验规则（姿势白名单、无长按时不许写姿势与音效）；学会后**不消耗**手册；冷却仍走原版 `ItemCooldowns`（因此
  `mxt:on_cooldown` 物品条件照旧可用）。
- **不做**：旧数据（写了 `items` 的 `technique_binding`）**不迁移也不报错**——`RecordCodecBuilder` 会静默忽略 `items`
  ，那些包里的手册会退回"生成的玉简"。这是未发布阶段的口径，写在 `docs/数据包格式.md` 里。

1. 编译：`./gradlew.bat compileJava compileTestModJava --console=plain`。
2. 测试包资源：改过 `src/test-mod/resources` 后跑 `./gradlew.bat processTestModResources --console=plain`。
3. 探针（**需实机，先问**）：`/mxt_test` 的功法 / 物品腿，重点看"空玉简不解析、带组件解析"两条。
4. 人工（实机）：创造模式找 `功法玉简` 应为空壳；`/picker mxt:technique` 每个功法一份玉简且 tooltip 显示功法名。
