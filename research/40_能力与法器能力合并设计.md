## 0. 结论

一句话：**只留一个概念 —— `Ability`（`data/<ns>/mxt/ability/<path>.json`）。`ArtifactAbility`
与固有表 `mxt:artifact_ability_type` 整体退役；法器定义里的 `abilities` 变成"能力引用或内联能力"
的列表（**内联那半已于同日收缩掉，最终只收技能 id 或 `#技能标签`，见 §12**）；`ToggableArtifactAbility`
升级为与宿主无关的 `Toggable`；冷却成为每个能力实例各自一条的通用能力。**

| # | 决定                                                                                                    | 一句话理由                                                                                                  |
|---|-------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------|
| 1 | `mxt:passive` / `mxt:active` 两个包装类型**删除**                                                             | 它们只是"把技能授予出去"。合并后法器直接列出能力 id，`type` 自己说明它是被动（`mxt:modifier`）还是按一下（`mxt:active`），不再需要第二处声明"我是被动/主动"     |
| 2 | `mxt:flight` / `mxt:storage` / `mxt:upkeep` 变成 **`mxt:ability_type` 的条目**                             | 它们本来就是"这件东西能干什么"，与 `mxt:modifier` / `mxt:channelled` 同级                                                |
| 3 | 法器 `abilities` 接受**注册表 id** 或**内联对象**；内联对象的身份是**派生 id** `<父>/<key>`                                   | 保留"一个文件写完一件法器"的写法，同时给每个条目一个稳定身份（状态、冷却、轮盘格都按它寻址）。沿用现有 `ArtifactCapability` 已经把 `法器id/key` 拼成一个 id 的做法   |
| 4 | 新增接口 `Toggable`（`key` / `displayName` / `state` / `activate`），**判据 = 实现它**，与宿主无关                      | 轮盘只说一句"我能被触发"。技能、法器技能、脚本、命令、HUD、将来的载具面板走同一个入口                                                          |
| 5 | 冷却**按能力实例**独立：`Ability.cooldown` + 附件里的冷却表，键从 `Holder<Ability>` 改成 `AbilityRef`（含派生 id）               | 顶层注册表能力 = 全局一条冷却（老行为）；内联能力 = 每件宿主各一条。容器里的子能力本来就各算各的（`AbilityService.useComposite` 已经是这样），这个口径**保持并推广** |
| 6 | 状态与冷却是唯一的**两处寻址**，都改成 `Identifier`（能力 id 或派生 id）                                                      | 现在 `DataStorageHolder` 已经按 `Identifier` 寻址，冷却表按 `Holder` 寻址；统一成前者，内联能力才可能有状态                           |
| 7 | 借 Origins 的三样：**内联容器能力 + 派生 id**、**类型自带状态组件**（冷却不该让包作者手写两遍）、**`Toggleable` + `KeySettings`**（含"按住"语义） | 见 §9                                                                                                   |

## 1. 合并后的形状

### 1.1 一个定义、三种来源、一个入口

```text
                        ┌─────────────────────────────────────────────┐
   授予来源             │  Ability（mxt:ability 注册表条目，或内联对象）│
   ────────             │  name/description/type/costs/cooldown/...    │
   技能书（technique）──▶│                                             │
   命令 / 战利品        │  type = mxt:active | modifier | triggered |  │
   修炼突破 / 阵法      │         aura | channelled | composite |     │
   物品（法器携带）────▶│         word | empty | flight | storage |   │
   脚本（KubeJS）       │         upkeep                              │
                        └──────────────┬──────────────────────────────┘
                                       │ 地址 = AbilityRef（id 或 <父>/<key>）
                        ┌──────────────▼──────────────────────────────┐
   状态与冷却           │ AbilityAttachment.storage（按 id 寻址）       │
   （宿主 = 持有者）     │ AbilityAttachment.cooldowns（按 AbilityRef）  │
                        └─────────────────────────────────────────────┘
                                       │
   唯一按一下的入口       AbilityActivationService.activate(holder, ref, carrier?)
                                       │            ▲
                                       │            └── 轮盘 / 命令 / KubeJS / HUD / 载具面板
                                       └── mxt:active → AbilityService.use（校验→付款→行为）
                                           mxt:flight → FlightService.mount/dismount
                                           mxt:storage → 打开箱子
```

### 1.2 类型全表（合并后 11 个，全在 `mxt:ability_type`）

| `type`           | 来源                               | 需要物品宿主 | 行为                                                    |
|------------------|----------------------------------|--------|-------------------------------------------------------|
| `mxt:empty`      | 现有                               | 否      | 占位（注册表默认项）                                            |
| `mxt:active`     | 现有                               | 否      | 按一下施放；`slot` 字段                                       |
| `mxt:triggered`  | 现有                               | 否      | 事件触发；`triggers` + `chance`                            |
| `mxt:modifier`   | 现有                               | 否      | 常驻属性修正（原"被动技能"）                                       |
| `mxt:aura`       | 现有                               | 否      | 范围脉冲；`interval` + `radius`                            |
| `mxt:channelled` | 现有                               | 否      | 引导；`tick_interval` + `upkeep_costs`                   |
| `mxt:composite`  | 现有                               | 否      | 组合；`abilities` + `all_required`                       |
| `mxt:word`       | 现有                               | 否      | 口令效果（白名单）                                             |
| `mxt:flight`     | **新**（原 `artifact_ability_type`） | **是**  | 载人飞行：`speed` + `display`；每 tick 的 `costs` 走顶层 `costs` |
| `mxt:storage`    | **新**                            | **是**  | 这件宿主自带容器：`slots`                                      |
| `mxt:upkeep`     | **新**                            | **是**  | 携带期间周期扣费：`interval` + `on_fail`；费用走顶层 `costs`         |

> 合并顺带修掉现在的**重复声明**：`mxt:flight` 有 `costs`、`mxt:upkeep` 有 `costs`，与顶层 `Ability.costs` 是同一个概念的两份字段。合并后
`costs` 只有顶层一处（`mxt:channelled.upkeep_costs` 是"引导维持"这一特殊语义，保留在类型里并改名统一见 §6.3）。

### 1.3 法器定义退化成"能力清单"

> 本节例子包含内联写法；**最终形状只收技能 id 或 `#技能标签`**，见 §12 的收缩记录。

```json
// 之前（两套形状）
{
  "items": "minecraft:diamond_sword",
  "abilities": [
    { "type": "mxt:passive", "abilities": "mxt_test:artifact_guard" },
    { "type": "mxt:active",  "abilities": "mxt_test:firebolt" },
    { "type": "mxt:flight",  "speed": 0.1, "costs": [{ "id": "mxt_test:qi", "amount": 1 }] },
    { "type": "mxt:storage", "slots": 9 }
  ]
}

// 之后（一套形状：引用 + 内联）
{
  "items": "minecraft:diamond_sword",
  "abilities": [
    "mxt_test:artifact_guard",
    "mxt_test:firebolt",
    { "key": "flight",  "type": "mxt:flight",  "speed": 0.1, "costs": [{ "id": "mxt_test:qi", "amount": 1 }], "cooldown": 100 },
    { "key": "storage", "type": "mxt:storage", "slots": 9, "cooldown": 20 }
  ]
}
```

- 字符串 = 引用注册表条目，身份就是那个 id（多件法器可以共用同一条能力定义）。
- 对象 = 内联能力，`key` 在一份宿主定义内唯一，身份 = `<法器 id>/<key>`（`mxt_test:bound_sword/flight`）——*
  *今天 `ArtifactCapability` 拼出来的一模一样**，所以轮盘里已经存着的 `wheel_layout` 格子不用迁移。
- 内联能力没有 `key` 由加载期拒绝（身份不能是空的）。

## 2. 身份：当时为什么考虑过派生 id（**该形状已收缩，见 §12**）

> **已收缩**：本节描述的"内联子能力 + 派生 id + `AbilityRef`"是同日的中间形状，落地当天就被两次收缩取代——先取消内联（
`abilities` 只收 id 或 `#标签`），随后 `AbilityRef` 也删除（能力就是它自己的 `Holder<Ability>`）。保留本节是为了看清"
> 稳定身份"这个需求当初是怎么被满足的，**不要照它写新代码**。

### 2.1 为什么必须有派生 id

合并的硬约束是"内联条目也要有稳定身份"，否则三件事同时崩：

1. **状态**：`DataStorageHolder` 按 `Identifier` 寻址（`storage().get(id, kind)`），内联能力若无 id 就没法存冷却、充能、开关。
2. **冷却**：`AbilityAttachment.cooldowns` 现在是 `Map<Holder<Ability>, Long>`；内联能力没有 `Holder`。
3. **轮盘格**：`WheelSlot(kind, id)` 落盘在网络与附件里，格子的身份到现在为止一直是 `Identifier`。

Origins 的解法值得直接借：`MultiplePower` 把子能力写成 `Map<String, Power>`，`PowerHolder` 把子能力的 id 拼成
`<父 id>_<key>` 并**递归展平**（`PowerHolder.stream()`），子能力 `isHidden() == true`，状态按展平后的 id 存。我们照抄这个思路，只把
`_` 换成 `/`（`.` 与 `_` 在 `Identifier` 路径里合法但语义混乱，`/` 已经是本仓库 "一个 id 里带子项" 的既有写法）。

### 2.2 `AbilityRef`

```java
// 一个能力的地址：注册表条目用 Holder，内联条目用派生 id；两者都能编码成一个 id。
public sealed interface AbilityRef {
    Identifier id();                       // 派生 id 也是 Identifier
    Optional<Holder<Ability>> resolved();  // 内联条目为空
}
```

- 顶层引用：`resolved()` 有值，`id()` = 注册表 id。
- 内联条目：`resolved()` 为空，`id()` = `<父>/<key>`，值随宿主定义一起解码出来（宿主解析时构造，缓存在解析结果里）。
- **序列化**：`cooldowns` / `channelled_ability` 只存 `Identifier`，运行时用 `AbilityRefs.resolve(registries, id)` 还原（派生
  id 按最后一个 `/` 切分，找宿主定义，再按 key 找内联条目）。这与 `ArtifactCapability.parse` 的规则**完全一致**
  ，所以两处可以共用一份实现。
- 一次性代价：`AbilityService`、`AbilityStorage`、`AbilityEventBridge`、`AbilityModifierService`、`WheelSources`、
  `WheelService`、`AbilityWheelEntry`、`WheelEntryKind.exists` 的签名从 `Holder<Ability>` 换成 `AbilityRef`
  。这是本次重构最大的一块机械改动（约 10 个文件）。

### 2.3 内联能力能不能被别处引用

**不能**，也不该能：`AbilityRef.id()` 只在"它所属宿主的解析结果"里可解析。想被别处共用就把它提升成注册表条目（写一个
`mxt/ability/*.json`），法器里写字符串引用它。这条规则要写进文档，否则包作者会以为 `ns:path/key` 到处可用。

## 3. `Toggable`：与宿主无关的"按一下"

### 3.1 接口

```java
/**
 * Something the wheel can trigger. Implementing it is the whole of saying "put me on the wheel"; who owns the
 * ability (an entity's grant, an item being carried) is the caller's business, not this interface's.
 */
public interface Toggable {
    // Unique within one host definition; becomes the second half of the entry's id (`<host>/<key>`).
    String key();

    Component displayName();

    // Empty = a one-shot (nothing stays on, e.g. storage); present = a switch (e.g. flight).
    default Optional<Boolean> state(ToggleContext context) { return Optional.empty(); }

    // Server side only, one call per press; a refusal is a value, never an exception.
    Result activate(ToggleContext context);

    record Result(boolean changed, @Nullable Failure failure) { ... }

    enum Failure { NOT_CARRIED, NOT_OWNED, ALREADY_SET, UNAVAILABLE, ON_COOLDOWN, NO_CARRIER, INSUFFICIENT_COST }
}

// 取代 ArtifactToggleContext：宿主可以是"玩家的授予"，也可以是"玩家携带的某件物品"。
public record ToggleContext(LivingEntity holder, @Nullable ItemStack carrier, AbilityRef ability, FormulaContext formula) {}
```

与现在的 `ToggableArtifactAbility` 的差别只有一条，但很关键：**`activate` 不再自带"这件法器"这个前提**，`carrier`
变成可空的上下文。于是：

| 实现                            | `key()`                | `state()`    | `activate()`                                                       |
|-------------------------------|------------------------|--------------|--------------------------------------------------------------------|
| `mxt:active`（默认实现，所有主动技能免费获得） | `"active"`（或 `slot` 名） | 空（一次性）       | `AbilityService.use(ref, holder, carrier)` —— 冷却、消耗、条件、元素亲和全走同一条管线 |
| `mxt:channelled`              | `"channel"`            | 空            | 起引导 / 放引导                                                          |
| `mxt:flight`                  | `"flight"`             | 在读的那件载具就是本能力 | `FlightService.mount/dismount`                                     |
| `mxt:storage`                 | `"storage"`            | 空            | 打开箱子（复用原版 `ChestMenu`）                                             |
| 将来：护体、剑域、引灵入刃…                | 各自常量                   | 有/无          | 各自实现                                                               |

### 3.2 判据与轮盘

- `WheelEntryKind.ARTIFACT` 退役，`WheelSources.offers` 与 `WheelEntryKind.exists` 的两个 switch 合并成一个（40 号稿 §3 方案
  A 的目标，本稿顺手达成）。
- `AbilityWheelEntry` + `ArtifactWheelEntry` → 一个 `ToggableWheelEntry(ref, toggable, carrier?)`；
  `cooldownTicks(player)` 统一读"该 `AbilityRef` 的冷却"（§4），`usable(player)` 统一问 `ability.condition()` 与冷却。
- 格的显示名：能力的 `name`（`DefinitionText.name`）优先，内联能力没有名字时回退到 `toggable.displayName()`（沿用今天的语言键）。
- **兼容**：`wheel_layout` 里已有 `kind = artifact` 的格子，id 形状（`ns:path/key`）在新模型里**含义不变**（还是"父定义 +
  key"）。迁移只需把那个 kind 映射成新的统一 kind（或保留 `ARTIFACT` 作为旧值的别名）。这是选 `/` 拼法的直接红利。

### 3.3 "其他地方要用可以直接接入"

唯一入口：

```java
public final class AbilityActivationService {
    // 服务端；ref 由调用者给，carrier 由来源决定（技能书/命令 = null，法器 = 那件物品）
    public static Toggable.Result activate(LivingEntity holder, AbilityRef ref, @Nullable ItemStack carrier);
    // 只问状态，不改变任何东西（客户端 HUD / 轮盘画状态用）
    public static Optional<Boolean> state(Player player, AbilityRef ref);
}
```

调用者：`WheelService.trigger`（轮盘）、`/mxt ability toggle`（命令）、`MxtKubeJsAbilityBindings`（脚本）、HUD
面板、将来的载具/法宝面板、其他模组（经 `api/` 里的接口）。**权限、冷却、消耗、条件都在 `activate` 内部完成**，调用者不重复。

## 4. 独立冷却

### 4.1 现状（已经"每能力一条"，但不完整）

| 部分   | 现在                                                                                                    | 问题                                                                                                           |
|------|-------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------|
| 声明   | `Ability.cooldown`（顶层 `NumberProvider`）**加上** `components: [{"type":"mxt:cooldown","ticks":N}]`       | **同一个冷却写两遍**：顶层那个用于 `AbilityService.prepare` 的判定与轮盘显示，存储那个用于状态读取（`mxt:storage_cooldown` 条件）。两处数值不一致时行为取决于谁先写 |
| 状态   | `AbilityAttachment.cooldowns`（`Holder<Ability>` → 截止 tick）**加上** `mxt:cooldown` 存储（`duration` + 写入时刻） | 两份状态：一份在冷却地图里，一份在存储里；`revoke` 时清两处                                                                           |
| 键    | `Holder<Ability>`                                                                                     | 内联能力没有 `Holder`                                                                                              |
| 覆盖对象 | 只有 `mxt:ability` 里 8 个类型                                                                              | `mxt:flight` / `mxt:storage` / `mxt:upkeep` 完全没有冷却                                                           |

### 4.2 目标口径

1. **所有 11 个类型都能写 `cooldown`**（顶层字段，`NumberProvider`，默认 `0`）。`mxt:storage` 因此可以"开一次箱 20
   秒内不能再开"，`mxt:flight` 可以"落地后 5 秒内不能再起剑"。
2. **冷却按 `AbilityRef` 各算各的**：
    - 顶层条目 → 一条冷却（无论从技能书、命令还是三件法器上来的，都是同一条）——**这是老行为，不变**。
    - 内联条目 → 派生 id 一条，于是"同一份 `<剑>/flight` 只有一把剑那一条"，两把不同的剑各自独立。
    - `composite` / 容器里的每个子能力各自一条（`AbilityService.useComposite` 已经逐步写各自的冷却，保持）。
3. **状态只留一份**：`mxt:cooldown` 存储是唯一真源（它已经记着 `duration` 与写入时刻），`AbilityAttachment.cooldowns` 退化成它的
   **索引缓存**（或直接删掉，改由 `AbilityStorage` 读存储；`isOnCooldown` 只在每 tick 的手里被查询，读一次
   `DataStorageHolder` 是可接受的）。
4. **声明只写一遍**：`cooldown` 字段**自动**产生 `CooldownDataStorage`（就像 Origins 的
   `HasCooldownPower.createComponents` 自动 `collector.add(new CooldownComponent(...))`）。`components` 列表里的
   `mxt:cooldown` 保留为"显式覆盖长度"的唯一写法（老包兼容），文档改成"通常不用写"。
5. **起算点**：仍然是"提交成功那一刻"（`CooldownDataStorage.changedAt`），不是"施放开始"。读条技的冷却从读条结束算，与今天一致。
6. **可选的共享冷却组**（**待拍板**，Origins 没有这个概念）：`cooldown_group`
   （字符串）；同一宿主上同组的能力共用一个截止时间。收益是"两个技能共享一个冷却"这类设计；代价是冷却表要按组再寻址一层。**建议
   P2 再说**，先让"每实例独立"落地。

### 4.3 冷却的显示（借 Origins 的 `hud_render`）

Origins 的 `CooldownSettings(cooldown, hud_render)` 让**每个能力自己声明冷却怎么画**（
`HudRenderable.getMinValue/getMaxValue/getValue/shouldRender`）。我们的对应物现在是：轮盘的 `cooldownTicks` +
`mxt:storage_cooldown` 条件 + 资源条框架（`data/resourcebar`）。

建议（P2，可选）：给顶层加一个可选的 `hud` 子对象（`{"type": "mxt:cooldown_bar", ...}`），把一个能力的冷却/充能画进 HUD 布局框架（
`screen/overlay/hud/` 已经是可拖动元素框架，加一个"能力状态元素"即可）。这属于"合并后的附加收益"，不是合并的前提。

## 5. 物品宿主（carrier）

### 5.1 来源要带上物品

`AbilityAttachment` 的来源账本键是 `Identifier`（`AbilitySources.equipment(slot, stack)` = `mxt:equipment/<槽>/<物品>`
），所以"这个能力是从哪件物品来的"**现在已经能从来源 id 反推**——包括槽位。于是：

```java
// 一个能力此刻的宿主物品：按来源 id 反查持有者的槽（双手 + Curios），第一件命中者胜。
public final class AbilityCarriers {
    public static Optional<ItemStack> find(LivingEntity holder, AbilityRef ref);
    public static List<ItemStack> all(LivingEntity holder, AbilityRef ref);
}
```

- 来源 id 已经是 `equipment/<slot>/<namespace>/<path>`，反查不需要新存档字段。
- `mxt:flight` / `mxt:storage` / `mxt:upkeep` 声明"我需要 carrier"（`AbilityType.requiresCarrier()`，默认 `false`）；拿不到就返回
  `Failure.NO_CARRIER`（对应今天的 `NOT_CARRIED`），**不报错**——被技能书授予一次飞行能力是合法写法，只是它永远飞不起来。
- 现在 `ArtifactToggleService` 的"第一件携带者胜"口径直接搬进 `AbilityCarriers.find`。

### 5.2 三处物品状态的去向

| 现在                                             | 之后                           | 迁移                                                                                                                 |
|------------------------------------------------|------------------------------|--------------------------------------------------------------------------------------------------------------------|
| `FlightAttachment.archetype: Holder<Artifact>` | `AbilityRef`（就是那条飞行能力）       | 存档老值（法器 id）能解码成一个 `AbilityRef`；老飞行再登入会被判成"那次飞行的能力已不是这条定义"而落剑（可接受，飞行本来就是瞬时状态；要更稳就按法器 → 旧 `mxt:flight` 条目做一次映射，见 §7） |
| 储物内容在物品组件 `mxt:artifact_storage`               | 不变（容量改读 `mxt:storage.slots`） | 无                                                                                                                  |
| `mxt:artifact_state`（归属 + 温养）                  | 不变（它本来就是**物品**的状态，不是能力的）     | 无                                                                                                                  |
| `mxt:upkeep` 无状态（世界时间锚）                        | 不变                           | 无                                                                                                                  |

**刻意不做的**：不把物品状态搬进 `AbilityAttachment`。飞行"哪件载具"、储物"里面装了什么"本质属于物品；搬到玩家附件会把"
两把一样的剑"变成分不开的一件事（40 号稿 §2.1 的结论仍然成立，只是现在不需要它当阻碍了）。

### 5.3 归属（owner）

- `artifact.require_owner`（认主才能飞行/储物）留在**法器定义**上：它说的是"这件东西"，不是"这条能力"。
- `upkeep.owner_only` 留在 `mxt:upkeep` 类型里（它说的是"这条周期的费用由谁付"）。
- 合并**不**引入通用的 `requires_owner` 字段：两个旗标语义不同，合流只会让包作者猜。

### 6.2 `artifact.abilities`

> 本节描述的是合并当时的"id 或内联对象"形状；**内联已收缩掉**，字段最终只收技能 id 或 `#技能标签`（见 §12）。

- 内联对象的字段 = `Ability` 的字段 + 必填 `key`。

      key，加载期自然拒绝）。

### 10.4 开放项

- `AbilityRef` 的缓存：派生 id 每次解析都要找宿主定义 → 需要一张"世界加载期构建、注册表实例变化时失效"的索引（与
  `DamageElements` 的缓存键口径相同）。
- 内联能力与 `/reload`：宿主定义重建时，`AbilityAttachment` 里按派生 id 存的状态**保留**（id
  没变）——这是期望行为，但要写清楚"改 key 等于换了一个能力，旧的冷却与充能留在存档里等清理"（`revoke` 时清，但内联能力没有
  revoke 事件）。
- `composite` 与"父子活跃"语义：要不要借 `Power.isActive` 让容器成为"开关一关，子能力全停"。
- `ServerCache` 的校验点搬家：intent 校验删掉后，跨定义校验还剩哪些（法器认领同一物品、轮盘 id 可解析、内联 key 唯一）。
- **技能自带的容器（`mxt:storage`）在"没有物品"时内容存哪**：现在必然挂在物品组件上；合并后一个被技能书授予的 `mxt:storage`
  语法合法但无处可存。三个选项：加载期拒绝非物品宿主的 `mxt:storage`（推荐，简单明确）、退化成"打开时临时生成"、或引入"
  能力自己的容器状态"（等于把 Origins `InventoryComponent` 那套搬进来，与 §5.2 的方向相反）。

### A.0 结论

**能统一，但"统一"分四层，收益与代价差一个量级；只有前两层值得现在考虑。**

| 层     | 统的是什么                                                                     | 判定                                                                                                       |
|-------|---------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------|
| ① 机制层 | "可发动条目"的身份与校验、来源、付款、tooltip                                               | **值得做**：`ToggableArtifactAbility` 与 `ActiveAbilityType` 是同一个概念的两份实现，轮盘现在为此各维护一套 kind / 身份 / 校验（附录 A.3.1） |
| ② 形状层 | 法器能力从内联条目变成**命名注册表条目**（可被多件法器引用、可打标签）                                     | **可做**：不动运行模型，解决"每把剑重复写一份参数"的真实痛点（附录 A.3.2）                                                              |
| ③ 实体层 | 把 `mxt:flight` / `mxt:storage` / `mxt:upkeep` 变成 `AbilityType`，法器退回"授予来源" | **不建议现在做**：`flight` / `storage` 的状态、身份、驱动三项都与 `Ability` 的模型对不上（附录 A.2），换来的只是"概念数 2→1"                    |
| ④ 反向  | 把 `Ability` 并进法器能力                                                        | **不可行**：技能必须能脱离物品存在（技能书 / 命令 / 修炼 / 战利品 / 阵法 / KubeJS 都在授予技能）                                            |

一句话概括：**`Ability` 是"你会什么"（注册表单例 + 持有者身上的授予与状态），`ArtifactAbility` 是"这件东西能让你做什么"
（物品堆 + 定义上的性质与状态）。两者只在一处真的相交——`mxt:passive` / `mxt:active`——而那一处本来就是"法器把技能授予出去"
，不是"两种能力"。**

### A.2 对不上的三点（实体层合并的硬阻碍）

#### A.2.1 状态归属：持有者 vs 物品

`Ability` 的运行状态全在**持有者**身上，键是 `Holder<Ability>`：技能撤销再授予、换一件物品，冷却与充能都还在——技能是"人"的属性。
`flight` / `storage` / `upkeep` 的状态全在**物品**上：飞的是哪件法器（`FlightAttachment.archetype`）、箱子里装了什么（物品组件）、这件东西归谁（
`mxt:artifact_state`）。

合并必须二选一：

- 把法器状态搬进持有者附件 → 同一个玩家同时带两把剑就分不开了，除非把物品堆身份写进键，"技能状态"实际变成"物品实例状态"；
- 或者给 `Ability` 引入 **per-item 实例**（`scope: entity | item` + 实例键）→ 给现在很干净的"注册表单例 + 持有者账本"
  加一层实例化，`AbilityStorage` 的键要从 `Holder<Ability>` 变成 `(Holder<Ability>, 实例)`。

#### A.2.2 身份与参数：注册表 id vs 物品堆

`Ability` 是**共享**的：同一份技能定义可以被法器、技能书、命令、战利品分别授予，参数写在定义里、所有持有者一样。
`flight.speed` / `storage.slots` 是 **per-artifact** 的：两把剑要不同速度，现在各自在自己的 `artifact` 定义里写一份。

合并必须二选一：

- 每把剑写一个独立的技能定义（参数随定义走）→ 包作者从"一个文件写完"变成"两个文件 + 引用"，`mxt:flight` 这类能力会大量重复；
- 或者允许**内联定义 / 参数覆盖**（`Artifact.abilities[]` 里直接写技能对象）→ 形状上等于"注册表条目可以内联"。
  `util/codec/RegistryCodecs` 目前只有 `holderOrTag` / `holderOrTagList` / `keyOrTagList`，**没有** inline-or-holder
  助手，要新增一个。

#### A.2.3 驱动者：一次施放 vs 别的东西

`AbilityService` 只有一条主线：**校验 → 计划付款 → 提交 → 跑动作**，一次施放有开始有结束（读条与引导只是把它拉长）。`flight`
是持续状态机（每 tick 位置、朝向、消耗、下马），`storage` 是一个界面入口——它们都不是"施放"。塞进 `AbilityType` 只会得到两个"
看着像技能、其实不是"的类型，`AbilityService` 里要多两条旁路——**那不是统一，是把两个系统搬进同一个 switch**。

反过来，`mxt:upkeep`（携带期间按周期付 `costs`，付不出跑 `on_fail`）与 `ChannelledAbilityType`（引导期间按 `tick_interval` 付
`upkeep_costs`）**是真的挨着**：差别只在"谁在维持"（持有者主动引导 vs 物品被动索取），以及 `on_fail` 走的是 `ItemAction` 通道。

### A.3 四个方案

#### A.3.1 方案 A（当时建议先做）：统一"可发动条目"这一层

现状里最明显的重复：`ToggableArtifactAbility`（`key()` / `displayName()` / `state()` / `activate()`）与
`ActiveAbilityType`（"轮盘能不能触发它"的判据）**是同一个概念的两份实现**。轮盘为此维护两套东西：

- `WheelEntryKind.{ABILITY,ARTIFACT}` 两个 kind，两套身份（注册表 id vs `法器id/key`）；
- 两处存在性校验：`WheelEntryKind.exists` 的 `ABILITY` 与 `ARTIFACT` 两个 case；
- 两处授予校验：`WheelSources.offers` 的 switch（`abilities(...)` vs `ArtifactToggleService.find(...)`）；
- 配置界面左右两个池，以及 `WheelSources.abilities` / `toggles` 两条来源读取路径。

可以做的：把"可用性 + 触发"的判定收成一份（`WheelMenuEntry` 已经是渲染与交互侧的共用契约，缺的是**身份与可用性**的共用部分）——一个
`EntryRef(kind, id)`，加 `usable(player)` / `trigger(player)`；两个 kind 的 `exists` 与 `offers` 收进一张表。配置界面的左右分池
**不必合并**（玩家看得懂"技能 / 法器"两栏），合并的只是判定。

代价：`WheelSlot(kind, id)` 是**落盘附件**（`wheel_layout`）也是网络包字段，kind 收窄是破坏性变更（`kind` 收成 3
值需要迁移或作废旧布局）；配置界面分池与文案要跟着改。收益：新增一种"可发动的东西"只实现一个接口，不再动两处 switch。

#### A.3.2 方案 B（当时建议，独立于 A）：把法器能力做成命名注册表条目

新增数据包注册表 `mxt:artifact_ability`，条目形状就是现在的 `ArtifactAbility`（`type` 仍走固有 `mxt:artifact_ability_type`
分派），并让 `Artifact.abilities[]` 接受 **id** 或 **内联对象**（需要新增 `RegistryCodecs` 的 inline-or-holder 助手；
`Artifact` 的字段类型相应从 `List<ArtifactAbility>` 变成 `List<Holder<ArtifactAbility>>` 或 `Either` 形态）。

- **收益**：两把剑共用一份 `mxt:flight` 参数；`#tag` 可以把一族法器共有的能力打包；`ServerCache.checkGrantedAbilityKinds`
  这类跨定义校验可以升级成注册表级校验；tooltip 与文档有稳定引用对象（`DefinitionText` 的 `name` / `description`
  可以直接给法器能力用，现在它们连显示名都只能写代码常量或语言键）。
- **代价**：数据包注册表 34 → 35 张（`docs/数据包格式.md`、`docs/模块实现审计.md`、`docs/guide/**`、文档站中英各一份全部要同步）；
  `Artifact` 的取值路径（`abilities()` / `flight()` / `storage()` / `upkeep()` / `toggables()` / `grantedAbilities()`
  ）都要改成先解析 Holder；`ServerCache` 的校验时机从"随法器定义就地检查"变成"注册表加载后统一检查"。
- **不动的**：运行模型。`FlightService`、`ArtifactUpkeepService`、`ArtifactStorageService`、轮盘、状态归属、存档全部不变。这是它比方案
  C 划算的原因。

#### A.3.3 方案 C（当时不建议现在做——最后被采纳，代价见正文）：`flight` / `storage` / `upkeep` 变成 `AbilityType`

做法：新增三个 `AbilityType`，法器只用 `mxt:passive` / `mxt:active` 把它们授予出去，`artifact_ability_type` 整张表退役，
`ServerCache` 的 intent 校验换成"这三个类型是不是主动"。

必须一起解决：

1. **物品作用域**（附录 A.2.1）：`AbilityStorage` 的键与 `FlightAttachment.archetype` 的语义都要改（现在是法器定义 id）；
2. **物品通道**（附录 A.2.3）：`upkeep.on_fail` 是 `ItemAction`，`Ability` 只有 `EntityAction` / `BiEntityAction`；`Ability`
   的 16 个 group 槽已经用 `MiscCodecs.pair` 撑满，再加通道要么再并一组、要么给 type 引入子对象；
3. **授予模型的副作用**：飞行从"拿着剑就能飞"变成"被授予期间能飞"，同时背上冷却 / 读条 / 充能 / 元素亲和 /
   目标选择器这一整套对飞行无意义的字段（它们在 `Ability` 上，不按 type 可选）；
4. **轮盘身份**：等于方案 A 的全部内容；
5. **存档迁移**：`wheel_layout`、`FlightAttachment`、老包的 `artifact.abilities[]` 写法；
6. **语义倒退**：`storage.slots` 是"这件东西的容量"，共享技能定义后"每件法器不同格数"只能靠独立定义表达。

#### A.3.4 方案 D（不可行）：把 `Ability` 并进法器能力

技能必须能脱离物品存在：功法手册（`mxt:technique` 载体）、`/mxt ability`、`GrantAbilityAction`、`GrantAbilityLootFunction`、
`CultivationGrantService`（突破授予）、`FormationActionRunner`（阵法授予）、KubeJS 都在授予技能。法器只是**其中一个来源**（
`AbilitySources.equipment` / `CURIOS`）。

### A.4 终局形态：如果一定要"概念数 = 1"

要让 `flight` / `storage` / `upkeep` 变成普通技能类型，`Ability` 要先长出三样东西：

1. **作用域与实例键**：`scope: entity | item`，状态索引从 `Holder<Ability>` 变成 `(Holder<Ability>, 实例)`；
2. **物品通道**：`ItemAction`，或一个"物品槽上下文"（`upkeep.on_fail`、托管组件的读写）；
3. **per-instance 参数覆盖**：内联定义或参数覆盖子对象（否则每把剑一份定义）。

代价：`AbilityService` 的"一次施放"主线要为"持续状态机"开旁路；`Ability` 的字段继续膨胀；`AbilityAttachment` 从"技能账本"
变成"技能 + 物品实例账本"。**收益是概念数，代价是内核复杂度**——按 [
`05_技能系统与固有注册表.md`](05_技能系统与固有注册表.md) 记的现状，这笔交易不划算。

### A.5 若采纳，建议的推进顺序

1. **方案 B**：法器能力注册表化 + 允许 id 引用与内联对象。独立、不破坏运行模型，先解决复用。

4. **`flight` / `storage` 保持现状**，除非出现"同一个能力需要由非物品来源提供"的真实需求。
