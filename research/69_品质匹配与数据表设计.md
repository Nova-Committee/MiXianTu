# 69 品质匹配与数据表设计

> **基准**：工作树（2026-10-04，含 `68` 的供热改道）；代码事实对着 `ItemQualityService` / `ItemMatcher` /
> `ItemQualityCondition` / `CostTransaction` / `ForgingMaterial` / 画符工作站逐处读过，NeoForge 侧对着
> `neoforge-26.1.2.99-sources.jar` 与 `minecraft-patched-26.1.2.99-sources.jar` 读过。
> **状态**：**设计稿，未实现**。本文只描述"该长成什么样"与"为什么"，字段级最终形状实现后以代码与
> [`docs/数据包格式.md`](../docs/数据包格式.md) 为准。

## 0 结论

品质今天只有**一个解析入口**，但**两套匹配语言**都不读它。要"让大部分地方支持 quality"，不是往每个输入点
各写一段判定，而是分三层：

1. **事实层**——档位从哪来。在既有的"组件 → 锻造结果 → 定义默认 → 灵植"之外，新增**一格数据表**：
   NeoForge 的 **Registry Data Map**（`data/mxt/data_maps/item/quality.json`，键可写物品 id 或 `#物品标签`，
   值就是档位）。它一次补上"普通材料没有默认档数据源"这个缺口，而且**读它不需要 `Provider`**。
2. **要求层**——"够不够档"只实现一遍：新记录 `QualityRequirement`（`quality` 集合/标签成员判定 +
   `min_quality` 按品质链序号比高低），唯一出口 `QualityRequirements.test(access, stack, requirement)`。
3. **适配器层**——四种薄壳把这套要求挂到所有"收物品"的地方：**物品条件**、**`ItemMatcher` 条目**、
   **NeoForge 自定义材料（`IngredientType`）**、**Java 单点检查**。前两个管我们自己的字段
   （`Cost`、五张 binding、`mxt:item_matcher`、货币、灵植…），第三个**一次覆盖所有配方**
   （原版合成、其他模组配方、我们的灵气合成与画符）。

**不新增数据包注册表**：注册表总数仍是 39。数据表不是注册表。

## 1 现状（代码事实）

### 1.1 档位今天怎么被读

`ItemQualityService.find(Provider, ItemStack)` 是唯一解析入口，按固定四格取第一个命中的
（`runtime/item/ItemQualityService.java:128-159`）：组件 `mxt:quality` → 锻造结果 `mxt:forging_result` →
定义默认（法器 / 符箓 / 功法 / 炉型）→ 灵植 `spirit_herb.quality`。消费点已经不少：锻造的
`materialModifier`、炼丹的 `inputModifier`（都取投入材料的最低档）、货币 `value_multiplier`、
使用门禁 `condition`、tooltip、`/picker`、`/quality`、KubeJS。

### 1.2 两套匹配语言，都不读品质

| 语言 | 形状 | 谁在用 | 能不能按档筛 |
| --- | --- | --- | --- |
| 原版 `Ingredient` | `{"item"/"#tag"}`，`HolderSet<Item>`，`test` 就是 `stack.is(...)` | 所有配方（`mxt:spirit_shaped`/`shapeless`、`mxt:talisman_drawing`、原版与其他模组） | 只能靠 NeoForge 的 `neoforge:components` 做**精确相等** |
| 我们的 `ItemMatcher.Entry` | 7 种条目（`item` / `tag` / `wildcard` / `regex` / `spirit_storage` / `herb_tag` / `technique`，`registry/MxtItemMatchers.java:20-26`） | `Cost` 的 `mxt:item`（`ItemCost.java:21-25`、`ItemCostDraft.java:31-43`）、五张 binding 的 `items`、`mxt:item_matcher` / `item_id` / `item_tag` 条件、货币 `items`、灵植 `entries`、拾取器 | **不能**（没有任何条目读品质，也没有"≥某档"的比较） |

### 1.3 读不到品质的输入点（按模块）

| 输入点 | 现在的判据 | 位置 |
| --- | --- | --- |
| 丹炉 主药/辅药/药引 仓 | 被某条 `spirit_herb` 认领 + 该角色药力 > 0 | `AlchemyFurnaceInventoryBlockEntity.java:159-173` |
| 锻造材料 12 格 | 蓝图 `input` 的硬物品 id + 数量 | `ForgingMaterial.java:18-36`、`ForgingSurface.java:58-68` |
| 画符符纸格 | 硬编码 `stack.is(paper())` | `TalismanWorkstationMenu.java:325`、`TalismanWorkstationService.java:319-325` |
| 符笔颜料 | 一个物品标签 + 全局服务端配置 | `BrushPigmentService.java:34-46, 66-68` |
| 灵气合成网格 | 只由配方匹配筛 | `SpiritCraftingMenu.java:262` |
| 灵植种子 | `growth.seeds` 的 matcher 条目 | `SpiritHerbService.java:49-55` |

已经能读品质的两处是例外：丹炉**核心物品**（走 `ItemQualityService.check`）与货币的
`unavailable_when`（`ItemCondition` 里可写 `mxt:item_quality`）。

### 1.4 症结是 `Provider`

`ItemQualityService.find` 要 `Provider`（后两格要查定义与灵植），而两套匹配语言的判定入口
（`Ingredient.test(ItemStack)` / `ItemMatcher.Entry.matches(ItemStack)`）**都拿不到 registry access**。
所以"按档匹配"要么改这两个签名（牵动十几个调用点），要么让匹配能**自己读到档位**。
本设计选后者：把"物品/标签声明的档位"放进一张**可同步、按键 O(1) 的数据表**，无 access 也能读。

## 2 NeoForge 给的两个钩子

### 2.1 Registry Data Map（机制全文见 [`70`](70_数据表与ItemMatcher替代评估.md)）

数据表（Registry Data Map）是 NeoForge 的"**注册表条目 → 值**"数据包表面：键可写条目 id 或 `#标签`（加载期展开成
条目），值由我们自己的 codec 决定，支持 `replace` / `remove` / `neoforge:conditions` / 可选同步，**读它不需要
`Provider`**。机制细节、能力边界，以及"能不能替代 `ItemMatcher` 那堆表"的逐条评估，全部在
[`70`](70_数据表与ItemMatcher替代评估.md)，本稿只用到它的三点：值可以放 `Holder<ItemQuality>`、可同步到客户端、
按 `stack.getItemHolder()` 查（必须是 reference holder）。

### 2.2 `ICustomIngredient` / `IngredientType`

NeoForge 把 `Ingredient.CODEC` 包成了 `Codec.xor(自定义材料分派, 原版 HolderSet)`
（`IngredientCodecs.codec`），分派键是 `neoforge:ingredient_type`，类型注册在静态注册表
`neoforge:ingredient_serializer`（`NeoForgeRegistries.Keys.INGREDIENT_TYPES`）。NeoForge 自带
`neoforge:components`（`DataComponentIngredient`，字段 `items` / `components` / `strict`）、
`neoforge:compound`（`children`）、`neoforge:difference`、`neoforge:intersection`、`neoforge:block_tag`、
`neoforge:custom_display`。

自己注册一种的收益是**一处实现换来所有配方**：任何收 `Ingredient` 的地方（原版配方、别的模组的配方、
我们的 `mxt:spirit_shaped` / `shapeless`、`mxt:ingredient` 物品条件）都能写这一种材料。

两条硬约束：

- **`items()` 不能为空**：`ICustomIngredient.items()` 的注释写明"至少要返回一件物品，否则这条材料被视为空，
  **整条配方失效**"，而且查看器（JEI/EMI）靠它枚举候选。所以自定义材料**必须自带一个可枚举的物品集**。
- **`isSimple()` 的语义是"只看物品就能判"**：`DataComponentIngredient.isSimple()` 是 `false`，
  `Compound` / `Difference` / `Intersection` 都是"有一个子材料不 simple 就不 simple"。我们这种读档位的材料
  必须报 `false`，否则 `StackedContents` / 配方书会把它当成纯物品材料。

## 3 设计

### 3.1 三层

```
事实层  组件 / 锻造结果 / 定义默认 / 【数据表 mxt:quality】/ 灵植   →  ItemQualityService.find
                 ↓  一处读法，两种强度（有 access / 无 access）
要求层  QualityRequirement { quality[], min_quality }              →  QualityRequirements.test
                 ↓  一份 codec
适配器  物品条件 ｜ matcher 条目 ｜ 自定义材料 ｜ Java 单点检查
```

### 3.2 事实层：数据表 `mxt:quality`

- 注册：`DataMapType.builder(Identifier("mxt", "quality"), Registries.ITEM, ItemQuality.CODEC).synced(ItemQuality.CODEC, false)`
  （值类型待拍板，见 §7）。
- 解析顺序建议改为：组件 → 锻造结果 → **定义默认** → **数据表** → 灵植。定义在前，现有行为一字不变，
  数据表专职"普通材料的默认档"。
- `ItemQualityService` 增加一个**可空 access** 的读法：`find(@Nullable Provider access, ItemStack stack)`，
  `null` 表示"只读组件 / 锻造结果 / 数据表"三格（这三格都不需要 registry）。
- 客户端：数据表同步过来之后，"物品/标签声明的档位"在客户端同样可读，无 access 也画得出档位。

### 3.3 要求层：`QualityRequirement`

```java
public record QualityRequirement(List<Either<Holder<ItemQuality>, TagKey<ItemQuality>>> qualities,
                                 Optional<Holder<ItemQuality>> minQuality) { … }
```

- `qualities`：成员判定（可用 `#品质标签`）。**"≥三档"今天就能靠标签写**，代价是每加一档要回来补标签；
- `minQuality`：按 `ChainCache.rankOf`（`util/ChainCache.java:111`）比序号，**跨链一律 `false`**——
  不同链的序号没有可比性，这里不许"不可比就放行"；
- 两者同写＝都要满足；都不写＝不筛档（等价于"任何档"，含没有档位的物品——这点要在文档里写清）。
- 唯一出口：`QualityRequirements.test(@Nullable Provider access, ItemStack stack, QualityRequirement requirement)`。
  无 access 时只读那三格，读不到就答否——**确定、可文档化**，不是随机。

### 3.4 四个适配器

| 适配器 | 新增什么 | JSON | 一次覆盖 |
| --- | --- | --- | --- |
| **物品条件** | `mxt:item_quality` 加可选 `min_quality` | `{"type":"mxt:item_quality","min_quality":"example:tier_3"}` | 所有跑 `ItemCondition` 的地方（货币 `unavailable_when`、五张 binding 的 `conditions`…） |
| **matcher 条目** | 新条目 `mxt:quality`：`items`（必填，`ItemMatcher` 条目列表）+ 上面那份 requirement | `{"type":"mxt:quality","items":["mxt:blank_talisman"],"min_quality":"example:tier_3"}` | `Cost` 的 `mxt:item`、五张 binding 的 `items`、`mxt:item_matcher` / `item_id` / `item_tag`、货币 `items`、灵植 `entries`、`tool_binding`/`blueprint_binding`、`artifact.items`、拾取器 |
| **自定义材料** | `ICustomIngredient` + 注册 `IngredientType` 到 `neoforge:ingredient_serializer` | `{"neoforge:ingredient_type":"mxt:quality","items":"mxt:blank_talisman","min_quality":"example:tier_3"}` | **所有配方**：原版、其他模组、`mxt:spirit_shaped`/`shapeless`、`mxt:talisman_drawing`、`mxt:ingredient` 条件 |
| **Java 单点检查** | 无新类型，调 `QualityRequirements.test` | — | 机器槽位（丹炉输入仓、符纸格、锻造材料、灵植种子），以及将来炉型/丹方的材料门槛 |

两个新适配器都**要求 `items` 必填**：`ItemMatcher` 是 OR 列表，不自带物品约束就没法表达"必须是符纸且≥三档"；
材料侧则因为 §2.2 的 `items()` 非空是硬要求。

`itemLevel()` / `isSimple()` 的口径：

- matcher 条目：`itemLevel() = requirement.isEmpty() && items 全为 itemLevel`。有档位要求时返回 `false`，
  `runtime/hold/HoldLookup.java:60-68` 那套"itemLevel 建索引 / 非 itemLevel 逐堆问"的分工立刻正确；
- 材料：`isSimple() = requirement.isEmpty() && items.isSimple()`。

### 3.5 Provider 矩阵

| 求值场景 | 有 `Provider` | 能读到哪些格子 |
| --- | --- | --- |
| 数据包定义解码（注册表 / 配方 / 条件） | 有 | 五格全读 |
| `ItemCondition` 求值 | 有（`ctx.holder().level()`） | 五格全读 |
| 配方匹配（`Ingredient.test`） | 没有 | 组件 + 锻造结果 + **数据表** |
| `ItemMatcher.Entry.matches`（cost / binding / `HoldLookup`） | 没有 | 同上 |
| 客户端 tooltip / 渲染 | 有（客户端同步的注册表与数据表） | 五格全读 |

服务端匹配（配方、扣费）实际上拿得到服务器：适配器内部用
`ServerLifecycleHooks.getCurrentServer()` 取 `registryAccess`（仓库里 `MxtDatapackRegistries.holderOrEmpty`、
`CurrencyValueService.exchangeOffers` 已是这个写法），取不到（纯客户端）就退成三格。
**不建议**地改 `Ingredient.test` / `Entry.matches` 的签名——那是十几个调用点的连锁改动。

### 3.6 缓存

数据表本身已经是 `Map<ResourceKey, T>`，按条目查是 O(1)，不需要我们自建索引。若将来给
`ItemMatcher` 建"按物品"的索引（照 `ChainCache` 的写法），失效点用 **`DataMapsUpdatedEvent`**
（服务端 reload 与客户端同步都会发），而不是只挂 `TagsUpdatedEvent`。

## 4 与现状的差异

| 变化 | 影响面 |
| --- | --- |
| 新增数据表 `mxt:quality` | 新数据包表面（一个新目录，作者要学）；**注册表总数不变** |
| `ItemQualityService.find` 加一格 + 可空 access 重载 | 一个类；老调用点不改 |
| `mxt:item_quality` 加可选 `min_quality` | 老 JSON 不变（字段可选）；语义新增 |
| 新条目 `mxt:quality`（matcher） | 老 JSON 不变（新类型）；`MxtItemMatchers` +1 行 |
| 新 `IngredientType` `mxt:quality` | `NeoForgeRegistries.Keys.INGREDIENT_TYPES` +1 行 + 一个类 |
| `QualityRequirement` / `QualityRequirements` | 新类两个；`ItemQualityCondition` 内部改成复用它（字段名不变） |

**没有破坏性改动**：不删字段、不改字段类型、不动存档与附件、不动现有解析顺序里已命中的格子。

## 5 不做 / 推迟

- **不做"把档位物化到堆上"**：世界里的既有物品（被 `artifact` / `spirit_herb` / `technique`
  认领的那些）没有组件，无法批量补写；所以"定义默认"那一格必须保留，匹配必须能走解析链。
- **不给品质加"效果强度"字段**（`46` §5 已定）。
- **不做 matcher 的通用 AND 组合器**：用 `mxt:quality` 自带的 `items` 表达"物品 AND 档位"就够；
  真需要通用组合时再说。
- **不让 `min_quality` 跨链比较**（§3.3）。
- **`P2`（`ForgingMaterial` → 材料化）与 `P3`（符纸格放宽）本轮不做**：它们是本套落地之后的收尾——
  那时 `ForgingMaterial` 只要改成"材料 + 数量"，符纸格只要从硬 id 换成物品标签，档位门槛直接复用
  `QualityRequirements.test`。两条的前提与代价见本稿 §8。
- **不改颜料（`P4`）**：按用户要求忽略。

## 7 待拍板

| 议题 | 建议 | 备选 |
| --- | --- | --- |
| 数据表在解析顺序里的位置 | 定义默认**之后** | 定义默认之前（数据表更强） |
| 数据表值类型 | 直接 `Holder<ItemQuality>`（复用 `ItemQuality.CODEC`，最小） | 一份记录（如 `{quality, min}`；§10 已确认值可以任意复杂，但将来加字段是破坏性改动）；`Identifier` + 用时回查（更保守，且要改读法） |
| `min_quality` 跨链 | `false` | 报加载期 problem |

| 同步 | `synced(ItemQuality.CODEC, false)` | 不建同步列（客户端读不到，tooltip 之外都要掉档） |

## 8 附：`P2` / `P3` 在这套之后怎么接（本轮不做）

- **`P2` 锻造材料**：`Ingredient` 没有数量，所以形状是"材料 + `count`"（照 NeoForge `SizedIngredient` 的
  `NESTED_CODEC`：`{"ingredient": …, "count": 3}`；**不要用它的 `test`**，那个要求单堆够量，而锻造是跨格求和）。
  连带：`StartupMaterials` 要记**实际取走的堆**（现在记"声明堆"，带组件的材料会退化成不带组件）；
  `ForgingBlueprint.inputError` 的"同一物品写两次"要退化；界面显示改用 `ingredient.items()` 的第一件。
- **`P3` 画符符纸格**：槽位是 `Predicate<ItemStack>`，放宽成物品标签一行就够（代价侧的 `ItemEntry` 换成已存在的
  `TagEntry`）；但**"符纸必须≥三档"要靠 `QualityRequirements.test`**，`Ingredient` / 标签都给不了；
  "好纸画好符"是另一个消费点（结算读一次投入材料）。

## 9 数据表能不能替代 `ItemMatcher` 那堆表？

**已单独立稿：[`70_数据表与ItemMatcher替代评估.md`](70_数据表与ItemMatcher替代评估.md)。** 结论是不能整体替代
（两者最本质的区别是 `ItemMatcher` 匹配 **`ItemStack`**、数据表匹配 **`Holder`**），但有几张"纯条目级、无身份、
无叠加"的表适合迁移；逐表判定与迁法都在 `70`。
