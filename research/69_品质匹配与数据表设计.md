# 69 品质匹配与数据表设计

> **状态**：**部分落地**——**事实层已经落地并且就是现状**（`QualityService.find` 三层 + `default_quality` 数据表），
> **要求层与四个适配器未实现**。本稿 2026-10-04 **整篇重写**：旧稿写在"每个模块各自管档"的世界里
> （组件 → 锻造结果 → 定义默认 → 灵植 → 数据表 五格、`ItemQualityService`、`artifact` / `talisman` /
> `technique` / `alchemy_furnace` / `spirit_herb` 各自带档字段），那套逻辑已经废弃——现在**档位只有
> `QualityService` 一个服务、只有一条解析顺序**，模块只在自己的规则里**定**档、然后写同一个组件。
> 本稿按现在的代码逐处重核过；旧稿的结论与沿革见文末**附录**。
> 字段级最终形状以代码与 [`docs/数据包格式.md`](../docs/数据包格式.md) 的 `quality` / `default_quality` 两节为准。

## 0 结论

"让大部分地方支持 quality"不是往每个输入点各写一段判定，而是三层：

1. **事实层（已落地）**——档位从哪来：`QualityService.find` 三层，组件 `mxt:quality` → **这一堆携带的定义
   自己声明的档**（`api/QualityProvider` + 已登记的载体）→ 数据表 `mxt:default_quality`。一处读法，
   消费点全部调它，**没有任何模块自己拼一套解析**。
2. **要求层（未实现）**——"够不够档"只实现一遍：`QualityRequirement { qualities[], min_quality }`，
   出口 `QualityRequirements.test(access, stack, requirement)`。今天只有**成员判定**
   （`mxt:item_quality` 的 `qualities` 列表或标签），没有"≥某档"。
3. **适配器层（未实现）**——四个薄壳把要求挂到所有"收物品"的地方：**物品条件**加 `min_quality`、
   **新的 `ItemMatcher` 条目** `mxt:quality`、**NeoForge 自定义材料**（`IngredientType`，一次覆盖所有配方）、
   **Java 单点检查**（机器槽位）。

**不新增数据包注册表**：数据表不是注册表。

## 1 现状（2026-10-04 逐处重核）

### 1.1 唯一解析入口：`QualityService.find`

`runtime/item/QualityService.java`，三层，第一个命中的赢：

| 层 | 来源 | 读它要不要 registry access |
| --- | --- | --- |
| ① | 组件 `mxt:quality`（`Holder<ItemQuality>`），**按 id 回查注册表**——查不到就当没有 | **要**（`intrinsic` 拿不到 `RegistryLookup` 就答空） |
| ② | 这一堆携带的定义自己声明的档（见 §1.2） | 不要（组件里的 holder 就在堆上） |
| ③ | 数据表 `mxt:default_quality`（`ItemStack#getData`，键是物品 id 或 `#物品标签`） | 不要 |

`QualityService` 同时也是**写入口**（`set` / `clear` / `hasOverride`）、三个修正的取值口
（`modifier(quality, selector, context)`，`value_multiplier` / `forging_modifier` / `alchemy_modifier`）、
显示口（`coloredName` / `displayName` / `ordered`）、以及**使用门禁**（`check` / `Failure` / 五个事件 + `canUse`）。

### 1.2 第二层：定义自己声明档，载体决定"问谁"

- 对外契约 `api/QualityProvider`：`Optional<Holder<ItemQuality>> defaultQuality()`。
  **实现它本身什么都不改**：定义类型还要在 `QualityService.carry` 登记自己的载体组件才算进了第二层。
- `carry` 两个重载：组件值就是定义（`Holder<T>`）；或组件是个 record、给一个把定义取出来的函数。
  `T extends QualityProvider`，没实现接口的类型登记不过。
- 载体清单在 `runtime/item/QualityCarriers.java`，`QualityService` 类加载时先登记本模组的，**附属模组的排在后面**；
  一次查询按登记顺序走完，第一个答出档的赢。**这是登记，不是扫堆**（按组件遍历的顺序没有契约）。
- **载体只凭这一堆答得出**：两个重载都不给它 `RegistryLookup`，因为使用门禁那条路手里只有品质注册表。
  取出的 holder 没绑定（当前包删了那条定义）时这一层答空、继续往下走。

**九个定义声明可选 `quality`**（都走 `ItemQuality.CODEC.optionalFieldOf("quality")`），各由一个已登记载体读到：

| 定义 | 共用件（"物品说不清是哪一档"的现场） | 载体组件 | 取值 |
| --- | --- | --- | --- |
| `technique` | 功法手册（默认共用 `mxt:cultivation_jade_slip`） | `mxt:technique` | 裸 `Holder<Technique>` |
| `alchemy_furnace` | 所有炉型规格共用炉子方块物品 | `mxt:alchemy_furnace` | 裸 `Holder` |
| `alchemy_wall_material` | 炉壁方块物品 | `mxt:alchemy_wall_material` | 裸 `Holder` |
| `spirit_root` | 灵根石 | `mxt:spirit_root` | 裸 `Holder` |
| `physique` | 体质载体 | `mxt:physique` | 裸 `Holder` |
| `pill` | 丹药载体 | `mxt:pill` | `PillComponent::pill` |
| `formation` | `formation_plate` | `mxt:formation_plate` | `FormationPlateComponent::formation`（**存下来的原字段**，不看允许列表） |
| `secret_realm` | 秘境令牌 | `mxt:secret_realm_token` | `SecretRealmTokenComponent::realm` |
| `contract_type` | 契约卷轴 | `mxt:contract_scroll` | `ContractScrollComponent::contractType` |

**四个不接的（各有理由，不是遗漏）**：

- `artifact` / `spirit_herb`——**按物品认领**（`implements ItemMatcher`），堆上没有装定义身份的组件，
  第二层没有可问的对象，档写在 `default_quality` 里；
- `talisman`——它的载体 `mxt:talisman` 装的是**一列**符的 id，没有单份定义可问，档由画符配方写组件、
  写不上才兜底到数据表；
- 列表型载体一律不登记：`mxt:forging_methods` / `mxt:forging_blueprints` / `mxt:element` / `mxt:talisman`。

### 1.3 模块只"定档"，不再"管档"

| 模块 | 它自己的规则 | 落点 |
| --- | --- | --- |
| 锻造 | 蓝图 `quality_by_extra_steps` 曲线（按多打的步数查档） | `ForgingService.effectiveExtraSteps` → `ForgingWorkstationService:229` 写 `mxt:quality` |
| 画符 | 配方 `grades[]`（按完成度查档） | `TalismanWorkstationService:230,254` 读结果、写 `mxt:quality` |
| 定义 | 定义里的 `quality` 字段（§1.2，九个） | 由载体读，不写库 |
| 数据包 | `mxt:default_quality`（物品 id / `#标签` → 档） | 第三层 |
| 显式覆盖 | 只要写组件就行：`/quality set`、KubeJS `MxtQualities.set`、配方结果组件 | 第一层 |

**读档一律走服务**，今天的消费点（全部在 `QualityService` 之后）：

| 消费点 | 读法 | 用途 |
| --- | --- | --- |

| 物品条件 `mxt:item_quality` | 解析出的那一档**在不在**写下的列表/标签里 | `ItemCondition` 的所有位置（货币 `unavailable_when`、绑定 `conditions`…） |

| `ItemBindingService`（attack / use / tick / `refreshWeapon`）、`AbilityEventBridge:153`、`TechniqueItemService:197`、`TechniqueCommand:84`、`AlchemyWorkstationService:103-106` | `canUse` / `check` | 决定自家的动作跑不跑 |

### 1.4 两套匹配语言，都不读档

| 语言 | 形状 | 谁在用 | 能不能按档筛 |
| --- | --- | --- | --- |
| 原版 `Ingredient` | `{"item"/"#tag"}`，`HolderSet<Item>`，`test` 就是 `stack.is(...)` | 所有配方（`mxt:spirit_shaped` / `shapeless`、`mxt:talisman_drawing`、原版与其他模组的配方） | 只能靠 NeoForge 的 `neoforge:components` 做**组件精确相等** |
| 我们的 `ItemMatcher.Entry` | **七**种条目（`item` / `tag` / `wildcard` / `regex` / `spirit_storage` / `herb_tag` / `technique`，`registry/MxtItemMatchers.java:20-26`） | `Cost` 的 `mxt:item`、五张 binding 的 `items`、`mxt:item_matcher` / `item_id` / `item_tag` 条件、货币 `items`、灵植 `entries`、拾取器 | **不能**（没有任何条目读档，也没有"≥某档"） |

### 1.5 读不到档的输入点

| 输入点 | 现在的判据 | 位置 |
| --- | --- | --- |
| 丹炉 主药 / 辅药 / 药引 仓 | 被某条 `spirit_herb` 认领 + 该角色药力 > 0 | `AlchemyFurnaceInventoryBlockEntity:171` → `SpiritHerbService.potency` |
| 锻造材料格 | 蓝图 `input` 的硬物品 id + 数量 | `ForgingMaterial(Identifier id, int count)` |
| 画符符纸格 | 硬 id：`stack.is(TalismanDrawingRecipe.paper())` | `TalismanWorkstationMenu:325`；消耗侧 `TalismanWorkstationService:321` 的 `ItemEntry` |
| 符笔颜料 | 一个物品标签 + 服务端配置 | `BrushPigmentService:34,45`（`PIGMENT` 标签 + `stack.is(PIGMENT)`） |
| 灵气合成网格 | 槽位不筛，只由配方匹配决定 | `SpiritCraftingMenu` |
| 灵植种子 | `growth.seeds` 的 matcher 条目 | `SpiritHerbService:52` |

### 1.6 症结是 `Provider`（新形状下变了，但没消失）

两套匹配语言的判定入口（`Ingredient.test(ItemStack)` / `ItemMatcher.Entry.matches(ItemStack)`）**都拿不到
registry access**；而今天的 `find` 在 access 为空时**会跳过第一层**（组件要按 id 回查注册表）。
也就是说"无 access 读法"今天只能读到**第二层（载体）+ 第三层（数据表）**——对"这一堆被明写了档"的情形
（锻造 / 画符 / 配方结果组件）会答否，这是"按档筛"落地前必须决定的一件事，见 §3.2。

## 2 NeoForge 给的两个钩子

### 2.1 Registry Data Map（机制全文见 [`70`](70_数据表与ItemMatcher替代评估.md)）

数据表是 NeoForge 的"**注册表条目 → 值**"数据包表面：键可写条目 id 或 `#标签`（加载期展开成条目），
值由我们自己的 codec 决定，支持 `replace` / `remove` / merger / `neoforge:conditions` / 可选同步，
**读它不需要 `Provider`**。本稿只用到它的三点：值可以放 `Holder<ItemQuality>`、可同步到客户端、
由 `ItemStack#getData` 按物品条目查。

### 2.2 `ICustomIngredient` / `IngredientType`

NeoForge 把 `Ingredient.CODEC` 包成 `Codec.xor(自定义材料分派, 原版 HolderSet)`，分派键是
`neoforge:ingredient_type`，类型注册在静态注册表 `neoforge:ingredient_serializer`
（`NeoForgeRegistries.Keys.INGREDIENT_TYPES`）；NeoForge 自带 `neoforge:components`（`items` / `components` /
`strict`）、`compound`、`difference`、`intersection`、`block_tag`、`custom_display`。

自己注册一种的收益是**一处实现换来所有配方**：任何收 `Ingredient` 的地方（原版配方、别的模组的配方、
`mxt:spirit_shaped` / `shapeless`、`mxt:ingredient` 物品条件）都能写这一种材料。

两条硬约束：

- **`items()` 不能为空**：`ICustomIngredient.items()` 写明"至少要返回一件物品，否则这条材料被视为空、
  **整条配方失效**"，而且查看器（JEI / EMI）靠它枚举候选——所以自定义材料**必须自带一个可枚举的物品集**。
- **`isSimple()` 的语义是"只看物品就能判"**：读档的材料必须报 `false`，否则 `StackedContents` / 配方书
  会把它当成纯物品材料。

## 3 设计

### 3.1 三层

```
事实层（已落地） 组件 mxt:quality → 携带的定义（QualityProvider + 登记的载体）→ 数据表 default_quality
                       ↓ 一处读法 QualityService.find（两种强度：有 access / 无 access，见 §3.2）
要求层（未实现） QualityRequirement { qualities[], min_quality }  →  QualityRequirements.test
                       ↓ 一份 codec
适配器（未实现） 物品条件 ｜ ItemMatcher 条目 ｜ 自定义材料 ｜ Java 单点检查
```

### 3.2 事实层：现状 + 要补的"无 access 读法"

现状见 §1.1 / §1.2，**不再改动形状**。要补的是 §1.6 那个缺口，两步：

1. **服务端匹配拿到 access**：匹配路径（配方 / 扣费）实际上在服务端，用
   `ServerLifecycleHooks.getCurrentServer()` 取 `registryAccess`——仓库里
   `MxtDatapackRegistries` / `ItemElements` / `ItemAuraService` / `CurrencyValueService` / `DamageElements`
   都是这个写法。
2. **无 access 时把第一层放宽成"直接用堆上的 holder"**：现在 `intrinsic` 拿不到注册表就答空；
   改成"只要 holder 绑定着就用它"。代价是包换过、那条品质 id 已不存在时，一次会话里可能沿用堆上那份旧档——
   这与"附件里存 `Holder`、不看注册表"是同一条口径（`RegistryFixedCodec` 解出来的 holder 本来就不看注册表）。

这两步落完，"无 access 读法"与"有 access 读法"在**服务端**结果一致；纯客户端（拿不到服务端实例）才退化成
"没有第一层"。

### 3.3 要求层：`QualityRequirement`

```java
public record QualityRequirement(List<Either<Holder<ItemQuality>, TagKey<ItemQuality>>> qualities,
                                 Optional<Holder<ItemQuality>> minQuality) { … }
```

- `qualities`：成员判定（可用 `#品质标签`），**就是今天 `mxt:item_quality` 的语义**，搬过来复用；
- `minQuality`：按 `ChainCache.rankOf` 比序号，**跨链一律 `false`**——不同链的序号没有可比性，
  这里不许"不可比就放行"；
- 两者同写＝都要满足；都不写＝不筛档（等价于"任何档"，**含没有档的物品**——这点要在文档里写清）；
- 唯一出口：`QualityRequirements.test(@Nullable Provider access, ItemStack stack, QualityRequirement requirement)`。
  无 access 时按 §3.2 的读法，读不到就答否——确定、可文档化。

### 3.4 四个适配器

| 适配器 | 新增什么 | JSON | 一次覆盖 |
| --- | --- | --- | --- |
| **物品条件** | `mxt:item_quality` 加可选 `min_quality`（内部改成复用 `QualityRequirement`，字段名不变） | `{"type":"mxt:item_quality","min_quality":"example:tier_3"}` | 所有跑 `ItemCondition` 的地方（货币 `unavailable_when`、绑定 `conditions`…） |
| **`ItemMatcher` 条目** | 新条目 `mxt:quality`：`items`（必填，条目列表）+ 上面那份 requirement | `{"type":"mxt:quality","items":["mxt:blank_talisman"],"min_quality":"example:tier_3"}` | `Cost` 的 `mxt:item`、五张 binding 的 `items`、`mxt:item_matcher` / `item_id` / `item_tag`、货币 `items`、灵植 `entries`、拾取器 |
| **自定义材料** | `ICustomIngredient` + 注册到 `neoforge:ingredient_serializer` | `{"neoforge:ingredient_type":"mxt:quality","items":"mxt:blank_talisman","min_quality":"example:tier_3"}` | **所有配方**：原版、其他模组、`mxt:spirit_shaped` / `shapeless`、`mxt:talisman_drawing`、`mxt:ingredient` 条件 |
| **Java 单点检查** | 无新类型，调 `QualityRequirements.test` | — | 机器槽位（丹炉输入仓、符纸格、锻造材料、灵植种子），以及将来炉型 / 丹方的材料门槛 |

两个新适配器都**要求 `items` 必填**：`ItemMatcher` 是 OR 列表，不自带物品约束就没法表达"必须是符纸且≥三档"；
材料侧则因为 §2.2 的 `items()` 非空是硬要求。

`itemLevel()` / `isSimple()` 的口径：

- matcher 条目：`itemLevel() = requirement.isEmpty() && items 全为 itemLevel`。有档位要求时返回 `false`，
  `runtime/hold/HoldLookup` 那套"itemLevel 建索引 / 非 itemLevel 逐堆问"的分工立刻正确；
- 材料：`isSimple() = requirement.isEmpty() && items.isSimple()`。

### 3.5 Provider 矩阵

| 求值场景 | 有 `Provider` | 能读到哪些层 |
| --- | --- | --- |
| 数据包定义解码（注册表 / 配方 / 条件） | 有 | 三层全读 |
| `ItemCondition` 求值 | 有（`ctx.holder().level()`） | 三层全读 |
| 配方匹配（`Ingredient.test`） | 走 §3.2 第 1 步拿服务端 access | 三层全读（纯客户端才退化） |
| `ItemMatcher.Entry.matches`（cost / binding / `HoldLookup`） | 同上 | 同上 |
| 客户端 tooltip / 渲染 | 有（客户端同步的注册表与数据表） | 三层全读 |

**不建议**改 `Ingredient.test` / `Entry.matches` 的签名去穿 access——那是十几个调用点的连锁改动；
§3.2 那两步就是替代方案。

### 3.6 缓存

数据表本身是 `Map<ResourceKey, T>`，按条目查 O(1)，不需要我们自建索引。若给 `ItemMatcher` 建"按物品"的索引
（照 `ChainCache` 的写法：按注册表实例开键 + `ServerCache` 里失效），失效点用 **`DataMapsUpdatedEvent`**
（服务端 reload 与客户端同步都会发），而不是只挂 `TagsUpdatedEvent`。

## 4 与现状的差异

| 变化 | 影响面 |
| --- | --- |
| `mxt:item_quality` 加可选 `min_quality` | 老 JSON 不变（字段可选）；语义新增 |
| 新条目 `mxt:quality`（matcher） | 老 JSON 不变（新类型）；`MxtItemMatchers` +1 行 + 一个类 |
| 新 `IngredientType` `mxt:quality` | `NeoForgeRegistries.Keys.INGREDIENT_TYPES` +1 行 + 一个类（`items()` 非空、`isSimple() = false`） |
| `QualityRequirement` / `QualityRequirements` | 新类两个；`ItemQualityCondition` 内部改成复用它 |
| `find` 的无 access 读法放宽（§3.2 第 2 步） | 一个私有方法；**不再跳过第一层** |
| 匹配路径取服务端 access（§3.2 第 1 步） | 新适配器内部；老调用点不改 |

**没有破坏性改动**：不删字段、不改字段类型、不动存档与附件、不动现有解析顺序。

## 5 收尾项（各自怎么接，不再是"做不做"的问题）

- **锻造材料形状**：`ForgingMaterial` 现在是 `(Identifier id, int count)`，硬 id 换不成"材料 + 档位要求"。
  换成 NeoForge `SizedIngredient` 的形状——`{"ingredient": …, "count": 3}`（`NESTED_CODEC`；**不要用它的
  `test`**，那个要求单堆够量，而锻造是跨格求和）。连带：起手材料要记**实际取走的堆**（现在记"声明堆"，
  带组件的材料会退化成不带组件）；蓝图 `inputError` 的"同一物品写两次"要退化；界面显示改用
  `ingredient.items()` 的第一件。
- **画符符纸格**：槽位是 `Predicate<ItemStack>`（`TalismanWorkstationMenu:325` 的硬 id），放宽成物品标签一行就够
  （消耗侧的 `ItemEntry` 换成已存在的 `TagEntry`）；**"符纸必须≥三档"要靠 `QualityRequirements.test`**，
  `Ingredient` 与标签都给不了。"好纸画好符"是另一个消费点（结算读一次投入材料）。
- **符笔颜料**：今天是"一个物品标签 + 服务端配置"（`BrushPigmentService.PIGMENT`），它是"载体自己的存量"
  那套形状的例外之一（见 `AGENTS.md`），**不必然**要接要求层；要不要接由内容侧定，接了也只是把
  `stack.is(PIGMENT)` 换成"标签 + 要求"。

## 7 开放问题

1. `min_quality` 跨链答否 vs 报加载期 problem（倾向答否：链可以后补）。
2. 两个新适配器的 `items` 必填（见 §3.4），材料侧没有选择余地。
3. `mxt:quality` 这个名字在**两个不同注册表**里各用一次（matcher 条目类型 / 材料类型），JSON 上下文不同，
   不会撞——要不要起两个名字待定（数据表那一层已经叫 `mxt:default_quality`，没有这个问题）。
4. §3.2 第 2 步（无 access 时直接用堆上的 holder）要不要做：不做的话，"配方按档筛"在纯客户端读不到
   被明写过档的堆；做的话要接受"包换了、旧档在一次会话里仍然算数"。
5. 数据表要不要加 `priority`：今天是裸值、没有 merger，两个包抢同一件物品按"后加载者赢"
   （另外六张物品键表都带 `priority`）。要一致就得把值从裸字符串变成对象。
