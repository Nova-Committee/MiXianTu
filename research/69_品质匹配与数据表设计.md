> **状态**：**已落地**（2026-10-04）。三层事实层、要求层、四个适配器、"比大小只有一处实现"、以及丹炉核心的
> 炉阶**都在代码里**；正文按代码逐处重核过，**只写现在是什么形状**，每一批做了什么见 §8、被推翻的旧写法见附录。
> 还欠的只有**实机验证**与 §9 里那几条仍未决的口径。
> 字段级最终形状以代码与 [`docs/数据包格式.md`](../docs/数据包格式.md) 的 `quality` / `default_quality` /

## 0 结论

"让大部分地方支持品质"不是往每个输入点各写一段判定，而是四件事：

1. **事实层**——档位从哪来：`QualityService.find` 三层（组件 → 这一堆携带的定义 → 数据表），一处读法；
2. **要求层**——"够不够档"只实现一遍：`QualityRequirement` + 唯一出口 `QualityRequirements.test`；
3. **适配器层**——四个薄壳把同一份要求挂到所有"收物品"的地方：**物品条件**、**匹配器条目**、
   **自定义材料**、**Java 单点检查**（丹炉核心是它今天唯一的运行时调用点，§5），外加一个把**整份材料**
   写进 `ItemMatcher` 的条目 `mxt:ingredient`；
4. **比大小**——两个档谁高只有一个出口：`QualityLadders.compare` / `atLeast` / `rank`（§2.3）。

**没有新增数据包注册表**：数据表不是注册表（评估见 [`70`](70_数据表与ItemMatcher替代评估.md)）。

## 1 事实层：档位从哪来

### 1.1 唯一解析入口 `QualityService.find`

`runtime/item/QualityService.java`，三层，第一个命中的赢：

| 层 | 来源 | 读它要不要 registry access |
| --- | --- | --- |
| ① | 组件 `mxt:quality`（`Holder<ItemQuality>`） | 有注册表时**按 id 回查**（当前包删了那条 → 这一层答空）；**拿不到注册表时直接用堆上那个 holder**（只要求 `isBound()`） |
| ② | 这一堆**携带的定义**自己声明的档（§1.2） | 不要（载体只读堆上的组件） |
| ③ | 数据表 `mxt:default_quality`（`MxtDataMaps`，`synced`，键是物品 id 或 `#物品标签`，**没有 merger**） | 不要 |

第 ① 层的两种强度是刻意的：纯客户端（拿不到服务端实例）读不到"明写在堆上的档"以外的注册表信息，
而服务端匹配路径用 `QualityRequirements.serverAccess()` 拿到真注册表，两边在最要紧的地方一致（§2.2）。

`QualityService` 同时是**写入口**（`set` / `clear` / `hasOverride`）、三个修正的取值口
（`modifier(quality, selector, context)`：`value_multiplier` / `forging_modifier` / `alchemy_modifier`）、
显示口（`coloredName` / `displayName` / `ordered`）、以及**使用门禁**（`check` / `Failure` / 五个事件）。

### 1.2 第二层：定义自己声明档，载体决定"问谁"

- 对外契约 `api/QualityProvider`：`Optional<Holder<ItemQuality>> defaultQuality()`。
  **实现它本身什么都不改**：定义类型还要在 `QualityService.carry` 登记自己的载体组件才算进了第二层。
- `carry` 两个重载：组件值就是定义（`Holder<T>`）；或组件是个 record、给一个把定义取出来的函数。
  `T extends QualityProvider`，没实现接口的类型登记不过。
- 载体清单在 `runtime/item/QualityCarriers.java`，`QualityService` 类加载时先登记本模组的，**附属模组的排在后面**；
  一次查询按登记顺序走完，第一个答出档的赢。**这是登记，不是扫堆**。
- **载体只凭这一堆答得出**：两个重载都不给它 `RegistryLookup`。取出的 holder 没绑定时这一层答空，继续往下走。

**九个定义声明可选 `quality`**（都走 `ItemQuality.CODEC.optionalFieldOf("quality")`），各由一个已登记载体读到：

| 定义 | 共用件（"物品说不清是哪一档"的现场） | 载体组件 | 取值 |
| --- | --- | --- | --- |
| `technique` | 功法手册（默认共用 `mxt:cultivation_jade_slip`） | `mxt:technique` | 裸 `Holder<Technique>` |
| `alchemy_furnace` | 所有炉型规格共用炉子方块物品 | `mxt:alchemy_furnace` | 裸 `Holder` |
| `alchemy_wall_material` | 炉壁方块物品 | `mxt:alchemy_wall_material` | 裸 `Holder` |
| `spirit_root` | 灵根石 | `mxt:spirit_root` | 裸 `Holder` |
| `physique` | 体质载体 | `mxt:physique` | 裸 `Holder` |
| `pill` | 丹药载体 | `mxt:pill` | `PillComponent::pill` |
| `formation` | `formation_plate` | `mxt:formation_plate` | `FormationPlateComponent::formation`（**存下来的原字段**，不看允许列表） |
| `secret_realm` | 秘境令牌 | `mxt:secret_realm_token` | `SecretRealmTokenComponent::realm` |
| `contract_type` | 契约卷轴 | `mxt:contract_scroll` | `ContractScrollComponent::contractType` |

**四个不接的（各有理由，不是遗漏）**：

- `artifact` / `spirit_herb`——**按物品认领**（`implements ItemMatcher`），堆上没有装定义身份的组件，第二层没有
  可问的对象，档写在 `default_quality` 里；
- `talisman`——它的载体 `mxt:talisman` 装的是**一列**符的 id，没有单份定义可问，档由画符配方写组件、
  写不上才兜底到数据表；
- 列表型载体一律不登记：`mxt:forging_methods` / `mxt:forging_blueprints` / `mxt:element` / `mxt:talisman`。

### 1.3 模块只"定档"，读档一律走服务

| 模块 | 它自己的规则 | 落点 |
| --- | --- | --- |
| 锻造 | 蓝图 `quality_by_extra_steps` 曲线（按多打的步数查档） | `ForgingWorkstationService` 写 `mxt:quality` |
| 画符 | 配方 `grades[]`（按完成度查档） | `TalismanWorkstationService` 读结果、写 `mxt:quality` |
| 定义 | 定义里的 `quality` 字段（§1.2 九个） | 由载体读，不写库 |
| 数据包 | `mxt:default_quality`（物品 id / `#标签` → 档） | 第三层 |
| 显式覆盖 | 只要写组件就行：`/quality set`、KubeJS `MxtQualities.set`、配方结果组件 | 第一层 |

今天的消费点（全部在 `QualityService` 之后，**没有第二套解析**）：

| 消费点 | 读法 | 用途 |
| --- | --- | --- |
| 锻造投入材料 `ForgingService.materialModifier` | 被**消耗**的每一堆各查一次，取**最低**的 `forging_modifier` | 折算多打的步数（工具与图纸格不参与） |

| 使用门禁 `QualityService.check` | 解析出的那一档自己的 `condition`（+ 绑定条件、丹药上限/冷却） | 五个事件取消原生交互 |
| 物品条件 `mxt:item_quality` | 解析出的那一档**在不在**写下的列表/标签里、够不够 `min_quality` | `ItemCondition` 的所有位置 |
| 匹配器条目 `mxt:quality` / 材料 `mxt:quality` | 同上（`QualityRequirements.test`） | 所有 `ItemMatcher` 位置 / 所有原版 `Ingredient` 位置 |
| **丹方 `furnace_quality`** | 核心那一堆的档 | 炉阶门槛（§5） |
| tooltip / picker / 面板 / 炉子状态 / 锻造界面 / 轮盘 | `coloredName` / `displayName` | 画档位名 |
| `/quality get\|set\|clear\|upgrade\|chain`、KubeJS `MxtQualities`、`QualityUpgradeService` | `find` / `set` / `clear` / `hasOverride` | 管理入口与升级（`upgrade_costs` / `upgrade_condition`） |
| `ItemBindingService`、`AbilityEventBridge`、`TechniqueItemService`、`TechniqueCommand` | `canUse` / `check` | 决定自家的动作跑不跑 |

## 2 要求层

### 2.1 `QualityRequirement`

`data/quality/QualityRequirement.java`：

```java
public record QualityRequirement(List<Either<Holder<ItemQuality>, TagKey<ItemQuality>>> qualities,
                                 Optional<Holder<ItemQuality>> minQuality) { … }
```

- 两个字段各给一个**公开 `MapCodec` 常量**（`QUALITIES_FIELD` / `MIN_QUALITY_FIELD`），由各适配器 `forGetter`
  内联，JSON 键就是 `quality` / `min_quality`，不嵌套一层 `requirement`；
- `qualities`：成员判定（可用 `#品质标签`），**就是 `mxt:item_quality` 从前的语义**；
- `minQuality`：按**这一档所在那条链**比位置，**跨链一律答否**，不许"不可比就放行"；
- 两者同写＝都要满足（AND）；都不写＝不筛档（`isEmpty()`）——这一条**只对 Java 的 `test` 成立**，
  数据包侧三条口子都在加载期拒绝空要求（"静默恒真"是最难查的一类错误）。

### 2.2 唯一出口 `QualityRequirements.test`

`runtime/item/QualityRequirements.java`：

```java
public static boolean test(@Nullable Provider access, ItemStack stack, QualityRequirement requirement);
public static @Nullable Provider serverAccess();
```

- 空要求恒真（含没有档的物品）；
- 档解析走 `QualityService.find`，**没有第二套解析**；
- `min_quality` 交给 `QualityLadders.atLeast`，**没有第二套比大小**；
- **没有 access 时 `min_quality` 答否**（链是服务端索引出来的，堆上读不出位置），成员判定仍答得出——
  纯客户端因此只剩"这一堆的档在不在列表里"；
- `serverAccess()` = `ServerLifecycleHooks.getCurrentServer().registryAccess()`，**匹配路径**（`Ingredient.test` /
  `Entry.matches` / 扣费）用它，与 `MxtDatapackRegistries` / `CurrencyValueService` 同一写法。
  **没有去改 `Ingredient.test` / `Entry.matches` 的签名**——那是十几个调用点的连锁改动。

三个数据包适配器都会在**加载期**拒绝空要求：条件与条目用 `.validate(...)`，材料同样，丹方的
`furnace_quality` 用 `flatXmap`（§5）。

### 2.3 比大小只有一个出口

`data/quality/QualityLadders.java`：

```java
public static OptionalInt compare(Provider access, Holder<ItemQuality> left, Holder<ItemQuality> right);
public static boolean     atLeast(Provider access, Holder<ItemQuality> tier, Holder<ItemQuality> floor);
public static OptionalInt rank(Provider access, Holder<ItemQuality> tier);
```

- `compare`：**正数＝前者更高**（`left 的位置 − right 的位置`），同一档＝`0`，**空＝无法比较**；
- `atLeast`：就是 `compare >= 0`（空的当假）——`min_quality` 的判据；
- `rank`：链上位置（从这一条链的入口档数起）；画符的 `paper_rank` 与丹方的 `furnace_rank` 都用它。

**空的口径**（唯一需要记的一条）：

- 跨链 → 空（两条链的序号互不相干，既不是放行也不是拒绝）；
- **只被"走不出来的链"装着的档 → 空，连自己跟自己都是空**（成环 / 分叉 / 坏链接 / 并进别的链时整条链不索引），
  所以 `atLeast(t, t)` 对它是 `false`。这条刻意的严格是"比大小"与"要求层"共用一份实现的前提，也保住了
  `min_quality` 既有规则：**没被索引到的档一律答否**；
- **别把空当成"更低"**。`QualityService.ordered()` 是 tooltip 顺序，**不是**大小顺序。

KubeJS 侧：`MxtKubeJsApi.compareQualities(Entity, Identifier, Identifier)` → `OptionalInt`（id 在当前包里查不到 → 空），
绑定方法 `MxtQuality.compare(entity, left, right)` → `Integer`／`null`。

## 3 四个适配器

| 适配器 | 形状 | JSON | 一次覆盖 |
| --- | --- | --- | --- |
| **物品条件** | `mxt:item_quality`（字段名不变，`min_quality` 是新增的可选字段） | `{"type":"mxt:item_quality","quality":["#example:tier"],"min_quality":"example:tier_3"}` | 所有跑 `ItemCondition` 的地方（货币 `unavailable_when`、绑定 `conditions`…） |
| **`ItemMatcher` 条目** | 新条目 `mxt:quality`：`items`（必填）+ 同一份要求 | `{"type":"mxt:quality","items":["mxt:blank_talisman"],"min_quality":"example:tier_3"}` | `Cost` 的 `mxt:item`、`artifact` / `pill_binding` / `technique_binding` / `spirit_herb` 的 `items`、`mxt:item_matcher` / `item_id` / `item_tag`、灵植 `growth.seeds`、拾取器 |
| **自定义材料** | `data/quality/QualityIngredient` + `registry/MxtIngredientTypes`，注册进 `neoforge:ingredient_serializer` | `{"neoforge:ingredient_type":"mxt:quality","items":"mxt:blank_talisman","min_quality":"example:tier_3"}` | **所有配方**（原版、别的模组、`mxt:spirit_shaped` / `shapeless`、`mxt:talisman_drawing`），以及两处"就是 `Ingredient`"的字段：锻造蓝图 `input`、画符符方 `paper` |
| **Java 单点检查** | 无新类型，直接调 `QualityRequirements.test` | — | **丹炉核心的炉阶（§5，今天唯一的运行时调用点）**；三个数据包适配器内部也各自调它 |

### 3.1 两个新适配器都要求 `items` 必填

`ItemMatcher` 是 OR 列表，不自带物品约束就没法表达"必须是符纸且≥三档"；材料侧则是 NeoForge 的硬要求：
`ICustomIngredient.items()` 必须能枚举出至少一件物品，否则这条材料被视为空、**整条配方失效**，而且
JEI / EMI 靠它列候选。

`itemLevel()` / `isSimple()` 的实际口径：

- matcher 条目 `mxt:quality`：`itemLevel()` **恒假**（要求必填，而且读档就是读堆），
  `HoldLookup` 那套"itemLevel 建索引 / 非 itemLevel 逐堆问"的分工因此立刻正确；
- 材料 `mxt:quality`：`isSimple()` **恒假**，`items` 用 `Ingredient.NON_AIR_HOLDER_SET_CODEC`（可枚举的 `HolderSet`），
  **不是** `ItemMatcher` 条目——`wildcard` / `technique` 这类条目根本没有物品集。

### 3.2 `mxt:ingredient`：把整份材料写进 `ItemMatcher` 的唯一通道

`util/matcher/builtin/IngredientEntry`（`MxtItemMatchers` 第九种条目）：包里写一整个原版 `Ingredient`
（物品、数组、`#标签`，以及自定义材料 `mxt:quality`），`itemLevel()` 取那个材料自己的 `isSimple()`。
画符那次取纸的代价走的就是它——**这是"材料侧的要求能进 `Cost`"的唯一办法**。
**与同名的物品条件 `mxt:ingredient` 是两个注册表**；与 `mxt:quality` 在条目 / 材料两个注册表各用一次是同一情形。

## 4 按档筛物品：三个口子 + 几处硬判据

**三个口子**（同一份要求、同一处判据）：① 物品条件 `mxt:item_quality`；② 匹配器条目 `mxt:quality`
（另有 `mxt:ingredient` 条目把整份材料写进 `ItemMatcher` 位置）；③ 自定义材料 `mxt:quality`
（凡是用原版 `Ingredient` 的地方都能用，**锻造蓝图 `input` 与画符符方 `paper` 也在内**）。

**仍是硬判据、读不到档的只有两处**（都是刻意的现状）：

- **丹炉输入仓**（主药 / 辅药 / 药引）：判据是"被某条 `spirit_herb` 认领 + 那味药的药力 > 0"，与档位无关；
  想按档筛**这份丹方**用 `furnace_quality`，筛的是**核心**而不是药材（§5）；
- **符笔颜料**：`mxt:brush_pigment` 标签 + 服务端配置，**不接要求层**（它是"载体自己的存量"那套形状的例外，
  接不接由内容侧定，本体不动）。

**符纸是两条**：槽位认标签 `mxt:talisman_paper`（客户端也答得出"这算不算纸"，**别把档位要求塞进槽位谓词**），
符方自己的 `paper` 字段（原版 `Ingredient`，不写＝那个标签）在开局时收窄并决定实际取走哪一张；
"符纸至少某档"就写成 `mxt:quality` 材料，结算把这张纸的链上位置作为 `paper_rank` 给 `result` 的公式。
**写到标签外面的纸永远开不了局**（那一格放不进去）。

两套匹配语言的现状：

| 语言 | 条目 / 形状 | 能不能按档筛 |
| --- | --- | --- |
| 原版 `Ingredient` | `{"item"/"#tag"}`，外加 NeoForge 的自定义材料分派 | **能**：`neoforge:ingredient_type: mxt:quality` |
| 我们的 `ItemMatcher.Entry` | **九**种：`item` / `tag` / `wildcard` / `regex` / `spirit_storage` / `herb_tag` / `technique` / `quality` / `ingredient` | **能**：`mxt:quality`（+ `mxt:ingredient` 转材料） |

## 5 丹炉核心的炉阶

**多方块结构不动**（炉壁、炉型、形状都不接品质）。品质这一侧挂在**核心**那件物品上——它就是"设置温度"、
开界面、记批次的那一件（`mxt:alchemy_furnace`），它今天已经能带档：规格自己的 `quality` 字段 → 组件
`mxt:quality` 覆写 → `default_quality` 兜底（§1.1），而且**没有档直接拒绝开炉**（`FURNACE_QUALITY`）。
本次给它两件事：

1. **丹方可以要求炉阶**：`mxt:alchemy` 配方新增可选字段 `furnace_quality`，形状就是 `QualityRequirement`
   （`quality` 成员 + `min_quality`，两者至少写一个，**写空对象在加载期被拒**）：

   ```json
   "furnace_quality": { "min_quality": "example:kiln_b" }
   ```

   预览与开炉都用 `QualityRequirements.test(access, station.furnaceItem(), 要求)` 判它，也就是**第四个适配器
   （Java 单点检查）的第一个运行时调用点**。失败原因是新的一条 `AlchemyFailure.FURNACE_TIER`
   （`screen.mxt.alchemy.failure.furnace_tier`）——它与 `FURNACE_QUALITY`（"核心根本没有档"）是两回事。
   顺序：匹配 → 就座/结构/规格 → **没有档** → **炉阶不够** → 这一档自己的使用条件 → 槽位/容量 → 温度 /
   环境 / 产物仓。**炉阶不够不扣料、不动供热方块**（与其他拒开一致）。
2. **丹方公式可以读炉阶**：核心的档在**它自己那条链**上的位置作为变量 **`furnace_rank`** 注入这一份丹方
   公式的上下文（与画符的 `paper_rank` 同一形状：没有档 / 档不在链上都是 `0`）。**可用范围只有丹方自己的
   公式字段**（主辅阈值、`catalyst_requirement`、`balance_tolerance`、`target_temperature`、
   `temperature_tolerance`、`duration`、`minimum_aura`）——药力公式与档位自己的修正**读不到它**；
   `AlchemyRecipe.FURNACE_RANK` 是常量名，它**不是** `mxt:formula_variable` 注册表条目（那张表是代码注册表，
   数据包加不了变量），所以未知名字仍按框架口径"记一条诊断、按 0 参与运算"（见 §9）。

## 6 Provider 矩阵与缓存

| 求值场景 | 有 `Provider` | 能读到哪些层 |
| --- | --- | --- |
| 数据包定义解码（注册表 / 配方 / 条件） | 有 | 三层全读 |
| `ItemCondition` 求值 | 有（`ctx.holder().level()`） | 三层全读 |
| 配方匹配（`Ingredient.test`） | 走 `QualityRequirements.serverAccess()` | 三层全读（纯客户端才退化） |
| `ItemMatcher.Entry.matches`（cost / binding / `HoldLookup`） | 同上 | 同上 |
| 客户端 tooltip / 渲染 | 有（客户端同步的注册表与数据表） | 三层全读 |
| 丹方公式（`furnace_rank`） | 有（开炉的人是服务端玩家） | 只用核心那一堆的档 |

数据表本身是 `Map<ResourceKey, T>`，按条目查 O(1)，不需要自建索引。链（阶梯 / 境界）的索引在
`util/ChainCache`：**按注册表实例开键** + `ServerCache.onDatapackLoaded` 里 `invalidate()`（数据表在
`DataMapsUpdatedEvent` 那一侧同步）。

  与本次改动之前一样。**药力公式读不到**（该版曾把它交给 `AlchemyResolver.mixture`，代价见下），
  **任何档位的 `alchemy_modifier` 公式也读不到**（`parameters` 收的是不带 rank 的上下文）——
  高级炉子靠上一条规则更快，不靠在 modifier 里读自己的炉阶。手里没有核心的路径（配方管理器
  `AlchemyRecipe.matches`）照旧读 0。
- **中途那版的代价（留档）**：第一版按字面把 `furnace_rank` 也交给了药力上下文，实机立刻撞出后果——
  药力一变**混合物就跟着变**，而混合物是"挑哪条丹方"的唯一依据（`AlchemyResolver.gaps` 的
  `BALANCE` 差：平衡 ＝ Σ(数量×药力×热偏置) / Σ(数量×药力)，药力同时是分子与分母，只有"有热偏置的药"
  变了平衡才会移动）。夹具里主药（偏置 +1）药力写成 `+ furnace_rank` 后，rank 1 让平衡从 `0` 变成
  `0.125`，而 `hot` 写的是 `balance_tolerance: 0` → **本来匹配的丹方不再匹配**（探针报 `CONFLICT`、
  时长 `-1`）。玩起来的现象就是"换一件更好的核心，这炉丹反而配不出来了"——这与"核心只是炉子"的直觉
  冲突，所以改成上面那套。

**夹具**（都在测试包）：`data/mxt/data_maps/item/default_quality.json` 加了"tag 与具体物品各写一次、
优先级相反"的两条（gravel：tag 0 + 自己 5 → normal；flint：tag 5 + 自己 0 → excellent），一条腿同时盖住
合并的两个方向；**`mxt:tooltip_order` 标签本来就有**（`data/mxt/tags/mxt/quality/tooltip_order.json`，
`excellent` / `normal` / `poor` 三档，第四批加 `ordered()` 时一起写的，只是当时没有消费者），本轮一个字节
没动它——第一次跑出 MISMATCH 是**我把期望写成了两档**，不是标签没加载（`ordered()` 一直是对的）；
`mxt_test:alchemy/kiln_b` 的 `alchemy_modifier` 从 `1` 改成 `2`（"高炉阶更快"的夹具）、
`mxt_test:alchemy/quick`（孤立档、常数 `alchemy_modifier: 2`，用来验原料侧那一个因子）；
`recipe/alchemy/zz_input_gate.json`（主药 12 + 热 2 / 辅药 12，带 `input_quality`——只有把每个药材翻倍才会
被选中，所以不影响既有夹具的匹配结果，也不影响 `AlchemyProbes` 的 `matchedCount` 期望）。
`herb/alchemy/heat.json` 先是改成读 `furnace_rank`、后来**改回常数 `2`**（药力不再读炉阶），
`rank_scale.json` 删掉换成上面的 `quick.json`。

**第二次实机**（同日，`runTestServer` + RCON，仍然不需要玩家）：`/mxt_test quality` 变成
**27 条腿**（22 条原有 + `default_quality_priority` / `tooltip_order` / `picker_catalogue` /
`kubejs_requirement` / `alchemy_input_gate` 五条）+ 新的炉门探针 **17 条腿**。第一次跑出 5 条 MISMATCH，
全部是**夹具 / 期望写错**而不是代码错：`tooltip_order` 第二项是 `normal`（见上，期望写错）；
`gate-core-upper` 报 `CONFLICT` 且时长 `-1`（上面那条代价，改设计后消失）；
`gate-input-marked` 仍然 `INPUT_TIER`（只标了第一格，而这个门问每一格）。修完第二次全绿，第三次
（补上 KubeJS 那条腿）也是全绿；**第五次（收口成"核心档 modifier 定时长"之后）同样一次全绿**——
`core-tier-speed` 3（`hot` 的 4+1 被核心那一档的 2 半除）、`core-tier-mixture` 2.0（**混合物不再随核心变**）、
`material-tier-speed` 2（同一规则在原料侧），两个门与 27 条质量腿全部照旧。

这一轮还带来一个新东西：**`AlchemyGateProbes`——不需要玩家的丹炉门探针**。它用一个**桩控制器**
（`AlchemyWorkstation` 的实现，只回答"结构完整、上限 200、核心是这一堆、槽位是这些"）+ `FakePlayer`
直接调 `AlchemyWorkstationService.preview` / `start`（照 `DrawingProbes` "没有玩家就自己造一个 FakePlayer"
的写法）：两个门都在温度 / 环境 / 产物容量之前判，所以桩够用。于是 **`furnace_quality` / `input_quality`
/ 时长规则 / `furnace_rank` 的运行期行为第一次真的被跑过**（核心档位不够 → `FURNACE_TIER`；输入档位不够 →
`INPUT_TIER`；炉阶 0/1 下丹方公式算出 4/5；核心档 modifier 2 与原料档 modifier 2 各自把时长减半）。
`AlchemyProbes` 里那 10 条需要玩家的腿仍然没跑（留作对照，见 §9）。

## 9 开放问题

1. **丹方公式的变量名没有加载期校验**（符方的 `paper_rank` / `percentage` 有）：未知名字按框架口径
   "记一条诊断、按 0 参与运算"，写错不会拒绝加载。**用户明确列为"预期内行为"，不做**。
2. **炉子档位管什么、不管什么（已定，见 §8.7 第三轮）**：管"最低要求"（`furnace_quality` / `input_quality`）、
   管"更快"（核心那一档自己的 `alchemy_modifier` 除进时长）、管"能烧到多高"（那一份规格的
   `max_temperature`，与炉壁耐温、供热方块取最低——所以核心只是三个上限之一）；**不管混合物**（药力公式读不到
   `furnace_rank`）。仍**未决**的只有一件事：要不要给"炉壁"也开一条随时可换的上限（今天炉壁只有材料定义里的
   一个数，结构不动就换不了）。
3. **`QualityService.ordered()` 的无参重载仍没有消费者**：拾取器用的是 `ordered(access)`（客户端安全那一
   个），无参版本只是给附属模组的便利入口（服务端静态注册表），不算悬空实现。
4. **仍未跑的验证**（都需要 client）：`AlchemyProbes.coreQuality` 的 10 条腿（现在有了不需要玩家的
   对照组，见 §8.7——要不要删掉重复的那批由人定）、`/mxt_test alchemy` 全体、客户端读档路径
   （tooltip / 拾取器 / 客户端 ask `min_quality`）、KubeJS 的实机调用。
5. **其它验证缺口**（与品质无关或更早就有）：第二层载体腿、`CostTransaction` 真扣一次品质条目、
   `mxt:item_quality` 条件与 JSON `Cost` 的**文件**夹具、灵气合成的自定义材料从配方管理器读回。
6. 旧稿的几条已决口径（保留备查）：跨链答否而不是加载期报 problem；两个新适配器的 `items` 必填；
   `mxt:quality` 在条目 / 材料两个注册表各用一次（JSON 上下文不同，不撞，暂不改名）。
7. **progression 侧两条同类死检查没删**：`rebuildProgressionChains` 的 "`next_level … is not a progression`"
   与 `validateTechniqueLevels` 的 "enters the unknown progression level"——和 §8.7 删掉的两条同形，但不在
   本轮清单里，留着待定。
