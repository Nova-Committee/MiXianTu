# 91 方块灵气缓存按子区块重建、位置改为现查

> 2026-10-19，用户逐条给定形状。本文只讲这一轮的三件事：
> ① `rebuild` 的粒度降到子区块（保留整区块重载）；② 内部计数改用调色板的 `count()`，缓存只留聚合；
> ③ `sources`（精确环要的方块位置）不再入档，改由 `BlockAuraService` 用"调色板闸门 + 选择性遍历"现查。
> 存档形状有破坏性变化（`sources` / `absorbed_by` 两个键消失），读旧档不报错、只丢键，见 §5。
>
> **§3 / §6 已经被 [`92`](92_阵法作为灵气消费者与统一分配设计.md) 取代**：吸收（`absorbedAura` / `FormationAbsorption`）
> 整个删掉了，阵法改成与玩家并列的消费者，所以 `rebuild` 里不再有"被阵法覆盖时退回逐位置"这条分支，
> 那段地面计算搬到了 `BlockAuraService.groundInSphere`，每 `PERIOD` 由分配器调一次。其余章节仍然有效。
> **§5 的"整块聚合入档"也已被 [`93`](93_灵气池按子区块细化设计.md) 取代**：池子按子区块存，`blockAura` 与
> `initialized` 两个字段都删了，"有没有播种"由 `aura` 里有没有这一段的 map 判断。

## 1. 为什么动

现状（`BlockAuraService.rebuild` + `AuraChunkAttachment`）有三个互相叠加的浪费：

1. **rebuild 是整列三层 `for`**：`16 × 16 × (maxY − minY)`，主世界 98,304 次 `chunk.getBlockState`，
   其中绝大多数区块一个发射方块都没有。而且循环顺序是 `x → z → y`，而 `PalettedContainer` 的索引是
   `(y << 8) | (z << 4) | x`（`Strategy.getIndex`），`y` 最内层意味着每次读都跨 256 格，缓存在每一格都失效。
2. **缓存里每个发射方块一条**：`BlockAuraSectionCache.sources` 存 `BlockAuraContribution(position, aura,
   absorbedBy)`，`position` 写 `[x, y, z]` 三个 int、`aura` 是每个方块重复一份完全相同的 map。
   一段全是水的区块就是 4096 条，且每条都带一份冗余的 aura map 与控制器列表。
3. **位置只有一个读者**：`AuraService.applyBlockDistance` 的"精确环"（查询点周围 ±1 个 section，最多 27 段）
   需要逐方块位置；其余全部只用 `section.aura()`（聚合）。为这一个环把全区块的位置持久化，不划算。

## 2. 目标与不做

**做**：

- `rebuild` 增加子区块粒度的入口（`rebuild(level, chunk, sectionY)`），保留整区块重载并让后者内部就是"逐段"。
- 每段的聚合用 `section.getStates().count(...)` 算：单状态段是 **O(1)**，混合段是一遍位存储。
- 位置不再进缓存、不进存档；`BlockAuraService.sources(...)` 按需枚举并返回运行期用的列表。
- 方块的 `Block → 定义` 索引（`Index`）从"每次 rebuild 重建"改成常驻 + `DatapackCache.onTagsUpdated` 失效。

**不做（各自单列，见 §8）**：

- 不做精确环的 tick 级记忆化（同一段每 tick 只枚举一次）。
- 不改 `applyBlockDistance` 的加权公式，也不动 `15`/`17` 的查询半径口径。
- 不引入 8³ 子桶、不上 `PalettedContainer` 的 mixin 原始位扫描。
- 不动 `HERB_CHUNK`（那是一份有意存位置+年龄的数据，javadoc 里写了理由）。

## 3. 计数用调色板，结果是精确的

`PalettedContainer.count(CountConsumer)`（`PalettedContainer:304-311`）：

- 调色板只有一个值时直接 `accept(值, 4096)` —— 整段石头/水/空气都是这条路；
- 否则一遍位存储累加 `Int2IntOpenHashMap`，再逐调色板条目回调。

聚合的代数性对得上：`AuraChunkAttachment.merge` 是 amount 相加、`max.resolve(amount)` 相加、regen 相加、
颜色按 amount 加权平均。所以 **N 个完全相同的 `AuraValue` 合 N 次 = `(N·amount, N·resolve(amount), N·regen, 原色)`**
（权重是同一种颜色，加权平均还是它）。新增 `AuraChunkAttachment.scaled(value, count)` 直接产出这个值，
不必真的合并 N 次。

于是每段的聚合与旧的逐方块聚合**逐字段相等**，不是近似。

**但这条路只对"没有阵法够得着的区块"成立。** 旧的聚合是"环境部分"，被阵法吸收的方块要从里面**排除**
（共享池会减掉整个区块的聚合，留在里面就等于同一份灵气既进环境又进阵法）。排除是位置判定
（`absorbedBy(pos)`），没法从计数里做，所以：

- `Sources.empty()` → 走 `count()`，一段一次 `count`，无位置；
- 否则 → 该区块退回**一次逐位置遍历**，同一趟同时产出"环境聚合（跳过被吸收的）"与"每控制器吸收合计"。
  这与旧代码的语义完全一致，只是把"一段一段分别扫"合成"一遍扫完"。

有阵法覆盖的区块本来就是少数，且立/撤阵会显式标脏，所以这条分支的成本可接受。

## 4. 位置现查：三档剪枝

`sources(...)` 返回 `List<BlockAuraContribution(position, aura)>`（运行期对象，带 `aura` 值，
好让 `AuraService` 不必再查一次定义）：

1. `section.hasOnlyAir()` —— O(1)，整段空气直接否掉；
2. `section.maybeHas(state -> index.byBlock().containsKey(state.getBlock()))` —— O(调色板条目)，
   `SingleValuePalette` 1 次、`LinearPalette` ≤16、`HashMapPalette` ≤256；`GlobalPalette` 恒真（>256 种状态）是已知最坏情况；
3. `section.getStates().bitsPerEntry() == 0` —— 整段一种状态，命中就是全 4096 个位置、**一次存储读都不需要**；
4. 剩下的才扫 4096，顺序为 `y → z → x`（x 最内层＝顺序访问位存储），比较用 `state.getBlock() == target`
   （`BlockState` 与 `Block` 都是单例，引用比较）。

被阵法吸收的方块要跳过（环境聚合里已经把它们减掉过，精确环再加一次就是双计），
所以 `sources(...)` 顺带用 `FormationAbsorption.Sources.absorbedBy(pos)` 过滤；没有阵法时该列表为空，
一次距离比较都不做。

同一次 rebuild 里的复用：`Sources` 与 `Index` 每次 rebuild 各建一次，逐段传下去，不在段里重新构造。

## 5. 数据形状的前后对比

**旧**（`AuraChunkAttachment.CODEC`）：

```json
"block_aura_sections": {
  "<sectionY>": {
    "aura":    { "<aura id>": {"amount": …, "max": …, "regen_per_tick": …, "color": …} },
    "sources": [ {"position": [x, y, z], "aura": { … }, "absorbed_by": [[x, y, z], …]} , … ]
  }
}
```

**新**：

```json
"block_aura_sections": { "<sectionY>": { "aura": { … } } }
```

- 破坏性但**不崩**：`RecordCodecBuilder` 对多出来的键是静默忽略（房规里那条"未知字段静默丢掉"），
  所以旧档读进来 `sources` 直接被丢掉，`aura` 照常成为基线；新档写出去不再有那两个键。
- `absorbedAura` 本来就"永不保存"（`AuraChunkAttachment:40-42` 的注释），这一轮仍然只活在内存里。

**关键前提：每段的聚合必须继续入档。** `initializeAuras` 在初始化时把整个 `blockAura` 加进池子，
之后每次重建走 `applyBlockContribution(previous, current)` 的差值；读档时池子与聚合都来自存档，差值为 0。
若连聚合也不存，`initialized` 已是 `true`，第一次重建就是"从空加到全量"，**每次读档把方块部分再加一遍**。

## 6. 吸收（阵法供给）怎么算

`absorbedAura`（按控制器记的合计）仍然只在整区块重建时算，且**只在有阵法够得着这个区块时**才算：
`Sources.of(...)` 为空就直接写一张空表，并因此可以走 §3 的计数路径。

有阵法时走 `walk(...)`：一次逐位置遍历、`maybeHas` 闸门、`bitsPerEntry()==0` 短路，
同一趟既给出每段的环境聚合（跳过被吸收的方块），也给出每控制器的吸收合计；位置用完即丢。

子区块入口（`rebuild(level, chunk, sectionY)`）**不动吸收表**：它是给"某一段的聚合脏了"用的，
而阵法覆盖与否不是一段的属性。它自己仍然要区分两种情况——被阵法覆盖的区块上必须走 `walk`（否则会把
被吸收的方块算进环境），只是不写回吸收表。阵法立/撤本来就会把半径内所有区块标脏走整区块重建
（`FormationWorldService.invalidateAura`），所以这条不对称在实践中不会留下旧值。这条限制写进代码注释。

## 7. 索引常驻

`Index`（`Block → List<BlockAura>`）原来是每次 `rebuild` 都重建一遍：每次都要
`MxtDatapackRegistries.holders(...)` 加逐条 `RegistryCodecs.resolve`（展开 `#标签`）。
现在改成常驻 + 显式失效，照 `AlchemyHeatService` 的形状：

- `BlockAuraService.reload(RegistryAccess)`：重建整张表（`DatapackCache.onTagsUpdated` 里调，
  因为标签可以在不换注册表实例的情况下变）；
- `BlockAuraService.clear()`：丢掉（客户端 `LoggingOut` 时调）；
- 惰性兜底：表为空且从没建过时，`index(access)` 现建一次（防止早于 datapack 加载的调用路径）。

`matches(ServerLevel, BlockState)` 同步改成查这张表，顺带把"每个放置/破坏事件都重新解析一遍全部定义"
这个热路径消掉（它原来在 `AuraChunkTicker` 的 `BreakBlockEvent` / `EntityPlaceEvent` 里逐事件调用）。

## 8. 后续（本轮不做）

1. 精确环的 `sources` 记忆化：`AuraQueryCache` 加一张 `(chunkPos, sectionY) → List<…>`，跟着 `advance` 每 tick 清。
2. `AuraChunkTicker.markDirty` 不要 `getChunkAt`（它会 `loadOrGenerate`，立阵时把半径内区块全部加载）。
3. 把 `sources` 换成 8³ 子桶聚合（位置从根上消失，代价是 ≤7 格误差）。
4. 真要"每 tick 大量枚举位置"时，才考虑 mixin 进 `PalettedContainer` 直接扫原始 long（`BitStorage` 是公开接口，
   但 `data` 字段与 `Data` record 都是 private，只能用 `@Unique` 方法暴露，不能用 `@Accessor`）。
