## 0. 结论

一句话：**只留一个概念 —— `Ability`（`data/<ns>/mxt/ability/<path>.json`）。`ArtifactAbility` 与固有表 `mxt:artifact_ability_type` 整体退役；法器定义里的 `abilities` 变成"能力引用或内联能力"的列表；`ToggableArtifactAbility` 升级为与宿主无关的 `Toggable`；冷却成为每个能力实例各自一条的通用能力。**

| # | 决定 | 一句话理由 |
| --- | --- | --- |
| 1 | `mxt:passive` / `mxt:active` 两个包装类型**删除** | 它们只是"把技能授予出去"。合并后法器直接列出能力 id，`type` 自己说明它是被动（`mxt:modifier`）还是按一下（`mxt:active`），不再需要第二处声明"我是被动/主动" |
| 2 | `mxt:flight` / `mxt:storage` / `mxt:upkeep` 变成 **`mxt:ability_type` 的条目** | 它们本来就是"这件东西能干什么"，与 `mxt:modifier` / `mxt:channelled` 同级 |
| 3 | 法器 `abilities` 接受**注册表 id** 或**内联对象**；内联对象的身份是**派生 id** `<父>/<key>` | 保留"一个文件写完一件法器"的写法，同时给每个条目一个稳定身份（状态、冷却、轮盘格都按它寻址）。沿用现有 `ArtifactCapability` 已经把 `法器id/key` 拼成一个 id 的做法 |
| 4 | 新增接口 `Toggable`（`key` / `displayName` / `state` / `activate`），**判据 = 实现它**，与宿主无关 | 轮盘只说一句"我能被触发"。技能、法器技能、脚本、命令、HUD、将来的载具面板走同一个入口 |
| 5 | 冷却**按能力实例**独立：`Ability.cooldown` + 附件里的冷却表，键从 `Holder<Ability>` 改成 `AbilityRef`（含派生 id） | 顶层注册表能力 = 全局一条冷却（老行为）；内联能力 = 每件宿主各一条。容器里的子能力本来就各算各的（`AbilityService.useComposite` 已经是这样），这个口径**保持并推广** |
| 6 | 状态与冷却是唯一的**两处寻址**，都改成 `Identifier`（能力 id 或派生 id） | 现在 `DataStorageHolder` 已经按 `Identifier` 寻址，冷却表按 `Holder` 寻址；统一成前者，内联能力才可能有状态 |
| 7 | 借 Origins 的三样：**内联容器能力 + 派生 id**、**类型自带状态组件**（冷却不该让包作者手写两遍）、**`Toggleable` + `KeySettings`**（含"按住"语义） | 见 §9 |

## 1. 合并后的形状

### 1.1 一个定义、三种来源、一个入口

```text
                        ┌─────────────────────────────────────────────┐
   授予来源             │  Ability（mxt:ability 注册表条目，或内联对象）│
   ────────             │  name/description/type/costs/cooldown/...    │
   技能书（technique）──▶│                                             │
   命令 / 战利品        │  type = mxt:active | modifier | triggered |  │
   修炼突破 / 阵法      │         aura | channelled | composite |     │
   物品（法器携带）────▶│         word | empty | flight | storage |   │
   脚本（KubeJS）       │         upkeep                              │
                        └──────────────┬──────────────────────────────┘
                                       │ 地址 = AbilityRef（id 或 <父>/<key>）
                        ┌──────────────▼──────────────────────────────┐
   状态与冷却           │ AbilityAttachment.storage（按 id 寻址）       │
   （宿主 = 持有者）     │ AbilityAttachment.cooldowns（按 AbilityRef）  │
                        └─────────────────────────────────────────────┘
                                       │
   唯一按一下的入口       AbilityActivationService.activate(holder, ref, carrier?)
                                       │            ▲
                                       │            └── 轮盘 / 命令 / KubeJS / HUD / 载具面板
                                       └── mxt:active → AbilityService.use（校验→付款→行为）
                                           mxt:flight → FlightService.mount/dismount
                                           mxt:storage → 打开箱子
```

### 1.2 类型全表（合并后 11 个，全在 `mxt:ability_type`）

| `type` | 来源 | 需要物品宿主 | 行为 |
| --- | --- | --- | --- |
| `mxt:empty` | 现有 | 否 | 占位（注册表默认项） |
| `mxt:active` | 现有 | 否 | 按一下施放；`slot` 字段 |
| `mxt:triggered` | 现有 | 否 | 事件触发；`triggers` + `chance` |
| `mxt:modifier` | 现有 | 否 | 常驻属性修正（原"被动技能"） |
| `mxt:aura` | 现有 | 否 | 范围脉冲；`interval` + `radius` |
| `mxt:channelled` | 现有 | 否 | 引导；`tick_interval` + `upkeep_costs` |
| `mxt:composite` | 现有 | 否 | 组合；`abilities` + `all_required` |
| `mxt:word` | 现有 | 否 | 口令效果（白名单） |
| `mxt:flight` | **新**（原 `artifact_ability_type`） | **是** | 载人飞行：`speed` + `display`；每 tick 的 `costs` 走顶层 `costs` |
| `mxt:storage` | **新** | **是** | 这件宿主自带容器：`slots` |
| `mxt:upkeep` | **新** | **是** | 携带期间周期扣费：`interval` + `on_fail`；费用走顶层 `costs` |

> 合并顺带修掉现在的**重复声明**：`mxt:flight` 有 `costs`、`mxt:upkeep` 有 `costs`，与顶层 `Ability.costs` 是同一个概念的两份字段。合并后 `costs` 只有顶层一处（`mxt:channelled.upkeep_costs` 是"引导维持"这一特殊语义，保留在类型里并改名统一见 §6.3）。

### 1.3 法器定义退化成"能力清单"

```json
// 之前（两套形状）
{
  "items": "minecraft:diamond_sword",
  "abilities": [
    { "type": "mxt:passive", "abilities": "mxt_test:artifact_guard" },
    { "type": "mxt:active",  "abilities": "mxt_test:firebolt" },
    { "type": "mxt:flight",  "speed": 0.1, "costs": [{ "id": "mxt_test:qi", "amount": 1 }] },
    { "type": "mxt:storage", "slots": 9 }
  ]
}

// 之后（一套形状：引用 + 内联）
{
  "items": "minecraft:diamond_sword",
  "abilities": [
    "mxt_test:artifact_guard",
    "mxt_test:firebolt",
    { "key": "flight",  "type": "mxt:flight",  "speed": 0.1, "costs": [{ "id": "mxt_test:qi", "amount": 1 }], "cooldown": 100 },
    { "key": "storage", "type": "mxt:storage", "slots": 9, "cooldown": 20 }
  ]
}
```

- 字符串 = 引用注册表条目，身份就是那个 id（多件法器可以共用同一条能力定义）。
- 对象 = 内联能力，`key` 在一份宿主定义内唯一，身份 = `<法器 id>/<key>`（`mxt_test:bound_sword/flight`）——**今天 `ArtifactCapability` 拼出来的一模一样**，所以轮盘里已经存着的 `wheel_layout` 格子不用迁移。
- 内联能力没有 `key` 由加载期拒绝（身份不能是空的）。

## 2. 身份：`AbilityRef` 与派生 id

### 2.1 为什么必须有派生 id

合并的硬约束是"内联条目也要有稳定身份"，否则三件事同时崩：

1. **状态**：`DataStorageHolder` 按 `Identifier` 寻址（`storage().get(id, kind)`），内联能力若无 id 就没法存冷却、充能、开关。
2. **冷却**：`AbilityAttachment.cooldowns` 现在是 `Map<Holder<Ability>, Long>`；内联能力没有 `Holder`。
3. **轮盘格**：`WheelSlot(kind, id)` 落盘在网络与附件里，格子的身份到现在为止一直是 `Identifier`。

Origins 的解法值得直接借：`MultiplePower` 把子能力写成 `Map<String, Power>`，`PowerHolder` 把子能力的 id 拼成 `<父 id>_<key>` 并**递归展平**（`PowerHolder.stream()`），子能力 `isHidden() == true`，状态按展平后的 id 存。我们照抄这个思路，只把 `_` 换成 `/`（`.` 与 `_` 在 `Identifier` 路径里合法但语义混乱，`/` 已经是本仓库 "一个 id 里带子项" 的既有写法）。

### 2.2 `AbilityRef`

```java
// 一个能力的地址：注册表条目用 Holder，内联条目用派生 id；两者都能编码成一个 id。
public sealed interface AbilityRef {
    Identifier id();                       // 派生 id 也是 Identifier
    Optional<Holder<Ability>> resolved();  // 内联条目为空
}
```

- 顶层引用：`resolved()` 有值，`id()` = 注册表 id。
- 内联条目：`resolved()` 为空，`id()` = `<父>/<key>`，值随宿主定义一起解码出来（宿主解析时构造，缓存在解析结果里）。
- **序列化**：`cooldowns` / `channelled_ability` 只存 `Identifier`，运行时用 `AbilityRefs.resolve(registries, id)` 还原（派生 id 按最后一个 `/` 切分，找宿主定义，再按 key 找内联条目）。这与 `ArtifactCapability.parse` 的规则**完全一致**，所以两处可以共用一份实现。
- 一次性代价：`AbilityService`、`AbilityStorage`、`AbilityEventBridge`、`AbilityModifierService`、`WheelSources`、`WheelService`、`AbilityWheelEntry`、`WheelEntryKind.exists` 的签名从 `Holder<Ability>` 换成 `AbilityRef`。这是本次重构最大的一块机械改动（约 10 个文件）。

### 2.3 内联能力能不能被别处引用

**不能**，也不该能：`AbilityRef.id()` 只在"它所属宿主的解析结果"里可解析。想被别处共用就把它提升成注册表条目（写一个 `mxt/ability/*.json`），法器里写字符串引用它。这条规则要写进文档，否则包作者会以为 `ns:path/key` 到处可用。

## 3. `Toggable`：与宿主无关的"按一下"

### 3.1 接口

```java
/**
 * Something the wheel can trigger. Implementing it is the whole of saying "put me on the wheel"; who owns the
 * ability (an entity's grant, an item being carried) is the caller's business, not this interface's.
 */
public interface Toggable {
    // Unique within one host definition; becomes the second half of the entry's id (`<host>/<key>`).
    String key();

    Component displayName();

    // Empty = a one-shot (nothing stays on, e.g. storage); present = a switch (e.g. flight).
    default Optional<Boolean> state(ToggleContext context) { return Optional.empty(); }

    // Server side only, one call per press; a refusal is a value, never an exception.
    Result activate(ToggleContext context);

    record Result(boolean changed, @Nullable Failure failure) { ... }

    enum Failure { NOT_CARRIED, NOT_OWNED, ALREADY_SET, UNAVAILABLE, ON_COOLDOWN, NO_CARRIER, INSUFFICIENT_COST }
}

// 取代 ArtifactToggleContext：宿主可以是"玩家的授予"，也可以是"玩家携带的某件物品"。
public record ToggleContext(LivingEntity holder, @Nullable ItemStack carrier, AbilityRef ability, FormulaContext formula) {}
```

与现在的 `ToggableArtifactAbility` 的差别只有一条，但很关键：**`activate` 不再自带"这件法器"这个前提**，`carrier` 变成可空的上下文。于是：

| 实现 | `key()` | `state()` | `activate()` |
| --- | --- | --- | --- |
| `mxt:active`（默认实现，所有主动技能免费获得） | `"active"`（或 `slot` 名） | 空（一次性） | `AbilityService.use(ref, holder, carrier)` —— 冷却、消耗、条件、元素亲和全走同一条管线 |
| `mxt:channelled` | `"channel"` | 空 | 起引导 / 放引导 |
| `mxt:flight` | `"flight"` | 在读的那件载具就是本能力 | `FlightService.mount/dismount` |
| `mxt:storage` | `"storage"` | 空 | 打开箱子（复用原版 `ChestMenu`） |
| 将来：护体、剑域、引灵入刃… | 各自常量 | 有/无 | 各自实现 |

### 3.2 判据与轮盘

- `WheelEntryKind.ARTIFACT` 退役，`WheelSources.offers` 与 `WheelEntryKind.exists` 的两个 switch 合并成一个（40 号稿 §3 方案 A 的目标，本稿顺手达成）。
- `AbilityWheelEntry` + `ArtifactWheelEntry` → 一个 `ToggableWheelEntry(ref, toggable, carrier?)`；`cooldownTicks(player)` 统一读"该 `AbilityRef` 的冷却"（§4），`usable(player)` 统一问 `ability.condition()` 与冷却。
- 格的显示名：能力的 `name`（`DefinitionText.name`）优先，内联能力没有名字时回退到 `toggable.displayName()`（沿用今天的语言键）。
- **兼容**：`wheel_layout` 里已有 `kind = artifact` 的格子，id 形状（`ns:path/key`）在新模型里**含义不变**（还是"父定义 + key"）。迁移只需把那个 kind 映射成新的统一 kind（或保留 `ARTIFACT` 作为旧值的别名）。这是选 `/` 拼法的直接红利。

### 3.3 "其他地方要用可以直接接入"

唯一入口：

```java
public final class AbilityActivationService {
    // 服务端；ref 由调用者给，carrier 由来源决定（技能书/命令 = null，法器 = 那件物品）
    public static Toggable.Result activate(LivingEntity holder, AbilityRef ref, @Nullable ItemStack carrier);
    // 只问状态，不改变任何东西（客户端 HUD / 轮盘画状态用）
    public static Optional<Boolean> state(Player player, AbilityRef ref);
}
```

调用者：`WheelService.trigger`（轮盘）、`/mxt ability toggle`（命令）、`MxtKubeJsAbilityBindings`（脚本）、HUD 面板、将来的载具/法宝面板、其他模组（经 `api/` 里的接口）。**权限、冷却、消耗、条件都在 `activate` 内部完成**，调用者不重复。

## 4. 独立冷却

### 4.1 现状（已经"每能力一条"，但不完整）

| 部分 | 现在 | 问题 |
| --- | --- | --- |
| 声明 | `Ability.cooldown`（顶层 `NumberProvider`）**加上** `components: [{"type":"mxt:cooldown","ticks":N}]` | **同一个冷却写两遍**：顶层那个用于 `AbilityService.prepare` 的判定与轮盘显示，存储那个用于状态读取（`mxt:storage_cooldown` 条件）。两处数值不一致时行为取决于谁先写 |
| 状态 | `AbilityAttachment.cooldowns`（`Holder<Ability>` → 截止 tick）**加上** `mxt:cooldown` 存储（`duration` + 写入时刻） | 两份状态：一份在冷却地图里，一份在存储里；`revoke` 时清两处 |
| 键 | `Holder<Ability>` | 内联能力没有 `Holder` |
| 覆盖对象 | 只有 `mxt:ability` 里 8 个类型 | `mxt:flight` / `mxt:storage` / `mxt:upkeep` 完全没有冷却 |

### 4.2 目标口径

1. **所有 11 个类型都能写 `cooldown`**（顶层字段，`NumberProvider`，默认 `0`）。`mxt:storage` 因此可以"开一次箱 20 秒内不能再开"，`mxt:flight` 可以"落地后 5 秒内不能再起剑"。
2. **冷却按 `AbilityRef` 各算各的**：
   - 顶层条目 → 一条冷却（无论从技能书、命令还是三件法器上来的，都是同一条）——**这是老行为，不变**。
   - 内联条目 → 派生 id 一条，于是"同一份 `<剑>/flight` 只有一把剑那一条"，两把不同的剑各自独立。
   - `composite` / 容器里的每个子能力各自一条（`AbilityService.useComposite` 已经逐步写各自的冷却，保持）。
3. **状态只留一份**：`mxt:cooldown` 存储是唯一真源（它已经记着 `duration` 与写入时刻），`AbilityAttachment.cooldowns` 退化成它的**索引缓存**（或直接删掉，改由 `AbilityStorage` 读存储；`isOnCooldown` 只在每 tick 的手里被查询，读一次 `DataStorageHolder` 是可接受的）。
4. **声明只写一遍**：`cooldown` 字段**自动**产生 `CooldownDataStorage`（就像 Origins 的 `HasCooldownPower.createComponents` 自动 `collector.add(new CooldownComponent(...))`）。`components` 列表里的 `mxt:cooldown` 保留为"显式覆盖长度"的唯一写法（老包兼容），文档改成"通常不用写"。
5. **起算点**：仍然是"提交成功那一刻"（`CooldownDataStorage.changedAt`），不是"施放开始"。读条技的冷却从读条结束算，与今天一致。
6. **可选的共享冷却组**（**待拍板**，Origins 没有这个概念）：`cooldown_group`（字符串）；同一宿主上同组的能力共用一个截止时间。收益是"两个技能共享一个冷却"这类设计；代价是冷却表要按组再寻址一层。**建议 P2 再说**，先让"每实例独立"落地。

### 4.3 冷却的显示（借 Origins 的 `hud_render`）

Origins 的 `CooldownSettings(cooldown, hud_render)` 让**每个能力自己声明冷却怎么画**（`HudRenderable.getMinValue/getMaxValue/getValue/shouldRender`）。我们的对应物现在是：轮盘的 `cooldownTicks` + `mxt:storage_cooldown` 条件 + 资源条框架（`data/resourcebar`）。

建议（P2，可选）：给顶层加一个可选的 `hud` 子对象（`{"type": "mxt:cooldown_bar", ...}`），把一个能力的冷却/充能画进 HUD 布局框架（`screen/overlay/hud/` 已经是可拖动元素框架，加一个"能力状态元素"即可）。这属于"合并后的附加收益"，不是合并的前提。

## 5. 物品宿主（carrier）

### 5.1 来源要带上物品

`AbilityAttachment` 的来源账本键是 `Identifier`（`AbilitySources.equipment(slot, stack)` = `mxt:equipment/<槽>/<物品>`），所以"这个能力是从哪件物品来的"**现在已经能从来源 id 反推**——包括槽位。于是：

```java
// 一个能力此刻的宿主物品：按来源 id 反查持有者的槽（双手 + Curios），第一件命中者胜。
public final class AbilityCarriers {
    public static Optional<ItemStack> find(LivingEntity holder, AbilityRef ref);
    public static List<ItemStack> all(LivingEntity holder, AbilityRef ref);
}
```

- 来源 id 已经是 `equipment/<slot>/<namespace>/<path>`，反查不需要新存档字段。
- `mxt:flight` / `mxt:storage` / `mxt:upkeep` 声明"我需要 carrier"（`AbilityType.requiresCarrier()`，默认 `false`）；拿不到就返回 `Failure.NO_CARRIER`（对应今天的 `NOT_CARRIED`），**不报错**——被技能书授予一次飞行能力是合法写法，只是它永远飞不起来。
- 现在 `ArtifactToggleService` 的"第一件携带者胜"口径直接搬进 `AbilityCarriers.find`。

### 5.2 三处物品状态的去向

| 现在 | 之后 | 迁移 |
| --- | --- | --- |
| `FlightAttachment.archetype: Holder<Artifact>` | `AbilityRef`（就是那条飞行能力） | 存档老值（法器 id）能解码成一个 `AbilityRef`；老飞行再登入会被判成"那次飞行的能力已不是这条定义"而落剑（可接受，飞行本来就是瞬时状态；要更稳就按法器 → 旧 `mxt:flight` 条目做一次映射，见 §7） |
| 储物内容在物品组件 `mxt:artifact_storage` | 不变（容量改读 `mxt:storage.slots`） | 无 |
| `mxt:artifact_state`（归属 + 温养） | 不变（它本来就是**物品**的状态，不是能力的） | 无 |
| `mxt:upkeep` 无状态（世界时间锚） | 不变 | 无 |

**刻意不做的**：不把物品状态搬进 `AbilityAttachment`。飞行"哪件载具"、储物"里面装了什么"本质属于物品；搬到玩家附件会把"两把一样的剑"变成分不开的一件事（40 号稿 §2.1 的结论仍然成立，只是现在不需要它当阻碍了）。

### 5.3 归属（owner）

- `artifact.require_owner`（认主才能飞行/储物）留在**法器定义**上：它说的是"这件东西"，不是"这条能力"。
- `upkeep.owner_only` 留在 `mxt:upkeep` 类型里（它说的是"这条周期的费用由谁付"）。
- 合并**不**引入通用的 `requires_owner` 字段：两个旗标语义不同，合流只会让包作者猜。

## 6. 数据包形状变化

### 6.1 `mxt:ability` 顶层字段

| 字段 | 变化 |
| --- | --- |
| `name` / `description` | 不变（内联能力也可以写） |
| `type` | 不变（顶层内联分派，**文档现在的写法是错的**，见 §10.3） |
| `costs` | 不变；从现在起也是 `mxt:flight` / `mxt:upkeep` 的费用 |
| `cooldown` | 不变；语义扩展为"所有类型都支持" + "自动产生冷却状态"（§4.2） |
| `cast_time` | 不变（`mxt:active` / `mxt:channelled` 用） |
| `icon` | 不变（轮盘图标） |
| `components` | 不变；`mxt:cooldown` 变成"通常不用写" |
| `modifiers` / `damage_condition` / `condition` / `entity_action` / `target_selector` / `target_condition` / `bi_entity_action` / `element_affinity` / `element_affinity_mode` | 不变 |
| `key` | **新增（可选）**：只在内联于某个宿主时使用，作为派生 id 的后半段。顶层注册表条目写了它没有意义（加载期警告） |
| `item_action` | **新增（可选）**：对宿主物品执行的行为（`mxt:upkeep.on_fail` 并进来）。`ItemAction` 通道本来就有，`Ability` 只是缺这个字段 |
| `hidden` | **新增（可选，借 Origins `BaseSettings.hidden`）**：不进轮盘/HUD，但照常生效。容器子能力自动隐式 `hidden` |

字段预算：`Ability` 的 `RecordCodecBuilder.group` 现在是 16 个槽（17 个 JSON 字段，用 `MiscCodecs.pair` 并了一组）。加 `key` / `item_action` / `hidden` 需要再并一到两组，做法与 `cast_time`+`cooldown` 那一对相同。

### 6.2 `artifact.abilities`

- 类型：`ArtifactAbility[]` → `List<Either<Holder<Ability>, InlineAbility>>`。
- 内联对象的字段 = `Ability` 的字段 + 必填 `key`。
- 加载期校验（现在 `Artifact` 构造器里的三条"最多一条 flight/storage/upkeep" + "同 key 唯一"）：
  - `key` 在**一份宿主定义内**唯一（保留）。
  - "最多一条 `mxt:flight`"这类限制**取消**：改成"同 key 唯一"就够，`key` 由包作者给，两把不同形状的飞行也能共存（想限制就写同一 key，加载期自然拒绝）。

### 6.3 三个新类型自己的字段

| 类型 | 字段 | 从哪来 |
| --- | --- | --- |
| `mxt:flight` | `speed`（必填）、`display`（默认原值） | 原 `FlightArtifactAbility`；`costs` 上移到顶层 |
| `mxt:storage` | `slots`（必填） | 原 `StorageArtifactAbility`；容量仍按 9 取整、最多 54 |
| `mxt:upkeep` | `interval`（默认 20）、`on_fail`（默认 `mxt:no_op`）、`owner_only`（默认 true） | 原 `UpkeepArtifactAbility`；`costs` 上移到顶层，`on_fail` 用新顶层字段 `item_action` 还是留类型里？**建议留类型里**（它是"扣费失败时的补偿"，语义属于这条周期规则；顶层 `item_action` 留给别的用途） |

`mxt:channelled.upkeep_costs` **保留原名**（它是"引导维持"的专用费用，与顶层"施放费用"是两笔账；改名会让所有老包静默失效）。

### 6.4 会被删掉的

| 删 | 说明 |
| --- | --- |
| `mxt:artifact_ability_type`（整张固有注册表） | 与 `mxt:ability_type` 重复 |
| `ArtifactAbility`、`EmptyArtifactAbility`、`GrantArtifactAbility`（含 `Intent`）、`FlightArtifactAbility`、`StorageArtifactAbility`、`UpkeepArtifactAbility`、`ToggableArtifactAbility`、`ArtifactToggleContext`、`FlightDisplay`（移进 `mxt:flight` 类型） | 被 11 个 `AbilityType` 取代 |
| `mxt:passive` / `mxt:active` | 不再需要"授予包装" |
| `ServerCache.checkGrantedAbilityKinds` / `claimItems` 里的 intent 校验 | 不再有两份 intent；"引用能不能被授予"这件事消失（`mxt:modifier` 被 `mxt:active` 的槽引用只是没意义，不是错误） |
| `WheelEntryKind.ARTIFACT`、`ArtifactWheelEntry`、`ArtifactToggleService`、`ArtifactCapability`（并入 `AbilityRef`） | 轮盘只剩一套"可触发条目" |

#### 9.2.7 明确不要拿（跨类）

1. **origin / layer 与"选择起源"流程**：与 `SourceLedger`（按来源记账）不是一回事，两套授予模型不能并存。

5. **`Sided` 条件标记**（客户端跳过 server 专属 condition）：我们是服务端权威。
6. **静态侧表存运行时状态**（`HoldActionPower` 的 `static WeakHashMap`，不落盘不同步，"1 tick 没输入 = 松开"）：要拿的是"按住蓄力"的**玩法**，状态必须落 `data/storage/runtime/`（照 `ChannelPulse`），松开走显式事件（`cancelCast` 已有先例）。
7. **未知 `type` 静默兜底**（`DefaultedMappedRegistry` + `createEmpty` 让写错的类型安静地变成 `origins:empty`）：与我们"`type` 必填、空类型显式写"的口径相反。
8. **死字段与 FIXME 级实现**：`TogglePower.retain_state`、`BaseSettings.loading_priority`（零消费者）、`Power.getId` 的字符串后缀合成身份（自带 `//FIXME::Use PowerHolder instead`）、`StatusBarTexturePower` 的 `//FIXME::Move to Mixin class`。
9. **`Badge` / `PresetBadges`**：纯查看界面装饰。
10. **把容器存进实体附件**（`InventoryPower` 的决定）：我们存在物品组件上，方向更适合"随物品走"，不要反着改。

**三条排期判断**

- **先补信号，再谈 power**：jump / land / wake_up / block_place / bonemeal / projectile_hit / tame_hit / pickup / respawn 这九个信号缺一个，9.2.1 里对应类型就只能是空壳。补信号是**独立于本次合并**的一条线（`data/trigger/TriggerSignals.java` + `runtime/trigger/VanillaTriggerBridge.java`）。
- **不要移植 Origins 的资源 / HUD 家族**（`resource` / `modifiable_resource` / `math_resource` / `linked_resource` / `status_bar_texture` / `overlay`）：我们的 `resource` 定义 + `NumberProvider` + `data/resource/ResourceBar.java` + `registry/MxtFormulaVariables.java` 整体更强，重复引入会产生两套上限算法。
- **可以照抄实现而不是只抄语义的两个**：`HoverPower.java:37-44`（tick 清零 Y 速度）与 `PreventDeathPower.java:49-65`（`setHealth(1)` + cancel），逻辑短、不依赖 Origins 概念。

## 10. 不做、待拍板与开放项

### 10.1 刻意不做

- **不把 `resource` / `aura` / `curse` 并进 `Ability`**：它们是**定义**（有注册表、有身份、有面板），能力是**行为**；`mxt:modifier` 已经能读它们，合并只会让"资源"这个概念消失。
- **不动 `Cost`**（上一轮刚统一）与**货币**（`currency` 永不进能力）。
- **不引入 `loading_priority`**：原版数据包覆盖已经解决同名冲突。
- **不把物品状态（储物内容、归属、温养）搬进玩家附件**：见 §5.2。
- **不改 `Artifact` 的 `items` / `spirit_capacity` / 认主那套**：它们不是"能力"。

### 10.2 待拍板（按 `AGENTS.md` §7）

1. **`artifact.abilities` 混写**：允许"字符串引用 + 内联对象"混在一个数组里（本稿推荐），还是只允许其中一种？
2. **内联能力的 `key` 必填还是自动生成**：本稿推荐必填（身份要稳定，且轮盘格子落盘用得上）；自动生成（按数组下标或类型名）会让"移动数组顺序"改变身份。
3. **轮盘 `kind` 收窄**：`ARTIFACT` 保留为兼容别名（推荐）还是迁移存档？
4. **`cooldown_group`（共享冷却组）**：要不要（§4.2 第 6 条）。
5. **`AbilityRef` 是否进 `api/`**：它会被 KubeJS 与将来的其他模组看到；进 `api/` 就等于承诺形状。
6. **死亡后能力状态**（借 Origins `respawn` 引出的问题）：冷却/充能/开关现在跨死亡保留，是否要清？

### 10.3 顺带发现的文档错误（与本稿同一处，建议一起修）

`docs/数据包格式.md:775` 与文档站 `datapack/json/ability.md`（中英）把技能类型对象写成**顶层 `ability` 字段**，但**代码与实际数据包都是顶层 `type`**：

- 代码：`Ability.DIRECT_CODEC` 用 `AbilityType.CODEC.forGetter(Ability::type)`，而 `AbilityType.CODEC` 是内联的 `dispatchMap("type", ...)` → 键就是 `type`。
- 证据：`src/test-mod/resources/data/mxt_test/mxt/ability/qingxiao_firebolt.json:2`（`"type": "mxt:active"`、`"slot": "primary"` 平铺）、`data/probe/mxt/ability/*.json` 全部如此。
- 受影响：仓库 `docs/数据包格式.md`（字段表 1 行 + 4 段示例）、文档站 `datapack/json/ability.md` 中英各 4–5 处。**照文档写的包会加载失败**。

### 10.4 开放项

- `AbilityRef` 的缓存：派生 id 每次解析都要找宿主定义 → 需要一张"世界加载期构建、注册表实例变化时失效"的索引（与 `DamageElements` 的缓存键口径相同）。
- 内联能力与 `/reload`：宿主定义重建时，`AbilityAttachment` 里按派生 id 存的状态**保留**（id 没变）——这是期望行为，但要写清楚"改 key 等于换了一个能力，旧的冷却与充能留在存档里等清理"（`revoke` 时清，但内联能力没有 revoke 事件）。
- `composite` 与"父子活跃"语义：要不要借 `Power.isActive` 让容器成为"开关一关，子能力全停"。
- `ServerCache` 的校验点搬家：intent 校验删掉后，跨定义校验还剩哪些（法器认领同一物品、轮盘 id 可解析、内联 key 唯一）。
- **技能自带的容器（`mxt:storage`）在"没有物品"时内容存哪**：现在必然挂在物品组件上；合并后一个被技能书授予的 `mxt:storage` 语法合法但无处可存。三个选项：加载期拒绝非物品宿主的 `mxt:storage`（推荐，简单明确）、退化成"打开时临时生成"、或引入"能力自己的容器状态"（等于把 Origins `InventoryComponent` 那套搬进来，与 §5.2 的方向相反）。
