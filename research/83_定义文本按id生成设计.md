# 83. 定义文本彻底按 id 生成

**状态：已落地**（2026-10-05 按用户要求"彻底取消掉 `NamedDefinition` 和注册表对象的 `name` 和 `description`，全都走根据 id 自动生成"；`compileJava` / `compileTestModJava` / `processTestModResources` 通过、两份 lang 键集合一致；**探针未实跑**）

**取代 [`37`](37_名字与描述自动填充设计.md) 与 [`38`](38_定义文本字段全量应用.md) 的文本层**：那两稿建起来的东西（`api/NamedDefinition`、`util/codec/ContextNameCodec`、`util/codec/ContextNameListCodec`、`RegistryOps` 携带解码期条目 id 的那套 mixin + 访问器）本稿全部删除。**生成键的四段式拼法不变**——变的只是"定义还能不能自己带文本"这一个问题的答案：从"能，写了就以它为准"变成"不能，永远按 id 生成"。

## 0. 一句话

**定义不再存文本。** 一个定义的 `name` 与 `description` 永远是**按它注册时的 id 现算出来**的翻译键：

```
名字：  <注册表路径>.<注册表命名空间>.<条目命名空间>.<条目路径>
描述：  <名字键>.description
```

包唯一能"给一个定义配词"的办法，就是**翻译这个生成的键**。于是"写出来的文本压过生成的键"这件事在形状上不再可能——`RecordCodecBuilder` 里根本没有那个字段可写。

## 1. 为什么改

`37` / `38` 那套形状的代价体现在四处，都是"为了支持一个可选文本字段"而付的：

1. **两条显示路径必须同时维护。** 调用方问 `DefinitionText.name(holder)` 时，它得先看这个定义实不实现 `NamedDefinition`：实现了就读它身上的字段，没实现才按 holder 的 key 推键。于是"名字从哪来"有两个答案，且**同名的键可能有两种来源**——一种是包里写的字面量，一种是推导出来的键，两者在显示上不可区分。
2. **列表型文本需要第二套编解码器。** `minor_stages` 是"一组文本"，于是 `ContextNameListCodec` 单独存在，而它承载的 `RealmStage` 刚好又撞上 `RecordCodecBuilder.group` 的 16 组件上限，被迫用 `MiscCodecs.pair` 把 `name` 与 `description` 并成一组、把别的字段也凑对——**上限压力有一半是这个字段造成的**。
3. **解码期的条目 id 必须被"运"到 codec 里。** 省略字段时要生成键，生成的键又取决于"这条定义正在以什么 id 解码"，而 codec 本身拿不到这个信息。于是有了 `RegistryOpsMixin` + `RegistryDataLoaderMixin` + `accessor/ResourceLoadingOps`：在 loader 建 `RegistryOps` 时把当前 `ResourceKey` 塞进去，codec 再从 ops 里读出来。三个文件、两处注入，只服务这一个字段，且**注入失败只在运行期才暴露**（`defaultRequire: 1` 会让它直接崩在启动）。
4. **旧包的坏字段是静默的。** `RecordCodecBuilder` 不认识未知字段、会静默丢掉（`AGENTS.md` §4），所以 `"name": 123` 这类写错的值不会报错，只是那个键不再生效——而这个字段恰恰是"内容作者最容易写错、又最不容易发现"的那一类。

反过来，生成键那条路本来就是**默认路径**（绝大多数包根本不会写 `name`），把它提成唯一路径，付出的是"老包写了 `name` / `description` 的地方文本不再生效"这个**破坏性迁移**，换来的是：定义里没有任何文本、显示路径只有一条、`minor_stages` 退化成一个整数、三个只为它存在的注入文件消失。

## 2. 新形状

### 2.1 生成键就是拼出来的

`util/DefinitionText.java` 收缩成一个只有静态方法的工具类（私有构造器），唯一的拼法仍是四段式：

| 出口 | 用途 |
| --- | --- |
| `key(ResourceKey<?>)` | 最完整的一条：`key.registry()` 给注册表、`key.identifier()` 给条目 id |
| `key(Identifier registry, Identifier id)` | 手里是注册表 id |
| `key(String category, String registryNamespace, Identifier id)` | 唯一真正拼字符串的地方 |
| `category(Identifier registry)` | 类别＝注册表的 path，**不是**另起一个名字 |
| `name(ResourceKey<?>)` / `name(Holder<?>)` | 名字 |
| `description(ResourceKey<?>)` / `description(Holder<?>)` | 名字键 + `.description` |
| `minorStage(ResourceKey<?>, int)` / `minorStage(Holder<?>, int)` | 名字键 + `.minor_stage.` + 0-based 下标 |
| `derived(ResourceKey<?>, String)` / `derived(Holder<?>, String)` | 上面两条共用的底座：名字键 + 后缀 |
| `name(Identifier id, String category)` | **只剩一个 id 时**的兜底（台账 / 命令参数 / 网络载荷 / `AuraResult.source()` 这类运行期来源 id） |
| `resolved(Component)` | 这段文字到底有没有：字面量，或被定义的键 |
| `nameOrId(...)` | 必须显示点什么的名字出口：被翻译就用名字，没有就回退 **id** |

**`name(holder, category)` 这个两参重载已删除。** 类别由注册表自己答（就是注册表路径），调用方不再传；只有手里连注册表都没有、只剩一个 `Identifier` 时才用最后一行的两参形式。

**`defaultText(...)` 已删除**——它是"省略时生成什么"的那个出口，现在没有"省略"这回事了。

### 2.2 被删的文件

| 文件 | 为什么删 |
| --- | --- |
| `api/NamedDefinition.java` | 接口本身：定义不再有文本可读 |
| `util/codec/ContextNameCodec.java` | 单值文本字段的 codec |
| `util/codec/ContextNameListCodec.java` | 列表型文本字段的 codec（唯一用户是 `minor_stages`） |
| `accessor/ResourceLoadingOps.java` | 把解码期条目 id 交给 codec 的访问器 |
| `mixin/codec/RegistryOpsMixin.java` | 同上，往 `RegistryOps` 上挂 key |
| `mixin/codec/RegistryDataLoaderMixin.java` | 同上，在 loader 侧把 key 塞进去 |

`src/main/resources/mxt.mixins.json` 的 `mixins` 段因此回到四项：`EntityMountRemovalMixin`、`EntityPerchMixin`、`MinecraftServerRuntimeAccessor`、`ServerLevelSeedMixin`（两条 `codec.*` 移除）。**这是本稿顺带赚到的**：省掉两处只在运行期才验证的注入。

### 2.3 `minor_stages` 从"一组名字"变成"一个整数"

`realm_stage.minor_stages` 现在是 `Codec.INT.optionalFieldOf("minor_stages", 0)`：**数量**，范围 `0`–`1024`（`RealmStage.MAX_MINOR_STAGES`，构造器 `validate` 拒绝越界）。每一重的名字一律生成：

```
<本境界名字键>.minor_stage.<0-based 下标>
```

用户对这条拍的是 **"一起去掉，只留数量"**——连"只留名字列表、去掉别的"这个折中也没取，子境界的名字不再有任何书写途径。

- 原来写 `"minor_stages": ["金丹初期", "金丹中期", "金丹后期"]` 的包，改成 `"minor_stages": 3`；三重的名字变成 `…minor_stage.0/1/2`。
- `InformationManager.minorStageText` 从 `minorStages().get(index)` 改成 `DefinitionText.minorStage(realm, index)`。
- `CultivationService.minorStage` 的段数从 `minorStages().size()` 改成 `minorStages()`（整数本身）。
- `minor_stage_abilities[].stage` 的越界校验跟着改成"对着这个整数比"。
- 子境界名也过 `DefinitionText.resolved(...)`：`InformationManager.minorStageText` 在没被翻译时返回 `null`，那一重就整段不显示（与"这一境界没有子境界"同一条路），不会把 `…minor_stage.3` 打进信息面板。

### 2.4 `description` 照旧画，只是换成生成的键

用户对"还要不要画描述"拍的是 **"照旧画，改为纯生成的键"**。所以 `DefinitionText.description(...)` 与 `resolved(...)` 都**保留**，画描述的还是这四处（一处没增没减，第四处是聊天栏读出功法那一行、原先漏记了），只是文本来源从"字段"变成"生成的键"：

1. 品质提示框（`ItemQualityTooltipAppender`）
2. 契约卷轴提示框
3. 认领丹药的物品提示框（`ItemBindingTooltipAppender.appendPill`）
4. 功法书被读时聊天栏那一行（`TechniqueItemService.readOut`）

**名字也只有两个出口**：必须显示点什么的地方（列表行 / 标题 / 面板条目 / 当参数嵌进别的句子）用 `DefinitionText.nameOrId(...)`，没被翻译就回退显示 **id**；可以空着的地方（提示框里只起标题作用的那一行）用 `resolved(text(...))` 整行不画。

四处都过 **`DefinitionText.resolved(...)`** 这道闸门——它查的是语言文件里到底有没有这个键（`Language.getInstance().has(key)`；字面量与带 fallback 的翻译件照旧算有），没有就整行不输出，而不是把 `quality.mxt.foo.description` 这行原文打进提示框或聊天栏。**这条闸门现在比过去更重要**——过去"包写了字面量"是不需要翻译的，现在**所有**描述都只在被翻译时才出现；而且 `getString()` 不能当判据（键缺失时它回退成键名本身，永远非空）。

`ItemQuality.Modifier.description` 与 `DescribedEntry.description`（`pill` / `item_binding` 的 `conditions[]`）**不受影响**：它们是子对象自己的字段，不是定义文本，继续按原样写、原样画。

## 3. 逐处落地

### 3.1 24 个定义记录

按注册表路径列出（名字键的类别就是它）：

`ability`、`alchemy_furnace`、`alchemy_wall_material`、`artifact`、`aura`、`contract_type`、`cultivation`、`curse`、`element`、`formation`、`medicinal_property`、`physique`、`pill`、`pill_binding`、`progression`、`quality`、`realm_stage`、`resource`、`secret_realm`、`spirit_herb`、`spirit_root`、`talisman`、`technique`、`tribulation`

每个文件做四件事：从 record 头删掉两个 `Component` 参数、从 `implements` 子句删掉 `NamedDefinition`、删掉两行 `ContextNameCodec.*.forGetter(...)`、删掉不再使用的 `CATEGORY` 常量与 import。

**两个特例：**

- **`MedicinalProperty`**：这个定义**只有**那两个字段，删完就是 `record MedicinalProperty()`。它的 `DIRECT_CODEC` 改成 `MapCodec.unit(new MedicinalProperty()).codec()`——定义本身不声明任何数据，全部含义就是它的 id。它的 `implements NamedDefinition` 删掉后不补任何接口（它本来也不实现 `QualityProvider`）。
- **`Progression`**：`name` / `description` 原本排在最前，删完 record 头从 `(Component, Component, Optional<Holder<Progression>>, NumberProvider, double)` 变成 `(Optional<…>, NumberProvider, double)`，`.apply` 的 lambda 参数跟着少两个。

### 3.2 `MiscCodecs.pair` 的松动

`RealmStage`（原 18 组件）、`SecretRealm`（原 17）、`Formation` 都曾为 16 上限把 `name` + `description` 并成一组（`SecretRealm` / `Formation` 是"描述 + 品质"凑一对）。字段删掉后这三处**不再需要那一对**，改成普通的一字段一线：

- `RealmStage`：`minor_stages` 从 pair 里出来，变成一行 `Codec.INT`；group 降到 16 以内（注释从"Eighteen components; three pairs"改成"Sixteen components"）。
- `SecretRealm` / `Formation`：`MiscCodecs.pair(ItemQuality.CODEC.optionalFieldOf("quality"))` 这个只有一项的 pair 拆成 `ItemQuality.CODEC.optionalFieldOf("quality").forGetter(X::quality)`，`.apply` 的 lambda 相应少一个 `text` 参数。

**其余 `pair` 保留不动**（`Formation` 的 `structure_template`+`structure_check`、`RealmStage` 的三对、`SecretRealm` 的 `enter_condition`+`exit_condition`、`AlchemyRecipe` 的三对）——它们本来就在，去掉也无害，但**没有必要为了这次改动去动它们**。

### 3.3 显示侧与消费者

| 位置 | 改法 |
| --- | --- |
| `QualityService.coloredName(holder, text)` 的调用点（picker / 丹炉菜单 / 锻造台两处 / 品质提示框） | 一律换成已有的 `QualityService.displayName(holder)`（它本来就是 `coloredName(holder, DefinitionText.name(holder))`） |
| `StorageAbilityType` 的储物容器标题 | `context.ability().value().name()` → `DefinitionText.name(context.ability())` |
| `ArtifactDescription` 的技能行 | `ability.name()` → `DefinitionText.name(entry)`（`entry` 是那个 `Holder<Ability>`） |
| `SpiritHerbTooltipAppender` | `herb.name().copy()` → `DefinitionText.name(found)` |
| `AbilityWheelEntry.title()` | `this.ability.value().name()` → `DefinitionText.name(this.ability)` |
| `PillItem.getName` | `pill.value().name()` → `DefinitionText.name(pill)` |
| `AlchemyFurnaceMenu` 的炉型名 | `holder.value().name()` → `DefinitionText.<Component>map(DefinitionText::name)`（显式见证，`orElse` 另一侧是 `Component`） |
| `PillComponent.applyTo` | 构造 `new Pill(...)` 时少传两个文本参数 |
| `Pill.defaults()` | 同上，改成 `new Pill(Optional.empty(), DEFAULT_COLOR, …)` |

**丹药提示框需要"这个定义是谁"**，而 `PillResolution` 过去只带一份叠好的 `effects`（`Pill` 值，没有 id）。这里加了一列 **`Optional<Holder<Pill>> definition`**：`bound` / `componentOnly(definition, effects)` 带上来源 holder，只有"组件覆盖默认值、任何定义都没认领"那一种情形是空——**那一情形下不印标题**，而不是编一个。`unbound` 仍然记下那个已经不在注册表里的 holder（它正是要显示"绑定不存在"的那条路径）。

**`MxtTestCommands.verifyGeneratedNames` 重写**：原来它断言"夹具写的字面量压过生成的键"，现在断言每一类都读出生成键、并且**没被翻译的键不算已画文本**（`resolved` 为假）。原来那段"往 `RegistryOps` 上手动塞 key、解码一个定义、验证名字"的探针连同 `ResourceLoadingOps` import 一起删除——访问器已经不存在，而且新形状下"解码期 id"这个中间态根本不需要存在。

## 4. 破坏性迁移

| 老包写了 | 现在 |
| --- | --- |
| `"name": …` / `"description": …`（定义顶层） | **未知字段，静默忽略**（`RecordCodecBuilder` 的既定口径，`AGENTS.md` §4）。文本要显示出来，唯一办法是翻译生成的键 |
| `"minor_stages": ["a", "b"]` | **类型不符，整个定义解码失败**（`Codec.INT` 收不了数组）——这一条比上面那条响，因为它是字段类型错了 |
| `"minor_stages": 9` | 照旧，含义从"9 个名字"变成"9 重" |
| `"minor_stages"` 省略 | 照旧：`0` |

`"minor_stages"` 的失败是**刻意留响的**：老写法里那个数组装的往往就是显示文本（`"金丹初期"` 这种），静默变成一个数字是不可能的；直接拒绝、让包的作者看见，比"把数组长度当数量用"诚实。

**lang 侧**：本体主包的两份 lang 里，定义类别的键只有 5 个是生成的（`element.mxt.mxt.common`、`aura.mxt.mxt.common`、`resource.mxt.mxt.common`、`artifact.mxt.mxt.sky_swallowing_sword`、`ability.mxt.mxt.sky_swallowing_sword_qi`），它们本来就长这样，**无需改动**（本体主包从来没写过 `name` / `description`）。测试包的两份 lang：
- `core_forming` 那三重的键从 `.minor_stage.early/middle/late` 改成 `.minor_stage.0/1/2`（`qi_refining` 的九重本来就是 `.0`–`.8`，不用动）；
- 补 `element.mxt.mxt_test.metal.description`（那个夹具原来在 JSON 里写 `{"text": "Metal probe"}`，字面量没有键可查，现在描述必须被翻译才画得出来）；
- 删掉 `medicinal_property.mxt.mxt_test.herb/aux[.description]` 两条**没有任何夹具引用**的孤儿键（实际存在的是 `herb/auxiliary`）。

改完两份 lang 各自的 zh / en 键集合一致：本体 1166、测试包 385（原 386，减去两条孤儿、加上补的那条描述）。

## 5. 没有做 / 明确不做

- **不给"某处仍可写文本"留后门。** 用户要的是"彻底取消"，所以没有保留任何"定义自带文本"的口子（没有隐藏字段、没有"只在 X 情形下读字段"的特例）。
- **不改生成键的拼法。** 本稿就是"把过去的**默认**提成唯一路径"，所以键仍然是 `<类别>.mxt.<命名空间>.<路径>`，老包只要当初**翻译了生成的键**（而不是写了字面量），行为一字不变。
- **不动 `ItemQuality.Modifier.description` 与 `DescribedEntry.description`。** 它们不是定义文本。
- **不顺便清理其他 `pair`。** 见 §3.2。
- **不改 `docs/`（仓库内已停用的历史快照）。** 数据包字段说明的去处是文档站与 `docs/数据包格式.md`。
