# 灵气解析性能:每 tick 记忆与按需重算

## 现象

spark 采样服务端主线程,`AuraZoneEventBridge.onEntityTick` 占约 **88%**,调用链:

```
EntityTickEvent.Post
└─ AuraZoneEventBridge.onEntityTick        87.32%
   └─ AuraService.getPositionAura          87.17%
      └─ AuraService.resolveAura           87.11%
         └─ AuraService.applyBlockDistance 86.36%
            └─ AuraService.addWeighted     81.86%
               └─ sourceAvailability       51.34%
                  └─ staticZone            49.67%
                     └─ best               38.40%
                        └─ pickHighestPriority 36.33%
```

## 归因:抽样图会骗人,要自己量

抽样把 49.67% 归给 `staticZone`,很容易读成"注册表扫描太贵,建个索引就好"。所以加了**分阶段计时**(
`config.mxt.server.aura.query_stats` 打开,或用测试模组的单次查询报告),实测单次未缓存查询:

| 阶段                                 | 每次查询的开销      |
|------------------------------------|--------------|
| `biome`(`getBiome` + 取 ID)**57 次** | ≈ 23 µs      |
| `static`(注册表选域)                    | ≈ 6 µs       |
| `pools`(环境存量)                      | ≈ 0.5 µs     |
| `sources`(方块来源可用度)                 | ≈ 7 µs       |
| **合计**                             | **≈ 140 µs** |

**真凶不是注册表扫描,是 `getBiome`:每次查询被调 57 次**(7×7 区块里每个方块来源各一次),而它是 `staticZone` 的第一件事,*
*不在任何缓存里**。注册表那几微秒在 5 个 `aura_zone` 的测试包里根本不是问题。

`staticZone` 之所以在抽样图里显得占一半,是因为它被**从 `sourceAvailability` 里反复调用**,而每次都要先读群系。抽样按方法聚合,就把这笔账全记在它名下了。

## 措施

### 一、每 tick 记忆(`AuraQueryCache`)

同一游戏刻内,同一位置、同一定义的解析结果是确定的:输入只有位置、本 tick 的区块库存、游戏刻,没有随机也没有跨 tick 状态。

`AuraZoneEventBridge.onLevelTick`(`EventPriority.LOWEST`)在 `AuraChunkTicker`(`HIGH`)重算完本 tick 库存**之后**推进纪元。每个随
tick 失效的键都带 `gameTime`,纪元不匹配即未命中——即使推进没发生,最坏只是全部重算,不会返回过期数据。`getPositionAura` 在*
*查表之前**先 `flushDirty`,所以本 tick 放置的方块立刻可见。

| 表              | 键              | 摊销对象                       |
|----------------|----------------|----------------------------|
| `STATIC`       | 位置             | 注册表选域                      |
| `FORMATION`    | 位置             | 阵法匹配 + `max_bonus`         |
| `RESULT`       | 位置             | 整条管线                       |
| `POOLS`        | 位置 + 定义        | 环境存量(perlin + 波动)          |
| `BIOME`        | 位置             | **`getBiome`(实测省 20~38%)** |
| `AVAILABILITY` | 附件 + 来源 + 资源   | 来源可用度的环境部分                 |
| `HOLDER`       | 定义(不随 tick 失效) | 定义→holder 定位               |

每张表上限 16384 条,超限换新表;未命中只会重算。

### 二、按需重算(关键的一步)

实测发现:**一个位置每 tick 只被问一次**。审计打出的原始计数是"50 个方块来源、50 次调用、**50 次未命中**"——加上 `RESULT`
后每位置每 tick 仍要付一次全价 140 µs。缓存救不了没有重复的工作。

所以 `onEntityTick` 不再对每个实体每 tick 查询,而是先问"这个实体的答案**可能**变了吗":

```
needsQuery(实体) =
     新实体
  或 换了方块坐标 / 维度
  或 距上次重算已达到 entity_refresh_interval
```

跳跃的怪每 tick 都算,静止的怪几乎不算。这是收益最大的一步,因为它把"查询次数"这个乘数直接砍掉。

开关与代价都写在一个配置项上:

`config.mxt.server.aura.entity_refresh_interval`(默认 **10** 刻,范围 1~1200)

实体静止时唯一能让它看到不同灵气域的途径是:区块库存重建、新阵法出现、永久区域被编辑。**这个配置就是这个延迟的上界**。设为 1
即完全恢复旧行为(每实体每 tick 查询)。

代价说清楚:`AuraZoneEvent.Enter` / `Leave` 在实体静止时最多延迟该数值的刻数。跳跃中的实体不受影响。

### 三、外部手段:装 C2ME(不改本模组代码)

`getBiome` 的开销分两半。一半是**固定成本**:每次调用都要重做一遍 8 角抖动 Voronoi(`BiomeManager#getBiome`,48 次 LCG + 24
次 `Math.floorMod`),再走一次完整的 `ChunkSource#getChunk(..., BIOMES, false)` 往返(两次哈希查找 +
`CompletableFuture#join` + 4 格共享缓存整段右移),最后才读到区块里的调色板。已加载区块上这就是实测的 **0.40 µs/次**。

另一半是**噪声回退**:区块还没到 `BIOMES` 状态时,原版不会说"读不到",而是**当场把 5 条气候噪声跑一遍**(每条分量还会各自重算一次
`SHIFT`,单次约 100 次 `ImprovedNoise#noise`)。这条路径在原版里**没有任何缓存**——`flat_cache` / `cache_2d` 那两个标记只在区块生成的
`NoiseChunk` 里生效,`RandomState` 造 sampler 时甚至会把标记直接拆掉。

这后一半有现成的外部解法:

- [C2ME(C^2M-Engine)](https://modrinth.com/mod/c2me-neoforge) 是做区块生成 / IO / 加载多线程化的优化模组;它的 NeoForge
  移植版在 Modrinth 上明确列出了 `26.1.2`(与本仓库同一个 MC 版本),且标注服务端必需(`server_side: required`)。
- 它确实接管了生物群系源的 `getBiome` 调用路径:上游有一条 issue
  的名字就叫 [“C2ME should not overwrite TheEndBiomeSource's getBiome method”](https://github.com/RelativityMC/C2ME-fabric/issues/269)
  ,说明这是 C2ME 主动改写的地方,不是我们一厢情愿。

**它能覆盖什么、不能覆盖什么(这条别记错):**

| 开销                                                       | 装 C2ME 之后                 |
|----------------------------------------------------------|---------------------------|
| 未加载 / 生成中区块的噪声计算(昂贵那一半,单次约 1~3 µs 量级)                    | 有机会被接管、多线程化与缓存            |
| 已加载区块上的每次读取(8 角 Voronoi + `getChunk` 往返 + 调色板,约 0.40 µs) | **不受影响**,只能靠减少调用次数(本页"二") |
| 调用次数本身(实测 57 次/查询)                                       | 只有本模组能改                   |

所以定位说清楚:**C2ME 是给整合包使用者的可选缓解手段,不是本模组的依赖,也不能替我们省掉该做的优化**
。它属于世界生成级别的模组(改 chunk / noise 路径,影响整个存档的生成与加载),要不要装由使用者决定;本模组这边继续走"
压调用次数"这条线。

> 未核对的部分:没有实机验证过 C2ME 对"`getBiome` 噪声回退"的具体缓存实现(它究竟按什么粒度记忆化)
> 。上面只核实了两条外部事实——"支持 `26.1.2`"与"改写了 biome source 的 `getBiome`"。

## 实测

审计 `verifyAuraResolutionMemo`:

| 项目   | 结果                                                         |
|------|------------------------------------------------------------|
| 等价性  | 开启/关闭记忆的 `aura()`/`source()`/`sourceKind()`/`rules()` 完全一致 |
| 重复查询 | 155.6 µs → 5.8 µs,约 27 倍                                   |
| 群系记忆 | `static` 段 19.7 µs → 14.1 µs/查询                            |

审计 `verifyEntityQueryGate` 覆盖五种情形:新实体必须算、同刻重复必须跳、窗口内必须跳、窗口到达必须重算、移动一格必须立即算、实体离开维度后不再保留状态。

变异测试:把 `advance` 的纪元写成 `gameTime - 1`(缓存永不命中),审计立刻报

```
IllegalStateException: Aura memo did not make repeat resolution cheaper
```

把门的条件写反(同刻也算),审计立刻报

```
IllegalStateException: Aura entity gate resolved a stationary entity twice in the same tick
```

## 线上观测

`config.mxt.server.aura.query_stats` 打开后,每 200 tick 输出两行:

```
MiXianTu aura resolution: N queries, M skipped entity ticks, X ms total, Y us per query
[mxt] aura resolver over T level ticks: ... biome a hit / b miss, static c hit / d miss, ...
[mxt] aura stage cost per query: biome n calls / p us, static q us, pools r us, sources s us
```

判读方法:

- **`skipped` 远大于 `queries`** → 门在工作,绝大多数实体 tick 没有产生解析。
- **`us per query` 在 1 量级** → 命中的都是同刻重复;在 10~150 量级 → 每次查询都是新位置,该看阶段开销。
- **`biome n calls`** → 一次查询读多少次群系。修好后每个新位置 1 次 + 每个来源 1 次(来源位置的群系无法共用)。

## 未做的事

- **没给 `aura_zone` 建索引**。测试包只有 5 个域,注册表扫描约 6 µs/查询,不是瓶颈。只有在数据包里堆到上百个 `aura_zone`
  时才值得做"群系/维度 → 候选域"的 O(1) 查表。
- **没做"一个来源只取一次环境值"**。目前每个来源对每种灵气资源各取一次;资源多且单来源灵气种类少时有一次去重机会,收益不大。
- **没有跳过静止实体的 `blockPosition()` 调用**。门本身仍是一次 map 查找,约几十纳秒,相对 140 µs 可忽略。
