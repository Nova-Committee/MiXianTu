# 38 —— 定义文本字段的全量应用与翻译键的统一

> **状态**：已落地（2026-09-23）。
> **基准**：对着 `api/NamedDefinition.java`、`util/DefinitionText.java`、`util/codec/{ContextNameCodec,ContextNameListCodec,MiscCodecs}.java`、`data/` 下那 18 个定义类、`src/test-mod/java/com/iafenvoy/mxt/testmod/MxtTestCommands.java`、`docs/数据包格式.md` 写的。
> 本文接着 `37_名字与描述自动填充设计.md`：37 定的是**机制**（可选字段 + 从解码时的条目 id 生成键），38 定的是**给谁用、键长什么样**，并推翻了 37 §3 的"两套键"。

## 1. 需求与用户原话

1. 「接下来给所有需要展示名字或描述的注册表对象都应用 `ContextNameCodec`，这样用户可以选择使用默认键，冲突的时候也可以选择自定义。同时更新文档说明这一点，json 结构表也要写（附带默认键）」
2. 问到"默认键用哪一套"时，用户答：「**统一成 `ContextNameCodec` 的**」——即把 `DefinitionText` 的 id 派生键也改成带注册表命名空间的那一套，两套键合成一套（37 的"多一段注册表命名空间"不再是差异，而是唯一的拼法）。
3. 覆盖范围选了「只加现在真会显示名字的那批（18 类）」，绑定类与规则类不加。
4. `description` 选了「只加字段 + 文档」，界面接入另开一轮。

## 2. 定下的口径

- **键**：`<类别>.<注册表命名空间>.<定义命名空间>.<路径>`。注册表命名空间恒为 `mxt`（`MxtResourceKeys` 里每张表都是 `mxt:<path>`），所以 `mxt:fire` 在 `mxt:aura` 里是 `aura.mxt.mxt.fire`，`example:refined` 在 `mxt:item_quality` 里是 `quality.mxt.example.refined`。后缀接在后面：描述是 `.description`，计数型子境界是 `.minor_stage.<下标>`。
- **唯一出口**：`DefinitionText.key(String category, String registryNamespace, Identifier id)` 拼键，`DefinitionText.defaultText(String category, ResourceKey<?> entry, String suffix)` 拼**默认文本**（键 + 该字段自己的后缀：名字是空串、描述是 `.description`、计数字境界是 `.minor_stage.<下标>`）。`DefinitionText` 的 id 派生路径与 `ContextNameCodec` / `ContextNameListCodec` 全走这两个出口，codec 里不再出现键的拼法，只回答"字段写没写"。`DefinitionText.name(Identifier, String)` 这种只有 id 的重载假定注册表命名空间是 `MiXianTu.MOD_ID`（所有 mxt 注册表都成立），已在注释里写明。
- **18 张注册表**（其余 16 张不加）：`resource`、`aura`、`realm_stage`、`element`、`spirit_root`、`physique`、`ability`、`curse`、`technique`、`skill_stage`、`cultivate_action`、`artifact`、`formation`、`tribulation`、`secret_realm`、`contract_type`、`talisman`、`item_quality`。
- **契约**：`api/NamedDefinition`（`name()` / `description()`）。这 18 个记录都实现它，`DefinitionText.name(Holder…)` 认得出接口就直接读字段——**显示路径不需要知道哪个定义自带文本**，自定义名字因此自动在所有显示点生效（picker、信息面板、若干 tooltip、命令）。
- **迁移是破坏性的，按用户口径执行**：主包 3 条键、测试包 113×2 条键改成四段式；测试包里 3 条与既有新式键重复（值相同）去重，键数 135 → 132。**内容包的旧键不会自动兼容**，不迁移就显示裸键——这是"统一"的价钱，"保留两套、翻译不到回落"那条路被用户否掉了。

## 3. 为什么显示读字段，而不是继续读 id 派生键

字段省略时的默认值就是同一个键，所以"读字段"在默认情况下与"读键"完全等价；差别只在于写了文本时谁赢。把这件事放进 `DefinitionText` 而不是散到 60 个显示点，有三个理由：

- 同一个判断只能有一份实现（语言文件里有没有这条翻译、字段是不是字面量……），散开写必然分叉；
- 显示点大多只有 `Holder`，让它们各自判断"该读字段还是拼键"会把内部形状泄漏到界面层；
- 反过来，`DefinitionText.name(...)` 一旦成为唯一出口，将来再加文本字段也不用改调用方。

`DefinitionText.resolved(Component)` 是这条路上唯一的新判断：文本是字面量、或者是一条语言文件里真有的键，才算"这个名字说得出来"；技级面板据此决定显示名字还是回落到序号（技能水平没翻译时不显示裸键）。

## 4. `RecordCodecBuilder.group` 的 16 个组件上限

加两个字段之后有三个记录越界：`RealmStage` 18 个、`Ability` 17 个、`SecretRealm` 17 个（`Formation` 正好 16，没动）。DFU 的 `group` 只生成到 16 个参数的重载。做法是 `MiscCodecs.pair(MapCodec<A>, MapCodec<B>)`：把两个**相邻**字段并成一组（`RealmStage` 并了 `tribulation`+`breakthrough_particle` 与 `success_action`+`fail_action`，`Ability` 并了 `cast_time`+`cooldown`，`SecretRealm` 并了 `enter_condition`+`exit_condition`），**JSON 键与语义不变**，只是 Java 侧少一个组件位。这不是"顺手重构"的空间：换字段顺序或换并法都会改变 JSON 键，必须与 `docs/数据包格式.md` 的表同步。

## 5. 不做 / 推迟 / 待拍板

- **`description` 没有界面**：字段入数据、脚本与 `NamedDefinition` 可读，但这一轮没有任何 tooltip/面板画它（`item_quality.description` 是 37 就有的那一行，不算新接入）。
- **其余 16 张注册表不加字段**：绑定类（`item_binding` 等，名字来自被绑定的物品）、规则与内部类（`trigger`、`resource_bar_context`、`element_reaction`、`forging_method`、`forging_blueprint`、`spirit_herb`、`creature_profile`、`currency`、`aura_zone`、`block_aura`、`item_aura`）仍只有 id 派生键，但它们**也**跟着换了新拼法（`DefinitionText` 是共用的）。
- **不给旧键留回落**：见 §2 最后一条。若将来要平滑过渡，得另做一轮"两套键都查"的兼容层，那是新设计。
- **`DefinitionText.name(Holder)` 会调用 `holder.value()`**：这些显示点都在注册表加载之后（界面、命令、tooltip），未绑定的 holder 在这条路上本来也画不出东西；真遇到再说。
