# 76_符箓使用类型分派设计

**状态：部分落地（2026-10-07，用户给定形状；四个关键分叉已由用户拍板，见 §1.2）。已落地：§2.1 的公共字段、§2.2 的类型注册表与 `empty` / `self` / `area` / `crosshair` 四个类型、§2.5 的发动顺序、`max_use` 取代磨损。未落地：`mxt:thrown` 与投掷物实体、测试包夹具与探针腿迁移、`type` 收紧为必填，见 §7。**

符箓从"一列技能 + 磨损"改成"按 `type` 分派的一次使用"：公共字段收敛到 `name` / `description` / `type` / `condition` / `costs`，效果由四个内置使用类型各自的 `entity_action` / `bi_entity_action` 表达；`abilities` 字段删除，`durability` / `consume` 由各类型的 `max_use` 取代；`mxt:thrown` 是唯一没有 `max_use` 的类型，也是唯一生成投掷物实体的类型。

## 1. 目标与拍板结果

### 1.1 用户原话里的硬要求

1. 给符箓 JSON 引入 `type` 分派；**公共（默认）字段只有** `name` / `description` / `condition` / `costs` / `type`。
2. 四种使用类型：自己身上使用、范围使用、准星对准使用、丢掷使用。每个类型有自己独立的参数（例：投掷是唯一没有 `max_use` 的）。
3. 每个类型都需要 `entity_action` 与 `bi_entity_action` 等动作字段。
4. **使用时的目标各不相同**。
5. 准星使用：准星上没有实体就无法执行，并且这条**优先于** `condition`（不满足就不发动，与 `condition` 写什么无关）。

### 1.2 已拍板（用户四问四答）

| 分叉 | 结论 |
| --- | --- |
| 投掷怎么落地 | **生成投掷物实体**（新实体类型 + 渲染 + 命中结算） |
| `abilities` 字段 | **移除**，符箓只跑动作 |
| `max_use` 与旧字段 | `max_use` **取代** `durability` + `consume`；`capacity`（灵气存量）保留 |
| 范围使用的目标 | **复用 `target_selector` + `target_condition`**，与技能同一套选择器 |

## 2. 形状

### 2.1 公共字段（`data/Talisman.java`）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `name` / `description` | 文本（可选） | 不变（`ContextNameCodec`，生成键同旧） |
| `type` | `TalismanType` | **新增**，`type` 分派，见 §2.2 |
| `condition` | `EntityCondition`（可选） | 不变：对持有者的闸门，付款之前问 |
| `costs` | `Cost[]`（可选） | 不变：`mxt:aura` 条目仍从载体自己那口存量扣，其余走持有者账户 |
| `capacity` | double ≥ 1（可选，默认 1） | 不变 |

> **偏离说明**：用户列出的公共字段里没有 `capacity`，本稿把它留在公共层。理由是它是**载体**的性质（一次发动要多少灵气 × 能存几次发动），与"这一条符怎么用"无关，且灌注长按、展示架、灵气条、`capacity(stack)` 缓冲那几处都只读它。如果要严格照"公共只有五个字段"，把它下移到四个类型里即可——改动只有 `TalismanService.capacity()` 的取数处与四个类型的字段各增一行。

**删除的字段**：`abilities`（一列技能引用）、`durability`、`consume`。三者从 codec 里消失后，老文件里的同名键会**静默忽略**（`RecordCodecBuilder` 的既定口径），表现为"这条符什么都不做"，所以测试包与文档站必须同批迁移（§5）。

### 2.2 类型注册表

- 新代码注册表 **`mxt:talisman_type`**（`MxtRegistries.create("empty", …)` 的 `DefaultedRegistry`，形状照 `ABILITY_TYPE`）。
- `TalismanType.CODEC = MxtRegistries.TALISMAN_TYPE.byNameCodec().dispatchMap("type", TalismanType::codec, Function.identity())`（照 `AbilityType`）。
- 五个条目：`mxt:empty`（**默认、什么都不做**，照 `mxt:empty` 技能类型的口径——未知 type 落到它，不会静默变成"自己身上使用"）、`mxt:self`、`mxt:area`、`mxt:crosshair`、`mxt:thrown`。
- 每个类型自带自己的参数记录与 `MapCodec`，公共记录不认识它们（与 `Ability` 同构）。

### 2.3 四个类型的字段

| 类型 | 目标集 | 独有参数 | 动作字段 |
| --- | --- | --- | --- |
| `mxt:self`（自己身上使用） | 使用者自己 | `max_use` | `entity_action`、`bi_entity_action` |
| `mxt:area`（范围使用） | `target_selector` 选出的实体 | `max_use`、`target_selector`、`target_condition` | 同上 |
| `mxt:crosshair`（准星对准使用） | 沿视线 `length` / `radius` 的射线目标（**至少一个**） | `max_use`、`length`、`radius`、`limit`、`order`、`target_condition` | 同上 |
| `mxt:thrown`（丢掷使用） | 投掷物命中的那个实体 | `speed`、`gravity`、`target_condition`（**没有 `max_use`**） | 同上 |

- `max_use`：正整数。省略＝这一条符把载体**一次用尽**（等价于旧 `durability: 0` 口径：没有磨损条，发一次就消耗一件）。
- 类型各自的"目标怎么来"就是 §1.1 第 4 条说的"使用时的目标不同"：**动作字段的含义四处完全一致，只有目标集不同**。
- `mxt:crosshair` 内部**复用 `RayTargetSelector`**（不新写一套射线判定）：`length` / `radius` / `limit` / `order` 就是它的那几个参数，`include_actor` 不开放（准星永远不含自己）。
- `mxt:area` 的 `target_selector` 是必填的 `TargetSelector`（`mxt:area` / `mxt:cone` / `mxt:ray` / `mxt:self` / `mxt:js` 都能写），`limit` / `order` 已在选择器自己身上，不重复开字段。

### 2.4 动作语义（一处定死，别处不许再解释一遍）

沿用 `data/ability/ActionCarrier` 的既有口径，**不新写第二套动作执行**：

1. 发动时，`entity_action` 在**使用者自己**身上跑一次；
2. 然后对目标集里的每一个实体：`target_condition`（双实体条件，actor = 使用者，target = 该实体）通过则跑一次 `bi_entity_action`（actor = 使用者）。

于是"打在自己身上的符"＝ `entity_action`（作用者是持有者），"打在别人身上的符"＝ `bi_entity_action`，与技能完全同形，作者不必学第二套。`mxt:self` 的目标集是 `{使用者}`，所以它的 `bi_entity_action` 是 (使用者, 使用者)——写它没意义但不会报错（与"每个类型都有这两个字段"的要求一致）。

### 2.5 发动顺序（含准星那条硬要求）

```
① 载体能不能发动   ：空符 / 没灌满 / 冷却中 / 不是载体 → NOT_AN_ATTEMPT（不付款、不磨损）
② 取目标（仅准星） ：一个实体都没有 → REFUSED，先于 condition，不付款、不磨损
③ condition        ：各条铭刻自己的闸门 → 拒付
④ costs 付款       ：CostPayment（灵气条目从载体存量扣，其余走持有者账户）
⑤ 执行             ：self / area / crosshair 当场跑动作；thrown 生成投掷物（动作在命中时跑）
⑥ 结算             ：扣载体存量、记一次 max_use 磨损；载体被用尽时退回剩余灵气（旧口径保留）
```

第②步是用户明确要求的"超过 `condition` 的设置"：**目标存在与否先判，`condition` 只是在有目标之后再加一道闸**。文案新增 `actionbar.mxt.talisman.failure.no_target`（两份 lang 同批加）。

## 3. 投掷物（`mxt:thrown`）

- 新实体 **`mxt:talisman_projectile`**（`runtime/talisman/TalismanProjectileEntity extends ThrowableProjectile`，形状照 `runtime/spirit/SpiritBurstEntity`：`MobCategory.MISC`、`noLootTable`、默认无重力、`hurtServer` 拒绝）。
- 它携带：**定义 id**（`mxt:talisman` 的 id 字符串，既落盘也同步——只有 id 能跨端重建）、使用者（原版 owner）、发射参数（`speed` / `gravity` 来自定义）。
- 命中处理（服务端权威）：
  - 命中实体 → 跑该定义 type 的 per-target 半（`target_condition` 过滤 + `bi_entity_action`；`entity_action` 已在发动那一刻跑过）；
  - 命中方块 → 只消失（**不做 `block_action`**，见 §6）；
  - 载入时定义已不在注册表（reload 删了文件）→ 只消失，不报错；
  - 有存活上限（tick 上限），超时消失。
- 渲染：只注册一个渲染器（形态在落地时定：物品贴图 or 粒子尾迹，**不新增模型资源**）。
- 与载体：`mxt:thrown` 没有 `max_use`，发动即**消耗载体本身**（旧"没有磨损的载体发一次消耗一件"口径）；`capacity` 与存量退回照 §2.5 第⑥步。

## 5. 迁移与兼容

- 破坏性：`abilities` / `durability` / `consume` 三个键作废。老定义**能加载**（未知键静默忽略），但会变成"没效果的符"——这正是必须在同一批里迁移测试包与文档的原因。
- 本体自带数据包（`src/main/resources/data/mxt/`）里没有符箓定义，不受影响。
- 存档：载体上的 `mxt:talisman` 组件（一列符 + `mode`）与 `mxt:spirit_storage` 存量形状不变，老存档里的符继续能用，只是效果按新定义重算。耐久组件语义从"耐磨度"变成"次数"，数值会变（旧 `durability: 5, consume: 2` ⇒ 新 `max_use: 2`）——不写存档兼容。

## 6. 明确不做 / 留待后续

- **投掷命中方块的动作**（`block_condition` / `block_action`）：本稿不做 → **第四批已落地**（见 §7）。
- 投掷物的美术形态与手感（纯粒子 / 物品贴图 / 自转）：**自转已落地**（见 §7 第五批；仍是物品贴图，不加模型资源），粒子与命中音效未做。
- `capacity` 是否下移到各类型（§2.1 的偏离说明）。
- 旧的 `mxt_test:sigil_pulse` 一类技能定义：保留（别处还在用），符箓改成内联动作，不再引用它们。
- 符箓的"投掷"是否走原版投掷物手感（准星弧线、命中音效）：落地时对着 `ThrowableProjectile` 调。

## 7. 落地记录

**第五批（2026-10-07，只编译）**：投掷物的**自转**。新增 `render/talisman/TalismanProjectileRenderer` ＋ `TalismanProjectileRenderState`（继承原版 `ThrownItemRenderState`，只多 `spinSpeed` / `spinPhase` 两个字段），`MxtRenderers` 从借原版 `ThrownItemRenderer` 改为注册它。原版渲染器只把物品 billboard 到相机朝向、本身不转，所以自转加在 `poseStack.mulPose(camera.orientation)` **之后**、绕**相机自己的 X 轴**（`Quaternionf.rotateX`）：符纸像扔出去的纸牌一样前后翻。先写的是平面内的 `rotateZ`（符纸在屏幕平面里打转），实机看过觉得不对，改成 X 轴翻滚——代价是每圈有两次转到侧棱、几乎看不见。随机来自**实体 id 做种**（与掉落物 `bobOffs` 同一套做法），每 tick 0.20～0.55 弧度、正反随机，另加一个随机起始角；角度由 `state.ageInTicks`（`tickCount + partialTick`）累积，所以同一次投掷全程同一个转速、各客户端算出来一样、相邻帧连续。与原版 `ThrownItemRenderer` 的差异只有：不再 `scale`（原注册走的就是 1 参数构造器，倍率恒为 1），光照与阴影沿用 `EntityRenderer` 默认（原版 `fullBright=false` 时同一条路径）。`compileJava` 通过；**未实机**：自转没在游戏里看过。

**第四批（2026-10-07，只编译）**：投掷的**方块那一半**落地。`TalismanType` 新增 `landOnBlock(use, pos, direction)`（默认空实现，只有投掷覆写），`ThrownTalismanType` 新增两个字段：`block_condition`（`BlockCondition.optionalCodec`，缺省恒真）与 `block_action`（`BlockAction.optionalCodec`，缺省 `no_op`）——用户点名只要 `block_condition`，但方块条件本身不产生效果，命中方块的效果只能由方块动作表达（爆炸是 `BlockAction`，落雷是方块版 `spawn_entity`），所以两半一起给，条件失败＝动作不跑。`TalismanProjectileEntity.onHitBlock` 先跑 `landOnBlock` 再 `discard`（命中实体那条路不变），`land` / `landOnBlock` 共用一个新的私有 `use()`（只有定义还在、且 owner 仍在时才建 `TalismanUse`）。测试包新增两条：`thrown_blast_sigil`（`block_condition` ＝爆炸抗性 `< 1000000`，`block_action` ＝ `mxt:explode` 威力 3；实体那一半用 `mxt:target_action` + `use_target_position` 包 `mxt:explode`）与 `thrown_bolt_sigil`（命中方块落 `minecraft:lightning_bolt`，命中实体用 `mxt:spawn_lightning`）。顺带补上 10 条此前没有名字键的测试符箓（测试包两份 lang 各 +12 键，现 376）与四个类型类里混进的中文 Javadoc 前缀。文档站 `datapack/json/talisman.md` 中英各补：类型字段表那一行、方块那一半的说明、一个丢掷示例。`compileJava` / `compileTestModJava` / `processTestModResources` 通过，`check:i18n` / `check:links` / `check:parity` 通过；**未实机**：投掷物、方块那一半、爆炸与落雷都还没在游戏里看过。
