>   供气，改为全部供给阵法，阵法用其抵扣 `maintenance_costs`，缺口才由阵主支付；不设存量、按资源类型

>      减掉"本区块方块聚合量"，若只在查询时过滤，被吞的灵气会从聚合里漏回环境，同一份灵气能被花两次。
>      因此 `BlockAuraContribution` 增加 `absorbed` 标记，`AuraChunkAttachment` 聚合时排除它们、
>      另存一份 `absorbed_aura` 总量。
>   2. 阵法**激活/拆除时让对方块重算**（`FormationWorldService.invalidateAura` → `AuraChunkTicker.markDirty`），
>      否则被吞方块会继续供环境而阵法白拿。
>   3. 抵扣规则抽成 `FormationService.MaintainRule.remaining`，与支付分离 —— 规则因此可独立断言，
>      不必为了观察一个余额而在世界里立起一座阵法。
>   4. 审计断言覆盖：半径包含判定（含界外拒绝）、被吞方块离开共享聚合且进入阵法总量、抵扣比例、
>      全额外覆盖时不向阵主收钱、以及**异种资源不抵扣**。端到端一条验证"放入发射器 → 重建 →
>      出现在阵法应得总量里"。
>   5. 追加配置 `formation_plate.draws_environment`（**默认关闭**）：打开后，阵法**所在位置**解析出的
>      **自然环境灵气**也参与抵扣。为此 `AuraPool` 增加第四个分量 `supplied`（该点灵气里有多少来自场地
>      方块），`AuraService` 在解析时填入 —— 否则"允许花地皮"的阵法会把自己的发射量花第二遍。
>      组合规则抽成 `FormationWorldTicker.combine`，与读取分离以便断言"关闭时地皮灵气绝不参与"。

#### A. `tick_ability` 字段 → **不采纳**

三条理由，任一条都足够：

1. **区域分发已经存在。** `entity_tick_action` 就是那个钩子（§2.2.1），再加 `tick_ability` 等于给同一件事准备两个字段，
   日后必然出现"两个都写了、以谁为准"的问题。
2. **`tick_ability` 需要一个 actor 实体，而阵法没有。** `mxt:area` 以 actor 为中心选择，`mxt:aura` 也是挂在某个实体的
   `ABILITY_HOLDER` 上逐 tick 分发（`AbilityEventBridge.tickAuras` 遍历 `abilities.sources()`）。于是只剩两条路：
    - **用阵主当 actor** → 阵主离线阵法就失灵（何况现在有维护消耗的阵法**在阵主离线时会被当场拆除**，见 §7 第 4 项）；阵主站偏了，
      作用圆心也跟着偏，半径语义与 `max_bonus` / `aura_zone` 不再一致。
    - **造一个"阵心虚拟实体"** → 新概念，要处理存档、碰撞、被击杀、被其他模组扫描；而它服务的只是 17 号一个阵法。
3. **ability 的一半字段对阵法没有意义** —— `costs` / `cast_time` / `cooldown` / `components` / `words` 都是"施法者"概念。

> **备选方案**（把 `target_selector` / `target_condition` / `bi_entity_action` 下沉到 `formation`）同样不采纳：
> 它把 actor 问题原样搬进 `formation`，却让字段表变长、语义两处维护。

#### B. 所有者 → **采纳，但语义必须收紧**

现状 `FormationMemberEntityCondition`（`MxtEntityConditions.java:37`，`formation_member`）的真实行为是：

```js
// FormationMemberEntityCondition.java:22-23
entity.level().getData(MxtAttachments.FORMATION_WORLD).formations().values().stream().anyMatch(formation ->formation.active() &&formation.owner().filter(entity.getUUID()::equals).isPresent());
```

即"**拥有本维度任意一个 active 阵法**"，而且它是 `MapCodec.unit(INSTANCE)`（**无参数**），根本无法表达"这个阵法"。
原文说的"语义自相矛盾"属实，且比原文描述的更严重。

新增 `mxt:formation_owner` 的语义与边界：

| 情形                           | 结果                      |
|------------------------------|-------------------------|
| 在阵法上下文中，实体 UUID == 携带者 owner | `true`                  |
| 在阵法上下文中，携带者 owner 为空（无主阵法）   | `false`                 |
| **不在阵法上下文中**（普通技能、物品绑定条件里）   | **`false`**（不是"拥有任意阵法"） |

**现有 `mxt:formation_member` 的处理**（二选一，**不要**按原文的拆法改成"在范围内且通过成员判定"——那是第三种语义）：

1. **保留行为、改名** `mxt:owns_formation` —— 更贴切，且与新增的 `formation_owner` 形成"任意 vs 这个"的清晰对立；
   代价是破坏现有数据包引用。
2. **保留 id、改文档** —— 只在文档里写清"任意 active 阵法"，并标注与 `mxt:formation_owner` 的区别。

> `mxt:formation_is_owner`（原文建议 3）**不采纳**。它想要的是"非阵法所有者无法控制阵法"这条**交互期**规则，
> 属于阵盘物品 / 命令的检查点，不是实体条件。顺带指出一个现存缺口：`FormationPlateItem.useOn` **只校验阵盘组件、
> 不校验所有权** —— 任何人拿到绑定某阵法的阵盘都能激活它。这是玩法决策，需要拍板。

#### C. `formation_x/y/z` → **采纳，但走显式上下文值，不进注册表**

`MxtFormulaVariables` 目前只注册了 5 个变量（`zero` / `random` / `caster` / `target` / `realm`）。
文档里写的 `formation_radius` / `distance` **根本不在注册表里** —— 它们是 `FormationWorldTicker` 通过 `Map.of(...)` 传的
**显式上下文值**。这不是遗漏，是设计规则，`FormulaVariables` 自己的类注释写得很明白：

> Values that belong to no object — damage, a block position, an event payload — are not variables;
> callers keep those in the context's explicit value map.

阵心坐标正属于"belongs to no object"，而且 `FormulaContext.value()` **先查显式值再查注册表**，`NumberProvider.CODEC`
又接受字符串形式的表达式 —— 所以 `"formation_x"` 走显式值这条路**一分钱都不用花**。

| 路线         | 成本                                                                       |
|------------|--------------------------------------------------------------------------|
| **显式上下文值** | **3 个 key**（改 `FormationWorldTicker` 里那个 `Map.of`）                       |
| 注册表变量      | 加一个 `FormulaVariable` 实现 + 注册 + 全局名字索引 + 两份文档；且会让**阵外**求值从"显式值缺失"退化成诊断噪声 |

**原文的 JSON 一字不改就成立**：

```json
{
  "type": "mxt:teleport",
  "x": "formation_x",
  "y": "formation_y",
  "z": "formation_z"
}
```

#### D. `entity_enter_action` / `entity_exit_action` → **采纳，但只加两个字段是不够的**

`ABILITY_HOLDER` 走 `entity(...)`，即 `.serialize(CODEC).copyOnDeath()` —— **授予的能力是持久的**，
玩家退出游戏、死亡、换维度都还在。于是：

- 玩家在增益阵里**退出游戏** → 没有任何 tick 会给他发 `exit` → **能力永久滞留**；
- 玩家在增益阵里**换维度** → 同上；
- 阵法被拆（结构破坏 / 灵力付不出）时，`deactivate_action` 是 **`BlockAction`，上下文是 `Level`**，**看不到实体**，
  无法逐实体撤销。

所以正确答案是**进出钩子 + 来源对账**（原语已经存在）：

```java
// AbilityAttachment.java:96
public boolean reconcileSource(Identifier source, Collection<Holder<Ability>> desiredAbilities)
```

语义正是"**这个 source 下只保留 desired，其余全部撤销**"，`AbilityEventBridge` 已经用它处理 curios 装备的来源。

设计：

1. 阵法用**带作用域的 source id**（如 `mxt:formation/<id>` 或 `mxt:formation/<controller 编码>`），`grant_ability` 的
   `source` 填它；
2. 每个阵法 tick，对范围内每个实体先 `reconcileSource(阵法 source, 当前应授集合)`，再执行 `entity_tick_action`；
3. `entity_exit_action` 显式执行 + 兜底 `reconcileSource(source, Set.of())`；
4. **拆除 / 付不出灵力**时，先对**上一 tick 记录在册**的实体逐个跑一遍第 3 步，再执行 `deactivate_action`。

**记账集合放内存，不进 `FormationInstance.Snapshot`** —— 它是瞬时状态，跨存档没有意义；重启后"里面所有人都是新进入"其实是
**正确**行为（授予幂等）。

必须写进文档的三条边界：

| 边界         | 行为                                                                              |
|------------|---------------------------------------------------------------------------------|
| 20 tick 粒度 | `FormationWorldTicker` 挂在 `gameTime % 20`，所以"穿过"（<20 tick 进出）与"同 tick 内进出"都观察不到 |
| 区块卸载       | `level.getEntities(...)` 只看已加载实体 → 卸载再加载会产生一次**假 exit + 假 enter**               |
| 重启         | 记账表清空 → 阵内实体全体视为 enter                                                          |

> ⚠️ **备选方案（"授予加计时器自动过期"）今天走不通** —— `timer` / `toggle` / `resource` / `target_lock` 四个能力组件
> **没有任何消费者**（`docs/模块实现审计.md:174`）。

#### E. `mxt:damage` 加 `damage_type` → **采纳方向，但原文低估了缺口**

现状全库只有两处发伤害（`DamageAction` / `DamageTargetBiEntityAction`），都是 `damageSources().generic()`：

```java
// DamageAction.java:22
if(Double.isFinite(amount) &&amount >0.0D)entity.

hurt(entity.damageSources().

generic(), (float)amount);
```

**连攻击者都没有** —— 也就是：击杀不归因到任何人、怪物仇恨不生效、依赖攻击者的条件上游一律失灵。
对 1 落雷阵 / 15 一意水剑阵 / 16 赤魂炼狱阵 / 7 禁绝阵 来说，**"谁打的"和"什么类型"同等重要**。
而 actor 恰好就是 §4.1 引入的携带者所提供的**阵主**。

落点按 `DamageAction` 自己的类注释办（"source-specific damage belongs in a dedicated code-owned action type"），
**加动作类型而不是加字段**：

| 动作                       | 说明                                                                |
|--------------------------|-------------------------------------------------------------------|

##### A. `tick_ability` 字段（**原方案**）


##### B. 所有者成为一等公民（**原方案**）

模组包用 `CustomName` 传 UUID、`所有者` TE 标签、命令参数排除主人 —— 三套土办法。基座需要明确：

| 需要明确的事        | 现状                             |

| 阵法是谁放的        | 文档未说明 `formation` 有 `owner` 概念 |

| 一个玩家能同时开几个阵法  | 未说明                            |

**建议**：

1. **隐式所有者** —— `formation` 激活时记录放置者，并作为 `entity_tick_action` 的上下文对象
2. **`mxt:formation_owner` entity condition** —— 该实体是当前评估阵法的所有者
3. **`mxt:formation_is_owner`** —— 当前玩家是否是这个阵法的所有者（对应模组包的"非阵法所有者无法控制阵法！"）
4. **补三条文档** —— 所有者离线行为、阵法数量上限、阵法持久化范围

##### C. `formation_x/y/z` 公式变量（**性价比最高**）（**原方案**）

1、15、16 三个阵法做同一件事：**把范围内敌人拉到阵心**再打。而 `mxt:teleport` 只能移到固定坐标：

```json

  "type": "mxt:teleport",
  "x": "formation_x",
  "y": "formation_y",
  "z": "formation_z"
}
```

`formula_variables.md:151-152` 目前只给了 `formation_radius` 和 `distance`，**没有阵心坐标**。
**只加 3 个变量，不加任何字段，就解锁 3 个阵法的核心机制。**

##### D. `entity_enter_action` / `entity_exit_action`（**原方案**）

8 个增益阵的做法是打 **22 tick 标记自然过期**。改用 `grant_ability` 后，需要回答"离开半径后能力何时移除"：

- `deactivate_action` 只处理**阵法拆除**，**处理不了"玩家走出去"**
- **建议**：加 `entity_enter_action` / `entity_exit_action`，与 `entity_tick_action` 对称

##### E. `mxt:damage` 加 `damage_type`（**原方案**）

| 阵法       | 现模组通道                 | 公式              |
|----------|-----------------------|-----------------|
| 1 落雷阵    | `BeThunderAttack`     | `140 + 1.6 × 值` |

```json
  "type": "mxt:damage",
```

### 3.1 决策：区域保护移出基座

> **项目方拍板原文**：「区域保护这种东西，直接丢给 FTB 领地就完事了」

完整决策记录见 `E:\Java\.process\audit\架构决策记录.md` **ADR-001**。本文只写**联动事宜**。

### 3.2 ⚠️ 版本对应（最容易搞错的一点）

**项目是 MC 1.12.2，而 FTB Chunks 是 1.16+ 的模组。**

| MC 版本           | 对应的领地模组                             |
|-----------------|-------------------------------------|
| **1.12.2（本项目）** | **FTB Utilities**（Forge 版，含区块认领与保护） |
| 1.16+           | FTB Chunks（区块功能拆分后的独立模组）            |

**本项目落地为 FTB Utilities**，不要写成 FTB Chunks。

### 3.3 为什么不自己做（四条理由）

1. **这不是"阵法"问题，是"领地"问题** —— 守家阵的能力集（claim 区域 + 白名单 + 拦截破坏/交互）与修仙玩法**无语义耦合**
   ，在修仙框架里内置领地系统属**职责错位**
2. **基座实现成本极高、收益极低** —— `MxtEvents` **18 个事件族没有任何方块破坏/交互事件**，要先补整套事件面 + 权限判定 +
   白名单持久化，而**这只服务 1 个阵法**
3. **外部模组更成熟** —— 可视化圈地、区块加载、队伍白名单、管理命令，远超硬编码半径 50
4. **避免事件拦截冲突** —— 两套保护系统的优先级与豁免规则会长期打架

> **补充技术证据**：模组包的阵法**依赖每 tick 生成临时实体**，一旦被区域保护模组取消 `EntityJoinWorld` 就**完全失效**。
> 这说明**保护功能不该由这套脆弱机制承担**，反过来也印证了移出基座的判断。

### 3.4 联动设计

**原则：只做一层薄桥接，双向都不侵入。**

- **#2**：**字段已删除**（`FormationInstance` 的 `active` 字段、`active()`、`deactivate()` 均移除，

> 位置回到普通数值字段，彻底没有"map 键必须是字符串"这条约束。比给 `Codec.LONG` 套一层字符串 xmap 更干净：
> 存档里能直接看出哪个数是哪个，而且**多出一条 map 表达不出的校验** —— 同一个 controller 出现两次会直接报错，
> 旧形状下根本不可能出现、也就不会被发现。
> 修完补了一条断言，**走 NeoForge 真正写存档时用的那套调用**（`TagValueOutput.store` + 断言 problem reporter 为空），
> 而不是只做一次 codec 往返 —— 因为这个 bug 的特征正是"只在真实存档路径上、且只在索引非空时"才出现。

      容错等于白做。运行期构造没有损失：唯一的调用方在造实例之前已经校验过 radius。
