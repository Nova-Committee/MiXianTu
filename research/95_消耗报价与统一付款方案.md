# 95 消耗报价与统一付款方案

> 状态：绑定事务、账单编辑、BANK exact、符箓单定义和阵法来源实扣已有实现。当前三步付款规则见 §14；统一来源分配、物品共享槽位计划、首笔画付款与跨 tick 作废仍未落地。仅编译验证，GameTest 未实跑；具体缺口以审查记录为准。
> 目标：一次付款只有一份真实账单；所有模块复用报价、改价、来源分配、模拟与实扣流程。具体扣除仍由 Cost 实现负责。
> 后续评估：§15 讨论 CostContext 来源接口与 AuraAccess / ItemAuraAccess 的 double 升级，均为提案，尚未修改实现。

## 1. 建议采用的形状

Cost 只负责根据上下文**构造绑定好的付款事务**。事务只接收 `simulate`，自行处理模拟与实扣，不再额外接收金额、付款者或上下文。上层只有一个 `CostPayment` 管理本次账单：

```text
Cost[] + CostContext
    → prepare：公式求值一次，返回已绑定的付款事务，组成账单
    → edit：事件改价、分配比例等修改账单
    → pay：重复目标诊断 → 按 List 顺序模拟全部条目 → 按相同顺序逐条实扣
    → 模拟通过且实扣阶段结束后，业务执行效果、发产物、提交状态
```

拆开的是定义解释与付款执行，模拟和实扣仍使用同一个付款事务的扣除算法。事务执行契约可嵌套在 `Cost.Transaction`，实现留在各 Cost 类型内部，不另造按模块划分的付款类。单纯把旧方法改名为 `test` / `commit` 不能解决价格、来源和调用顺序的问题，也没有必要恢复草稿管理器、按类型注册的工厂或整组快照回滚。

沿用已经确认的边界：

- 整组不回滚。实扣失败始终输出普通 WARN，继续后续扣款与业务效果；失败结果中已有的真实凭据仍须保留。
- 内置通道的单条扣除必须全额成功或不写入。检查不足时先扣一部分再拒绝，不属于允许的组级部分付款。
- 包作者尽量为同一份存量只写一条 Cost。重复目标使用 LoggerDispatcher 输出开发 WARN、运行 DEBUG；原条目不合并、不重排。
- 一张符箓只承载一个 `Holder<Talisman>`。
- 审查状态必须由代码事实支撑；尚未落地的设计不能据此标记为已修复。

## 2. 重构前的形状为何会反复出问题

重构前同时存在原 `costs` 列表、可修改的资源表与灵气表、原金额表、每个 Cost 的份额表，以及 `verifying` 标志。它们共同决定最终扣多少，但不是同一个事实来源。

因此删报价仍可能回退到原公式，新增报价没有执行条目，物品没有冻结价格，报价模式还可能延续到脚本实扣。飞行又先自行扣燃料、画符自行拍余额快照，进一步把付款边界拆散。

解决原则是：**可修改的账单本身就是待执行费用；汇总 Map 只是它的只读投影。** 来源抵扣要生成真实的扣除条目，不能通过修改一张展示表来暗示“别处已经付过”。

## 3. 共用模型与接口职责

### 3.1 Cost：构造付款事务；Transaction：执行绑定好的付款

当前核心接口轮廓如下，省略元数据与 Codec 成员：

```java
interface Cost {
    ResultWithData<Transaction> prepare(CostContext context);

    interface Transaction {
        ResultWithData<List<Debit>> execute(boolean simulate);
    }
}
```

继续使用现有 `Result` / `ResultWithData` / `Failure`，不为每个通道再造一套同结构结果类。`Transaction` 是执行契约，`Debit` 是真实扣除凭据；现有 Codec 分派不变。上述只列主要操作，事务还向公共账单暴露只读的目标、数量、单位等元数据。

`prepare` 只求价、绑定目标与校验参数，不判断当前库存是否足够，不调用脚本 check，不加载区块、不创建附件。每个金额 provider 在本次账单中只求值一次；物品数量也在这里冻结。它返回的是对象，不是要求调用者之后再补齐参数的工厂或回调。

`transaction.execute` 只使用对象已经绑定的固定金额、目标和权限上下文，不能再读原 `NumberProvider`，不能查询另一张表决定“本次价格”，也没有“报价不存在就回退原价”的分支。它负责通道检查，以及 `simulate=false` 时的真正扣除。`CostPayment` 在外层包装事务调用，事务不反向调用 `CostPayment`。

“不再依赖其他参数”是指执行不额外传参，不是脱离真实世界：绑定的账户、容器和世界池仍按执行时的真实库存判断。事务不能把创建时的库存当成承诺，也不能把模拟当成预留。事务不得被序列化为定义、缓存为跨实体共用单例或放进数据包注册表。

`simulate=true` 不产生实际扣除凭据。`simulate=false` 返回已知真实 `Debit`，失败也不能遗漏已发生的部分转移；底层原因由账单记录 WARN，不转为整笔付款失败。

事务的单次执行状态、结果缓存、主线程与重入检查由一个公共事务基类或执行骨架承担，各 Cost 内部的事务实现只写自身通道逻辑。不能让四种 Cost 分别复制一份状态机，也不能重新引入按类型创建草稿的注册工厂。

### 3.2 Transaction：本次费用的唯一事实来源

一个事务至少保存：

| 内容 | 含义 |
| --- | --- |
| 本次条目 id | 每次加入账单都独立生成，不能用 Cost 对象引用充当条目身份 |
| 执行逻辑 | 在对应 Cost 内部创建的事务实现，包含已解析的不可变参数 |
| 求值及权限上下文 | 付款者、公式上下文、来源标识，不能在实扣时换成另一名付款者 |
| 目标与通道 | 对哪个账户、哪份库存、哪个灵气身份或哪个脚本付款 |
| 固定数量与单位 | 实数资源、整数物品、整数银行灵气等，不再保存可重新求值的价格 |
| 来源贡献 | 保留各条目的上下文，方便定位重复与失败原因 |

事务的金额、目标及参数不可变，只有自身执行状态会变化。账单编辑阶段通过受控操作创建替代事务，例如公共数值事务的 `withAmount`；不能在事务内保留“执行时去可变 Map 找最终数量”的逻辑。替代事务继承原有绑定、只换固定数量，不重新运行原公式。0 表示从账单移除，不执行一个金额未知的空事务。

付款开始后生成不可变执行计划，原准备事务只由该账单持有，不再作为另一笔付款重复执行。通道、改价与来源分配共用事务元数据及模板，不要求飞行、修炼等业务各自实现 `withAmount`。不能把内部可变 List、Map、JSON 参数直接暴露给事件和脚本。JSON 参数按本次报价冻结，脚本收到副本，避免模拟修改参数后影响实扣。

源定义和本次账单是两种用途，不是两张可分别改价的账。求价结果转成固定账单后，不再从定义推导本次金额。

### 3.3 CostPayment：唯一编排入口

复用当前这个类，负责：

1. 将全部 Cost 报价，或将不同上下文已经报好的费用追加到同一笔账单。
2. 提供只读的资源、灵气、物品与其他成本视图。
3. 接受并校验账单编辑。
4. 付款时确定来源、统一模拟、统一实扣、累计实际凭据、缓存最终结果。

它不包含飞行、修炼、画符、阵法的类型判断，也不直接调用容器扣物品、资源 `set` 或脚本 consume。

`CostContext` 只表达“谁付、用什么求价、有哪些付款通道及其来源策略”。删除 `ledger`、`verifying` 等付款阶段状态；不再让 Cost 通过上下文反向写报价表。实体、容器和世界位置的有效性在付款时重新检查，不能因报价时存在就长期认为可用。

### 3.4 收敛和移除的现有结构

| 现有结构 | 处理方式 |
| --- | --- |
| `CostLedger`、`pricedResources`、`pricedAuras`、`shares` | 由绑定好的 Transaction 替代，不再维护平行金额表及比例反推 |
| `account()` / `auras()` 可写活表 | 改为只读投影；修改统一走账单操作 |
| `price` / `test` 混合求值、查库存 | 报价只求值；检查只读固定账单 |
| 公开 `commit()` 可以接在只报价后面 | 统一 `pay()` 自带完整模拟，不能跳过第一遍 |
| `payAll` 逐笔提交已准备付款 | 先把所有报价汇入一笔账单，统一模拟后执行，保留各条上下文 |
| 静态单条与 KubeJS 单条快捷路径 | 包装成单元素账单，走同一 `pay`；不再各有一套检查规则 |
| 定义层 `hasSameTarget` 互相猜测类型 | 使用事务绑定后的物理目标身份及通道能力，避免 VALUE、POOL、BANK 被当成同一目标 |

HUD / tooltip 每次展示可创建新报价；一次实际使用内部只允许求值一次。不能把“鼠标悬停时显示过价格”当作本次付款已报价。

## 4. 改价必须改到账单本身

保留资源事件使用 id-keyed 金额表的形式，但其读写通过统一适配器映射到本次账单：

- `resourceAmounts()` 返回副本。
- `replaceResourceAmounts(map)` 是**替换当前付款账户的资源费用**，不是增量追加。没有出现在新表中的资源费用被删除，传空表就是免除该部分费用；物品、池灵气、银行灵气、脚本条目不受影响。
- 新增已注册资源 id 时，统一创建该账户上的固定资源 Transaction，并纳入最终模拟与执行。不能只加入成功结果。
- 对同一资源费用的 VALUE 灵气与普通 resource 条目，先归一到同一个资源通道。改价后直接生成最终金额，不再按原条目份额分摊后反算。
- 非有限值、负数、未知资源、无法唯一确定付款账户等情况明确拒绝整次改价，保留原账单；不允许部分应用或静默忽略。编辑 API 中 0 表示删除，定义原始 amount 为 0 仍按原无效数量规则拒绝。
- 多账户账单的 id 表必须按账户作用域读取和替换，不能把不同账户的同名资源先加起来再改价。

例如原账单是 A 资源 5，事件改成 B 资源 3，则执行计划里只有 B 资源 3；A 不扣，B 必须实际扣 3。事件改成空表时，该部分执行计划为空，绝不会重新计算 A 的原公式。

修炼的比例调整也通过账单操作，例如 `scale(selection, ratio)`：比例有限且非负，替换选中事务的固定数量，0 删除条目；离散数量调整后按通道规则规范化。不能再使用 `auras().replaceAll(...)` 偷改旁路金额。

事件完成后账单封闭，事件的旧 Map 即使再次被修改也不影响本次执行。数据包重载、切换世界或目标失效时，跨 tick 的未付款账单作废，不在旧 Holder 与旧通道上继续扣款。

## 5. 多来源付款只做一套

### 5.1 来源策略代替“先在业务里扣，再修改余额表”

统一支持**有优先级的数值来源列表**。每个来源提供稳定的物理目标身份、可支付额度、单位粒度和精确扣除能力；同一个适配器按存储种类复用，不按玩法重新实现。

| 存储适配 | 接入的已有实现 | 付款时要求 |
| --- | --- | --- |
| 实体或明确资源账户 | `ResourceTransactions` | 全额检查后写入，保留使用权限检查 |
| 世界灵气池 | 当前池服务与 section 存储 | 只访问有效目标，准确扣对应区块和 section 的库存 |
| 方块银行 | 工作台等内部银行 | 提供精确全额扣除，见第 7 节 |
| 物品储存灵气、阵法储备 | 各自组件或存储访问器 | 使用当前存量、明确单位及真实变化通知 |
| 物品容器 | 现有 `Container` 与 matcher | 完整槽位计划后写入，不作为可随意拆分的数值来源 |

绑定是“来源对象 + 允许支付的目标 + 优先级 + 可选限额”。限额只限制这次可领多少，不代表已经交付。新增一种存储需要实现存储适配；新增一种玩法只组装绑定列表。

资源与灵气身份的转换必须显式绑定。某门灵气只能为它映射的资源付款，不能把同一资源的不同灵气无条件互换；多个候选灵气的选择顺序固定。整数来源只分配可精确表达的份额，不能因逐来源向上取整而总扣量超出最终报价。

### 5.2 统一来源分配

付款时对冻结的数值需求按优先级分配来源，生成确定的物理扣除条目。规划过程只读，不先烧燃料、不先减少池库存，也不先增加任何储备。

同一物理账户可能出现在多条来源路径中，因此规划时共用一份本次可用额度计算，不能把同一余额重复分配。额度表仅用于本次来源分配，不是旧余额快照，也不承担回滚。

例：费用 5，法器有 3、玩家有 10。统一计划是法器 3、玩家 2。两条都模拟通过后才实扣；若玩家只有 1，来源合计不足，模拟阶段失败，法器仍有 3。若法器有 5，只有法器扣除条目，没有“删除玩家价格后再回退原价”的问题。

来源分配后有两条守恒式：每个逻辑费用的已分配量等于固定费用；同一物理目标被分配的合计不超过其本次可用额度。不能满足就拒付。来源与展示视图都由同一计划导出，不能分别手算。

### 5.3 重复目标与条目顺序

- 普通 resource 与 VALUE aura 仍归一为同一资源目标，但仅用于诊断与守卫，不能据此合并金额或事务。
- 每条公式在自身上下文求值一次，模拟与实扣均使用这条固定事务。
- 执行前先检查重复目标。同次检查每个重复目标诊断一次，通过 LoggerDispatcher 使用开发 WARN、运行 DEBUG；不再按进程永久去重。
- 两遍都严格保持 List 追加顺序，不合并、不把脚本移到最后。同一个 Cost 对象出现两次也构造两个独立事务。
- 物理目标身份仍包含账户、灵气与 section 等。脚本按付款者 + id 诊断重复，各调用保持独立；物品只识别同容器且相同 matcher 的重复，不求解任意 matcher 交叠。
- 各模拟读取当前库存，不预留或累计虚拟扣量。余额 5、费用 4 和 3 时，两条模拟可通过，实扣依次为成功和失败；最终账单成功、余额 1，凭据只报告已扣 4。

包作者应把同一目标的费用写成一条，避免物品匹配需求交叠。统一来源分配仍是独立的后续设计，不得借其名义恢复 List 自动合并。

## 6. 付款状态和两遍执行

建议对外只保留报价、编辑、检查与付款四类操作。`pay()` 的内部顺序固定：

```text
若已结束，返回缓存的最终结果
若正在执行，返回重入拒绝
冻结账单，保持 List 顺序，检查重复目标并分派诊断日志
逐条 transaction.execute(simulate=true)
    任意失败 → 返回失败，实际凭据为空
逐条 transaction.execute(simulate=false)
    累计本条真实凭据
    本条返回失败或抛 RuntimeException → 普通 LOGGER.warn，继续下一条
返回成功和全部已知真实凭据，缓存终态；不回滚、不重试、不取消业务
```

报价和编辑属于可准备阶段；检查不授予永久有效的“已检查”资格。即使调用方提前做过检查，`pay()` 仍检查最终金额与当前存储；重新检查不重新求价。只报价后直接调用 `pay` 也必须执行脚本 check 和 consume。

付款开始后不能再编辑、追加或重新使用旧计划。一次 `pay` 不因失败而自动重试，不因为多次调用而重复扣除；再次发起付款必须显式创建新账单。事务自身的第一次 `execute(false)` 也缓存终态，重复调用不能再次扣款；`execute(true)` 不缓存库存判断、不写入。尚未实扣的临时模拟失败可以在库存改变后重新检查，但不得留下半份追加条目。

统一在服务端主线程执行。共同执行骨架使用有明确作用域的重入守卫，键至少包含付款者与正在操作的物理存储，`try/finally` 释放；同一付款对象另有执行状态守卫。组与其内部事务共享同次执行标识，不能重复获取守卫后把正常子事务误判为回调重入。允许不相交目标的独立付款，拒绝嵌套触碰当前目标，不能只用进程级一个 boolean。物品使用稳定的载体或会话身份，不能把可能被替换的 ItemStack 引用当唯一锁键。

执行顺序就是原始 List 顺序，脚本与内置通道均不重排。脚本检查必须只读；实扣时再次 check 或 consume 失败也只 WARN 并继续，不得假装已经自动退款。

`PaymentResult` 使用现有结果基类，携带不可变的实际 `Debit` 列表。报价投影与付款结果不能混称“已付金额”：

| 终态 | 凭据 | 后续业务 |
| --- | --- | --- |
| 模拟拒付 | 空 | 不执行效果，不交付产物 |
| 全部实扣成功 | 每个实际扣除的目标、数量及必要物品数据 | 提交效果与业务状态 |
| 实扣途中失败 | 保留之前、本条及后续返回的真实凭据；原因写普通 WARN | 继续后续费用和业务效果，不回滚、不自动重试；付款结果为成功 |

实扣的 RuntimeException 在统一账单边界捕获并输出固定 WARN，继续后续事务，保留已知凭据并缓存成功终态。抛异常条目尚未返回的扣量不可推断，既不虚报零也不伪造付清。JVM Error 不在此恢复约定内。`PaymentResult.isSuccess()` 表示模拟通过且实际尝试阶段结束，不保证每条都全额收齐。

## 7. 每种 Cost 如何落实同一个协议

### ResourceCost 与 VALUE AuraCost

报价各自沿用当前公式上下文规则：ResourceCost 使用该资源的公式上下文，AuraCost 保留调用方的灵气求值上下文，不顺手改公式含义。VALUE AuraCost 报价后归一到资源执行通道。

实扣使用账单固定金额，仍由 `ResourceTransactions` 提供全额检查与写入。模拟读取附件的只读视图或未初始化时的明确缺省状态，不为了检查创建附件或初始化库存。资源条件检查与实际余额更新共用同一存储规则。

### POOL AuraCost

固定灵气身份、世界、区块及 section，模拟不强制加载或初始化池。位置不可用或池未就绪时明确失败，由正常世界生命周期初始化，不在付款模拟中偷偷生成库存。

分配到的环境份额是带来源与上限的绑定，实际付款仍要扣池。报价表、共享分配额度和已支付凭据是三个不同概念，不能把一个无来源的数值 credit 当作真实交付。

### BANK AuraCost

现有 `AuraAccess.extract` 是允许部分转移的物流接口，仅靠 `extract(true)` 再 `extract(false)` 不能保证全额扣除。**不能继续把它直接当作原子付款接口，也不能忽略真实返回值。**

内部银行提供可选的精确付款能力，供共同来源适配使用：`takeExact(amount, simulate)` 成功即完整提供，失败即不修改。工作台对当前整数库存一次检查后更新即可实现，不需要整组回滚。物流 insert/extract 保留现有语义。

外部银行没有精确能力时，在付款规划阶段拒绝该来源；不能给一个默认实现，暗中退回“模拟后部分提取再尝试塞回”。外部实现若宣称支持却违反契约，按通道故障处理，不报付款成功；任意第三方代码违约无法由上层布尔参数自动修复。

银行的向上取整在固定报价时做一次；超出整数可表达范围明确拒绝，不能静默夹到 `Integer.MAX_VALUE` 后少扣。结果记录真正的整数扣量。

### ItemCost

数量在报价时按现有 ceil 规则规范化并冻结，拒绝非有限值、无效数量及整数溢出。是否允许读取额外公式变量沿用现行契约，不借付款重构更换变量含义。

每条 ItemCost 使用同一个容器计划算法检查自身需求，条目之间不合并、不共享预留。实际写入之前再次核对所有计划槽位的物品、组件、数量与可用性；核对完成才集中写入，不能边找边扣。内置容器写入阶段不执行脚本等任意回调；成功后统一通知 `setChanged`。单独调用一个 ItemCost 也通过这个计划器，不另写直接 remove 快捷路径。

物品凭据保存实际扣走的完整 ItemStack 副本，包含组件；报价只表达需求，不假定最终取自哪一个槽位。

### JsCost

构造事务只冻结 id 与参数、验证存在对应通道；模拟调用 check，实扣前也验证当前 check 再调用 consume，保证单个事务独立执行时不能绕过条件。重复检查不会重新求价格。没有 `ledger.verifying` 之类的跨阶段短路。缺少脚本、拒绝与异常都产生明确失败结果。

脚本成功返回只说明脚本宣称其成本已处理，不能自动推断内部扣了多少资源。凭据记录该脚本调用完成，不编造数值金额；已执行的脚本不可自动退款。同步重入当前付款目标由共同守卫拒绝。

## 8. 业务迁移：只留下业务规则和来源配置

| 调用方 | 允许保留的业务逻辑 | 必须改为共用流程的部分 |
| --- | --- | --- |
| 技能、引导、突破 | 条件、目标、施法时间、Pre/Post 事件、冷却及状态 | 保存同一报价，Pre 通过编辑适配器改账，`pay` 成功才执行效果和状态提交 |
| 飞行维护 | 条件、频率、失付后结束飞行 | 配置“法器存量 → 骑乘者账户”的数值来源，删除 `burn` / `refund` 和修改 account 的付款逻辑 |
| 修炼 | 共同分配的份额、修炼速度及收益公式 | 一份账单绑定地面与身体通道，通过受控 scale 调整池费用，统一 `pay`；不再两份付款加手写资源副本预检 |
| 阵法维护 | 优先来源、储备上限、维护成功状态 | 将有来源的供给、储备、账户绑定为同一来源列表；维护费用走共同付款，删除第二套手算 fromOwner 的消费实现 |
| 符箓发动 | 单个定义的条件、目标、耐久和载体规则 | 单一账单同时包含持有者费用与载体储存灵气；先付款，再 apply，再提交载体状态 |
| 灵气合成、灵植、品质、契约、锻造、法器普通维护 | 各自的触发、产物和状态 | 同一 `prepare → pay → 业务提交`；不直扣 Cost 对应账户 |
| KubeJS 单条与数组 | JSON 解码与脚本注册桥接 | 单条也变成单元素账单，不能直接绕过付款入口实扣 |

不同模块还会调用同样的 `pay` 成功判断，这是合理的业务边界，不是另造一套消费系统。存储适配中不同的实际读写代码也是必要差异；不允许重复的是求价、改价、来源抵扣、模拟调度和付款结果算法。

### 8.1 符箓发动与单定义

组件、Codec、生成、tooltip、探针一起改成单定义，明确空白载体的表示；不只在发动方法中拿列表第一项。

载体的灵气支出是本次付款的一个来源通道，与玩家的资源、物品费用一起报价及模拟。模拟通过并完成实扣尝试后才运行类型的 apply；不得先 apply 再创建另一笔 `CostPayment.pay`。载体数量与耐久所需条件也在效果前确认，随后按已确认规则提交一次。

这能同时删除多定义的合并循环和“提前烧载体灵气再补救”的诱因，不需要给符箓实现专用付款类。

### 8.2 画符：把付款推迟到首个有效笔画之前

建议作一处明确的时机调整，删除跨 tick 退款问题，而不是再建通用回滚框架：

1. 选择符方时生成并保存账单，做可支付预检，不取走材料；未画任何有效笔画就取消，直接结束，不需退款。
2. 首个笔画通过会话、限额、符笔与颜料等合法性检查后，先支付同一账单；支付成功才扣该笔颜料、记录笔画。
3. 实际消耗的符纸与品质从付款物品凭据读取并保存在会话，不能沿用选择符方时尚未扣除的纸张快照。
4. 已开始画之后，材料已经支付，之后失败或取消仍按现有失败规则处理，不退款；后续笔画不能重复支付启动成本。

这样保留“未画就取消不花材料，已经画就承担材料”的主要规则，只将占用材料的时刻从选中符方移到首个有效笔画。选择后、首笔前库存可能变化，首笔付款失败时明确拒绝开始；若实扣阶段个别条目失败，只 WARN 并继续会话，保留已知真实付款凭据，不自动重试。

删除 `snapshotResources`、余额覆盖恢复、前后库存差值猜付款等路径。颜料仍是每笔的工具消耗，不为了统一接口强行塞进配方启动 Cost。选择空白符纸与配方额外物品费用共同交给容器计划器；额外费用仍不能改掉默认必须消费的那张符纸。

### 8.3 阵法供给与共享分配的边界

共享分配应提供实际来源与额度，例如哪一个世界、区块、section、灵气及本周期上限；不能只交出一张已经视作到账的灵气 Map。共同付款对这些来源实际扣减，再形成 Debit。

阵法将未用供给存入储备属于一次实际转移：也必须先从来源扣除，才向储备入账，并受储备容量约束；不能把“分给过但没取走”的数额直接存入。这里复用精确存储访问与来源规划，不把收益、再生和储备入账伪装成负数 Cost。

审查 B05 的共享 Map、B11 的周期顺序、B12 的分配算法仍需在分配服务自身修复；Cost 重构不自动等于它们全部解决。本方案要求接入时提供可追溯来源，避免继续扩大 B06 的无实扣信用问题。

## 9. 为什么没有恢复整组回滚

统一付款、冻结价格与存储精确扣除能消除本次确定的逻辑错误，但不能把任意第三方存储和脚本变成跨通道原子事务。来源在模拟后仍可能变化；脚本也可能违约修改别的存储。

因此本方案的保证是：内置单条全额或不写，整组先模拟，实扣失败固定 WARN、继续后续条目和业务效果，不重复扣款，并准确返回已知实际支出。仍不保证“任何付款失败都完全没花费”，这与此前接受的不回滚契约一致。

若之后要求整组严格全有或全无，就必须重新引入所有参与方遵守的预留/事务协议，或者限制可组合的通道；只改方法数量、执行顺序或增加一次模拟都无法得到这个保证。

### 10.2 必须覆盖的行为

| 场景 | 精确断言 |
| --- | --- |
| 物品 provider 依次给 1、3，库存 2 | 一次报价求值 1 次，付款只扣 1，库存剩 1 |
| 单条物品要 2，库存 1 | 拒付，库存仍 1，组件不变，无实际凭据 |
| 原价 A=5 改成空表 | A 扣 0，报价与结果都不报告 A 已支付 |
| 原价 A=5 改成 B=3 | A 不变，B 恰好减 3，凭据与余额一致 |

| 实扣时脚本拒绝或抛 RuntimeException | 固定 WARN、继续后续条目与业务效果；返回成功及已知真实凭据，不自动重试 |
| 同一账单调用 pay 两次 | 第二次返回相同终态，存量不再次变化 |
| 回调重入当前付款目标 | 明确拒绝；外层守卫在退出后释放 |
| 没有精确支付能力的外部银行 | 扣除前拒绝，不触发部分物流提取 |
| 银行整数溢出或错误实际返回值 | 越界在模拟前拒绝；实扣返回不足时固定 WARN 并继续，只报告真实扣量 |
| 符箓缺费、或效果本身会改变付款资源 | 缺费效果数为 0；付费成功只求价和扣费一次 |
| 画符选中后空白取消 | 资源与物品始终未扣，不存在旧余额覆盖退款 |
| 画符首笔及后续笔画 | 首笔付一次启动成本，后续不再付；使用实际消耗符纸的品质 |
| 阵法消耗零再生环境池 | 凭据中的池扣量与对应 section 库存减少量相同 |
| 报价跨数据重载、世界切换、目标失效 | 未付账单拒绝执行，不沿用失效目标 |

几处随之确定的语义：

- **同一目标相加后只扣一次**：账单冻结时按 `CostTarget` 分组，同一目标的金额在存储自己的单位里相加，用一个事务扣一次。旧的"份额表 + 比例反推"因此不存在了，`resource=1` 与 `VALUE aura=3` 命中同一账户仍然是扣 4。
- **重复目标改为按目标认**：`Cost.hasSameTarget` 删掉，改由账单比较绑定后的 `CostTarget`（这正是 §3.4 最后一行要的口径：`VALUE`、`POOL`、`BANK` 因此不会被误认为同一个目标）。警告每个出处、每个目标各打一次。
- **`prepare` 不查通道**：上下文没给出账户 / 位置 / 容器 / 玩家时，把存储绑成"缺席"，到 `execute` 才以 `NO_CHANNEL` 拒付。这是 §3.1 与 §7 的要求（报价不需要位置），也是 `Costs.auras` 这种"只读一个灵气数组价格、没有 level 与 pos"的调用点还能工作的原因。
- **执行顺序由账单定**：内置存储先跑，脚本最后；同类之间保持书写顺序。`mxt:js` 的 `consume` 之前会再跑一次 `check`，没有 `verifying` 之类的跨阶段短路。
- **物品条目全或无**：先只读规划槽位（按槽位顺序），整份计划成立再复核、再集中写入，`Debit` 里是真正扣走的堆副本。这一条修掉了 B23 里的"边找边扣"。
- **银行不再少扣报成功**：实扣那一次 `extract` 若仍返回剩余量，按通道故障拒付，而不是当成功（B25 的一半；精确接口 `takeExact` 与外部银行的规划期拒绝仍未做）。
- **`amount()` 的单位**：实数数值 / 整数物品 / 整数银行灵气 / 一次脚本调用（脚本没有可求和的数值，凭据记 1 次调用）。

## 14. 当前付款规则：诊断、模拟、实扣

本节替代 §13 中的合并执行、脚本后置及实扣失败终止语义。现有 `Cost.prepare`、绑定事务、账单编辑与真实凭据形状保留，所有调用方复用同一 `CostPayment`。

1. 最终条目列表冻结后，检查重复目标，通过 `LoggerDispatcher.of(LOGGER)` 输出开发 WARN、运行 DEBUG；每次检查同目标只提示一次，运行环境沿用分派器限额。重复不拒绝、不合并、不重排。只报价不输出重复诊断，`test` 与 `pay` 各自执行前检查。
2. 按 List 追加顺序调用所有事务的 `execute(true)`。任意失败则不进入实扣，返回失败，不执行业务效果；模拟不预留余额，不累计虚拟扣量。
3. 全部模拟通过后，以相同顺序逐条调用 `execute(false)`。返回失败或抛 RuntimeException 均使用普通 `LOGGER.warn`，不分派、不限流；继续后续事务，最终返回成功，业务继续。不抛出、不回滚、不取消、不自动重试。脚本实际 check/consume 的运行时异常同样交到统一实扣边界处理，不先打 ERROR。

结果只记录已知真实 Debit，包含失败条目返回的部分支出。抛异常条目的未知扣量不能编造；此前与后续返回的凭据仍保留。最终结果缓存，第二次 pay 返回同一对象，不再执行任何事务。JVM Error 不属于可恢复的实扣失败。

已增加 `verify/cost_duplicate_order`、`verify/cost_entry_order`、`verify/cost_real_failure`、`verify/cost_real_exception` 四条探针，覆盖不合并与原序、脚本位置、部分失败继续与凭据、真实脚本异常后的继续与终态。`verify/cost_bank_exact` 已改为验证银行异常少扣只 WARN、账单成功并保留真实扣量。编译通过；这些探针未实跑。

方案中统一来源分配、共享槽位规划、首笔付款和生命周期约束仍需单独实施，不因这次流程调整标记完成。审查 B29 按当前代码关闭；B32 保留物理身份修复，不再要求合并预检。后续修复已让修炼按每种灵气的总需求分摊 grant，并区分无预分配与零份额，B13/B36 原缺陷已关闭；这属于来源适配修复，CostPayment 仍不合并条目。公共事务骨架也已按付款者与脚本 id 保护直接入口，付款后模拟返回空 Debit，B28/B34 已关闭。以上仅完成静态、隔离与编译验证，游戏探针未实跑，详见审查第 7.7 节。

## 15. 来源接口与灵气存取实数化评估

§15.1～§15.5 保留实施前的评估，落地事实见 §15.6；§14 的付款顺序与失败规则继续有效。

### 15.1 当前复杂度来自哪里

`CostContext` 有 9 个 record 分量，其中 `level`、`pos`、`bank` 与 `AuraTarget` 共同表达一种灵气来源。`AuraCost.prepare` 再按 VALUE / POOL / BANK 分支，来源增多就要同时改上下文与费用定义。构造器还允许 POOL 没有位置、BANK 没有银行等组合；其中一些用于只报价，另一些只有付款时才发现缺通道。

三个枚举的职责应区分：

| 结构 | 代码现状 | 建议 |
| --- | --- | --- |
| `AuraTarget` | 决定具体扣哪一种存储 | 用来源接口替代，来源自己绑定事务 |
| `CostChannel` / `hasChannel` | 当前主代码与探针没有调用方；SCRIPT 与物品共用判断，有容器但无玩家也会回答支持 SCRIPT | 实施时移除这份平行能力表，实际能否支付由对应事务回答 |
| `CostOrigin` | 当前用于重复目标与实扣失败日志 | 保留为诊断信息，来源能力不从它推导 |

### 15.2 推荐的最小抽象

保留 `CostContext` 为小型 record，把灵气来源抽成一个接口。拟议契约：

```java
public interface AuraCostSource {
    ResultWithData<Cost.Transaction> bind(CostContext context, Holder<Aura> aura, double amount);
}
```

拟议的上下文只需 6 个分量：`payer`、`formula`、`origin`、`account`、`auraSource`、`itemTarget`。资源仍复用 `ResourceHolderAttachment`，物品仍复用 `Container`，脚本仍要求 `player()`；这三条已有能力无需再包装一层通用字典。`account` 与 `itemTarget` 保留显式覆盖和付款者兜底的现有含义。

`AuraCost.prepare` 求值一次后直接调用 `auraSource.bind(...)`，来源只绑定目标和固定数量，不查库存、不扣款、不重新求公式。工厂方法 `of` / `account` / `pool` / `bank` 可以保留，内部选择适配器，业务调用无需认识存储分支。

适配器按存储种类共用：

| 来源 | 绑定方式 | 最终目标 |
| --- | --- | --- |
| 资源账户 | 复用 `ResourceChannel.transaction`，将 aura 映射到其 resource | 原账户 + resource |
| 环境池 | 适配器持有 Level 和不可变 BlockPos，复用池的检查与扣除 | 维度 + 区块 + section Y + aura |
| 灵气存储 | 适配 `AuraAccess`，扣除用 `extract(..., exact=true, simulate)` | 原始存储身份 + aura |

默认账户来源可用无状态实现，在 `bind` 时读取当前 context，避免 `withPayer` 后来源仍捕获旧付款者；银行的 actor 与 registries 也在绑定时固定。已构造事务继续只接收 `simulate`。

接口放 `api/`，工厂与实现留在消耗模块；不引入按修炼、阵法、工作台分别实现的来源体系。扣除仍由 Cost 绑定出的事务负责，统一顺序仍只有 `CostPayment`。

还需保留三项边界：

1. **物理目标身份**：两个适配器包装同一银行时仍是同一目标；环境池同一 section 的不同位置仍命中同一库存。账户 aura 必须继续生成 `CostTarget.Account`，和普通 resource 费用共享重复诊断及重入守卫，不能统一伪装成 `AuraStore`。
2. **只报价**：`Costs.auras` 没有真实位置也能读价格。用明确的只报价来源构造同一套事务，执行时返回 `NO_CHANNEL`；不伪造世界、不在报价时读取库存。阵法强制走账户的调用则显式换成账户来源。
3. **缺通道**：真实付款缺少账户、容器或玩家仍通过结果拒绝，不靠来源枚举预判，也不把普通失败变成异常。

### 15.3 AuraAccess 升级为 double 的可行性

**可行，并且与现有底层存量一致，建议连同 `ItemAuraAccess` 一起升级。** 当前直接实现 AuraAccess 的主代码类有 2 个，物品实现有 3 个（2 个 UseItemAuraAccess、1 个 ItemAuraAccess）；测试里的模拟银行与全部调用点也要更新。

现有基础已经支持小数：

- `SpiritStorageComponent.amounts` 是 `Object2DoubleMap<Holder<Aura>>`，Codec 已使用 double，组件同步也沿用这份 Codec。
- 世界 `AuraPool` 与资源账户使用 double。
- 符箓发动按原始小数扣存量，法器 `consumeEnergy` 也支持小数。

目前的整数接口反而有实际精度损失：

- `SpiritStoneItem.normalizeStored` 对已有存量先 `floor`，真实调用会写回。1.75 的存量抽取 1，最后会变成 0，丢掉额外的 0.75；请求 exact 抽取 2 时也可能先把存量写成 1，再拒绝抽取。
- `TalismanItem.insert` / `extract` 同样先对 double 存量取整，再写回新值；发动后留下的小数可能在补充或抽取时丢失。
- BANK 的 `AuraCost.units` 会把 0.25 的费用变成 1；`SpiritVesselItem.room` 则忽略不足 1 的剩余空间。

升级后建议维持现有返回含义：`insert` / `extract` 返回未移动量，参数和返回值均为 double，容量表改成 `Object2DoubleMap`；`exact=true` 仍要求全额或不写，`simulate=true` 完全只读。按住灌注仍可每 tick 请求 1.0，这个速率不必跟着改；最后只差 0.25 时允许接收 0.25，并按实际转移量计费。

### 15.4 必须联动与可以单独处理的范围

| 范围 | 所需调整 |
| --- | --- |
| `AuraAccess` / `ItemAuraAccess` | 参数、返回、容量表与输入校验共同升级；展示架继续桥接物品存储 |
| 灵石、符箓、灵力容器 | 去除存取时的 floor 与 int 中间量；模拟和 exact 拒绝均不写入、不顺便规范化旧存量 |
| `SpiritPour.Entry` / `SpiritChargeService.Charge` | stored / capacity / intake 的承载改为 double；取整只留在百分比和 hold tick 等显示、时间计算中 |
| `ItemAuraService` | 容量与读取存量去掉整数瓶颈；耗尽清空不能再假定 `Integer.MAX_VALUE` 能抽完，使用已知可取数量 |
| 灵气工作台与 `AuraCost` | 需求、缓存、实际库存、容量、事务与凭据一致支持小数；移除银行费用的 ceil，0.25 就扣 0.25 |
| 工作台界面与 Jade | 当前进度走整数 DataSlot 并截到 Short.MAX_VALUE，Jade 也用 putInt / getInt；需同步迁移到保留 double 的菜单数据与 NBT 传输，不能只改服务端库存 |
| 符箓容量、画符成品充能与管理员填充 | 数值链路支持 double；容量公式是否保留现有向上取整作为显式兼容策略，需要在实施前确定 |
| 法器 | 已有实数存量与扣除可复用；`ArtifactService.capacity` 仍 floor 并返回 int，若要统一所有灵气容量则一起迁移，养护加成等业务保留 |
| 灵力射线 | 当前发射量有明确的整数换算，整数请求可直接传入 double 接口；仅为存取接口升级无需改实体同步。若也允许小数发射，再修改 amount 的存档与实体数据同步 |

原版当前提供 INT / FLOAT 实体同步器，没有现成 DOUBLE 同步器。射线小数化若实施，应通过已有 NeoForge `ENTITY_DATA_SERIALIZERS` 注册机制接 double，使用 `ByteBufCodecs.DOUBLE`；不转 float，不新增 Mixin。

灵气存取可以复用升级后的 `AuraAccess`，环境池可由绑定位置的适配器接入。资源账户仍经 `ResourceChannel`：其资源身份、使用权限、失败资源和真实凭据属于付款语义。`AuraAccess` 本身不增加 CostTarget、付款来源枚举或账单状态，`getCapacity` 也不承担推断库存及可抽取权限的职责。

### 15.5 数值边界、兼容性与验收

- 所有输入、存量和容量只接受有限非负数；NaN、正负无穷和负数不能被转成免费成功。0 是无操作，物品个数与使用次数继续为整数。
- `exact` 和剩余量计算集中复用同一份数值规则。容差只处理浮点运算误差，不免除真实不足：不能因 `amount < 1e-9` 就视为已付，也不能让正数请求在库存完全没变化时报已扣。超出可表达精度的请求应拒绝，凭据保留已知实际扣量。
- 实扣前复核仍存在；exact 不足不得写入，外部存储违约仍按 §14 输出 WARN 并继续。升级 double 不改变两遍执行、不合并条目的契约。
- Java API 的返回类型、参数与泛型变更会破坏附属模组二进制兼容，必须重新编译；数据包仍是 JSON number，整数写法可继续读取。
- `mxt:spirit_storage` 的存档与组件同步本来就是 double，通常无需字段迁移，但仍需实际往返验证；工作台灵气缓冲当前不保存，无旧库存字段可迁移。工作台菜单与 Jade 的网络读写必须同时更新。
- 数值宽度从 4 字节变 8 字节，现有 fastutil 已提供对应容器，无需新增依赖。此改动主要解决精度和来源耦合，不能据此宣称 tick 性能提升。

实施时的行为探针至少覆盖：0.25 原价支付与凭据；1.75 抽取 1 后保留 0.75；exact 不足和 simulate 的零写入；补满 0.25 只收对应费用；0.1 连续转移与重复充放不增量；NaN/无穷/负数/极小量；同一 section、同一银行的包装身份；账户 aura 与 resource 的重复识别；缺通道的只报价；double 存档、组件、菜单与 Jade 往返。继续回归现有 Cost 顺序、异常与重入探针。

实施可分两步：先换来源接口并维持原有数值行为，再统一存取接口与数值链路；两步可以在同一轮完成，每步明确验收。此评估未改 Java、字段、数据包与玩家文档，也未新增或实跑游戏探针；不将上述问题标为已修复。

### 15.6 来源接口与 double 链路的落地

用户确认统一迁移全部灵气数值链路，不保留符箓容量、法器容量与射线发射量的整数换算；物品数量、耐久、颜料、tick、百分比与槽位仍为整数。

- `CostContext` 已缩为 6 个分量，`AuraTarget`、`CostChannel` 与 `hasChannel` 已移除；`AuraCostSource` 在 `api/`，来源工厂在 `runtime/cost/`。`AuraCost` 只求值一次并委托来源绑定事务。
- 账户来源继续复用 `ResourceChannel`，环境池通过 `WorldAuraAccess` 与银行共用存取事务。银行目标保留原对象身份，环境目标保留维度/区块/section 身份；只报价来源无需库存，执行返回 `NO_CHANNEL`。环境适配器只读已加载区块的现有附件，不加载区块、不因模拟创建附件。
