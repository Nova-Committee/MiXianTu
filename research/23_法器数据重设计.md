## 0. 结论摘要

1. **现状（详见 §1）**：7 个字段里只有 `refine_action` 有真正的消费者；`granted_abilities` 零消费者、`storage_slots`
   无调用者、飞行没有玩家入口、`mxt:refining` 配方零调用者；**没有任何写侧把 archetype 挂到物品上**，所以整个模块在实机里等于不存在。
2. **重做的实质是补两件事，不是加字段**：
    - **身份绑定**：定义自己声明"我是哪些物品的法器"（`items`，`ItemMatcher`），与 `spirit_herb` / `weapon_binding` /
      `item_binding` 完全同构。这一步直接消灭"没有写侧"这个根因。
    - **能力列表化**：把 `granted_abilities` / `flight_speed` / `flight_costs` / `storage_slots` 四组字段收进一个**固有分派
      **的 `abilities` 列表，行为由代码拥有、数据包只选类型（沿用 `mxt:ability_type` / `mxt:formula_variable` 的既有做法）。
3. **灵力存储改成按灵气计量**：`spirit_capacity` 变成 `灵气 → 上限` 的 map，存量**复用 `mxt:spirit_storage` 组件**
   （灵石与符箓载体已经在用同一个形状，`SpiritStorageComponent` 的类注释就写了"One shape serves every whole-unit store"）。
   `mxt:artifact_state` 因此只留 `owner_uuid` / `archetype` / `nourishment`。
4. **新增固有注册表 `mxt:artifact_ability_type`**，内置 `mxt:empty`（默认项）、`mxt:passive`、`mxt:active`、`mxt:flight`、
   `mxt:storage`。注册表名沿用 `MxtResourceKeys` 现有命名风格，默认项沿用 `MxtRegistries.create("empty", …)`。
5. **必填字段只有两个：`item_type` 与 `items`。** 其余全部可省（`optionalFieldOf`）。旧字段名**不报错也不生效**——
   `RecordCodecBuilder` 只读它被告知的键（本条初稿曾写"用 `refuseKeys` 点名拒绝"，2026-09-21 当天按用户要求推翻，见 §10.6）。
6. **跨定义校验放进 `ServerCache.rebuild()`**：那里已经有"收集全部问题、一次报完"的框架，`/mxt registries validate`
   直接产出。要加的检查见 §2.4 / §3.1。
7. **一个顺带修掉的坑**：今天的 `ArtifactService` / `ArtifactStorageService` 用 `MxtDatapackRegistries.get(key, id)`
   读定义，而那个入口在**多人客户端上会抛 `IllegalStateException`**（`registry(key)` 依赖
   `ServerLifecycleHooks.getCurrentServer()`，`MxtDatapackRegistries.java:209-215`）。新解析必须一律走 `Provider` /
   `RegistryAccess` 重载（`ItemBindingService` 就是服务端 / 客户端各一份），否则工具提示与 Curios 槽位判定在客户端根本读不到定义。

## 2. 新 JSON 结构

文件位置不变：`data/<namespace>/mxt/item_archetype/<path>.json`。

### 2.1 完整示例

```json
{

  "items": [
    "#mxt:artifact/sword",
    "mxt_test:bound_sword"
  ],
  "spirit_capacity": {
    "mxt:qi": 500,
    "mxt_test:sword_intent": 50
  },
  "abilities": [
    {
      "type": "mxt:passive",
      "ability": [
        "mxt:sword_body",
        "#mxt:artifact/sword_passives"
      ]
    },
    {
      "type": "mxt:active",
      "ability": "mxt:sword_rain"
    },
    {
      "type": "mxt:flight",
      "speed": 0.08,
      "costs": [
        {
          "id": "mxt:qi",
          "amount": 1
        }
      ]
    },
    {
      "type": "mxt:storage",
      "slots": 9
    }
  ],
  "curios_equipable": true,

    "type": "mxt:sequence",
```

最小可用定义（只有两个必填字段，就是一个"什么都不给"的器型）:

```json
{
  "item_type": "talisman_carrier",

```

### 2.2 顶层字段

| 字段                 | 类型                                  | 必填    | 默认          | 消费者 / 说明                                                                                                                                     |
|--------------------|-------------------------------------|-------|-------------|----------------------------------------------------------------------------------------------------------------------------------------------|
| `item_type`        | String（非空）                          | **是** | —           | 器型标识。三个真消费者：① Curios 槽位策略（`curios_equipable` 之外的将来分组）② `mxt:refining` 配方按器型匹配（§2.7）③ `/mxt registries` 诊断与将来工具提示分组。空字符串加载期报错。                |
| `items`            | `ItemMatcher`                       | **是** | —           | 身份绑定：`ItemMatcher.find(MxtDatapackRegistries.holders(access, ITEM_ARCHETYPE).map(Reference::value), stack)`，与四种 binding、`spirit_herb` 同一套解析。 |
| `spirit_capacity`  | `Map<Holder<aura>, NumberProvider>` | 否     | `{}`        | 每种灵气的存储上限，见 §2.3。空 map = 这件法器不是容器。                                                                                                           |
| `abilities`        | `ArtifactAbility[]`                 | 否     | `[]`        | 固有分派能力列表，见 §2.4。                                                                                                                             |
| `curios_equipable` | bool                                | 否     | `false`     | 是否允许放进 Curios 槽位（预留），见 §2.5。                                                                                                                 |
| `refine_action`    | `ItemAction`                        | 否     | `mxt:no_op` | 认主／精炼时对持有者与物品执行的行为（字段与语义都不变）。                                                                                                                |

**刻意不设为必填的**：`spirit_capacity`、`abilities`、`curios_equipable`、`refine_action`——全部 `optionalFieldOf`
，理由是全仓一致的"老文件要能继续解析"。

**刻意不新增的字段**（避免与既有权威打架）：

- **不新增 `display_name`**：定义名一律由 id 走 `DefinitionText`（`item_archetype.<命名空间>.<路径>`），这是
  `docs/数据包格式.md:57` 的既定规则，`Talisman` 的类注释也把这条写死了。
- **不新增 `icon`**：法器是"已有物品的规则"，图标属于物品本身。
- **不新增 `quality_group`**：品质组已经由四种 binding 提供（`ItemBindingService.ResolvedBindings.qualityGroup`
  ），法器不参与品质抽取。
- **不新增 `priority`**：同一物品被多份定义匹配时按 `ItemMatcher.findAll` 的现有规则（`priority()` 默认 0，注册表顺序）取第一份；这种情况按
  §2.4 的校验报 problem，不引入新字段。

### 2.3 `spirit_capacity`：灵气 → 上限

| 项       | 约定                                                                                                                                           |
|---------|----------------------------------------------------------------------------------------------------------------------------------------------|
| JSON 形状 | 对象，键是 `aura` 的 id（**只接受具体灵气，不接受标签**——灵气按条目计量，标签会随数据包变动把存量读成另一种东西，这与 `Talisman.aura_cost` 的注释同一个理由）                                           |
| 值       | `NumberProvider`，可写常数或公式；每次读取时求值                                                                                                             |
| 求值后的处理  | 非有限 → 记一条警告并按 0；`≤ 0` 按 0；否则 `Math.floor` 取整（存量是整数单位）                                                                                        |
| 温养加成    | `有效上限[a] = floor(声明上限[a] × (1 + 0.5 × nourishment))`，`nourishment` 夹在 `0..1`，两端都夹。**加成由管线乘，公式里不要自己写**（同 `element_modifier` 的教训：数据包重复相乘会静默翻倍） |
| 缺省语义    | map 为空或某灵气不在 map 里 = **这种灵气灌不进去**（容量 0），与今天"`spirit_capacity` 缺省 0"一致                                                                        |

存量的形状**复用 `mxt:spirit_storage`**（`SpiritStorageComponent` = `Map<Holder<Aura>, int>`）：

- 灵石、符箓载体、法器从此是同一个"整单位灵气存储"形状的三个用户，一个组件、一套工具提示（`SpiritStorageTooltipAppender`）、一个
  `mxt:spirit_storage_not_full` 条件。
- **但长按灌注手势并不因此自动到手**（落地时修正了本节原来的说法）：那条手势只属于实现了 `UseItemAuraAccess` 的**物品类**
  （目前只有 `TalismanItem`、`SpiritStoneItem`），而法器是"已有物品"，本体不会给它改类。所以法器的灵力写入路径仍然主要是
  `mxt:charge_artifact`；内容方若自建物品类实现该接口，也能获得长按灌注。
- `ArtifactSpiritEnergy` 从"单值 double 视图"改成"**某一种灵气的视图**"（构造时带 `Holder<Aura>`），容量不再传
  `Double.MAX_VALUE`。

### 2.4 `abilities`：固有分派列表

新增固有注册表 `mxt:artifact_ability_type`，与 `mxt:ability_type` 同构：

```java
public interface ArtifactAbility {
    MapCodec<ArtifactAbility> CODEC =
            MxtRegistries.ARTIFACT_ABILITY_TYPE.byNameCodec().dispatchMap("type", ArtifactAbility::codec, Function.identity());

    MapCodec<? extends ArtifactAbility> codec();
}
```

| `type`        | 记录                              | 字段                                                             | 行为                                                                                         |
|---------------|---------------------------------|----------------------------------------------------------------|--------------------------------------------------------------------------------------------|
| `mxt:empty`   | `EmptyArtifactAbility`（枚举单例）    | 无                                                              | 什么都不做的占位类型，显式写 `"type": "mxt:empty"`；它同时是这张注册表的默认项（`type` 本身仍是必填字段）。                       |
| `mxt:passive` | `GrantArtifactAbility`（意图 = 被动） | `ability`：`Holder<ability>`、`#标签` 或二者的混合数组                     | 授予能力。属性修正 / 条件在**授予期间**生效（`ModifierAbilityType` 的既有语义）。                                    |
| `mxt:active`  | `GrantArtifactAbility`（意图 = 主动） | 同上                                                             | 授予"可发动"的能力；能力热键栏与技能菜单会自动收录（`AbilityHotbarClient.allAvailable` 只筛 `ActiveAbilityType`）。     |
| `mxt:flight`  | `FlightArtifactAbility`         | `speed`（必填 `NumberProvider`）、`costs`（`ResourceCost[]`，默认 `[]`） | 飞行：`FlightService.mount` 的 `NOT_FLYABLE` 判定改为"本定义有没有 `mxt:flight` 条目"，`tick` 用的速度与消耗从这条目读。 |
| `mxt:storage` | `StorageArtifactAbility`        | `slots`（必填 `NumberProvider`）                                   | 储物槽位数（`ArtifactStorageService` 的 `configuredSlots` 改读这里）。                                  |

**关于主动／被动为什么是两个名字、却共用一份形状**：两者的 JSON 完全一样，运行时都走同一条授予路径（能力自己的 `type`
才决定生命周期），分开的价值在于**意图 + 加载期交叉校验**——`mxt:active` 引用的能力必须是主动类型、`mxt:passive`
引用的能力不得是主动类型，写错的包在 `/mxt registries validate` 里当场看到，而不是等玩家发现"这件法宝的技能按不出来"
。若不想承担这份校验成本，退路是只留一个 `mxt:grant`（见 §9.1）。主动／被动条目也接受 `#标签`，标签会按注册表展开后逐个校验。

**`ability` 字段为什么接受标签**：`Talisman` / `SpiritRoot` / `Physique` / `Technique` 的 `granted_abilities` 全部接受
`HolderOrTag`，法器没有理由更窄。实现用 `RegistryCodecs.holderOrTagList(MxtResourceKeys.ABILITY)`（现在的
`AutoIgnoreListCodec.create(Ability.CODEC)` 既不吃标签，坏条目还会被静默丢弃）。

**校验（放进 `ServerCache.rebuild()`）**：

1. 同一个法器定义里 `mxt:flight` 超过 1 条 → problem（速度取哪一条没有正确答案）。
2. 同一个法器定义里 `mxt:storage` 超过 1 条 → problem（槽位是相加还是取大没有正确答案）。
3. `mxt:active` / `mxt:passive` 引用的能力类型不匹配 → problem（§2.4 开头说明）。
4. 同一件物品被两份法器定义匹配 → problem（`ItemMatcher.findAll` 会按注册表顺序取第一份，静默择一是最难查的一类问题）。
5. `spirit_capacity` 的键是 `mxt:disabled` 的灵气 → 按 §3.3 与其它注册表一致的口径处理（视为不存在）。

### 2.5 `curios_equipable`（预留）

- 类型 bool，默认 `false`，语义是"**这份器型允许放进 Curios 槽位**"，不是"这个物品现在能进"。
- 消费者（落地时改一处）：`CuriosIntegration.acceptsBelt` 现在写的是"栈上有 archetype 就算法器"（
  `CuriosIntegration.java:43-45`），改成 `curios_equipable`。**这是行为变更**：今天只要有组件就被 `WEAPONS_ARTIFACTS`
  模式接收，改后必须显式声明。
- 为什么是 bool 而不是 `slots` 列表：用户明确要预留一个布尔；给槽位名（`back_weapon` / `belt_item`）是下一步的事。**将来若要槽位名
  **，正确做法是新增一个可选字段（如 `curios_slots`）而不是把 bool 改成对象——改类型会让现有文件解析失败。
- 判定必须走客户端可用的注册表入口（§0.7），因为 Curios 的槽位 validator 在客户端也会被问。
- **落地后多了一个消费者**：护符槽（Curios 内置 `charm` 四格）的准入条件也是这个字段（`CuriosIntegration.acceptsCharm`，同一条
  `Provider` 判定），设计见 §11。

### 2.6 组件层的变化

| 组件                     | 变化                                                                                                    | 说明                                                                                       |
|------------------------|-------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------|
| `mxt:artifact_state`   | **删 `spirit_energy`，也删 `archetype`**；只留 `owner_uuid`、`nourishment`（落地时按用户拍板：身份只由 `items` 决定，组件不再参与解析） | 存量搬到 `mxt:spirit_storage`；一件物品只可能是它 `items` 所认领的那种法器，"同一物品两种形态"暂时没有表达方式（见 §10.4）         |
| `mxt:spirit_storage`   | 语义扩展：灵石、符箓载体、**法器**三用                                                                                 | 形状不变（`Map<Holder<Aura>, int>`）。                                                          |
| `mxt:artifact_storage` | 不变                                                                                                    | 载荷是 `List<ItemStack>`，槽位上限永远来自定义、不来自组件（今天的类注释已经这么写）。                                     |
| `mxt:item_abilities`   | 语义改成"**手工附加**的能力"（可选保留）                                                                               | 解析后的能力集合 = 定义声明的（`mxt:active` / `mxt:passive`）∪ 组件里的。这样已有的手写组件继续生效，KubeJS / 命令改一个栈也仍然可行。 |

### 2.7 与 `mxt:refining` 配方的关系（顺带，可选）

`mxt:refining` 现在把整份 `Artifact` 内联在配方里（`RefiningRecipe.java:24`）。新设计里身份由 `items` 决定，精炼不再承担"
挂定义"的职责，配方应该收敛成：

```json
{
  "type": "mxt:refining",
  "input": "#mxt:artifact/sword_blank",
  "item_type": "sword"
}
```

即"把某种器胚精炼成某器型的法器"。本轮**没有动 `RefiningRecipe`**：`archetype` 仍然是内联的 `Artifact`（形状换成了新
schema），改成 `Holder` 引用与引入按 `item_type` 的匹配留到法器本体闭环之后再定（它至今零调用者，见 §10.4）。

## 3. 运行时模型

### 3.1 身份解析（`ArtifactService.definition`）

```
definition(access, stack):
  1. artifact_state.archetype 存在且解析得到 → 用它（覆盖）
  2. 否则 ItemMatcher.find(holders(access, ITEM_ARCHETYPE), stack) → 第一份匹配
  3. 都没有 → empty（"这不是法器"）
```

- 必须提供 `Provider` / `RegistryAccess` 重载，客户端与服务端各一份调用（§0.7）。
- **缓存**：匹配是一次注册表线性扫描（与四种 binding 相同）。法器身份会在飞行 tick、Curios 槽位判定、工具提示里被频繁问到，因此：
    - `FlightAttachment` 继续持有解析后的 `Holder<Artifact>`（现在就是这么做的），tick 时只做一次"是否仍然是同一份定义 +
      是否仍归我"的廉价校验，不重新扫描；
    - 条件与工具提示这类每次都要问的入口，按房规用"按注册表实例开键 + `MAX_CACHED_REGISTRIES` + 双检 `LOCK`"的缓存（参见
      `DamageElements`、`ElementReactionService`）。
- **归属**：`owner_uuid` 仍由 `ArtifactService.refine` 写（战利品函数 `mxt:set_artifact_owner` 是现成入口）。定义层不引入
  `require_owner`（**§10.11 已推翻**：定义层引入了 `require_owner`，默认 `false`，认主从前提变成选项）；固定语义：*
  *飞行、储物访问与 `mxt:owned_by` 要求"持有者就是主人"**（§10.11 起飞行与储物改按 `require_owner` 判权，`mxt:owned_by`
  不变）。授予能力**不**查归属（落地时按 §10.3 修正：本体里除了战利品函数没有任何"把已有物品认主"的玩法入口，要求认主会让法器在实机里等于拿不到技能）。

### 3.2 授予与回收

- 复用的既有机制：`AbilityAttachment.reconcileSource(source, desired)`（`AbilityAttachment.java:104`）按来源替换贡献，
  `AbilityEventBridge.onEquipmentChange` 与 `syncCuriosAbilities` 已经在用。
- 改动只有一处：`AbilityEventBridge.itemAbilities(stack)` 从"只读组件"改成"组件 ∪ 定义声明"，**不新增事件、不新增来源 id**
  。来源仍是 `mxt:equipment/<槽>/<物品>` 与 `mxt:curios_equipment`。
- 热键栏、技能菜单、被动属性修正、冷却、`DataStorage` 状态全部零改动地继续工作。

### 3.3 灵力

- 读：`ArtifactService.capacity(stack, aura, fallback, context)` → §2.3 的公式。
- 写：`ArtifactService.addEnergy(stack, aura, amount, fallback, context)` → 写进 `mxt:spirit_storage`，并按"真正收下 ÷
  本次该灵气的有效上限"抬高 `nourishment`（只升不降、夹 `0..1`，与今天一致，只是分母变成该灵气自己的上限）。
- `mxt:charge_artifact` 动作：加一个必填 `aura` 字段（`Holder<Aura>`），语义变成"往这种灵气里灌 amount"。`capacity` 字段保留为
  **没有解析到定义时的回退**（与今天文档口径一致：`docs/数据包格式.md:1213`）。
- `mxt:energy_range` / `mxt:owned_by` 两个物品条件：前者加 `aura`（读某一种灵气的存量），后者不变。
- **`ISpiritEnergy` 角色**：法器对外主要暴露 `ItemAuraAccess`（多灵气）。`ISpiritEnergy` 这条单值通道保留给"只要一种灵气"
  的调用方，用 `ArtifactSpiritEnergy(stack, aura, capacity)` 表达"就这一种"，不再用 `Double.MAX_VALUE` 当容量。

### 3.4 飞行

- `FlightService.mount`：从定义里取 `mxt:flight` 条目（§2.4 保证最多一条）；没有 → `NOT_FLYABLE`。
- `tick`：速度与 `costs` 从条目读，其余（碰撞、载具校验、资源不足、下马恢复 `CREATIVE_FLIGHT` 属性与飞行速度）完全不变。
- **玩家入口仍然缺**：`FlightToggleC2SPayload` 有服务端处理、没有客户端发送方。本设计不改玩法入口，只把数据形状挪进
  `mxt:flight`；入口（客户端按键 / 命令 / 探针）列为 §7 的推迟项。

### 3.5 储物

- `ArtifactStorageService.slots` 改读 `mxt:storage` 条目，其余（`0..256`、`floor`、只有主人能访问、只在服务端）不变。
- **仍然没有调用者**：本设计只统一数据形状，不新增界面。谁来做容器界面（内容方方块 / 模组界面）是独立决定，见 §7。

### 3.6 Curios

- `acceptsBelt`：`artifacts → definition(access, stack).map(Artifact::curiosEquipable).orElse(false)`（§2.5）。
- `belt_mode` / `back_mode` 配置项与默认值（都是 `MANUAL`）不变。
- 护符槽（内置 `charm`，四格）另有一条只认 `curios_equipable` 的判定，且**不挂配置项**，见 §11。

## 9. 被否掉的方案

### 9.1 只留一个 `mxt:grant` 类型

更省一层命名与一份交叉校验，代价是 JSON 上看不出"这件法宝给的是主动还是被动"。**暂不采用**，但保留为退路：若将来`mxt:active`
也要长出法器专属的发动入口（法器技能栏 / 按键 / 右键），它才真正值得独立存在；在那之前它只是意图标注。

### 9.2 `abilities` 里内联技能字段（不引用 `mxt:ability`）

即让 `{"type": "mxt:active", "costs": [...], "entity_action": ...}` 自己长出一套技能词汇表。**否决**，理由与 `Talisman`
的类注释同一条：本模组每个"像技能"的效果都已经落在 `Ability` 上，再养一套平行词汇意味着 15 个字段的 Codec 有两份实现、两处修
bug，而且复用了不了技能注册表里的现成内容。

### 9.3 把 `spirit_capacity` 留成单值 `double`

与用户点名要的"map 灵气存储上限"冲突，而且在多灵气法器上无法表达"只装两种灵气"。**否决**。

### 9.4 用物品标签（`data/<ns>/tags/item/...`）代替 `items` 字段

标签能做到"物品 → 法器"，但做不到"一个物品对应哪一份定义"以外的东西（优先级、器型、来源可追溯），而且定义侧的信息会散到两个文件里。
`ItemMatcher` 已经同时支持物品 id 与标签，且四种 binding 都这么做。**否决**。

### 9.5 靠 `mxt:refining` 配方当唯一写侧

这是现状的实际形态，也是模块死掉的根因：没有调用方就没有身份。**否决**（配方仍保留，但降级为"精炼玩法"而不是"身份唯一来源"）。

### 10.3 与本文不一致之处（以本节为准）

1. **授予能力不查归属**（本文 §3.1／§3.2 原建议"授予与飞行都要求主人"）。理由：本体里唯一会写 `owner_uuid`

4. **`mxt:charge_artifact` 仍是主要灌能路径**：§2.3 曾写"长按灌注即可"，而那条手势只属于实现了 `UseItemAuraAccess`

5. 授予条目的字段名是 `abilities`（接受单个 id、`#标签` 或混合数组），不是 §2.4 表格里写的 `ability`。
6. `ISpiritStorage` 的签名改了（带 `Provider`），§5 的"不动"清单里把它列错了。
7. **`mxt:empty` 不是"省略 `type` 时的回退"**（本文 §2.4 原表格如此描述，实为错误）：固有分派的 `type` 是必填字段，省略会加载失败；

### 10.11 追加：`require_owner`——认主从"前提"变成"选项"（2026-09-21）

用户先问"目前认主逻辑是什么样的，怎么所有物品都要认主"，随后拍板："数据包添加一个配置，设置是否要认主。"

- 当时的实现（也是这一问的答案）：状态是 `mxt:artifact_state.owner_uuid`；唯一写入者是 `ArtifactService.refine`，而本体里只有战利品函数
  `mxt:set_artifact_owner` 会调它；读取者只有三处——`FlightService.ownsEquippedArchetype`、
  `ArtifactStorageService.mayAccess`、物品条件 `mxt:owned_by`。因为**认领物品就等于那件物品是法器**，每一件都从"未认主"开始；而
  `mxt:set_artifact_owner` 与 `mxt:owned_by` 在 main 与测试包里都是**零引用**
  ——实机里既没有认主入口，也没有任何内容用到它，等于飞行与储物对所有法器永久不可用。这条一直写在审计的"仍然没有玩法入口"
  里，只是 §10.10 把认主画进 Tooltip 之后才变得肉眼可见。
- 拍板结果：**不取消认主，改成可配置**。新增定义字段 `require_owner`（bool，默认 `false`）：
    - `false`（默认）：未认主的法器**谁都能用**；一旦被某个实体认主（`refine` 写入 `owner_uuid`），此后只认主人——认主是"
      绑定归属"，不是使用前提。
    - `true`：未认主一律拒绝（旧的严格语义）。
- 判权只做一处：`ArtifactService.mayUse(ItemStack, Holder<Artifact>, UUID)`（`isOwner || (!requireOwner && !hasOwner)`
  ），并顺手加 `ArtifactService.hasOwner(ItemStack)`。调用点两处：`FlightService.ownsEquippedArchetype`、
  `ArtifactStorageService.mayAccess`（后者原来直接问 `isOwner`，现在先解析定义再判权）。
- **不跟着改的**：`mxt:owned_by` 保持字面语义（问的就是"归属是不是你"，未认主即 false，与 `require_owner`
  正交——数据包想强制归属就拿这个条件自己当门槛）；授予能力、Curios 装备、灵气存储也与认主无关，这点没变。
- Tooltip 跟着分工：有主人 → 绿色 `✔ 已认主`（高级提示补 UUID）；`require_owner: true` 且未认主 → 红色
  `✖ 未认主 · 需认主后才能飞行与储物`；`require_owner: false` 且未认主 → **不占行**（常态不是警告）。
- 测试包：`azure_flight_sword` 加 `require_owner: true`（唯一走严格分支的夹具，顺便让飞行门槛有覆盖），另外三件保持默认
  `false`。探针新增**判权腿**（严格件未认主时本人与他人皆拒、认主后本人可用而他人被拒；宽松件未认主人人可用、认主后只认主人），名册腿与

### 10.14 追加：`weapon_binding` 的伤害/攻速改为"替换物品自身数值"（2026-09-21）

用户截图报：下界合金剑的 Tooltip 里在"在主手时"一段多出红色 `-2.4 攻击速度 [-2.4]` 与蓝色 `+6 攻击伤害 [+6]`，问"

  `mxt_test:mxt/weapon_binding/bound_sword.json` 的 `attack_damage: 6` / `attack_speed: -2.4`。旧代码把它们按 `ADD_VALUE`
  **叠加**在物品自身修正之上，于是：
    - 下界合金剑：伤害 `1 + 7 + 6 = 14`、攻速 `4 - 2.4 - 2.4 = -0.8`（**负攻速**，被原版染红）；
    - 钻石剑：伤害 `1 + 6 + 6 = 13`、攻速同样 `-0.8`。

### 11.1 结论摘要

1. **用 Curios 内置的 `charm` 槽型**，不新建槽型：写 `data/mxt/curios/slots/charm.json`，只声明 `size: 4` 与一个校验器；实体归属在

2. **槽位只收"定义里声明了 `curios_equipable: true` 的法器"**：判定交给 `ArtifactService.curiosEquipable`
   ，与给腰带写的是同一个字段。Curios 自带的 `curios:tag` 校验器**保留**（合并而不是替换），所以 `curios:charm` 物品标签仍是"
   放非法器"的逃生门。
3. **不加配置项、不加 lang、不新建资源**：Curios 自带 `curios.identifier.charm` 名字与 `curios:slot/empty_charm_slot` 图标，
   `curios_equipable` 就是那条规则。
4. **不渲染**：法器是任意已有物品，没有模型；4 个槽只出现在 Curios 界面里。背部/腰部那两套渲染器（`back_render` /
   `belt_render` 资源包偏移）不动。
5. **一个必须写清楚的影响**：Curios 的槽位 id 是**全局字符串**，同 id 的定义会合并，所以这 4 格是"给整个整合包的 `charm`
   槽型定的"，任何模组/数据包里能进 `charm` 的物品都会共享这 4 格。用内置槽型的代价就是这个，用户点名要内置类型时已经接受了它。

### 11.3 Curios 15 的加载语义（照着源码核过，决定了这轮怎么写）

1. **槽位 id 是字符串，不是 ResourceLocation**：`CuriosSlotResources.populateData` 用
   `entry.getKey().getPath().substring("slots/".length())` 当 key，命名空间只记进 `idToMods` 供 GUI 显示来源。所以
   `data/mxt/curios/slots/charm.json` 与 Curios 自带的 `data/curios/curios/slots/charm.json` 指向**同一个槽**。
2. **同 id 的定义按命名空间排序后逐个 `apply` 到同一个 Builder**（`curios` 排最前），因此我们的文件是**在内置定义之上合并
   **。
3. `SlotType.Builder.apply` 的合并规则（决定了每个字段该怎么写）：
    - `order`：`replace=false` 时取 `min(已有, 本次)` → **不写**，让 Curios 保留 200。
    - `size`：`operation` 缺省是 `set`，`replace=false` 时取 `max(已有, 本次)`；`add`/`remove` 走独立的 `sizeMod`。内置
      `charm` **没有声明 `size`**，而 `build()` 在 `size == null` 时先按 `1` 起算，所以：
        - 写 `"size": 4`（set）→ 4 格 ✅；
        - 写 `"size": 4, "operation": "add"` → `1 + 4 = 5` 格 ❌（不是直觉上的 4）。**这轮用 set。**
        - 另有一条上游入口：整合包可以在 **Curios 自己的配置**（`CuriosConfig.COMMON.slots`，形如 `id=charm;size=8`
          ）里给同一个槽型加格数；它在我们之后 apply，同样是 `set`+`max` 语义，所以只能把 4 格**调大**、不能调小。要让一个包拿到少于
          4 格，得改我们的槽文件。
    - `validators`：`replace=false` 时**并集**，不是替换 → 只写我们自己的 id，`curios:tag` 自动保留。
    - `icon`：本次不写 → 保留内置的 `curios:slot/empty_charm_slot`（不覆盖上游值）。
    - `entities`（槽文件里的那个字段）：不写 → 走 `else` 分支给 `player_like` 补默认实体类型（这影响 `getItemSlotTypes`
      的默认判断）。
4. **玩家真正拿到哪些槽**由 `entityMap` 决定，而它来自"槽文件里的 `entities`"与"实体文件里的 `slots`"。Curios
   只发槽定义、不发实体文件，所以**必须**在我们自己的实体文件里加 `"charm"`。
5. `curios:tag` 校验器的实现是 `stack.is(curios:<槽id>) || stack.is(CuriosTags.CURIO)`（`impl/CuriosSlots.java`
   静态注册），对应的物品标签是 `curios:charm`。

`data/mxt/curios/entities/entities.json` 的 `slots` 增加 `"charm"`（现在是 `back_weapon`、`belt_item`、`charm`）。

#### 11.4.2 判定

`CuriosIntegration.registerPredicates` 增加一行（三个判定都经同一个私有 `registries(SlotContext)` 取注册表视图，理由见下一条）：

```java
CuriosSlotTypes.registerPredicate(Identifier.fromNamespaceAndPath("mxt", "charm_artifact_auto"),CuriosIntegration::acceptsCharm);
```

```java
private static boolean acceptsCharm(SlotContext context, ItemStack stack) {
    if (stack.isEmpty()) return false;
    Provider access = registries(context);
    return access != null && ArtifactService.curiosEquipable(access, stack);
}
```

- 走 `Provider` 重载，因为 Curios 的槽位校验在客户端也会被问（同 `acceptsBelt`）。
- 不做 `isOwner` 判断：**"能不能放进槽"与"是不是你的"是两件事**，后者由飞行、储物访问与 `mxt:owned_by` 负责。
- **§10.12 起**：注册表视图统一从 `CuriosIntegration.registries(SlotContext)` 取，**没有实体的 `SlotContext` 返回 `null`
  、判定回答"不认领"**。这条路径真实存在：Curios 在构建配方书与创造模式搜索索引时会拿没有实体的上下文问同一个判定，此前三个判定直接读
  `context.entity().level()`，于是每个物品抛一次 `Cannot invoke LivingEntity.level() because ... is null`（详见 §10.12）。

#### 11.4.3 为什么不再加一个 `charm_mode` 配置

`back_mode`/`belt_mode` 存在是因为那两个槽在 `curios_equipable` 出现之前就要放行"武器"（由 `weapon_binding`
决定），需要一个"标签驱动 / 全放 / 放武器"的开关。charm 槽只有一条规则，且**规则本身就是数据包写的**：想放别的东西就把物品加进
`curios:charm` 标签（`curios:tag` 校验器还在）。再加一个配置只会多出两份 lang 与文档站配置页的一行，而不增加表达力。

### 11.5 效果与边界

- 玩家在 Curios 界面看到 4 个 `charm` 槽（名字与图标由 Curios 提供，中文名等 `curios.identifier.charm` 的翻译）。
- 放进槽里的法器照常生效：`AbilityEventBridge.syncCuriosAbilities` 每 20 tick 读**所有** Curios 物品堆，法器定义声明的能力因此同样被授予（
  `mxt:passive`/`mxt:active` 都算），脱下即回收。
- 槽位是**全局**的：整合包里所有模组的 `charm` 物品（或其 `curios:charm` 标签成员）都共享这 4 格，我们的法器也在别的模组定义的
  `charm` 槽里可用（只要那边的校验器放行）。
- 不渲染、没有快捷交换（`key.mxt.swap_back` 仍只服务背部第一个槽）。

### 11.7 不做的 / 推迟的

- **渲染**：4 格都不画在角色身上（用户拍板）。
- **快捷交换**：charm 槽没有对应按键；将来若要，需要先定"哪一格"的语义（`BackSlotSwapC2SPayload` 只换背部第 0 格）。
- **每格语义**：4 格目前完全等价，没有"第 1 格才有某种加成"的说法；要有就得先有读取槽位的条件（`mxt:has_equipped_item`已经支持点名
  `curios:<槽位>`，但那是"槽位"级，不是"第几格"）。
- **配置项**：见 §11.4.3。

### 11.8 被否掉的方案

1. **自建槽型**（例如 `data/mxt/curios/slots/artifact_charm.json`）：槽位 id 是全局字符串，自建一个 `artifact_charm` 能做到"
   只影响自己"，但用户明确要"curios 内置类型"，且内置 `charm` 本来就有名字与图标。
2. **`operation: "add"`**：直觉上"加 4 格"，实际因为内置定义没写 `size`、`build()` 从 1 起算，会得到 5 格。
3. **收所有法器**：会让 `curios_equipable` 只剩腰带一个消费者，且"能进 charm"变成无法关闭的默认，不如让数据包显式表态。
4. **新增 `curios.charm_mode` 配置**：见 §11.4.3。
5. **复用腰带渲染**：4 格只有两个腰侧位置，会静默重叠；要给就得定义优先级，属于渲染设计，不在本次范围内。
