# 发消息行为设计（send_message）

状态：已落地（**仅编译验证**；未起测试服务端，探针只编译未运行）

## 1. 动机与范围

四轴行为（entity / block / item / bi-entity）与阵法功能模块（`formation_action_type`）里都没有"对玩家说话"这个动作。要在数据包里说一句话，今天只能靠 `mxt:js` 走 KubeJS，或者干脆没有——而这两条路对"阵法警告""符箓提示""法器冷却播报"这类常见需求都太重。

本次新增一个类型 **`mxt:send_message`**，五处各登记一次：

| 轴 | 注册表 | 位置 |
| --- | --- | --- |
| entity | `MxtEntityActions` | `data/action/builtin/SendMessageAction.java` |
| block | `MxtBlockActions` | 同上 |
| item | `MxtItemActions` | 同上 |
| bi-entity | `MxtBiEntityActions` | 同上 |
| formation | `MxtFormationActionTypes` | `data/formation/builtin/SendMessageFormationAction.java` |

用户给定形状：**四轴全都加**、**阵法也加**、消息正文**支持纯文本与翻译键两种写法**、`condition` 用来**筛收件人**（不是筛触发者）。

## 2. 一个类覆盖四轴

`SendMessageAction` **一个 record 同时实现四个接口**，照 `NoOpAction` 的先例（它也是 `enum` 同时实现四个）。四轴之间唯一的差别是"手上有几个实体"，所以按轴各写一个类会得到四份只差一行的代码。

各轴交给 `send` 的候选实体：

| 轴 | 行为自己的实体 | 配对另一方 |
| --- | --- | --- |
| entity | `context.entity()` | 无 |
| item | `context.holder()` | 无 |
| block | 无（只有位置） | 无 |
| bi-entity | `context.actor()` | `context.target()` |

## 3. `target` 字段：收件人怎么选

```json
{ "type": "mxt:send_message", "message": "…", "target": "self" }
```

| 取值 | 含义 |
| --- | --- |
| `self`（默认） | 行为自己的那个实体 |
| `other` | 配对里的另一方 |
| `all` | 世界里的全部玩家 |

**`all` 是唯一在四种轴上都能用的取值**，因为它问的是 `ServerLevel.players()` 而不是上下文里的实体——方块行为手上一个实体都没有，只有 `all` 找得到人。这不是特例分支，而是"哪一档收件人不依赖实体"这个问题的答案。

### 3.1 非玩家收件人必须什么都不发（本次修掉的一个 bug）

第一版写成了：

```java
Optional<ServerPlayer> addressee = this.target.player(actor, other);
if (this.target == MessageTarget.SELF && addressee.isEmpty()) return;
List<ServerPlayer> candidates = addressee.map(List::of).orElseGet(server::players);
```

只挡住了 `SELF`。于是 `target: "other"` 而对方**不是玩家**（一头牛、一根箭）时，`addressee` 是空的，`orElseGet` 落到 `server.players()`——"告诉对方一声"变成了**全场广播**。`SELF` 落在非玩家实体上同理。

改法是让"命名收件人"与"全场"走两条路，命名收件人落空就**什么都不发**：

```java
List<ServerPlayer> candidates;
if (this.target == MessageTarget.ALL) candidates = server.players();
else candidates = this.target.player(actor, other).map(List::of).orElseGet(List::of);
```

这条约束写进了注释，并由 `/mxt_test message` 的 `dispatchesOnEveryAxis` 腿直接对 `MessageTarget.player()` 断言四种组合（玩家/非玩家 × `SELF`/`OTHER`/`ALL`）——**纯函数，不需要收包就能测**。

## 4. `message` 字段：两种写法

复用已有的 `MiscCodecs.TRANSLATABLE_COMPONENT`（物品名等处在用）：

```java
Codec.either(Codec.STRING, ComponentSerialization.CODEC)
     .xmap(e -> e.map(Component::translatable, Function.identity()), Either::right);
```

- **裸字符串**按翻译键读 → `{"message": "your.pack.key"}`，配数据包自己的 lang。
- **对象**按完整文本组件读 → `{"message": {"text": "hi", "color": "red"}}`，样式保留。

所以正文这一块**不需要新 codec**，也不该新造一个。

## 5. `channel` 字段：发到哪儿

`MessageChannel` 是**共享枚举**，放在 `com.iafenvoy.mxt.data`（不是某个 action 子包里），因为四轴与阵法模块都要用：写成两份嵌套枚举会让同一个数据包值出现两个类型。

| 取值 | 效果 |
| --- | --- |
| `chat`（默认） | `sendSystemMessage(msg, false)`，进聊天栏 |
| `actionbar` | `sendSystemMessage(msg, true)`，物品栏上方 |

**默认 `chat`**：动作栏是覆盖式显示，一句数据包没主动要求放那儿的话会盖掉玩家自己的按键提示，也会被下一句盖掉。默认值指向"不抢占"的那一侧。

## 6. `recipients` 字段：逐人筛选

```json
{ "type": "mxt:send_message", "message": "…", "recipients": { "type": "mxt:sneaking" } }
```

类型是现成的 `EntityCondition`（65 个内置条件），不写＝`AlwaysCondition.INSTANCE`（恒真）。

**判定是逐个候选玩家做的**，不是对整批做一次——这才让"只通知好友""只通知阵主的敌人"写得出来。行为自己的实体也是候选之一，条件同样能把它筛掉。

条件拿到的上下文是 `context.copyTo(new EntityConditionContext(player, formula))`——`copyTo` 会把扩展数据（`Context.ORIGIN`、阵法模块塞的 `FormationCarrier.KEY`）一并带过去，所以条件里读得到这次发动的地点与阵法载体。

未知的 `type` 会让**整份定义解码失败**（注册表分派本来就是这个口径），不会静默降级成"不筛任何人"。

## 7. 阵法轴

`SendMessageFormationAction` 是**独立 record**（阵法的 `FormationActionType` 是个纯 `codec()` 接口，行为靠 `FormationActionRunner` 里的 `instanceof` 分派，与四轴不是一套），只有三个字段：`message` / `channel` / `recipients`。

它**没有 `target`**：`FormationActionRunner.perEntity` 本来就是"对每个被覆盖实体各跑一次"，收件人天然就是"覆盖到的每一个人"，再给一个 `target` 只会与调用点矛盾。非玩家实体直接跳过（收不到消息），条件对它们求值也没有意义。

```java
private static void message(SendMessageFormationAction module, Entity entity, EntityActionContext context) {
    if (!(entity instanceof ServerPlayer player)) return;
    if (!module.recipients().test(player, context)) return;
    player.sendSystemMessage(module.message(), module.channel().actionBar());
}
```

阵法模块里**没有"发给阵主"这一档**：谁站在半径里谁收到，阵主自己也在内。要单独通知阵主是另一件事，现在没做。

## 8. 边界

- **只在服务端生效**。客户端 level 没有玩家表，`send` 直接返回，不假装发出去了。
- **不检查玩家是否看得见发信者**：`sendSystemMessage` 是直接投递，没有视线/距离判定。想让消息只落在附近，用 `recipients` 套一个距离条件。
- **不发送"来源"**：消息显示为系统消息，没有玩家名做前缀。要让消息看起来来自某个人，写 `mxt:actor_action` 套一条 `target: "self"` 的实体行为（阵法轴没有这条）。
- **一句一个包**：`all` 在一百人的服务器上是一百次 `sendSystemMessage`。数据包自己控制频率（阵法轴受 `interval_ticks` 与阵法拍约束；字段名与单位见 [`88`](88_阵法功能模块重设计.md) §11）。
- **消息正文不做长度限制**：与 `sendSystemMessage` 一致的信任口径，数据包自己写的内容。
