## 0. 结论摘要

1. **长按是"一个入口、两种结算"**：右键长按（原版 use 周期，非潜行）→ 未认主时**完成长按**才扣血认主；自己是主人时**按住期间**把自身灵气注入法器；别人是主人时**这次右键根本不接管**（不 arm、不出姿势，退回原版行为）。
2. **只借 `HoldService`，不新造手势**：法器的长按和功法（`TechniqueBinding`）、灵石符箓灌注（`SpiritChargeHold`）走同一套 `HoldBinding` + `HoldSource` + use 周期，姿势、音效、时长、客户端保活全部复用。
3. **接口扩展（用户点名）**：`HoldBinding` 增加带持有者的 `claims(LivingEntity, Provider, ItemStack)` 与 `holdTicks(LivingEntity, Provider, ItemStack)` 默认方法，`HoldService` 在所有调用点把持有者递下去。旧声明零改动：默认实现转发到原来的无实体重载。
4. **三个新数据包字段**（全部可选，默认值即"能用"）：`hold_ticks`（默认 20，0＝这个法器不接管长按）、`refine_health_cost`（**见 §11：不写＝免费**）、`refine_condition`（默认恒真）。
5. **一个全局配置**：`artifact.allow_lethal_refine`（默认关）——血量 ≤ 成本时拒绝认主、不扣血；打开则照扣，可能致死。这是"1 和 2 都做可配置"的落地方式，按用户要求放全局服务端配置而不是每个定义一个开关。
6. **认主仍只有一个写侧**：长按走 `ArtifactService.refine`（写 `owner_uuid`、跑 `refine_action`、发 `ArtifactRefineEvent`），所以战利品函数、KubeJS 与这条手势不会各写一套。
7. **`refine_condition` 只在手势里判**（`ArtifactHoldService.claim`）：`ArtifactService.refine` 保持无条件写入，因为它同时是战利品函数与脚本的入口——把条件塞进那里会让"生成时指定主人"的战利品表静默失效。

## 1. 行为表

| 持有者状态 | 长按开始时（claims） | 按住期间（每刻） | 长按完成时（Finish） |
| --- | --- | --- | --- |
| 未认主 | 接管 | 什么都不做 | 判 `claim_condition` → `refine`（写归属 + 跑 `claim_action`，代价也在里面）→ 跑一次 `use_action` |
| 自己是主人 | 接管（且法器至少有一种灵气还有空位） | 每种声明的灵气各 1 点，1:1 从自己的灵气池扣；**真的收下灵气的刻各跑一次 `pour_action`** | 报一句"已注入 N 点" + 跑一次 `use_action` |
| 别人是主人 | **不接管**（prompt 一句"此物已认主他人"，不取消事件） | — | — |
| 自己是主人但已灌满 | 不接管（提示"此物已充满灵气"） | — | — |
| 中途松手 | — | — | 什么都不结算；已经灌进去的灵气**不退回**（与灵石灌注同口径） |

- **潜行右键**永远不是长按（`HoldService` 的既有规则）：潜行是物品的"另一个行为"。
- **物品自带的 use 不被动**：食物、药水这类自带 `minecraft:consumable` 的物品，如果同时是法器，`HoldService` 不覆盖它自己的 use（既有规则）。

## 2. 数据包字段（`mxt:artifact`）

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `hold_ticks` | `NumberProvider` | `20` | 长按的 use 周期长度（刻）。求值后夹在 `0..72000`；**0 表示这个定义不接管长按**（`HoldLookup` 直接不收它）。声明级（无实体）按空上下文求值，因此写公式时不要依赖持有者。 |
| `claim_condition` | `EntityCondition` | `mxt:always_true` | 认主条件（原 `refine_condition`）。长按完成时判一次；不满足则认主失败，`claim_action` 不跑。 |
| `claim_action` | ItemAction | `mxt:consume_health{amount:4}` | **认主时做什么**，**代价也在里面**（默认即扣 4 点生命；免费写 `mxt:no_op`）。可写单条或数组。**没有预检**（见 §13 / §14）。 |
| `pour_action` | ItemAction | `mxt:no_op` | 注灵时，每一个真的收下灵气的刻各跑一次。 |
| `use_action` | ItemAction | `mxt:no_op` | 整段长按走完时跑一次（认主成功时与注灵结束时都跑）。 |

> 第四次改动一度把代价拆成独立字段 `claim_cost`，第五次改动又把它并入 `claim_action`（见 §14）——上面这张表是**最终**形状。

`abilities` 里额外多了 `mxt:upkeep`（周期性代价，见 §13）。旧名 `refine_health_cost` / `refine_action` / `refine_condition` 都已进入"写了也不读"清单。

示例：

```json
{
  "item_type": "sword",
  "items": "minecraft:diamond_sword",
  "spirit_capacity": { "mxt:qi": 200 },
  "hold_ticks": 30,
  "claim_condition": { "type": "mxt:has_ability", "ability": "mxt:sword_body" },
  "claim_action": [
    { "type": "mxt:consume_health", "amount": "4 + realm_rank" },
    { "type": "mxt:charge_artifact", "aura": "mxt:qi", "amount": 40 },
    { "type": "mxt:damage_item", "amount": 1 }
  ],
  "abilities": [
    { "type": "mxt:upkeep", "costs": [{ "id": "mxt:qi", "amount": 1 }], "interval": 20,
      "on_fail": { "type": "mxt:damage_item", "amount": 1 } }
  ]
}
```

（不写 `claim_action`＝默认扣 4 点生命；**免费认主要显式写 `{"type": "mxt:no_op"}`**，删掉字段不等于免费；`abilities` 里那条是可选的周期性代价。）

## 3. 流程

```
右键（非潜行）
  └ HoldService.onItemUse
      └ HoldLookup.hold(stack) → ArtifactHold（这个定义声明 hold_ticks > 0 且认领该物品）
          └ ArtifactHold.claims(holder, registries, stack)
              ├ 无主人            → true（认主手势）
              ├ 主人是自己且有位  → true（注入手势）
              └ 其它              → false（不 arm；本模组自己的 RightClickItem 订阅补一句提示）
  └ arm：写入 use 周期（时长 = hold_ticks）

按住期间（每刻，服务端）
  └ ArtifactHoldService.onUseTick
      └ 主人是自己：对 spirit_capacity 的每一种灵气
          ├ 余量 = capacity(含温养加成) - stored，取 min(1, 余量)
          ├ 1:1 从持有者该灵气对应的 resource 池扣（走 ResourceService.change，量以实际被收下的为准）
          └ ArtifactService.addEnergy(...)（顺带抬高温养度）
      └ 客户端那一侧只保活姿势，不写任何状态

长按完成（服务端）
  └ ArtifactHoldService.onUseFinish
      ├ 未认主：refine_condition 不满足 → 提示；血量不足且配置为拒绝 → 提示；否则 refine + 扣血
      └ 已是自己的：报本次注入总量
```

## 4. 判定与边界

1. **`claims` 只读两侧一致的状态**（物品组件上的归属、物品上的存量与定义里的上限），不读"持有者灵气池还有没有灵气"。理由是它会在客户端也被问一次，而两端答案必须一致——池子不够这种事放在每刻结算时报一句就够了（与 `SpiritChargeService` 的分工相同）。
2. **灌哪种灵气**：`spirit_capacity` 写了哪几种就灌哪几种，每种每刻 1 点，互不挤占；没写这种灵气（容量 0）自然跳过；玩家池不够的那种这一 tick 跳过，不报错。
3. **扣血用 `entity.damageSources().magic()`**：走 `hurt`，因此会经过抗性提升/保护附魔的减免，也能正常触发死亡与死亡消息。**不做**"非法术伤害"的特殊处理——这是一次秘法代价，不是环境伤害。
4. **致死边界**由配置决定（§5）。判定比较的是**原始生命值**与成本，而不是伤害减免后的实际损失。
5. **认主条件是"能不能认主"，不是"能不能用"**：`require_owner`（§23 §10.11）决定飞行与储物要不要先认主，`refine_condition` 决定这次认主成不成立，`mxt:owned_by` 仍然是"归属是不是你"的字面问题。三者互不替代。
6. **`claim_action` 只在真的认主成功时跑**（`ArtifactService.refine` 内部），条件失败时不会跑——数据包不会为一次失败付出代价（代价也是这条行为的一部分）。
7. **不可伤害的持有者**（创造模式、`invulnerable`）：`hurt` 收不到血，但认主照常成立。这是有意的——否则创造模式下这条手势永远不可用；代价是"创造模式认主免费"。

| --- | --- | --- |

## 6. 接口扩展

```java
// data/item/HoldBinding.java（新增，全部是默认方法，旧声明零改动）
default boolean claims(LivingEntity holder, Provider registries, ItemStack stack) { return this.claims(registries, stack); }
default int holdTicks(LivingEntity holder, Provider registries, ItemStack stack) { return this.holdTicks(registries, stack); }
```

`HoldService` 把持有者递下去的位置：`onItemUse`（arm 时判定）、`onUseTick`（客户端保活）、`playHoldSound`（音效节奏用的总时长），以及 `arm` / `armQuietly` 的公开签名。为什么需要实体：法器的答案是"这件东西现在归不归你"，而这是持有者的属性，不是物品的属性——原先的接口只有 `Provider + ItemStack`，任何按持有者分辨的手势都写不出来。

## 7. 与既有模块的关系

- **`SpiritChargeService`（灵石/符箓灌注）不变**：那套是给实现了 `UseItemAuraAccess` 的**物品类**用的，法器是"已有物品的规则"，本体不会给它改类，所以法器自己读 `spirit_capacity` 与 `mxt:spirit_storage`。两者共用 `HoldLookup`，因此同一件物品同时被两套声明认领时按 `HoldLookup` 的匹配顺序（注册顺序 + 优先级）取第一份。
- **`TechniqueBinding` 不变**：`learn_time` 的语义与法器的 `hold_ticks` 互不影响。
- **认主入口**：§23 §10.11 记的"玩家侧认主入口依然不存在"由本文关闭——入口就是长按。战利品函数 `mxt:set_artifact_owner` 与 KubeJS 仍是另外两条写侧。

## 8. 被否掉的方案

1. **给法器加 `ItemUseAnimation`/`hold_sound` 字段**：姿势与音效是本体口径而不是内容口径（功法也只给了一个"能自定义"的例外），先固定成代码里的选择；真要开放，加字段即可，不影响现有 JSON。
2. **在 `ArtifactService.refine` 里判 `refine_condition`**：那会让战利品函数（"生成时指定主人"）在条件不满足时静默不写归属，排查成本高。条件属于**手势**。
3. **"血量不足扣到剩 1 点"**：用户没选；它会引入"成本随血量缩水"的隐藏语义。
4. **认主失败时把已灌的灵气退回**：中途松手本来就不结算，只有"完成长按但条件/血量不过"才会走到这里；那种情况下这一轮压根没有灌灵气（未认主分支不灌），所以没有可退的东西。
5. **每个定义一个 `allow_lethal` 字段**：见 §5。

## 9. 不做的 / 推迟的

- **姿势与音效的字段化**（§8.1）。
- **认主进度条**：`TechniqueItemService` 给功法阅读画了百分比条，法器这一轮只报"开始/结束"与每刻的注入总量；要画条得先定"未认主"与"注入"两种手势各自的分母。
- **`mxt:refining` 配方的调用方**：仍然是零调用者，本文不动它。
- **储物/飞行入口**：与本文无关，仍缺（§23 §10.4）。

## 11. 2026-09-21 第二次改动：扣血改成可选 + 做成 action（**已被 §12 取代，保留为历史**）

> **本节记录的是一个中间状态，现已被 §12 推翻**：`refine_health_cost` 先是变成可选字段、由手势自己也扣一次；第三次改动把字段整个删掉，扣血只由 `refine_action` 里的行为完成。保留本节是为了留下"当时为什么先选了保守方案、代价是什么"。

用户原话："给 artifact 加一个认主之后的 action，扣血做成 action"，随后补充"扣血改成 optional，可以选择不扣"。拍板结果（三选一里选的）：

1. **新增内置物品行为 `mxt:consume_health`**（`data/action/builtin/item/ConsumeHealthItemAction.java`，注册 `MxtItemActions.CONSUME_HEALTH`）：`amount` 是必填的 `NumberProvider`，对行为上下文里的持有者造成一次 `damageSources().magic()` 伤害。**它不预检、不拒绝**——行为是效果，不是闸门。
2. **`refine_health_cost` 改成可选**：字段类型从 `NumberProvider`（默认 `4`）改成 `Optional<NumberProvider>`，**不写就是免费认主**，`ArtifactService.refineHealthCost` 对"没有声明"返回 `0`。旧的"默认 4 点"整个消失（不是改成默认 0）。
3. **认主后的动作沿用现有的 `refine_action`**，不新开 `refine_actions`、也不给手势单开第二个钩子：`Artifact.refineAction` 本来就在 `ArtifactService.refine` 里、写完成归属之后执行，长按认主、战利品函数与脚本三条路都会跑到，且 `ItemAction.CODEC` 本来就接受"单条或数组"。

代码落点与语义：

| 位置 | 行为 |
| --- | --- |
| `ArtifactHoldService.claim` | 条件 → 代价（**没声明就跳过预检**）→ `ArtifactService.refine`（写归属 + 跑 `refine_action`）→ 代价 > 0 时 `new ConsumeHealthItemAction(new Constant(cost)).execute(...)` |
| `ArtifactService.refineHealthCost` | 没有声明／求值非有限／≤ 0 → `0`（免费）；写得再大也不夹上限（夹取交给血量与致死判断） |
| `ArtifactDescription.appendHold` | 代价 > 0 → `tooltip.mxt.artifact.hold_claim`（带数字）；否则 → `tooltip.mxt.artifact.hold_claim_free`（"长按：认主（无需代价）"，不再报一个 0） |
| `ArtifactHoldService.report` | 同上：`actionbar.mxt.artifact.claimed`（带数字）／`actionbar.mxt.artifact.claimed_free` |

**为什么让手势的扣血也走这条 action**：否则"扣血"会有两份实现（手势里一份、行为里一份），改一处忘一处。现在 `ConsumeHealthItemAction` 是唯一的扣血实现，手势只是"用声明的数值调它一次"。

**已知的边界（有意留下，写进文档）**：

1. **写在 `refine_action` 里的 `mxt:consume_health` 不经过手势的预检，也不看 `allow_lethal_refine`**：那条路是数据包亲手安排的效果，可能把持有者扣死。手势那条（`refine_health_cost`）才做"血量 ≤ 代价就拒绝"。
2. **两处都写会各扣一次**（先 `refine_action` 里的，后字段那条），文档里明说了"通常只需要一处"。
3. **战利品函数路径不判代价**：`mxt:set_artifact_owner` 跑 `refine_action`，所以把扣血行为写在那里的包会让"被指定的主人"挨这一下；这是包的显式选择，不是本体的默认。

**被否掉的方案**（这三个是问用户时摆在桌面上的另外两个 + 一个变体）：

1. **只把 `refine_health_cost` 改成可选、不加 action**：改动最小，但"扣血"仍然只有本体能表达，数据包没法把它挪到别处或换成别的代价。
2. **彻底声明化：删掉 `refine_health_cost`，扣血只由 `refine_action` 里的 `mxt:consume_health` 表达**：字段最少、语义最纯，但① 预检与工具提示只能去行为树里"尽力找一条扣血行为"，嵌套一层（`mxt:sequence` / `chance` / `if_else`）就找不准；② 老字段会被 `RecordCodecBuilder` 静默忽略，等于让老包悄悄变成免费认主。
3. **再加一个只属于长按手势的认主后钩子**：三条认主路径会有两个收尾点，文档与用户都得记住"哪个钩子在哪个入口跑"，收益不抵成本。

## 12. 2026-09-21 第三次改动：删掉 `refine_health_cost`，代价全部交给 action（**已被 §13 取代，保留为历史**）

### 12.1 最终形状

1. **字段删除**：`Artifact` 的 `refine_health_cost`（以及它短暂存在过的 `Optional` 形态）整个移除；record 现在是 `(item_type, items, spirit_capacity, abilities, curios_equipable, require_owner, refine_action, refine_condition, hold_ticks)`。旧键从此属于"写了也不读"的一类（`RecordCodecBuilder` 静默忽略）。
2. **代价 = 一条行为**：`refine_action` 里的 `mxt:consume_health`（`amount` 必填）就是"以血认主"；只想免费就把它删掉，想再加别的代价就往同一个数组里加。
3. **手势只"读回"，不自己扣**：`ArtifactService.refineHealthCost(...)` 现在读的是定义自己的行为树，而不是字段：

### 12.2 这次改动的后果（都写进了文档）

1. **代价跟着路径走**：`refine_action` 在战利品函数（`mxt:set_artifact_owner`）与脚本直接调 `ArtifactService.refine` 时同样会跑，所以那两条路**也会扣血，而且没有预检**。这是"全部交给 action"的直接结果，不是 bug。
2. **嵌套写的代价读不到**：`mxt:chance` / `mxt:if_else` 里的扣血不会被预检、不会出现在 Tooltip 数字里，但轮到它时会照扣。想被预检就平铺写。
3. **老包静默变成免费认主**：`refine_health_cost` 不再被读，写了既不报错也不扣血。这是本仓一贯的口径（`RecordCodecBuilder` 忽略未知键），但代价字段属于"踩了会静默改平衡"的那类，所以三处文档都点名要手工搬进 `refine_action`。
4. **"两处都写会扣两次"这个坑消失了**（§11 的边界 2 作废）。

### 12.3 考虑过但没做的

1. **连血量预检与 `allow_lethal_refine` 一起删掉**：那样"血量不足拒绝认主"会彻底消失，而这个行为是上一轮用户明确要"做成全局配置"的，静默删掉不合适。保留成"读回平铺代价才预检"。真不要预检的话，把 `refineHealthCost` 的调用点从 `claim` 里删掉即可，改动很小。
2. **递归扫描整棵行为树（含 `chance` / `if_else` 分支）**：读到的数不再等于"实际会扣的数"，预检会变成假承诺，故不做。
3. **保留字段、同时支持 action（§11 的形态）**：用户明确否掉。

## 13. 2026-09-21 第四次改动：功能拆分 + 周期代价交给 ability + 取消预检（**其中的"代价独立成字段"已被 §14 取代，保留为历史**）

> **本节记录的是第四个中间状态**：功能拆分、周期代价交给 `mxt:upkeep`、取消预检这三件事都留下了；只有"代价独立成 `claim_cost` 字段"这一步在第五次改动里被并入 `claim_action`。看最终形状请读 §14 与 §2。

### 13.1 最终形状

`mxt:artifact` 的字段（`Artifact.java`）：

| 字段 | 类型 | 默认 | 职责 |
| --- | --- | --- | --- |
| `hold_ticks` | `NumberProvider` | `20` | 手势多长；`0`＝不接管长按 |
| `claim_condition` | `EntityCondition` | 恒真 | **能不能认**（原 `refine_condition`） |
| `claim_cost` | ItemAction | `mxt:consume_health{amount:4}` | **付什么**（`Artifact.DEFAULT_CLAIM_COST`；免费写 `mxt:no_op`） |
| `claim_action` | ItemAction | `mxt:no_op` | **认下之后做什么**（原 `refine_action`） |
| `pour_action` | ItemAction | `mxt:no_op` | 注灵时**每个真的收下灵气的刻**各一次 |
| `use_action` | ItemAction | `mxt:no_op` | 整段长按**走完**时一次（认主成功／注灵结束都算） |

"其他 action 默认 `no_op`"落在 `claim_action` / `pour_action` / `use_action` 三个字段上；只有代价不是 `no_op`，因为"默认扣四点血"就是要求。

`abilities` 新增 **`mxt:upkeep`**（`UpkeepArtifactAbility`）：

| --- | --- | --- | --- |
| `costs` | `ResourceCost[]` | `[]` | 每 `interval` 刻扣一次的资源（全有或全无） |
| `interval` | `NumberProvider` | `20` | 结算周期（刻），求值非法时回落到 20 |
| `on_fail` | ItemAction | `mxt:no_op` | 付不出时对持有者与该物品堆执行的行为 |
| `owner_only` | bool | `true` | 只对主人生效（未认主＝没人付）；`false`＝谁带着谁付 |

### 13.3 代价与边界

1. **没有预检**：代价照扣，可能当场致死；扣死也算认下（归属已写）。打不掉血的持有者认主免费（伤害收不到）。
2. **三条写归属的路都付代价**：长按、`mxt:set_artifact_owner`、脚本直接 `refine`；后两条没有手势、也没有任何检查。
3. **周期代价与认主代价彻底分开**：`mxt:upkeep` 是按世界时间结算的持续代价，"带上就开始付"；`claim_cost` 是认下那一次的价格。想两样都要就两处都写。
4. **`owner_only` 的默认值为真**：未认主的法器不向任何人收费——这与 `require_owner`（能否飞行／储物）是两件事，别混。
5. **`interval` 用的是世界时钟**：结算发生在"世界时间 % interval == 0"的刻，不是"拿起后每 N 刻"；好处是不需要在物品堆上存计数器，两端（客户端／服务端）读数也一致。

### 13.4 被否掉的方案

1. **把代价做成 `NumberProvider` 字段（恢复 `refine_health_cost` 的形态）**：用户选的是"两个槽"，且代价保持成行为才能在同一个位置换成别的代价。
2. **把周期代价继续挂在 `claim_action` 上**（例如每 tick 由别的系统读它）：那正是这次要拆掉的东西——认主的收尾与持续消耗不是同一件事。
3. **用 `entity.tickCount % interval` 之外的每堆计数器**：需要在物品堆上新增组件来存相位，且 `reload` / 复制物品时相位会漂。
4. **`on_fail` 用实体行为（EntityAction）**：失败惩罚通常要作用在**这件法器**上（磨损、掉耐久），所以用能同时拿到持有者与物品堆的 `ItemAction`。

## 14. 2026-09-21 第五次改动：`claim_cost` 并入 `claim_action`

## 15. 2026-09-21 第六次改动：注灵反馈的两处修正（用户实机报的问题）

用户报了两个现象（**都是注灵手势的反馈，不是灵气本身被清空**）：

1. "绑定到钻石剑上的那个法宝……充满 20 格灵气直接归零了从头开始充"。
2. "灵宝的灵气满了，错误显示的是'自身灵气不足'"。

### 15.1 现象 1 的原因：计数器在每个 use 周期边界清零

`hold_ticks` 默认 20，而注灵是**每刻 1 点**，所以一个 use 周期正好搬 20 点。原版按住右键不放时会**一个周期接一个周期地重开**（客户端在 `rightClickDelay` 到点后再次发起 use），而 `ArtifactHoldService.onUseStart` 在**每个新周期**都 `POURED.remove(uuid)`——于是动作栏的「注入灵气 N 点」每 20 刻从 1 重新数，读起来就像"充满 20 点后归零重充"。**灵气存量（`mxt:spirit_storage`）从头到尾没有被清零**：全仓只有 `addEnergy`（只增）与两处未被调用的 `consumeEnergy` / `ArtifactSpiritEnergy` 会写这个组件。

修法：把"一次手势"的边界从 **use 周期**改成**按住期间**——`POURED` 现在存 `(total, lastTick)`，连续有进账就继续累加，静默超过 `SESSION_GAP_TICKS = 40` 刻（2 秒，远大于两个周期之间的间隔）才算新一次；松手（`Stop`）仍然清空。周期结束的提示改成「本次共注入灵气 %s 点」（`actionbar.mxt.artifact.poured`），语义与实现一致。

### 15.2 现象 2 的原因：`hasRoom` 问的是"任何一门还有空位"

原来什么都不动时报不报错，只问了一句话：`ArtifactService.hasRoom(...)` = "**有没有任何一门**声明的灵气还有空位"。护身玉符那类**多灵气**法器只要还有一门不满，这句话就是真——即使那一门正是玩家池子空掉的那门，于是"法器满了"和"你付不出"被压成了同一句「自身灵气不足」。钻石剑（`qi` 100 ＋ `water_power` 50）配上 `mxt_test:qi` 的境界门禁／空池子，正好踩中：`water_power` 满了、`qi` 付不出，报的还是笼统那句。

修法：新增 `ArtifactHoldService.blockedAura(holder, stack, artifact)`，按**与 `pour` 完全相同的次序**找"第一门还有空位"的灵气：
- 它付得出 → 返回 `null`（正常情况下这一刻就已经搬动了，走不到这里）；
- 它付不出 → 返回它，动作栏报「自身灵气不足：<灵气名>」（新键 `actionbar.mxt.charge.insufficient_aura`，按灵气显示名填）；
- 一门都没空位（法器真的满了）→ 返回 `null`，**什么都不报**。

这样"满了"与"付不出"不再共用一个答案，而且**满的法器永远不会再报玩家灵气不足**。

### 15.3 验证

- `gradlew compileJava compileTestModJava processTestModResources`：**绿**。
- 新增探针腿（**只编译，未实跑**）：把护身玉符灌满 → `blockedAura` 返回 `null`（满＝安静）；清空玩家 qi 池后拿一件空护身玉符 → `blockedAura` 返回 `qi`（点名）。
- 文案：`actionbar.mxt.artifact.poured` 改「本次共注入灵气 %s 点」；新增 `actionbar.mxt.charge.insufficient_aura`（中英各一条，键数 +1）；`SpiritChargeService` 用的旧键 `actionbar.mxt.charge.insufficient` 保持不变。
- 文档：`docs/数据包格式.md` 长按要点、`docs/guide/play/interaction.md`、`docs/模块实现审计.md` 探针行；文档站中英 artifact 页同步。

## 16. 2026-09-21 第七次改动：认主显示玩家名，而不是 UUID

用户原话："认主显示玩家名称而不是id，参考jade的（但是不要用jade的API）"。

Jade 能做到是因为它**在服务端把数据取好再发下来**；本模组的提示框是在**客户端**画的，所以要让它显示名字，只有两条路：把名字随物品一起存下来，或者在画提示框时去查。这里两条都用，以第一条为准。

### 16.1 落点

| 位置 | 行为 |
| --- | --- |
| `ArtifactStateComponent` | 新增 `owner_name`（可选字段，`RecordCodecBuilder` 的 `optionalFieldOf`）：`(owner_uuid, owner_name, nourishment)`。老物品照旧解析（缺名字＝空） |
| `ArtifactService.refine` | 写归属时顺手写名字：`current.withOwner(uuid, PlayerNames.displayName(owner))`。**这是唯一同时拿得到"身份"和"名字"的时刻**，战利品函数也因此自动受益 |
| `util/PlayerNames`（新） | `displayName(entity)`（认主时取名字）与 `resolve(uuidString)` / `knownToServer(server, uuid)`（老物品的兜底查询）：服务端 = 在线玩家列表 → 持久化名字缓存；客户端 = 当前连接的玩家列表 → 已收到的答案 → 问服务端一次。`FMLEnvironment.getDist()` 过关后才碰客户端那半 |
| `util/ClientPlayerNames`（新） | 客户端那一半单独一个类，专用服务器永远不会加载它（`net.minecraft.client.Minecraft` 在服务端不存在，靠惰性解析只在真正调用时加载）；内含"问过的 id"与"已收到的答案（含空答案）"两张表 |
| `network/payload/OwnerNameC2SPayload`、`OwnerNameS2CPayload`（新） | 只带 UUID 的请求 + 带 `Optional<String>` 的答复；在 `NetworkManager` 按既有规矩登记（C2S 用带 handler 的 `playToServer`，S2C 在服务端只登记 codec、在客户端才带 handler），服务端处理器用 `context.reply(...)` 回包 |
| `ArtifactDescription.appendOwnership` | 认主行改成 `tooltip.mxt.artifact.owned` 带参：`state.ownerName().or(() -> PlayerNames.resolve(owner)).orElse(owner)`；**只有当这一行显示的是名字时**，F3+H 的高级行才另起一行给出 UUID；`unowned` 行不再借用同一个键（拆成独立分支） |
| `ArtifactDescription.keys` | 修掉一个隐患：它原来只看组件**根**的 contents，而认主/未认主行是"颜色标记 + 文案"两段（`literal("✔ ").append(translatable(...))`），于是这类行会返回**渲染文本**而不是翻译键——探针里那两条期望（`tooltip.mxt.artifact.owned` / `unowned`）**永远不可能通过**。现在递归找行内第一个翻译键，找不到才回落到文本 |

### 16.2 边界（有意留下的）

1. **名字只是显示，UUID 才是身份**：`isOwner`、`mxt:owned_by`、飞行与储物全都仍然只问 `owner_uuid`；玩家改名不会失去法器（行里显示的是认主当时的名字）。
2. **不查会话服务**：`sessionService.fetchProfile(uuid)`（新版本里的 `ProfileResolver`）能查到**任何**玩家（含本服从没见过的人），但那是**阻塞的网络请求**，而两个调用点——提示框（渲染线程）与包处理器（主线程）——都不该等它。服务端因此只回答"它已经知道的名字"：在线玩家列表 + `services().nameToIdCache()`（`usercache.json` 那份缓存，纯 map 查询）。这正是"认主时就把名字写下来"的理由。
3. **客户端问一次、记住答案**：`OwnerNameC2SPayload`（只带 UUID）/ `OwnerNameS2CPayload`（名字或空），客户端把答案——**包括"没有"**——缓存下来，所以一次会话每个 id 只问一次；提示框是每帧重建的，名字在下一帧自然出现，不需要主动重绘。服务端没见过的玩家回空，界面继续显示 UUID（而不是编一个名字）。
4. **非玩家主人**（脚本/战利品函数用实体当主人）：存的是这个实体的显示名（例如 `Pig`），比 UUID 可读；要更严格可以只对玩家记名字，但那样脚本认下的法器只能显示 id。
5. **本仓不依赖 Jade**：没有引用 Jade 的任何类，只是照着"名字要能在客户端读出来"这一目标另做了一套（Jade 是服务端取好数据再下发，这里是"存一份 + 缺了再问一次"）。
