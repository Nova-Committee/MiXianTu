## 2. 术语与单位

| 词 | 含义 |
| --- | --- |
| **寿元** | `SpiritStatsAttachment` 上的一对数：**剩余**（还能活多少）与**上限**（这一世一共拿到过多少）。计量单位永远是**刻**（tick），与现有存档字段一致 |
| **岁** | 只存在于**显示层**：`ticks_per_year`（服务器配置）把刻换算成"岁"给玩家看。数据包与代码里**不出现"岁"**，避免第二套单位 |
| **记账** | 这个实体受寿元约束（上限 ≥ 0）。反义是**不受限**（上限 < 0） |
| **结算** | 每隔 `settle_interval` 刻做一次：按倍率扣剩余，扣到 0 就走耗尽流程 |
| **流逝倍率** | `age_per_settle ÷ settle_interval`。两个都是整数配置项，所以倍率是精确的有理数，不需要在附件里存小数进位 |
| **耗尽** | 剩余第一次到 0 的那一刻，全流程**只发生一次** |

## 3. 账本模型：两个数 + 七条规则

### 3.1 状态

| 状态 | 编码 | 含义 | 谁会处于这个状态 |
| --- | --- | --- | --- |
| **未记账** | `total < 0`（默认 `-1`） | 从来没有被授过寿元 | 老存档里的所有实体、没开寿元的服上的所有人 |
| **记账中** | `0 ≤ remaining ≤ total` | 正常 | 播种 / `set` / `add` / 突破加寿之后；**玩家身死（转旁观者）之后也留在这里（剩余 0）** |
| **记账结束** | `remaining < 0 && total == 0` | 这一世不再受寿元约束（`NONE` 走完、非玩家生物身死被拦下、`Pre` 取消且无人续命、转世时基数为 0） | 耗尽流程走完且身体还在时 |
| **不受限** | `remaining < 0` | 与上两行同一件事的读法：**倒计时不跑** | 未记账 / 记账结束 |

**为什么用 `total == 0` 而不是新加一个 `initialized` 标志**：`-1` 已经同时表示"没数据"和"不受限"两件事，播种逻辑必须能区分"从没给过"与"给过之后关掉了"，否则耗尽过一次的实体会在下一个结算周期被重新播种、再死一次，无限循环。用一个**已有的数字**多承担一种状态（`total` 只会是 `-1` / `0` / 正数三种），比往附件里再加一个布尔字段更省——也避免"两个字段互相矛盾"的新坑。

### 3.2 规则（全部集中在一处，别在别处再算一套）

| 操作 | 未记账（`total < 0`） | 记账中（`total ≥ 0`） |
| --- | --- | --- |
| **播种**（登录 / 首次结算 / 突破） | `total = remaining = base_lifespan`（`base_lifespan == 0` 时不播种） | 不动 |
| **`set n`**（`n ≥ 0`） | `total = remaining = n` | 同左 |
| **`add +n`**（续命） | 先按 `max(base_lifespan, 0)` 起算，再两值同加 `n` | `total += n`，`remaining += n` |
| **`add -n`**（抽寿，`n > 0`） | 先按 `max(base_lifespan, 0)` 起算，再 `remaining -= n` | **只减剩余**：`remaining = max(0, remaining - n)`，**上限不动** |
| **突破**（`realm_stage.lifespan = v`） | 先按 `max(base_lifespan, 0)` 起算，再两值同加 `v` | 两值同加 `v` |
| **结算** | 不动 | `remaining = max(0, remaining - age_per_settle)` |
| **耗尽后写回** | — | `NONE` / `Pre` 取消且无人续命 / 非玩家身死被拦下 → `remaining = -1, total = 0`（记账结束）；**玩家身死 → 保持 `remaining = 0`**（寿元确实用完了；旁观者不被结算，放出来后若没人续命会再次身死）；`REINCARNATE` → `total = remaining = max(base_lifespan, 0)`，`base_lifespan == 0` 时按第一行 |

三条附带结论：

1. **上限只增不减**（唯一的例外是 `set`，它本来就重写一切），所以"寿命上限"是这一世累积的资产，抽寿扣的是余额。
2. **`set` 拒绝负值**（加载期/执行期都拒）：`-1` 不再是"设成不受限"的官方写法——想结束记账只有两条路：走完耗尽流程，或者用 `set 0` 之后等下一次结算。KubeJS 侧原来那种"`spirit().setLifespanRemaining(-1)`"从此不属于公开口径（`docs/guide/kubejs/api.md` 要改）。
3. **写入路径永不直接致死**：`add` / `set` 把剩余写到 0 时**不做**耗尽评估，只在下一次结算时判——`settle_interval` 可以配成 1 刻（＝立刻）。这样做是为了不让"致死 / 洗修为"发生在某个技能或 `CostTransaction` 事务的中间（重入与半提交风险），耗尽流程因此**只有一个出口**。
4. **`add 0` 什么都不做**（2026-09-25 实现时补的口径）：`add` 是"加减"，加零没有任何语义，**不该顺手开一个账本**。这一条不是洁癖：`realm_stage.lifespan` 求值后四舍五入到 `0` 时也走 `add(…, 0)`，而"开账在 0"正是"这一世已经用完"，下一次结算就会身死 / 转世——于是任何一档写了 `lifespan: 0`（或公式恰好算出 0.4 以下）的境界都会静默杀人。`set 0` 仍然是有效写法（那是明确要"剩余 0"），只有 `add` 的零被短路。

## 4. 数据面：来源与死因

### 4.1 `realm_stage.lifespan`（境界 → 寿元的默认换算）

| 项 | 形状 |
| --- | --- |
| 字段 | `lifespan`，可选，`NumberProvider`（与 `breakthrough_exp` 同一套：可写裸数，也可写公式） |
| 单位 | **刻** |
| 缺省 | 不写＝这一档不给寿元。用 `Optional` 而不是 `optionalFieldOf(..., new Constant(0))`，是为了让"没写"与"写了 0"在 JSON 上仍然分得开 |
| 生效时机 | **突破成功那一刻，且只加一次**：`CultivationService.attempt` 的 `result.advanced()` 分支里，紧挨着 `target.successAction().execute(...)` 与 `MinorStageService.refresh(...)`（`runtime/cultivation/CultivationService.java:92-104`） |
| 语义 | 按 §3.2 的"突破"行：两值同加（未记账时先按 `max(base_lifespan, 0)` 起算） |
| 加载期校验 | 求值结果必须是有限数；`< 0` 在加载期拒绝（负数该用 `mxt:modify_lifespan` 的抽寿，而不是"这一档减寿"） |

**为什么不做成"上限 = 这一档的值"**：那样后一档只要写得比前一档小，玩家就会凭空少一截寿元；而"每突破一档延一次寿"是单调的，写错只表现为"少加了"，不会把已有余额吃掉。要表达"这一档的基础寿元是 200 岁"就在这一档写 `lifespan` 的**增量**，链条上的和就是上限——这也正是"上限"这个数的来源，信息面板才有东西可显示。

**形状代价**：`RealmStage` 的记录已经有 18 个组件、靠三组 `MiscCodecs.pair` 压在 `RecordCodecBuilder.group` 的 16 上限下（`data/cultivation/RealmStage.java:80-113`，`AGENTS.md` §4 有这条房规）。加第 19 个字段要**把 `lifespan` 并进现有的某一对**（建议与 `passive_modifiers` 成对），JSON 键不变、`group` 仍然是 16 组。

### 4.2 `mxt:modify_lifespan`（实体行为：唯一的任意写入点）

| 字段 | 类型 | 缺省 | 含义 |
| --- | --- | --- | --- |
| `mode` | `add` / `set` | `add` | 加（可负＝抽寿）或重写账本 |
| `amount` | `NumberProvider` | 必填 | 刻数；`add` 接受负数，`set` 必须是 `≥ 0` 的有限数 |

- **宿主**：`ctx.entity()`，非 `LivingEntity` 时空操作（不报错、不记日志——与 C11 的口径一致：漏写行为＝静默空操作）。
- **总开关关着也照写**：它只是往账本上记数，流不流逝由总开关决定（§5.1）——于是数据包可以在任何服上安全地写"续命"，服主开不开是另一个开关。
- **执行**：走 `LifeSpanService` 的公开入口（§8.2），**不自己碰附件**。
- **`set` 的负值**：加载期拒绝（`.validate(...)`，与"空表 / 空列表用 validate 拒绝"同一口径）。
- **配方**：它是普通 `EntityAction`，所以丹药（`pill_binding` 的行为）、诅咒、符箓、阵法、天劫时间线、KubeJS 全能调它；不需要为"续命"另造一种形状（这正是审计里说的"一个反向 `Cost`"要解决的问题——见 §11 为什么不选 `Cost`）。
- **注册**：`registry/MxtEntityActions.java` 加一行 `MODIFY_LIFESPAN`，类放 `data/action/builtin/entity/ModifyLifespanAction.java`。

### 4.3 伤害类型 `mxt:lifespan`（**非玩家生物**的死因）

> 玩家走的是"转为旁观者"（§5.2），**不经过伤害、不经过死亡事件**；这个伤害类型只服务非玩家生物（灵兽、妖兽、NPC…），让它们能按原版的规矩死掉（掉落、死亡事件、别的模组的保命效果都照常）。

| 项 | 内容 |
| --- | --- |
| JSON | `src/main/resources/data/mxt/damage_type/lifespan.json`（本体第一次自带伤害类型） |
| 文案 | `death.attack.mxt.lifespan`（中英各一份，走原版 `message_id` 惯例） |
| 标签 | 加进本体自带的 `data/mxt/tags/damage_type/no_bonus.json`（原本只有 `minecraft:out_of_world`，现在多这一条）——于是它**不被元素管线塑形**，`DamageCalculationService.bypasses(source)` 为真，直接 `hurtServer`（`runtime/damage/DamageCalculationService.java:53-79`） |
| 致死 | `DamageCalculationService.deal(null, entity, Float.MAX_VALUE, Optional.of(lifespanType), null)`：**走原版伤害与事件链**，于是不死图腾、`LivingIncomingDamageEvent`、其它模组的保命效果都能拦（这正是我们要的"可被内容拦截"） |
| 归因 | 无攻击者（`attacker = null`）；`Scale` / `exhaustion` 等按原版习惯留空 |
| 兜底 | 数据包把 `mxt:lifespan` 删掉／覆盖成别的东西时，解析失败要退回 `minecraft:generic_kill` 并记一条 warning——**不能因为一个数据包错误就让"寿元耗尽"变成不死** |
| 续命 | `Pre` 事件才是"官方续命口"：在 `Pre` 里写正值就是续命成功（§5.4）；伤害链只是第二道可被拦截的关口 |

### 4.4 （附带，可去掉）两个只读公式变量

| 名字 | 值 |
| --- | --- |
| `lifespan_remaining` | 剩余刻数；未记账/不受限答 `NaN` |
| `lifespan_total` | 上限刻数；同上 |

- 注册方式与 `SecretRealmVariable` 同一套（`registry/MxtFormulaVariables.java`）：从 `context.caster()`（退 `player()`）读实体，读的是**只读**路径，未记账答 `NaN` 而不是 0，好让条件能区分"没账本"与"账本是 0"。
- **不做**比较型 `entity_condition`（例如"寿元低于 X 才能用"）：那要新增一个条件类型，属于另开一稿；暂时用公式 + `mxt:js` 表达。
- 这一项是"顺带便宜拿下"的附加项：让 `mxt:modify_lifespan.amount` 与丹药配方能写"补到上限的一半"这类公式。不要它就从 §12 的清单里划掉，不影响 A2 的闭环。

## 5. 运行时：结算、耗尽、转世

### 5.1 结算（性能与倍率都在这里）

```
LifeSpanEventBridge.onEntityTick(Post):
    if (客户端) return
    if (!enabled) return                                       // 总开关：关掉就一行都不做（连附件都不读）
    if (level.getGameTime() % settle_interval != 0) return     // 全局一次取模，不给每个实体记计数器
    LifeSpanService.settle(entity)

LifeSpanService.settle(entity):
    if (!enabled) return                                       // 服务自己也守一遍：探针/附属直接调用时同一口径
    if (entity 是 ServerPlayer 且 isCreative() 或 isSpectator()) return
                                                               // 创造与旁观不在生存规则里；旁观也正是"身死"之后的形态
    spirit = entity.getExistingData(SPIRIT_STATS)              // 只读：没账本的实体到此为止（P3）
    if (spirit == null || !(entity instanceof LivingEntity)) return
    if (spirit.total() < 0 && base_lifespan > 0) seed(spirit)   // 有账本却没给过 → 按凡人基数起算
    if (spirit.remaining() < 0) return                          // 不受限
    before = spirit.remaining()
    spirit.setRemaining(max(0, before - age_per_settle))
    warnIfCrossed(spirit, before)                               // §7.2
    if (spirit.remaining() > 0) return
    expire(entity, spirit)                                      // 唯一的耗尽出口
```

- **总开关**（`enabled`，默认关）：关掉时 `settle` 第一行就返回——不播种、不扣、不判、不提醒、不发事件，**连附件都不读**，这块开销归零。写入路径（行为 / API / 命令）**照常记账**：值留在存档里，开关打开后从那一刻接着跑，**不补扣关闭期间的时间**。面板那一行在关闭时也不显示（§7.1）。
- **周期与倍率**：`settle_interval`（默认 20 刻）与 `age_per_settle`（默认 20 刻）之比就是流逝倍率；`age_per_settle = 0` ＝"只结算、不老化"（＝不老）。两个都是整数，**不需要在附件里存小数进位**，倍率也永远不会漂移。
- **只在线的刻**（拍板 ③）：倒计时挂在实体 tick 上，玩家下线就没有 tick，所以**离线不流逝、登录不补扣**。这一条要写进文档，别让服主以为它是日历时间。
- **只在服务端**：`LifeSpanService` 一律服务端调用；客户端只读同步过来的附件画面板。
- **同步**：每次结算写值 → `markDirty()` → `MxtAttachments.flushDirtyAttachments` 同步一次（`registry/MxtAttachments.java` 的 `entity(...)` 路径）。默认 20 刻结算一次＝**每人每秒一个包**，可以接受；`settle_interval = 1` 会变成每刻一个包，工具提示里要写清"越小越精细、开销越大"。
- **读取时机**：每次结算读一次配置（不缓存、不加回调），所以改配置**下一次结算立刻生效**，不需要重启，也不需要 `/reload`。

### 5.2 耗尽：三条分支（`on_expire`）

```
expire(entity, spirit):
    Pre event（可取消，带 entity + spirit）
    if (cancelled):
        if (spirit.remaining() > 0) return          // 监听者续了命 → 账本照旧，倒计时接着跑
        closeAccount(spirit)                        // remaining = -1, total = 0
        return
    switch (on_expire):
        NONE:        closeAccount(spirit)
        DEATH:       if (entity instanceof ServerPlayer player):
                         player.setGameMode(GameType.SPECTATOR)     // 玩家：身死＝转为旁观者
                         message(player, "message.mxt.lifespan.deceased")
                         // 账本保持 remaining = 0（寿元确实用完了，不是"不受限"）；
                         // 结算对旁观者直接返回（§5.1），所以不会每个周期重放这一次身死
                     else:
                         deal(Float.MAX_VALUE, mxt:lifespan)        // 非玩家生物：按原版规矩死
                         if (entity.isAlive()) closeAccount(spirit) // 被拦下/无敌 → 记账结束，不重试
                         + 一条 warning 日志
        REINCARNATE: resetCultivation(entity)       // §5.3 清单
                     total = remaining = max(base_lifespan, 0)
                     base_lifespan == 0 → closeAccount(spirit)
    Post event（带 outcome()）
```

三条分支共有的口径：

- **不会每周期重放**：`NONE` 与转世把账本写成"记账结束"或新值；非玩家 `DEATH` 也结束记账；玩家的 `DEATH` 则把形态换成旁观者，而结算对旁观者直接返回。任何一条分支走完都不存在"每 tick 判一次耗尽"的循环。
- **`DEATH` 对玩家＝转为旁观者**（拍板 ⑥）：不经过死亡事件、不掉物品、不插重生点、不用死亡文案——改成聊天栏一句 `message.mxt.lifespan.deceased`。**不记原来的游戏模式**：要放人复活（管理员 `/gamemode`，或内容包在 `LifeSpanEndEvent.Post` 里自己动手）由调用方自己负责。放出来之后账本仍是 `0`，**没有人续命就会在下一次结算再次身死**——这就是"寿元尽了就得有人续命"的硬口径。
- **非玩家生物照原版死**：`mxt:lifespan` 致死量走伤害链（§4.3），掉落、死亡事件、别的模组的保命效果都照常；被拦下就结束记账、不重试（否则就是无限循环的致死尝试）。
- **`NONE` 不是"缺口没闭"**：它发事件、结束记账，之后想怎么处理（变成魂体、传给继承人、扣一笔资源）都由监听者在 `Post` 里做——基座给的默认答案是 `DEATH`，不是 `NONE`。
- **转世不经过死亡**（拍板 ⑤ 的读法）：不致死、不掉落物品、不触发死亡事件，当场洗掉修为与境界、寿元回基数。想把"转世"做成"真的死一次"的整合包把 `on_expire` 设成 `NONE`，在 `LifeSpanEndEvent.Post` 里自己致死即可（那时死亡掉落、重生点都归原版管）。
- **不受限之后仍可被救回**：`mxt:modify_lifespan` / 命令 / 事件里的 API 写一个正值，账本立刻回来（`total ≥ 0`），倒计时重新开始。所以"记账结束"不是终点，而是"等一个明确的值"。

### 5.3 转世重置清单（拍板 ⑤ + ⑦）

**每一行都是一个配置开关**（「转世」页，§6.2），默认值就是拍板 ⑤ 的那一条策略；实现里 `reincarnate` 按顺序读这些开关，最后统一重算技能授予与被动属性。

| 动什么 | 默认 | 开关 | 依据 |
| --- | --- | --- | --- |
| 先死一次（掉落 + 死亡文案 + 重生点） | 关 | `kills` | 拍板 ⑦；开着就是"真的死一遍再洗回凡人" |
| 境界与修为进度 | 清空 `CultivationAttachment` 的 `realm_stages` / `cultivation_progress`（`resetCultivation()`），于是回凡人、可以重新突破第一档；同时停打坐、清 `cultivate_action` 与打坐冷却 | **清** | `reset_cultivation` | `attachment/CultivationAttachment.java` |
| 子境界层数记录 | 清 `minor_stage_records` | **清** | `clear_minor_stages` | A1 的层数门槛是"只增不减"的记录，转世后不清就会让"曾达到过 N 层"永久为真；转世＝那一世没了，记录也该没 |
| 进行中的天劫 | 清 `TRIBULATION` 附件（`TribulationService.cancel(data)`：不发成功也不发失败） | **中断** | `cancel_tribulation` | `runtime/tribulation/TribulationService.java` |

| 灵根 / 体质（含启用停用状态） | **保留** | **保留** | `keep_spirit_roots` | 拍板 ⑤ |
| 功法与技能水平 | **保留**（"记忆还在，道基重来"） | **保留** | `keep_techniques` | 拍板 ⑤ + §13 开放项 2 |

| 技能授予与被动属性 | 无论开关怎么配，重置完都跑一次 `CultivationGrantService.recalculate(entity, spirit, abilities)` 与 `PassiveAttributeService.reconcile(entity)`：境界给的收回，灵根 / 体质 / 功法给的重新加上 | 总是 | — | `runtime/cultivation/CultivationGrantService.java`、`runtime/ability/PassiveAttributeService.java` |

### 5.4 事件的新口径

| 事件 | 变化 |
| --- | --- |
| `LifeSpanEndEvent.Pre` | 形状不变（`entity()` / `spirit()`），**语义变**：取消之后不再无条件变成永久不受限——事件里写了正值（用 `spirit()` 或服务 API）就是"续命成功"，倒计时从新值继续；什么都没写才结束记账 |
| `LifeSpanEndEvent.Post` | 加一个 `outcome()`（`NONE` / `DEATH` / `REINCARNATE`），让监听者知道走的是哪条分支（KubeJS 那侧是通用事件对象，方法名会照常可见） |
| `LifeSpanRebirthEvent`（新，2026-09-25 追加） | **显式转世**专用的一对：`Pre`（可取消，取消＝整件事不做）/ `Post`。只由 `LifeSpanService.reincarnate` 这个公开入口发，所以 `mxt:reincarnate`、`/mxt lifespan reincarnate`、KubeJS `MxtLifespan.reincarnate` 与 Java 附属都覆盖它；耗尽那条路仍只发 `LifeSpanEndEvent`。**为什么不在耗尽路上也发**：那里的账已经花光，`Pre` 一旦可取消，取消就只能落成"关闭账本"，否则每次结算都会再试一次——把两种来因分开，比给同一个事件加两套取消语义干净 |
| 新增？ | **不加**"每次结算"事件：结算是最热的一行，事件留给"耗尽"这个真正的时刻 |

### 5.5 边界与不变量

- 非 `LivingEntity`（掉落物、箭、船…）：不结算（`settle` 在类型判断处返回）。
- **已经死掉的实体不结算**：它只剩死亡动画那几刻，既不该"变老"，也不该在尸体上判一次耗尽（实现里是 `settle` 的一道 `isAlive()` 门）。
- **创造模式与旁观模式不结算**：它们不在生存规则里；旁观也正是"身死"之后的形态，于是身死过一次的玩家天然不再被反复处理。想把某个玩家放出来（管理员 `/gamemode` 或内容包在 `Post` 里动手）之后，**没有续命就会再次身死**。
- **总开关关闭时不结算**：连附件都不读，也不播种 / 不提醒 / 不发事件；写入路径照常记账（§5.1）。
- 客户端：一律返回"没变化"，不写日志。
- `SPIRIT_STATS` 仍然 `copyOnDeath`：**死亡不重置账本**（凡人的一世由耗尽流程结束，而不是由任何一次死亡结束）；转世重置发生在耗尽流程内部，与死亡无关。
- 数值：`settle` 读到的任何非有限值都按 0 处理并记一次 warning（与全仓"运行期遇到 NaN/Infinity 按 0"一致）。
- **寿元不进 `resource` 系统**：resource 是数值（回复/上限/资源条），寿元是有终点的生命周期，语义不同；面板单独一行，不做资源条。

## 6. 配置系统（本章是重点）

### 6.1 原则：什么进配置、什么进数据包

| 判据 | 归配置 | 归数据包 |
| --- | --- | --- |
| 它是"这个服务器怎么运转"还是"这个世界里是什么"？ | 运转 → 配置 | 世界 → 数据包 |
| 它需要按存档／按整合包替换吗？ | 不需要（安装级）→ 配置 | 需要 → 数据包 |
| 它是一张**表**（境界 → 寿元、丹药 → 续命量）吗？ | 表永远不进配置 | 数据包 |
| 换一个值会改变已有存档里每个实体的命运吗？ | 会（起点、倍率、后果）→ 配置，且文档写明 | 不会 → 数据包 |

由此得到本稿的划法：**总开关、起点、节奏、倍率、后果、提醒、显示换算、转世保留清单** 进配置；**每一档加多少寿、哪种丹药续多少** 进数据包。配置里**不出现**任何具体世界观数字。

### 6.2 新增「寿元」页与「转世」页（`MxtServerConfig.Lifespan` / `.Reincarnation`）逐项

**「寿元」页**：`public final Lifespan lifespan = new Lifespan();`，类名 `Lifespan extends AutoInitConfigCategoryBase`，`super("lifespan", "config.mxt.server.lifespan")`；页顺序放在 `cultivation` 之后、"转世"之前（与"修炼 → 寿元 → 转世 → 符箓"的读法一致）。**第一项就是总开关**，服主打开配置页先看到"这条路开不开"，再看到具体数值。

| # | key | 类型 | 默认 | 范围 | 名字键 | 工具提示要点 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | `enabled` | `BooleanEntry` | **`false`** | — | `config.mxt.server.lifespan.enabled` | **总开关**：关＝整条寿元线不运转（不结算、不播种、不耗尽、不提醒、面板也不显示那一行），写入照常记账但不流逝；开＝账本从那一刻起接着跑，**不补扣关闭期间的时间**。默认关，所以升级后行为不变 |
| 2 | `base_lifespan` | **`LongEntry`** | `0` | `0 .. 1_000_000_000_000` | `config.mxt.server.lifespan.base_lifespan` | **总开关打开后**，玩家首次登录（以及"有账本却从没被给过"的实体首次结算）拿到的寿元，按刻计；**0＝不自动播种**（只有数据包 / 命令明确给过的实体才受约束）。转世后也重算到这个值 |
| 3 | `settle_interval` | `IntegerEntry` | `20` | `1 .. 72_000` | `config.mxt.server.lifespan.settle_interval` | 每隔多少刻结算一次；越小越精细、开销与同步越多 |
| 4 | `age_per_settle` | `IntegerEntry` | `20` | `0 .. 72_000` | `config.mxt.server.lifespan.age_per_settle` | 每次结算扣掉多少刻寿元；与结算周期之比就是流逝倍率（20/20＝常速，20/40＝半速，40/20＝双速），**0＝不老** |
| 5 | `on_expire` | `EnumEntry<LifespanOutcome>` | `DEATH` | `NONE` / `DEATH` / `REINCARNATE` | `config.mxt.server.lifespan.on_expire` | 寿元归零时做什么（`DEATH` 名字写「身死」，工具提示里说清"玩家会被转为旁观者，非玩家生物直接死亡"）；`nameProvider` 走 `config.mxt.server.lifespan.on_expire.<值小写>` |
| 6 | `warning_fraction` | `DoubleEntry` | `0.1` | `0.0 .. 1.0` | `config.mxt.server.lifespan.warning_fraction` | 剩余降到上限的这个比例时提醒一次（跨过阈值那一次，不是每周期都提醒）；**0＝不提醒**。它只在总开关打开、账本真的在跑之后才有机会触发 |
| 7 | `ticks_per_year` | `IntegerEntry` | `24_000` | `1 .. 1_000_000` | `config.mxt.server.lifespan.ticks_per_year` | 人物面板与提醒把刻换算成"岁"的除数（24000 刻＝一游戏日）；填 1 就直接显示刻 |

**总开关与 `base_lifespan` 不重复**，两者答的是不同的问题：

| 问题 | 由谁回答 |
| --- | --- |
| 这个服要不要寿元这套规则？ | `enabled`（默认关） |
| 开了之后，没被显式给过寿元的人要不要自动拿到一个起点？ | `base_lifespan`（0＝不自动给，只认数据包/命令写下的值） |

所以四种组合都是有意义的，例如「`enabled = true` + `base_lifespan = 0`」＝只让内容包点名给寿元的那些实体受约束（灵兽、NPC、被诅咒的玩家），凡人不受影响。

**「转世」页**（`MxtServerConfig.Reincarnation`，`super("reincarnation", "config.mxt.server.reincarnation")`，放在「寿元」之后、「符箓」之前）：拍板 ⑦ 把 §5.3 的保留清单整个做成开关，8 项全是 `BooleanEntry`，**默认值合起来就是拍板 ⑤**（不改配置＝第一轮设计的行为）。

| # | key | 默认 | 工具提示要点 |
| --- | --- | --- | --- |
| 1 | `kills` | `false` | 开＝转世前先走一遍死亡流程（掉落、死亡文案、重生点），再洗回凡人；关＝不掉物品、不插重生点、不触发死亡事件 |
| 2 | `reset_cultivation` | `true` | 清空境界、修为进度、打坐状态与打坐冷却；境界给的被动属性与子境界技能随之收回 |
| 3 | `clear_minor_stages` | `true` | 清空"曾经达到过第几层"的记录；不清则把层数当门槛的内容在转世后仍认为门槛已达到 |
| 4 | `cancel_tribulation` | `true` | 中断进行中的天劫：不发成功、也不发失败 |
| 5 | `clear_resources` | `false` | 清空该实体的全部资源数值（下次读取时按定义重新初始化）。默认不动——哪个资源算"修为"是数据包的事 |
| 6 | `keep_spirit_roots` | `true` | 保留灵根、体质与它们的启用 / 停用状态 |
| 7 | `keep_techniques` | `true` | 保留功法与技能水平（"记忆还在，道基重来"） |
| 8 | `keep_soul` | `true` | 保留业力 / 心魔 / 神魂强度 / 神识范围 |

第 6～8 项是"保留"口径、第 2～5 项是"清掉"口径，混着读是刻意的：前者回答"身体还是什么"，后者回答"这一世做过什么"，一个服主想调哪一种都能一眼找到。**技能授予与被动属性的重算不受开关控制**（§5.3 最后两行），因为那不是策略而是正确性：境界给的必须在境界没了之后收回。

实现细节（照抄现有页的写法，`config/MxtServerConfig.java`）：

- 每个条目都要 `.key("…")` + `.tooltip("config.mxt.server.<页>.<项>.tooltip")`，**名字键省略 `.tooltip`**；`LongEntry` 用 `.range(long, long)`（本仓库第一次用 `LongEntry`，它是 Jupiter 自带类型，与 `IntegerEntry` 同一族）。
- 数值条目的 `.range(...)` **同时就是解码校验**（`AGENTS.md`／类注释里的既定口径：下游不再 clamp 一遍）。`age_per_settle` 的 `0` 是合法值，别把它当"没填"。
- 枚举要 `.nameProvider(value -> Component.translatable("config.mxt.server.lifespan.on_expire." + value.name().toLowerCase()))`。
- 枚举定义放在 `MxtServerConfig` 里（与 `BackMode` / `ClaimLinkage` / `BeltMode` 同级）：`public enum LifespanOutcome { NONE, DEATH, REINCARNATE }`。
- 命令别名开关 `commands.lifespan`（§8.1）照现有的 18 个写法加一行。
- **不动 `dataFixer`**：新页是新 key，没有历史写法要迁；现有的两条规则（`friends → compat`、整路径削成短键）继续管用。


### 6.4 读写路径、权限与热生效

| 项 | 口径 |
| --- | --- |
| 文件 | `./config/mxt/mxt-server.json`（`MxtServerConfig` 的既有路径） |
| 谁能改 | `MiXianTu` 里注册的是 `ConfigManager.getInstance().registerServerConfigHandler(MxtServerConfig.INSTANCE, PermissionChecker.IS_OPERATOR)`——**管理员**；单机由整合包作者/玩家在配置界面改 |
| 界面 | 客户端 `ConfigSelectScreen` 里多两个页：「寿元」与「转世」；服务端配置由 Jupiter 同步给客户端显示（读到的值以服务端为准）。面板那一行因此读得到 `enabled` 与 `ticks_per_year` |
| 热生效 | **「寿元」的 7 项都在下一次读取时生效**：`enabled` / `settle_interval` / `age_per_settle` / `on_expire` / `ticks_per_year` / `warning_fraction` 在结算与显示时各读一次（关掉总开关，下一次 tick 就停）；`base_lifespan` 只影响**将来的播种与转世重算**，**不回头改写已经记账的实体**（改小它不会让老玩家当场暴毙，这条要写进工具提示）。**「转世」的 8 项只在真正转世的那一刻读一次**，所以改它不影响任何已经发生过的事 |
| 不加回调 | 不用 Jupiter 的 `callback(...)` 去"改配置时补算"——那会让"改了配置"变成一次隐式批量写入，行为不可预期 |

### 6.5 明确**不**放进配置的东西

| 想法 | 为什么不 |
| --- | --- |

| ~~转世的保留清单（保留功法吗、清哪些资源）~~ | 拍板 ⑦ 推翻：**整个清单做成「转世」页的 8 个开关**（§5.3）。第一轮的理由是"不给所有服开一份策略矩阵"，但保留清单的每一项都是"这个世界怎么运转"（见 §6.1 的判据），而且开关只在那一个时刻读一次、不构成矩阵 |

## 7. 玩家可见面

### 7.1 人物信息面板一行

- 注册点：`screen/information/InformationManager.java` 的静态块，`register("lifespan", Side.CULTIVATION, …)`，插在 `realm` 与 `cultivation_progress` 之间（**行序＝注册顺序**）。
- 显示：`剩余 / 上限` 按 `ticks_per_year` 换算成"岁"（一位小数，与 `health` 那一行的 `%.1f` 风格一致）；`remaining < 0` 时显示「不受限」。
- **总开关关闭（或这一档没启用）时不显示这一行**：那一行等于"系统不存在"，不给玩家一个看不懂的 0；已经变成旁观的玩家仍能看到它（账本上写着 `0 / 上限`，正好说明"寿元已尽、等着有人续命"）。
- 数据来源：同步过来的 `SPIRIT_STATS` 附件（`ShouldSyncAttachment`），所以面板照常每 `information.refresh_interval`（客户端配置，默认 20 刻）重建一次即可。
- 边界：只对**玩家**显示（面板本来就只描述本地玩家），非玩家实体的寿元不上界面。

### 7.2 低于阈值时提醒一次

- 前提：总开关打开、这一档正在倒计时。
- 触发条件：**任何一次让剩余下降的写入跨过阈值时**——结算、`add` 负数（抽寿）、`set` 到更小的值，规则统一是 `before > threshold && after <= threshold`（`threshold = ceil(total × warning_fraction)`）。不需要"已提醒过"的标志位：把剩余抬回阈值之上（续命）之后，下一次跨过会再提醒一次，这正是想要的语义；不判"跨过"的话，抽寿一次扣到底就会漏掉这句提醒。
- 出口：`ServerPlayer` 的动作栏一句 `actionbar.mxt.lifespan.warning`（`sendSystemMessage(component, true)`）；非玩家不提醒。
- `warning_fraction = 0` 关闭；`total ≤ 0`（不受限）不提醒。

## 8. 命令、Java API 与 KubeJS

### 8.1 `/mxt lifespan`（已采纳，见 §13 开放项 1）

| 节点 | 行为 |
| --- | --- |
| `/mxt lifespan` / `/mxt lifespan get [<targets>]` | 报每个目标的「剩余 / 上限」（无账本报"未记账"）；不写目标读执行者自己 |
| `/mxt lifespan set <targets> <ticks>` | 重写账本（两者同值），`ticks ≥ 0` |
| `/mxt lifespan add <targets> <ticks>` | 加减（负数＝抽寿） |
| `/mxt lifespan reincarnate <targets>` | 当场跑「转世」页那份重置清单并重开账本（2026-09-25 追加，见 §13 开放项 11） |

- 全部写节点 `requires(ServerCommandManager::mayChange)`（权限判断只有那一份）。
- 参数：目标是 `EntityArgument`；`ticks` 用 Brigadier 的 `LongArgumentType`（原版这一档没有 `LongArgument` 类，而刻数会超过 int，所以不用 `IntegerArgumentType`）。
- 顶层别名 `/lifespan` 一起加（现有 18 个别名全都有，保持一致）：`config.mxt.server.commands.lifespan[.tooltip]` 两个 lang 键，`docs/guide/play/commands.md` 的「别名一共 18 个」已改成 19。
- 它不是闭环的必需品（行为 + API 已经够用），但在服上"给某个人续一次命"很实用，探针也能借它做一次端到端验证。

### 8.2 服务 API（`runtime/cultivation/LifeSpanService`）

| 方法 | 说明 |
| --- | --- |
| `long remaining(Entity)` / `long total(Entity)` | 只读；未记账 / 不受限答 `-1`（不创建附件） |
| `Result set(LivingEntity, long ticks)` | `ticks ≥ 0`；写账本（两者同值）。**总开关关着也照写**（只记账不流逝） |
| `Result add(LivingEntity, long ticks)` | 正数续命（两值同加）、负数抽寿（只减剩余，见 §3.2）；同上，关着也照写 |
| `boolean seed(LivingEntity)` | 按 `base_lifespan` 播种，返回是否写了值（登录与结算共用）；总开关关着时不播种 |
| `boolean settle(Entity)` | 结算一次（bridge 与探针共用；探针靠它做精确数字断言）；**总开关关着、创造 / 旁观、没账本时直接 `false`** |
| `Result reincarnate(LivingEntity)` | 走一遍 §5.3 的重置清单（按「转世」页的开关），四个入口调的是同一个方法：数据包行为 `mxt:reincarnate`、`/mxt lifespan reincarnate`、KubeJS `MxtLifespan.reincarnate`、Java 附属自己的触发器。发 `LifeSpanRebirthEvent.Pre`（可取消＝整件事不做，返回 `Result.refused(CANCELLED)`）与 `Post`；**总开关关着也照做**（它是一次明确的裁决，不是时间在流逝），**不发耗尽事件** |
| `Component display(long remaining, long total, int ticksPerYear)` | 面板那一行与动作栏提醒共用的显示组件（剩余为负读作「不受限」） |
| `Result` + `Failure` | 沿用房规：失败用结果记录，不用异常。最终只有 `SERVER_ONLY` / `INVALID_VALUE` 两个取值——`NOT_LIVING` 没有留下：`set` / `add` 的形参就是 `LivingEntity`，非生物在编译期就进不来 |

`SpiritStatsAttachment` 上加：`lifespanTotal()`、`setLifespan(long remaining, long total)`（两值一起写，长度校验与现在的 `remaining >= -1` 同口径）。

### 8.3 KubeJS 全局 `MxtLifespan`

### 9.3 需要真玩家、探针覆盖不到的部分（报告里要明说）

- **阈值提醒**：动作栏那一句只在跨过阈值的那一次出现。
- **`/mxt lifespan`**（若采纳）：四条子命令的反馈文案与权限。

## 10. 与现状的差异（会改变行为的部分，逐条）

| # | 变化 | 影响面 |
| --- | --- | --- |
| 1 | `Pre` 取消不再是"永久不受限"，而是"看有没有写下正值" | KubeJS 脚本与附属若依赖旧语义，行为会变；文档同步 |
| 2 | 不再为每个实体创建 `SPIRIT_STATS` 附件（`getData` → `getExistingData`） | 老存档里已经被塞上的空附件**不会**被清掉（可以留一条 `/mxt` 维护命令，或不管）；新存档不再产生 |
| 3 | 附件新增 `lifespan_total`（宽容可选，老存档读作 `-1`） | 存档格式向后兼容（读得进来、不报错）。但要注意**语义**：一个只写了正值 `lifespan_remaining`、没有 `lifespan_total` 的老存档，按 §3.1 读作**未记账**（上限 `-1`），所以它会被 `base_lifespan` 重新播种、而不是接着那个数倒计时。未发布阶段的旧值只可能由 KubeJS 脚本写下，属可接受；要保住它就在 `LifeSpanEvent` 或首次登录前用 `set` 写一次 |
| 4 | 新增伤害类型 `mxt:lifespan`，并写进本体的 `mxt:no_bonus` 标签文件 | 用 `replace: true` 覆盖该标签的包要自己把这一条加回去；它只服务**非玩家生物** |
| 5 | `realm_stage` 多一个可选字段（并组，JSON 键不变） | 老包不受影响；编辑器 schema 要重生成 |
| 6 | 新增服务器配置页「寿元」7 项（**总开关 `enabled` 默认关**，`base_lifespan` 默认 0）与「转世」8 项（默认值合起来＝拍板 ⑤） | **默认不改变任何现有行为**：不结算、不播种、不老化、不提醒、面板不显示那一行；转世的默认策略与第一轮设计一致 |
| 7 | 新增 `mxt:modify_lifespan`、KubeJS `MxtLifespan`、`/mxt lifespan` 与别名 `/lifespan`（别名 18→19） | 新增能力，不改老路径 |
| 8 | 转世会清空 `minor_stage_records` | 用 A1 的 `min_minor_stage` 门槛的包在转世后门槛会重新"没达到过"（§13 开放项 7） |

## 11. 明确不做 / 推迟

| 想法 | 为什么不做 |
| --- | --- |
| **离线补扣**（登录按世界时间补算） | 拍板 ③；补扣要处理"补到负数时怎么死、在登录的哪一步死"，收益不抵复杂度。要日历时间的服可以把 `settle_interval` / `age_per_settle` 调快 |
| **用反向 `Cost`（负灵气＝得寿元）当生产者** | `Cost` 的语义是"扣"：`plan` 要断言付得出、`commit` 要写负号、失败码要为"负消耗"另立一套。审计里那三个候选形状，**实体行为**是最干净的一个（它本来就是"对实体做一件事"的通用通道） |
| **接回魂体流程**（`SoulService.transfer` 仍被 `SoulEventBridge` 停用） | 转世按拍板 ⑤ 是"当场洗修为"，不产生魂体实体；魂体是另一条独立的事（它连渲染都留给内容），不该被 A2 顺手拉起来 |
| **寿元做成资源（`resource` / 资源条）** | 语义不同（生命周期 vs 数值），而且资源没有"耗尽后果"这回事 |
| **`entity_condition` 比较寿元** | 要新增条件类型，属另一稿；先用公式变量（§4.4）+ `mxt:js` |
| **常驻 HUD 元素** | 拍板 ④ 只要面板一行 + 阈值提醒；HUD 元素（可拖动框架）随时能后加，不占本稿 |
| **每次结算发事件** | 最热的一行不该有事件总线 |
| **按堆叠 / 按物品记寿元** | 寿元是实体属性，与物品无关 |
| **身死＝真的死一次**（致死伤害 + 掉落 + 重生点） | 拍板 ⑥ 定的是"玩家转旁观者"：不掉物品、不填死亡文案，玩家还能留在世界里看（也便于服主/内容包复活）。想要"死一次"的包把 `on_expire` 设 `NONE`，在 `LifeSpanEndEvent.Post` 里自己致死 |
