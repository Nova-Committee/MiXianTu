> **用途**：把「一只生物停在另一只生物身上（灵宠站肩是最常见的一种）」做成基座能力，并关掉
> [`audit/基座缺口审计.md`](audit/基座缺口审计.md) 的 **B6**。

> （`build/moddev/artifacts/minecraft-patched-26.1.2.99-sources.jar`，下文行号都出自它）；参考实现是
> **另一个仓库** `E:\Java\IceAndFire-CE`（只读，未编译未运行，下文行号同样给出）。
> **状态**：**基座 + 附属契约已落地**（2026-09-27）。
> 第一轮（基座）：附件、座位点、下肩策略与服务器配置。第二轮（入口，§9）：`api/Perchable` 与
> `PerchService.perch(生物, 载具)`，**座位由乘客自己回答、本体不提供实体类**；数据包 / 命令 / 脚本的

## 0. 一句话

B6 说"基座没有肩挂设施"，对；但**缺口比它写的小**：平台已经有"乘客座位"这一整套机制，玩家只是**唯一一个
有载具身份却没有座位表的类**。所以本轮不改任何数据形状，只做四件事：一个记录偏移的附件、一个让座位点
生效的 mixin、一个写/清记录的服务、一条下肩策略（服务器配置）。渲染层、新 payload、姿态动画**都不需要**。

## 1. 现状复核（对着 HEAD）

### 1.1 B6 当时写的

- **缺什么**：基座没有任何"生物挂在玩家肩上"的设施。
- **已核事实**：`bi_entity_action.mount` 的语义是 `ctx.actor().startRiding(ctx.target())`，把 actor 写成生物、
  target 写成玩家，生物只能成为玩家身上的**普通乘客**（原版座位与碰撞箱位置）；玩家侧唯一的挂载渲染层
  画的是 `ItemStack`（`render/accessory/BackWeaponRenderer.java:61` 走 `submitItem`）；座位附件只长在载具实体上
  （`runtime/artifact/FlyingSwordEntity.java:219-228`）。
- **需要补全的内容**：一条生物挂到玩家身上的新通道 —— 附件（或给 `mount` 加座位参数），加上**玩家侧的实体
  渲染层或乘客附件**。

### 1.2 本轮改正三处

| # | B6 的说法 | 复核结果 |
|---|---|---|
| 1 | 「需要**玩家侧的实体渲染层**」 | **不需要。** 肩上那个生物是一个**真实乘客**，它在实体列表里、有自己的同步坐标，每个客户端照常用自己的渲染器画它。26.1.2 的 `EntityRenderDispatcher` 全仓没有"渲染乘客"这一段（grep `renderPassengers` / 乘客遍历 = 0 命中），乘客不是由载具渲染的。ICF 的做法也印证这一点：它**没有任何玩家侧渲染层** |
| 2 | 「`mxt:mount` 方向相反，无法复用」 | **只对技能类型 `mxt:mount`（法器载具）成立。** 同名的 bi-entity action 是 `actor.startRiding(target)`（`registry/MxtBiEntityActions.java:23`），actor=生物、target=玩家**方向正好**，今天就已经能用——它缺的不是方向，是**座位点** |
| 3 | 「生物只能成为玩家身上的普通乘客（原版座位与碰撞箱位置）」 | **准确值**：玩家的座位点兜底是 `(0, 1.8, 0)`，即**玩家的头顶**（见 §2.1）。而且玩家默认**只能载 1 个**乘客（`canAddPassenger` = `passengers.isEmpty()`，`Player` 未覆盖）。所以今天写 `mxt:mount` 的观感是"灵宠站在你头上"，不是"挂在肩上" |

另外补一条 B6 没提但更根本的：**原版鹦鹉那套肩挂机制无法复用**（见 §2.3），它不是"挂载"而是一个
**存储槽**，而且只画鹦鹉。

## 2. 平台机制（26.1.2 源码证据）

### 2.1 乘客的位置是怎么算出来的

```
Entity#rideTick()                                    Entity.java:2307-2317   ← 由关卡对每个乘客调用
  ├─ setDeltaMovement(Vec3.ZERO)
  ├─ tick()（发 EntityTickEvent.Pre/Post）
  └─ if (isPassenger()) getVehicle().positionRider(this)
Entity#positionRider(passenger, move)                Entity.java:2325-2329
  ├─ position = getPassengerRidingPosition(passenger)          = 载具位置 + 座位点
  ├─ offset   = passenger.getVehicleAttachmentPoint(vehicle)   = 乘客自己的 VEHICLE 点（兜底 ZERO）
  └─ move(passenger, position - offset)
Entity#getPassengerRidingPosition(passenger)         Entity.java:2338-2340   （`this.dimensions`，缓存）
LivingEntity#getPassengerRidingPosition(passenger)   LivingEntity.java:4053-4056
  └─ position + getPassengerAttachmentPoint(passenger, getDimensions(getPose()), scale)   ← 实时，不走缓存
Entity#getPassengerAttachmentPoint(...)              Entity.java:2342-2348
  └─ getDefaultPassengerAttachmentPoint(this, passenger, dimensions.attachments())
       └─ attachments.getClamped(EntityAttachment.PASSENGER, 乘客序号, vehicle.yRot)
EntityAttachment.PASSENGER 的兜底点                   EntityAttachment.java:9,23-25
  └─ Fallback.AT_HEIGHT = (0, height, 0)
```

四条结论：

1. **座位点就是 `EntityAttachment.PASSENGER` 的一个点**，按**乘客序号**取（越界夹到最后一个），并且**由平台按
   载具的 `yRot` 旋转**（`EntityAttachments.transformPoint`：`point.yRot(-rotY · π/180)`）。
2. **`LivingEntity` 载具用的是实时尺寸**（`getDimensions(getPose())`），所以改了座位点**不需要
   `refreshDimensions()`**，也不会碰载具的碰撞箱（只换 attachments，`width`/`height` 不变）。
3. **两边（客户端与服务端）都算**：`ServerLevel.java:865` 与 `ClientLevel.java:381` 都对乘客调 `rideTick()`。
   所以座位是**本地算出来的**，不经过网络——ICF 需要一个双向 payload，只是因为它的入口在客户端（右键/按键
   被客户端抢先处理），不是因为座位需要同步。
4. 乘客的**每 tick 位置都被重新写一遍**（`positionRider` 用 `setPos`），所以挂在别的生物身上的生物**走不掉**。

### 2.2 玩家是唯一没有座位表的载具

原版所有想要自定义座位的载具都覆盖了 `getPassengerAttachmentPoint`：

| 载具 | 位置 | 与 `super` 的关系 |
|---|---|---|
| `AbstractHorse` | `AbstractHorse.java:1039-1042` | **调 `super` 再叠自己的偏移** |
| `AbstractMinecart` | `AbstractMinecart.java:171-173` | 下沉时用自己的点，否则走 `super` |
| `Llama` | `Llama.java:449-451` | 直接调静态 `getDefaultPassengerAttachmentPoint`，**绕过 `super`** |
| `Camel` | `Camel.java:489+` | 自算，绕过 |
| `Slime` | `Slime.java:256-258` | 自算，绕过 |
| `Strider` | `Strider.java:175-182` | 调 `super` 再叠 Y |
| `AbstractBoat` | `AbstractBoat.java:135+` | 自算，绕过 |
| **`Player`（`Avatar`）** | `Avatar.java:21-36, 66-67` | **根本没有座位**，落到 `Entity` 的兜底点 |

`Player` 的尺寸表在 26.1.2 挪到了新的 `Avatar`（`Player extends Avatar`）：站立 `0.6×1.8`、**潜行 `0.6×1.5`**、
游泳/鞘翅/旋斩 `0.6×0.6`、睡觉 `0.2×0.2`（`Avatar.java:18-36`）。于是：

- 兜底座位点 `AT_HEIGHT` = `(0, dimensions.height(), 0)`，玩家站立时就是 **(0, 1.8, 0)＝头顶**；潜行时跟着
  降到 `(0, 1.5, 0)`（因为 `LivingEntity` 用实时尺寸）；**睡觉时塌到 `(0, 0.2, 0)`**——这正是原版鹦鹉
  "睡觉就掉下来"的原因之一。
- 容量：`Entity#canAddPassenger` = `this.passengers.isEmpty()`（`Entity.java:2456-2458`），`Player` 未覆盖 ⇒
  **玩家默认只能载 1 个乘客**；`startRiding(e)` = `startRiding(e, false, true)`（`Entity.java:2351-2353`），
  只有 `force = true` 才跳过容量与"乘客没在潜行"这两个闸门。

### 2.3 原版鹦鹉那套为什么不能复用

`ServerPlayer` 把肩上的实体**存成 NBT 后 `discard()`**（`ServerPlayer.java:271-273, 431-454, 841-855`），
同步给客户端的只有一个品种枚举 `OptionalInt`（`Player.java:138-141, 1857-1870`），客户端画的是写死的
`ParrotModel`（`ParrotOnShoulderLayer.java:50-52`，位置 `(±0.4, -1.3/-1.5, 0)`，潜行手调 0.2），而且
20 tick 内没人接管就把实体**弹回世界里**（`ServerPlayer.java:858-865`）。

它是一条**「把生物暂时收起来」的存储通道**（还给自动落地、入水、飞行、睡觉、细雪五种条件兜底），不是挂载：
肩上那只生物在世界上**不存在**、不 tick、不能被交互。灵宠要战斗、要跟随、要被别的系统看见，所以这条通道
不合适；ICF 也没有用它。

### 3.2 与本设计的数值等价

把 ICF 的算式代进平台那一套（`transformPoint(point, yRot)` = `point.yRot(-yRot)`）：

- 座位点 `(0.5, 1.4, 0)` ⇒ `x' = 0.5·cos(yRot)`、`z' = 0.5·sin(yRot)`；ICF `i == 0` 给的是
  `extraX = 0.5·sin(π + yBodyRot - 90°) = 0.5·cos(yBodyRot)`、`extraZ = 0.5·cos(yBodyRot - 90°) = 0.5·sin(yBodyRot)`
  —— **同一组数**（玩家的 `yRot` 与 `yBodyRot` 平时相等）。
- 于是三个位置就是：**`(0.5, 1.4, 0)` / `(-0.5, 1.4, 0)` / `(-0.2, 1.8, 0)`**（右/左/背后，按 ICF 的 `i` 顺序）。

**唯一的差别**：ICF 自己硬编码了潜行时的 1.2（站 1.4），而平台侧玩家的尺寸**本来就随姿态变**（站 1.8 / 潜行 1.5）。
所以本设计把偏移的 **y 定义成"从载具当前顶部往下量"**：`(±0.5, -0.4, 0)` 在站立时算出 `1.4`（与 ICF 一致），
潜行时算出 `1.1`（ICF 是 1.2，差 0.1）——换来的是**不用自己判断姿态**，且睡觉/游泳这类姿态跟着一起变。
两个肩位的具体数值属于**入口/数据**的决定（见 §4.5），本轮只把它当参数；另外整个偏移会按平台交给座位钩子的 `scale`
（含幼年缩放与 `/scale` 一类缩放）等比缩放，与 `AbstractHorse` / `Camel` 那些原版座位的口径一致。

## 4. 定案

四个词：**一条记录、一个座位点、一个服务、一条策略**。数据包与本轮无关。

### 4.1 记录：`attachment/PerchAttachment.java`

- 长在**乘客**身上（不是载具身上）：偏移是"这段关系"的属性，同一个生物换一个载具就是另一个偏移。
- 内容只有**一个已解析的偏移 `Vec3`**（载具局部坐标系；`x` 是载具的左侧、`z` 是车头方向，y 从载具当前顶部
  往下量，见 §3.2），空 = 没挂着。**不存"左肩/右肩"这类名字**：名字是入口层的词汇，存名字等于给同一件事
  造第二份真相（第二轮的入口把名字解析成 `Vec3` 再写进来）。
- 形状照附件房规：`ShouldSyncAttachment` + `Vec3.CODEC.lenientOptionalFieldOf("offset")`，注册用
  `entityWithoutDeathCopy`（同步给客户端；生物死了不该把"挂着"这件事带给新实体）。

### 4.2 座位点：`mixin/EntityPerchMixin.java`

- 目标：`Entity#getPassengerAttachmentPoint(Entity, EntityDimensions, float)`，`@Inject(at = HEAD, cancellable = true)`；
  乘客身上有 `mxt:perch` 就返回 `offset` 锚到载具当前顶部、按平台给的 `scale` 缩放、再按载具 `yRot` 旋转，否则原样走平台
  （缩放与旋转都照原版座位覆写那条路：`AbstractHorse` / `Camel` 等也是把偏移乘 `scale` 再交给平台旋转）。
- **为什么不打 `Player`**：挂点是**乘客自己声明**的，载具是谁都认（用户拍板）。附带三个好处——
  ① 不需要 `instanceof Player` 这条热路径判断；② 探针可以两只探针生物互挂，**无玩家也能实机断言**；
  ③ 与"乘客序号"解耦，两个肩位不需要各占一个 index。
- **为什么不用 `getDefaultDimensions` / `EntityEvent.Size`**：`LivingEntity#getDimensions(Pose)` 是 `final`，
  而 `positionRider` 走的是**实时** `getDimensions(getPose())`，`EntityEvent.Size` 只影响缓存下来的那份、
  对定位不可见；`getPassengerAttachmentPoint` 才是官方给载具留的座位钩子（§2.2 那张表）。
- 旋转那一行**复刻了平台私有的 `EntityAttachments.transformPoint`**（`private static`，拿不到）；换成
  自己搭一个 `EntityAttachments` 去借平台那一行，每次定位要分配一个 `EnumMap` + 4 个列表，不划算。
  代码里注明出处。

### 4.3 服务：`runtime/perch/PerchService.java`

单点实现（"谁挂着、写/清记录"只有这一份），形状照 `ContractService`：`Result(boolean changed, Failure failure)`。

| 方法 | 语义 |
|---|---|
| `perch(Entity entity, Entity vehicle, Vec3 offset)` | 校验（不能是自己、偏移必须有限、不能已经在骑别的、载具身上**已挂的数量** < 配置上限、`startRiding(vehicle, true, true)` 成功），成功后写记录。已经在骑**同一只**载具时只改偏移（平台对第二次 `startRiding` 直接答 false）。`force = true` 是为了绕过原版"玩家只能载 1 个"与"乘客不能在潜行"两个闸门，容量改由自己数（数的是"乘客里有记录的几个"，要座位的那一个不算已占的位，所以换个肩位不是占第二个名额） |
| `release(Entity entity)` | 清记录 + `stopRiding()`；两者顺序保证事件监听者看到的仍是"挂着"的状态 |
| `perchOffset(Entity entity)` | 只读查询（`getExistingData`，不创建附件） |

`Failure`：`SELF` / `INVALID_OFFSET` / `ALREADY_RIDING` / `FULL` / `REFUSED`。计数是私有实现，不对外开一个只有探针会用的公开方法。

### 4.4 策略：`runtime/perch/PerchEventBridge.java` + 服务器配置「肩挂」页

- 挂在 `EntityTickEvent.Post`，**从乘客侧看**（每 tick 一次 `getExistingData`，不创建附件）：不挂着就直接返回；
  载具没了就清记录；载具满足任一条启用的下肩条件就 `release`。
- 条件（每条一个开关，默认全开，取自原版鹦鹉那条规则再加潜行）：
  `fallDistance > 0.5` / `isInWater()` / `isInPowderSnow`（字段，不是方法）/ `Player.getAbilities().flying` 或
  `LivingEntity#isFallFlying()` / `LivingEntity#isSleeping()` / 载具潜行（手动下肩）。
- 另有 `max_perches`（默认 2，两项两肩）。**默认值不改变现有行为**：不挂上去就不会掉下来。
- 为什么不放进数据包：这是"服务器怎么对待这件事"的策略，与 `realm_stage.lifespan` 那类"一条定义自己的数"
  不同；照「寿元」页的先例进配置。

## 5. 已知边界

1. **载具自己的座位算法优先**：`Llama` / `Camel` / `Slime` / `AbstractBoat` 完全自算、不经过 `super`，挂点对
   它们**不生效**；`AbstractHorse` / `Strider` / `AbstractMinecart` 会调 `super`，于是挂点被返回后被它们
   **再叠一层自己的偏移**。玩家（`Avatar`）与普通 `Mob` 载具完全听挂点——这正是本轮的目标场景。
2. **潜行会让玩家变矮**（1.8 → 1.5），y 锚在顶部所以挂着的东西跟着降；**睡觉**会把玩家尺寸塌成 `0.2×0.2`，
   所以"睡觉"必须在默认下肩条件里，否则会挂进被窝里。
3. **挂着的生物仍然是普通生物**：会 tick、能被打、AI 照跑（但每 tick 位置被写回，走不掉）。它随载具
   跨维度/退档（乘客关系存进载具的存档），也就是说**玩家登出时灵宠在玩家的存档数据里**——内容侧要知道这一点。
4. **`force = true` 也跳过了原版"乘客不能在潜行"的闸门**：所以挂上去这个动作本身不受生物自己的潜行状态限制，
   这是"基座受理"的口径（要不要看潜行由调用方决定）。
5. **第一个打在原版实体类上的 mixin**：`mxt.mixins.json` 此前只有 server / level / codec / 客户端覆写四项，
   `defaultRequire: 1` 意味着注入失败会直接崩在启动——所以座位点写错方法名是一条会立刻炸的路径，不是静默失效。

## 6. 否掉的方案

| 方案 | 为什么否掉 |
|---|---|
| 复用原版鹦鹉的肩上 NBT | §2.3：那是一条"把实体收起来"的存储通道，只画 `ParrotModel`、只认品种枚举，挂着的生物不存在于世界 |
| 照 ICF 在**生物自己的 `rideTick` 里 `setPos`** | 那条路要求生物类自己写代码（第三方实体的 `rideTick` 我们改不了），而且要把平台的旋转数学抄一遍；`EntityAttachment.PASSENGER` 是平台为"载具的座位"留的同一个位置，用它可以一行都不抄（§2.2） |
| 打 `LivingEntity#getDefaultDimensions`（把座位写进玩家尺寸表） | 表达力更"正统"（座位出现在 `dimensions.attachments()` 里），但要走 `refreshDimensions()` 才会进缓存那份，且会连带影响玩家自己的 `getAttachments()` 与 `EntityEvent.Size`。**只为定位服务的东西不该动碰撞箱表** |
| 用 `EntityEvent.Size` 改尺寸 | §4.2：它改的是缓存那份，而定位走实时尺寸，等于没生效 |
| 新增一个"玩家肩挂"专用通道（只在玩家身上生效） | 用户拍板要通用（任何载具都认乘客声明的挂点），而且通用版**无玩家也能探针实机验证** |
| 给 `mxt:mount` 现在就加 `seat_offset` / 新增 `mxt:perch` 动作 | 用户明确"这个先不做 action"。留到下一轮，且届时要在"扩展已有动作"与"新增动作"之间再选一次（两条路都通，取舍是词汇清晰度 vs 动作数量） |
| 座位点同步给客户端（新 payload） | §2.1 第 3 条：客户端自己算，没有同步的必要 |

### 9.2 本轮落地：把 1–4 收成"附属契约"（**不造实体类**）

**一件东西**：`api/Perchable`（[`interfaces.md`](../../docs/guide/java/interfaces.md) 有面向附属的说明）。

```java
public interface Perchable {
    Optional<Vec3> perchOffset(Entity vehicle, List<Vec3> claimed);   // 空 = 拒绝这具载具
    default void onPerched(Entity vehicle) { }
    default void onPerchReleased(Entity vehicle) { }
}
```

- **本体不提供实体类**（铁律 9）：生物是附属的东西，基座只提供"挂"这件事与它要问的两个问题。所以这里没有 `SpiritBeastEntity` 之类的类，也没有注册表——**实现接口就是全部资格**（与 `Contractable` 同形，数据包造不出资格）。
- **偏移仍只有一处真相**：接口返回的是同一个坐标系（载具局部、y 从顶部往下量），框架把它写进 `mxt:perch` 附件；**接口不返回"左肩/右肩"这种名字**（名字是入口层的词汇，§4.1）。
- **拒绝就是空**：`Optional.empty()` = 这具载具我现在不上去（不在主人身上、状态不对、位置已满……），框架不写记录、回 `Failure.NOT_WILLING`。
- **`claimed` 是"这具载具上已经声明的偏移"**：有多种座位可给的生物可以据此挑一个空的（挑不到就拒绝）。这一格只有它有用，所以由框架算好传进来，不另开一个公开查询。
- **两个钩子是时刻，不是状态**：`onPerched` 只在**真的从没挂到挂上**时调用（同一具载具上换个座位不算第二次就座），`onPerchReleased` 在记录清掉、乘客关系也结束之后调用（自己下来 / 被策略放下 / 被判失效三条路都走它），并且传的还是那具载具（`stopRiding` 之后问不到了）。**载具已经消失的那一种没有载具可传**，所以钩子不触发；要精确判断状态就问 `PerchService.perchOffset(生物)`（记录是唯一真相）。
- **顺手修掉一个旁路**：`PerchEventBridge` 原来在"载具没了/死了"这一支里直接 `perch.clear()`，既绕过了"写 / 清记录只走 `PerchService`"这条口径，也让**骑乘关系没结束**（死掉的载具可能还挂着乘客）。现在这一支改走 `PerchService.release`：记录清、`stopRiding`、钩子照常。
- **受理仍在 `PerchService`**：`perch(生物, 载具)` 是新增的重载（先问生物、再走原来那套检查），`perch(生物, 载具, 偏移)` 与 `release` / `perchOffset` 不变；`Failure` 多一个 `NOT_WILLING`（"没给出座位"——拒绝与"压根没实现接口"都是它）。

**验证**：`/mxt_test perch` 多一段腿（`ProbeBeast` 作为"附属的生物"实现 `Perchable`）：框架问到它给的偏移 → 记录里就是那个坐标 → `onPerched` 记了一笔；`release` 之后 `onPerchReleased` 记了一笔；把答案改成空 → `NOT_WILLING`；拿一只**没实现接口**的猪去挂 → 同样 `NOT_WILLING`。同一趟腿组里其余五段（默认座位 / 声明座位 / 旋转 / 容量 / 下肩策略）照旧。

### 9.3 仍在外面（登记，不猜）

| 不进这一轮的东西 | 为什么 / 建议 |
|---|---|
| **数据包动作**（`bi_entity_action.mxt:mount` 加座位参数，或新的 `mxt:perch`） | 属"玩家入口"（`AGENTS.md` §7）。两条路都通：扩展既有动作省一个词汇，新动作语义更直白。**要不要做由用户定**；真做时它只需要写 `PerchService.perch` 一行——"座位从哪来"已经有答案了 |
| **KubeJS 方法**（`MxtPerch`） | 同上；脚本侧受众比数据包小，但与"脚本能查询/授予功法"那一轮同形，接通成本很低 |
| **命令**（`/perch`） | 同上；探针之外，这是唯一能在实机里手动验"真人玩家当载具"的入口，**做它顺手解决 §9.1 第 8 条** |
| **载具侧的否决契约** | 需要第二个接口（"我接受谁挂在我身上"），而载具可以是任何实体、包括原版的。今天内容可以在**乘客自己**的答案里读载具状态来表达（例如"主人没在潜行我才上去"），所以先不加 |
| **座位自动错开** | 内容策略：`claimed` 已经给到手上，要不要"第二个自动去另一侧"由生物自己答 |
| **把挂着的生物变不可选中 / 免疫** | 内容策略，用现成的目标条件表达（§4.5 已记） |
| **姿态与动画** | 谁的模型谁负责；内容侧的判断依据是 `entity.getVehicle()`（§4.5 已记） |
