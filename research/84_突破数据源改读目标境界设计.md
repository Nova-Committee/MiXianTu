# 84. 突破数据源改读目标境界

**状态：已落地**（2026-10-05 按用户要求；`compileJava` / `compileTestModJava` 通过；**探针未实跑**）

**取代 [`36`](36_子境界设计.md) 的切分数据源**（那一稿的 §2 切分口径与 §3.1 凡人段已按本稿改写，本稿只讲"为什么换个阶段读"）。
**同时删掉 `Aura.start_exp`**——这不是顺手清理，而是同一件事的结果：见 §3。

## 0. 一句话

**一次突破要多少钱、能囤多少、要什么条件、要不要自动，一律从"要爬到的那一档"（B）读，不再从"现在站的那一档"（A）读。**
于是 `Transition` 这个记录整个消失：突破只剩 `(target, aura)` 两个信息，连"现在站在哪"都不需要了——它只是用来**找** B 的。

用户原话：

> 1. 把 Transition 简化；2. 目前突破境界 A->B 的时候，是从 A 读取数据，改成从 B 读取（理解为突破到当前境界的条件和 exp），
> 这样 Aura 就不需要承载突破信息了

## 1. 为什么改

### 1.1 数据本来就属于"目的地"

一档境界的 `breakthrough_exp` 记的是**"从上一档爬到我要多少"**，不是"从我这往外爬要多少"。这两件事在数值上

```
B.breakthrough_exp  ==  从 A 爬到 B 的量
A.breakthrough_exp  ==  从上一档爬到 A 的量
```

所以"突破 A → B 要多少修为"这个问题，B 自己就答得出来，而且是**直接**答；问 A 要绕一层（A 的字段答的是另一段路）。
旧的读法能跑，靠的是一条**约定**：写包的人必须让"每一档的 `breakthrough_exp` 恰好等于从上一档爬到它的量"。
这条约定本身没错（`84` 落地后仍是同一套数值），但它让**字段的写法与字段的用途错位**——A 的字段被拿来当"离开 A 的价钱"，
而它字面意思是"进入 A 的价钱"。首档尤其别扭：凡人还没有 A，于是凭空要一个 `aura.start_exp`。

### 1.2 首档的洞

凡人 → 首境界这一步，旧口径下 A 不存在，所以那份阈值不属于任何 `realm_stage`，只能挂在 `Aura.start_exp` 上。
于是同一个概念有两个存放处：**有 A 时读 `realm_stage.breakthrough_exp`，没有 A 时读 `aura.start_exp`**。
`Transition` 的 `mortal` 分支、`profile` 字段、`conditions()` / `autoBreakthrough()` 里那两对**恒为常量**的三元
（`mortal()` 把 `current := target`，两个分支永远等价）全是这个洞的补丁。

改读 B 之后这个洞自己就没了：凡人朝**首境界**爬，就读书首境界的 `breakthrough_exp`。首档仍是 `realm_stage`，
没有任何"不属于任何阶段"的阈值，`start_exp` 也就没有存在的理由。

## 2. 改成了什么

### 2.1 全链读 B

| 读什么 | 旧 | 新 |
| --- | --- | --- |
| 突破要求 `breakthrough_exp` | A | **B** |
| 囤积上限 `max_experience` | A | **B** |
| `breakthrough.conditions` | A | **B**（本来就是 B，`mortal` 分支除外） |
| `auto_breakthrough` | A | **B**（同上） |
| 凡人的要求 / 上限 | `aura.start_exp`（要求 = 上限 = 它） | **首境界的 `breakthrough_exp` / `max_experience`** |

统一之后 `threshold()` 不再分支：一次读 `target` 的两个字段。

### 2.2 `Transition` 整个消失

原形状是 `(current, target, aura, profile, mortal)`，`profile` 只为凡人的 `start_exp` 存在，`mortal` 只为
"`conditions()` / `autoBreakthrough()` 该读哪个"存在。数据源改读 B 之后：

- `current` **没有任何读取点**了（`next()` 只是用它找后继），
- `profile` 随 `start_exp` 一起消失，
- `mortal` 失去意义（两个三元的两支本来就等价）。

所以不是"简化成 `(target, aura)`"，而是**连记录本身都不需要**：`next(...)` 直接返回 `Optional<Holder<RealmStage>>`，
`attempt` / `commit` 收 `(aura, targetHolder)` 两个参数。**这是要求 1 与要求 2 其实是同一件事的证据**——
`Transition` 的复杂度全部来自"从 A 读"。

### 2.3 子境界除数跟着走（改 [`36`](36_子境界设计.md) 的口径）

`minor_stages` 的**数量与名字属于 A**（`minor_stage_abilities` 是按 A 的下标索引的），但**除数是 B 的
`breakthrough_exp`**——因为进度就是朝 B 涨的，这一点与阈值同源。所以一个阶段的"第几重"要用到链上的两档：

```
条目数 = A.minor_stages          （A 的属性：能力下标按它索引）
除数   = B.breakthrough_exp      （B 的属性：进度朝它涨）
```

**链到头（没有 B，例如 `mxt_test:tribulation`）读 `NaN`**：没有"要爬到的要求"，就没有可切的段。这是新出现的第五种
NaN 情形，旧口径下不存在（旧口径只看 A 自己，链尾照样切得动）——但链尾本来也不该有子境界可显示。

### 2.4 顺带：守卫与上限都不动

- `RESOLVING_MINOR_STAGE` 重入守卫保留（除数仍是公式字段，仍可能读到 `minor_stage`）。
- `threshold()` 的可用性判据（有限、`breakthrough_exp >= 0`、`max_experience >= breakthrough_exp`）逐字保留，
  只是换成 B 的字段。
- `Aura.start_cultivate_conditions` **保留**：它管的是"能不能开始修炼"（`CultivationMethodService.canStartCultivation`），
  与突破无关，不在本稿范围内。

## 3. `Aura.start_exp` 删除的理由与代价

**理由**：它唯一的读取点是凡人分支（旧 `CultivationService.threshold()`），改读首境界后那个点不存在了。
`start_exp` 的 codec 默认是 `new Constant(0.0D)`，而凡人旧口径下 `max = min = start_exp`，**不写这个字段的包等于
"凡人一步都爬不动"**（要求 0、上限 0）——它本来就是个必须写、写错就静默卡死的字段。

**代价**：包作者失去"给凡人单独定一个门槛"的能力。这是**刻意**的：那个门槛与首境界的 `breakthrough_exp` 是同一个
概念的两份写法，允许两者不同只会让"凡人爬到一半、进了首境界进度却清零重来"这种口径出现（进度在突破时清零，见
`commit()`）。要调凡人的门槛就调首境界的 `breakthrough_exp`。

**兼容**：`RecordCodecBuilder` 不认识未知字段、会静默丢掉，所以老包里的 `"start_exp": ...` **不报错、直接失效**，
凡人门槛改由首境界决定。按仓库口径（见 `AGENTS.md` §4），字段删除必须同步测试包与文档站；本仓库 `docs/` 已停用，
字段说明进文档站（另一仓库），测试包两处 `start_exp` 已删。

## 4. 测试包与探针

**夹具几乎不用改**：因为新旧数值在测试包里恰好一致——`mxt_test:qi_refining` 是 `{breakthrough_exp: 100,
max_experience: 100}`，而旧 `aura/qi.json` 写的是 `start_exp: 100`（凡人要求 = 上限 = 100）。所以凡人 → `qi_refining`
这一步的**要求与上限逐字不变**，`MxtTestCommands` 那条寿命探针（`remaining == total == 2400`）的算术完全不动。

改动只有两处：`aura/qi.json` 与 `aura/spirit_power.json` 各删一行 `start_exp`。

**`verifyMinorStages` 的切分数字也不用改**，但原因值得记下来，因为它**不是**因为"新旧口径等价"：
`qi_refining` 的 `breakthrough_exp` 是 100，它的下一档 `foundation` 也是 100，所以"除数取 A"与"除数取 B"在这条链上
恰好同值。（`foundation` 的 `max_experience` 是 250 而 `breakthrough_exp` 是 100——所以上**限**在 `qi_refining → foundation`
这一步从 100 变成了 250，囤积上限放宽，不影响任何探针的断言。）

`spirit_power_refining` 的 `{breakthrough_exp: 10, max_experience: 100}` 与旧 `start_exp: 10` 也构成同样的巧合
（凡人步要求不变），但它的**囤积上限从 10 变成 100**——探针里没有依赖它的断言（burst 探针用的资源上限来自
`resource/spirit_power.json` 的 `100 + level * 10`，与阶段阈值无关）。

## 6. 不做 / 推迟

- **不给 `Aura` 保留"凡人门槛"字段**（见 §3）。
- **不动 `start_cultivate_conditions`**：与突破无关。
- **不改公式变量的语义**：`minor_stage` 仍是 0-based、不适用仍读 `NaN`，只是 NaN 多了一种来源。
- **不新增玩家入口**。
