# 88 阵法功能模块重设计

**一句话**：把阵法"做什么"收成一份列表——`FormationActionType` 内置 `activate` / `tick` / `interval` / `inactivate`
四个钩子，顶层的六个通用 action 字段拆成三个模块类型（`mxt:activate` / `mxt:tick` / `mxt:inactivate`），
灵气覆写从 `mxt:buff` 独立成 `mxt:aura`，`range_display` 更名 `particle`、`none` 更名 `empty`。

状态：已落地（2026-10-19；用户给定形状，三处形状选择由用户拍板）。**§10 是同日追加的阵形绘制**（`mxt:particle`
从"半径轮廓"改成"外环 + 星形"，一帧一个命令粒子），**§11 把模块节流改成 tick 单位、并把模块拍（10 tick）与维护周期
（20 tick）拆成两个时钟**，**§12 把"逐 tick 变大"交给客户端**（服务端一拍只交一段，客户端自己播出来），
**§13 把整个描线时钟搬到客户端**（服务端只发"还在渲染 + 起点/剩余"的订单，进度与重铺都由客户端一张表管），
**§14 把阵形换成 `mxt:formation_shape` 注册表**（折线与圆两种笔画、每笔自己的颜色/渐变、内置的三个星形变成模组包里的 JSON），
**§15 把颜色、窗口与疏密收进笔画的通用字段（模块不再有 `color` / `size` / `spacing`）、给每一笔加 `start` / `end` 窗口与圆的 `start_angle`**；
本稿标题、§2 的钩子签名、§4 表格里 `mxt:particle` 那一行、以及 §10–§13 的"一帧铺完整幅图 / 一拍交一段 / 三个内置星形"
都按 §10–§15 读。

## 1. 现状的问题

改之前是两套东西并存：

- `Formation.actions`（`FormationActionType` 列表）——"功能模块"，`attack` / `buff` / `protection` /
  `range_display` / `send_message` / `none`；
- 顶层六个字段——"通用钩子"，`activate_action` / `tick_action` / `deactivate_action`（方块行为）与
  `entity_tick_action` / `entity_enter_action` / `entity_exit_action`（实体行为）。

坏处有三条：

1. **接口是个空壳**。`FormationActionType` 只有一个 `codec()`，真正的行为写在 runtime 的
   `FormationActionRunner` 里，靠 `instanceof` / `switch` 按 record 类型分派——加一个模块要改两个仓库层次，
   而且 `data/formation/builtin/*` 里那几个 record 只是"字段容器"。仓库里其它地方（`data/action/builtin/*`）
   的写法是"record 自己实现 `execute` 并调用 runtime 服务"，阵法这一块是唯一的例外。
2. **两套生命周期**。模块只能挂在"周期 + 逐实体"这一个时刻上（`interval_periods` 就是它的节流），
   阵法的激活与拆除只有顶层钩子够得到；反过来，顶层钩子又拿不到模块的节流。表达力被这两套切开了。
3. **灵气寄生在 `mxt:buff` 上**。`aura_zone` / `max_bonus` 是"阵地替换灵气解析"，与"给实体发技能"是两件事，
   却被塞进同一个模块，于是 `AuraService` 必须去 `actions` 里捞 `BuffFormationAction`；写在同一个模块里也
   让"这座阵法只改灵气、不给人东西"没有干净的写法。

## 2. 四个钩子

```java
public interface FormationActionType {
    Codec<FormationActionType> CODEC = ...;            // type 分派
    MapCodec<? extends FormationActionType> codec();
    default void activate(FormationActionContext context) {}
    default void tick(FormationActionContext context) {}
    default void interval(FormationActionContext context) {}
    default void inactivate(FormationActionContext context) {}
    default int intervalPeriods() { return 1; }
}
```

四个都是 `default` 空实现：模块只实现它需要的节拍；`mxt:empty` / `mxt:protection` / `mxt:aura` 一个都不实现
（前两个什么都不跑，第三个只是给 `AuraService` 读的声明）。

| 方法 | 阵法自身（`context.perEntity() == false`） | 逐实体（`context.perEntity()`） |
| --- | --- | --- |
| `activate` | 立阵成功、写完索引与事件之后一次 | 实体进入半径（含立阵后第一拍已经在里面的） |
| `tick` | 每个维护周期一次 | 每个被覆盖的实体每周期一次 |
| `interval` | 同上，但只在该模块自己的 `interval_periods` 到期的那一拍 | 同上 |
| `inactivate` | 拆除时一次（`deactivate` 的唯一出口里） | 实体离开半径、或阵法被拆除 |

`tick` 与 `interval` 的范围相同、差别只在节流：想要每周期都跑的模块实现 `tick`，想稀疏的模块实现
`interval` 并写 `interval_periods`。节流由框架做（`FormationIntervals.due(module.intervalPeriods(), gameTime, PERIOD)`），
相位取自世界时钟，所以同一份定义的多座阵法、以及一座阵法里的所有人仍然**在同一拍**上跑，
模块自己不带计数器。

四个钩子都在两个范围上被调用，所以模块必须自己认边：只作用于实体的模块（`mxt:attack` / `mxt:buff` /
`mxt:send_message`）在 `context.entity() == null` 时直接返回，只作用于阵法自身的模块（`mxt:particle`）
在 `context.perEntity()` 时返回。这条写在接口注释里，因为它是新接口最容易踩的坑。

## 3. 上下文

`runtime/formation/FormationActionContext`（record）：`level` / `controller` / `carrier`（阵法 id、阵心、半径、
阵主名单）/ 可空的 `entity` / `distanceSquared`。它同时是模块看世界的唯一一扇窗——模块不再拿到 ticker、
`FormationInstance` 或别人的局部变量。

- `formula()`：阵身那次是 `FormulaContext.of(level)`（只有 `zero` / `random`，与旧的 `tick_action` 口径一致）；
  逐实体那次是 `FormulaContext.of(entity, ...)` 并带 `formation_radius` / `distance` / `formation_x|y|z`，
  与旧 `entity_*_action` 完全一致。
- `block()`：旧的 `BlockActionContext`（Level + 阵心 + Level 公式），给通用方块行为用。
- `entityContext()`：旧的 `EntityActionContext`，并把 `FormationCarrier` 塞进扩展数据（`mxt:formation_owner` /
  `mxt:formation_ally` 读它）。

放在 `runtime` 而不是 `data`：它握有 `FormationInstance` / `FormationOwners` 这类运行时对象。
`data/formation/FormationActionType` 反过来 import 它——`data → runtime` 在本仓库是既有写法
（`data/action/builtin/*` 一直在 import `runtime/*Service`），不是新引入的环。

## 4. 模块清单

| 现在 | 之前 | 节拍 | 说明 |
| --- | --- | --- | --- |
| `mxt:attack` | 同名 | `interval`（逐实体） | 字段与语义不动 |
| `mxt:buff` | 同名 | `interval`（逐实体） | **去掉** `aura_zone` / `max_bonus` |
| `mxt:aura` | 新 | 无 | `aura_zone`（**必填**）+ `max_bonus`；只被 `AuraService` 读 |
| `mxt:particle` | `mxt:range_display` | `interval`（阵身） | 字段不动，`due` 的闸门移到框架里 |
| `mxt:send_message` | 同名 | `interval`（逐实体） | 字段不动 |
| `mxt:protection` | 同名 | 无 | 仍是被 `FormationProtection` 查询的声明 |
| `mxt:empty` | `mxt:none` | 无 | 空模块，同时是分派表默认项（id 一起改） |
| `mxt:activate` | 顶层 `activate_action` + `entity_enter_action` | `activate` | `block_action`（BlockAction）+ `entity_action`（EntityAction） |
| `mxt:tick` | 顶层 `tick_action` + `entity_tick_action` | `tick` | 同上 |
| `mxt:inactivate` | 顶层 `deactivate_action` + `entity_exit_action` | `inactivate` | 同上 |

`mxt:aura` 的 `aura_zone` 做成**必填**：没有 zone 的 `max_bonus` 本来就无处可加（上限加在"覆盖后选中的那个
zone"提供的资源上），一个只写 `max_bonus` 的模块是静默无效的拼写错误，按仓库口径应当拒收。

## 5. 三个通用模块

三组顶层字段 = 三个时刻 × 两个范围，所以三个类型各带一对字段：`block_action` 走 `context.block()`，
`entity_action` 走 `context.entityContext()`，同一个钩子里靠 `perEntity()` 二选一。两个字段都可选
（`optionalCodec` 的默认值就是 `mxt:no_op`），所以 `{"type": "mxt:tick"}` 等于不写。

于是"模块与通用钩子谁先谁后"这个问题消失了：**一切都按 `actions` 的列表顺序跑**。旧文档里
"每周期先跑模块、再跑 `entity_tick_action`"的说法作废，取而代之的是"列表顺序就是执行顺序"。

## 6. 分派与既有口径

`FormationActionRunner` 缩成三个静态方法（阵身 `activate` / 阵身 `periodic` / 阵身 `inactivate` 与逐实体同形），
每周期（20 tick）的顺序不变：

1. 结构校验不过 → 拆除；维护费付不出 → `UpkeepFailed`（取消＝这一拍白过）；
2. `Tick` 事件（不可取消，钱已经花了）；
3. `TickEffects`（可取消）——**取消就等于这一周期什么都不跑**，与旧口径一致；
4. 阵身 `periodic`：每个模块 `tick`，到期的模块再来一次 `interval`；
5. 逐实体：进场的先 `activate`，然后每个被覆盖实体的 `tick` / `interval`，最后离场的 `inactivate`。

`spare_friends` 的口径一字不变：被豁免的实体不进在场集合，因此也拿不到 `activate` / `inactivate` / `tick`
（逐实体那三个范围）。

## 7. 破坏性变化

- 顶层六个字段全部删除：老包写了它们是**未知键静默忽略**（仓库口径），表现为"阵法不再有那些行为"。
- `mxt:range_display` → `mxt:particle`、`mxt:none` → `mxt:empty`：老 id 变成未知 `type`，**整个定义解码失败**。
- `mxt:buff` 的 `aura_zone` / `max_bonus` 不再被读（未知键静默忽略），老包的灵气覆写会静默消失——
  这一条最难受，所以测试包夹具与文档站同时改。

## 10. 阵形绘制（同日追加，用户给定形状）

`mxt:particle` 从"把半径轮廓画出来"改成"把阵形画出来"：外面一圈环，里面 `FormationShape` 的星形
（`five` / `six` / `eight`）。渲染方式是**新加一个粒子**，它带 `Shape` / `radius` / `color` / `progress`；
客户端收到后在**第一 tick** 把整幅图铺成 `DUST`，然后立刻自毁。`progress` 是"画到多少"，范围 `0~1`。
（"第一 tick 铺完整幅图"已被 §12 取代：现在一拍只铺一段，其余由客户端逐 tick 补。）

### 10.1 几何：`data/formation/FormationShapePath`

- **顶点 0 在正东（+X）**，其余沿圆等分。环是这些顶点所在的那个圆（按角度采样，不是按顶点连折线——环就是
  环，不是正多边形）；星形按 `FormationShape.routes` 的顶点序号连折线（`FIVE` 一笔隔一个顶点，
  `SIX` / `EIGHT` 各是两组互不相交的图形）。
- **两层各按自己的总长截断**：环画到圆周的 `progress` 那一段，星形画到自己总长的 `progress` 那一段，两条一起
  长；同一层里每条 route 也各自截断，所以六芒星是两个三角同时长，而不是一个长完再长另一个。
- **点数是算出来的**：`ceil(这一笔已画长度 / spacing) + 1`，端点一定落在 progress 指定的位置上；
  每笔封顶 `MAX_POINTS_PER_STROKE = 2048`——这是客户端保护（`spacing` 0.01 配半径 4096 会一帧铺几万个），
  不是给作者定的规则。`spacing <= 0` / 半径非正由 `steps()` 退化成"不画"或封顶，不会崩。

### 10.2 一帧 = 一个命令粒子

- 新粒子类型 `mxt:formation`（`FormationParticleOptions`：`shape` / `radius` / `dust` / `spacing` / `progress`；
  第五项按 §12 改成 `draw_in`）。
  `FormationParticleType` 的 `overrideLimiter = true`；**用 `registerSpecial` 登记、没有 particles json**；
  客户端 `FormationParticle` 继承 `NoRenderParticle`（落进 `NO_RENDER` 组，不跟可见粒子抢 `SINGLE_QUADS`），
  在第一 tick 铺完 DUST 后 `remove()`（§12 之后是走完 `span` 再 `remove()`）。
- 服务端每拍**每个看得见的玩家只发一个包**（`FormationShapeDisplay`，半径 + 32 格，口径与旧的范围显示一致）：
  整幅图在客户端铺开，所以点数只花客户端的粒子，不花带宽。旧代码是"一个点一个包"，这是本轮最大的开销变化。
- 客户端铺 DUST 走 `level.addParticle(dust, true, false, …)`（8 参重载）。**必须走它**：6 参那条会吃
  `ClientLevel.doAddParticle` 的 32 格与"粒子效果"两道闸门，半径超过 32 格的阵法会被剪掉一圈。顺带记下本轮
  查原版得到的两条结论：**视锥只挡渲染、不挡 tick**（`ParticleEngine.tick` 不看相机，`QuadParticleGroup.extractRenderState`
  才看），真正会吃掉远处粒子的是 `ClientLevel.doAddParticle` 那道 32 格。

### 10.3 进度按立阵时刻推进

- `FormationInstance` 加 `activated_at`（`lenientOptionalFieldOf`，**老档读作 0 ＝ 已经画完**，不会重放动画）。
  `FormationWorldService.activate` 在写完世界索引、跑开场节拍**之前**打戳，经 `FormationCarrier` 透出。
  （进度算式与字段名已被 §11 改成 `duration_ticks`，见下。）
- `duration_ticks = 0`（默认）＝不画动画，第一拍就是完整的；重新立阵会重新计时（实例是新建的）。

### 10.4 其它

- `runtime/formation/FormationRangeDisplay`（旧的 `ring` / `sphere` 显示）**整体留作备用、无人调用**，自带一份
  `Shape` 枚举与 `VISIBLE_MARGIN`，不再被模块引用（模块不再有 `Shape` 枚举）。旧的"纯圆环"显示因此**没有数据包
  入口**了：`mxt:particle` 画的一定是"环 + 星"。
- 破坏性：`mxt:particle` 的 `particle` / `points` / `shape: ring|sphere` 一律不再被读（未知键静默忽略），
  `shape` 改成**必填**的 `five` / `six` / `eight`，不写＝整个定义解码失败。

  探针代替不了。

## 11. 两个时钟：模块拍与维护周期（同日追加，用户给定）

用户在实机看阵形之后给的调参意见是三条：间隙调到原来的 1/3、尘埃默认大小调到 2、**频率快一倍**。前两条
是默认值的事（`spacing` `1 → 0.33`、`size` `1 → 2`），第三条澄清下来是**框架的事**：

> 本身 `interval_periods` 单位应该是 tick，然后刷新频率改成 10 tick

原来的口径是"`interval_periods` 数阵法周期，因为派发只落在 20 tick 边界上"（`research/18` §"阵法周期"）。
那条推理没错，错的是它把**两个不同的东西**绑成了一个格子：**账单**与**画面**。于是本轮把时钟拆开。

### 11.1 形状

- `FormationIntervals.TICK = 10`：**模块拍**。`FormationWorldTicker` 每 10 tick 派发一次，两个范围
  （阵法自身 / 逐实体）都在这一拍上被问。
- `FormationIntervals.PERIOD = 20`：**维护周期**。维护费、`mxt:tick` 那一档、实体进出的记账与
  `releaseOutside` 的清扫都还按它算——**收钱的速度一点没变**。
- 字段改名与改单位：`interval_periods` → **`interval_ticks`**（单位 tick）。名字不改就是在骗人（一个叫
  `_periods` 的字段装着 tick 数是本仓库最忌讳的形状），所以宁可破坏性改。
- 取值范围 `10..24000`（旧上限 1200 周期 × 20 = 24000 tick，**上限一秒没松**），并且**必须是 10 的倍数**：
  比拍子还细、或落在拍子之间的值（例如 15）永远不可能被问到，按仓库口径**解码期拒收**而不是静默取整。
- 默认值按模块各给：`attack` / `buff` / `send_message` 仍是 `20`（**行为与改动前逐字一致**），
  `mxt:particle` 是 `10`（**每一拍都重画**，动画因此从 1 fps 变 2 fps）。
- `FormationActionType.intervalPeriods()` → `intervalTicks()`（默认值 `PERIOD`）；`FormationIntervals.due(ticks, gameTime)`
  就是 `gameTime % ticks == 0`，相位仍取自世界时钟，模块仍然不带计数器。
- `FormationWorldTicker.dispatch(level)` → `dispatch(level, gameTime)`；结构校验与
  `UpkeepFailed` / `Tick` 留在周期拍上（重读模板不该一秒两次），`TickEffects` 改成**每一拍发一次、取消这一拍**。
- **同一件事的另一个字段也跟着改**：`mxt:particle` 的 `duration_periods` → **`duration_ticks`**
  （`0..24000`），进度算式简化成 `(now - activated_at) / duration_ticks`。这个字段是同一天新加的、没有老包，
  所以不留迁移；留着 `_periods` 而 `interval_ticks` 是 tick 只会让同一个模块里两种单位并存。

### 11.2 语义上要说清的两处

- **被宽恕的一期不再等于冻结的一期**：`UpkeepFailed` 被取消时，那一期不扣费，但**它的另一拍照常跑**
  （代码注释已按这个写）。原因是"取消 = 这一周期什么都不做"在一个周期有两个拍的世界里没法只靠一次判定表达，
  而 `UpkeepFailed` 的用途本来就是"让阵法熬过一段穷日子"，不是冻结它。
- **逐实体那一趟现在也每 10 tick 跑一次**：`level.getEntities` 的扫描因此翻倍（记账表是纯内存的
  `FormationEntityActions.PRESENCE`，不写附件，所以只是 CPU）。换来的是逐实体模块也能用 10 tick 的间隔
  （`mxt:attack` 想一秒打两次就写 `10`）。**这是本轮唯一一处性能代价**，没实测过服务器规模下的影响。

### 11.3 破坏性

- `interval_periods` 与 `duration_periods` 都不再被读：老包写了它们是**未知键静默忽略**，
  `interval_periods` 退回该模块的默认值（`attack` / `buff` / `send_message` 是 20，`particle` 是 10）——
  也就是说老包写 `interval_periods: 3`（旧义 = 60 tick）会变成 20 tick 或 10 tick。**这一条最需要提醒**，
  测试包夹具与文档站同时改掉了。
- 写了不是 10 的倍数的 `interval_ticks` 会**让整个定义解码失败**（不是静默忽略）。

### 11.4 验证

- `compileJava` / `compileTestModJava` / `processTestModResources` 通过；文档站中英同步、`AGENTS.md` §4 已改。
- 探针：`formation/beats` 改成"两个时钟"的形状（30 tick 间隔在 t=30 那一拍只有 `interval` 没有 `tick`），
  并断言 `beatDue(30) && !periodDue(30)`、`PERIOD % TICK == 0`、以及**不是 10 的倍数会被拒**；
  `MessageProbes` 的 `intervalGate` 改成 tick 语义并补了越界值被拒的一条。
- **`runGameTestServer`：282 个测试全绿**（18.2 s，一次通过）。测试包夹具与探针里所有 `interval_periods` /
  `duration_periods` 已换成 tick 字段（`formation_range_probe` 40 tick、`formation_message_probe` 60 tick、
  三个 `star_*` 的 `duration_ticks` 60）。
- **未跑**：`runTestClient`——2 fps 的观感、`spacing 0.33` + `size 2` 的疏密，仍然只能实机看。

## 12. 逐 tick 变大交给客户端（同日追加，用户报"开始的时候动画卡顿"）

> 本节把"一拍切一段"，但**时钟仍在服务端**；同一天又被 §13 整个搬到客户端（`drawn/target/span` 的记录换成了
> `raisedAt/drawn/drawInTicks/holdTicks`）。下面留着的是当时的推理与 `band` 的来历，形状以 §13 为准。

用户实机看到的症状是：`duration_ticks 60` 的阵法在立起来那一刻是**六级跳**——服务端每一拍（10 tick）才把
`progress` 往前推一次，客户端只会在收到的那一 tick 把"到当前进度为止的整幅图"铺一遍，所以图形在 0.5 秒里
不动、然后跳一大段。§10 的形状没有错，错的是**把"拍"当成了"帧"**。

### 12.1 形状：一拍交一段，客户端自己播

- **服务端仍然每拍（`interval_ticks`）只发一个包**，但包里不再是"整幅图 + 一个进度"，而是一段：
  `data/formation/FormationDrawIn`——`drawn`（这一拍开始时图形已经到哪）、`target`（这一拍结束时该到哪）、
  `span`（客户端要用多少 tick 走完）。`FormationDrawIn.at(activated_at, gameTime, duration_ticks, interval_ticks)`
  是唯一的算法：`target = clamp(elapsed/duration)`、`drawn = clamp((elapsed-interval)/duration)`、
  `span = round((target-drawn) * duration)`——最后一条让**收尾那一拍自动变短**（55 tick 的动画在第 60 tick 那一拍
  只剩 5 tick 可走），所以客户端恰好和动画同时收笔。`duration_ticks = 0` 退化成 `(1, 1, 0)`，即"一拍一幅完整图形"，
  与 §10 的行为一致。
- **客户端 `FormationParticle` 现在活 `span + 1` 个 tick**：第一 tick 铺 `[0, drawn]`（迟到的玩家、以及"已经画好的
  那部分靠每拍重铺来续命"都靠它），之后**每 tick 只补刚长出来的那一段**，走完自毁。顺滑度因此由客户端的帧率决定，
  与 `interval_ticks` 写多大无关（`interval_ticks` 现在只管"服务端多快推进 / 多快续命"）。
- **几何加了 `band(from, to)`**：`outline(progress)` 就是 `band(0, progress)`。这是"每 tick 只补一段"能成立的前提——
  按 `band` 铺，第 k 个 tick 的点集与前面那些 tick 的点集不重叠（除了两端共享的那个端点），所以一个 beat 的动画
  总共只花**一幅图的点数**，比 §10 的"每拍重铺整幅"还少。若改成"每 tick 重铺 `[0, progress]`"，一个 60 tick 的动画
  会铺 60 幅图，粒子数直接爆掉。
- 服务端**不知道也不管**客户端怎么播：`FormationShapeDisplay.draw(..., FormationDrawIn)` 依旧只按玩家发一个包，
  几何与点数全在客户端算（§10.2 的口径不变）。图形的**高度**也收在 `FormationShapeDisplay.center(BlockPos)` 一处
  （`DRAW_HEIGHT = 0.1D`，即阵心方块底面往上 0.1 格、贴着地面；原先用的是 `getCenter()`，也就是方块中心，
  半径一大看着像浮在半空），探针里钉了这条数。

### 12.2 两条要记下来的原版事实

- **一拍与下一拍之间是"一 tick 重叠"，不是空档**：`ParticleEngine.tick()` 先把各组 tick 完，**最后**才把
  `particlesToAdd` 排进组里（`ParticleEngine.java:85-110`），所以包落地那一 tick 创建的粒子要到下一 tick 才第一次
  `tick()`。于是第 k 拍的播放在第 k+1 tick 开始、在第 k+1+span tick 结束，而第 k+1 拍的包正好在 span tick 后落地，
  两边首尾相接（重叠一 tick，无害）。
- 一拍的**续命**仍然靠服务端：`band` 铺下去的点只活它自己那点寿命（`DustParticleBase` 里
  `lifetime = max(baseLifetime * scale, 1)`，`baseLifetime = 8/(rand*0.8+0.2)` ∈ [8, 40]，`size 2` 时 [16, 80]），
  所以"已经画好的那一段"是靠每一拍的 `[0, drawn]` 重铺（`span` = 10 tick，短于最短寿命 16）活着。**这条给
  `interval_ticks` 划了下界**：它一旦大过尘埃的寿命，图形会开始闪——这不是本轮引入的，§10 也是每拍重铺。

### 12.3 验证

- 探针 `formation/shape` 扩了两组断言：`band` 的形状（只含两段之间、`from >= to` 不画、两段拼起来覆盖整幅图、
  起点落在自己那个进度上）与 `FormationDrawIn` 的调度（首拍无内容、中间拍恰好覆盖一个 beat、收尾拍被截短、
  `span` 不超过自己的 `interval_ticks`、画完 / `duration_ticks = 0` / 老档都是 `(1, 1, 0)`）、以及
  `progressAt(0) == drawn`、`progressAt(span) == target`。腿尾加了一条 `note` 把关键数印进日志
  （`130 points on the whole figure, 134 on the two halves, one beat plays 0.48333332 -> 0.5 over 10 client ticks`）。
- **`runGameTestServer`：282 个测试全绿**（15.4 s）。
- 落地时抓到两处自己的错，都靠先把算式在体外跑了一遍（拿 `java` 单文件把 `FormationDrawIn.at/at` 与
  `band` 各复刻一份、把断言先跑绿再写进探针）：
  1. "两段拼起来覆盖整幅图"的上界原来是 `full + 2`，实际是 `full + 2 × 笔画数`——**每一笔**一分为二都会多算两个点
     （两半各自向上取整多一个间隔，再加上共享的接缝点）。FIVE 两笔，实际 134 = 130 + 4，原式会正好卡在边界外。
  2. "band 的起点"原本按 `band(0, 0.5).getFirst()` 断言成环的**对径点**，但 `band` 先铺环再铺星，环那一段是从
     `from` 开始的，所以 `band(0, 0.5)` 的首点还是正东；改成断言 `band(0.5, 1)` 的首点才是对径点。
- **未跑**：`runTestClient`——顺不顺滑只能实机看。

## 13. 描线的时钟搬到客户端（同日追加，用户给定形状）

用户对 §12 的结论是"有了个更好的 idea"：**启动动画改成纯客户端控制，服务端只负责维护"是否渲染"，客户端本地自己搞一个
计时器推进度**。§12 的做法虽然把一拍切成了一段、画面已经顺了，但"进度"仍然是服务端每拍算一个数发下来的——服务端的
拍子仍然是时钟。本轮把时钟整个搬到客户端。

动手前问过用户一个岔路（**起点从哪来**），用户选了"**跟服务端对齐**"：客户端第一次看见一座阵时，服务端要告诉它
"现在已经画到哪"，客户端把这一段一次铺上、再用自己的计时器长完剩下的；而不是一律从 0 重播一遍。

### 13.1 形状：服务端发"订单"，客户端跑时钟

- **包体换成 `FormationDrawIn(raisedAt, drawn, drawInTicks, holdTicks)`**（`data/formation/FormationDrawIn`，
  §12 那个 `drawn/target/span` 记录被整个替换）：
  - `raisedAt`＝哪一次立阵（`FormationInstance.activated_at`）。**它同时是订单的身份**：客户端按阵心方块存表，
    这个数一变就是新的一次描线，旧图形被替换而不是接着长。
  - `drawn`＝服务端时钟此刻画到哪（`clamp(elapsed/duration)`）；客户端第一次看见时先按它把 `[0, drawn]` 铺满。
  - `drawInTicks`＝剩下的该由客户端用多少 tick 长完＝`duration - elapsed`。**它恒等于 `(1 - drawn) × duration`**
    （同一条直线的两种写法），这就是"客户端从 `drawn` 起、用自己的时钟走 `drawInTicks` 拍，会和服务端的斜坡同时收到
    1"的证明——两条斜坡同一个斜率，而服务端只发其中一个点。
  - `holdTicks`＝多久没收到下一张订单就停画＝`2 × interval_ticks`，夹在 `[30, 200]`（下限为了扛住服务端跑慢，
    上限为了不让一个把 `interval_ticks` 写成 24000 的包让阵拆了还站半小时）。
- **`interval_ticks` 的语义从"重画频率"变成"心跳间隔"**：JSON 一个字没改（仍默认 10、仍必须是 10 的倍数），但它现在
  只决定"服务端多久确认一次还在渲染"与"hold 窗口多大"，与画面流畅度无关。
- **客户端一张表 + 一个 tick 事件**：`render/particle/FormationFigures`（`@EventBusSubscriber(DIST.CLIENT)`，
  `ClientTickEvent.Post` 推进、`ClientPlayerNetworkEvent.LoggingOut` 与换 level 清表，形状照 `BurningItemManager`）：
  - 第一 tick 铺 `[0, drawn]`（于是中途走过来、中途登录、断帧之后重新收到订单的人看到的都是**正确进度**）；
  - 之后每 tick 只补 `band(laid, target)`，`target = start + (1-start) × (now-startedAt) / drawIn`；
  - 每 10 tick 把整幅重铺一次续命（尘埃活得比 10 tick 长；这条原来是服务端每拍做的，现在归客户端）；
  - 超过 `holdTicks` 没收到订单就整条丢掉，已经铺出去的尘埃自己淡出。
- **载体粒子的职责缩到最小**：`FormationParticle` 现在只在第一 tick 把订单交给 `FormationFigures` 再自毁；`mxt:formation`
  仍然是"命令粒子"（`overrideLimiter`、`registerSpecial`、没有 particles json），因为它还兼着"绕过原版 32 格与
  「粒子效果」两道闸门"的活。
- **为什么状态必须落在客户端的一张表里**：服务端**必须**反复发订单（新来的玩家要拿起点、断帧要恢复、参数改了要跟着变），
  而"一个订单一个粒子"没法去重——粒子引擎不提供"查一查某个位置有没有同类粒子"的接口。所以订单只能当消息用，
  状态只能自己存；`FormationFigures` 就是那一份状态。这也是本轮唯一新增的可变客户端状态，生命周期跟着 level 与连接走。

### 13.2 语义变化

- **停止方式变了**：以前"服务端不再发包"就等于立刻停止重铺；现在客户端要等 `holdTicks`（默认 `2 × 10 = 30` tick
  ＝1.5 秒）才停。所以拆阵是"**停止描线 + 尘埃淡出**"，不是瞬间消失（尘埃本来就要淡 1~4 秒，视觉上更连贯）。
- **`interval_ticks` 写大的后果变了**：它不再让画面变卡（时钟在客户端），但会让心跳变稀、`holdTicks` 变长——
  也就是拆阵之后图形残留更久，而且心跳间隔一旦大过尘埃寿命（`size 1` 时最短 8 tick），图形会在两次心跳之间闪。
- **同一座阵所有人同时收笔**：起点对齐意味着后到的人只看到"剩下的那一段"（剩余为 0 的人直接看到画满的图），
  只有 0 号顶点那一次立阵才有人看到"从头长"。
- `duration_ticks` / 老存档的口径不变：`duration_ticks = 0` 或老档（`raised_at = 0` 且世界时间已经很大）都是
  `(raisedAt, 1, 0, hold)`＝一次铺满、不描线。

### 13.3 验证

- `compileJava` / `compileTestModJava` 通过。
- 探针 `formation/shape` 里 §12 那组调度断言换成新形状：首单 `0 / 600`、半途单 `0.5 / 300`、**对齐等式**
  `(1-drawn) × duration ≈ drawInTicks`、画完与 `duration_ticks = 0` / 老档都是 `drawInTicks = 0`、
  hold 窗口 `10→30 / 60→120 / 24000→200`，外加一组扫值（四种时长 × 三种间隔 × 每个 beat）断言
  `drawn ∈ [0,1]`、`drawInTicks ∈ [0, duration]`、`holdTicks > 0` 且等式恒成立。
- **又是先在体外跑一遍**：拿 `java` 单文件复刻 `FormationDrawIn.at` 与客户端那条 ramp，把断言与"客户端收笔的时刻"
  先跑绿再写进探针。这一次它抓到一个真问题：**浮点乘法会让客户端晚一跳收笔**（`start + (1-start) × k / drawIn`
  在 `k = drawIn` 时可能得到 0.99999994）。改成"先用 tick 数判终点、到点直接给 1"之后，体外扫过
  `duration ∈ {10, 55, 600, 24000}` × 每个起点都**恰好**在 `duration - elapsed` 那一 tick 收笔。
- **`runGameTestServer`：282 个测试全绿**（20.2 s）——新的订单断言与"高度"那条一起跑过。
  第一次跑是**红的**，而且红在了 §12 那条"图在底面往上 0.1 格"的断言上：它上一轮加完时用户说先别跑，所以**从来没实跑过**，
  期望值把 `z` 写成了 `-5.5`，而 `new BlockPos(3, 64, -5)` 的中心是 `getZ() + 0.5 = -4.5`（差 1.0 格，断言红了）。
  代码本身没错，错的是探针；修完即全绿。教训照旧：**探针里的数字也要先在体外算一遍**——这一条如果跑的是客户端，
  就会变成"图整体偏了一格"这种只能靠眼睛发现的问题。
- **未跑**：`runTestClient`——客户端的表、心跳超时（拆阵后残留 1.5 秒）与观感只能实机看。

## 14. 阵形改成 `mxt:formation_shape` 注册表（同日追加，用户给定）

用户在工具页（`tools/formation_figure.html`）里定了图形的形状之后要求："在 Java 里面实现，同时把之前内置的 568 三个星改成对应的
json，新建一个 `mxt:formation_shape` 注册表"。也就是说 §10 那个"三个内置星形写死在 enum 里"的东西整个换成数据包定义。

### 14.1 形状

> 本节的字段形状已被 §15 改掉（颜色收进笔画的通用字段、模块不再有 `color`、另加 `start` / `end` 与圆的 `start_angle`），
> 下面这段按当时的形状读。

- **新注册表 `mxt:formation_shape`**（第 42 张 datapack registry）：一份定义就是 `{"strokes": [...]}`，
  1~256 笔。`FormationShape` 从 enum 变成那个 record（`CODEC` = `RegistryFixedCodec`，`DIRECT_CODEC` = `strokes` 字段），
  `MxtResourceKeys.FORMATION_SHAPE` + `MxtDatapackRegistries.register(...)`。
- **一笔 = `FormationStroke`，sealed，两个实现**：`Circle(center, radius, color, gradient)` 与
  `Polyline(points, color, gradient)`。分派走**代码注册表** `formation_stroke_type`（`MxtRegistries` + `MxtResourceKeys` +
  `MxtFormationStrokeTypes` 两个 id `circle` / `polyline`），与全仓二十多个 `type` 分派同一形状；
  sealed 是为了让 `FormationShapePath` 的 `switch` 穷尽——**没有第三种走法可加**。
- **坐标**用 `MiscCodecs.HORIZONTAL_PAIR`（`Vec2`，JSON 是 `[x, z]`，与秘境边界中心同一个 codec），**单位是阵列半径**，
  所以一份图形跟着半径缩放；`1` 就是阵列自己的环。
- **每笔的颜色**：`color`（`ExtraCodecs.STRING_RGB_COLOR`，构造器掩掉 alpha）或 `gradient`
  （`FormationStroke.Stop` 的 `{"at", "color"}` 列表，2~16 个，**按 `at` 升序**，两端之外保持端点色）；两个同时写＝解码期报错
  （照 `Formation` 的两份结构那条口径）。两个都不写就用模块的 `color`——`FormationStroke.colorAt(along, fallback)` 是唯一的取色出口。
- **服务端只发 id**：`FormationParticleOptions` 从"粒子选项里带图形枚举"改成
  `(Holder<FormationShape> shape, radius, color, size, spacing, FormationDrawIn)`，`FormationShape.STREAM_CODEC =
  ByteBufCodecs.holderRegistry(...)`（与 `Aura` / `Talisman` 一样，客户端自己有那份定义）。`FormationShapeDisplay.draw`
  因此缩成 `(level, controller, frame)`——**帧由模块自己拼**，服务端不再有几个散参数。
- **采样带颜色**：`FormationShapePath.outline/band` 返回 `List<Dot>`（`Dot(Vec3 position, int color)`），
  每一笔按自己的总长截断、按**格数**除以 `spacing` 算点数；笔画的颜色按"这一点在这一笔上的位置"取（`along` = 整笔的 0~1），
  所以渐变是锚在笔画长度上的，不随进度拉伸。客户端逐点构造 `new DustParticleOptions(dot.color(), size)`。
- **三个内置星形变成模组自己包里的 JSON**（`src/main/resources/data/mxt/mxt/formation_shape/{five,six,eight}.json`，
  id 是 `mxt:five` / `mxt:six` / `mxt:eight`），坐标用同一套顶点公式生成到 9 位小数，**不带颜色**（照旧吃模块的 `color`）。
  代码里再没有针对它们的特例。
- 工具页跟着这次改动挪了三处格式：外层包一层 `{"strokes": [...]}`（正好是一个定义文件）、`type` 写全 `mxt:circle` / `mxt:polyline`、
  渐变的 stop 从 `[at, "#hex"]` 改成 `{"at":…, "color":…}`（异构二元组在仓库里一律走具名字段，见 `Cost` 的 `{id, amount}`）。

### 14.2 落地时踩到的两个坑

1. **代码注册表建了但没登记**：`MxtFormationStrokeTypes.REGISTRY` 没写进 `MiXianTu` 构造器那一串 `register(bus)`，
   于是 `type` 解析不到任何东西——整个世界以 `Failed to parse mxt:five from pack mod/mxt` 直接加载失败。
   **新加一个 `DeferredRegister` 一定要在 `MiXianTu` 里登记**，编译不会提醒。
2. **`type` 要写全命名空间**：`"type": "circle"` 会被读成 `minecraft:circle`，整个定义加载失败。这个是**工具页先写错的**——
   它当初按"枚举名"写；改成注册表之后必须写 `mxt:circle`。工具页的 `readStroke` 现在对不带前缀的写法单独报一句
   "a stroke's type carries its namespace"。

   两条都只在**实跑**里暴露（编译全绿），而第一条的报错信息只说明"解析失败"，真正的 `Caused by: List is too short: 0,
   expected range [1-256]` 要往下一层翻才看得到——**这类"注册没生效"的症状是"定义整个读不出来"，不是"某一项不生效"**。

### 14.3 验证

- 探针 `formation/shape` 重写：模块字段比 `HolderHelper.id(display.shape())`（`mxt:eight`）、不认识的图形 id 被拒、
  三个内置定义的形状（`five` = 环 + 6 点一笔、`six` / `eight` = 环 + 两笔 4/5 点）、每笔颜色的三条规则（渐变按整笔读、
  没写颜色吃模块色、两处同时写与乱序渐变都被拒）、空的 / 零半径的 / 单点的 / 不认识 `type` 的图形都被拒、
  **工具页写出来的那段 JSON 能被解码**，以及几何（首点在正东、整幅在一米高度、点数随 spacing、封顶、band 拼起来覆盖整幅、采样点带颜色）。
  两个数字照旧：半径 8、`spacing 1` 时环 52 点 + 五角星 78 点 = **130 点**——`note` 行里印出来了，说明**三份 JSON
  与旧 enum 的几何逐点一致**（这正是本次迁移要证明的事）。
- "图在环内"那条断言的容差从 `r² + 1e-6` 改成 `r² × (1 + 1e-6)`：`Vec2` 存的是 float，而坐标现在是**写出来的数**
  （9 位小数喂给 float，半径 8 上约 4.0E-7 格的误差，平方之后就该用相对容差）。
- 测试包四个夹具的 `"shape": "five"` 全部改成 `"mxt:five"` 等；`processTestModResources` 已跑。
- **`runGameTestServer`：282 个测试全绿**（19.96 s）。
- **未跑**：`runTestClient`——颜色与渐变在游戏里什么样、以及客户端读定义这套（holder 同步）在真客户端上的表现。

## 15. 颜色、窗口与疏密收进笔画、圆加起始角（同日追加，用户给定）

用户要求三件事："取消掉 Action 里面的 `color` 字段，改成 stroke 的通用字段。同步给 stroke 添加两个字段：`start`、`end`，
取值均为 0~1，用于控制什么时候开始什么时候结束。最后给 circle 加一个起始点的参数（相对于 E 方向的角度）"，
随后又要求把 `mxt:particle` 上的 `size` / `spacing` 也"细化到每个 Stroke 上"。
三处歧义由用户拍板：**颜色必写**（不写＝加载期报错，不留一个谁也没写的白色兜底）、**角度用度数**、
**`size` / `spacing` 搬到笔画上、缺省 `2` / `0.33`**（模块那两个字段删掉）。

### 15.1 形状

- **`FormationStroke.Common(color, gradient, size, spacing, start, end)`** 是每一笔的通用字段：`Circle` 与 `Polyline`
  各持一份，两个实现都不再自己声明颜色、疏密与大小。JSON 里它们是**平的**（与 `type` / `radius` / `points` 同级）——
  子类型的 `RecordCodecBuilder.group` 里塞一个 `Common.CODEC.forGetter(...)`，`MapCodec` 在 `group` 里可以嵌套，
  与 `MiscCodecs.pair` 是同一套原语；接口上六个访问器都是默认方法，转发到 `common()`，调用点看不出这层。
- **`mxt:particle` 不再有 `color`**：颜色没有模块级的兜底了，一笔**必须**写 `color` 或 `gradient` 之一
  （`Common.validate`：两个都写、两个都不写都报错；`end > start` 也在同一个 validate 里）。模组自带的三份 JSON
  每一笔补 `"color": "#ffffff"`——与旧行为（模块默认白）观感一致。
- **`mxt:particle` 也不再有 `size` / `spacing`**：两者降为笔画的字段，**可选**，不写就用 `Common.DEFAULT_SIZE = 2`
  与 `Common.DEFAULT_SPACING = 0.33`（`optionalFieldOf` 的默认值，所以笔画里存的是具体数、不是 `Optional`，
  采样处不需要"回退参数"这一层）。范围照旧 `0.01..4` 与 `0.01..64`。于是**一幅图可以外环稀、内层密**：
  点数与尘埃大小都是逐笔算的（`band` 里读 `stroke.spacing()`，`Dot` 多带一个 `size`）。
- **窗口**：`start` / `end` 都是 0~1、默认 `0` / `1`。`FormationShapePath.band` 先把它映射到每一笔自己身上
  （`local = (progress - start) / (end - start)` 夹在 0~1），`local` 不前进就整笔跳过；渐变仍按**整笔**的 `along` 读，
  所以它不随窗口拉伸。工具页的两个输入框因此不许交叉（正在输入的那个赢，另一个让位）。
- **圆的起始角**：`start_angle`（`Codec.doubleRange(-360, 360)`，默认 `0`），**度数**、相对正东、朝 +Z 为正；
  只在 `Circle` 上。采样处 `Math.toRadians(startAngle) + 弧长进度`。
- **连带变简单的地方**：`FormationParticleOptions` 从 `(shape, radius, color, size, spacing, drawIn)` 瘦成
  `(shape, radius, drawIn)`（wire 与 codec 各少三段）、`FormationShapePath.outline/band` 少一个 `fallback` 与一个
  `spacing` 参数、`FormationStroke.colorAt(along)` 少一个参数、`Dot` 多一个 `size`——"回退色"与"模块级疏密"这两条
  概念整个消失了。`FormationFigures` 逐点构造 `DustParticleOptions(dot.color(), dot.size())`。
- 工具页跟着改：paint 的 `default` 模式去掉（每笔必须上色，新笔画拿"new strokes"那个取色器）、`one stroke` 组里多出
  start / end / start_angle / spacing / size 五个输入框（都跟着选中那一笔走）、圆的边缘手柄改成"起点"
  （拖它同时定半径与角度，角度按 divisions 吸附）；`array` 组只剩 `radius`（它才是阵列自己的），
  点数与尘埃大小都按每一笔自己的 `spacing` / `size` 算、不在默认值的才写进 JSON。
- 工具页的**动画预览**补全：`Play` 本来就是按游戏速度播 `duration_ticks`，这次加了**速度滑条**（离散档
  `0.1× … 8×`，默认 1× 就是游戏速度）、**`loop`**（画完停一下再从头，免得重启只是闪一下）与一个
  `已画 tick / duration_ticks` 的读数；播放中改速度或时长会把斜坡重新锚在当前进度上，画面不跳。
  **这三个都是预览设置，不进 JSON**（`duration_ticks` 是模块字段，照旧不进图形文件）。
- **线条自己也动**：`lines`（原 `geometry`）那一层不再一次画完整幅，而是按同一套规则只描到"已经该有的地方"
  ——圆按角度扫到 `TAU × local`、折线按弧长走到 `pointAt(total × local)`、窗口照旧先映射；没走到的那一段以
  **ghost**（`INK.ghost`，低透明度）留在原地，否则 `progress 0` 会是一块空板子、也没法在动画中途改图。
  于是关掉 `dust` 也能看"线在写字"而不是"点在铺地"。

### 15.2 破坏性

- 老包的 `mxt:particle` 写了 `color` / `size` / `spacing` ＝未知键静默忽略（仓库口径）：**图形里没写颜色的笔画会让整个
  定义加载失败**（自带的三个已经补好，包自己的图形要么补 `color`、要么改成渐变），而 `size` / `spacing` 只会退回默认值
  （`0.33` / `2`，正是模块原来的默认）——所以只在"包把模块的 `spacing` 调粗/调细过"时看得出差别，要保留就把它们写到笔画上。
- 工具页写出来的图形永远带颜色，所以它不会产出被拒的文件；反之它**读**一个没写颜色 / 窗口不成立 / 疏密越界的文件会明确报错。
