# 运行期物品使用会话设计

## 1. 目标与取舍

修复 [临时使用组件审查](audit/临时使用组件审查.md) 的 TU01–TU05，并让其他模块能声明自己的长按用途。数据包字段与现有 HoldBinding 声明不变。

不再把运行期行为写进持久化的原版 `minecraft:consumable`。`TemporaryUseComponent` 与 HOLD/PILL 所有者枚举由统一的 `ItemUseCycles` 替代；会话只属于具体实体实例与手部物品栈，复制、分离、掉落和存档均不会复制它。

弱引用只防止运行期索引保活实体与物品，正确性不依赖 GC。结束、取消、空闲、实体离开、退出及关服各有显式清理出口。

## 2. 可扩展契约

`api/ItemUseCycle` 描述一次使用：

| 接口 | 契约 |
| --- | --- |
| `id()` | 用途 Identifier，不维护封闭枚举 |
| `durationTicks()` / `animation()` | 正整数 tick 时长与动画，本次会话固定 |
| `canStart(holder, stack)` | 开始前的资格检查；默认允许 |
| `tick(holder, stack, remainingTicks)` | 两侧运行；实现自行把业务写入限制在服务端 |
| `isConsumption()` | 该用途完成是否属于消费；默认 false |
| `finish(level, holder, stack)` | 服务端执行一次，返回最终物品栈；默认保留原栈 |

在 NeoForge 游戏事件总线上监听 `ResolveItemUseCycleEvent`，调用 `claim(cycle)` 认领。先认领者生效；内置 Hold 用 HIGH，丹药用 NORMAL，附属模组可按优先级选择覆盖或兜底。实现不得持有玩家或实时物品栈，运行时参数由回调提供。

不为新用途增加独立组件、所有权分表或清理监听器。新用途只实现描述与业务回调；需要在完成后结算丹药的用途同时实现真实消费和 `isConsumption=true`。仅返回 true 不会自动扣物品。

## 3. 会话与原版边界

一次右键在 LOWEST 准备会话，但仍由物品自己的 `use` 决定是否进入原版使用周期。物品栈必须仍在对应实体手中。再次准备会先关闭未开始的旧会话，使用中的会话不允许被重新武装覆盖。

自带 consumable、可交换装备、格挡、动能武器或原生正使用时长的物品不准备会话。相似的静音动画组件也一律视为原生值，既不覆盖也不删除。

原版组件没有适合运行期虚拟使用的公开覆盖入口，因此保留一个公共侧 Mixin，接入基础 `Item` 的四个方法：`use`、`getUseDuration`、`getUseAnimation`、`finishUsingItem`。使用 NeoForge 已提供的 MixinExtras：开始与完成用 `WrapMethod` 保留原调用，时长与动画用 `ModifyReturnValue` 读取原返回值，不使用 HEAD 提前返回。不改 `ItemStack` 组件读取、实体 tick、存档或全局事件分派，也不新增依赖。物品子类自有覆盖仍优先；需要接入本协议的自定义物品须委托相应基础方法。

`use` 只有在原版返回 `PASS`、未开始使用且手部栈未改变时才尝试开始；原生非零时长与非 NONE 动画保留。完成方法先运行原调用，只有结果仍为原栈且数量、组件及会话未变时才执行用途回调；原生替换或修改结果会关闭会话并直接保留。原生使用组件在准备后才加入时同样优先，未开始的旧会话不能中断它。

服务端完成仍经过 `ItemStack.finishUsingItem` 包装层，保留原版剩余物品与冷却处理。丹药的实际扣除调用原版 `Consumable.onConsume`，保留无限材料模式、食物监听、统计和进度等行为；Hold 默认完成保持原栈。完成回调有重入保护，回调异常会清理会话并传播原异常。

实体实例天然隔离逻辑侧和重登会话。客户端远端玩家没有本地右键事件，改在原版同步使用标志后第一次读取时长时解析会话；不新增网络包。槽位同步产生的新栈接替动画索引，旧栈解除；服务端仅允许等物品及等组件的新栈接替，客户端允许同物品的同步状态变化。

## 4. 完成分派

`ItemBindingService` 的通用完成行为保留。丹药次数、冷却与药效另外检查消费用途：运行期会话必须真实经过 `finish` 且声明为消费；未接入虚拟会话的原生消费读取完成事件的使用前副本中的 consumable。创造模式不减数量仍是消费，因此不以数量差判断。

功法、法器、玉简、容器与灌注的 Tick/Finish 业务改为读取已开始的 Hold 会话，而不是看到物品匹配某个 HoldBinding 就执行。一个物品携带多个业务定义时，只运行本次真正选择的用途。

## 5. 生命周期与边界

| 出口 | 行为 |
| --- | --- |
| Start 取消、非正时长或手部不符 | 拒绝开始并清理准备记录；开始后复核实际使用栈及剩余时长，覆盖末位取消与客户端预测标记 |
| Finish / Stop（含取消 Stop） | LOWEST 清理，普通业务回调先结算 |
| Tick 取消、非正剩余时长或非法换栈 | 关闭会话并终止原版使用，防止被当成正常完成 |
| 未启动点击、直接 stopUsingItem | 实体 Post 在空闲时清理 |
| 实体离开、玩家退出 | 立即清理该实体实例 |
| 客户端断线、服务端停止 | 仅清理对应逻辑侧 |

本轮不会猜测并剥除旧实现已经写进存档的 consumable：它与合法原生组件可能完全等值，缺少可信来源标记，无法安全自动迁移。新实现不再产生这种遗留；已有污染需由管理员确认后移除。

## 7. 临时组件与事件方案复评

本节记录临时组件与事件方案的源码复评；复评时实现使用四个基础 `Item` HEAD 钩子。随后按 §7.4 的方向完成低侵入改造，当前实现见第 3 节，验证状态见 §7.5。

### 7.1 临时写入能改进什么

临时 `consumable` 确实能让基础 `Item` 自己回答开始、时长、动画和消费，不必分别接管这四个方法。若继续采用实际写入组件的方式，至少需要保留以下改进：

- 一次使用对应一个可关闭会话，保存实际写入的栈、写入前的值与本次写入实例；新用途实现接口，不增加 HOLD/PILL 所有者枚举。
- 原生使用行为优先。未知组件即使与本模块生成的值完全相等，也不得认领或覆盖。
- 关闭只恢复本次仍拥有的值，不整栈恢复旧 patch，以免覆盖其他模块在使用期间的修改。关闭幂等，启动异常也须有 `finally` 出口。
- 通过 `LivingEntityUseItemEvent` 和实体退出事件集中管理开始、Tick、完成、中断及清理；丹药结算仍按实际用途判断。

这些规则可以解决原栈的所有权与回收问题，**不能单独解决组件已经流入副本、存档或网络的情况**。`AutoCloseable` 只保证作用域结束时关闭登记对象，不会自动发现使用期间产生的新栈；弱引用也不能代替恢复。

### 7.2 不能只靠生命周期回收的源码依据

以当前展开的 Minecraft / NeoForge 源码为基准：

| 源码入口 | 已确认行为 | 对原方案的影响 |
| --- | --- | --- |
| `DataComponents.java:170` | `CONSUMABLE` 同时注册 persistent 与 networkSynchronized | 不能把某次写入的值单独声明为 transient |
| `ItemStack.java:615` | `copy()` 复制组件 map，`split()` 经计数复制得到新栈 | 清理原栈不会清理已经分出的组件 patch |
| `ItemStack.java:117` | 存档 Codec 直接取 `components.asPatch()` | 只拦截公开的 `getComponentsPatch()` 不能保护保存 |
| `ItemStack.java:191` | 网络编码也直接取 `components.asPatch()` | 客户端写入同样不能按“只影响显示”处理；某些发包路径会携带物品栈 |
| `ItemStack.java:644` | `transmuteCopy` 直接从组件 patch 构造另一种物品 | 单独给 `copy()` 加清理也不是完整出口 |

即使临时写入被限制在同步的 `try/finally` 中，同一调用栈内触发的事件监听器也可以复制或保存该栈。原版自身也会制作使用前副本。作用域缩短只能减少暴露窗口，不能证明没有泄漏。

持久化一个自定义所有权标记可以给将来的恢复提供凭据，但仍需为副本、转移、保存与读取设计统一的归一化入口。它不会让原版 `consumable` 自动变成瞬时组件，也不会自动阻止副本在恢复前被原版当作可消费物品。只在下次 Tick 扫描背包不是完整修复。

### 7.3 事件组能替代哪些步骤

| 步骤 | 事件能力与限制 |
| --- | --- |
| 开始倒计时 | `Start` 可改本次 duration，但原版在发事件前已调用 `getUseDuration` |
| 持续执行及中断 | `Tick` / `Stop` 可以承担；仍要处理取消和无事件退出 |
| 时长查询 | 没有对应查询事件；使用进度及渲染还会再次读取总时长 |
| 动画查询 | 没有对应查询事件；基础 `Item` 从 `consumable` 读取动画 |
| 远端玩家显示 | 原版同步使用标志后直接读取时长，不经过本地右键和 `Start` 事件 |
| 最终结果替换 | `Finish` 可设置 resultStack，但触发时 `ItemStack.finishUsingItem` 已执行完剩余物品及冷却处理 |

最后一项不能简单改为“在 Finish 才扣物品”：原版剩余物品转换依赖使用前后数量，事件触发前未扣除，就不能继续依赖已经执行过的那次转换。应继续在原版包装层以内完成用途结算，不复制一份原版结算实现。

右键事件可以直接调用 `startUsingItem` 并返回取消结果，但会抢在物品自己的 `use` 之前接管交互。当前基础 `Item` 钩子允许物品子类先执行自己的覆盖；两种方式不是兼容性等价替换。也不能在右键事件里重放 `stack.use` 后仅返回结果：游戏模式收到事件取消会提前返回，跳过它原本的结果栈安装等后处理。

### 7.4 推荐的优化边界

不恢复跨 Tick 挂在真实栈上的临时原版组件。原方案中“一份描述驱动所有用途”的思路继续保留，由会话承载时长、动画与完成语义，生命周期继续走事件。

减少对原版行为的覆盖，采用原版执行后的窄兜底：

1. `use` 先运行原版，只有返回 `PASS` 且匹配会话时才尝试开始。
2. `getUseDuration` 仅在原版返回 `0` 时兜底，非零值包括负值均保留；`getUseAnimation` 仅在原版返回 `NONE` 时兜底。远端会话发现仍发生在时长读取处。
3. `finishUsingItem` 的用途回调仍放在 `ItemStack` 剩余物品 / 冷却包装层以内，不搬到 `LivingEntityUseItemEvent.Finish`。需要复核原版返回值和本次会话仍然匹配，不能覆盖已经产生的原生结果。

这条路线仍保留四个方法的钩子，不需要给复制、序列化和网络组件导出增加全局拦截，且让原版方法保留执行机会。它能识别原调用的返回值及栈变化，不把无法观察的外部副作用当成可推断的用途标记。

### 7.5 低侵入改造与验证

开始与完成的原调用都由同一会话服务包装，原调用异常会关闭本次会话并传播异常。完成重入先检查实时栈的会话守卫，即使栈已被清空，也不能再次进入原完成方法或用途回调。这两个包装的原调用异常及原生结果让步路径按会话实例关闭，避免误清回调替换的记录。

已有 12 组 `verify/item_use_cycle/*` 增补以下检查，不新增选择组：准备后加入原生格挡和装备组件、使用中加入原生消费组件、原生返回的替换栈、最后一份丹药的剩余物品、冷却仅在完成后生效、原生完成返回替换或原地修改时不再执行业务、清空原栈后重入、原生完成异常与 Start 监听器异常清理。原生完成的替换 / 修改及清空重入检查直接向会话包装层提供原调用；格挡、装备、消费、剩余物品和冷却走实际物品及实体调用链。
