# 85 进度记录按所有者种类分开存放设计

**状态：已落地（仅编译验证，探针未实跑）。** 2026-10-11。用户要求："不再统一存储 Progression，改成类似
`DataStorageHolder` 的模式，做一组的 instance（注意要泛型，因为 Map 的 Key 改成 `Holder<T>` 强类型），然后
再让 creature 和 technique 分别拿一份 `ProgressionHolder`，这样就能分开了"；随后追加："`ProgressionAttachment`
应该不再使用，`ProgressionHolder` 放入各自 attachment，同时 `ProgressionHolder` 也要处理升降级"。

## 1. 要修的是什么

`mxt:progression` 一份附件装全体所有者的等级，键是**所有者 id 一个 `Identifier`**：

```java
// 修之前
HolderHelper.idOptional(holder) == holder.unwrapKey().map(ResourceKey::identifier)
```

`HolderHelper` 把 `ResourceKey` 的第二段（注册表）丢掉，只留 `Identifier`。于是 `technique mxt_test:x` 与
`creature_profile mxt_test:x` **在附件里是同一个键、共用同一格**。没有任何跨注册表的唯一性检查在拦这件事，
唯一的护栏是"约定上不要撞名"（主包 0 功法 / 0 档案，测试包 7 功法 / 2 档案，交集 0）。

撞名的后果逐条：

| 位置 | 症状 |
| --- | --- |
| `ProgressionDriver.promote` | 两条链互相污染，一个身体上的记录被另一条链的 `next_level` 推着走 |
| `ProgressionAdminService.setLevel` | 靠 `heldBy(...).findFirst()` 认所有者，取的是**注册顺序**（`CultivationHooks` 先于 `CreatureHooks`），所以 `/contract level` 可能拿功法链去校验灵宠的等级 |
| `TechniqueService.forget` / `CreatureProgressionService.clear` | 互相删掉对方的记录 |
| `ProgressionEntityCondition.owner` | 一个裸 `Identifier` 说不清指的是哪一类 |

## 2. 采纳的形状

**种类由"哪份附件装着它"表达，而不是由键里的一个描述符表达。**

- 新增 `data/progression/ProgressionHolder<T extends ProgressionOwner>`：泛型，键是 `Holder<T>`，
  **注册表维度因此留在键里**，一个功法与一个档案即使 id 相同也是两个所有者、两格。
- `SpiritIdentityAttachment` 装 `ProgressionHolder<Technique> techniqueLevels`（存档字段 `technique_levels`）。
- `CreatureSpiritAttachment` 装 `ProgressionHolder<CreatureProfile> profileLevels`（存档字段 `profile_levels`）。
- **`ProgressionAttachment` 与 `MxtAttachments.PROGRESSION` 整个删除**；`ProgressionKind` 那套"种类描述符"
  方案（曾短暂存在）也删除——种类既然由附件回答，就不需要第二个描述符，也就不会有"描述符与键不一致"这种坏状态。

每个 holder 只认它自己那一张注册表的键码（`ProgressionHolder.codec(Codec<Holder<T>>)`，两侧各传
`RegistryFixedCodec.create(MxtResourceKeys.TECHNIQUE / CREATURE_PROFILE)`），所以**一份 holder 从形状上就
解不出别类的键**。

### 2.1 `EntitySources.Owner` 带上 holder

所有者与它的 holder 一起交给调用方，服务因此不需要"按 id 再去哪份附件里找"：

```java
public record Owner<T extends ProgressionOwner>(Holder<T> holder, ProgressionHolder<T> levels) {
    public Identifier id() { return HolderHelper.id(this.holder); }
    public T definition() { return this.holder.value(); }
}
```

`EntitySources.Grants.collect` 的 `ProgressionAttachment progress` 参数**删除**：授予系统读自己那一类的附件，
这是"种类由来源回答"的同一句话。`EntitySources.held(Entity, Identifier)` 保留（命令 / 脚本的裸 id 入口），
但它现在只有"按 id 问一处"的能力，**id 撞名时它是模糊的**——所以能分清种类的调用方直接问自己的来源
（`ContractCommand.level` 问 `CreatureSpiritAttachment`，`TechniqueService.forget` 问
`SpiritIdentityAttachment`）。

### 2.2 holder 自己处理升降级

这是本次新增的能力（此前只有 `setLevel` 一个写入方向）：

| 成员 | 语义 |
| --- | --- |
| `current(owner)` | 记录，或所有者自己的 `entryLevel`（从未晋升时） |
| `next` / `previous` | 链上下一格 / 上一格；`previous` 只在有记录时才有答案（入口级以下不属于这条爬升） |
| `promote(owner)` | 上一格，链顶与无链都返回 false |
| `demote(owner)` | 下一格；**落到入口级 = 清掉记录**（见下） |
| `follows` / `rank` / `levelCount` | 可达性与链上位置 |
| `set` / `clear` / `prune` / `retainOnly` / `clear()` / `setLevels` | 写入 |

**"只在晋升后才写入"这条口径不变，并因此得到一个好处**：入口级 = 没有记录。所以

- 数据包把某条链的入口级抬高时，**所有从未晋升过的身体自动跟着走**（它们本来就没记录）；
- `demote` 落到入口级时 `set(owner, null)`，记录被清掉而不是写入"入口级"这个值；
- 反过来，`set(owner, entryLevel)` 与 `set(owner, null)` 同义，`clear` 的判据只有一处。

`prune`（记录已不在自己链上）与 `retainOnly`（记录的主人已经不被持有）都只在真的删了东西时才标脏。

### 2.3 脏标记：holder 不知道附件类型

沿用 `DataStorage` 那一套"写入方不回调附件"的反面 —— 这里 holder **必须**标脏（它改了存档内容），但
**不能 import 附件类型**（会反向依赖）。做法是抄 `DataStorageHolder` 的思路但只取一半：holder 收一个
`util/ShouldSyncAttachment` 引用，`ownedBy(host)` 交上来，写入口调 `host.markDirty()`（`ShouldSyncAttachment`
的 `markDirty()` 是无参 final 方法，`checkDirty()` 读即清，`MxtAttachments.flushDirtyAttachments(Post)` 据此同步）。

### 2.4 缺席字段的默认实例必须复制

`lenientOptionalFieldOf(name, default)` 会拿**同一个** default 实例给每一次解码，而 holder 里是一张可变 Map：
两份身体共用一份 holder 就会互写。所以：

- 两份附件都给 `Optional` 之外的**显式 default**（`new ProgressionHolder<>()`），
- **`ownedBy(host)` 复制那张 Map**（不是共享引用），构造器只经 `ownedBy` 接收 holder。

这条是硬约束：`ProgressionHolder` 的"值相等"（`equals` / `hashCode` 只比 `levels`）也是为它服务的——
可选字段的省略判据是"值等于默认值"。

## 3. 各调用点的落点

| 文件 | 改法 |
| --- | --- |
| `ProgressionService` | 全部经 `EntitySources.Owner` 问 holder；`rankFromEntry` / `levelCount(ProgressionOwner)` 挪进 holder（它们只需要链与 `entryLevel`，不需要身体）；`pruneForeignLevels` 保持"先读记录、真删了才计数与报日志" |
| `ProgressionDriver` | 用 `holder.set` |
| `ProgressionAdminService` | 保留 `Identifier` 签名（命令 / 脚本入口），内部走 `EntitySources.held`；新增 `Owner` 重载给能分清种类的调用方（`ContractCommand`） |
| `ProgressionDamageMultiplier` | 遍历 `heldBy` → `recorded`/`current`，逻辑不变 |
| `ProgressionEntityCondition` | `heldBy` + `current`，`owner` 仍是裸 id 列表（问"任一所有者"，不指定种类） |
| `TechniqueProgress` | `rows(spirit, resources, ctx)` 少了 `ProgressionAttachment` 参数 |
| `TechniqueService.forget` | 收 `@Nullable Holder<Technique>`（按 id 解不出 holder 时留给 KubeJS 那一层先解）；记录清理由 `spirit.techniqueLevels().clear` |
| `CreatureProgressionService.clear` | 清 `CreatureSpiritAttachment.profileLevels()` |
| `LifeSpanService` | `setLearnedTechniques(List.of())` 已经会 retain 掉全部记录，所以那句 `PROGRESSION.clear()` 直接删除 |
| `TechniqueCommand.repair` | `pruneLevels` 的 Map 键改成 `Holder<Technique>`（比较用 `HolderHelper.id`） |
| `MxtKubeJsApi` | 四处 `progression*` 改走 `EntitySources.held`；`forgetTechnique` 先按 id 解 holder（这同时修掉了 `TechniqueService.forget` 改签名后留下的编译错） |
| `InformationPanelScreen` | 少传一个附件参数 |
| 测试探针 | 6 处改读各自附件（含新增的降级腿） |

## 4. 存档形状

老形状 `{"levels": {<identifier>: <progression>}}` 被替换：

```json
{ "technique_levels": { "<功法 id>": "<progression id>" } }   // spirit_identity
{ "profile_levels":   { "<档案 id>": "<progression id>" } }   // creature_spirit
```

两者都是**可选字段**，老存档里的 `progression` 附件整体变成无人读取的孤儿数据（`RecordCodecBuilder` 对未知
字段静默丢弃是既定口径，见 `AGENTS.md` §4）。**这是一次破坏性迁移**：老存档的等级记录会丢，需要 `/reload`
之外的迁移工具时由管理员用 `ProgressionAdminService` 重新写。

## 6. 边界与未做的事

- **`EntitySources.held(Entity, Identifier)` 在 id 撞名时是模糊的**（`findFirst` 取注册顺序）。命令与脚本的
  裸 id 入口仍是这个形状；要精确就必须点名种类（`ContractCommand` 那样直接问自己的附件）。**没有加"跨注册表
  唯一性检查"**——本设计正是为了不再需要它。
- `demote` 目前**没有真实的游戏内调用点**（只有探针），它是本次明确要求提供的能力；`/contract level` 写一个
  更低的等级走的是 `set`，效果相同。
- 未做：老存档的迁移工具；`/technique forget` 按"身体里还存着、当前包已不提供"的引用清记录时，若该引用连
  `Holder` 都解不出（`MxtDatapackRegistries.holder` 回空），`forgetTechnique` 会返回 `ABSENT`——这是本次保留
  的既有边界。
