# 元素与物品通道：四项需求的可行性分析

## 基准

- 对着读的代码：`runtime/element/ElementReactionService.java`（附着与反应）、`data/cultivation/ElementReaction.java`（反应的字段）、`data/cultivation/Element.java`（`damage_types` / `damage_attachment` / `attachment_decay`）、`runtime/damage/*`（两层管线的元素来源）、`runtime/ability/AbilityEventBridge.java`（技能挂的事件）、`registry/MxtFormulaVariables.java`（公式能读到什么）、`data/trigger/TriggerRule.java` + `data/context/TriggerContext.java`（触发器能拿到什么）。
- 起因（用户 2026-09-22 提问）：四项"能不能做"——
  1. 攻击方自身元素不与目标反应，但与所持物品反应；
  2. 武器元素与攻击方自身冲突时降低能力；
  3. 被击者的法宝等被动技能物品抵消部分元素反应；
  4. damage type 分组。
- **本文只做可行性判断，不动代码。**

## 先讲清两条既有机制，后面四项都由它们决定

**（甲）每一击只有一个"元素集合"，且它被用两次。** `DamageEventBridge` 用 `DamageElements.strike(source)` 得到集合后，**同一个集合**先交给第二层减免，紧接着交给 `ElementReactionService#applyFromStrike` 做附着。元素的来源只有两种：伤害类型被某元素**认领**，或者没人认领时**回落到攻击者的灵根**；管线不记录"这次是哪一种"。文档里"读一次来源、用两次"说的就是这件事。

**（乙）附着量是"元素"的属性，不是"来源"的属性。** `Element#damageAttachment`（默认 `0`）决定一次打击留下多少，`attachment_decay`（默认 `0`）决定每 tick 掉多少；两者默认都是 0，所以**默认情况下元素是纯关系、不累积、也就不会反应**。反应本身（`mxt:element_reaction`）只认**实体**身上的附着，`condition` 是 `EntityCondition`，**看不到伤害类型，也看不到伤害来源**。

顺带一条对四项都重要的限制：**数据包无法在"这一击落地前"改它的数值**。第一层的因子只来自 `AbilityService#withAbilityScaling` 写进公式上下文的 `damage_multiplier` / `element_modifier`；技能侧挂的是 `LivingDamageEvent.Post`（打完之后），没有任何订阅者能在 `LivingIncomingDamageEvent` 上按物品改数。触发规则（`TriggerRule` = 触发器 + 条件 + 行为）能执行任意 `EntityAction`，但那是"事后做事"，不是"改这一击"。

## 一、攻击方自身元素不与目标反应，但与所持物品反应

### 前半：自身元素不与**目标**反应

**基本上已经能做到，而且默认就是如此。** 只要不给那个元素写 `damage_attachment`，它就算作为这一击的元素参与了减免，也不会在目标身上累积，于是永远不会触发反应。另一种写法是让每一击都声明 `damage_type`/`element`（声明了就用认领者，不再回落到攻击者灵根），攻击者的身体元素根本不会成为这一击的元素。

**做不到的是"按来源区分"**：同一个元素，"来自身体时只算关系不累积、来自武器时要累积"——因为附着量是元素自身的属性，而且每击只有一个集合（机制甲、乙）。要做到得新增一个口径，例如给 `Element` 加"哪些来源会附着"的字段，或让 `DamageElements` 把来源（认领/回落/声明）一并交出来。

### 后半：自身元素与**所持物品**反应

**用 `mxt:element_reaction` 做不到。** 反应的定义是"某实体身上的附着达到 demand → 执行 action"，它挂的是**实体的附件**；物品不是实体，没有附着可攒。而且"物品的元素"目前**根本没有定义**（见下）。

能用现有零件近似写出来的一条路：**触发规则 + 条件 + 行为**。例如一条 `mxt:attack` 规则，条件 `mxt:has_element`（自己带火）+ `mxt:equipped_item`（手上是水属物品），行为 `mxt:damage`（打自己）、`mxt:attach_element`、或 `mxt:add_resource`（负值）。代价是它写在**规则**里而不是元素定义里，"反应"这两个字在数据包里就没有统一位置了。

**"物品的元素"今天有什么？**

| 可能读法 | 现状 |
| --- | --- |
| 灵草的 `element_tags` | **有**，并且可通过 `mxt:item_matcher` 里的 `mxt:herb_tag` 判定（`HerbTagEntry`） |
| 物品里存的灵气 → `Aura#aura_type` | 数据在（`mxt:spirit_storage` / `mxt:item_aura` 组件 + `Aura.aura_type`），但**没有任何代码把"物品的元素"读出来** |
| 武器/法器自己的元素 | **没有这个字段**（`weapon_binding` / `item_binding` / `artifact` 都不带元素） |

所以这一项要做的第一步是**定义"物品的元素"**：要么立一条"物品元素 = 它存/声明的那份灵气的 `aura_type`"的口径（不加字段），要么给绑定/法器加一个 `element` 字段。

## 二、武器元素与攻击方自身冲突时降低能力

三个缺口叠在一起：

1. **物品元素**：同上一节，不存在。
2. **"冲突"没有定义**：元素之间只有 `overcomes` / `adapted_to` 两条关系（乘法）；`conflicting_elements` 是**灵根授予时的互斥**，不参与伤害。所以"武器的水克我的火"要用哪条关系、方向如何，得先定。
3. **没有"攻击前改这一击"的钩子**：如上（甲、乙之外的那条限制），数据包改不了这一击的数值；`element_modifier` ≠ 这个用途，它是"这次施放的亲和"，由灵根算出。

**能近似的**：`mxt:attack` 规则给攻击者上负面效果、扣资源、或打一点自伤（"反噬加重"）。**改不了的是这一击本身的伤害**——那需要管线多一个因子。

最小可行做法：在第一层加一个来源为"武器元素 vs 自身元素"的因子（例如 `element_conflict_multiplier`，与 `element_modifier` 同层），由管线自己算并乘进去；这属于**倍率语义**变更，按仓库约定要先拍板。

## 三、被击者的法宝等被动物品抵消部分元素反应

分三种"抵消"，现状完全不同：

| 想要的效果 | 今天能不能 | 靠什么 |
| --- | --- | --- |
| 带着某法宝时**这条反应不触发** | **能** | `mxt:element_reaction` 的 `condition` 是 `EntityCondition`，可用 `mxt:has_equipped_item` / `mxt:item_matcher` / `mxt:has_ability` 判定 |
| **削减反应伤害**（连续比例） | **体质能，法宝不能** | 反应的 action 一般写 `mxt:damage`（无归属）→ 走第二层 → 受击者的 `damage_taken_multiplier` 生效。但那是**体质**字段，法宝/被动技能给不出管线因子 |
| 法宝**直接**提供一个减伤因子 | **不能** | `Ability.modifiers` 只加原版属性（护甲等），管线不读它；反应也没有自己的倍率字段 |

近似做法有两条，都绕道：① `mxt:element_reaction` 的 action 用 `mxt:if_else` 分档（带法宝打 6、不带打 12）——"部分抵消"变成硬分档；② 法宝授予一条被动技能，用它自己的 `mxt:equip` 触发规则跑 `mxt:grant_physique`，用体质去削减——减的是**所有**伤害，不只是反应。

要注意反应还**看不到伤害类型**（机制乙），所以"只对某类伤害引发的反应生效"这种条件写不出来。

## 四、damage type 分组

**分组这件事本身今天就有**：原版 `damage_type` 注册表上的标签（模组自带的 `mxt:no_bonus`、原版的 `is_fire` / `bypasses_armor` / `is_projectile` 等）。现在能被消费的地方有三处：

- `element.damage_types` 里写 `#命名空间:标签`（认领一族伤害类型）；
- 伤害条件 `mxt:damage_type_tag`（可挂在技能的 `damage_condition` 上）；
- 标签驱动的管线规则（`mxt:no_bonus` 就是这一类）。

**做不到的三件事**（都是"分组不只是选择器"才需要的）：

1. **分组不带内容**：标签只有成员，没有字段。"这一组按另一套口径结算"需要一个新的动态注册表（例如 `mxt:damage_type_group` 带自己的规则字段）。
2. **`element.damage_types` 是扁平列表**：`List<Either<Holder<DamageType>, TagKey<DamageType>>>`，不能给每个类型/标签单独配 `damage_attachment`。所以"同一个元素，被 A 组伤害打中累积 4、被 B 组打中累积 8"写不出来——附着量只有元素级的一个数字。
3. **反应看不到伤害类型**：`element_reaction.condition` 是实体条件，没有 `DamageSource`，所以"某组伤害不引发反应"只能靠把那些类型的 `damage_attachment` 归零来间接实现。

## 落地记录（2026-09-22，批次一：物品元素）

用户拍板：**口径兜底 + 字段覆盖**。已实现的部分：

- **读取口** `runtime/cultivation/ItemElements`（`Elements` 的物品侧对偶），两级：
  1. **定义声明**：`ItemBindingService.weapon(access, stack)` / `ItemBindingService.binding(access, stack)`（本轮把它从 private 改成 public）/ `ArtifactService.definition(access, stack)` 各自取第一个匹配（`ItemMatcher` 的常规读法），三条结果**取并集**，每条经 `Elements.expand` 展开标签并过滤 `mxt:disabled`。
  2. **物品携带的灵气**：一个都没声明时，`mxt:spirit_storage` 组件的 `soleAura()`，为空再落到 `ItemAuraService.type(access, stack)`（即 `mxt:item_aura` 定义声明的灵气），取该灵气的 `aura_type`。**存量为空**因此读作"它声明的那种灵气"，与 `SpiritStorageComponent` 的既有口径一致。
  3. 法器 `spirit_capacity` 的键**刻意不参与**：那是"能装什么"，不是"是什么"。
- **字段**（都是 `HolderOrTag<element>[]`，默认 `[]`，末尾追加，不动既有键序）：`weapon_binding.element`、`item_binding.element`、`artifact.element`。
- **消费面**：新物品条件 `mxt:item_element`（`ItemElementCondition`，`elements` 必填、空列表加载期拒绝），读同一口径。
- **形参类型用 `RegistryAccess` 而不是 `HolderLookup.Provider`**：`Provider.lookupOrThrow` 返回 `RegistryLookup<T>`，拿不到 `Elements.expand` 需要的 `Registry<Element>`；`Level#registryAccess()` 正好给的是 `RegistryAccess`。
- **没有 memo**：读取要走绑定注册表扫描，调用方应在一次结算里只问一次（已写进类注释，后面接管线时按这条来）。
- 测试包：`bound_sword` 的 `weapon_binding` 声明 `["mxt_test:fire"]`，`spirit_gathering_jade` 的 `artifact` 声明 `["#mxt_test:basic"]`（= 火 + 水）；`/mxt_test element` 第 12 条腿断言钻石剑 = {火}、紫水晶碎片 = {火, 水}、青霄灵晶 = {火}（走灵气回落，`mxt_test:spirit_power` 的 `aura_type` 是火）、木棍 = 空，并断言条件给出同样答案。

**批次二起（未做）**：2 的自冲突因子、3b 的法宝减伤因子、4 的分组带内容。设计口径见上面的「要动手时的最小路径」。

## 落地记录（2026-09-22，批次二：来源区分 + 自冲突因子）

用户拍板：**复用 `conflicting_elements` + `Element` 新字段**。已实现：

- **来源区分（1a）**：`DamageElements` 多出 `Origin`（`TYPE` = 伤害类型被认领、`ROOTS` = 没人认领回落到攻击者灵根）与 `Strike(elements, origin)` 记录，新入口 `reading(Level, Optional<Holder<DamageType>>, Entity)` / `reading(DamageSource)` **一次读出两半**（元素与来源必须来自同一次查表，否则调用方可能把 A 的元素配上 B 的来源）；两个旧的 `strike(...)` 保留为 `reading(...).elements()` 的薄包装，所以条件（`mxt:element`）、审计与既有调用点一行都不用改。
  - **口径**：`DamageEventBridge` 只用同一来源的元素做减免，但**只有 `Origin.TYPE`** 才把它交给 `ElementReactionService#applyFromStrike`。于是"身体里的元素只决定这一击打多疼，不在目标身上留附着"——灵根管伤害、武器/术法管附着。
  - **这是行为变更**：此前回落到灵根的打击只要元素写了 `damage_attachment` 就会累积。测试包元素探针第 9 条腿的 `metal_left` 期望因此从 `3.0` 改成 `0.0`（那条打击没有声明类型），并在伤害探针新增 `origin` 腿：同一发 10 点火焰，走被认领的 `minecraft:magic` 留 `4.0`、不声明类型留 `0.0`。
  - `ElementReactionService#applyFromStrike` 本身仍是"给什么就附什么"（它拿不到来源），分流写在管线里，注释已说明。
- **自冲突因子（2）**：`Element` 新增 `conflict_multiplier`（Double，默认 `1.0`，加载期校验有限非负）。`DamageCalculationService#selfConflictMultiplier(attacker)` 读**主手物品**的元素（`ItemElements`）与攻击者**在效灵根**的 `conflicting_elements`，命中就乘上那个元素自己的 `conflict_multiplier`；它被折进第一层，排在 `element_modifier` 之后、`pair`（体质打出 × 克制）之前。
  - **同一个元素只乘一次**，无论几条灵根与它相冲（否则两条相冲灵根会把它平方）；**不要求这一击用的就是那个元素**（跟自己的武器较劲，打什么都弱），这是按用户原话「武器的元素和攻击方自身冲突的时候，降低能力」的字面读法。
  - 数值住在**被握着的元素**上而不是灵根上：它是"我被硬用"的自我声明。
  - 夹具：`mxt_test:water` 的 `conflict_multiplier` = `0.5`，新 `weapon_binding/water_sword`（金剑）声明 `element: ["mxt_test:water"]`；探针腿让 `anti_water_root`（火体、`conflicting_elements` 含 water）握金剑打 4 点伤害 → 第一层 `2.0`，空手 `4.0`，实机掉血 `2.0`。
- 未做的判定：**元素反应本身不受自冲突影响**（因子只作用于第一层伤害），法宝减伤与分组留到批次三。

## 落地记录（2026-09-22，批次三之 3b：法宝抵消元素反应）

用户选的是"给法宝/被动一个管线因子"。落地形状与理由：

- **着力点选在"攒的速度"而不是"反应的效果"。** 反应的效果来自 `element_reaction.action`，那是任意数据包行为，管线无法在不改动作系统的前提下缩放它；而附着的量恰好有一个合法的统一位置（`ElementReactionService#applyFromStrike` 的调用点）。所以：**受击方携带物声明的 `attachment_multiplier`（Double，默认 `1.0`）相乘后乘在附着量上**，`0.5` 只留一半、`0` 一点也不留（于是那条反应永远不会被这一击触发）。
  - 要说清的边界：它压的是**攒的速度**，反应自身的效果（例如那段伤害）不受影响；想让反应**伤害**也变轻，用受击者体质的 `damage_taken_multiplier`（那条打击无归属，会走第二层）。这两条路在文档里都写了。
- **字段位置**：与批次一的 `element` 一样放在三个物品定义上（`artifact` / `weapon_binding` / `item_binding`），校验用新加的 `MiscCodecs.NON_NEGATIVE`（`Codec.doubleRange(0, MAX)`，负值与 NaN 都在加载期被拒——`NaN` 被拒是因为 `Double.compareTo` 把它排在最大之上）。
- **"携带"沿用既有口径**：`ArtifactUpkeepService#carried`（双手 + 每个 Curios 槽），本轮由 private 改为 public 并加注释说明"谁携带"只有一个定义；法器放在护符槽照样生效。
- **执行点**：`DamageEventBridge` 在附着那一步把 `DamageCalculationService#attachmentMultiplier(target)` 交给 `applyFromStrike` 的新重载（旧三参重载保留，等价于倍率 1.0，直接调用者不受影响）。
- 探针：受害方主手拿 `minecraft:prismarine_shard`（被 `ward_jade_talisman` 认领，本轮给它加 `attachment_multiplier: 0.5`）→ 同一发被认领的 10 点火焰留 `2.0`（空手 `4.0`）、掉血仍 `10.0`，并直接断言 `attachmentMultiplier` 为 `0.5` / 空手 `1.0`。
- 未做：法宝**不能**压制反应自身的效果（见上），也没有做"抗性上限/下限"之类的额外口径。

## 落地记录（2026-09-22，批次三之 4：`damage_types` 能带自己的附着量）

用户选的是"先扩 `element.damage_types` 支持 per-entry 数值（旧写法仍接受）"。落地：

- **新值类型** `data/cultivation/DamageTypeClaim(type, Optional<Double> damageAttachment)`，`CODEC = Codec.either(holderOrTag, 对象)`：
  - 裸 `"minecraft:magic"` / `"#命名空间:标签"` = 老写法，走元素自己的 `damage_attachment`；
  - `{"damage_type": "minecraft:lava", "damage_attachment": 2.0}` = 这一类打击自己的量；`damage_attachment` 可省略（等于元素默认值），**写 `0` 是"这一组不累积"的正经答案**（`Optional.of(0.0)`，与"没写"区分得开）。
  - 序列化稳定：没有自己数值的 claim 会写回裸字符串。
- `Element#claims` 改成对 claim 逐个 `matches`（`RegistryCodecs.matches` 的 tag 展开没变）。
- **反查表形状变化**：`indexes` 从"类型 → 元素列表"变成"类型 → `DamageElements.Claim(元素, 附着量)`"，附着量在**建表时**按"claim 自己的数 or 元素默认值"解析好（`Element` 的值那时就在手边）。同一个元素对同一类型写两条 → **第一条生效**（沿用原先 `claimants.contains` 的去重读法）。
- `DamageElements.Strike` 多一张「元素 → 附着量」表，`reading(...)` 一次性给出元素 / 来源 / 量（`Origin.ROOTS` 也给表，值取元素默认值，反正它不会走附着）。
- `ElementReactionService#applyFromStrike` 新增收这张表的入口（配同一轮的法宝倍率），旧的 Set 入口保留并委托（等于用元素默认值）。
- 夹具与探针：`mxt_test:fire` 的 `damage_types` 改成混写（`magic` 裸串、`lava` 对象带 `2.0`），伤害探针新增 *分组腿*：同一发 10 点火焰在无灵根靶子上，走 `magic` 留 `4.0`、走 `lava` 留 `2.0`，掉血都是 `10.0`。
- 边界：这条只影响**被认领**的打击（回落到灵根的本来就不附着）；`mxt:no_bonus` 的直通仍然优先于一切。

## 汇总

| # | 需求 | 现状 | 判定 |
| --- | --- | --- | --- |
| 1a | 自身元素不与目标反应 | `damage_attachment` 默认 0；声明伤害类型即可不回落到灵根 | ✅ 能（但**不能按来源**区分累积与否） |
| 1b | 自身元素与所持物品反应 | 物品无附着、无元素字段 | ❌ 反应机制做不到；触发规则可近似 |
| 2 | 武器元素与自身冲突 → 降低能力 | 无物品元素、无"冲突"定义、无伤害前钩子 | ❌ 需要新机制（新因子 + 物品元素） |
| 3a | 法宝让某条反应不触发 | `element_reaction.condition` | ✅ 能（全有全无） |
| 3b | 法宝削减反应伤害 | 体质已生效；法宝给不出因子 | ⚠️ 只能绕道（分档 / 法宝→体质） |
| 4 | damage type 分组 | 原版标签 + `mxt:damage_type_tag` | ✅ 作为选择器可用；❌ 分组不带内容 |

## 要动手时的最小路径（每条都要先拍板）

| 目标 | 最小改动 | 影响面 |
| --- | --- | --- |
| 物品元素 | 不加字段：口径定为"物品存/声明的灵气的 `aura_type`"；或加字段：`weapon_binding`/`item_binding`/`artifact` 增 `element` | 新口径影响所有读物品的元素判定；加字段属于**新增数据包字段**（三处文档 + 测试包） |
| 来源区分（1a） | `DamageElements` 交出"来源"（认领/回落/声明），`applyFromStrike` 按来源决定是否累积 | **改变现有一击的行为**：目前回落来源也累积（只要元素写了 `damage_attachment`） |
| 自冲突（2） | 第一层加一个因子（武器元素 vs 自身元素），与 `element_modifier` 同层 | **倍率语义**变更，先拍板 |
| 法宝减伤（3b） | 让法宝/被动提供一个管线因子，或给 `element_reaction` 加自己的倍率字段 | 新字段 + 管线多读一处 |
| 分组带内容（4） | 新动态注册表 `mxt:damage_type_group`；或先给 `element.damage_types` 支持 per-entry 数值 | 新注册表要登记、三处文档、审计与文档站同步 |

## 不做的事

- 不为了实现这些去改 `ElementReactionService` 的链式上限与 `IN_CHAIN` 重入守卫——它们与本次讨论无关。
- 不把"物品元素"直接等同于灵草的 `element_tags`：那只是灵草一族，武器与法器没有这条通道，混为一谈会让后面两项建在沙子上。
