## 0. 需求与结论速览

| 需求 | 结论 | 要动的东西 |
|---|---|---|
| ①**仅凭功法修炼**，无功法无法修炼 | 给"要求"补一条能读到功法的条件（`mxt:technique`），写在 `cultivate_action.start_condition` / `condition` 上；再让**选择器按"适不适用"挑**，挑不到就报一个新的失败原因 | 1 个新实体条件 + `CultivationModeService.resolveAction` 改判定 + 1 个 `Failure` 值 |
| ②**修炼不受限制** | 就是"要求为空"的那条定义——**今天的行为**，一行数据不写即可 | 无（回归基线） |
| ③ 两种方式**同时存在**于同一个包 | 一条方式一个 `cultivate_action` 定义，"哪种方式生效"由每条自己的要求回答；不再需要"全局开关" | 无（靠 ①② 的同一套东西） |
| ④ 素材里的**双修** | 双修在今天没有任何加成（素材 §6.3 自己也是这么写的），所以它是**一条要求**而不是一套机制：新条件 `mxt:partner` 扫附近实体，内层是**双实体条件**——于是"对方在修炼"（`mxt:target_condition`）与"对方是我好友"（现成的 `mxt:friend`）都能直接写 | 1 个新实体条件 |
| ⑤ 素材里的**打坐蒲团** | "坐在蒲团上"= 一条 `start_condition`（`mxt:riding` 的内层双实体条件套 `mxt:entity_tag`，或 `mxt:on_block` 套方块条件）。缺的不是条件，是**数据包能开练的入口** | 2 个新实体行为 `mxt:cultivate` / `mxt:stop_cultivating` |
| ⑥ 素材里的**熟练度 → 层数 → 境界门槛** | **已经全都有**：`skill_stage.mastery` + `Technique.mastery_resource` + `TechniqueMasteryService`（熟练度满自动晋升）+ `StageConfiguration.condition`（晋升条件，写 `mxt:realm` 就是境界门槛）。缺的只是"修炼这一拍怎么涨熟练度" | 无（用 `tick_action` + `mxt:add_resource`，见 §4 的熟练度两行） |
| ⑦ 素材里的**层数 → 属性 / 层数决定速度** | 缺：`StageConfiguration` 只能给能力，不能给属性，也没有"本级覆盖修炼倍率" | `StageConfiguration` 加两个可选字段（§3.9，可与 ①② 分开做） |
| ⑧ 素材里的**互斥组 / 体质禁令 / 灵裕值中断 / 悟性** | 都已能表达（`exclusive_tags` / `learn_condition` + `mxt:physique` / `mxt:aura_range` + `aura_costs` / 属性即公式变量 `caster_<attribute>`） | 无 |

**一句话**：把"能不能练、拿什么练"从散落的五处收成**定义自带的入场要求**，并让选择器用同一把尺子挑——**① 和 ② 于是只是同一张表里两条要求不同的定义**，可以同时存在，且不写要求的老包行为不变。

## 1. 需求拆解

### 1.1 需求①"仅凭功法修炼，无功法无法修炼"

这句话有三种强度，必须挑一种（本稿按 (b) 设计，但 (a)(c) 都只是同一形状的写法）：

| 强度 | 意思 | 写法 |
|---|---|---|
| (a) 门槛 | 只要**任意**学过一门就能练 | `{"type": "mxt:technique"}` |
| (b) 分支 | **不同的功法/功法族走不同的方式**（不同消耗、不同倍率、不同场地） | 每条方式写自己的 `mxt:technique` 要求 + `match: all/any` + `#标签` |
| (c) 指定 | 只有**这一门**能练 | `{"type": "mxt:technique", "techniques": ["ns:xxx"]}` |

**结论**：不要做 (a) 那种"全局 bool"。做成 (b)，(a)(c) 都是它的退化情形；这样"凡人吐纳"与"青元剑诀"可以是两条方式，各有各的门槛与产出。

### 1.2 需求②"修炼不受限制"

= 一条**不写任何要求**的 `cultivate_action`（`start_condition` / `condition` 都不写）。这就是今天所有测试包定义的行为，所以 ② 是**回归基线**：改完之后，一个不写要求的包必须与今天逐 tick 一致。

### 1.3 需求③"两种方式同时存在"

这才是真正的设计约束：选择器不能再看"谁是默认/谁是第一个"，必须看**"这一条此刻适不适用于我"**。同时要避免出现"选到了却起不来"。

### 1.4 素材里与"方式"有关的条目（后面 §4 逐条映射）

蒲团=座位、修炼拍 20 tick、熟练度公式与悟性、单层进度上限、境界门槛、层数→属性、层数→真元速度、功法是"开关键"而非"加速器"、双修（同一本书 + 双方坐 + 5 格内）、散功、离婚罚款、HUD/面板、天妒之体禁令、互斥团簇、突破概率加成、无极培元功的专属路线。

## 2. 现状：一次修炼被五层门禁管着

### 2.1 五层门禁（都读代码得出）

| # | 在哪 | 字段 | 什么时候读 | 语义 |
|---|---|---|---|---|
| 1 | `Aura` | `start_cultivate_conditions` | **只在开始**（`CultivationActionService.canStartCultivation:76-80`） | 每条有 `first_realm` 的链都得通过 |
| 2 | `AuraZone` | `cultivate_condition`、`rules.cultivate_suppress` | 开始 + 每拍（`canCultivateInEnvironment:281-294`、`aura.suppressCultivate()`） | 环境；`mxt:aura_range` 被特判成"多个独立合格来源，任一命中即可"，`cultivation.forbid_without_eligible_aura` 决定"一个都没有"算不算停 |
| 3 | `RealmStage` | `cultivate_condition` | 每拍（`eligibleRealmCultivations`、`handlesNaturalRegeneration`） | 这条链的回复算不算数 |
| 4 | `CultivateAction` | `start_condition` / `condition` | 开始一次 / 每拍 | 这条方式自己的门槛 |
| 5 | `MxtServerConfig.Cultivation` | `forbid_without_eligible_aura`、`allow_movement` | 同上 / 渲染 | 服务器策略（**不是**数据包） |

状态侧：`CultivationAttachment`（`cultivate_action` 选中的那条、`cultivating`、`next_cultivate_tick`、`cultivate_cooldowns` 按方式分别记）。

### 2.2 三个"读不到"（本稿要补的就是这三个）

1. **读不到功法**：`MxtEntityConditions` 的 65 个实体条件里**没有任何一个提到 `technique`**（`has_ability` / `has_spirit_root` / `has_physique` / `realm` / `has_realm` 都有）；`exclusive_tags` 只管**学习瞬间**的互斥，不表达"要持有什么才能练"。
2. **读不到"在修炼"**：没有 `mxt:cultivating`；`CultivationAttachment.cultivating` 只被运行时代码读。
3. **读不到"身边有没有这样的人"**：注意**关系本身不是缺口**——玩家↔玩家的**有向**关系已经有了：好友系统（`FriendService`、`/friend`、持久附件 + 离线镜像、双实体条件 `mxt:friend`，见 `docs/guide/play/friends.md`），另有 `mxt:relation` / `mxt:same_team` / `mxt:distance`。缺的是那条**通用扫描**："以我为圆心 R 格内存在满足 X 的实体"。素材的双修（同一门功法 + 双方打坐 + 5 格内）正是这一类。
   ⇒ 直接后果：`mxt:partner` 的内层判据**必须是双实体条件**而不是实体条件，否则 `mxt:friend` 这种"只能两两提问"的判据嵌不进去。

### 2.3 起停入口只有键盘

`CultivationToggleC2SPayload` → `ServerNetworkHandler:125` → `CultivationModeService.toggle` 是**唯一**的玩家入口；非玩家由 `CultivationActionEventBridge` 每 tick 驱动，但**数据包/脚本里没有任何东西能把一个实体"开练"**（`MxtEntityActions` 里没有 `mxt:cultivate`；`MxtKubeJsApi` 只有 `addCultivation` / `tryBreakthrough`，没有功法查询与起停）。

⇒ 所以"蒲团"这类东西今天做不出来：条件能写"必须骑着蒲团"，但没人能"右键蒲团开始修炼"。

### 2.4 选择器今天是"盲选"

`CultivationModeService.resolveAction:66-72` 的顺序是：**① 注册表里第一条 `default: true`** → ② 附件里存着的那条 → ③ 注册表里第一条。两个后果：

- 只要存在一条 `default: true`，**存在附件里的选择永远选不上**（存储形同虚设）；
- 它不看要求，所以多条方式共存时"谁被选中"与"谁能用"完全无关。

## 3. 设计

### 3.1 一个概念

> **修炼方式（cultivation method）= 「入场要求」+「一次循环跑什么」。**

两条都在**同一个** `mxt:cultivate_action` 定义里，一条方式一个 JSON 文件。**不开新注册表**（否掉的方案见 §3.10）。

### 3.2 落点地图

| 件 | 做什么 | 优先级 |
|---|---|---|
| A `mxt:technique` 实体条件 | 读"我学过哪些功法" | P0（需求①） |
| E 选择器按适用性挑 | 多条方式共存 | P0（需求③） |
| B `mxt:cultivating` 实体条件 | 读"在不在修炼" | P1（双修维持、阵法/技能联动） |
| C `mxt:partner` 实体条件 | 读"身边有没有这样的人"（内层是**双实体**条件，好用上 `mxt:friend`） | P1（需求④） |
| D `mxt:cultivate` / `mxt:stop_cultivating` 行为 | 数据包能起停 | P1（需求⑤） |
| F `StageConfiguration` 加两个字段 | 层数→属性、层数→速度 | P2（需求⑦，可独立做） |
| G 具名中止原因 / 显式选择命令 / `mxt:mutual` | — | 推迟，见 §6 |

### 3.3 A：实体条件 `mxt:technique`

```json
{"type": "mxt:technique"}
{"type": "mxt:technique", "techniques": ["#mxt:sword_arts"], "match": "any"}
{"type": "mxt:technique", "techniques": ["mxt_test:qingxiao_breathing_manual", "#mxt:body_arts"], "match": "all"}
```

| 字段 | 类型 / 默认 | 语义 |
|---|---|---|
| `techniques` | `HolderOrTag<technique>[]`，默认 `[]` | 点名的功法或 `#标签`；**空 = 只要求"学过任意一门"** |
| `match` | `any`（默认）/ `all` | `any` 命中其一即可，`all` 全都要（`techniques` 为空时无意义） |

- 读的是 `SpiritIdentityAttachment.learnedTechniques()`，**与 `exclusive_tags` 的"持有 vs 生效"无关**（功法今天没有启用开关，灵根/体质才有）；要"停用"语义时用 `mxt:not` + 将来的功法开关，不在本稿内。
- 标签展开走既有的 `RegistryCodecs.resolve(..., Provider, key)`（客户端与服务端同一条路径），与 `granted_abilities` 同一口径。
- 空表**不是**恒真：`{"type":"mxt:technique","techniques":["#a:b"],"match":"all"}` 与 `[]` + `all` 的差别要在加载期点名（空 `techniques` + `match: all` 直接 `DataResult.error`，避免静默恒真）。
- 想表达"没有功法"用 `{"type":"not","condition":{"type":"mxt:technique"}}`，不另设 `invert` 字段。

### 3.4 B：实体条件 `mxt:cultivating`

```json
{"type": "mxt:cultivating"}
{"type": "mxt:cultivating", "action": "mxt_test:qingxiao_meditation"}
```

| 字段 | 类型 / 默认 | 语义 |
|---|---|---|
| `action` | `Holder<CultivateAction>`，可选 | 不写 = 只要在修炼；写了 = 必须正好在跑这一条 |

读 `CultivationAttachment.cultivating`（+ 可选的 `cultivate_action` 比较用 `Holder.is`）。**服务端权威**：客户端读到的是同步过来的状态，条件本身只在服务端求值。

### 3.5 C：实体条件 `mxt:partner`

```json
{"type": "mxt:partner",
 "range": 5.0,
 "count": {"min": 1, "max": 1},
 "bientity_condition": {"type": "and", "conditions": [
   {"type": "target_condition", "condition": {"type": "mxt:cultivating"}},
   {"type": "target_condition", "condition": {"type": "mxt:technique", "techniques": ["mxt_test:dual_manual"]}},
   {"type": "friend"}
 ]}}
```

| 字段 | 类型 / 默认 | 语义 |
|---|---|---|
| `range` | double，默认 `5.0`，范围 `0.5..32` | 以自己为中心的球形半径（**上限是为了把每 tick 的实体扫描关住**） |
| `count` | `{min, max}`，默认 `{1, 无上限}` | 命中数量区间；`max: 1` 就是素材里"一对一"的双修 |
| `bientity_condition` | `BiEntityCondition`，默认 `mxt:always_true` | **actor = 自己、target = 候选同伴**，所以既有双实体词汇全都用得上：`mxt:friend`（好友）、`mxt:distance`、`mxt:relation`、`mxt:same_team`、`mxt:undirected`；要测**对方自身**的状态就套 `mxt:target_condition`（它把内层 `EntityCondition` 作用在 target 上） |

- 字段名与 `mxt:riding` 的 `bientity_condition` 同形（那里 actor = 骑手、target = 坐骑），作者不用记第二套词汇。
- 自己永远不算；被扫的实体限 `LivingEntity` 且存活。
- **"好友才能双修"直接写 `{"type":"friend"}`**（好友有向）；"互相都是好友"今天没有直白写法（`mxt:undirected` 是"任一方向"），要用双重否定 `{"type":"not","condition":{"type":"undirected","condition":{"type":"not","condition":{"type":"friend"}}}}`——登记为将来可加的 `mxt:mutual`（§6）。
- 这是"关系"缺口的**最小落地**：它只回答"身边有没有这样的人"，**不建立持久关系**（谁是道侣、散伙代价 ⇒ §6）。
- 代价：每 tick 一次 `level.getEntities(aabb, predicate)`。所以 **① 上限 32；② 建议只写在需要的方式的 `condition` 里**；③ 探针里要有一条"两个人靠近/分开"的腿来钉住它（§8）。

### 3.6 D：实体行为 `mxt:cultivate` / `mxt:stop_cultivating`

```json
{"type": "mxt:cultivate"}
{"type": "mxt:cultivate", "action": "mxt_test:qingxiao_meditation"}
{"type": "mxt:stop_cultivating"}
```

- `mxt:cultivate`：走选择器（或指定那条）→ `CultivationActionService.start`。已经在本方式里 → 空操作；`ALREADY_ACTIVE` / 冷却 / 条件不满足 → **空操作**（行为的签名不带结果，见下）。
- `mxt:stop_cultivating`：等价于今天的 `CultivationModeService.stop`，并把该方式的 `cooldown` 写进附件。
- **只在服务端生效**，客户端/非 `LivingEntity` 直接返回。
- 行为系统不回传 `Result`（`EntityAction.execute` 是 `void`），所以"失败了为什么"不会自动有反馈。要提示就自己在数据包里用 `if_else` + `mxt:cultivating` 分支发消息；**本稿不给 `EntityAction` 加返回值**（那会牵动全部行为类型）。
- 有了它，"蒲团"才成立（`if_else` 的字段是 `condition` / `if_action` / `else_action`，`mxt:on_block` 的内层是**方块条件**）：
  ```json
  // 蒲团物品右键的行为（示意）
  {"type": "if_else",
   "condition": {"type": "on_block", "condition": {"type": "block_id", "block": "mxt_test:cushion"}},
   "if_action": {"type": "mxt:cultivate"}}
  ```

### 3.7 E：选择器改成"按适用性挑"

`CultivationModeService.resolveAction` 换成带实体的版本，顺序改成：

```
applicable(action) = action.start_condition().test(entity, context)
                     && CultivationActionService.canStartCultivation(entity, context)
1. 附件里存着的那条，若 applicable          ← 存储优先于 default（今天反着）
2. applicable 里第一条 default == true
3. 注册表里第一条 applicable
4. 一条都没有 → Failure.NOT_APPLICABLE
```

四条硬约束：

1. **同一把尺子**：`applicable` 用的判定与 `start` 里的 `conditionsMet` 是同一个表达式，杜绝"选到了却起不来"。
2. **冷却不进适用性**：否则"上次那条在冷却"会把玩家换到另一条方式上，等于绕过冷却。冷却仍然是开始时的 `Failure.COOLDOWN`。
3. **优先级 = 注册表顺序 + `default`**，不新增 `priority` 字段。要"这条优先"就写 `default: true`（同表多条 `default` ⇒ 注册表顺序决定，加载期不报错，但建议文档里劝一次）。
4. **行为变更（要拍板）**：今天 `default` 压过附件里的选择；改后存储压过 `default`。改的原因是③：多条方式共存时"玩家上次选的"必须比"包作者的默认"优先，否则附件字段永远读不到。

配套：
- `Failure` 加 `NOT_APPLICABLE`；lang 加 `actionbar.mxt.cultivation.failure.not_applicable`（zh「没有一门满足条件的修炼法门」/ en 同理）。**不要复用 `NOT_ACTIVE`**——那条已经用于"状态对不上"的运行时情形（今天 `resolveAction` 空手时也报它，属于借用；顺手改掉）。
- `/mxt cultivate status` 已经会显示选中的是哪种方式，不用改。
- `CultivationModeService.toggle` 的 `stopIfCultivating` / 自动突破 / 灵气分配三条路径**不动**（它们读的都是附件里存着的那条，而不是选择器的结果）。

### 3.8 两个需求的完整写法

**②不受限制**（= 今天的行为，也是"没有功法也能练"的包）：

```json
{
  "default": true,
  "tick_interval": 20,
  "absorb_amount": "1 + realm_rank * 0.05",
  "aura_gains": [{"id": "mxt:spirit_power", "amount": 1}]
}
```

**①仅凭功法**（同包里再加一条，两条可同时存在）：

```json
{
  "tick_interval": 20,
  "start_condition": {"type": "mxt:technique", "techniques": ["#mxt_test:meditation_arts"]},
  "condition":       {"type": "mxt:technique", "techniques": ["#mxt_test:meditation_arts"]},
  "absorb_amount": "2 + realm_rank * 0.1",
  "aura_costs": [{"id": "mxt:spirit_power", "amount": 1}],
  "tick_action": {"type": "add_resource", "resource": "mxt_test:sword_mastery", "amount": "1"}
}
```

**④双修**（在①的基础上把"对方"写进维持条件；`start_condition` 只要求"在场"，`condition` 要求"对方也在修"——这正是今天 `start_condition` / `condition` 的既有分工）：

```json
{
  "start_condition": {"type": "mxt:partner", "range": 5.0,
    "bientity_condition": {"type": "and", "conditions": [
      {"type": "friend"},
      {"type": "target_condition", "condition": {"type": "mxt:technique", "techniques": ["mxt_test:dual_manual"]}}
    ]}},
  "condition": {"type": "mxt:partner", "range": 5.0,
    "bientity_condition": {"type": "and", "conditions": [
      {"type": "target_condition", "condition": {"type": "mxt:cultivating"}},
      {"type": "target_condition", "condition": {"type": "mxt:technique", "techniques": ["mxt_test:dual_manual"]}}
    ]}}
}
```

> "**互相**在修炼"为什么不会死锁：`cultivating` 是**开始前就写好的持久状态**——A 先坐下（此时 B 还没修，A 的 `condition` 会失败并把 A 停掉）。素材的做法是每 tick 互相写对方的状态位；本设计的做法更简单也更可预测：**`start_condition` 管"能不能坐下"，`condition` 管"坐下之后还算不算数"**，所以只要 A、B 各自都能通过 `condition`，两边就都继续；一边站起来 → 另一边下一拍 `condition` 失败 → `Failure.CONDITIONS` 停下（今天的提示是 `actionbar.mxt.cultivation.failure.conditions`）。若一定要"必须同时坐下"，就用既有的 `mxt:cultivating` 条件把"对方已经在修"也写进 `start_condition`——语义变成"先后坐下"，与素材一致（素材里也是一个人先坐、另一个再坐）。

### 3.9 F：层数闭环（可选，可后做）

`Technique.configuration` 的值 `StageConfiguration` 现在只有 `condition`（到达该级的条件）+ `ability`（该级起累计生效的能力）。素材的"功法层数"还差两件事，加两个可选字段即可，**都在同一个 record 里，不开第二处**：

| 新字段 | 类型 / 默认 | 语义（与既有字段一起读） |
|---|---|---|
| `passive_modifiers` | `AttributeEntry[]`，默认 `[]` | **累积**：从入口级到当前级，每一级的都生效 → 对应"每突破一层永久加属性" |
| `cultivation_modifier` | `NumberProvider`，可选 | **覆盖**：当前级写了就用当前级的，否则回落 `Technique.cultivation_modifier` → 对应"层数决定真元/吸收速度" |

读法与落点：

- `ability` 保持"最低要求、累积"（既有口径，`SkillStageService.unlockedAbilities`）。
- `passive_modifiers`：`PassiveAttributeService.entries:107-108` 现在只读 `technique.passiveModifiers()`；改成"功法级列表 **++** 链上从入口到当前级的各级 `passive_modifiers`（按链序）"，沿用现有的 `kind = "technique"` + 功法 id 作为 source、下标在拼好的列表上递增。层数变化时后面的下标会移动，但那段本来就是"先算全集、再删多余、再逐个 apply"，不会留残留。
- `cultivation_modifier`：`CultivationAffinity.combine:97-101` 现在对所有已学功法**连乘**；改成"先取该功法当前级的覆盖值（`SkillStageService.currentStage` → `configuration.get(stage)`），没有则用功法级默认"，再连乘。**连乘口径不变**（多门功法各自贡献一次）。
- 素材的"熟练度增速与层数无关、与悟性有关"不需要新东西：悟性是属性，公式写 `caster_<attribute>` 即可（`MxtFormulaVariables.EntityVariable.state` 会先查属性、再查资源、再查元素）。
- 境界门槛（素材 §4.3 第二层卡）**今天就能写**：`{"type":"mxt:realm","realm":"…","comparison":"at_least"}`。

## 6. 不做 / 推迟（明写，免得当成漏了）

1. **熟练度原生化**：不加 `CultivateAction.mastery` 字段。理由：`tick_action` + `mxt:add_resource` 已经能涨熟练度，而"涨哪个资源"正是每条方式自己知道的事（一条方式一族功法时，让这一族共用同一个熟练度资源，或一门功法一条方式）。**约束要写进文档**：`skill_stage.mastery` 比的是**资源绝对值**（不是"这一门攒了多少"），所以两条功法共用同一个资源会被一起推着晋升。
2. **显式选择命令** `/mxt cultivate select`：先不做。多条方式同时适用时按 §3.7 的确定性顺序取第一条即可；真出现"同一个人两种方式都想留着"的包再加（届时顺序要写进文档）。
3. **具名中止原因**：`condition` 只回答真假，所以"同伴走了"与"功法被摘了"都会报同一句 `failure.conditions`。要分开就得给 `CultivateAction` 加"中止动作"字段（`RealmStage` 的 `fail_action` 是同一形状的先例）——推迟。
4. **道侣/散伙**：**关系不用新建**（好友系统就行），但"谁是道侣"这件事没有专门的持久字段，"散伙代价"也没有基座概念——都留给内容（好友 + 命令/技能）。C 只解决"身边有没有这样的人"。
5. **`mxt:mutual`（互相都是好友）**：`mxt:friend` 有向，`mxt:undirected` 是"任一方向成立"，所以"两人互相为友"今天只能靠双重否定（§3.5）。加一个包装类型很小，但没进本稿。
6. **共修加成（人数进公式）**：不加 `cultivators` 公式变量。多人共享灵气池今天已经有 `aura_zone.distribution`（`RANDOM` / `EQUAL` / `REALM_WEIGHTED`）+ `realm_stage.aura_share_weight` 两级分配，够用；"两个人修更快"属于内容（`absorb_amount` 写不出来时再加变量）。
7. **功法遗忘/散功入口**（审计 T6）：与修炼方式无关，但素材 §7.1 会撞上它——登记，不修。
8. **不给 `EntityAction` 加返回值**：D 的失败反馈只能靠数据包自己用条件分支写。
9. **功法"启用/停用"开关**：灵根/体质有（`CultivationToggleService`），功法没有。A 因此读的是"学过"而不是"生效中"。
