## 1. 需求拆解

### 1.1 需求①"仅凭功法修炼，无功法无法修炼"

这句话有三种强度，必须挑一种（本稿按 (b) 设计，但 (a)(c) 都只是同一形状的写法）：

| 强度 | 意思 | 写法 |
|---|---|---|
| (a) 门槛 | 只要**任意**学过一门就能练 | `{"type": "mxt:technique"}` |
| (b) 分支 | **不同的功法/功法族走不同的方式**（不同消耗、不同倍率、不同场地） | 每条方式写自己的 `mxt:technique` 要求 + `match: all/any` + `#标签` |
| (c) 指定 | 只有**这一门**能练 | `{"type": "mxt:technique", "techniques": ["ns:xxx"]}` |

**结论**：不要做 (a) 那种"全局 bool"。做成 (b)，(a)(c) 都是它的退化情形；这样"凡人吐纳"与"青元剑诀"可以是两条方式，各有各的门槛与产出。

### 1.2 需求②"修炼不受限制"

= 一条**不写任何要求**的 `cultivate_action`（`start_condition` / `tick_condition` 都不写）。这就是今天所有测试包定义的行为，所以 ② 是**回归基线**：改完之后，一个不写要求的包必须与今天逐 tick 一致。

### 1.3 需求③"两种方式同时存在"

这才是真正的设计约束：选择器不能再看"谁是默认/谁是第一个"，必须看**"这一条此刻适不适用于我"**。同时要避免出现"选到了却起不来"。

### 1.4 素材里与"方式"有关的条目（后面 §4 逐条映射）

素材里与"方式"有关的条目（后面 §4 逐条映射）：修炼拍 20 tick、熟练度公式与悟性、单层进度上限、境界门槛、层数→属性、层数→真元速度、功法是"开关键"而非"加速器"、双修（同一本书 + 双方坐 + 5 格内）、散功、离婚罚款、HUD/面板、天妒之体禁令、互斥团簇、突破概率加成、无极培元功的专属路线。（素材里的"打坐蒲团"已于 2026-09-27 移出范围：见文首修正二。）

### 2.3 起停入口只有键盘

`CultivationToggleC2SPayload` → `ServerNetworkHandler:125` → `CultivationModeService.toggle` 是**唯一**的玩家入口；非玩家由 `CultivationActionEventBridge` 每 tick 驱动，但**数据包/脚本里没有任何东西能把一个实体"开练"**（`MxtEntityActions` 里没有 `mxt:cultivate`；`MxtKubeJsApi` 只有 `addCultivation` / `tryBreakthrough`，没有功法查询与起停）。

⇒ 所以修炼的起停今天只有"玩家按键（客户端请求）"这一条路：数据包、脚本、非玩家实体都开不了练。**这条不再是缺口**：①–④ 全都建立在"玩家自己按键"之上，"右键某个东西开练"属于内容（2026-09-27 第二次修正已把蒲团移出范围，D 随之降为可选）。

### 2.4 选择器今天是"盲选"

`CultivationModeService.resolveAction:66-72` 的顺序是：**① 注册表里第一条 `default: true`** → ② 附件里存着的那条 → ③ 注册表里第一条。两个后果：

- 只要存在一条 `default: true`，**存在附件里的选择永远选不上**（存储形同虚设）；
- 它不看要求，所以多条方式共存时"谁被选中"与"谁能用"完全无关。

> **2026-09-27 已改**：`default` 字段删除，顺序变成"**附件里存着的那条优先，其次挑 `priority` 最大的一条**"——两个后果里的第一条没有了；
> 第二条（不看要求）仍在，即 §3.7 里还没做的那半件。
>
> **2026-09-27 修正三（已落代码，筛子按修正四调整过）**：这两步都要再改一次——**先在整张表里筛出 applicable 的（`start_condition` 与 `cultivate_condition` 都成立），再在筛出来的里面按 `priority` 挑**，
> 附件里存着的那条不再有特权。见 §3.7 与文首修正三。

## 3. 设计

### 3.1 一个概念

> **修炼方式（cultivation method）= 「入场要求」+「一次循环跑什么」。**

两条都在**同一个** `mxt:cultivate_action` 定义里，一条方式一个 JSON 文件。**不开新注册表**（否掉的方案见 §3.10）。

### 3.2 落点地图

| 件 | 做什么 | 优先级 |
|---|---|---|
| A `mxt:technique` 实体条件 | 读"我学过哪些功法" | **已落地**（2026-09-27） |
| E 选择器按适用性挑 | 多条方式共存 | **已落地**（先筛 applicable——`start_condition` 与 `cultivate_condition` 都校验——再按 `priority` 挑；`NOT_APPLICABLE` 已加） |

### 3.3 A：实体条件 `mxt:technique`

```json
{"type": "mxt:technique"}
{"type": "mxt:technique", "techniques": ["#mxt:sword_arts"], "match": "any"}
{"type": "mxt:technique", "techniques": ["mxt_test:qingxiao_breathing_manual", "#mxt:body_arts"], "match": "all"}
```

| 字段 | 类型 / 默认 | 语义 |
|---|---|---|
| `techniques` | `HolderOrTag<technique>[]`，默认 `[]` | 点名的功法或 `#标签`；**空 = 只要求"学过任意一门"** |
| `match` | `any`（默认）/ `all` | `any` 命中其一即可，`all` 全都要（`techniques` 为空时无意义） |

- 读的是 `SpiritIdentityAttachment.learnedTechniques()`，**与 `exclusive_tags` 的"持有 vs 生效"无关**（功法今天没有启用开关，灵根/体质才有）；要"停用"语义时用 `mxt:not` + 将来的功法开关，不在本稿内。

> **落地实况（2026-09-27）**：`data/condition/builtin/entity/HasTechniqueEntityCondition.java`，注册在 `MxtEntityConditions` 的 `technique`；
> 直接条目比较读的是"身体的授予账本"（`SpiritIdentityAttachment`），标签那一侧用 `Holder.is(TagKey)`；同名战利品条件（`HasTechniqueLootCondition`）

### 3.5 C：实体条件 `mxt:partner`

```json
{"type": "mxt:partner",
 "range": 5.0,
 "count": {"min": 1, "max": 1},
 "bientity_condition": {"type": "and", "conditions": [
   {"type": "target_condition", "condition": {"type": "mxt:cultivating"}},
   {"type": "target_condition", "condition": {"type": "mxt:technique", "techniques": ["mxt_test:dual_manual"]}},
   {"type": "friend"}
 ]}}
```

| 字段 | 类型 / 默认 | 语义 |
|---|---|---|
| `range` | double，默认 `5.0`，范围 `0.5..32` | 以自己为中心的球形半径（**上限是为了把每 tick 的实体扫描关住**） |
| `count` | `{min, max}`，默认 `{1, 无上限}` | 命中数量区间；`max: 1` 就是素材里"一对一"的双修 |
| `bientity_condition` | `BiEntityCondition`，默认 `mxt:always_true` | **actor = 自己、target = 候选同伴**，所以既有双实体词汇全都用得上：`mxt:friend`（好友）、`mxt:distance`、`mxt:relation`、`mxt:same_team`、`mxt:undirected`；要测**对方自身**的状态就套 `mxt:target_condition`（它把内层 `EntityCondition` 作用在 target 上） |

- 字段名与 `mxt:riding` 的 `bientity_condition` 同形（那里 actor = 骑手、target = 坐骑），作者不用记第二套词汇。
- 自己永远不算；被扫的实体限 `LivingEntity` 且存活。
- **"好友才能双修"直接写 `{"type":"friend"}`**（好友有向）；**"互相都是好友"写 `{"type":"mutual","condition":{"type":"friend"}}`**（2026-09-27 追加，见 §6 第 9 条）——`mxt:undirected` 是"任一方向成立"、`mxt:mutual` 是它的对偶"两个方向都成立"；在它落地之前只能靠双重否定 `not(undirected(not(friend)))` 表达。
- 这是"关系"缺口的**最小落地**：它只回答"身边有没有这样的人"，**不建立持久关系**（谁是道侣、散伙代价 ⇒ §6）。
- 代价：每 tick 一次 `level.getEntities(aabb, predicate)`。所以 **① 上限 32；② 它落在哪个条件上决定了这次扫描被问几次**——写在 `cultivate_condition` 里（双修就是这条）是"每次按 C 挑选 + 每拍结算"各一次，写在 `tick_condition` 里是"每拍维持"一次；③ 探针里要有一条"两个人靠近/分开"的腿来钉住它（§8）。

### 3.6 D：实体行为 `mxt:cultivate` / `mxt:stop_cultivating`

**已落地**（2026-09-27；需求 ⑤ 蒲团已删，所以它不是被需求逼出来的，而是"数据包 / 脚本 / 非玩家实体也能开练"这个事实的入口）。

```json
{"type": "mxt:cultivate"}
{"type": "mxt:cultivate", "action": "mxt_test:qingxiao_meditation"}
{"type": "mxt:stop_cultivating"}
```

- `mxt:cultivate`：走选择器（或指定那条）→ `CultivationModeService.start`。已经在本方式里 → 空操作；`ALREADY_ACTIVE` / 冷却 / 条件不满足 → **空操作**（行为的签名不带结果，见下）。
- `mxt:stop_cultivating`：等价于今天的 `CultivationModeService.stop`，并把该方式的 `cooldown` 写进附件。
- **只在服务端生效**，客户端/非 `LivingEntity` 直接返回。
- 行为系统不回传 `Result`（`EntityAction.execute` 是 `void`），所以"失败了为什么"不会自动有反馈。要提示就自己在数据包里用 `if_else` + `mxt:cultivating` 分支发消息；**本稿不给 `EntityAction` 加返回值**（那会牵动全部行为类型）。
- 若要做，`if_else` 的字段是 `condition` / `if_action` / `else_action`，`mxt:on_block` 的内层是**方块条件**——"右键某物开始修炼"就是这两件拼起来。

### 3.7 E：选择器改成"按适用性挑"

`CultivationModeService.resolveAction` 已经改成带 `priority` 的版本，还差"适用性"这一层。**落地后的**顺序（修正三 + 修正四）：

```
applicable(action) = action.start_condition().test(entity, context)          ← 能不能坐下
                     && action.cultivate_condition().test(entity, context)   ← 这一拍能不能拿到成果
                     && CultivationActionService.canStartCultivation(entity, context)   ← 灵气侧门禁
1. 先在整张 cultivate_action 表里筛出 applicable 的（附件里存着的那条也一起过筛，没有特权）
2. 在筛出来的里面取 priority 最大的一条
3. 同分按注册表顺序
4. 一条都没有 → Failure.NOT_APPLICABLE
```

即"**先找出来能用的，再按优先级挑**"：适用性是筛子，`priority` 才是排序；不是"先按 `priority` 抢一条，再问它能不能用"。**`tick_condition` 不在筛子里**（修正四）：它答的是"已经在修炼的身体还要不要继续"，坐下之前必然为假，拿它筛会让两个还没入定的人互相挡住——双修第一次开练就是这个毛病。

四条硬约束：

1. **筛子里的两条与运行期同一把尺子**：`start_condition` 用的判定就是 `start` 里那句 `conditionsMet`（选择器复用它），`cultivate_condition` 也是运行期每拍要问的那条——所以"被选中"意味着"起得来、而且这一拍有成果"。**已落地**。
2. **冷却不进适用性**：否则"上次那条在冷却"会把玩家换到另一条方式上，等于绕过冷却。冷却仍然是开始时的 `Failure.COOLDOWN`。
3. **顺序只有 `priority`**：`default` 字段已删，先后由每条自己声明的 `priority` 决定（大者先，同分按注册表顺序）；**附件里存着的那条不再有特权**。
4. **取代"存储优先"那条老口径**：从前让附件压过 `default` 是为了"附件字段别读不到"；现在顺序由 `priority` 显式给出、附件只作**运行记录**（tick / 停止 / 自动突破读它），就不该再让"上次跑的是哪条"压过包作者的排序——否则一具身体第一次开练之后就永久锁死在那条上（见下面那条副作用）。**已落地**。

配套：
- `Failure` 加了 `NOT_APPLICABLE`；lang 加了 `actionbar.mxt.cultivation.failure.not_applicable`（zh「没有一门当下能修的法门」）。**没有复用 `NOT_ACTIVE`**——那条是"状态对不上"的运行时情形（tick 时附件里不是这条）。**已落地**。
- **停止不走选择器**：按 C 时若正在修炼，用**附件里存着的那条**（`spirit.cultivateAction()`）去停。从前 `toggle` 是先 `resolveAction` 再把结果交给 `stop`；改成先筛后挑之后，挑出来的可能是**另一条**——`stop` 会拿错 id（`stopCultivateAction` 只在 id 与附件一致时清 `cultivating`），甚至因为"当前那条已经不适用"而挑不出来（`NOT_ACTIVE`），结果是**停不下来**。所以 `toggle` 分成两支：正在修炼 → 用附件那条停；否则 → 选择器挑一条开始。**已落地**。
- `/mxt cultivate status` 已经会显示选中的是哪种方式，不用改。
- `CultivationModeService.toggle` 的 `stopIfCultivating` / 自动突破 / 灵气分配三条路径**不动**（它们读的都是附件里存着的那条，而不是选择器的结果）。
- **现状的一个副作用（2026-09-27 核查，修正三解决的正是它）**：附件里那条只在**成功开始**时写入（`CultivationAttachment.startCultivateAction`），只有转世的 `resetCultivation` 会清空，而旧选择器又"附件优先"——所以一具身体只要成功开练过一次，`priority` 对它**再也不起作用**。改成"先筛后挑"之后，每次按 C 都重新在"此刻能用的"里面按 `priority` 挑，所以学了功法、`priority` 更高的那条一变得适用就会自动换过去。
- **`cultivate_condition` 的用途很窄（修正四）**：**基本只用于双修判定**——"身边得有人、而且他手上得拿着东西，我这一拍才拿得到成果"。单人的门槛用另外两个更直白：不满足就别修（灵气浓度、维度、功法、场地）写 `start_condition`，"修到一半不该继续"写 `tick_condition`。

### 3.8 两个需求的完整写法

**②不受限制**（= 今天的行为，也是"没有功法也能练"的包）：

```json
{
  "priority": 1,
  "tick_interval": 20,
  "absorb_amount": "1 + realm_rank * 0.05",
  "aura_gains": [{"id": "mxt:spirit_power", "amount": 1}]
}
```

**①仅凭功法**（同包里再加一条，两条可同时存在）：

```json
{
  "tick_interval": 20,
  "start_condition": {"type": "mxt:technique", "techniques": ["#mxt_test:meditation_arts"]},
  "tick_condition": {"type": "mxt:technique", "techniques": ["#mxt_test:meditation_arts"]},
  "absorb_amount": "2 + realm_rank * 0.1",
  "aura_costs": [{"id": "mxt:spirit_power", "amount": 1}],
  "tick_action": {"type": "add_resource", "resource": "mxt_test:sword_mastery", "amount": "1"}
}
```

**④双修**（**2026-09-27 修正四之后是一条法门，判据"拿手上的"**）：`cultivate_condition` 问"5 格内有没有一个拿着手册的好友"，`start_condition` 留给场地（这里有蒲团/场地就写在这里，没有就不写），`tick_condition` 想让"对方一起身我这边也停"就再问一次"同伴在不在修"。

```json
{
  "priority": 10,
  "start_condition": {"type": "mxt:on_block", "condition": {"type": "mxt:block_tag", "tag": "mxt_test:meditation_seats"}},
  "cultivate_condition": {"type": "mxt:partner", "range": 5.0, "count": {"min": 1, "max": 1},
    "bientity_condition": {"type": "and", "conditions": [
      {"type": "friend"},
      {"type": "target_condition", "condition": {
        "type": "mxt:main_hand_item",
        "item_condition": {"type": "mxt:has_component", "component": "mxt:technique"}}}
    ]}},
  "tick_condition": {"type": "mxt:partner", "range": 5.0,
    "bientity_condition": {"type": "and", "conditions": [
      {"type": "target_condition", "condition": {"type": "mxt:cultivating"}},
      {"type": "friend"}
    ]}},
  "tick_interval": 20,
  "absorb_amount": "2 + realm_rank * 0.1"
}
```

> 流程：A 按 C——`start_condition`（坐在蒲团上）与 `cultivate_condition`（5 格内有拿着手册的好友）此刻都成立 → A 坐下；B 按 C 同样成立 → B 也坐下。两边都成立是因为**判据问的是"手上拿着什么"而不是"对方在不在修"**：后者在 A 坐下之前必然为假，两个人就谁也进不去（这正是修正三把它们塞进同一个筛子时暴露出来的毛病）。
>
> 任一方走开、把手册收起来或不再是好友 → 另一方的 `cultivate_condition` 下一拍不成立 → **这一拍空过**（不扣钱、不给收获），**运功不中止**（人还坐在那儿）；若希望对方起身就把这边也停掉，就把"同伴在修"那条也写进 `tick_condition`（上面写了，于是下一拍 `Failure.CONDITIONS` 中止）。两个需求各由一条条件回答，不用再拆成两条法门。
>
> **`mxt:cultivating` 的位置**：它只在"已经在修炼"之后才可能为真，所以**天然属于 `tick_condition`**；写进 `start_condition` 或 `cultivate_condition` 就等于"两个人都坐下之前谁也进不来"。

### 3.9 F：层数闭环（可选，可后做）

`Technique.configuration` 的值 `StageConfiguration` 现在只有 `condition`（到达该级的条件）+ `ability`（该级起累计生效的能力）。素材的"功法层数"还差两件事，加两个可选字段即可，**都在同一个 record 里，不开第二处**：

| 新字段 | 类型 / 默认 | 语义（与既有字段一起读） |
|---|---|---|
| `passive_modifiers` | `AttributeEntry[]`，默认 `[]` | **累积**：从入口级到当前级，每一级的都生效 → 对应"每突破一层永久加属性" |
| `cultivation_modifier` | `NumberProvider`，可选 | **覆盖**：当前级写了就用当前级的，否则回落 `Technique.cultivation_modifier` → 对应"层数决定真元/吸收速度" |

读法与落点：

- `ability` 保持"最低要求、累积"（既有口径，`SkillStageService.unlockedAbilities`）。
- `passive_modifiers`：`PassiveAttributeService.entries:107-108` 现在只读 `technique.passiveModifiers()`；改成"功法级列表 **++** 链上从入口到当前级的各级 `passive_modifiers`（按链序）"，沿用现有的 `kind = "technique"` + 功法 id 作为 source、下标在拼好的列表上递增。层数变化时后面的下标会移动，但那段本来就是"先算全集、再删多余、再逐个 apply"，不会留残留。
- `cultivation_modifier`：`CultivationAffinity.combine:97-101` 现在对所有已学功法**连乘**；改成"先取该功法当前级的覆盖值（`SkillStageService.currentStage` → `configuration.get(stage)`），没有则用功法级默认"，再连乘。**连乘口径不变**（多门功法各自贡献一次）。
- 素材的"熟练度增速与层数无关、与悟性有关"不需要新东西：悟性是属性，公式写 `caster_<attribute>` 即可（`MxtFormulaVariables.EntityVariable.state` 会先查属性、再查资源、再查元素）。
- 境界门槛（素材 §4.3 第二层卡）**今天就能写**：`{"type":"mxt:realm","realm":"…","comparison":"at_least"}`。

> **现状核查（2026-09-27，只读对照代码）——F 不是非做不可，现有写法能覆盖**：
>
> - **层数 → 属性**：不必加 `passive_modifiers`。`StageConfiguration.ability` 本来就是**累积**的（`SkillStageService.unlockedAbilities` 用 `ServerCache.isStageAtLeast` 把"当前级及以下"的每一级都收进来，见 `CultivationGrantService:53-55`），而技能类型里已经有 `mxt:modifier`（`ModifierAbilityType`，就是 `modifiers: AttributeEntry[]`）。所以"每突破一层永久加属性"＝**给那一级的 `ability` 挂一个 `mxt:modifier` 技能**：升级自动授予、降级/忘功自动撤销，属性来源也沿用既有的 `technique/<功法 id>` 一条账。
> - **层数 → 吸收速度**：不必加 `cultivation_modifier` 覆盖。上面那个每级技能加出来的属性，公式读得到（`caster_<attribute>`，`MxtFormulaVariables.EntityVariable.state` 先查属性），所以 `absorb_amount: "1 + caster_<属性> * 0.1"` 就是"层数决定速度"。
> - **代价**：它是**间接**的——速度跟着属性走，别的来源（灵根、体质、法器、丹药、buff）动同一个属性也会一起改；想让"速度"只由层数决定、与属性解耦，才需要 F 的 `cultivation_modifier`。另外每级多一个技能定义（内容侧多几个文件），而 F 是写在同一级的 `configuration` 里。
> - **前提**：属性必须是**已经注册的**（原版或某个内容模组注册的；公式名是拍平后的 `caster_<命名空间>_<路径>`，例如 `caster_minecraft_max_health`）。属性注册表是静态表，本体没有自己的属性，**数据包也注册不了属性**——只有原版属性可用时，"借一个属性当层数刻度"会挤占原版语义（拿 `minecraft:max_health` 当修炼速度刻度就是这种味道）；有一个内容模组专门给的属性才是干净写法。
> - **结论**：**先用现有写法**（本体零改动，内容侧挑一个属性），F 只在两种情况值得加字段：① 要一个与属性解耦、能连乘进 `CultivationAffinity` 的层数倍率；② 内容侧找不到合适的属性。这一条把 §0 的 ⑦ 从"缺"改成"能表达，只是不直白"。

### 3.10 否掉的方案（留档，别再提第二遍）

### 3.11 中止的名字与手动点名（2026-09-27 追加，用户拍板形状）

两件都在"选择器之外"，所以不改上面那条唯一的挑选顺序：

**① 具名中止原因（`abort_reason`，可选 Text Component）**。`tick_condition` 只回答真假，所以"同伴走了"与"功法被摘了"本来报同一句 `failure.conditions`。现在给 `CultivateAction` 加一个可选文本，**只在"因为 `tick_condition` 不成立而中止"这一条路上**生效：中止时把这段文本随 `Result.abortReason` 带出来，actionbar 用它替代通用文案（失败去重记录也带上它，否则两条不同的原因会被当成同一条而不提示）。其余中止原因（`ENVIRONMENT` / `INSUFFICIENT_AURA` / `INVALID_FORMULA`）仍然各报各的枚举文案——包只给"维持条件断了"这一件事起名，别的失败它管不着。**没有做成"中止动作"**：那要新开一个会跑动作的字段与一套失败反馈，而这里要的只是"这句话由包来说"。

**② 手动点名一条法门（`/mxt cultivate select <action>`，一次性）**。`CultivationModeService.startNamed(entity, action)`：正在跑同一条 → `ALREADY_ACTIVE`；**先用同一把筛子问"此刻适用吗"**，不适用 → `NOT_APPLICABLE` 且**不动正在跑的那条**（先停再问会把"点名失败"变成"白白散功"）；适用则停掉旧的那条、再走同一条 `start`。**它不落盘**：没有新的附件字段，也没有"手动那条优先"这一层——所以本次挑选顺序一个字都没变，下一次按修炼键照样由"筛适用 + `priority`"决定。这样选是因为用户拍板要"一次性开练"：包作者说了算的排序不该被管理员的一次临时操作改写，而"我要一直修这条"用 `priority` 表达才对。

手册那一侧不需要物品夹具：`mxt:has_component` 读的是 `mxt:technique` 组件，探针自己用 `MxtItems.CULTIVATION_JADE_SLIP` + `MxtDataComponents.TECHNIQUE` 拼一份（测试包里 `qingxiao_breathing_manual` 有 `technique_binding`，`ItemBindingService.techniqueCarrier` 会返回**被声明的物品**、不带组件，所以不能用它）。

**夹具里的 `type` 一律写全 id**（`mxt:and` / `mxt:not` / `mxt:friend` / `mxt:target_condition`）：这些分派走 `byNameCodec()`（即 `Identifier.CODEC`），省命名空间会被当成 `minecraft:and`，注册表加载整包失败、服务端起不来。`docs/数据包格式.md` 的「固有类型分派」已补上这一句。

**探针腿**（`/mxt_test cultivate probe`，一条腿一行 `OK / MISMATCH`，最后汇总 `cultivation probe: OK` / `MISMATCH`）——`/mxt_test cultivate` 本身仍是"用硬编码 id 开一次练并回显失败名"的快捷入口（测试包的 kit / guide 文案指着它）。落地时按下面这些腿写，编号对着本文档：

1. **不写就被问**：`select` 不写任何一次开练——已加入世界的身体本来就带着一份空的 `mxt:cultivation`（`TriggerRehydrators` 在 `EntityJoinLevelEvent` 上重建触发数据时会读一次资源公式上下文，那里用的是 `getData`），所以断言是"记录里没有在跑的法门"，无功法时选中 `free_meditation`（需求②的基线）。
2. **门槛拦得住**：`technique_meditation` 对无功法身体既不 `applicable`、`start_condition` 也不成立。
3. **`mxt:technique` 的四态**：没学 → `named`/`strict` 不成立而 `worldly` 成立；学了 tag 里那门 → `technique_meditation` 成立、`named` 与 `strict` 仍不成立、`worldly` 转假；再学 `sword_manual` → `named` 与 `strict`（`all`）都成立。
4. **附件不是特权**（修正三的回归）：身体在跑 `free_meditation`（`priority` 5）时学了功法，`select` 立刻改选 `technique_meditation`（10），而附件里存的仍是 free；停止后附件不再 `cultivating`。
5. **`tick_condition` 的假不影响坐下**（修正四的核心）：`dual_meditation` 的 yield 条件成立、upkeep 条件为假时照样 `start`，第一拍才因 `CONDITIONS` 停，**并且那一次中止带着 `abort_reason` 写的名字**（具名中止原因的落地断言）。
6. **双修两边都坐得下**：一对互相为友、各自拿着手册的身体相距 3 格，两边同时 `start` 成功，同一拍各扣 1 点 `water_power`、各得 1 点 `sword_mastery`。
7. **空过而不中止**（修正四的回归）：把同伴的手册收走 → 到期的那一拍 `waiting` 且什么都没变（钱、收获、`next_cultivate_tick` 三样都不动、仍在修炼）；手册放回 → **同一拍**立刻结算并推进到 `+20`。
8. **`mxt:partner` 问的是对方**：自己拿着手册、同伴空手 → 不成立；好友拿着手册但在 8 格外（探针用竖直上方 8 格，免得和别的格子互相看见）→ 不成立；身边没人 → 不成立；一个合格同伴 → 成立；`count.max: 1` 而身边有三个 → 不成立。
9. **`mxt:cultivating`**：在修的身体为真、对着另一条法门为假、没在修的身体为假。
10. **起停行为**：`{"type":"mxt:cultivate"}` 让身体开练到选择器挑的那条（`free_meditation`），`{"type":"mxt:stop_cultivating"}` 停下并把该法门的 `cooldown`（200）写进附件——立刻重启被拒，`now + 200` 重启成功；带 `action` 的写法能点名起一条（有那门功法时成功，没有时静默不动）。
11. **收尾**：一对双修各自按附件里存着的那条停得掉，且"不写要求的法门"对已有功法的身体照样适用（回归基线）。
12. **一次性点名**（第 7 项）：身体此刻适用 `qingxiao_meditation`(1) 与 `technique_meditation`(10) 时，`startNamed(qingxiao_meditation)` 真的把它开起来（附件里也是它），而 `select` 依然答 `technique_meditation`——点名不落盘、不改排序；点名一条不适用的（`technique_meditation` 给无功法身体）→ `NOT_APPLICABLE` 且**正在跑的那条照旧在跑**；点名正在跑的那条 → `ALREADY_ACTIVE`。（点的是 `qingxiao_meditation` 而不是 `free_meditation`：第 4 条腿停过 free，**停止会把该法门的冷却写进附件**，同一具身体再点它只会拿到 `COOLDOWN`。）
13. **遗忘**（第 11 项）：给身体先设好一个境界、学一门带层数记录的功法、记下它授予的技能；`forget` 之后 → 学过的列表里没有它、**它自己的层数记录也没了**、授予的技能被撤掉，而**境界记录还在**（"不动主境界等其他的"）；对没学过的 id 再调一次 → `ABSENT`。
14. **`mxt:mutual` 是"两个方向"**（第 9 项）：探针的好友监听器多一个**单向拒绝表**（按"判官>候选"的有序对答 `FALSE`，`FALSE` 覆盖好友池），于是让 `seatB` 单向不认 `bareB`：`mxt:friend` 在那个方向成立、反方向不成立，`mxt:undirected` 两个方向都成立，而 `mxt:mutual` 两个方向都不成立；再拿一对互相为友的（`bareB` 与 `crowd1`）断言 `mxt:mutual` 成立。

`mxt:partner` 的好友那一侧**不能**用 `FriendAttachment` 直接写：`mxt:friend` 走 `FriendService`，而非玩家一律答 `FALSE`（"只有玩家有好友表"），所以探针注册一个 `FriendEvent.Relation` 监听器，对自己点名的那批探针实体两两答 `TRUE`，命令结束后注销。

**跑过什么**：A、`priority` / `tick_condition` 改名、B/C/D/E 与 `cultivate_condition`（修正四）落地时跑过编译（`compileJava compileTestModJava processTestModResources`）；§8 的夹具与探针腿这一批同样跑过编译 + `processTestModResources`（新夹具拷进 `build/resources/testMod`），七个新 JSON 用 node 逐个 `JSON.parse` 验过语法；第三批（7/8/11）同样跑过编译，两份 lang 的键集合核对（**904** 键、两边一致），编辑器 schema 重新生成 + `check-mxt-schemas` 报 `no problems found`。

实跑抓出来的四个问题（前两个是夹具/探针自身的错，后两个当场修）：

1. **夹具 `type` 少了命名空间**：`dual_meditation.json` 的 `"and"` / `"friend"` / `"target_condition"` 与 `worldly_meditation.json` 的 `"not"` 被解析成 `minecraft:and` 等 → `Registry loading errors`，服务端整个起不来。全部改成 `mxt:` 全名后加载通过。
2. **第 1 条腿的断言过严**：`getExistingData(CULTIVATION)` 在任何**加入世界**的身体上都非空（`TriggerRehydrators` 在 `EntityJoinLevelEvent` 里重建触发数据，读资源公式上下文时用 `getData`），断言改成"记录里没有在跑的法门"。用 `/summon minecraft:pig` + `/data get entity` 直接看到 `"mxt:cultivation": {}`（连 `resource_holder` / `ability_holder` 等一起），证据确凿。
3. **第 10 条腿的 `entityAction` 用 `JsonOps` 解不了点名**：`{"type":"mxt:cultivate","action":"mxt_test:named_meditation"}` 的 `action` 是 `RegistryFixedCodec`，抛 `Can't access registry ResourceKey[minecraft:root / mxt:cultivate_action]`；助手改成 `RegistryOps.create(JsonOps.INSTANCE, level.registryAccess())`（数据包加载本来就是 RegistryOps，所以这不是本体的问题，只是探针的解析方式）。
4. **第 12 条腿点错了法门**：原先点 `free_meditation`，但第 4 条腿停过它、**停止会写该法门自己的冷却**，于是只拿到 `COOLDOWN`；改点最低优先级的 `qingxiao_meditation`(1)，"点名那条开起来了、而 `select` 仍答优先级最高的 `technique_meditation`"这一条才成立。腿的报错串里也补了 `failure=`，下次失败能直接看出原因。

另外：`/mxt_test cultivate probe` 是**从控制台跑**的，所以第 10 条腿里 `{"type":"mxt:cultivate"}` 的"不具名就用选择器挑"这条路走的是 `CultivationModeService.select`（探针实体），与玩家按修炼键同一条；但**键盘/客户端的入口本身仍未被实机验证**。
