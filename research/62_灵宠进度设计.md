## 0. 结论（拍板）

| 问题 | 决定 |
| --- | --- |
| 链的**所有者** | **`creature_profile`**：一只生物套上档案就持有这条链；它就是 `ProgressionOwner` 的第二个实现 |
| 熟练度从哪来 | **数据包 / 脚本自己喂**：档案写 `mastery_resource` 点名一个 `resource`，涨它是数据与脚本的事（现成有 `mxt:add_resource`、灵气 `regen`、KubeJS）——本体不加内容（`AGENTS.md` §1.9） |
| 升级给什么 | 现成的 `configuration[level].ability`（累计授予：`mxt:modifier` 加属性、`mxt:triggered` 做反击…）＋ **`damage_multiplier` 对这条链授予的能力生效（含生物）** |
| 通用化范围 | **抽通用晋升驱动 + 通用授予重建**，功法侧改为走同一套（`60` §6 早就预留的这一步） |
| 入口 | **管理员命令**（`/contract info` 报等级，新增设置节点）＋ **KubeJS 读写** |
| 等级归谁 | **解约清零**；死亡不单独处理（实体本身没了）；灵兽袋经实体 NBT 带着走 |

**本轮明确不做**（位置先留好，见 §7）：

- `ProgressionConfig` 加 `action`（"每级一个动作"）——保持 `condition` + `ability` 两个字段；
- `creature_profile` 的 `granted_abilities`——**入口等级自己的 `configuration` 就是"与生俱来"**（`grantedAbilities` 是累计的，见 §2.1）；
- 玩家侧入口（喂食道具、灵宠面板、进化贴图）；
- 「已契约」实体条件（`mxt:contract`）——它是"只有灵宠能长"的必要条件，见 §7 开放项 1。

## 1. 现状（代码事实）

### 1.1 通用层已经按"将来灵宠共用"写好了

| 东西 | 今天是什么 |
| --- | --- |
| 链的一级 | `mxt:progression` 注册表：`next_level` / `mastery`（`NumberProvider`，默认 `0`）/ `damage_multiplier`（默认 `1.0`，加载期拒非有限与非负）。**链没有身份字段**，入口＝没有任何一级指向它的那一级 |
| 所有者 | `data/progression/ProgressionOwner`：`entryLevel()` + `levels()`（`Map<Holder<Progression>, ProgressionConfig>`）。`ProgressionConfig` ＝ `condition`（**必填**，不需要条件就写 `mxt:always`）+ `ability`（`HolderOrTag<ability>` 列表，**累计**：所在等级及其以下每一级都算） |
| 状态 | 附件 `mxt:progression`：`Map<所有者 id, 已达等级>`，**只在晋升之后才写入**，所以"包改了入口等级、没晋升过的人跟着走" |
| 读取与计算 | `runtime/progression/ProgressionService`：`currentLevel`（存的或所有者的入口）/`nextLevel`/`advanceCondition`/`canAdvance`/`grantedAbilities`/`setLevel`/`pruneForeignLevels` |
| 来源 | `runtime/progression/ProgressionSources`：`List<Function<Entity, List<Owner>>>`，今天**只有一条**（已学功法）；`Owner(id, definition)` 里的 `id` 就是等级记录的键 |
| 条件 | `mxt:progression`：`level` + `comparison`（`exact`/`at_least`/`at_most`）+ 可选 `owner`。它遍历 `ProgressionSources.heldBy(entity)`——**因此天生对任何实体成立**，不分玩家与生物 |
| 信号 | `mxt:progression_level`，上下文带 `owner` 与 `level`（链内序号） |

### 1.2 驱动与授予**已经跑在所有生物身上**（这是关键）

`AbilityEventBridge.onEntityTick`（`:94`）对**每个服务端 `LivingEntity`** 都跑，不是只对玩家：

- 每 tick：`PassiveAttributeService.tick(entity)`（`mxt:modifier` 的被动属性就是在这里挂/摘）、`tickAbilities(...)`、施法收尾；
- **每 20 tick**：`TechniqueMasteryService.tick(entity)`（`:116`）——功法那条晋升驱动，今天对生物是空转（生物没有已学功法）；
- 触发式能力（`mxt:triggered`）经 `AbilityEventBridge:322` 调 `AbilityService.use(...)`，走的是与按键**同一条施放路径**。

结论：**生物只要被授予能力，能力本来就会生效**——不需要为灵宠另造一套"能力生效"机制。

### 1.3 灵宠侧今天有什么

| 东西 | 今天是什么 |
| --- | --- |
| 档案 | `creature_profile`：`entities` / `spawn_action` / `intelligence` / `condition` / `inner_core` / `preferred_aura_elements` / `minimum_aura`。生物加入世界时套一次，写进 `mxt:creature_spirit`（`profile` Holder + `intelligence` + `inner_core`，宽容读） |
| 契约 | `contract_type`（双方条件、四个时刻的动作、`costs`、`max_owned`、`recall_cooldown`）＋ `mxt:contract` 附件（类型、签订时刻、召回闩与冷却、当前命令）＋ 主人索引 `bound_beasts` |
| 契约结束 | `ContractService.release`（`:72`：`onContractReleased` → `release_action` → `data.clear()` → 删索引 → `Post`）与 `onDeath`（`:122`：`death_action` → `onContractDeath` → `data.clear()`） |

### 1.4 缺的四处（就是本稿要补的全部）

1. **所有者**：`CreatureProfile` 没实现 `ProgressionOwner`，也没有 `default_level` / `mastery_resource` / `configuration` 字段；
2. **来源**：`ProgressionSources.SOURCES` 里没有生物这一条；
3. **驱动**：`TechniqueMasteryService` 把"教谁晋升"写死在功法上（它直接读 `Technique.masteryResource()`）；
4. **授予重建**：`CultivationGrantService.recalculate` 只重建修炼来源（灵根 / 体质 / 功法 / 子境界），且 `TechniqueProgression.damageMultiplier` 只遍历已学功法。

### 1.5 三处顺带记下的现状问题（抽通用时一起收拾）

- `TechniqueMasteryService.tick` 用 `entity.getData(MxtAttachments.SPIRIT_IDENTITY)`——**每 20 tick 给每个生物凭空造一份身份附件**（`getData` 会创建）。同类读取应当用 `getExistingData`（`AGENTS.md` §4）。
- `ProgressionEventBridge` 的清扫（归属校验）**只扫在线玩家**（登录 + 数据包重载），生物侧没有对应时刻——`60` §2 末尾已标注这一点。
- `TechniqueCommand.pruneLevels` 是玩家专用的 `/technique repair` 清扫，注释里已经写着"其它所有者拥有的进度不该被功法修复带走"——生物侧需要一条同类清扫，但它不该长在 `/technique` 上。

## 2. 形状

### 2.1 `creature_profile` 新增三个字段（与功法**逐字同形**）

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `default_level` | `Holder<progression>` | 无 | 这条链的入口等级。不写＝这只生物不持有链（也就没有进度） |
| `mastery_resource` | `Holder<resource>` | 无 | 用哪个数值衡量熟练度；与 `Progression.mastery` 比较的就是它 |
| `configuration` | `Map<Holder<progression>, ProgressionConfig>` | `{}` | 每一级给它什么能力、要什么条件 |

**加载期校验照抄 `Technique.validate` 的两条**：`configuration` 非空必须有 `default_level`（否则这份配置不属于任何链）；`mastery_resource` 写了也必须有 `default_level`。`ProgressionConfig` 本身不动。

**"与生俱来的能力"不用新字段。** `grantedAbilities` 是"当前所在等级**及其以下**每一级"的并集，而入口等级是每一只生物一出生就站着的等级——所以把能力写在**入口等级**的 `configuration` 里，就等于天生会；写在下一级就是晋升才学会。这是 §0 里"不加 `granted_abilities`"的依据（功法侧也一样：它的 `granted_abilities` 是"学了就有"，灵宠侧没有"学"这个动作，有没有契约都是同一只兽）。

**没写这三个字段的档案不是所有者**：`ProgressionSources` 只报 `entryLevel().isPresent()` 的档案，于是老包一个字不改、行为一字不变。

**不给灵宠加 `passive_modifiers` / `attribute_modifiers` 字段。** 那两个字段属于**功法与体质**（`Technique.passiveModifiers` / `Physique.attributeModifiers`），由 `PassiveAttributeService.entries` 按"持不持有"直接读取、与等级无关。灵宠侧要"生来就有的属性"就写**入口等级**的 `mxt:modifier` 能力：同一种效果只留一个形状（`AGENTS.md` §4），而且它自带"等级掉落后属性跟着摘掉"的行为。

### 2.2 所有者与来源（两处小改动）

```java
// data/creature/CreatureProfile.java
public record CreatureProfile(...) implements NamedDefinition, ProgressionOwner {
    @Override public Optional<Holder<Progression>> entryLevel() { return this.defaultLevel; }
    @Override public Map<Holder<Progression>, ProgressionConfig> levels() { return this.configuration; }
    @Override public Optional<Holder<Resource>> masteryResource() { return this.masteryResource; }  // §2.3 新加
}

// runtime/progression/ProgressionSources.java
private static final List<Function<Entity, List<Owner>>> SOURCES = List.of(
        ProgressionSources::techniques,
        ProgressionSources::creatures);
```

`creatures` 读 `mxt:creature_spirit` 的 `profile`（**用 `getExistingData`**，只读查询不造附件），有档案且档案声明了链就报一个 `Owner(档案 id, 档案)`。

**档案 Holder 存在附件里**，沿用全仓口径：包改了、甚至删了这份档案，身体里存着的那份 Holder 仍算数（`ProgressionEntityCondition` / `heldBy` 都直接 `value()`，不看注册表）。

### 2.3 通用晋升驱动（把 `TechniqueMasteryService` 抽出来）

`ProgressionOwner` 加一个方法，因为它就是"谁在测熟练度"的答案：

```java
Optional<Holder<Resource>> masteryResource();
```

两个实现都有这个字段，所以不设默认实现（接口在 `data/progression/`，不是 `api/`，不受"附属要实现"的兼容约束）。

新 `runtime/progression/ProgressionDriver`：

| 成员 | 行为 |
| --- | --- |
| `tick(LivingEntity)` | 遍历 `ProgressionSources.heldBy(entity)`，对每个所有者跑晋升循环（**每次最多 64 次**，照今天的 `MAX_PROMOTIONS_PER_PASS`），返回"有没有晋升过" |

单次晋升的判据与今天**逐条相同**，只是不再写死功法：`currentLevel` → `nextLevel` → `target.mastery().evaluate(context)` 有限且 `resources.get(mastery) >= required` → `advanceCondition(definition, target).test(entity, context)` → `setLevel` → 发 `mxt:progression_level`（带 `owner` 与链内序号）。资源与公式上下文**一次取好、所有所有者共用**。

- `TechniqueMasteryService` **删除**，`AbilityEventBridge` 每 20 tick 那一处改调 `ProgressionDriver.tick(entity)`；返回真就调一次授予重建（§2.4）。
- 驱动只碰它必须碰的附件：`heldBy` 走 `getExistingData`，`setLevel` 时才 `getData`（顺手解决 §1.5 第一条）。
- 技能 / 灵宠**不各写一份循环**——这是 `60` §6 留的那一步，今天到点了。

### 2.4 通用授予重建（把 `CultivationGrantService` 抽出来）

一个入口，先把 `mxt:grant/*` **全部**撤销，再按各系统重授予（`AbilitySources.GRANT_PREFIX = "grant/"`，撤销本来就按前缀过滤，所以通用化不需要新键）：

| 来源类目 | 授予来源 id | 授予什么 |
| --- | --- | --- |
| `spirit_root` / `physique` / `technique` / `realm_stage` | 原样不动 | 修炼侧原样不动 |
| **`creature`（新）** | `mxt:grant/creature/<命名空间>/<路径>` | 该生物档案的入口等级与**累计已达等级**的 `ability`（`ProgressionService.grantedAbilities`） |

**为什么必须"重建"而不是"只加"**：解约清零（§2.6）之后等级记录没了，但 `mxt:modifier` 已经在身上挂了属性——不撤销就永远留着。撤销 + 重授予是唯一能把"等级掉了"表达干净的做法，而且它已经是今天功法侧的做法（晋升与遗忘都走它）。

触发点三处：**档案刚写进生物时**（`CreatureProfileService.apply` 成功之后）、**通用驱动报告晋升时**、**契约结束清零之后**。函数结尾照旧调 `AbilityEventBridge.rebuildTriggerSubscriptions(entity)`。

### 2.5 `damage_multiplier` 抽通用（生物的技能伤害这才吃得上倍率）

今天是 `TechniqueProgression.damageMultiplier(holder, ability)`：遍历**已学功法**，找出"授予该能力"的那些，取倍率最高的一档。改成 `runtime/progression/ProgressionDamageMultiplier`，遍历换成 `ProgressionSources.heldBy(holder)`，规则不变（**按能力问，不按持有者问；多个所有者都授予同一能力时取最高**）。

**调用点一个都不用加**：`AbilityService.withAbilityScaling`（`:451`，`:459` 是唯一一处）本来就在 5 条施放路径上，而生物身上的触发式能力经 `AbilityEventBridge:322` → `AbilityService.use` 走的正是这条路。所以抽完之后，**灵宠用它被授予的能力打出的伤害自动吃倍率**。

玩家侧结果不变（来源集合仍只有功法），`docs/数据包格式.md` 里"只作用于这条链授予的能力打出的伤害、不给持有者一切伤害加 buff"的口径也照样成立，只是"这条链"从"功法这条链"变成"任何所有者这条链"。

### 2.6 解约清零（用户拍板）

**语义**：等级是"灵宠"的，不是"这只兽"的——契约一断，进度归零（再契约从入口等级重来）。

| 时刻 | 做什么 | 排在哪 |
| --- | --- | --- |
| `release`（主动解除 / `break` / `force`） | 清该生物档案的等级记录 + 授予重建 | 与 `data.clear()` 同一处收尾，**排在 `release_action` 之后**（动作还读得到等级） |
| `onDeath`（灵宠死亡带动契约结束） | 同上 | 排在 `death_action` 之后 |

- 清记录用 `ProgressionAttachment.clearLevel(档案 id)`（已有方法），**不清整张表**：一只兽理论上可以同时持有别的所有者的进度（今天不会，但方法本来就在）。
- 死亡时清了也无人看（实体马上就没了），但**保持一致**更重要：`death_action` 若把生物救活，它就是一只没有等级的兽。
- **灵兽袋不触发清零**（契约没解），而附件本来就随实体 NBT 走，所以收进袋子再放出来，等级还在。
- **从未被契约过的生物不受影响**：清零只发生在契约结束那一刻，见 §7 开放项 1。

### 2.7 入口：命令 + KubeJS

**一个服务，两个入口**（避免命令与脚本各写一套校验）：`runtime/progression/ProgressionAdminService`（或把 `setLevel` 的校验并进 `ProgressionService`）：

```
Result setLevel(LivingEntity entity, Identifier owner, Holder<Progression> level, boolean force)
Failure: UNKNOWN_OWNER（这具身体不持有这个所有者）/ FOREIGN_LEVEL（这一级不在它的链上）/ SAME_LEVEL / (服务端以外由上层拒)
```

- 校验"在不在链上"用 `ProgressionService` 已有的走法（`entryLevel` 沿 `nextLevel` 走，`MAX_CHAIN_LENGTH` 兜底，`pruneForeignLevels` 内部那个 `follows` 就是它——**抽成公开的 `follows(owner, level)` 复用，别写第二份**）。
- 成功之后：写记录 → 授予重建 → 发 `mxt:progression_level`（**发**：管理员改等级与自然晋升应当对数据包产生同样的反应，否则"升级触发天劫/提示"这类写法只在自然晋升时有效）。

**命令**（挂在已有的 `/contract` 下，因此**不需要新配置项**，`MxtServerConfig.Commands.contract` 已经存在）：

| 节点 | 参数 | 权限 | 做什么 |
| --- | --- | --- | --- |
| `info <target>`（改） | `EntityArgument.entity()` | 只读 | 加一行：所有者 id + 当前等级 + 下一级 + 熟练度（现有 / 需要） |
| `level <target> <level> [force]`（新） | `EntityArgument` + `ResourceArgument.resource(context, PROGRESSION)` | `requires(mayChange)` | 写这只生物自己档案那条链的记录；`force` 跳过"在不在链上" |

（等级参数用原版 `ResourceArgument`：解析、补全、"没有这个条目"三件事一起拿来，符合 `AGENTS.md` §4。写节点照约定加 `requires(mayChange)`。）

**KubeJS**：新全局 `MxtProgression`（`MxtKubeJsPlugin.registerBindings` 里注册一个），把"按所有者问"这件事做成通用形状，而不是只给灵宠开一个口：

| 方法 | 语义 |
| --- | --- |
| `level(entity, owner)` | **记录的**等级 id，没晋升过是 `null`（与现有 `MxtTechniques.level` 同义） |
| `current(entity, owner)` | **生效的**等级 id（没记录就是入口等级） |
| `next(entity, owner)` | 下一级 id，最高一级是 `null` |
| `mastery(entity, owner)` | `{have, required}`：`mastery_resource` 的当前值与该级要求值 |
| `setLevel(entity, owner, level)` | 受校验的写：走 §2.7 那同一个服务，返回 `{changed, failure}`（服务端权威、失败用结果记录不用异常——`AGENTS.md` §4） |

现有 `MxtTechniques.level(entity, technique)` **保留不动**（它已经有文档与用户），内部改走同一个出口即可。

### 2.8 清扫扩到非玩家（`60` §2 留的那一条）

归属校验（"身体里那条记录已经不在自己链上了"）今天只在**登录**与**数据包重载**时对在线玩家跑。生物侧补两个时刻：

| 时刻 | 范围 |
| --- | --- |
| `EntityJoinLevelEvent` | **这一只**：任何加入服务端世界的实体都判一次（等价于玩家的"登录"）。没记录的直接早退，所以普通刷怪几乎是零成本 |
| `ServerDataLoad`（数据包重载） | 从"在线玩家"扩到**所有已加载实体**：`server.getAllLevels()` + `level.getEntities().getAll()`（仓库里已有同样走法：`runtime/trigger/TriggerLifecycleEvents:54`），只对 `getExistingData(PROGRESSION)` 非空的做链走 |

清掉之后要**按新等级重算授予**（今天的 `ProgressionEventBridge.prune` 只重算修炼来源，通用化后调 §2.4 那一个入口）。

## 3. 免费得到的东西（不用改一行代码）

`ProgressionSources` 一加上生物这条来源，下面这些**当天就成立**：

- **"几级以上的妖兽才签得了"**：`contract_type.creature_condition` 里写
  `{"type": "mxt:progression", "level": "example:beast_3", "comparison": "at_least"}`——条件本来就在被契约的生物身上求值；
- **"主人修为到某级才签得了"**：同一条件写在 `owner_condition` 里，问的是主人自己的链；
- **"某个能力只在三级后出现"**：`mxt:has_ability` 等条件读的是生物自己的状态，而等级授予的能力就在它身上；
- **"在灵气浓郁处自动长大"**：`AbilityEventBridge` 的资源再生循环（`:102`）对**每个生物**跑——包只要声明一个 `aura`，把它的 `resource` 指到那只兽的 `mastery_resource`，再给 `regen`，妖兽在灵脉上就会自己涨熟练度，本体一行都不加；
- **"喂丹药涨熟练度"**：`mxt:add_resource` 动作（`MxtEntityActions.ADD_RESOURCE`）＋丹药的 `on_consume` 就能写出来，不需要本体出物品。

## 4. 灵宠身上"哪些能力类型有意义"

等级能给的只有能力，所以这份表决定了灵宠成长能做出什么花：

| 能力类型 | 在灵宠身上的意义 |
| --- | --- |
| `mxt:modifier` | **主力**：被动属性（血量 / 攻击 / 护甲 / 移速…），`condition` 每 tick 复查，掉了等级自动摘 |
| `mxt:triggered` | 受伤 / 攻击 / 死亡信号触发一套动作（反击、吸血、临死爆发） |
| `mxt:aura` | 按半径对周围逐目标跑动作（威压、光环） |
| `mxt:interval` | 按固定间隔自己跑（吐息、回复） |
| `mxt:active` / `channelled` / `word` / `targeted` / `storage` / `upkeep` / `flight_control` / `mount` | 需要**按键**或**物品宿主**，生物身上没有入口，写了也不会有反应（`storage` 要物品、`flight_control`/`mount` 是"法器 + 功法"那两条） |

**写内容时要知道的一个静默点**：属性加成只对**这只生物本来就有的属性**生效——`PassiveAttributeService.apply` 在 `entity.getAttribute(attribute) == null` 时直接返回（不创建属性实例），所以把 "攻击力 +5" 加在一只没有 `attack_damage` 的生物上，日志没有、效果也没有（与本仓"某类字段写了不生效不报错"是同一类口径，只是这次是原版属性表决定的）。

## 7. 开放项（需要一句话拍板）

> **本节两条已于同日关闭**：第 1 条见 §12.1（落地形状与稿子里设想的字段名不同：实际是 `bound` / `type` / `behavior`，没有 `owner`），第 3 条见 §12.2。以下正文保留当时的判断，不再修改。

1. **"只有灵宠能长"需要一条条件**：今天**没有**任何条件能问"这只生物被契约了吗 / 主人是谁 / 是哪种契约"。所以本稿只能保证"档案给链、数据决定谁长"，**一只从未被契约的野生妖兽只要数据包喂它熟练度，它就会长**——而"解约清零"对它没有机会生效（没有解约事件）。要么接受这个口径（数据包自己用条件收窄，例如只喂灵宠拿得到的资源），要么补一条实体条件 `mxt:contract`（`{contracted: true/false, type: ..., owner: ...}`）——它对 `creature_condition`、等级门槛、KubeJS 都有用，我建议**补，但可以另开一轮**。
2. **管理员设等级是否发信号**：本稿按**发**设计（§2.7）。若你希望"只有自然晋升才触发数据包反应"，改成不发即可。
3. **每级一个动作**（`ProgressionConfig.action`）：本轮不做。将来做的时候，位置在 `ProgressionConfig`（加一个 `EntityAction`），消费点在 `ProgressionDriver` 晋升成功那一拍——**不要**放到信号里（信号是给数据包的，动作是给所有者的）。
4. **死亡时是否也清零**：本稿按"清"（一致性），因为 `death_action` 理论上能把生物救活。若不希望，改一行。

### 12.1 `mxt:contract` 实体条件（收掉 §7-1）

- 新 `data/condition/builtin/entity/ContractEntityCondition`，注册为 **`mxt:contract`**。
- 字段三个：`bound`（bool，默认 `true`）＝"身上有没有一份契约记录"；`type`（`HolderOrTag<contract_type>` 的列表）＝把问题限定到某几种契约类型；`behavior`（行为 id 的列表）＝它当前那条命令是不是其中之一。读的就是灵宠身上那条 `mxt:contract` 记录（`getExistingData`，只读不造附件）。
- 没有记录的生物：`bound: true` 答否、`bound: false` 答是。**`bound: false` 与 `type` 同写在加载期被拒**（"没契约"与"契约是哪一种"互相矛盾，与全仓"两处对同一件事各写一遍矛盾就拒收"同一口径）。
- **"只有灵宠能长"因此不需要新机制**：把要守的那一级的 `condition` 写成 `{"type": "mxt:contract"}` 即可。§7-1 从"只能靠数据自己收窄（例如只喂灵宠拿得到的资源）"升级为"可以精确表达"。

### 12.2 每级第三个字段 `action`（收掉 §7-3）

- `ProgressionConfig` 从两个字段变三个：`condition`（必填）/ `ability`（累计）/ `action`（`EntityAction`，默认 `mxt:no_op`）。
- **消费点只有一处**：`ProgressionService.enterLevel(entity, owner, definition, level)` —— 它先跑该级的 `action`、再发 `mxt:progression_level`。自然晋升（`ProgressionDriver.promote`）与管理员的等级写入（`ProgressionAdminService.setLevel`）都走它，**顺序统一成"写记录 → 动作 → 信号 → 重建授予"**（管理员那边原来是"写记录 → 重建 → 信号"，现在与自然晋升完全同形）。原先的 `publishAdvance` 被 `enterLevel` 取代（它本来只有这两个调用点）。
- **为什么动作排在信号之前**：动作是"这一级自己的后果"（改体型、发提示、生成特效），信号是"告诉世界"；先做事再说话，反应方拿到的就是已经变过的身体。**为什么动作排在授予重建之前**：与既有的自然晋升一致（那条路上信号本来就早于重建），一致性优先于"动作能看见新能力"。
- 测试包：`probe_beast` 的第二级配了 `{"type": "mxt:add_resource", "resource": "mxt_test:beast_growth", "amount": 1}`，所以晋升到二级后熟练度是 10＋1＝11，探针据此断言"动作正好跑了一次"。
