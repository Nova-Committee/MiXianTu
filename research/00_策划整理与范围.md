# 修仙框架策划整理与范围

## 目标

本项目是 NeoForge 26.1.2 的修仙模组运行时框架。Java 负责稳定、可同步、可校验的底层能力；具体修仙数值和玩法由数据包与 KubeJS
扩展。内容作者应能新增境界、元素、灵根、体质、功法、法术、丹方、阵法和劫数，而不需要修改 Java 源码。

## 本期范围

本期只覆盖游戏运行时和内容扩展接口：

- 实体与区块持久化数据、服务端权威校验、客户端同步。
- 数据包定义、热重载、动态注册表及其 KubeJS 注册入口。
- 修为、灵气、修炼、统一能力、法宝、炼丹、阵法、生物、天劫等通用机制。
- 必要的基础 HUD/容器/提示数据接口；界面布局和复杂交互不在本期重点。
- 与 Curios、救援/复活类模组的可选兼容层。

## 明确不在本期

- 数据包可视化编辑器及其导入、导出、校验界面。
- 预置的“炼气、筑基、火球术、筑基丹、五行灵根”等具体内容和数值平衡。
- 宗门剧情、秘境地图、美术模型、装饰物的具体实现。
- 为每个修仙流派单独编写硬编码逻辑。

## 内容设计原则

1. Java 中不得以具体境界、具体技能或具体物品 ID 作为逻辑分支。
2. 可变内容使用命名空间 ID、标签、JSON 数据包和 KubeJS 回调表达。
3. 运行时状态与静态定义分离：定义来自注册表，玩家/实体仅保存注册表 ID、进度和局部状态。
4. 服务端是唯一可信来源；客户端仅保存 UI、预测或渲染所需的同步快照。
5. 每个定义和存档附件都带版本号，数据包重载或模组升级时执行校验和迁移。
6. KubeJS 适合效果、数值修正和内容编排；频繁 tick、寻路、范围扫描、网络包和持久化由 Java 处理。
7. 技能统一归入 `Ability`：术法、神通、功法被动、灵根的元素相关效果、体质的独立加成和法宝触发均是能力定义或能力来源，不能各自维护独立的冷却、条件和事件系统。
8. 元素、灵根和体质是三个独立维度：灵根必须绑定单一元素，多灵根由列表组合；体质不绑定元素，只提供独立加成、条件和能力。
9. 数据包只能实例化 Java 已注册的类型；任何需要 Java 类、`MapCodec`、原版注册表接入或服务端事件钩子的行为，必须先进入固有注册表。

## 优先级

| 优先级 | 交付目标                                 | 说明                    |
|-----|--------------------------------------|-----------------------|
| P0  | core、固有类型注册表、数据包注册表、附件、事件、网络、标签、调试命令 | 所有后续模块的共同前提。          |
| P1  | 境界/元素/灵根/体质/灵气/修炼、统一能力、物品能力与储物、灵石    | 形成最小可玩的修仙循环。          |
| P2  | 炼丹、阵法、飞剑/飞行、劫数、妖兽/灵宠、锻造              | 由 P1 的统一能量、施法和回调机制支撑。 |
| P3  | 宗门、头衔、秘境、灵魂形态、维度/位面、言出法随             | 作为内容包或独立扩展模块接入。       |

## 最小闭环

玩家获得元素绑定的灵根、独立体质和初始修为 -> 在区块灵气环境下执行修炼动作 -> 从功法、灵根、体质或法宝来源获得能力 ->
在统一能力状态机中以 `costs: [{id, amount}]` 原子消耗/恢复灵力等资源、满足条件并执行动作 ->
使用带灵力容器的物品与储物法宝 -> 满足数据包定义的条件尝试突破 -> 成功或失败事件交给数据包/KubeJS处理。

炼丹、阵法、飞剑、灵宠和天劫均应是这个闭环的扩展消费者，而不应另建孤立的数值体系。
