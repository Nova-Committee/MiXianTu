# 外部内容接入可行性分析

本文对照以下外部策划文档，说明其功能在 MiXianTu（Mxt）框架中的落点：

- `7c5648c63aba4ebb9fcc2bfbd38a1368cx.docx`：生物图鉴与怪物配置需求。
- `f815f0ed8dfc4948afc8c5360b09777ecx.docx`：地图建造与建筑配置需求。
- `80b7147a65444d0f9745d7b3d4082f49cx.docx`：美术资源与音效配置需求。

## 范围原则

Mxt 是修仙玩法的**绑定层和规则层**，而不是具体内容包。

- Mxt 不定义任何具体怪物、Boss、物品、功法、地图、剧情或数值。
- KubeJS、原版数据包和资源包负责注册、制作并配置具体内容。
- Mxt 通过动态数据表，将已注册的实体、物品、方块和维度接入灵气、境界、资源、技能、阵法、契约、品质和经济规则。
- FTB 系列负责任务、队伍、领地和通用权限等服务器基础设施；它们不是 Mxt 的替代品，而是可选协作方。
- GeckoLib 负责实体、坐骑、宠物和 Boss 的模型、骨骼动画；Mxt 只关心这些实体的玩法绑定。

因此，“仅数据包 + KubeJS”指不新增 Java 内容模组；“加上 FTB 等常见模组”允许使用 FTB 系列、GeckoLib 和资源包承担其各自的通用职责。

## 各层职责

### Mxt

Mxt 负责稳定的、服务端权威的修仙规则：资源与境界、灵气环境、物品绑定、能力与条件、阵法、天劫、锻造炼丹、契约、品质及货币。它不拥有具体内容的
ID、数值和美术资源。

### 数据包与 KubeJS

数据包声明 Mxt 规则的实例和引用关系；KubeJS 注册内容、监听游戏事件、调度剧情和将外部内容连接到 Mxt。KubeJS 的复杂逻辑应优先调用
Mxt 已有的受校验 API，避免直接篡改附件状态。

### FTB 系列

FTB Quests 适合任务进度、任务链和奖励展示；FTB Teams/Chunks 适合队伍、领地和权限。Mxt 的宗门系统可以读取或映射这些通用身份，但不重复实现它们的基础能力。

### GeckoLib 与资源包

GeckoLib 处理动态模型、骨骼动画和可视化实体；资源包提供贴图、声音、BGM、字体与 GUI 资源。Mxt 的 Action
可播放已注册声音、生成已注册粒子，但不会生成素材或客户端渲染管线。

## 仍需内容实现决定的边界

1. 若只需要预制副本维度，Mxt 的 `realm_instance` 足够承担进出、人数和时限规则。
2. 若要求每支队伍拥有同时存在、彼此隔离且可复制/销毁的地图实例，需要专门实例维度运行时；这不是数据包、KubeJS 或 FTB 的通用职责。
3. 若需要全新的客户端 GUI、网络同步协议、Boss 状态机或渲染管线，应放入独立内容模组或扩展，而不应扩张 Mxt 的核心范围。
4. 外部实现只要能产出既有实体、物品、方块、维度或玩家状态，就可以通过 Mxt 的 Holder 引用、标签、Matcher、Action 和 Condition
   接入修仙规则。
