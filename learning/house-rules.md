# 写代码的房规

- **注释三律**（全仓统一口径）：
  1. **命名先自解释，注释只做附加解释**：能从名字读出来的不要再讲一遍（`/** The player's name. */ getName()` 属于噪音）。
  2. **对外 API 之外不写成套 Javadoc**：只有 `api/` 与 KubeJS 桥接这类"别人要实现 / 别人要调用"的契约才写完整 Javadoc；本体内部（**含 `public` 成员**）默认不写 Javadoc，只在**有明确限制需要特别标明**时写——顺序/时序、重入与线程、按注册表实例开缓存键、原版与平台怪癖及 workaround、魔数与 tag 名的来历、单点实现约束（"唯一出口，别在别处再算一套"）、服务端/客户端边界、会静默失败的行为。
  3. **不重复解释，一处两行内**：单处注释（对外 API 的 Javadoc 除外）不超过两行；同一条解释不要在类、构造器、方法上各写一遍。
  - 长解释属于文档：设计动机、方案对比、历史与移植来源写进 `research/` 或文档站的技术页（`docs/docs/technical/`），代码里只留结论与约束（别让注释成为某段设计说明的唯一一份）。
- **Definition 的两个 Codec**：`CODEC` 是 Holder Codec，`DIRECT_CODEC` 是直接对象 Codec，注册表注册后者。
- **`DIRECT_CODEC` 必须每次解码都造一个新对象，不能返回共享实例**：`MappedRegistry` 判"这个值是不是已经登记过"用的是 **`IdentityHashMap`（比引用，不比 `equals`）**，所以 `MapCodec.unit(new X()).codec()` 这种"捕获一个静态实例"的写法会让**第二份文件**撞上 `Adding duplicate value 'X[]' to registry`，整个世界加载失败（`Util.pauseInIde` 那条 ERROR）。**空组件 record 是唯一会暴露这个坑的形状**：有字段的 `RecordCodecBuilder` 每次解码都 `new`，所以别的表都被字段救了，只有零字段的 `MedicinalProperty` 中招（实机踩到）。**要用 `MapCodec.unit(X::new)`（Supplier 重载）**，它每次 `decode` 都调一次 `get()`。同一条理由也适用于将来任何"定义没有任何字段、纯粹靠 id 认身份"的表。
- **`RecordCodecBuilder` 不认识未知字段，会静默丢掉**：一份写着 `element` 的体质会被当成"没有元素"照常跑。这是刻意的口径：**改字段名 / 删字段时老文件不会报错，只是那个键不再生效**，所以字段变动必须同步 `docs/docs/datapack/json/<定义>.md`（中英各一份）与测试包，别指望加载期替你发现。**"某个类型永远读不到的已知字段"走同一条口径，一律静默忽略**：`mxt:mount` / `mxt:flight_control` 写了 `entity_action` / `components` / `cast_time` 之类、`mxt:active` 写了 `slot`、`mxt:textured_bar` 的 `fill_sprite` 写了尺寸、`structure_check: always` 的阵法又写了结构、`durability: 0` 的符箓又写了 `consume`—— 这些写了既不报错也不生效。**边界就是"永不读的键"这一类**，下面这些照旧拒收：空表 / 空列表用 `.validate(...)` 拒绝（否则会静默变成恒真或恒假）；字段**值**的校验（有限性、非负、区间）走 `.validate(...)`；**重复条目**（同一个 store 写两次、同一条技能链的 tier 写两次）与"两处对同一件事各写一遍互相矛盾"（例如阵法同时写 `structure_template` 与 `structure`）；未知的枚举取值（"忽略"对一个字段值没有自然含义）。
- **链式 `.validate(...)` 会打断类型推断**：尾部接了 `.validate` 之后要写显式见证 `RecordCodecBuilder.<X>create(...)` / `RecordCodecBuilder.<X>mapCodec(...)`（参见 `Element`、`Physique`）。
- **集合 Codec 是容错的**：`CollectionCodecs` / `TolerantMapCodec` / `TolerantListCodec` 会把坏条目打一条日志后**丢弃**。所以"定义写错"往往表现为"这一项不存在"，排查时先看日志里的 `Ignoring invalid list element`。
- **列表里的空堆要用 `ItemStack.OPTIONAL_CODEC`**：`ItemStack.CODEC` / `STREAM_CODEC` 都拒绝空堆（`count` 必须 1..99、物品不能是 `minecraft:air`），而**组件与附件是要落盘、要同步给客户端的**——只要列表里出现一个空堆，整包就编码失败（`clientbound/minecraft:container_set_slot` 报 `Failed to encode`：用空堆表示"这一格是空的"就会这样炸）。所以凡是用空堆占位的列表一律 `ItemStack.OPTIONAL_CODEC.listOf()`（方块实体的库存 NBT 一直是这么写的）；单个可选堆用 `.optionalFieldOf(name, ItemStack.EMPTY)` 能兜住，因为值等于默认值时字段会被整个省掉。列表里根本不会出现空堆时（例如 `copyStacks` 已经过滤），`ItemStack.CODEC` 没问题。
- **只读查询用 `getExistingData(...)`**，不要为了问一句"它有没有灵根"就创建一份空附件（会跟着进存档）；只有真正要写的地方才 `getData(...)`。
- **缓存按注册表实例开键**（见 `DamageElements`、`ElementReactionService`、`FormulaNames`）：`/reload` 不会重建 datapack registry，世界加载才会换实例；**但别只靠这个键**——凡是"索引内容来自数据包定义"的实例键缓存，还要在 `DatapackCache.onTagsUpdated`（根 `TagsUpdatedEvent`，两端共用同一份静态索引）里显式 `invalidate()`，否则换了包而实例没换时会一直用旧顺序；上限参考 `MAX_CACHED_REGISTRIES` + `LOCK` 双检。**按 `ServerLevel` / `LevelChunk` 开键的静态集合另有一条**：值里能走到键的**一律不许用弱键**——值含 `LevelChunk`，而 `LevelChunk` 持有 `private final Level level`，键从 map 自己身上就强可达，`WeakHashMap` 也回收不了（`AuraChunkTicker` 的 `LOADED` / `PENDING` / `REFRESH` 就是这样，只能靠 `ChunkEvent.Unload` 与 `LevelEvent.Unload` 清，而且"这个区块现在是加载的"是**事实**、不是可达性，弱引用给不了）。值不含 level 的（纯数据、只有 id / 数值）用 Guava `MapMaker().weakKeys()`——键按引用比（就是 `IdentityHashMap` 的语义）、并发安全，世界一关条目自己就没，别让别的模块点名来清（`AuraQueryCache` 的八张表、`CurseScheduler.QUEUES` 是这一种；**不要**用 `Collections.synchronizedMap(new WeakHashMap<>())`，迭代时被 GC 清键会 `ConcurrentModificationException`）。**凡是绕过 `MinecraftServer` 直接 `level.close()` 的路径（运行时维度、秘境的卸载）必须自己发一次 `LevelEvent.Unload`**，与 `MinecraftServer` 停机时的顺序一致（先发事件、再 close），否则所有"只订阅事件"的模块都会把那个 level 一直钉住。
- **跨 tick 的实体状态一律按 `UUID` 记账，不拿 `Entity` / `Player` 当键**：静态缓存一旦拿实体做键，就把实体、它的世界、它的区块整条链钉住（`Entity` → `Level` → `ChunkMap`），再怎么挂卸载钩子也总有漏的路径。全仓因此**没有一处静态集合是 `Map<Entity, …>` / `Set<Entity>`**——查询记忆（`LAST_QUERY`）、提示与进度缓存（`LAST_PROGRESS` / `LAST_FAILURES` / `REQUESTS`）、阵法在场名单（`PRESENCE`）、诅咒排队（`nextDue`）的键全是 `UUID`，值里也不放实体。**代价是 id 会比实体活得久，所以按 id 记账的人自己负责在实体离开时 `forget`**（`AuraZoneEventBridge` 听 `EntityLeaveLevelEvent` 就是干这个）。**唯一的例外是"当拍缓冲区"**：`VanillaTriggerBridge.PENDING_EFFECTS` 的值是实体，但它在自己的 `ServerTickEvent.Post` 里先整表取快照再 `clear()`，最多活一个 tick；同类结构必须同样的形状（单拍清空、不跨 tick 残留）。`ThreadLocal<Set<Entity>>` 这类重入守卫不算（只活在一次调用的栈上）。
- **重入守卫用 `ThreadLocal<Set<...>>` + try/finally**（见 `CurseService.IN_TRANSACTION`、`ElementReactionService.IN_CHAIN`、`TriggerDispatcher.DISPATCHING`）：链式触发很容易写成无限递归。
- **失败用结果记录，不用异常**：`Result(changed, failure)` + `Failure` 枚举（`CultivationIdentityService`、`CultivationToggleService`、`AbilityService.UseResult` …）。客户端调用一律返回 `false` / `0` / `failure = SERVER_ONLY`，不写日志。
- **显示名走 `DefinitionText.name(holder)`，而且定义里一个文本字段都没有**（`spirit_root` / `physique` 原先的 `rarity` 已并入 `quality` 引用，`mxt.rarity.<值>` 那套查询与 `DefinitionText.rarity(String)` 都已删除；**列一个档位时用 `QualityService.displayName(holder)`**，它把这一档自己的颜色刷在它自己的名字上）。**24 张注册表的定义不再有 `name` / `description`**（`api/NamedDefinition`、`util/codec/ContextNameCodec`、`util/codec/ContextNameListCodec` 与"把解码期条目 id 运进 codec"的 `accessor/ResourceLoadingOps` + 两条 `mixin/codec/*` 已**全部删除**，见 [`research/83`](research/83_定义文本按id生成设计.md)）：名字与描述**永远按注册 id 现算**，键是 `<注册表命名空间>.<注册表路径>.<条目命名空间>.<条目路径>`（注册表命名空间恒为 `mxt`，所以本模组所有定义键都以 `mxt.` 开头；路径里的 `/` 原样保留），描述再加 `.description`。**包唯一能给一个定义配词的办法就是翻译这个生成的键**——"写出来的文本压过生成的键"这件事在形状上已不可能，也别在别处再拼一套名字键、别再造第二套键。**出口按手里有什么选，类别一律由注册表自己答（就是注册表路径），调用方不再传类别串**：手里是 `Holder` 就交给 `name(holder)` / `description(holder)` / `minorStage(holder, 下标)`，只有 `ResourceKey` 就交给 `name(key)` / `description(key)` / `minorStage(key, 下标)`（它们从 `key.registry()` 取类别），**只剩一个 `Identifier` 才用 `name(id, 类别)`**——那要求调用方自己写类别，所以只留给"身体里那份引用之外只有 id"的场合：台账 / 命令参数 / 网络载荷里的 `Identifier`、`AuraResult.source()` 这类运行期来源 id（类别由 `SourceKind` 分支给出）、以及 Jade 这类客户端拿不到注册表的路径。**`name(Holder, String)` 与 `defaultText(...)` 都已删除**，别再按类别传参、也别再找"省略时生成什么"那个出口。**名字没被翻译时，界面里不许出现键名，出口只有两个**：`DefinitionText.nameOrId(...)`——必须显示点什么的地方（列表行 / 标题 / 面板条目 / 嵌在别的句子里当参数）回退显示 **id**（`mxt:aura/example.fire`，仍然认得出是哪一条）；`DefinitionText.resolved(DefinitionText.text(...))`——可以空着的地方（提示框里只起标题作用的那一行：丹药定义名、药材定义名、炉壁 / 炉型名、符箓类型说明行）**整行不画**。选哪个由"这里能不能什么都不显示"决定，不按文本长度或好看程度挑。**描述只有 `DefinitionText.description(...)` 一个出口**，画它的目前只有五处：品质提示框、契约卷轴提示框、认领丹药的物品提示框、手册的提示框（`ItemBindingTooltipAppender` 里紧跟功法名那一行）、功法书在聊天栏的读出行——**印之前一律先过 `DefinitionText.resolved(...)`**——它查的是语言文件里到底有没有这个键（`Language.getInstance().has(key)`；字面量与带 fallback 的翻译件照旧算有）——否则会把没被翻译的生成键当正文打进提示框或聊天栏（**现在这条闸门比过去更要紧**：过去"包写了字面量"不需要翻译，现在**所有**描述都只在被翻译时才画得出来）。`DefinitionText.resolved(...)` 也是"这段文字到底有没有"的判据，别用裸 `getString()` 判——键缺失时它回退成键名本身，永远非空，等于没有闸门。
- **功法书翻开时的两页贴图按功法 id 现取**（纯客户端资源，数据包侧只出功法 id）：`items/technique_book.json` 的 `on_true` 用模型类型 `mxt:technique_textures`（`render/model/TechniqueTextureModel`，走 `RegisterItemModelsEvent` 登记，`model` / `transformation` / `tints` 与 `minecraft:model` 同形），`pages` 把 `left` / `right` 两页各指到模型里的一个贴图槽（本体的读书模型两页共用一个槽，写的是 `{"left": "3", "right": "3"}`）：**贴图 id 全自动**，功法 `mxt_test:qi` 的两页就是 `mxt_test:item/technique/qi_left` 与 `..._right`（文件在 `assets/mxt_test/textures/item/technique/qi_left.png`），缺哪一页就退回**同一命名空间**的 `mxt_test:item/technique_book_page`，那张也没有才留着模型自己写的那张（拿 `MaterialBaker` 解出来跟 `missingno` 比，不比就等于画黑白格）。**一个槽只填一次，先填的是"自己画了图"的那一页**（两页共用一个槽时就是先 `_left` 后 `_right`）——别拿 `addTexture` 的调用顺序表达优先级，后写的会盖掉先写的；`pages` 点了一个**模型里没有的槽名**在 bake 期报一条 **ERROR**（模型把槽改名而 `pages` 没跟，症状正是"代码看着对、画面一点不变"：那一页被静默丢掉了），解码期只拒空槽名与 `left` / `right` 以外的页名。**它重烘几何、而不是逐面换 sprite**：两个槽默认指同一张 `technique_book_page`，按 sprite 认不出左右页，所以按 id 覆盖一份 `TextureSlots`（`Resolver.addFirst` 压过模型自己的链）后重烘，再交给 `CuboidItemModelWrapper` 的公开构造器（NeoForge 的 `TrimmedArmorModel` 是同一套原语）；结果按功法 id 缓存，缓存跟着资源重载重建，所以不需要 `DatapackCache.onTagsUpdated` 那类失效钩子。**重烘只能走 `resolved.getTopGeometry().bake(slots, baker, BlockModelRotation.IDENTITY, resolved, resolved.getTopAdditionalProperties())`，不许用 `resolved.bakeTopGeometry(...)`**：后者在默认状态上按模型缓存**第一次**烘出来的几何（`ModelDiscovery` 的 `KEY_DEFAULT_GEOMETRY`），`TextureSlots` 参数被整个忽略——症状就是"槽填对了、图集里也有图，画面依旧是原来那张"，别往图集或 UV 上想。**写哪个槽由模型文件说了算**：元素名烘完就丢，运行期只认得 sprite 与方向，所以包要独立换某一面，就得让那一面在模型里独占一个贴图槽。
- **读一门功法的时长、姿势与音效写在功法定义上**（`Technique.learn_time` / `hold_animation` / `hold_sound`），**不在 `technique_binding` 上**：绑定表只剩"哪些叠算这门功法的手册"（`items`）、本体生成的载体（`carrier_item`）、`priority` 与学习前条件。逐堆换个读法走 `mxt:technique_reading` 组件，它按**字段**覆盖功法给的那三个。解析只有一个出口：`ItemBindingService.reading(access, stack)` → `TechniqueReading`（三个值 + `requiresHold()`），`TechniqueHold` 与 `TechniqueItemService`（进度条、百分比、读完判定）都问它，别在别处再拼一套。**长按的默认值与姿势白名单在 `HoldBinding`**（`NO_HOLD` / `DEFAULT_HOLD_ANIMATION` / `DEFAULT_HOLD_SOUND` / `ALLOWED_ANIMATIONS`，`HoldBinding.validate` 在功法解码期跑），**内置功法书的姿势钉死在默认值上**——功法写的姿势只对手册自带物品的场合可见；老包写在绑定上的 `learn_time` 会被当未知字段静默忽略，那门功法退回右键即学。**`learn_time` 是 `NumberProvider`**（`mxt:technique_reading` 组件里的同名项也是），按**读取者**求值：取数只有 `TechniqueReading.holdTicks(FormulaContext)` 一个出口（`floor`、小于 `1` 当 `0`、不设上限、非有限由 `assertFinite` 报出并按 `0` 处理）。`TechniqueHold` 因此覆写了带持有者的 `holdTicks` **和 `claims`**——少了 `claims`，依赖持有者的公式会按空上下文答"不长按"，长按根本不武装。没有上限，所以 `HoldService.holdPercent` 的乘积必须留在 long 里（`ticks * 100` 在按住约两周时溢出）。**长按的音效与进度条都不走原版**：写的 `Consumable` 一律是 `SILENT_SOUND`（原版要等跑完 21.875% 时长才响，`learn_time` 写几天就几天不响），声音由 `HoldService.playHoldSound` 按固定 4 tick 播——阅读者那一份在**客户端** `onUseTick` 里播、服务端广播时把他排除；进度条是动作栏文字，客户端 60 tick 不刷新就自己消失，所以 `TechniqueItemService` 每 40 tick 至少重发一次。**玉简不是功法手册，走同一套长按但自己一条**：`mxt:jade_slip` 由 `JadeSlipHold` 声明成长按（`requiresHold`，`holdTicks()` 答 `NO_HOLD`），**时长写在堆上的 `mxt:jade_slip_reading` 组件**（缺省 `JadeSlipItem.DEFAULT_READ_TIME = 40`；写 `0` 与潜行右键都是一点即读，判定在 `JadeSlipItem.use`，别在别处再拼一套），读完由 `JadeSlipReading` 把 `mxt:stored_text` 打进聊天栏，姿势就是长按框架给的 `BOW`（原版那只阅读手势，没有 PAL 层）。
- **子境界只声明数量，名字一律生成**：`realm_stage.minor_stages` 是 `Codec.INT`（默认 `0`，`0`–`RealmStage.MAX_MINOR_STAGES`，构造器拒绝越界），**不是**文本数组；每一重的名字是 `<本境界名字键>.minor_stage.<0-based 下标>`，出口是 `DefinitionText.minorStage(...)`，**和描述一样只在被翻译时才画**（过 `DefinitionText.resolved(...)`，没被翻译的那一重就整段不显示）。老包把它写成数组会**整个定义解码失败**（类型不符），写成整数则照旧——用户对这条拍的是"一起去掉，只留数量"，所以子境界名没有任何书写途径。
- **技能的顶层字段按代码为准，三处容易写错**（逐处核实过，别照旧文档抄）：**技能上没有 `item_action`**（codec 里没有它，写了＝未知键静默忽略——**不要在文档里列这个键**，也别写成"对承载物品执行"；要作用于物品用实体行为 `mxt:equipped_item_action` 或法器自己的 `use_action` / `pour_action`）；**四个动作字段不是通用字段**（`entity_action` / `target_selector` / `target_condition` / `bi_entity_action` 在 JSON 里写在 `type` 同级，但由会跑动作的五个类型各自声明与读取——**通用字段表里不许列它们**，只在「每个类型读哪些字段」与「四个动作字段」里写）；**通用字段表只列所有类型都读的字段**（`cooldown` 只有会付款的类型读、`damage_condition` 只有 `mxt:triggered` 读，这两个也按类型写，不进通用字段表；**代码侧也一样**：`cooldown` 归会付款的八个类型、由额外接口 `CooldownSource` 暴露，`damage_condition` 归 `mxt:triggered`、挂在 `TriggerSource` 上）；**`hidden` 只在法器提示框里被跳过**（`ArtifactDescription`），轮盘的候选池只筛"按键型"（`WheelSources.abilities` 用 `AbilityActivationService::togglable` 过滤）、**不看 `hidden`**，按下时的分派是"实现 `Toggable` 走 `AbilityActivationService.activate`，否则回落成一次 `AbilityService.use`（给**已保存的轮盘格子**，它可以点名一个不可按键的技能）"；`damage_condition` 也只有 `mxt:triggered` 会读。
- **链的走法只有一套**（`util/chain/`：`Chain` / `ChainCache` / `ChainWalker`）：`quality` 的阶梯、`realm_stage` 的境界链、`progression` 的等级链都是"一条后继字段串成的直线"，所以走链与形状判定共用 `ChainWalker.walk` 一份实现——**链接指向表外、一个条目被两处指向（分叉）、成环、有条目没被任何线走到，都由 walker 自己 `LOGGER.error` 报出，域不要在外面再查一遍**。域只做两件事：把注册表读成有序表并给一个 `UnaryOperator<Holder<T>>` 说"这一条的后继是谁"（**返回的 `Holder` 要与表里那份相等**——walker 按 `Holder` 自己的 `equals` 比，所以同一个注册表条目的等值 holder 也算同一条；返回 `null` 表示线到此为止），以及读结果 `ChainCache<T>`（按条目读 `chainOf` / `next` / `previous` / `rankOf` / `contains` / `size`；`size()` 是**线的条数**，不是条目数；**别自己先取 `Chain` 再在它上面走**）。**`Chain` 不带名字**：哪个域要把"名字 ↔ 线"当索引，就自己在那个域里挂一张 map —— 境界线就是 `DatapackCache` 里的一对 `Holder` 键表 `realmLinesByAura`（正向：档案 → 整条线，读 `realmsOf`）与 `auraByRealm`（反向：任一档 → 它归哪个档案，读 `cultivationForRealm`），**不是一张 `BiMap`**（反向问题按条目问，而且 `Chain` 当 map 键要按整份节点列表哈希）；两张表由 `DatapackCache.realmLines` 在链走完之后按 aura 档案建起来，反向表只由"有档案的线"建（遍历档案 → 取它那条线 → 给每个节点填 owner），冲突（一条线被第二个档案认领）在那一刻报出；品质阶梯的名字由 `QualityLadders.name(access, tier)` 现读（入口档写的那个 `quality`）。域自己的规矩另起一遍检查并 `DatapackCache.report(注册表, id, 文案)` 报出：境界的 `next_realm` 不许跨 aura（这一条同时让 getter 返回 `null` 断链）、`progression` 的 mastery 不许沿链下降、品质的链名不许冲突或重名——**别把这些领域概念塞进 walker**。**数据包问题一律走 `DatapackCache.report(...)`**（`MiXianTu.LOGGER.error`，文案前缀是 `data/<包命名空间>/<注册表命名空间>/<注册表 path>/<条目 path>` 那套路径，作者能直接打开文件）；缓存不再保存问题列表，`/mxt registries validation` 只看 `DatapackCache.problemsFound()` 这个计数。
- **品质阶梯只有一套形状**：档位顺序与入口档**不写在别处**，由每一档自己的 `next`（上一档）在运行期走一遍得出，与 `progression` 的 `next_level` 同形；链名写在字段 `quality` 上（一个 `Identifier`），**写在入口档**（没有任何一档把它写成 `next` 的那一档）：`QualityLadders.inherit` 沿 `next` 把这一份传给更高档，读名字用 `QualityLadders.name(access, tier)`（在那条链上找写了 `quality` 的那一档；`/quality chain` 用它印链名，没有就是 `null`），所以写在别的档上不会成为链名——整条链就是没名字的（`/quality chain` 显示 `null`，不报错）；一档收到两个不同的链名仍然报错；升级那一步的代价与条件写在**指向的那一档**上（`upgrade_costs` / `upgrade_condition`）。**不许再新增一张只装阶梯的注册表**（`QualityChain` / `QualityChainService` 与 `quality_chain` 注册表都不存在），**绑定表也不声明链**（四张 binding 没有 `quality_chain` 字段），也**别在别处再算一套顺序**：阶梯本身就是 `Chain<ItemQuality>`（名字由 `QualityLadders.name` 从链上的档读出来，`Chain` 自己不装名字），`QualityLadders.cache(access)` 给出整份索引（按档位问邻居用它），`of(access, tier)` 只留给"要把整条链画出来"的调用点（`/quality chain`）；跨条目的问题（一档写的链名与传到它身上的不一致、两个入口抢一个链名）在 `QualityLadders.diagnose` 里就地 `DatapackCache.report(...)` 报出，"写了升级数据却没有 `next`"由 `DatapackCache.validateQualityTiers` 报。走链与两个方向都见上一条的 `ChainCache`。
- **物品上的品质只有两个 id、两个载荷**：**组件 `mxt:quality` 装的是整份品质对象**（`Holder<ItemQuality>`），所以它既定档位也定这一档所属的链；`mxt:item_quality` **只是物品条件**（`ItemQualityCondition`），名字不跟着改，别把两者当同一个东西。`mxt:item_quality` / `mxt:quality_chain` 都不是组件，写了就是未知组件。**"一堆读哪条链"就是"它解析出的那一档在哪条链上"**：没有第二个地方可以声明链，解析顺序只有**三层**（组件 `mxt:quality` → **这一堆携带的定义**自己声明的档 → 注册表 `mxt:default_quality`，它在物品键的九张表里是普通一张：条目按 `items` 认领物品、按 `priority` 分先后，值里写这一堆的 `quality`），只在 `QualityService.find` 一处，别在别处重排——**只有这一个组件装档位**（`mxt:forging_result` 只记蓝图 id 与步数，锻造结算写的是 `mxt:quality`；`/quality clear` 因此也会把锻造结算/铭刻写上的那一档一起清掉，退回**携带的定义**那一层、再退回这张注册表）。**第二层由"已登记的载体"提供**：定义类型实现 `api/QualityProvider`（`Optional<Holder<ItemQuality>> defaultQuality()`），再在 `QualityService.carry` 登记它的载体组件——**这是定义类型加入的唯一入口**，`carry` 有两个重载（组件值就是定义 `Holder<T>`；或组件是个 record、给一个把它取出来的函数），`T extends QualityProvider` 所以没实现接口的类型登记不过；`QualityService` 类加载时先登记本模组自己的载体，附属模组的排在后面，一次查询按登记顺序走完整个列表（**注册是契约，不是扫描堆上碰巧带着的组件**）。**载体必须只凭这一堆就答得出**：两个重载都不给它注册表（使用闸门 `QualityService.check` 手里只有品质注册表）；载体取出的 holder 没绑定时（当前包删了那条定义）这一层答空、继续往下走。**九个定义声明 `quality`**（都是可选、都走 `ItemQuality.CODEC.optionalFieldOf("quality")`），各由一个已登记载体读到：`technique` / `alchemy_furnace`（原必填，现可选）/ `alchemy_wall_material` / `spirit_root` / `physique` / `pill` / `formation` / `secret_realm` / `contract_type`——一类定义共用一件内置物品（所有功法书、所有丹、所有炉型规格、灵根石、体质石…），物品说不清是哪一档，只有堆上携带的这份定义说得清。**`artifact` / `spirit_herb` 没有 `quality` 是有意的**：它们按物品认领（`ItemMatcher`），堆上没有装定义身份的组件，没有可问的对象，档写在 `default_quality` 里；`talisman` 也没有：它的载体装的是一列符的 id，同样没有单份定义可问，档由画符配方写组件、写不上才兜底到 `default_quality`。**列表型载体一律不登记**（`mxt:forging_methods` / `mxt:forging_blueprints` / `mxt:element` / `mxt:talisman`）。**`spirit_root` / `physique` 原先的自由文本 `rarity` 已并入 `quality`**（破坏性迁移：老包的 `"rarity"` 键不再生效、那个定义就没有档；`mxt.rarity.*` 查询与 `DefinitionText.rarity(String)` 都已删除），列一个档位时用 `QualityService.displayName(holder)`。**模块自己的档位逻辑另算**：锻造按蓝图曲线定档后写组件、画符按完成度定档后写组件。别把这条与 `forging_blueprint.quality_by_extra_steps`、画符配方的 `grades[].quality`、`ItemQuality` 自己的 `quality`（那是**链名**）混为一谈。**要求层挂在哪儿只有这几种**：物品条件 `mxt:item_quality`、匹配器条目 `mxt:quality`、自定义材料 `mxt:quality`（`neoforge:ingredient_type`），外加匹配器条目 `mxt:ingredient`——它是"整份原版材料（含 `mxt:quality`）写进只吃 `ItemMatcher` 的位置"的唯一通道。**画符的符纸是两条**：槽位认标签 `mxt:talisman_paper`（客户端也答得出"这算不算纸"，**别把档位要求塞进槽位谓词**），符方自己的 `paper` 字段（原版 `Ingredient`，不写＝那个标签）在开局时收窄并决定实际取走哪一张；结算把这张纸的档在它自己链上的位置作为 `paper_rank` 给 `result` 的公式。**比两个档的大小只有一个出口**：`QualityLadders.compare(access, a, b)` → `OptionalInt`（**正数＝前者高**），`atLeast` 就是它 `>= 0`、`rank` 给链上位置；**空＝无法比较**（跨链、以及只被"走不出来的链"装着的档，**连自己跟自己都是空**），别把空当成"更低"，也别在别处再写一套比大小。
- **丹炉的档位挂在核心上，不挂结构**：丹炉要按品质筛的**不是投进去的药材，而是核心那件物品**（"设置温度"、开界面、记批次的那一件）——炉壁、炉型、形状一个品质字段都没有，别往多方块结构上加。丹方（`mxt:alchemy`）用可选字段 **`furnace_quality`**（就是 `QualityRequirement` 的嵌套形状：`quality` 成员 + `min_quality`，写空对象在加载期被拒）要求核心的档，判据是 `QualityRequirements.test(access, station.furnaceItem(), 要求)`、与另外三个口子同一处实现；失败原因是 `AlchemyFailure.FURNACE_TIER`，与"核心根本没有档"（`FURNACE_QUALITY`）是两回事，顺序排在后者之后、"这一档自己的使用条件"之前，拒开不扣料、不动供热方块。**同一份要求的输入侧是可选字段 `input_quality`**（同一个嵌套形状，同样拒空）：丹炉输入仓的**每一格非空输入**都要过 `QualityRequirements.test`，一格不过就是 `AlchemyFailure.INPUT_TIER`，排在 `FURNACE_TIER` 之后、核心自己的使用条件之前，同样拒开不扣料——`inputsSatisfy` 是它唯一的实现，别在别处再写一遍"这格药够不够档"。**炉温上限是三者取最低**：炉型规格自己可选声明 **`max_temperature`**（有限正数，省略＝这一层不设上限）、**18 块炉壁**里最低的那个耐温（`alchemy_wall_material.max_temperature`；需要校验的格子一共 22 个，另外四个是核心、两个投料仓与产物仓）、供热方块给出的最高温（`heat_source` 或方块自己实现的 `AlchemyHeatSource`）。规则只在 `AlchemyFurnaceDefinition.temperatureLimit(wall, heat, spec)` 一处，谁都不能把它写成"只由炉型决定"或"只由炉壁决定"——**更好的核心只能把上限抬到炉壁/供热允许的地方为止**（所以"高炉阶 → 更高炉温上限"是把高炉阶那一份规格的 `max_temperature` 写大，不是加在别人头上）；炉壁或供热缺一（上限读到 0）就是这台炉子根本不能开，`setTargetTemperature` 也会照着这个上限拒收。**读档那一步要按 `AlchemyFurnaceStructure.walls()` 的长度数**（别写死数字：炉壁数由结构表说了算，写死会让上限恒为 0）。**"更高级的炉子更快"是框架规则，不靠配方写公式**：批量时长先由丹方自己的 `duration` 算出，再除以**两个** `alchemy_modifier` 的乘积——**原料侧**取炉内已带档材料里最小的那一个（`inputModifier`，没带档的跳过），**核心侧**取核心那一档自己的 `alchemy_modifier`（`QualityService.modifier(access, station.furnaceItem(), …)`，核心没档就是 `1.0`）。所以包只要给高炉阶写 `alchemy_modifier: 2`，这台炉子炼什么丹方都更快，一行公式都不用。核心那一档在**它自己那条链**上的位置作为变量 **`furnace_rank`**（`AlchemyRecipe.FURNACE_RANK`）**只注入丹方自己的公式字段**（阈值 / 温度 / 时长 / 环境门槛），与画符的 `paper_rank` 同形状：没有档、档不在链上都是 `0`；**药力公式读不到它**（那会改混合物、进而改匹配结果——换核心不该改变"这炉丹配不配得出来"），**任何档位的 `alchemy_modifier` 公式也读不到它**（高级炉子靠上面那条规则更快，不靠在 modifier 里读炉阶），**手里没有核心的路径（配方管理器的 `AlchemyRecipe.matches`）同样读作 `0`**。它也**不是** `mxt:formula_variable` 注册表条目（那张表是代码注册表，名字写错不会在加载期被拒）。
- **修炼方式只有一套挑选**：一条运功法门就是一条 `cultivation`，**两对条件与行为各答一件事**——`start_condition`＝能不能坐下；`cultivate_condition`＋`cultivate_action`＝**这一拍能不能拿到成果**（条件不成立时**不中止**：不扣钱、不给收获、不推进结算，条件一恢复立刻结算，`cultivate_action` 只在结算成功那一拍跑）；`tick_condition`＋`tick_action`＝还继续不继续（`tick_condition` 不成立才中止，`tick_action` **每一个 tick** 都跑）。**选择器只有一处**（`CultivationModeService.select`）、顺序只有一条——**先筛"此刻适用的"，再在筛出来的里面按 `priority` 挑**（同分按注册表顺序，一条都没有报 `Failure.NOT_APPLICABLE`）；"适用"的判据是 `start_condition` + `cultivate_condition` + `CultivationMethodService.canStartCultivation`（灵气侧 `start_cultivate_conditions`），**`tick_condition` 不参与**（它答的是"已经在修炼的身体还要不要继续"，坐下前必然为假，拿它筛会让两个还没入定的人互相挡住）；**冷却也不进适用性**（否则换一条就是绕过冷却，冷却仍然只在开始时判）。**附件里的那条不参与挑选**（它只是"现在在跑的是哪条"的记录，tick / 停止 / 自动突破读它），**按 C 停止只用附件里那条**（`toggle` 分两支），别用选择器的结果。读状态用 `mxt:cultivating`（"对方在修"只能写在 `tick_condition`）、`mxt:partner`（"对方手上拿着什么"用 `mxt:target_condition` 套物品条件，双修就靠它，能在坐下前成立；`mxt:friend` **有向**，要"两人互相为友"写 `mxt:mutual` 套 `mxt:friend`——`mxt:undirected` 是"任一方向成立"、`mxt:mutual` 是它的对偶"两个方向都成立"）；起停用 `mxt:cultivate` / `mxt:stop_cultivating`（**数据包与脚本唯一开练入口**，另一个是玩家的修炼键）。**中止可以说出自己的名字**：`tick_condition` 不成立而中止时用 `abort_reason`（可选文本）替代通用文案，别的失败原因（环境、灵气、公式）不受它影响。**`/mxt cultivate select <action>` 是一次性点名**（管理员用）：点名那条立刻开练、正在跑的先停，但仍要过同一把筛子，不适用就拒绝且不动正在跑的那条；**不落盘**，按键时的顺序照旧。功法遗忘走 `TechniqueService.forget`（一个实现，`/technique forget` 与 `/technique drop` 两个入口）——**只删这门功法自己的层数记录**，境界/修为/资源/正在跑的法门都不在它管的范围里。

`auiPageWritable` / `auiBound` / `getOrThrow` / `find` / `missing` / `text` / `click` / `scrollList`）。**文档归 ApricityUI**，接口里因此没有 `auiSetDocument`：`AuiLinkedScreen.getLinkedDocument()` 是唯一出口，由 AUI 的宿主提供。子类宿主的 `init` 只有三步——`auiPreparePage(path)`（预热样式表，必须在文档存在**之前**）、`super.init()`（AUI 建文档；**窗口缩放会重进 `init` 并重建文档**，所以缩放也会重绑一次，那正好是一份干净的新 DOM）、`auiPageOpened()`（命名页面、绑契约）。**别自己 `implements AuiLinkedScreen`**：新界面继承上面两个之一。宿主**保留**四件：页面绑定、原版灰底（`AuiStyles.extract(this, graphics)`，别调 `super.extractBackground`）、**面板实时矩形**（`panel` 元素加 `Position.of` / `Size.of` 每帧算出的 `panelLeft/Top/Width/Height`，喂 `slotsDrawn()`、屏幕自己的命中判定与 `hasClickedOutside`——AUI 的容器宿主是整窗尺寸，"点面板外丢下手上物品"必须自己按面板矩形判）、以及**非槽位非物品元素的 tooltip**（`tooltip(Element, Supplier<List<Component>>)`，在 `super.extractRenderState` 之后登记；同一帧先排队的赢，所以物品自己的提示框不会被顶掉）。**几何就绪的判据弱化了**：只剩"面板实时矩形可用"，不再逐槽位做内容对账（那层随对账层一起删掉，理由见 `research/67_AUI宿主与容器协议迁移设计.md`）。**写页面元素只有一份实现**：`screen/aui/AuiElements`（`style` / `setText` / `setClass` / `setDisabled`，一律先比再写——每次 DOM 写都会重跑样式），宿主、`AuiScrollList` 与行绑定都调它，别在宿主里再抄一份 `put` / `flag` / `setText`（也**不回读**页面：Java 只写）。**按钮"能不能按"写 `disabled` 属性、别写类**（主题里是 `.button[disabled]`，而 ApricityUI 对带这个属性的元素根本不派发 `click`，样式与行为同出一处）；**同样地，凡是写入口自己会比对的状态都别再留一份"上次写了什么"的缓存字段**——那种缓存只会跟 DOM 走散。**新界面继承其中一个，别自己 `implements AuiLinkedScreen`**。子类的 `bindPage()` 用 `this.field = this.getOrThrow("id")`（节点标签有要求就 `this.getOrThrow("id", Canvas.class)`，标签不对等同于缺项；允许缺席的节点用 `find`）拿节点，其余结构性问题 `throw this.missing("...")`；`auiRebind()` 接住这个 `NoSuchElementException`、丢掉半份绑定、把缺的那一项写进一条 WARN（屏幕上一个字都不画），所以 `bindPage()` 没有返回值、也不许把失败写成别的异常（别的异常照旧直接崩，那是宿主的 bug）。页面路径只有 `screen/aui/AuiPages` 一处（宿主的 `auiPreparePage` 里预热样式表）。页面侧硬约定见 `docs/docs/java/screens.md`。
- **界面也可以整块交给 ApricityUI，自己一条像素都不画**（轮盘是第一处）：
与丹炉那种"页面画板 + 原版槽位"不同，轮盘的几何是常量，所以 Java **只在绑定时**把 12 条 `clip-path: polygon(...)`（扇环多边形，相邻扇留 0.6° 缝，缝里直接透出游戏画面当分隔线）与 12 个图标／名字锚点写进页面，之后每帧**只在状态真的变了时**写 class、文本与物品栈——**绝不回读 DOM 几何**（容器页那套"每帧读回几何"的对账层已整段删除，见上一条；轮盘的几何本来就是常量，绑定时写一次就够）。规矩与坑：① 每个 Text/class/物品栈都要带缓存再写（`getClassList().toggle` 每次调用都会 `setClassName`，不先 `contains` 比一下就是每帧重跑样式）；② 图标有两支——物品用 `<item>` + `setIngredientStack(stack)`，**贴图**用 `<texture src="…">`（按元素 CSS 尺寸画 Minecraft 贴图，不是从左上角裁），`<item>` 要写 `interactive="none"` 免得它自己再弹一个物品 tooltip；③ CSS 里**没有** `radial-gradient` / `conic-gradient`（只在 `<canvas>` 的绘制 API 里有），光环只能用整圆 + `box-shadow`，扇环的描边只能靠留缝；④ `@keyframes` / `transition` 都能用（可插值 transform / filter / box-shadow / opacity / 颜色，`FrameScheduler` 每帧推进，不是 20Hz），但 **animation 的优先级高于内联声明**：Java 写的适配缩放在哪个元素上，回摆／呼吸动画就别挂同一个元素（轮盘因此分 `#stage` / `#ring` / `#sectors` 三层）；⑤ 同一份 animation 连续重放不会重启，要重放就交替两个名字不同的类；⑥ **别用 `opacity` 藏层，能不用 `filter` 就别用**：两者走同一条 FBO 滤波通道，而且轮盘第一版用 `opacity: 0` 藏"指向高亮"那一层，实机十二扇全是高亮色（该层常显）——藏／显一律 `display: none` / `display: block`，"变暗／变亮"一律换渐变（轮盘的指向态因此只有"更深 + `transform: scale()`"，不叠 `drop-shadow`；`box-shadow` 不受这条限制，光环的呼吸就是它）；**入场 / 开合动画也只动 `transform`，别动 `opacity`**：轮盘那条 160ms 淡入实测会把首帧烘出来的文字栅格留在 ~10% 白（提示行开头几个字、以及首帧写下的扇名一直发暗——像素量过：暗字 17~25、白字 255），文字栅格的缓存键里没有祖先的不透明度，烘进去就不会再变亮；⑦ 文档是**全局**的（PIP 渲染器整批画 `Document.getAll()`），`removed()` 里必须 `document.remove()`；⑧ 页面缺失或节点缺失时**别让输入一起坏掉**：什么都不画（缺页与缺节点都是作者的错，只在日志里留一条 `Page … does not match its contract` / AUI 自己的 `[AUI Document]` 错误），键盘照旧能用；⑨ 页面路径只有一处（`screen/aui/AuiPages`）；⑩ **别给整块界面垫一层底盘，也别给扇里的内容盒加 `overflow: hidden`**：轮盘第二版垫了一层 208px 的圆当"缝的颜色"，实机它盖在扇环上面（绝对定位的兄弟之间别指望 DOM 顺序），去掉后缝里直接透出游戏画面；内容盒上的 `overflow: hidden` 则让每个有名字的扇多出一个盒大小的暗块（遮蔽机制的痕迹），名字本来就该在 Java 侧按可用宽度截断。每个状态的底色都写 `background-color` 兜底，免得某条渐变没解析出来时整圈消失。
