# 模块实现审计

**此文档已过时，新版：https://docs.qq.com/sheet/DWW9qRU1ST2Nob3Z5**

审计日期：2026-08-20。

本项目目前注册 **33 个原版 NeoForge 数据包注册表**。本文件将“通用数据驱动能力”与具体玩法拆开记录，避免某个玩法复用了成熟的
Action、Condition 或 NumberProvider 后，被误判为这些基础能力尚未实现。

## 判定标准

- **完成**：定义、所有字段的运行时消费者、存储/同步和入口已构成服务端闭环。
- **制作中**：定义与大部分运行时已存在，但至少一个字段、入口或下游联动没有消费者。
- **预留**：仅有数据结构、固有类型表或资源；尚未形成主要玩法闭环。

### 伤害管线

| 能力 | 状态 | 已实现内容 | 边界 |
| --- | --- | --- | --- |
| `DamageCalculationService` | 完成 | 模组自己发出的伤害只有这一条公共路径，分两层：**第一层出力**（发伤害处，攻击方一侧）把定义里的基础值乘以施放带来的 `damage_multiplier`、这次施放的 `element_modifier`（匹配灵根的 `element_ability_modifier`）、攻击者在效体质的 `damage_dealt_multiplier` 与**这一击的元素**对目标元素的 `overcomes`；**第二层减免**（`LivingIncomingDamageEvent`，受击方一侧）乘以受击者元素对**这一击的元素**的 `adapted_to` 与受击者在效体质的 `damage_taken_multiplier`。**2026-09-22 修掉一处实现与文档不一致并新增直通标签**：①*没有加害者*的一击此前仍会读 `overcomes`——只要这一击靠声明的 `damage_type`/`element` 拿到自己的元素，`elements` 就非空，于是自伤/反噬会把自己灵根之间的克制乘进去，而文档写的是"默认没有归属，因此不吃元素关系"；现在 `attacker == null` 时第一层**只**乘 `damage_multiplier` 与 `element_modifier`（施放的属性照旧缩放，功法越强反噬越重），`overcomes` 与加害者体质不参与，等于把文档的口径落到代码；第二层的适应照常结算（它是受击者自己的属性，自伤时也照算）。②新增原版 `damage_type` 标签 `mxt:no_bonus`（`data/mxt/tags/damage_type/no_bonus.json`，默认只收虚空 `minecraft:out_of_world`，内容包可追加或整体替换）：列进该标签的一击**两层都不结算**、**也不在受击者身上留元素**（`ElementReactionService` 不参与），数值原样交给原版（原版自己的护甲/附魔/抗性/吸收/无敌帧照旧）；判定按伤害类型（`DamageSource#is`），所以对本模组动作、其它模组与原生环境伤害一视同仁，三个执行点是 `deal`、`DamageEventBridge`、`ExplodeAction` 的伤害计算器，共用 `DamageCalculationService#bypasses` 一份判定。**2026-09-22 同轮加了两件事**：①第一层多一个**自冲突因子** `selfConflictMultiplier(attacker)`——攻击者在效灵根的 `conflicting_elements` 列出了**主手物品的元素**（`ItemElements` 读）时，乘上那个元素自己的 `conflict_multiplier`（默认 1.0）；同一个元素无论几条灵根与它相冲只乘一次，且**不要求这一击用的就是那个元素**（跟自己的武器较劲，打什么都弱）。②第二层的元素附着按来源分流：`DamageElements.reading(source)` 同时给出元素与来源，只有 `Origin.TYPE` 会走 `applyFromStrike`，`Origin.ROOTS`（没人认领、回落到灵根）只参与减免。**同日再加**③附着的**第二步**：`applyFromStrike` 多一个倍率参数，由 `attachmentMultiplier(target)` 从目标**携带**的物品（双手 + Curios，走 `ArtifactUpkeepService#carried`，本轮由 private 改 public）上读 `attachment_multiplier` 相乘得到，`1.0` 为无影响、`0` 为完全不留；它只压攒的速度，反应自身的效果由那条反应的 `action` 与第二层决定。**同日第三步**：附着量改由 `DamageElements.Strike.attachment()` 给出（每个被认领类型自己的数，或元素默认值），`applyFromStrike` 因此多一个收「元素 → 量」表的入口——"这一击留多少"与"这一击是什么元素"是同一次读取的产物。**2026-09-21 补上灵根与体质这两个身份的一半**：此前灵根只通过元素关系参与（它的 `element_ability_modifier` 只是公式变量，包不写 `* element_modifier` 就等于没有），体质则**完全不进管线**（只有原版属性这一条间接路径）——现在两者都是管线因子，且分清"属于这一击"与"属于这个人"：`damage_multiplier`/`element_modifier` 是这次施放的属性（所以打在自己身上的反噬照样按它缩放），两个体质倍率是**持有者自身**的属性（第一层读加害者的"打出"、第二层读受击者的"受到"），体质倍率一律在**持有者自己的**公式上下文里求值——"这个身体挨多少"不能取决于谁在问；多条体质相乘（各自是独立来源），公式产生的非有限值或负值按不贡献处理（与被动属性同一类公式同一条规则）。第一层放在发伤害处是因为只有那里同时知道施法者、目标和正在施放的能力，第二层放在受击处是因为只有那里能看到所有打过来的伤害（别的模组、原版摔落与怪物攻击都算），而且"适应什么"本来就是受击者的属性；两层不会重复结算——第二层挂的事件每次伤害序列只触发一次，无论这一击是谁发的。**2026-09-20：两层读同一份"这一击是什么元素"**，由 `DamageElements` 从伤害类型反查元素的认领（没人认领才回落到攻击者灵根），因此第二层这个只拿得到 `DamageSource` 的地方也能算环境伤害的属性；同一个元素集合随后用于往目标身上积累附着（`element.damage_attachment`），所以"算多少"与"攒多少"永远一致。归拢进来的路径：`mxt:damage`（默认无归属，嵌在目标/乘客/装备行为里时才把施法者记为加害者）、`mxt:damage_target`（施加者记为加害者）、阵法的 `attack` 模块（按 `attribute_to_owner` 决定归属，`damage_type` 有就用）、`mxt:explode`（每次单体伤害过第一层，施法者记为爆炸起因，元素按 `minecraft:explosion` 的认领读）。加害者与来源在这里统一构造：声明了 `damage_type` 就用它并把加害者记为起因，没声明就按原版 `playerAttack`/`mobAttack`/`generic` 选择。 | 元素倍率住在 `element` 定义里、体质倍率住在 `physique` 定义里，这个服务自己不带任何数值；`mxt:lightning` 等由原版结算的环境伤害不过第一层（没有可归的攻击者），但只要有元素认领了它的伤害类型，第二层照算属性；`mxt:damage` 打在自己身上时不记归属，因此没有克制与适应可言，也没有加害者的"打出"倍率可说（加害者是 `null`）；`damage_multiplier` 与 `element_modifier` 是"这次施放值多少"，仍然生效——反噬随功法水平与灵根亲和变重；多个功法都授予同一能力时取最高的 `damage_multiplier`（不相乘）。 |

### 统一消耗（`Cost`）

**2026-09-23 落地（只编译，未实跑）**，设计见 `research/39_全局消耗定义设计.md`。原来三套互不相通的消耗形状收成一个：

- 元素形状：`mxt:resource` / `mxt:aura` / `mxt:item` / `mxt:js` + `{id, amount}` 简写；`data/resource/ResourceCost` 已删除，`data/cost/builtin/ResourceCost` 是唯一的数值条目（字段名 `resource`，简写仍用 `id`）。
- 付款者是 `LivingEntity`：`CostContext` 带付款者、公式上下文、位置、可选的方块实体库存与"灵气从哪扣"（自己账上 / 场地灵气池 / 方块实体库存）；`mxt:item` 与 `mxt:js` 需要玩家，缺通道**拒付**而不是报错——阵法可以点名一个**资源账户**（`CostContext.account(...)`）而不是某个人，所以阵主离线时它照样有账可扣（阵法的"自家库存先抵扣"仍是它自己的 `PaymentPlan`，不在这一层）。
- 一个 `Cost` 只描述"要扣什么"（`charge`，只读）；校验与扣除共用同一份计划：`CostTransaction.plan` 逐项求值加查通道，`commit` 按通道写入，中途拒付就把已经写下的还原（`abort` 用不上——主要路径是"先在草稿上做，失败就丢草稿"）。数组里任何一项付不起，整组一项都不扣。
- 常量非正数金额、同一 store 写两次（同一数值两次 / 同一灵气两次）在**加载期**拒绝；运行期公式求不出正数返回失败枚举，不再抛 `IllegalStateException`。
- 迁移的字段：`ability.costs`、`mxt:channelled.upkeep_costs`、`realm_stage.costs`、`cultivate_action.costs` 与 `aura_costs`、`formation.activation_costs` / `maintenance_costs`、`forging_method.costs`、`mxt:flight.costs`、`mxt:upkeep.costs`、灵气合成配方的 `aura`（共 11 个）。
- **只收灵气条目的两处**：`cultivate_action.aura_costs`（老写法 `{灵气: 数量}` 仍读得进去）与灵气合成配方的 `aura`；两者都加了加载期校验（别的类型直接拒绝），也都走各自的事务通道——前者从修炼者脚下的**场地灵气池**扣（先按共享池分配系数缩放再提交），后者从**工作台自己的库存**按整数单位扣。原来那张"灵气 map"的语义没有变，只是形状并进了 `Cost`。
- **有意不动**：`talisman.aura_cost`（灵气 map，"载体要灌满多少"的要求，不是支付）、门槛性质的 `minimum_aura`（炼丹配方与 `creature_profile`）；货币的 `currency.exchanges[].cost` 是价格，与本口径无关。
- 旧的 `AutoIgnoreListCodec` 静默丢弃口径**在这批字段上取消**：解不出来的元素让整份定义加载失败。`ResourceLedger` 现在只接已经求值好的金额（零引用），`ResourceTransactions` 只负责"先全判后全写"。
